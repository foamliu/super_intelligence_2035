# 长上下文 ABF 准备方案（BaiZe-2B · 2026-10-26）

> 用户令：**长上下文用 ABF，要为此做好准备。**
> 结论先行：训练主配方保持 **16K / θ=1e6（ABF）**；长上下文能力靠 **ABF 外推 + 可选序列阶梯扩展**；
> 产品目标 **32K–128K**，能力上限 **1M**（推理侧）。下面把「已就绪 / 必查 / 必须做」分清。

---

## 1. 为什么是 ABF（而不是裸抬 max_position / PI / YaRN）

本项目 2026-10-06 的 **B1 实验**（模型 `p5b/hf_iter_4771`，2.22B，20B token，训练 ctx=4K、θ=1e4）已实测三种做法：

| 做法 | 4K | 32K | 128K | 256K | 512K | 1M | 结论 |
|:--|--:|--:|--:|--:|--:|--:|:--|
| Baseline（θ=1e4, mp=4096） | 75.36 | 拒 | 拒 | 拒 | 拒 | 拒 | 训练长度上限 |
| **maxpos_only**（θ=1e4, mp=131072） | **NaN** | NaN | NaN | NaN | NaN | NaN | ❌ 全崩 |
| **ABF（θ=1e6, mp=1M）** | 83.24 | 58.55 | 53.34 | 52.99 | 55.81 | **55.42** | ✅ 全程稳定 |

- **只抬 `max_position_embeddings` 不改 `rope_theta` ⇒ cos/sin 高频溢出 ⇒ 全 NaN**（连 4K 都 NaN）。
- ABF 的代价是「**在已训练长度上**」轻微退化（4K：75.36 → 83.24，+10.5%），换来 ∞ 长度外推能力。
- **本计划从零训练、θ 一开始就是 1e6**，因此不存在「事后换 θ」的税（这一点与 B1 的设定不同，必须写清楚）。

**ABF 理论式**（Xiong et al. 2023 / CodeLlama）：

```
θ_ABF = θ_train × (L_target / L_train) ^ (d / (d-2))        # 本项目 d=head_dim=128 ⇒ 指数 1.0159
```

`python scripts/abf_plan.py` 会打印各目标的 θ_ABF 与对应 CP/DP/gbs。⚠️ 该式仅作**升级参考**；
本项目实测 θ=1e6 已覆盖 1M，**默认不抬 θ**，只在实测退化时按表升级（每次只动 θ，其余不变，重测）。

## 2. 训练侧：已就绪（本次落地）

| 项 | 值 / 位置 | 说明 |
|:--|:--|:--|
| `ROPE_THETA` | **1,000,000** | `configs/common.env`；`train.sh` 传 `--rotary-base 1000000` |
| `ROPE_MAX_POS` | **1,048,576** | 只在**导出** config 生效；由 `check_rope.py` 卡口 |
| `ROPE_SCALING` | 空 | 训练期不启 PI/NTk/YaRN |
| 训练序列 | **16,384**（S1/S2） | 16K 是吞吐最优档（613,992 tok/s，CP1 DP16，graph OFF） |
| 扩展阶梯 | `configs/longctx_ladder.tsv` + `scripts/longctx_ladder.sh` | 32K→64K→128K，CP 2/4/8，**保持 tok/mb/GPU=16,384** |
| 校验 | `scripts/check_rope.py` | 56 层 / attention=4 / max_pos / θ / no scaling |

**阶梯配置（每级都维持 4.19M tok/step、accum=16，便于对比）**

| rung | seq | CP | DP | gbs | token 预算 | 步数 | 预估 tok/s | 预估墙钟 |
|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| 1 | 32K | 2 | 8 | 128 | 20 B | 4,769 | 351,526（实测） | ~15.8 h |
| 2 | 64K | 4 | 4 | 64 | 10 B | 2,385 | ~180K（外推） | ~15.4 h |
| 3 | 128K | 8 | 2 | 32 | 5 B | 1,193 | ~90K（外推） | ~15.4 h |

> 合计 ≈47 h / ≈750 GPU·h。**这是可选投资**：若产品只需 32K，只跑 rung1（~16h）即可。
> 32K 的 CP 开销是结构性的（#792：32K CP2 = 351,526 = 600K 的 59%），别指望长上下文还满速。

## 3. 数据侧：**必须先查**（否则长上下文训练是伪的）

`scripts/check_longctx_data.py` 按 EOD（**tokenizer_eod = 129280**）切分，统计「文档长度分布」：

```bash
python scripts/check_longctx_data.py \
  --shards "/nas_train/app.e0031982/datasets/baize-data/tokenized/Ultra-FineWeb/ultrafineweb_en_v1_4" \
  --eod-id 129280 --targets 32768,131072,1048576 --sample 8
```

**判据**（看 `token%` 而不是 `docs%`）：

| 目标 | 建议 token 占比 | 不达标怎么办 |
|:--|--:|:--|
| ≥32K | ≥20% | 长文档优先采样（按 doc 长度加权）/ 补书籍·论文·代码仓类长文源 |
| ≥128K | ≥5% | 同上；否则 128K 阶梯只学到「跨文档拼接」，收益虚高 |
| ≥1M | 通常 <1% | **正常**：1M 靠 ABF 外推，不靠长文档 |

> ⚠️ 现有 shard 是「文档连续拼接 + EOD 分隔」。若没有 **文档级 attention mask/重置**，长序列里会跨文档串味；
> 这属于训练框架能力（需 launcher 支持 doc-level reset）。没有它时，长上下文收益会被高估 —— 必须在报告里标注。

## 4. 评测侧：必须做的矩阵（复用既有脚本）

`run/baize_b1_longctx_extend.py`（已在库）支持 ABF 变体与 4K→1M 的 PPL/passkey/prefill/显存测试，
可直接对新的 HF ckpt 重跑（改 `CONFIGS` 里的 ckpt 路径即可）。

| 维度 | 测什么 | 门限 |
|:--|:--|:--|
| PPL vs ctx | 4K/8K/16K/32K/64K/128K/256K/512K/1M | 相对上一级抬升 ≤5%；1M ≤ baseline 4K 的 1.10×（B1 实测 55.42 vs 83.24 属正常下降） |
| Passkey | 4K / 8K / 32K / 128K | ≥95%（B1 老 ckpt 是 0%，属未训练长上下文，作为对照基线） |
| 下游退化 | CS8（8 集平均）在扩展前后 | 退化 ≤1pp |
| 成本 | prefill 时间 / 峰值显存 | 1M ≈172s / 34.7GB（B1 实测，单卡）→ 产品侧需评估 |

## 5. 决策树（什么时候抬 θ）

```
长上下文评测（当前 θ=1e6）
├─ 32K/128K PPL 抬升 ≤5% 且 passkey ≥95%
│   └─ ✅ 保持 θ=1e6，不抬（默认路径：省事、免再训）
└─ 某长度 PPL 抬升 >5% 或 passkey 掉点
    ├─ 只抬 θ（1e6 → 5e6）：用 abf_plan.py 的 θ_ABF 附近取值，**只改这一个变量**
    ├─ 短序列（16K）PPL 复核：退化 ≤1% 才接受
    └─ 仍不达标 ⇒ 该长度改为「阶梯续训」（longctx_ladder.sh 增加对应 rung）
```

## 7. 风险登记

| 风险 | 影响 | 处置 |
|:--|:--|:--|
| 只抬 max_pos | 全 NaN | 已用硬门禁 + 配置成对约束 + 报告红线拦死 |
