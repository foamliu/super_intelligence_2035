0. 概况与术语体系

Claude Code 是 Anthropic 官方「终端里的 agent」。技术栈（package.json / README.md）：TypeScript + Bun 运行时，React + Ink（React 渲染 CLI）做 TUI，Commander.js 解析 CLI，Zod v4 校验，ripgrep 做代码搜索，MCP SDK / LSP 接协议，OpenTelemetry + gRPC 遥测，GrowthBook 做 feature flag。核心引擎是两个大文件：QueryEngine.ts（1,295 行，Anthropic API 调用 / 流式 / 工具循环 / 重试）与 query.ts（query loop，68KB）。

它给自己建立的术语体系，本质是把「持久的事实源」与「要注入模型的投影片段」严格分离：

术语含义证据
SystemCompactBoundaryMessage压缩点插入的 type:'system', subtype:'compact_boundary' 标记，带 compactMetadata{trigger,preTokens,userContext,messagesSummarized} 与 logicalParentUuid（链回压缩前最后一条消息）。utils/messages.ts:4530-4555
SystemMicrocompactBoundaryMessage「微压缩」标记（清掉旧工具结果/附件），带 microcompactMetadata{tokensSaved,compactedToolIds,…}。utils/messages.ts:4557-4583
Transcript（JSONL）append-only 的会话事实源，每个 session 一个 .jsonl，完整历史永不删除；模型可见视图从它「投影」出来。utils/sessionStorage.ts（parseJSONL / getTranscriptPath）

⚠️ 任务书 5 条线用的是 cline 旧 vscode 架构名（ContextPipelinePrepareTurn / EditType·ContextUpdate / 时间戳截断 / Focus Chain / context-window-utils.ts）。claude-code 是完全不同的代码库，内核同构但形态不同：预处理 = getSystemPrompt+getUserContext+getSystemContext（memoize 前置注入）+ normalizeMessagesForAPI（投影）；无损编辑 = append-only JSONL + boundary 切片（非 EditMap）；Focus Chain = TodoWrite + Session Memory。本报告逐线给「旧→新」对照。

2. 线1 — 上下文注入与「投影」管线

① 它解决什么问题

每次请求发给模型前，要把「系统提示 / 环境上下文 / 用户配置（CLAUDE.md）/ git 状态」注入进去。claude-code 没有 cline 那种单一 ContextPipelinePrepareTurn 拦截器，而是把「上下文装配」拆成 多个 memoize 的纯函数 + 一个「消息投影」函数。

② 怎么实现（贴原文）

注入分三块，装配在 REPL 的 query loop 里 Promise.all 并行拉取：

// screens/REPL.tsx:2535
const [defaultSystemPrompt, userContext, systemContext] = await Promise.all([
  getSystemPrompt(toolUseContext.options.tools, mainLoopModel, ...),
  getUserContext(), getSystemContext(),
])

系统上下文（git 状态快照）+ 用户上下文（CLAUDE.md）都是 memoize 的、会话内只算一次：

// context.ts:113-115  ← getSystemContext / getUserContext 的注释
/** This context is prepended to each conversation, and cached for the
 *  duration of the conversation. */
export const getSystemContext = memoize(async () => { ... })   // :116
export const getUserContext  = memoize(async () => { ... })   // :155
// getUserContext 返回 { claudeMd, currentDate: `Today's date is ${getLocalISODate()}.` }  :184-187

系统提示主体在 constants/prompts.ts:444 的 getSystemPrompt(tools, model, mcpClients)（914 行文件），根据 model / tools / skills / env 动态拼装；getSystemContext 里 git 状态被截断到 2k 字符：

// context.ts:20, 85-89
const MAX_STATUS_CHARS = 2000
const truncatedStatus = status.length > MAX_STATUS_CHARS
  ? status.substring(0, MAX_STATUS_CHARS) + '\n... (truncated because it exceeds 2k characters...)' : status

③ 数据流图

getSystemPrompt(tools,model,mcp) ─┐ getUserContext() (CLAUDE.md, date) ─┼─▶ Promise.all ─▶ prepend 到消息头 getSystemContext() (git status, cacheBreaker) ─┘ │ 完整 messages（含 system meta / 完整历史 / snip 标签） → getMessagesAfterCompactBoundary()（切片，去 pre-compact） → (HISTORY_SNIP 时) projectSnippedView()（过滤 snipped 消息） → normalizeMessagesForAPI()（滤掉 system meta 消息 → API 参数） ←「投影」终点

④ 代价与边界

  • 「无损投影」的 claude-code 版 = 完整 transcript（事实源）vs 模型投影视图，而非 cline 的「逐消息 EditMap」。边界消息、api_error、snip 标签等 type:'system' meta 消息在 normalizeMessagesForAPI 被滤掉，但它们仍留在内存/盘上（UI 滚动回看不丢）。
  • 代价：注入是「按会话 memoize」的，意味着 getUserContext / getSystemContext 一旦算出就不再随会话演进而更新（git status 写死「snapshot in time, will not update」）。需要强制刷新得手动 .cache.clear()（见 commands/clear/caches.ts:52-53）。
  • systemPromptInjection（cache breaker）是 ant-only 调试态，靠改注入就 clear() 缓存来破坏 prompt cache（context.ts:29-34）。

⑤ 我的判断

claude-code 把「上下文注入」实现成函数式、可缓存、可并行的装配，而非一个处处拦截的中间件管线。这更简单直接，但也意味着没有单一可挂载的「prepareTurn」节点——这与线3「能否插件化拦截底层管线」直接相关（见 §4）。

3. 线2 — 检查点与「boundary 切片」式恢复

① 它解决什么问题

压缩后如何「回滚 / 恢复」到压缩前？claude-code 的答案不是时间戳截断（cline），也不是事件重放（deepseek），而是：append-only transcript + 一条 in-band 的 boundary 标记 + 「切片」投影。

② 怎么实现（贴原文）

边界消息是「写进 transcript 里的检查点标记」，并带 logicalParentUuid 链回压缩前最后一条消息：

// utils/messages.ts:4530-4555
export function createCompactBoundaryMessage(trigger, preTokens, lastPreCompactMessageUuid, userContext, messagesSummarized) {
  return { type:'system', subtype:'compact_boundary', content:`Conversation compacted`,
    timestamp, uuid, level:'info',
    compactMetadata:{ trigger, preTokens, userContext, messagesSummarized },
    ...(lastPreCompactMessageUuid && { logicalParentUuid: lastPreCompactMessageUuid }),
  }
}

压缩结果 & 压缩后消息的固定顺序（boundary → summary → keep → attachments → hookResults）：

// services/compact/compact.ts:299-310, 330-338
export interface CompactionResult {
  boundaryMarker: SystemMessage
  summaryMessages: UserMessage[]
  attachments: AttachmentMessage[]
  hookResults: HookResultMessage[]
  messagesToKeep?: Message[]
  ...
}
export function buildPostCompactMessages(r) {
  return [r.boundaryMarker, ...r.summaryMessages, ...(r.messagesToKeep ?? []), ...r.attachments, ...r.hookResults]
}

「投影 / 恢复」= 找最近一个 boundary，从它往后切（pre-compact 消息留盘、不进模型侧）：

// utils/messages.ts:4618-4643
export function findLastCompactBoundaryIndex(messages) { /* 从后往前扫，返回最近 boundary 下标 */ }
export function getMessagesAfterCompactBoundary(messages, options?) {
  const boundaryIndex = findLastCompactBoundaryIndex(messages)
  const sliced = boundaryIndex === -1 ? messages : messages.slice(boundaryIndex)
  if (!options?.includeSnipped && feature('HISTORY_SNIP'))   // 再叠加 snip 投影
    return projectSnippedView(sliced)
  return sliced
}

盘上持久化的「跳过 pre-compact」阈值（resume 用）：

// utils/sessionStoragePortable.ts:480
export const SKIP_PRECOMPACT_THRESHOLD = 5 * 1024 * 1024   // 读取 transcript 时据此跳过 pre-compact 段

partial compact 的「保留段重链接」元数据（边界消息上再挂 preservedSegment{headUuid,anchorUuid,tailUuid}）：

// services/compact/compact.ts:349-367
export function annotateBoundaryWithPreservedSegment(boundary, anchorUuid, messagesToKeep) {
  ...  return {...boundary, compactMetadata:{...boundary.compactMetadata,
    preservedSegment:{ headUuid: keep[0].uuid, anchorUuid, tailUuid: keep.at(-1).uuid }}}
}

③ 数据流图

append-only transcript (.jsonl) └─ 压缩时：executePreCompactHooks → forked agent 生成摘要 → createCompactBoundaryMessage(+logicalParentUuid) → buildPostCompactMessages([boundary, summary, keep, attachments, hookResults]) 写回 transcript └─ 恢复/发请求：readTranscriptForLoad（SKIP_PRECOMPACT_THRESHOLD 跳过 pre-compact） → getMessagesAfterCompactBoundary（slice(boundaryIndex)）→ normalizeMessagesForAPI → API

④ 代价与边界

  • 「非破坏」体现在：pre-compact 消息从不删除，只靠 boundary 标记 + 切片把它从模型视图里「摘出」。UI 滚动回看仍能见到完整历史。
  • 「回滚」语义弱：测得 .ts 里没有 uncompact/revert/rollback 这类用户态 API（grep 命中仅 RecompactionInfo 诊断字段、uncompacted 形容词）。回滚靠的是「换 boundary 重新切片」这个投影层动作，而非显式 undo。
  • 与 cline「PR #12747 专门修 compaction sidecar 可靠性」对照：claude-code 的「sidecar」就是这条 in-band boundary 消息本身（存在 transcript 里），没有独立的 sidecar 文件，因此不会出现「sidecar 丢而 transcript 在」的裂脑问题——但也意味着 boundary 一旦没写进 transcript，恢复就没有独立抓手。

⑤ 我的判断

claude-code 的检查点模型是「单事实源 + 切片投影」：事实源是 append-only JSONL，boundary 是写进源里的锚，视图靠切片产生。优点：无 sidecar 一致性负担、历史天然可回看；代价：无用户态回滚、pre-compact 段长期占盘（靠 SKIP_PRECOMPACT_THRESHOLD 只做读时跳过，不做物理裁剪）。这与 codex 的「WorldState Diff / AutoCompactWindow sidecar」、deepseek 的「重放即回滚」各是一条独立技术路线。

4. 线3 — Hook / 插件 / Skill（扩展边界）

① 它解决什么问题

把「上下文调控能力」开放给外部。claude-code 的答案是三件套：Hook（事件级拦截）+ 插件（Hook/MCP/Skill 打包分发）+ Skill（可复用工作流）。

② 怎么实现（贴原文）

Hook 事件全集（27 个，比 cline 的 beforeRun/afterRun/beforeTool 宽得多，且有 PreCompact/PostCompact）：

// entrypoints/sdk/coreTypes.ts:25-53
export const HOOK_EVENTS = [
  'PreToolUse','PostToolUse','PostToolUseFailure','Notification','UserPromptSubmit',
  'SessionStart','SessionEnd','Stop','StopFailure','SubagentStart','SubagentStop',
  'PreCompact','PostCompact',
  'PermissionRequest','PermissionDenied','Setup','TeammateIdle','TaskCreated','TaskCompleted',
  'Elicitation','ElicitationResult','ConfigChange','WorktreeCreate','WorktreeRemove',
  'InstructionsLoaded','CwdChanged','FileChanged',
] as const

Hook 有 4 种执行形态（command / prompt / http / agent），且每个带 if 权限式匹配与 once/async/asyncRewake：

// schemas/hooks.ts:194-213 Hook 配置 = Partial<Record<HookEvent, HookMatcher[]>>

压缩路径上 Hook 确实被调用（PreCompact 注入自定义指令）：

插件 = manifest + hooks + mcpServers + skills 的打包单位：

③ 数据流图

Hook 触发点（QueryEngine/query loop / toolExecution / compact.ts / sessionStart） → 匹配 hook 配置 (Partial<Record<HookEvent, HookMatcher[]>>，if 权限规则过滤) → 执行 command / prompt(llm) / http / agent(子agent) 四类 hook → 结果：PreToolUse 可拦/改参数，PostToolUse 可读结果，PreCompact 可注入 customInstructions， hookResult 作为 HookResultMessage 进 transcript

④ 代价与边界

  • 核心问题（Auto Compact 可否插件化实现？）—— 答：部分可。Hook 能拦截到 PreCompact/PostCompact 节点、注入自定义指令（mergeHookInstructions），但不能替换压缩引擎本身：摘要生成走的是 compactConversation → getCompactPrompt → streamCompactSummary（forked agent）这条硬编码在 services/compact/ 核心的路径，PreCompact hook 只能在它前面「加指令 / 加副作用」，拦不住也不替换总结动作。
  • 扩展边界结论：硬编码在核心的 = 压缩引擎、token 预算/阈值、forked-agent 总结、prompt-cache 管理；留给生态的 = 事件级 Hook（含 PreCompact/PostCompact）、插件打包的 MCP server / Skill、权限决策旁路。压缩策略本身不做成插件，与 deepseek-harness「压缩以插件形态实现但不开放给第三方」形成两种取向。
  • 代价：Hook 是进程外 command / 额外 LLM 调用（prompt/agent 类）——每次触发都有 spawn/roundtrip 开销；once/async/asyncRewake 引入并发与「唤醒模型」复杂度。

⑤ 我的判断

claude-code 的 Hook 粒度（27 事件 × 4 形态 × if 匹配）是四个 harness 里最细、最像「可编程操作系统」的，尤其 PreCompact/PostCompact 直击本任务主题。但它的「压缩」本体仍是核心硬编码，生态拿到的只是压缩「前后」的插入点，而非「中间」的替换点。

5. 线4 — Todo / Session Memory 任务状态跨压缩存活

① 它解决什么问题

压缩只收「对话说了什么」，而「接下来要做什么」「长期该记住什么」必须跨压缩存活。claude-code 用三条旁路把短期记忆（对话）与长期目标（todo / memory）解耦。

② 怎么实现（贴原文）

① TodoWriteTool（V1）—— todo 存在 AppState，按 agent/session 键控，不进消息流：

// tools/TodoWriteTool/TodoWriteTool.ts:65-94
async call({ todos }, context) {
  const appState = context.getAppState()
  const todoKey = context.agentId ?? getSessionId()
  const oldTodos = appState.todos[todoKey] ?? []
  ...
  context.setAppState(prev => ({ ...prev, todos: { ...prev.todos, [todoKey]: newTodos } }))
}

② Todo V2 —— 落盘到 ~/.claude/tasks/<taskListId>/（taskListId = 团队名/leaderTeamName/sessionId），是可直接跨 session 运行的 task 清单：

// utils/tasks.ts:199-224

  if (process.env.CLAUDE_CODE_TASK_LIST_ID) return process.env.CLAUDE_CODE_TASK_LIST_ID
  const teammateCtx = getTeammateContext(); if (teammateCtx) return teammateCtx.teamName
  return getTeamName() || leaderTeamName || getSessionId()
}
export function getTasksDir(taskListId) { return join(getClaudeConfigHomeDir(), 'tasks', ...) }

③ Session Memory / auto-memory —— 后台 subagent 周期抽取「本会话要点」写独立 markdown：

// services/SessionMemory/sessionMemory.ts:1-6
/** Session Memory automatically maintains a markdown file with notes about the
 *  current conversation. It runs periodically in the background using a forked
 *  subagent to extract key information without interrupting the main conversation flow. */
// services/extractMemories/extractMemories.ts:1-6
/** Extracts durable memories ... writes them to the auto-memory directory
 *  (~/.claude/projects/<path>/memory/). ... runs once at the end of each complete query loop */

③ 数据流图

对话 (messages) ──压缩──▶ boundary + 摘要 （被压缩 = 「收」） todo V1 → appState.todos[todoKey]（内存，会话内） V2 → ~/.claude/tasks/<id>/*.json（磁盘，跨会话/跨 teammate） memory → ~/.claude/projects/<path>/session-memory/*.md（forked subagent 抽） ~/.claude/projects/<path>/memory/*.md（end-of-loop 抽） （↑ 三者都不在消息流里，压缩/切片碰不到它们）

④ 代价与边界

  • 状态归属对照：可被压缩 = 对话消息（transcript pre-compact 段）；不可被压缩 = todo 清单（AppState / tasks 盘）、session-memory / auto-memory（独立 md）、plan（utils/plans.ts 的 getPlanFilePath）。
  • 代价：V1 的 appState.todos 是纯内存 React 状态，重启即丢（除非走 V2 落盘）。V1/V2 靠 isTodoV2Enabled() 切换，存在两套并存的分裂。
  • Session Memory / auto-memory 用 forked subagent（复用父会话 prompt cache）跑，是「用 token 换长期记忆」——每轮 loop 末或周期性的额外 LLM 调用。

⑤ 我的判断

claude-code 的「长期目标解耦」是三套机制叠加（todo / session-memory / auto-memory），比 cline 的 Focus Chain（当前多 stub）更落地，但因为机制多、且 V1/V2 并存，「状态到底存哪」没有一个唯一答案——这是它相对 opencode「一张 SQL 表」最不「干净」的地方。

6. 线5 — 模型能力适配与 token 计数策略

① 它解决什么问题

Auto Compact 的触发依赖「当前上下文用了多少 token」与「模型窗口多大」。claude-code 的计数策略与 cline（3 字符/token、默认 128K）显著不同。

② 怎么实现（贴原文）

窗口默认 200K 而非 128K，且支持 [1m] 后缀 / capability / beta 多级解析：

// utils/context.ts:9, 51-98
export const MODEL_CONTEXT_WINDOW_DEFAULT = 200_000
export function getContextWindowForModel(model, betas?) {
  if (has1mContext(model)) return 1_000_000          // [1m] 后缀
  const cap = getModelCapability(model)               // 能力表 max_input_tokens
  if (cap?.max_input_tokens && cap.max_input_tokens >= 100_000) return ...cap.max_input_tokens
  ...
  return MODEL_CONTEXT_WINDOW_DEFAULT           // 兜底 200_000
}

「规范」计数 = 上次 API 响应的 usage + 新消息的粗略估算（不是纯字符）：

// utils/tokens.ts:226-261 tokenCountWithEstimation
// = getTokenCountFromUsage(usage) + roughTokenCountEstimationForMessages(messages.slice(i+1))
//   getTokenCountFromUsage = input + cache_creation + cache_read + output  (tokens.ts:46-53)

粗略估算默认 4 字符/token（比 cline 的 3 更保守），JSON 修正为 2：

// services/tokenEstimation.ts:203-224
export function roughTokenCountEstimation(content, bytesPerToken = 4) {
  return Math.round(content.length / bytesPerToken)
}
export function bytesPerTokenForFileType(fileExtension) {
  switch (fileExtension) { case 'json': case 'jsonl': case 'jsonc': return 2; default: return 4 }
}

另有「精确」API 计数（countTokens）+ Bedrock 回退；附图/文档固定按 2000 token 保守估（tokenEstimation.ts:400-411：matches microCompact's IMAGE_MAX_TOKEN_SIZE）。

压缩阈值 = 有效窗口 − 20k 摘要输出预留 − 13k 缓冲，且带熔断：

③ 数据流图

getContextWindowForModel(model,betas) ─▶ 有效窗口 = 窗口 − min(maxOutput, 20k) ─▶ 阈值 = 有效窗口 − 13k tokenCountWithEstimation(messages) ─▶ ≥ 阈值 且 未熔断/未禁用 ─▶ autoCompact └ 否则：warning/error/blocking 分级提示（calculateTokenWarningState）

④ 代价与边界

  • provider 适配清单：Bedrock 无 countTokens → countTokensWithBedrock + 需要 foundation/backing model 解析；Vertex 要过滤不支持的 beta（VERTEX_COUNT_TOKENS_ALLOWED_BETAS，见 tokenEstimation.ts:167-170）；1M 上下文按 [1m] 后缀 / capability / beta header 三级判定，HIPAA 可 CLAUDE_CODE_DISABLE_1M_CONTEXT 关闭。
  • 「4 字符/token」是低估风险的修正方向：注释明说 «an underestimate can let an oversized tool result slip into the conversation»（tokenEstimation.ts:230-232），且对 JSON/图/文档做专门修正，避免「压缩触发太晚」。
  • 代价：计数依赖「上次 API 响应的 usage 存在」，并行工具调用会把同一消息 id 拆成多条 assistant 记录，tokenCountWithEstimation 必须回走到同一 message.id 的首条兄弟记录，否则漏算交错 tool_result（tokens.ts:214-224 注释详解）——这是它比 cline「字符估算」复杂的地方。

⑤ 我的判断

对照任务书 line5 的「Issue #7772（llama-server 窗口无法自动检测、默认按 128K 导致 131K 模型算错）」，claude-code 没有那个具体问题——它默认 200K 且走 capability/beta 多级 getContextWindowForModel。但它引入的新权衡是「usage+粗略双轨计数」的复杂度：精确但依赖 API 回执，估算则靠「4 字符/token」保守兜底。这是四个 harness 里最「工程化」的计数策略（精确 API 路径 + 有损估算路径 + Bedrock/Vertex 分支 + 熔断），也是最重的。
