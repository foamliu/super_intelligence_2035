## **三、自进化治本重构（本周最大突破）**

### **问题：L1 注入治本前净负**

V5\+evo·0719 串行重评发现 L1 注入净\-5题，与并发评估时的"\+1\.9pp 有益"结论矛盾。根因：L1 的 `[已验证]` 知识含 agent 自测推断（非代码真用 API），注入后误导 agent。

### **治本四改（commit 23ed5ff）**

|改动|位置|作用|
|---|---|---|
|**三态 status 系统**|reflection\.py / update\.py|verified/unverified/None 三态，区分确证 vs 推断|
|**used\_apis 真值锚定**|reflection\.py|`[已验证]` 只标代码真用的 API（used\_apis），非查了没用的 apis\[0\]|
|**ground\-truth 守卫**|update\.py|无 ground\-truth 不标 `[已验证]`；trace\-inferred success 用 GT enrichment 纠正（40 假阳性）|
|**读端 tiering**|format\_eval\_task\.py|注入按 status 分层，verified 优先填预算|

### **效果：治本后转正**

V5 baseline（裸跑无L1）74\.7% → V5\+evo（L1注入治本后）85\.4%，**净\+17题（gained20/lost3）**，真代码问题 35→16（\-54%），AssertionError 25→16（\-36%）。L1 注入机制有效，前提是知识精准。

## **五、MCP 请求超时根因破解（本周第二大突破）**

### **现象**

agent trace 大量 `MCP error -32001: Request timed out`，跨 V5/V5\+evo 稳定重现：

- V5 baseline：163 次，57 个 task

- V5\+evo：50 次，18 个 task

\- **100% 来自 run\_pyAether\_code\_tool**，其他工具零超时

- agent 端耗时全部精确 60\.0s

### **根因：两层 60s 叠加的复合超时**

\- **客户端 60s**：`@modelcontextprotocol/sdk` 的 `DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`，Cline 调 callTool 不传 options\.timeout，吃默认值

\- **server 沙箱 60s**：`.env SANDBOX_TIMEOUT=60`，沙箱慢时跑满 60s

\- **Semaphore 排队**：V5 加的串行锁（`RUN_CODE_MAX_CONCURRENT=1`），\-p4 下 4 worker 并发只放 1 个进沙箱，25% 请求排队≥30s

复合机制：排队 50s \+ 沙箱执行 15s = server 总 65s \> 客户端 60s → 客户端先报 \-32001。

### **★决定性单变量铁证**

用户存的 `2026_0718_221543` = V5 代码 \+ **无 Semaphore** \+ \-p4。与 \`2026\_0720\_020432\`（同 V5 代码 \+ 有 Semaphore \+ \-p4）唯一差=Semaphore。串行评估对照：

||0718无锁|0720有锁|变化|
|---|---|---|---|
|整体 pass 率|84\.8%|74\.7%|**\-10\.1pp**|
|timeout task pass 率|84\.9%|66\.7%|\-18\.2pp|
|timeout 拖累|\-0\.1pp（无）|\+12\.5pp|—|

**Semaphore 一个变量造成 \-10\.1pp 回归**。破解了"老版本 V5 甩现在一大截""agent 更勤奋"的历史谜团——真因是无锁时 run\_code 不 timeout，agent 每次拿到沙箱真反馈能真迭代；有锁的"更勤奋"（调用数多）实为 timeout 逼出的无效重试。

### **客户端超时配置调研（四条路三堵一通）**

|方案|结论|原因|
|---|---|---|
|`cline_mcp_settings.json` 加 timeout 字段|无效|字段被读但流向 run 级超时，不进 SDK callTool|
|改 SDK 默认值|✅**有效**|业务代码运行时从 node\_modules 加载（非内联进 ELF）|
|`MCP_REQUEST_TIMEOUT_MS` env|无效|SDK 1\.29\.0 不读 env|
|progress reset|无效|Cline 不传 resetTimeoutOnProgress:true|

### **落地：SDK 超时改 60000→300000**

精准只改一个常量值（4 处：esm/cjs 各 \.js \+ \.d\.ts），不动其他代码。已验证 node import 运行时读到 300000。沙箱侧 `SANDBOX_TIMEOUT=60` 保留（94% 执行\<60s，撞线 6% 是真死代码）。`npm install -g cline` 会覆盖，需重改（路径记记忆）。

## **十一、关键洞察**

1\. **不精准的知识比无知识更糟**：L1 治本前含 agent 推断，系统性误导（093 铁证）；治本后只沉淀代码真用 API，转净\+17题

2\. **validator 提醒位置 = 有效性的关键**：agent 被训练看 print\_log 不看 response，提醒放对位置（print\_log）才有效（task\-143 解决）

3\. **"救回率"算法陷阱**：收提醒题 pass 率 ≠ 救回率，要扣掉本就 pass 的题（76\.9% → 净\+4）

4\. **Semaphore 治抖动有代价**：\-10\.1pp 单变量回归，比它治的抖动更大；解法是拉高客户端超时而非去锁

5\. **串行评估是归因前提**：并发评估含 ±4\~16pp 抖动，所有 pass 率结论必须串行重评

6\. **两种机制效果相当**：validator\+E6（裸跑）≈ L1 注入，叠加正向（V5\.1\+evo 87\.3%）

7\. **业务代码运行时加载 node\_modules**：Cline 是 bun 编译 ELF，但 @cline/core \+ SDK 是运行时加载的可改 JS（非内联），改 SDK 默认值有效

8\. **agent 不知 task\_name**：task\_id 不注入 prompt，agent 用函数名当文件名——prompt 指令要用 func\_name
