2Reflexion —— 反思是奖励信号的"语义放大"

Reflexion: Language Agents with Verbal Reinforcement Learning

NeurIPS 2023
作者 Shinn et al. · arXiv 2303.11366v4 · 19 页 · logs/papers/2303.11366v4_Reflexion_Shinn2023_NeurIPS.pdf

① 核心机制（原文）

Reflexion 的 Self-Reflection 模型 Msr 输入是 {轨迹 τ, 奖励 r}，反思是对奖励 r 的语义放大（amplify）——不是凭空生成文本，必须锚定在评估器信号上。

to amplify r0 to a feedback form that can be used for improvement by an LLM, the Self-Reflection model analyzes the set of {τ0, r0} … for trial t. [§2, p.4]
协同结论（Table 3）—— 可靠评估信号是反思有效的前提：在 HumanEval Rust 50 道最难题上（GPT-4）：
  • 无测试 + 无反思（baseline）= 0.60
  • 有测试 + 无反思 = 0.52（更差——agent 无法判断对错，“performing harmful edits” 做有害编辑）
  • 无测试 + 有反思 = 0.60（不提升）
  • 有测试 + 有反思（完整 Reflexion）= 0.68
教训：没有可靠反馈信号时，反思非但无效还诱导有害编辑。这直接规定了我们反思函数的设计前提。
Table 3（从 PDF p.8 扣出）：Pass@1 on HumanEval Rust 50 hardest —— “Test generation omission”（无测试自评）降到 0.52，证明无可靠信号时反思有害。

② 我们吸取了什么

机制借鉴：反思必须锚定奖励信号。我们的四个 reflect_on_* 反思函数现均已带 success 参数并锚定 ground-truth 信号——success=True 时短路返回 None（docstring：“a passed task's errors are not failure signals”）。早期版本“无 success 参数”的记录已过时纠正。
已废弃：retry 闭环。Reflexion 的“重试拿真实反馈”闭环在 pass@1 场景下=作弊（重试暴露真实测试反馈），已废弃（详见 reflexion-deprecated）。但论文的反思 + 记忆 + Evaluator 机制在离线 L1 沉淀场景仍适用——这正是我们保留的部分。

3ExpeL —— 未治理的经验知识会反向伤害

ExpeL: LLM Agents Are Learners Through Self-Experiences

AAAI 2024
作者 Zhao et al. (Tsinghua) · arXiv 2308.10144v3 · 38 页 · logs/papers/2308.10144v3_ExpeL_Zhao2024_AAAI.pdf

① 核心机制（原文）

ExpeL 在 HotpotQA/ALFWorld/FEVER 上用 Reflexion 收集经验→抽抽象 insight→注入下游 unseen task。与我们 L1 机制最同构（跨任务经验→抽象→注入）。train 反馈是 success/fail 二元无标答，与我们 pass/fail + error_log 同构。

★关键实证（Table 3）——“未治理的经验反向伤害”铁证：在 HotpotQA 上，insight 提取阶段加入 reflections 反而降分：
  • ReAct baseline = 28.0 ± 1.4
  • hand-crafted insights = 32.0 ± 1.1
  • insights + reflections = 29.0 ± 0.4（低于 hand-crafted，reflections 反而伤害）
  • ExpeL（无 reflections）= 39.0 ± 1.7
原文：“adding reflections to the insight-generating process hurt performance”，原因是 “reflections sometimes outputting hallucinations, therefore misleading the insight extraction stage”。
Figure 6（从 PDF p.9 扣出）：Effects of Experience on Performance —— success/failure 多样性对比 > 单纯多成功轨迹。“diversity of success/failure data gathered using Reflexion was superior to using ReAct only”。

insight 治理很弱：仅 ADD/EDIT/UPVOTE/DOWNVOTE + importance count（UPVOTE+1 / DOWNVOTE−1，归零删除），无 GT 校验、无分级、无 disconfirm 门控。原文承认 “successful trajectories can be suboptimal and mislead the generated insights” 但只用投票应对。

② 我们吸取了什么

机制借鉴 1（Fig 6）：反例比正例信息量大。ExpeL 证明 success/failure 多样性 > 纯成功数量。这支撑我们用 disconfirm（反例计数）而非纯 source_count（成功计数）做 L1 排序——反例比正例更能识别误导知识。
机制借鉴 2（Table 3）：治理而非积累。ExpeL 加 reflections 反而降分，是“未治理经验反向伤害”的论文级铁证。这印证了我们 093 治本前净负、V5.3 净-4 题的根因——我们的 GT 校验 + 分级 + disconfirm 门控是对 ExpeL 治理弱点的直接改进，且有实证支撑治理必要性。
设定差异（非借鉴）：with-retention vs without-retention。ExpeL 选“复用具体成功解”（train/test 分开，复用相似轨迹=真迁移）；我们选 without-retention 只复用抽象 L1 不复用解（复用具体解=查表，污染自进化叙事）。我们比 ExpeL 严——这是固定题集自进化设定驱动的设计差异，不是缺陷。

4Trace2Skill (NVIDIA) —— 与我们方向最同构的一篇

Trace2Skill: Verifier-Guided Skill Evolution for Long-Context EDA Agents

arXiv 2026 (NVIDIA)
作者 Du & Pinckney (NVIDIA) · arXiv 2605.21810v1 · 17 页 · logs/papers/2605.21810v1_Trace2Skill_Du2026_NVIDIA.pdf

这是与我们最同构的一篇——同样“黑盒 verifier 二元判定 + agent 看不到答案 + 把 skill 当进化对象”，但三个关键机制方向相反（见 §9）。

① 核心机制（原文）

三关键设计：
  • 无 train/test，task-wise（§4.2）：“not a train/test generalization experiment … shared skills transfer unreliably”，每题独立进化。动机：“hard CVDP tasks are heterogeneous … motivating task-wise evolution”。
  • 隐藏 verifier 二元 pass/fail，但对硬失败太 sparse（§2.1）：p_r ∈ {0,1}。判定对单次提交确定，对 rollout 随机（temp 0.2），故用 repeats + LCB 治 agent 侧方差。
  • agent 看不到答案，sanitized 黑盒反馈（§2.1/A4）：verify_feedback 返回 sanitized pass/fail + partial test count + failure phase + next-focus hint，“enough to guide the next RTL edit, not enough to reveal the answer”。
Figure 1（从 PDF p.2 扣出）：Trace2Skill end-to-end flow —— oracle–mutator–selector 循环，从 rollout trace 蒸馏 skill。
核心结果（Table 1）：C1→C4 消融，8 道零基线硬题：
  • C1（seed skill，sparse verifier）= 0/8
  • C2（+ dense feedback）= 2/8 (12.5%) —— dense 反馈单独效果有限
  • C3（+ EA sparse）= 3/8
  • C4（+ EA + dense）= 6/8 (33.6%) —— dense 反馈耦合 skill 进化才放大
机制叫 skill-agent coadaptation：dense 反馈塑形 rollout 行为 → 产生的 trace 给 oracle/mutator 更清晰教训 → 下一代 skill 更好。每 EA 配置 640 rollout（8×5×4×4）。
度量三件套（最有借鉴价值）：
  • AgentProgressQ（rollout 执行质量）+ LCB（式 6）：F_LCB = max(0, F̄_progress − 1.96σ/√R)，“reduces the chance that a single lucky rollout dominates selection”。
  • SkillQ（skill 文本质量，带 M_keep 保留门防丢关键 lesson）。
  • SelectQ = pass@1 + ε·U（ε=0.49/max(R,N)）→ pass-dominant：“one additional hidden-verifier pass always outweighs dense tie-breakers”，无效/语义退化→−1。
校准（§3.2）：96 baseline rollout 上 AgentQ vs 稀疏 pass/fail 点二列相关 r=0.90、AUC=0.982。
Figure 2（从 PDF p.4 扣出）：AgentQ proxy on 96 baseline rollouts —— verifier fail 组 mean=0.410，verifier pass 组 mean=0.915，r=0.90。代理指标与真实 pass/fail 高度相关，可作 EA tie-breaker。

② 我们吸取了什么

借鉴 1：LCB 进评估统计。我们固定题集 without-retention 自进化，每题 k 次 rollout 取均值时用 LCB mean − 1.96σ/√R，惩罚单次好运（“靠一次满分拉高的序列 LCB 被压低”），避免单次好运主导轮次判断。
借鉴 2：anti-leakage 判据可复用。论文只返回功能观测（pass/失败阶段/partial 数），不返回参考解/harness/源码。我们对照检查 validator 是否越界——目前 validator 只报 API 误用类型 + 修复建议，未泄答案，合规。
借鉴 3：SelectQ pass-dominant 排序原则。质量分只作同 pass 率下 tie-breaker，一次真 pass 永远优先，避免“干净但行为停滞”的 skill 留存。指导我们的 skill quality gate（MUSE refine / SkillOS 四维）的排序原则。

5SkillOpt —— held-out gate 是 P2-6 的成熟参照

SkillOpt: Text-Space Skill Optimization for Frozen Agents

arXiv 2026
作者 Yang et al. (Microsoft + SJTU + Tongji + Fudan) · arXiv 2605.23904v2 · 27 页 · logs/papers/2605.23904v2_SkillOpt_Yang2026_MS-SJTU.pdf
⚠️ 别和 SkillOS 混：SkillOpt（2605.23904，MS+SJTU）= 独立 optimizer 编辑单一 skill 文档 + held-out gate；SkillOS（2605.06614，UIUC+Google）= RL 学 curator + 4 维 judge。arXiv 号差一位极易混。

① 核心机制（原文）

skill = frozen agent 的外部状态，文本空间优化（p1-2）：target model 冻结，独立 optimizer model 从 rollout 证据提 add/delete/replace 编辑 skill 文档。部署产物 best_skill.md（300-2000 token）。
train/val/test 三分 + held-out gate（p4 Fig.2, p6 §3.5）：原文 “an edit is accepted only when it strictly improves a held-out validation score”。rejected-edit buffer = 负反馈（§3.5）：rejected edit 不丢，记进 epoch-local buffer（失败模式 + 导致的分数下降），后续 reflection 能看到避免重复。epoch-wise slow/meta update = 动量（§3.6），显式追踪 regressions。
Figure 2（从 PDF p.4 扣出）：SkillOpt pipeline —— frozen target model 跑 rollout → optimizer 提 bounded edit → held-out selection split 上 gate → accept/reject（rejected 进 buffer 作负反馈）。
关键实证：52 个 (model, benchmark, harness) cell 全胜或并列第一（p3）。把 Ni 版 Trace2Skill（2603.25158）当 baseline 之一且全赢（p7，p17 ref[9]），平均超 per-cell 最强 baseline +5.4pp。GPT-5.5 平均提升 no-skill +23.5pp。⚠️baseline 的是 Ni 版不是 NVIDIA 版（与我们最同构的 NVIDIA 版与 SkillOpt 无直接对比）。

② 我们吸取了什么

借鉴 1（承重）：P2-6 held-out gate 有了成熟参照。SkillOpt 的三分 + “只接受严格提升 val 的 edit”就是我们要做的 P2-6。它取代 SelectQ 代理——held-out 是真实行为指标，比质量分代理更硬。
借鉴 2：V5.3 净-4 题解法被 SkillOpt 验证。§3.5 原话 “plausible textual diagnoses can still hurt the actual target model” = V5.3 的 3 误导 case（看似合理 L1 实际伤害 agent）。SkillOpt 解法 = held-out gate 事后拒绝伤害性 edit；我们 Scope Boundary = 事前加适用边界。两种解法同源（防“合理但有害”知识），方向不同，可结合。
借鉴 3：负反馈利用。SkillOpt 的 rejected-edit buffer（edit 级）与我们 disconfirm（API 级反例计数）同向但更系统——它启发我们用反例而非纯正例做淘汰信号。

6SkillOS —— 4 维技能质量门（对齐 Fig.12）

SkillOS: A Skill-Centric Operating System for LLM Agents

arXiv 2026
作者 Ouyang et al. (UIUC + Google Cloud AI Research) · arXiv 2605.06614v1 · 33 页 · logs/papers/2605.06614v1_SkillOS_Ouyang2026_UIUC-Google.pdf

① 核心机制（原文）

curation 是学出来的，非预设规则。SkillOS 用 GRPO 训练可学习 Curator（冻结 Executor），“a trainable skill curator updates and manages this collection through [insert/update/delete] operations”。grouping（消融第一重要）：相关任务组内早期技能由后续任务成功率评估，把延迟反馈变可用。复合奖励 r_task + r_fc + r_cnt + r_comp。8B RL Curator > Gemini-2.5-Pro 直接 curation——Curator-Executor 对齐靠 RL 不靠堆模型。
Figure 1（从 PDF p.2 扣出）：SkillOS pairs a frozen Agent Executor with a trainable Skill Curator —— executor 检索 SkillRepo 执行，curator 按 insert/update/delete 编辑 repo。
4 维 judge（Figure 12）——我们质量门的直接来源：ABSTRACTION / REUSABILITY / ACTIONABILITY / FAITHFULNESS，产出连续 reward 喂 RL。insert→update 相位转移（训练涌现，非硬编码），技能内容从“泛泛 tips”演化到“failure-handling + conditional branches”。
Figure 12（从 PDF p.21 扣出）：external judge 给 skill 内容打分 r_cnt 的 prompt 模板——4 维评分的工程实现。

② 我们吸取了什么

机制借鉴：4 维技能质量门（对齐 Fig.12）。我们的质量门已对齐论文 Fig.12 的 ABSTRACTION/REUSABILITY/ACTIONABILITY/FAITHFULNESS，取代早期错配的 CORRECTNESS/COMPLETENESS/...（只 ACTIONABILITY 重合）。实测过拟合 skill（带具体 task 名 / design_42）ABSTRACTION=0.10 精准识别，旧维度抓不到。
设计差异（非 bug）：连续 reward vs 二元 gate。论文用 4 维产出连续 reward 喂 RL（formative）；我们用 4 维做二元 gate（threshold 0.4，summative）。我们不训 RL Curator，故取 summative gate——这是设定差异，不掩盖 formative vs summative 本质不同。

7MUSE-Autoskill —— 失败是精炼入口，不是终点

MUSE-Autoskill: Skill-Centric Agent with Skill Evolution

arXiv 2026 (ByteDance)
作者 Lin et al. (ByteDance) · arXiv 2605.27366v2 · 30 页 · logs/papers/2605.27366v2_MUSE-Autoskill_Lin2026_ByteDance.pdf

① 核心机制（原文）

Skill 生命周期：create → evaluate → (fail) → update_skill 精炼 → 重检 → register。原文 “MUSE creates skills on demand, stores them across tasks, retrieves them through a skill catalog, and accumulates per-skill experience for later reuse and adaptation”。失败是精炼循环入口，不是终点：“a useful skill is created on demand … and continuously refined as new evidence accumulates”，“automatically triggering refinement when tests fail”。
Figure 2（从 PDF p.3 扣出）：MUSE-Autoskill Agent architecture —— skill 统一生命周期（creation / memory / management / evaluation / refinement）。
per-skill memory + Progressive Disclosure：.memory.md 在 Skill 被加载执行时才呈现给 agent（lazy），自由格式经验怪癖。覆盖率是瓶颈：47/75 covered，uncovered 计 0；covered-task accuracy 85% > human 81%（on same covered subset，非全面碾压）。单轨迹过拟合：hvac-control 80%→20% 回归。

② 我们吸取了什么

机制借鉴 1：质量门失败触发 refine，而非 discard。我们曾把 --block 误解为“block-and-discard”，已纠正为 block-and-refine（max_rounds=2），Layer1 也走 refine。这是 MUSE 最核心的借鉴——评估失败是进入精炼循环的信号。
机制借鉴 2：Progressive Disclosure（lazy catalog）。我们曾 eager 注入 catalog + 模板化文本，违背 Progressive Disclosure；已修（P2-4）：eager→lazy（Skill 不再注入 system prompt catalog，按需加载）+ 模板→自由经验。
澄清（不违背）：从失败 task 产生 scenario。曾担心“[unverified] 从失败 task 产生 scenario 违背 MUSE”——不违背，论文 §4.3/Appendix L 明确建议向失败轨迹扩展。但 [unverified] 条目未经运行时验证就注入，缺 MUSE 的弱信号校验（我们用三态 + disconfirm 补）。

③ 用在系统哪部分

论文机制我们的落地代码位置（已核对）
失败 → refine 循环（非 discard）refine_skill_with_llm：质量门失败触发 LLM 精炼，锚定质量报告memory_bank/sediment/skill_quality.py:753,770,776（“MUSE principle: evaluation failure is the entry to a refinement loop … NOT a discard signal”）

8定位 / 对比论文（简述，不展开机制）

以下论文不是机制借鉴，而是 related-work 的定位坐标或对比对象。撑大图景、确认我们的 delta，但未把它们的机制搬进系统。

定位背景 iScript
Xu et al. 2026 · 2603.04476 · Cadence Innovus Tcl 脚本生成

同赛道最近邻（过程式 EDA 脚本生成），但无自进化 / 无记忆 / 无迭代反馈——纯 single-turn CPT+SFT。function pass@1 仅 18.97%，语法对但逻辑错是主瓶颈（与我们 61.7% 逻辑错同构）。我们 vs iScript 的 delta = 自进化记忆治理 + API 正确性保障 + anti-leakage 蒸馏，iScript 完全没有这三条线。

定位背景 OpenROAD-Agent
Wu et al. 2025 (ASU+NYU) · ICLAD · OpenROAD-Agent_Wu2025

比 iScript 更近的邻居——NL→Python API 脚本生成→执行→报错→自纠错→迭代，与 pyAether 场景几乎同构。三阶段训练（SFT generation/correction + hybrid RL），94% accuracy。但无跨任务沉淀 / 无记忆 / 无 validator / 无读写分离 / 评估非隐藏测试。related work 里最该正面对比的 EDA baseline。

定位背景 FluxEDA
Chen et al. 2026 (Zhejiang U) · 2603.25243

5 层 agentic EDA 执行基础设施（gateway Socket-RPC + MCP Server + 持久后端 + 静态 Skills 层）。我们 = 决策 + 进化层，FluxEDA = 执行基础设施层，互补。都用 MCP 做标准化工具接口；它的“Skills”是静态工作流模板（非自进化蒸馏）。

定位背景 Agentic EDA Survey
Zang et al. 2026 · 2512.23189

L0→L4 自治度分层，我们位于 L3“Agentic EDA: agent 自主分解、生成脚本、与 EDA 工具交互闭环”。提“Code-Reality Gap”（语义盲/数据私有/现实差距）挑战——我们的 158 题 + 黑盒 verifier 是对此的具体回应。撑 intro 定位。

对比/不借鉴 ReVeal
Jin et al. 2025 (MSRA) · 2506.11442

标题实为“Self-Evolving Code Agents via Iterative Generation-Verification”。核心：agent 每轮交替 generation（代码）+ verification（自生成测试用例），调解释器拿 expected/actual + pass/fail。与 anti-leakage 直接冲突——verification 阶段 agent 自写测试 + 拿 expected output，等价于暴露隐藏 GT。是对比不是借鉴。我们走蒸馏（非 RL）在稀疏 pass/fail 下进化，是对 RLVR 线的补充。

方法论 AHE + Externalization
Lin (Fudan) 2604.25850 · Zhou (SJTU+OPPO) 2604.08224

AHE：三大可观测性（component/experience/decision），10 次迭代 Terminal-Bench 2 pass@1 69.7%→77.0%（超 Codex 71.9%）；核心发现——改进承载于 tool + middleware + long-term memory 而非 system prompt。Externalization：四大外部化（memory/skills/protocols/harness），“agent 进步越来越取决于外部认知基础设施”。两者是我们 multi-port 隔离→reproducibility + 文件制记忆的理论包装。

方法论 VeriHarness —— 结构化反馈是 T1 依据
Ray & Goyal 2026 · 2607.14167 · 4 页 short paper

核心实证：结构化反馈（失败位置 + 观察值 + 合法替代）比原始诊断 +44pp（GPT-4.1）/ +42pp（Llama-3.1-8B），在 50 paired TextWorld games、四 call cap 下。消融：增益主要来自“合法替代”（admissible alternatives），只给位置+观察值不够。prose vs JSON keyed 效果相近——信息内容有效，格式无关。启示：validator 命中应补充合法替代（如 TypeError 报错后附 ae.emyPointF(x,y) 构造示例），且回流 L1 时做结构化沉淀——这是我们 roadmap T1 的依据。

9与论文的三处本质不同（防"借鉴外壳"误判）

精读后我们发现，当前实现多处"借用论文术语外壳但错失机制精华"，且历史记忆有选择性引用/概念混淆。以下三处是与最同构的 Trace2Skill 的本质方向差异——引用时必须强调，否则 reviewer 会质疑"你和论文一样"。

不同 1：防泄露机制 —— 方向相反

论文靠物理隔离（agent 拿不到 check()）；我们靠 prompt 纪律 + 事后 strip。但我们 agent 技术上有能力自造强信号——run_pyAether_code_tool 让 agent 在沙箱自测，而沙箱≈GT 环境，agent 可自写 assert candidate(x)==期望值。真实状态：77% 失败 case 自测“successful+无 None”但 GT 不过——agent 只 assert callable/is not None 弱断言，不测实际效果。即“提升 agent 自测强度”在我们体系的天花板可能比论文加 verify_feedback 还高（不用造新工具，只让 agent 把已有沙箱能力用对）。

不同 2：进化时机 —— online vs offline

论文 online（rollout 后立即 verify→oracle→mutate，单批次内 5 代×640 rollout 快速收敛）；我们 offline（trace 的 execution_success 不可信 ~40 假阳性，必须一批评估后从 execution_results.jsonl 回填 GT，无 GT 守卫强制 False 防假阳性）。后果：论文一题能试 640 次快速收敛，我们一题 1 shot 靠多轮沉淀累积。我们 4 端口隔离治“评估稳定性”，论文 LCB 治“选择稳定性”，是不同层级手段。

不同 3：技能载体 —— task-wise vs cross-task

论文 task-wise（单题独立 skill，不跨题，因 RTL 语义异质迁移不可靠）；我们 cross-task（L1 跨题聚合 (identifier, description) bullet，向量检索 top-K 注入）。两者都能 work，因任务异质性不同：CVDP RTL 语义各异迁移不可靠，我们 pyAether API 调用模式有共性（SWIG 构造 / 命令族 / 创建类反向验证）可迁移。警示：跨题 L1 净+17 主要来自“API 用法/参数构造”可迁移知识；一旦知识偏向“某题特有逻辑”跨题注入变噪音——正是 P2-6 held-out 担忧的“逻辑错类退化”，论文 task-wise 结论是该担忧的论文级佐证。

已纠正的"借鉴外壳"误判（精读后修复）：
  • SkillOS 4 维门：早期用 CORRECTNESS/COMPLETENESS/ACTIONABILITY/REDUNDANCY 只 ACTIONABILITY 重合 → 已对齐 Fig.12 的 ABSTRACTION/REUSABILITY/ACTIONABILITY/FAITHFULNESS。
  • MUSE --block：曾当“block-and-discard” → 已改 block-and-refine（失败是精炼入口非丢弃）。
  • MUSE per-skill memory：曾 eager 注入 + 模板化 → 已改 lazy catalog + 自由经验（Progressive Disclosure）。
  • MemOrb 查询重写：曾记“已启用” → 实际 QUERY_REWRITE_LLM_ENABLED 默认 false，只有 rule-based 重写在跑（LLM 重写关闭）。
  • Reflexion 反思：曾记“无 success 参数” → 四个 reflect_on_* 现均带 success 锚定。
