📖 阅读前：这个系统在干什么

在读懂下文前，先建立几个基本概念：

EDA
电子设计自动化（Electronic Design Automation）。本系统的"API"指某 EDA 软件（pyAether）暴露的 Python 接口，用于做电路版图/设计操作。
任务（task）
一次 benchmark 的最小单元：给 AI agent 一个自然语言需求（如"统计某总线有多少位"），让它写一段调用 pyAether API 的 Python 代码，在远程沙箱执行，用隐藏测试用例判定通过/失败。一整轮 benchmark 有 158 个任务。
Cline / zhulong
两个 AI 编程 agent 的 CLI（类似 Claude Code）。agent 读任务描述、调用工具、生成代码。本系统为其提供工具与记忆。
MCP
Model Context Protocol（模型上下文协议）。MCP Server 是挂载在 agent 旁的工具服务端——agent 通过它调用 search_apis、查询记忆库等工具。本系统主体就是一个 MCP Server。
轨迹（trace）
agent 跑一个任务时的完整对话历史（搜了什么、调了什么工具、报了什么错）。自进化的"原料"就是轨迹。
沙箱跑通 ≠ 测试通过（重要）
代码在沙箱执行有两层结果：① 代码跑通（没抛异常、agent 自评"成功了"）和 ② 隐藏测试断言通过（ground-truth 判定的真正成功）。两者经常不一致——代码能跑完不代表结果对。ground-truth 特指 ②，是唯一可靠的成败信号（区别于 agent 自评的 ①）。
Skill / Rule
蒸馏产物：Skill 是按需加载的详细决策树（Markdown），Rule 是常驻生效的极简硬约束。两者都是给 agent 读的操作指南。

一句话概括自进化：把每轮 158 个任务跑完后留下的轨迹，沉淀成可复用的经验知识（L1 模式 / Skill），让后续任务的 agent 能检索到这些经验，从而提升通过率。沉淀是写侧（-e 开启），检索是读侧（L1 有内容时自动生效）——两者独立。

1总览：宏观架构与设计哲学

自进化系统的目标：把一次 benchmark 中每个任务的"搜了什么、用了什么 API、为什么失败"沉淀成结构化知识，让后续任务（乃至下一轮 benchmark）的 Agent 能检索到这些经验，从而 pass@1 更高。它围绕 三层记忆（L0/L1/L2）和 读写分离 两条主线展开。

图 1 · 自进化系统宏观架构（图中 Cline/zhulong 是 AI 编程 agent，MCP Server 是挂载在 agent 旁的工具服务端，详见上方"阅读前"）。读侧与写侧解耦：写侧由 -e 控制，读侧由"L1 有无内容"控制。
🎯 设计哲学（一句话）

评估器在循环之外，记忆分层且只沉淀有信号的知识；规则引擎做确定性脚手架、LLM 做语义判断；三态把"成功经验 / 方向对但未通过 / 失败教训"显式区分。

⚠️ 两条硬教训（2026-07-19/20，贯穿全文）

① 归因必须隔离评估：沙箱是有状态共享资源，单沙箱并发评估（workers=4）踩 lib.defs/TECHLIB 状态致 pass 率抖 ±4~16pp（011 同代码串行 5/5 pass、并发掉到 38%）。历史单沙箱并发 pass 率全部废弃，曾据此得出"L1 注入有益"等结论被串行重评推翻。2026-07-21 起 4 端口隔离（SANDBOX_ENDPOINTS=8664/8665/8667/8669，每端口独立 workdir）让并发请求落不同端口 → 无污染 → 并发评估可信（取代旧 EVAL_SANDBOX_WORKERS=1 串行）。

② 自进化的信任锚是知识精准度，不是知识量：L1 注入曾净负（093 铁证 = 任务 093 的参数名误判案例，[已验证] 含 agent 自测误判的错误参数名 isReplaceMismatched，误导 agent 把对的位置参数改成 kwarg→fail，详见 §5.5）。治本（reflection 不沉淀 agent 推断 + 无 ground-truth 不标 [已验证]）后转净 +17 题。不精准的知识比无知识更糟（系统性误导）——这是全文反复出现的主线。

📄 论文脉络：本系统对照多篇文献落地——CoALA（认知架构：三层记忆 episodic/semantic/procedural，并把 agent 动作分四类：内部动作检索/推理/学习 + 外部动作接地，接地指把模型决策连到外部工具/环境执行）、Reflexion（反思必须锚定评估器给出的奖励信号，否则反思会做有害编辑）、MemOrb（用向量检索跨会话记忆）、SkillOS（Skill 质量四维评审：抽象/复用/可操作/忠实）、MUSE-Autoskill（per-skill 运行时记忆 + 失败重写循环）、ACE（Agentic Context Engineering，上下文是"演进手册"而非不断膨胀的 prompt）、Lilian Weng《Harness Engineering》（可编辑边界 / 评估器在循环外 / 文件系统即记忆）；扩展引用 Voyager（self-verification）、Generative Agents（记忆检索三分量）、Self-Harness（弱点挖掘→提案→验证）。下文每个设计点都标注出处与原因。
📖 代号说明（全文统一）：下文用三套编号指代改进项——P2-N 是自进化 roadmap 待办编号（P2 系列是"较大改动"档，如 P2-1 读侧分层注入、P2-3 突触修剪、P2-7 语义合并、P2-5a REM 反事实），E-N 是参数填写/自测纪律编号（E1 SWIG 类型构造、E3 None 判空、E5 自测强度、E6 创建类生效验证，详见 §12.5），A-N 是 prompt/Rules 侧改动编号（A1 Rules 沙箱通过≠任务完成纪律、A2 验证失败回退搜索 footer）。093 铁证指任务 093 的参数名误判案例（§5.5）。顽固题/可及题/间歇题定义见 §14 开头。这些代号全文含义统一以此为准。

2.1 三层记忆 ↔ CoALA 的记忆三分

文件系统上是 L0/L1/L2 三层；下表第 4 行的 Skills/Rules 是 L1 蒸馏出的独立产物，映射到 CoALA 的 procedural 记忆，故单列。

📄 CoALA（Sumers et al.）：把长期记忆分三类——episodic（情景：具体事件经历）、semantic（语义：抽象世界知识）、procedural（规程：怎么做的技能/代码/prompt）。三者严格区分，且写 procedural（改操作规程）属高风险——"easily introduce bugs or subvert designers' intentions"。本系统的 L0/L1/Skills 正好对应，且 Skills 蒸馏带来源标记保护（见 §8）正是对 procedural 高风险的回应。
🎯 原因：分层让"原始轨迹"与"聚合知识"分离——L0 忠实记录每次尝试（可回溯），L1 只保留去重后的可复用模式（可注入）。若混在一层，要么 prompt 被原始日志撑爆，要么丢失回溯细节。

2.2 读写分离：写侧开关 ≠ 读侧开关

这是最易被误解、也是最关键的设计之一。写入端（把轨迹沉淀进记忆）与读取端（让 agent 看到已有知识）由两个独立开关控制：

写侧开关读侧开关
变量-e / EDA_EVOLVE_ENABLEDl1_has_content（L1 条目数 > 0）
默认关（需显式开启）由 L1 内容决定
控制什么本轮轨迹是否喂给自进化（Step 8 更新 / 8.5 蒸馏）是否注册"查询记忆库"工具 + 是否把 L1 注入 prompt
判定位置run_cline_script.shmain.py · format_eval_task.py
关键推论：一个 -e 关闭的运行，仍然会读到上一轮 -e 开启时沉淀的 L1。因为读侧只看"L1 有没有内容"，不看"本轮是否写入"。冷启动时 L1 文件有条目数 0（空骨架，非空文件）→ 读侧判定无内容 → 不注册工具、不注入。
🎯 原因：若读写共用一个开关，"想验证零知识基线"时要么连读侧也关（看不到已有知识，无法测真实效果），要么连写侧也开（污染基线）。分离后可独立控制：跑基线时 -e 关但 L1 已重置 → 真·零知识；跑自进化时 -e 开 → 沉淀。读侧始终反映"L1 实际有没有东西"。
📄 CoALA：把"从记忆检索"与"更新记忆"列为不同动作；读写分离正是这一原则的工程化。

2.3 级联自进化（按轮次粒度）

当前自进化是按轮次（一轮 158 个任务跑完后统一更新），不是按单次尝试。写侧主管模块 update.py 的主流程按顺序执行：L0 抽取 → 富集 → 根因分类 → L1 抽取合并 → Skill 自动晋升 → 用量统计 → 向量同步。下图是其中数据加工的核心 5 步（完整生命周期见 §13）：

1
L0 抽取 — 逐个轨迹解析成结构化记录，写入 L0_raw/task_artifacts/{任务ID}.md
2
富集 — 用沙箱真实通过/失败覆盖轨迹里的启发式成败判断；补全生成失败的任务；回填验证过的真实代码
3
根因分类 — 失败任务判定根因，环境/生成类故障跳过沉淀
4
L1 抽取合并 — 4 类反思产出条目，合并函数做去重/合并/状态升级，写回 L1 文件
5
后处理 — 模式自动晋升为 Skill、Skill 用量统计、L1 同步到 9003 向量库
📄 Lilian Weng《Harness Engineering》：评估器与权限控制必须在进化循环之外。本系统更新阶段读的是上一轮 benchmark 的沙箱执行结果（ground-truth），写侧不自评——评估器独立于写循环。

3.2 ground-truth 富集：覆盖不可靠的轨迹推断

⚠️ 核心问题：上表的"执行成功?"由轨迹推断（结果含 "successful" 字样），严重高估。实测：轨迹推断成功 150/158，而沙箱 ground-truth 真实通过仅 114/158——轨迹把约 36 个失败 task 误判为成功（含 4 个真成功也被轨迹漏判后修正回成功，净假阳性约 40）。若不富集，这些"看起来成功实则失败"的任务会被当成已验证的正面经验沉淀进 L1，污染知识库。

富集步骤从 EDA-Eval-Framework 的执行结果文件取沙箱真实通过/失败（ground-truth），直接覆盖轨迹推断的成败字段。定位执行结果用三级 fallback：精确匹配（读评估报告的生成文件名）→ 直接路径 → 递归搜索兜底。

# 富集核心：ground-truth 覆盖轨迹推断
if 任务已有记录:
    artifact["execution_success"] = passed   # 沙箱结果是真相
    if 旧值 != passed:
        enriched += 1                         # 仅在值翻转时计数
📄 Reflexion（Shinn et al.）：反思必须锚定在评估器奖励信号 r 上——"可靠 Evaluator 信号是反思有效的前提"。论文 Table 3：无测试+有反思 = 52%（比 60% 基线还差，反思做"有害编辑"）。本系统的 ground-truth 富集正是把"可靠的 r"喂给下游反思——这些假阳性若混入，等于在脏奖励上做反思。
🎯 原因：用覆盖而非"合并"——沙箱测试是黑盒 ground-truth，轨迹推断是噪声启发式，真相只有一个。覆盖保证下游反思/沉淀拿到正确 reward 标签。
已知脆弱点：当一个 batch 被多次评估时，精确匹配策略取最早的一个 eval，可能静默选错。需评估目录指向正确 eval。
★治本守卫（2026-07-19）：无 ground-truth 时（未设 EVAL_FW_DIR / 空结果 / 读取失败），_enrich_from_execution_results 三条跳过路径都把未富集的 execution_success 强制设为 False——防止轨迹推断的假阳性让失败 task 被标 [已验证]。代价是无 ground-truth 时漏沉淀真成功 task（宁缺毋滥原则）。正常带 EVAL_FW_DIR 沉淀不受影响。配合 §5.5（reflection 不沉淀推断），这是 L1 注入治本转正的两刀。

4写侧 · 失败根因六分类

失败有两层标注：错误码（what——发生了什么，15 类，如 TypeError/AttributeError/TimeoutError 等具体的异常类型）和 失败根因（why——为什么会失败，6 类）。根因分类函数在所有富集完成后统一计算（保证生成状态、代码数、错误都齐备）。

两层关系：错误码是细粒度的"表象"（15 类），失败根因是粗粒度的"根因"（6 类），多对一收敛——多个错误码归入一个根因。例如 TypeError、AttributeError、ImportError 三个错误码都归入"③ API 误用"根因；各种 Timeout 归入"① 环境故障"。根因是下游决定"要不要沉淀、沉淀成什么"的依据。
图 2 · 失败根因六分类优先级决策树
关键设计：③ API 误用先于 ④ 检索缺失判定。一个任务可能搜了很多 API（看起来像检索缺失），但若最终报参数类型错/属性错，根因是"用错了"而非"没搜到"。先判 API 误用避免误归类。

六类含义：ENV_FAILURE（环境故障：沙箱超时、session 初始化失败）、GEN_FAILURE（生成失败：没产出代码）、API_MISUSE（API 误用：参数类型/属性/导入错）、SEARCH_MISS（检索缺失：没搜到/搜太少）、LOGIC_ERROR（逻辑错：代码能跑但断言不过）、UNKNOWN（兜底）。

沉淀门：环境故障和生成故障不含 API 使用信号，沉淀进来只会用环境噪声冒充 API 教训，故跳过 API 反思；其余 4 类进入反思。环境故障类仍允许"决策反思"（若存在重复搜索等退化行为）。

📄 Reflexion：失败信号的可靠性分层，对应到六类：属性错/类型错（③ API 误用）信号最强（明确指向用错 API 或参数）；断言错（⑤ 逻辑错）信号半可靠（代码能跑但结果不对，不知是 API 选错还是逻辑写错）；未知（⑥）是猜测。这个分层直接驱动了 §5 的低信号保守判断（对断言错/未知这类低信号失败，要求 LLM 保守、宁可不下结论）。📄 SkillOS：根因分类策略本系统采用人工规则（SkillOS 论文方向是用强化学习从下游反馈学出该策略，本系统取其分类思想、简化为规则）。
🎯 原因：分类用规则而非 LLM——确定性、便宜、可调试。CoALA "code sparingly"：分类是确定性脚手架，语义判断留给下游反思 LLM。
真实盲点：V5+evo（串行 85.4%，详见 §14）23 个失败中，逻辑错占 61%——agent 最后一次执行代码跑通无报错（agent 自评"成功了"），但 ground-truth 隐藏测试断言未通过——即"代码能跑"≠"结果对"（见阅读前的两层区分）。这类"自验证层"问题横跨 ③ API 误用与 ⑤ 逻辑错（说不清是 API 用错还是逻辑错），6 类规则抓不到，靠 prompt/Rules/Skill + validate_code 缓解（详见 §12.5 三件套、§12.6 拦截器；失败分布见 §14.2）。治本前看 trace 实际错误是参数构造 83%（SWIG 类型传原生值），E1/validator 落地后压下参数构造，瓶颈转向逻辑错（创建类 API 跑通但没生效，治法见 E6/§12.5）。治本后顽固题已收敛到 2 道（143/146，跨 14 批可信评估），E6 对"创建没生效"类有效但未完全破零。

5写侧 · 反思层（四类反思）

反思层把 L0 结构化记录转成 L1 条目。有 4 类反思函数，按任务成败分派，每类产出不同性质的条目：

反思类型语义产出条目状态调用时机
场景反思（reflect_on_scenario）"在 X 场景用 Y API" 的使用经验已验证（成功时）或 待验证（失败但 LLM 判方向对）成功产正面；失败由 LLM 判 API 方向
坑点反思（reflect_on_pitfall）"X API 有个坑" 的负向警示状态留空（坑点，见 §6.1）仅失败
错→修反思（reflect_on_error_to_fix）"错 X → 修 Y" 的修复映射状态留空（坑点）仅失败
决策反思（reflect_on_decision）搜索/工具决策的得失状态留空（坑点）有重复搜索等退化行为时
四类反思都带成功信号并锚定奖励：成功任务（success=True）时，坑点/错→修反思直接短路返回 None——"通过的任务的错误不是失败信号"。只有失败任务才产出坑点/错→修条目。这正是 Reflexion"反思锚定奖励 r"的落地。

5.1 规则引擎 vs LLM 双路径

LLM 路径（主）：批量反思函数用线程池（默认 5 并发）跑 4 类反思。受 REFLECTION_ENABLED 开关控制，可用 --no-reflection 关闭用于消融实验。

规则引擎路径（fallback）：纯规则提取器（基于搜索记录/API 名/错误的确定性规则），仅在 LLM 反思关闭时启用。

规则引擎不越权（核心设计）：规则版的场景提取是两态——成功产已验证，失败返回 None（不产条目）。不产"待验证"。因为向量检索出的 API"看起来总是相关的"（词重叠近乎必然命中），规则无法区分"似是而非"——只有 LLM 能做"API 方向对但参数错"这种语义判断。故"待验证"是 LLM 专属。
📄 CoALA "code sparingly"：确定性逻辑用代码做脚手架（成功→已验证），创造性/语义判断交 LLM（失败→判断方向）。📄 Reflexion：反思是对奖励信号（任务成功/失败）的语义放大，必须锚定这个信号——通过的任务不产失败教训，失败的任务才产。

5.2 状态前缀由系统强制，不信 LLM

# 系统强制状态前缀
description = strip_status(description)               # 剥掉 LLM 自己加的前缀
authoritative_status = "verified" if success else "unverified"
description = f"[{authoritative_status}] {description}"  # 用真实成败重写

无论 LLM 输出什么前缀，系统都剥掉再用 ground-truth 成败重写。保证成功→已验证、失败→待验证 绝对可靠。此外场景反思用独立的系统提示词（与共享提示词分开），因为共享提示词的"哪里出错了"措辞与场景语义冲突。

🎯 原因：状态标签下游直接决定检索优先级与渲染（§6/§11），必须 100% 可信。LLM 偶尔不遵循格式，系统强制补前缀消除这个不确定性。

5.3 低信号失败的保守判断

有些错误码不指向明确根因——断言错（AssertFail）、未知错（Unknown）、执行错（沙箱执行层报的笼统错误）这三类（属 §4 的 15 类错误码中的低信号子集）只说"结果不符"，说不清是 API 选错、参数错还是逻辑错。对这类低信号失败，场景反思注入不确定性提示与保守指引，要求 LLM 保守：只有 API 明确相关才产条目，有疑虑返回"无"（→ 不写待验证条目，回退到坑点）。

📄 Reflexion：低质量奖励信号会产生"harmful edits"（Table 3：无测试+反思=52% 比基线差）。保守判断 = 不在噪声上放大，宁可不沉淀也不沉淀错的。

5.4 LLM 基础设施

多模型 fallback 链（逐级降级兜底）：DeepSeek → 通义千问 → 豆包（Doubao），按环境变量配置；所有模型配置在调用时读取（而非导入时读取，这样即使 .env 配置文件在模块导入之后才加载，配置也能读到），兼容 .env 后加载；限流时自动重试（解析"请等待35秒"类消息）。

📄 MemOrb：反思输入应是完整轨迹 + 显式 reward 分项。本系统反思输入是预提取摘要（搜索记录/API/错误），非原始轨迹——这是与 MemOrb 的设计差异。

5.5 治本：不沉淀 agent 推断（2026-07-19，★L1 注入转正的关键）

⚠️ 093 铁证：V5+evo（治本前）L1 含一条标 [已验证] 的"测试发现"——声称参数名 isReplaceMismatched（一个 s）是错的、正确的是 isReplaceMissmatched（两个 s）。agent 采信后把 V5 对的位置参数改成 kwarg → TypeError: unexpected keyword argument → fail。实际 API 根本不接受任何 isReplace* kwarg，只接受第 5 个位置参数。这条"测试发现"是 agent 自测时的误判（瞬态成功误归因到"两个 s"），被标 [已验证] 后系统性误导下游。
★治法（reflection.py）：rule 4 改为"Only state APIs the agent's code ACTUALLY called (used_apis fact). Do NOT infer 'correct wrapper pattern'/'correct parameter name'/'use property X vs setter Y' — these are agent guesses that may be wrong"。L1 只沉淀 used_apis 事实（代码真调用的 API）+ ground-truth 验证的用法，不沉淀 agent 的"测试发现/参数名修正/属性写法"类推断。治 093（参数名推断）/075/134/132（属性 vs 方法推断），不削 gained 题（它们靠 used_apis 事实）。

6.1 三态：已验证 / 待验证 / 坑点

7.1 佐证次数参与检索排序

检索时按佐证次数（source_count）做温和对数加权重排：

for r in vector_results:
    sc = r.get("source_count", 1) or 1
    boost = 1.0 + 0.1 * _math.log(max(sc, 1))   # 对数缩放，温和
    r["score"] = r["vector_score"] * boost       # 向量相似度仍主导
vector_results.sort(key=lambda r: r.get("score", 0.0), reverse=True)
温和是设计（0.1×log）：佐证次数高 = 被多个任务验证 = 更可信，给小幅加权。但对数缩放保证向量相似度仍主导，只在平局时偏向高频条目——不让"流行但不太相关"压过"小众但精准"。
📄 CoALA 引 Generative Agents（Park et al.）：记忆检索三分量 = 相关性 + 重要性 + 时效性。本系统实现 相关性=向量分、重要性=佐证次数加权（时效性暂不纳入）。
🎯 原因：纯向量相似度会在"语义相近但实际没人验证过"与"被多次成功佐证"之间无差别。佐证次数把"验证次数"作为重要性信号注入排序，让经得起考验的经验更靠前——但温和到不破坏语义检索本质。
📄 MemOrb + CoALA：向量语义检索替代纯词重叠。文档="标识符:描述" 合并是 MemOrb 完整轨迹嵌入的务实替代。稳定 ID 实现幂等重灌（去重）。

8.2 可编辑边界：手写 Skill 永不覆盖

每个蒸馏 Skill 的文件头带 origin: auto_distilled（自动蒸馏来源标记）。系统据此判定——手写 Skill（无此标记）永不被覆盖：

    print(f"  跳过：手写 Skill 已存在")
    continue   # 手写 Skill 存在则跳过，绝不覆盖
📄 Lilian Weng《Harness Engineering》："可编辑边界需妥善设计，权限控制要在进化循环外"。origin: auto_distilled 标记就是机器可读的可编辑边界——自进化只能改自动蒸馏的，绝不碰手写。
🎯 原因：手写 Skill（如 API 搜索策略、命令族选择）是人工精心设计的核心资产，自进化若覆盖它们会"subvert designers' intentions"（CoALA：写 procedural 属高风险）。来源标记让保护机制确定且可审计。

8.3 Rules 蒸馏（更高阈值 + 路径门控）

规则蒸馏步骤（Step 8.6）把 L1 蒸馏成常驻 Rule。与 Skill 的区别：Rule 极简（<500 token）、路径门控（paths: ["**/*.py"]，非 Python 任务不加载）、阈值更高（坑点阈值 3 vs Skill 的 2）。产出按错误类型分的坑点规则和合并的决策规则，写 ~/Cline/Rules/，同样带来源标记保护。

📄 CoALA：procedural memory 是最高风险写入面，所以 Rule 保持在最小、路径门控、高阈值——只把反复出现的硬约束固化为常驻指令，丰富上下文指导留给按需 Skill。"code sparingly"。

9.3 多样性检测（Jaccard 相似度）

读各 Skill 的"受影响 API"列表，算两两 Jaccard 相似度，报告 >0.3 的重叠对，作为第一层的重叠率惩罚项。

📄 Lilian Weng《Harness Engineering》：进化系统易多样性坍缩（收敛到同类方案），需显式机制——如 ShinkaEvolve（一种程序进化方法）的"拒绝采样"（与已有个体太相似的新解直接丢弃）。本系统的 Jaccard 重叠检测是其轻量实现，对高重叠 Skill 施加惩罚分。

9.4 重写循环：失败先重写再淘汰

失败的 Skill 不直接丢弃，先用 LLM 重写（基于低分维度的评审理由），再重跑质量门，最多 2 轮。重写成功则上线；仍失败才软弃用。

for round in range(2):                       # 默认 2 轮
    重写(skill, 评审报告)                      # 按低分维度重写 Skill 文件
    报告 = 重跑质量门()                        # 重跑两层评估
    if 报告["通过"]:

# 仍失败 → 标记软弃用（最后手段）
📄 MUSE-Autoskill："失败是重写循环的入口（创建→评估→重写→重评→注册），不是丢弃信号"。本系统直接对齐此生命周期。
历史实证（机制验证）：曾有一个类型错误的坑点 Skill 版本号 0.0.3、自动注入关闭，符合"经过重写（版本涨）后仍被软弃用（注入关闭）"的痕迹。一次实测：5 个原被淘汰 Skill 重跑 → 3 个重写通过（0.57→0.85/0.74/0.77），2 个 2 轮后软弃用。（当前 reset 后 L1 空态，蒸馏 Skill 随 -e 重新生成。）

10.1 用量统计推断

10.2 渐进式披露：失败笔记不预注入

核心设计：Skill 目录加载器不把每个 Skill 的失败笔记预注进目录清单。否则每个任务的清单都带上所有 Skill 的已知问题 = 违反渐进式披露。替代：每个 Skill 文件末尾有"已知问题"指针，agent 实际用该 Skill 时才按需读笔记。
📄 MUSE-Autoskill：per-skill 记忆笔记在 Skill 加载时呈现，自由格式经验怪癖（如"大 PDF 超时"），刻意不放发布包。本系统的按需消费正是 MUSE 模式。
路径差异（接 §8.1）："已知问题"指针只有自动晋升路径（B）产，独立蒸馏脚本（A）模板不带。纯路径 A 产的 Skill 会被写失败笔记但 Skill 文件不告诉 agent 去读它——按需消费契约对纯路径 A Skill 失效。-e 跑完沉淀链后，自动蒸馏 Skill 多数带指针（来自路径 B）。

12.2 三态渲染 + 必须验证免责声明

12.3 P2-1 分层注入（V5）+ 验证失败回退搜索纪律

P2-1 读侧分层：注入时按 status 分桶排序 verified(0) > unverified(1) > 无标签(2)，tier 内保持向量相似度序。verified 高相似度优先填满 1200 字符预算，不被低相似度 unverified 截断。边界安全（不灌半条）：预算装不下任何整条 bullet → 返回空；巨大 verified bullet 装不下 → 跳过它继续试同 tier 较小的（不让小 unverified 顶替大 verified）。source_count 不用于分层（95% 条目 count=1，区分度近零，靠 query.py 的 similarity×source_count re-rank 已吃掉）。
A2 验证失败回退搜索（V5）：注入 footer 从"必须验证"强化为"如果参考知识推荐的 API 验证失败（查不到/TypeError/返回 None），立即用 search_apis 搜索替代 API，不要反复试同一个 API"。配合 Rules（A1）的 always-on 纪律——防 agent 信了 L1 的 [已验证] 高频 API 就不搜替代方案。治本后（[已验证] 严格化，不含 agent 推断）L1 注入净 +17 题，A2 是"引导但不锁死"的护栏。
🎯 原因：V5 前注入按向量返回顺序塞到 max_chars，verified 可能被低相关 unverified 顶掉；且 agent 信了 [verified] 就不探索替代。P2-1 保证 verified 优先，A2 保证验证失败能回退——两者协同让 L1 知识"引导但不锁死"。

12.4 工具清单占位符

prompt 模板里的工具清单占位符在"L1 有内容"时填入"查询记忆库"工具说明（位于工具清单、搜索策略之前）；否则置空。即 工具清单（能力披露）与参考知识（实际内容）分两处：前者在工具列表，后者在 prompt 后段。

🎯 原因：逐任务向量召回（vs 一刀切截断）让每个任务只拿相关 L1，降噪声；1200 字符上限防 prompt 膨胀；三态标签让 agent 知道哪条可信、哪条要复核。

13.3 重置：服务状态感知的向量库清理

⚠️ 关键约束：向量库（ChromaDB）服务运行时打开 sqlite 并把集合常驻内存，运行中删文件会破坏内存中的客户端（"no such table" → 服务 500，进程还在但功能全坏，比崩溃更难发现）。故重置必须按服务状态分流。

重置逻辑按服务状态分流：

service_up = 检查向量服务健康()
清除结果 = 调 API 清空集合()
if service_up:
    # 服务在跑 → 仅走 API 清空，绝不碰磁盘（会杀服务）
elif 清除失败:
    # 服务健康但清空失败 → 不回退删磁盘（会杀死运行中的服务）
允许清磁盘 = not service_up          # 仅服务停止时才清磁盘孤儿
🎯 原因：有状态持久化服务的文件句柄是隐式的，运行中删文件静默腐蚀内存状态。服务在跑走 API（集合级删除+重建），服务没跑才动磁盘（清孤儿 sqlite + 段目录，保留目录本身）。API 清空与磁盘清理永不同时。
📄 Lilian Weng《Harness Engineering》："评估器与权限控制要在进化循环外，文件系统即通用接口"。重置的服务状态感知是对"有状态共享资源"的工程谨慎。

13.4 冷启动 L1 模板（条目数为 0 ≠ 空文件）

重置后 L1 文件不是消失，而是恢复成带文件头 + 分区标题但零条目的骨架，条目数为 0。语义是"还没有条目"而非"文件缺失"。这让读侧判定可靠返回"无内容"，且文件结构跨重置稳定（下游解析器、向量同步、判定都依赖文件头存在）。

📄 ACE：冷启动骨架（结构在、内容空）正是"演进手册"从空开始增量生长的起点。
