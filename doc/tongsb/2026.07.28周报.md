## **二、多端口隔离落地（评估可信的基石）**

07\-21 周报记录了 MCP 超时根因（Semaphore 排队 \+ 客户端 60s）与 SDK 改 300000 的治标方案。本周落地**真治本**：多端口物理隔离，取代单沙箱串行。

### **机制**

- **4 个隔离沙箱端口**（8664/8665/8667/8669）各自独立 workdir → 并发请求各落一个端口 → 物理隔离 lib\.defs/TECHLIB → 并发不再污染

- **生成侧**：MCP `main.py` 端口池 `asyncio.Queue`（替代 Semaphore），4 路真并行无排队 → \-32001 超时死结从根消除（不再靠 Semaphore 串行 \+ SDK 300s 治标）。`RUN_CODE_MAX_CONCURRENT` 缺省=端口数，`SANDBOX_ENDPOINTS` 配端口:workdir 映射

- **评估侧**：`run_eval.py` 4 进程分片（`run_sandbox_sharded`），各带 `SANDBOX_CONFIG_JSON` env 绑一个端口。\`EVAL\_SANDBOX\_WORKERS=4\` 默认

- **回退**：`RUN_CODE_MAX_CONCURRENT=1` 或 `EVAL_SANDBOX_WORKERS=1` 或清空 `SANDBOX_ENDPOINTS` → 回退单沙箱串行（无需改代码）

### **实测验证**

同一份生成结果（2026\_0720\_073406）4 并发 vs 串行逐题对比：**156/157 一致，0 个并发引入失败**，耗时 3\.7× 提速。155 翻转是 workdir 残留差异（非隔离失败）。

### **方法论影响**

- **历史单沙箱并发评估不可信**（±4\~16pp 抖动）——多请求踩同一 workdir 的文件竞争，全废弃

- **多端口隔离后并行评估可信**：4 端口各独立 workdir，并发不踩同一 lib\.defs。归因不再需要强制 `EVAL_SANDBOX_WORKERS=1`

- **版本对比的 delta 在多端口下干净**（无抖动噪声）

> 这是本周一切结论的前提：V5\.2/V5\.3 的 pass 率、gained/lost、顽固题核实都建立在多端口可信评估上。

### **Scope Boundary 三层重设计（07\-26\~27）**

L1 从"事实陈述"升级为"条件知识"，三层互补非 case\-by\-case：

- **沉淀侧**（reflection\.py \`\_SCENARIO\_PROMPT\`）：加 **Precondition**（trace 可观测 setup 条件）\+ **Constraint**（代码实际调用 API 的语义事实）。关键修正（避免重蹈 093 覆辙）：Scope Boundary 只允许陈述 trace 事实，**禁止推断 Alternative**；无法从 trace 支撑的维度直接省略（缺边界好过编造边界）。Gotcha Phrasing Rule：禁"avoid X"/"do not use"，必须写"X requires Y; recovered by \<代码实际采取的行动\>"

- **注入侧**（format\_eval\_task\.py）：scope marker 检测（正则匹配 Precondition/Alternative/Constraint/requires），有 scope 的条目 bullet 追加"⚠️有适用条件"；prompt section header 加说明文字

- **查询侧**（query\.py）：`_soften_absolute_negations` 对 QMB 返回 description 中"avoid them"/"do not use X"绝对否定追加 softening 注释；idempotent；vector \+ token overlap 两路径都调

- **skills 层盲区修复**（distill\.py 三处）：Workflow Skill 硬编码"Always emyInitAether"→条件式"只在无现有 session 时调"（116 回归直接根因）；FIX\_MAP 的 emyString 绝对化→soft\-tone 对齐 validator；Pitfall Skill 丢弃 description→加 `## Observed Cases`

### **保底修复链 \+ docstring embedding 根本修正（07\-27）**

116 题经 4 层根因逐层修复回归 PASS，揭示两个更深的结构问题：

**层 3 — 沉淀丢 API**：reflection\.py `core[:15]` 行截断 \+ `used_apis[:6]` API 截断 → 116 的 aeMakeCell 没沉淀进 L1。修：core 改覆盖性选择（保证所有 used\_apis 代码行进 core，cap 30 行）\+ used\_apis 全集（去掉 \[:6\]，61/150 题 \>6 个 API 受益）。

**层 4 — 注入 query 含代码骨架**：query 含 `import pyAether`/`def ...`/签名 → 116 自己条目排第 4 被挤出 top\_k=3。修：format\_eval\_task\.py 新增 `_extract_docstring_query`，从 docstring 内容提 query 跳过代码骨架。修后 116 自己条目排第 1（sim 0\.729，旧排第 4 sim 0\.699）。

**docstring embedding 根本修正**（用户对 B2 分类检索的本质质疑触发）：

- **根因**：9003 embedding 文本 = `"{identifier}: {description}"`，description 含**解法**（API 序列）；注入 query = task docstring（**问题**）。别的题"解法文本"和当前题"问题描述"语义相近就匹配，但解法 API 可能相反（建库 vs 不建库）。116 自己解法因 description 的 init 序列稀释 embedding，排 \#14 sim0\.618，注入的 top3 是别的题建库 solution

- **正确方向**：embedding 嵌"问题"（docstring 摘要），注入返回"解法"——同题 docstring 相同→向量 sim≈1\.0 自然召回自己解法；不同题 docstring 不同→不误匹配。不照抄答案（注入解法只给 API 名/方向非完整 Sequence）。不要 task\_id（用 docstring 向量自然匹配）

- **实施**（307 测试过）：vector\_sync\.py solution 层 embedding=document=task\_summary，metadata 存 solution\_description（解法，供返回）\+ task\_summary（问题）；9003 /recall 支持 where filter（按 knowledge\_layer 过滤）；注入 bullet 格式 `- ([已验证] 场景: <问题摘要> | <序列> ⚠️有适用条件)`，去 identifier 用 task\_summary 作场景表述；pitfall 不预注入（layers=\["solution"\]，pitfall 交 runtime query\_memory\_bank）

- **验证**：116 自己解法 sim=1\.000 排 top1（之前 \#14），同题 sim≈1\.0，别的题 0\.59\-0\.665 区分明显

**7 道回归题全验证（07\-27）：4/7 救回**——116/105/134/147 PASS（保底命中），114/151/150 仍 FAIL。核心发现：**误导链切断≠问题解决**——agent 缺的是任务上下文判断能力（读函数签名推断已存在/理解 TYPE\_ERROR 是参数错非 API 不可用），不是知识表述。L1/skill Scope Boundary 改动必要但不充分。

### **final\_code 替换 full\_code（推翻"47% 幻觉"）**

**根因**：`extract_task_artifact` 的 `full_code = codes[-1]` 取 trace 里**最后一次沙箱 run 的代码**，常是过时中间版本，不等于交给 GT 评测的最终代码。反思基于 full\_code 判断 → 报的 bug"对 full\_code 真、对提交假"，核对时对比提交代码判为"假阳性"，但 LLM 没幻觉，是看错了版本。

**142 铁证**：run\#19 写过对版本 → run\#20 改回错版本自测 → 最终提交文件是对版本。full\_code=run\#20\(错\)，final\_code=提交\(对\)。矛盾分析基于 full\_code 说"两个都用 n18"→对 full\_code 真阳性对提交假阳性。换 final\_code 后改指出"缺 PGR guard ring"（基于提交真实内容，非编造）。

**落地**：`l0_io.py _enrich_verified_code` 扩展到 FAIL 题也读 `eval_dir/code/<task_id>/pyAether_code/*.py` 存 `final_code`（完整不截）；`reflect_on_contradiction`/`reflect_on_scenario` 调用处 `full_code = final_code or full_code`。

**改变假阳性率判断**：之前核对 15 矛盾\+11 scenario 真阳性 33%/18%、假阳性 47%/64%；核对基准（提交代码）与 LLM 输入（full\_code）版本不一致。用 final\_code 重做反思后版本错位类"假阳性"消失（如 142）。**"47% 幻觉"是版本错位 \+ 核对基准不一致的假象**。

**方法学教训**：核对 pitfall 真假时 LLM 看的代码和核对基准必须一致；下负面结论前必须单题深核查根因；**Explore agent 批量核对不可信**（没 domain 知识，分不清"代码写了但执行行为错"和"代码没写"——063/074/114 均判错）。

### **LLM 矛盾分析 vs 覆盖率（33% 真 / 47% 假，断开沉淀）**

**全量核对 15 条 pitfall**（2026\_0725\_173506 沉淀，逐条对照 agent 代码\+GT）：真阳性 5\(≈33%\)、部分正确 3\(≈20%\)、假阳性 7\(≈47%\)。系统性问题：把自测中间错误当提交代码 bug（143/152/139）、编造场景（052/058）、把 GT mock 缺陷归咎 agent（146）、代码用对仍报错（142/134/139）。\[unverified\] scenario 路径更差（18% 真/64% 假）。

**结论**：假阳性会作为 \[unverified\] pitfall 注入误导下轮，净价值可疑 → **断开沉淀链，代码保留作诊断工具**（禁用 3 处接入注释，可恢复）。保留：函数定义、coverage\.py、print\_log/last\_run\_errorless 提取、题面加载——帮发现 A/D/B 根因分类 \+ mock 题只有 3 道。
