## 开场 + §1 技术领域（约 45 秒）

各位老师好。今天汇报的专利是 **P20261932——基于失败根因分类与沉淀门的 Agent 轨迹知识提取方法**。

这是 P20261929 的姊妹篇。一句话讲清创新点：本专利**不主张"反思"本身**——Reflexion 早有先例——我们的创新是把"**失败要不要沉淀、沉淀成什么**"这个原本由 LLM 模糊判断的问题，**转为可判定的根因驱动决策**：用六分类根因多对一收敛错误码，用沉淀门跳过无信号失败，用信号可靠性分层决定反思强度。

应用场景与 P20261929 同一套 EDA Agent benchmark——158 个任务，每个留下完整轨迹（搜索记录、API 调用、错误日志、成败信号）。本方法从这些轨迹里提取可复用知识，但**并非所有轨迹都值得提取**——环境故障和生成失败不含 API 使用信号，强行沉淀会用环境噪声冒充 API 教训，污染知识库。本专利就是解决"挑哪些失败沉淀、怎么沉淀"的问题。

---

## §2 先前技术（约 1 分钟）

引三个先例，每个铺垫一个本发明要解决的问题：

**第一，Reflexion**——让 Agent 对所有失败一视同仁反思并写记忆，不区分失败原因。环境超时、生成失败这类**不含 API 使用信号**的失败也被反思，产出"似是而非"的教训。论文自己证实：无可靠测试信号时反思反而有害，52% 比基线 60% 还差 8 个点。**问题**：如何按失败根因筛选哪些失败值得反思、哪些应跳过。

**第二，AutoGPT / BabyAGI**——2023 现象级开源 Agent，让 LLM 自主规划执行，但循环里**没有任何信号告诉它是否在进步**，会"跑几小时产出一文件夹半成品"。这类无信号失败若被沉淀，产出的"教训"实质是环境噪声冒充 API 教训。**问题**：如何识别并过滤不含 API 信号的环境故障和生成失败。

**第三，OpenCode**——22M 开发者在用的开源 Coding Agent，对失败仅由 LLM 自行重试，**无根因分类**，所有失败按错误码查 troubleshooting 文档。但错误码只描述"发生了什么"，不描述"为什么"：一个任务搜了很多 API 但最终报 TypeError，错误码是 TypeError，根因却是"用错了"而非"没搜到"。**问题**：如何把细粒度错误码多对一收敛为粗粒度失败根因。

## §3 发明目的 + 3 个挑战（约 30 秒）

发明目的：提供一种从 Agent 轨迹提取可复用知识的方法，使沉淀的知识**具有高信号质量**——只从含 API 信号的失败中提取，跳过环境噪声和生成失败，对低信号失败保守处理。

对应三个挑战：**失败原因的粗粒度归类 / 无信号失败的过滤 / 低信号失败的可靠性分层**。规则不越权、状态强制、精准归因这些是 §4 的实现细节，不是独立挑战。

---

## §4 技术方案 4 个模块（约 1 分 30 秒）

技术方案分四块，按数据流顺序讲：

**第一，双层失败标注与六分类根因判定**——本专利算法核心。每个失败任务有两层标注：错误码（what，15 类，从异常类型提取）与失败根因（why，6 类）。两层**多对一收敛**——TypeError/AttributeError/ImportError 都归入"API 误用"，各种 Timeout 归入"环境故障"。根因分类按**优先级递减**判定：SUCCESS → ENV_FAILURE → GEN_FAILURE → API_MISUSE → SEARCH_MISS → LOGIC_ERROR → UNKNOWN。**关键设计**：API 误用先于检索缺失判定——一个任务搜了很多 API 但报参数类型错，根因是"用错了"而非"没搜到"，先判检索缺失会产出错误的"该多搜"教训。

**第二，沉淀门筛选**——环境故障和生成故障不含 API 信号，**跳过 API 反思**；其余 4 类进入反思。沉淀门保证沉淀的每条知识都来自含 API 信号的失败。

**第三，信号可靠性分层反思**——过了沉淀门还不够，失败信号本身有可靠性分层：属性错/类型错信号最强，正常反思；断言错/未知错半可靠或纯猜测，**保守判断**——有疑虑返回"无"。此外**通过的任务在尝试过程中也报过错**（后来修好了），这些不是失败信号，反思锚定最终成败而非中间错误。

**第四，知识可信度保障**——四项工程保障合一：规则引擎不越权（只产"已验证"，"待验证"专属 LLM 的语义判断）；状态前缀系统强制（剥掉 LLM 自加前缀用 ground-truth 重写，100% 可信）；错误 API 精准归因（从错误日志按 5 种模式提取真正报错的 API 名，用于反例计数）；治本不沉淀 Agent 推断（只沉淀 used_apis 事实，不沉淀 Agent 的"测试发现/参数名修正"类猜测）。

## §5 有益效果 2 项（约 1 分钟）

效果两个，每个都有量化证据：

**第一，根因分类准确驱动下游治理**——实测 23 个失败中 API 误用 5 个（22%）、逻辑错 14 个（61%）、环境/资源 2 个（9%）、超时 1 个（4%），分类准确驱动了针对性的下游治理。

**第二，治本使 L1 注入从净负转净正**——这是最关键的证据。治本前 L1 注入**净负**，093 铁证：一条标"已验证"的条目声称参数名 `isReplaceMismatched` 是错的、正确的是 `isReplaceMissmatched`（两个 s），Agent 采信后把对的参数改错导致 fail——实际 API 根本不接受任何 isReplace* kwarg，这条是 Agent 自测时的误判。治本后 L1 注入**净增 17 题**，通过率 74.7% 提到 85.4%，真代码问题降 54%，AssertionError 降 36%。在 challenge split 上自进化 1-2 轮即在 test 上追平人类 V5.4 baseline，R2 方差收敛到与人类一致。
