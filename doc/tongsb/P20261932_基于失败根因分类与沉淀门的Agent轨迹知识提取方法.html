1技术领域 (Field)

本发明涉及人工智能领域的大语言模型 Agent 轨迹知识提取技术，具体涉及一种基于失败根因六分类与沉淀门（sedimentation gate）的 Agent 任务轨迹知识提取与沉淀方法。

所述方法面向电子设计自动化（EDA）场景下的代码生成 Agent：Agent 接收自然语言任务需求，调用 EDA 软件 API 编写 Python 代码并在远程沙箱执行，由隐藏测试用例判定通过/失败。一轮 benchmark 含 158 个任务，每个任务留下完整对话轨迹（搜索记录、API 调用、错误日志、成败信号）。本方法从这些轨迹中提取可复用知识，但并非所有轨迹都值得提取——环境故障和生成失败不含 API 使用信号，若强行沉淀会用环境噪声冒充 API 教训，污染知识库。

本发明通过失败根因六分类对每个失败任务判定"为什么会失败"（而非仅"发生了什么"），并通过沉淀门筛选哪些失败任务进入知识提取流程、哪些跳过，从而保证沉淀知识的信号质量。

本发明适用于一切"失败原因可分类、知识提取有信号质量要求"的 LLM Agent 轨迹挖掘场景。

2先前技术 (Related prior art)

2.1 不分根因的轨迹反思方法

Reflexion（Shinn et al.）让 Agent 对所有失败任务做反思并写入记忆，不区分失败原因。其缺陷：环境超时、生成失败这类不含 API 使用信号的失败也被反思，产出"似是而非"的教训。论文 Table 3 证实：无可靠测试信号时反思反而有害（52% < 60% 基线），在噪声上做反思会产生"harmful edits"。

2.2 基于错误码的失败处理方法

常见做法是按错误码（TypeError/AttributeError/TimeoutError 等）分类处理。但错误码只描述"发生了什么"（what），不描述"为什么会发生"（why）。例如一个任务搜了很多 API（看起来像检索缺失），但最终报参数类型错——错误码是 TypeError，但根因是"用错了 API"而非"没搜到"。仅靠错误码会误归类。

2.3 不分信号可靠性的反思方法

各类反思方法对所有失败一视同仁地做语义反思。但失败信号有可靠性分层：

  • 属性错/类型错（明确指向用错 API 或参数）——信号最强；
  • 断言错（代码能跑但结果不对，不知是 API 选错还是逻辑写错）——信号半可靠；
  • 未知错——纯猜测。

对低信号失败做激进反思会沉淀噪声知识。

2.4 规则引擎越权的提取方法

部分方法用纯规则提取器对所有失败产出"待验证"条目。但向量检索出的 API"看起来总是相关的"（词重叠近乎必然命中），规则无法区分"似是而非"——只有 LLM 能做"API 方向对但参数错"这种语义判断。规则引擎产出"待验证"会引入大量假阳性。

2.5 现有技术的共同不足

不足现有技术表现本发明解决方式
不分根因环境噪声也沉淀为 API 教训六分类 + 沉淀门筛选
错误码即根因TypeError 误判为检索缺失根因与错误码两层，多对一收敛
信号不分层低信号失败激进反思低信号保守判断，宁不沉淀
规则越权规则产"待验证"假阳性规则只产"已验证"，"待验证"专属 LLM
成败混判通过任务的错误当失败教训四类反思都锚定成功信号

3发明目的与技术问题 (Motivation & challenge)

3.1 发明目的

提供一种从 Agent 任务轨迹中提取可复用知识的方法，使沉淀的知识具有高信号质量——只从"含 API 使用信号"的失败中提取教训，跳过环境噪声和生成失败，且对低信号失败采取保守策略，避免"似是而非"的知识系统性误导下游 Agent。

3.2 技术挑战

挑战 1：失败原因的粗粒度归类

错误码是细粒度的"表象"（15 类，如 TypeError/AttributeError/TimeoutError），但下游知识提取需要粗粒度的"根因"（"是检索问题、API 用法问题还是逻辑问题"）。需要一个多对一收敛的根因分类器，将 15 类错误码归入 6 类根因，作为"要不要沉淀、沉淀成什么"的依据。

挑战 2：API 误用与检索缺失的判定顺序

一个任务可能搜了很多 API（看起来像检索缺失），但最终报参数类型错——根因是"用错了"而非"没搜到"。若先判检索缺失会误归类，把"搜得多但用错"误判为检索问题，产出错误的"该多搜"教训。需要让 API 误用先于检索缺失判定。

挑战 3：无信号失败的过滤

环境故障（沙箱超时、session 初始化失败）和生成失败（没产出代码）不含 API 使用信号。若强行反思沉淀，产出的"教训"实质是环境噪声冒充 API 教训，会污染知识库。需要一个沉淀门，让无信号失败跳过 API 反思。

挑战 4：低信号失败的保守判断

断言错（AssertFail）、未知错（Unknown）、执行错这三类只说"结果不符"，说不清是 API 选错、参数错还是逻辑错。对这类低信号失败做激进反思会沉淀噪声。需要注入不确定性提示，要求保守判断——只有 API 明确相关才产条目，有疑虑返回"无"。

挑战 5：规则引擎与 LLM 的职责边界

规则引擎（确定性、便宜）适合做"成功→已验证"这种明确判定，但不适合做"失败→API 方向对不对"这种语义判断（向量检索出的 API 看起来总相关，规则无法判似是而非）。需要明确划分：规则只产"已验证"，"待验证"专属 LLM，避免规则越权引入假阳性。

挑战 6：通过任务的错误不当失败教训

通过的任务在尝试过程中也报过错（后来修好了），这些错误不是失败信号。若把通过任务的中间错误当失败教训沉淀，会产出错误的负向知识。需要让反思锚定最终成败信号——通过的任务的错误不是失败信号。

挑战 7：错误 API 的精准归因

失败任务的错误日志中，报错的 API 可能不是第一个调用的 API（旧方法用 used_apis[0] 粗略归因，常归错）。需要从错误日志文本中精准提取真正报错的 API 名，用于反例计数与知识归因。

4技术方案 (Technical solution)

本发明提供一种基于失败根因分类与沉淀门的 Agent 轨迹知识提取方法，包括 双层失败标注模块、六分类根因判定模块、沉淀门筛选模块、信号可靠性分层反思模块、规则引擎与 LLM 双路径职责划分模块 五部分。

4.1 双层失败标注模块

每个失败任务有两层标注：

  • 错误码（what——发生了什么）：15 类，如 TypeError/AttributeError/ImportError/AssertionError/TimeoutError 等，从错误日志的异常类型提取；
  • 失败根因（why——为什么会失败）：6 类，由根因分类函数在所有富集完成后统一计算（保证生成状态、代码数、错误都齐备）。
两层关系：错误码是细粒度"表象"（15 类），失败根因是粗粒度"根因"（6 类），多对一收敛——多个错误码归入一个根因。例如 TypeError、AttributeError、ImportError 三个错误码都归入"③ API 误用"根因；各种 Timeout 归入"① 环境故障"。

4.2 六分类根因判定模块

根因分类函数（classify_failure_root）按优先级递减顺序判定，返回 6 类之一：

优先级根因判定条件含义是否沉淀
0SUCCESSexecution_success == True通过沉淀正面经验
1ENV_FAILURE错误码 ∈ {SANDBOX_TIMEOUT, SESSION_INIT_ERROR, ...}环境故障跳过沉淀
2GEN_FAILUREgen_status == "fail" 或 (codes==0 且 apis==0 且无错误)生成失败跳过沉淀
3API_MISUSE错误码 ∈ {TYPE_ERROR, ATTRIBUTE_ERROR, IMPORT_ERROR}API 误用沉淀
4SEARCH_MISS(codes==0 且 apis>0) 或 (searches>5 且 apis≤2)检索缺失沉淀
5LOGIC_ERRORASSERTION_ERROR 或 (codes>0 且 apis>0 且无非 UNKNOWN 错误)逻辑错沉淀
6UNKNOWN兜底未知兜底
关键设计：API 误用先于检索缺失判定。一个任务可能搜了很多 API（看起来像检索缺失），但若最终报参数类型错/属性错/导入错，根因是"用错了"而非"没搜到"。先判 API 误用避免把"搜得多但用错"误判为检索问题。

4.3 沉淀门筛选模块

沉淀门：环境故障和生成故障不含 API 使用信号，沉淀进来只会用环境噪声冒充 API 教训，故跳过 API 反思。其余 4 类（API 误用/检索缺失/逻辑错/未知）进入反思。

failure_root = classify_failure_root(artifact)
if failure_root in ("ENV_FAILURE", "GEN_FAILURE"):
    跳过 API 反思（环境故障类仍允许"决策反思"——若存在重复搜索等退化行为）
else:
    进入四类反思
技术效果：过滤无信号失败，保证沉淀知识的信号质量。实测环境故障类失败若被反思，产出的"教训"指向沙箱缺资源等环境问题，对下游 API 选择毫无指导价值。

4.4 信号可靠性分层反思模块

进入反思的失败任务，按失败信号的可靠性分层采取不同策略：

信号可靠性对应根因/错误码反思策略
最强API 误用（属性错/类型错/导入错）明确指向用错 API 或参数，正常反思
半可靠逻辑错（断言错）代码能跑但结果不对，不知 API 选错还是逻辑写错，保守判断
纯猜测未知错保守判断，有疑虑返回"无"

低信号保守判断：对断言错、未知错、执行错这三类低信号失败，场景反思注入不确定性提示与保守指引，要求 LLM 保守——只有 API 明确相关才产"待验证"条目，有疑虑返回"无"（→ 不写"待验证"条目，回退到坑点反思）。

4.5 四类反思都锚定成功信号

图 6 · 四类反思锚定成功信号时序
  • 场景反思（reflect_on_scenario）：成功产"已验证"；失败由 LLM 判 API 方向，产"待验证"；
  • 坑点反思（reflect_on_pitfall）：仅失败产出，成功时短路返回 None——"通过的任务的错误不是失败信号"；
  • 错→修反思（reflect_on_error_to_fix）：仅失败产出；
  • 决策反思（reflect_on_decision）：有重复搜索等退化行为时产出。

4.6 规则引擎与 LLM 双路径职责划分模块

LLM 路径（主）：批量反思函数用线程池（默认 5 并发）跑 4 类反思，受 REFLECTION_ENABLED 开关控制。

规则引擎路径（fallback）：纯规则提取器，仅在 LLM 反思关闭时启用。

核心设计——规则引擎不越权：规则版的场景提取是两态——成功产"已验证"，失败返回 None（不产条目）。不产"待验证"。因为向量检索出的 API"看起来总是相关的"（词重叠近乎必然命中），规则无法区分"似是而非"——只有 LLM 能做"API 方向对但参数错"这种语义判断。故"待验证"是 LLM 专属。
图 5 · 规则引擎不越权："待验证"专属 LLM，规则只产"已验证"

4.7 状态前缀由系统强制

无论 LLM 输出什么前缀，系统都剥掉再用 ground-truth 成败重写：

description = strip_status(description)               # 剥掉 LLM 自己加的前缀
authoritative_status = "verified" if success else "unverified"
description = f"[{authoritative_status}] {description}"  # 用真实成败重写

保证成功→"已验证"、失败→"待验证"绝对可靠。状态标签下游直接决定检索优先级与渲染，必须 100% 可信。

4.8 错误 API 的精准归因

失败任务的错误日志中，报错的 API 可能不是第一个调用的 API。本方法从错误日志文本中按优先级匹配 5 种模式精准提取真正报错的 API 名：

_ERROR_API_PATTERNS = [
    re.compile(r"in method '(\w+)'"),                    # SWIG TypeError
    re.compile(r"module 'pyAether' has no attribute '(\w+)'"),  # AttributeError
    re.compile(r"cannot import name '(\w+)'"),           # ImportError
    re.compile(r"invalid keyword argument for (\w+)"),   # wrong kwarg
    re.compile(r"(\w+)\(\) (?:got an? unexpected|missing required)"),  # 缺参/多参
]

用于反例计数（disconfirmation）：一个"已验证"的 API 场景条目，若被多个失败任务的真正报错 API 命中，记为反例，注入时加⚠️警告。

归因规则：反例只算 API_MISUSE（逻辑错/环境错不归因到 API——逻辑错说不清是哪个 API 的错，环境错与 API 无关）。

4.9 治本：不沉淀 Agent 推断

093 铁证：一条标"已验证"的条目声称参数名 isReplaceMismatched（一个 s）是错的、正确的是 isReplaceMissmatched（两个 s）。Agent 采信后把对的位置参数改成 kwarg → fail。实际 API 根本不接受任何 isReplace* kwarg。这条"测试发现"是 Agent 自测时的误判，被标"已验证"后系统性误导下游。
治法：反思规则改为"只陈述 Agent 代码真实调用的 API（used_apis 事实），不推断'正确 wrapper pattern'/'正确参数名'/'用属性 X 还是 setter Y'——这些是 Agent 猜测可能错"。L1 只沉淀 used_apis 事实 + ground-truth 验证的用法，不沉淀 Agent 的"测试发现/参数名修正/属性写法"类推断。

5有益效果 (Advantageous effects)

5.1 沉淀门过滤无信号失败，提升知识信号质量
环境故障和生成失败被沉淀门跳过，不进入 API 反思。实测若不过滤，环境故障产出的"教训"指向沙箱缺资源，对下游 API 选择毫无价值且污染知识库。沉淀门保证沉淀的每条知识都来自含 API 使用信号的失败。
5.2 API 误用先判避免误归类
"搜得多但用错"的任务若先判检索缺失会产出错误的"该多搜"教训。API 误用先判确保根因归因准确。实测 V5+evo 23 个失败中 API 误用 5 个（22%）、逻辑错 14 个（61%）、环境/资源 2 个（9%）、超时 1 个（4%），分类准确驱动了针对性的下游治理。
5.3 低信号保守判断避免噪声沉淀
对断言错/未知错的保守判断（宁不沉淀也不沉淀错的）对照 Reflexion 论文（无测试+反思=52% 比基线 60% 差），本发明通过保守策略避免在低信号上做有害编辑。
5.4 规则引擎不越权消除假阳性
规则版只产"已验证"（成功时），不产"待验证"，消除了"向量检索出的 API 看起来总相关"导致的假阳性。"待验证"专属 LLM 的语义判断，保证每条"待验证"都经过"API 方向对但参数错"的语义判定。
5.5 四类反思锚定成功信号避免错误负向知识
通过任务的错误不当失败教训——坑点/错→修反思在成功时短路返回 None。这避免了"通过的任务中间报过的错被当失败教训"的错误负向知识。
5.6 状态前缀系统强制保证可信
LLM 偶尔不遵循格式，系统强制补前缀消除不确定性。状态标签下游直接决定检索优先级与渲染，100% 可信使分层注入（已验证>待验证>无标签）可靠工作。
5.7 治本（不沉淀推断）使 L1 注入从净负转净正
治本前 L1 注入净负（093 铁证：含 Agent 推断的错误参数名"已验证"条目系统性误导，净 -5 题）；治本后（不沉淀 agent 推断 + [已验证] 严格化）L1 注入净 +17 题（74.7% → 85.4%），真代码问题降 54%，AssertionError 降 36%。
5.8 错误 API 精准归因提升反例计数准确性
旧方法用 used_apis[0]（第一个调用 API）粗略归因常归错。精准归因从错误日志提取真正报错的 API，使反例计数准确——"已验证"条目被多个失败任务的真正报错 API 命中时加⚠️警告，防止单一失败噪声污染已被多次成功确认的经验（降级守卫）。

5.9 自进化复现人类手工进化

6具体实施方式 (Detailed embodiments)

实施例 1：六分类根因判定函数

_ENV_ERROR_CODES = frozenset({"SANDBOX_TIMEOUT", "SESSION_INIT_ERROR",
                               "CONNECTION_ERROR", "FILE_NOT_FOUND"})
_API_MISUSE_CODES = frozenset({"TYPE_ERROR", "ATTRIBUTE_ERROR", "IMPORT_ERROR"})

def classify_failure_root(artifact: dict) -> str:
    if artifact.get("execution_success", False):
        return "SUCCESS"
    error_codes = {e.get("error_code", "") for e in artifact.get("errors", [])}
    searches = artifact.get("searches", [])
    apis = artifact.get("apis_fetched", [])
    codes = artifact.get("codes_executed", 0)
    gen_status = artifact.get("gen_status", "")

    # 1. ENV_FAILURE（优先级最高）
    if error_codes & _ENV_ERROR_CODES:
        return "ENV_FAILURE"
    # 2. GEN_FAILURE
    if gen_status == "fail":
        return "GEN_FAILURE"
    if codes == 0 and len(apis) == 0 and not error_codes:
        return "GEN_FAILURE"
    # 3. API_MISUSE（先于 SEARCH_MISS！）
    if error_codes & _API_MISUSE_CODES:
        return "API_MISUSE"
    # 4. SEARCH_MISS
    if codes == 0 and len(apis) > 0:
        return "SEARCH_MISS"
    if len(searches) > 5 and len(apis) <= 2:
        return "SEARCH_MISS"
    # 5. LOGIC_ERROR
    if "ASSERTION_ERROR" in error_codes:
        return "LOGIC_ERROR"
    if codes > 0 and len(apis) > 0 and not (error_codes - {"UNKNOWN_ERROR"}):
        return "LOGIC_ERROR"
    # 6. 兜底
    return "UNKNOWN"

def extract_error_api(error_log: str) -> str | None:
    for pat in _ERROR_API_PATTERNS:  # 5 种模式，按优先级
        m = pat.search(error_log)
        if m:
            return m.group(1)
    return None  # 纯 AssertionError 无 API 名 → 正确返回 None

def _count_disconfirmations(artifacts, l1_filepath, current_batch):
    errored_apis = set()
    for a in artifacts:
        if a.get("execution_success"): continue
        if a.get("failure_root") != "API_MISUSE": continue  # 反例只算 API_MISUSE
        for err in a.get("errors", []):
            api = extract_error_api(err.get("error_log", ""))
            if api: errored_apis.add(api)
