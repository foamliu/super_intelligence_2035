1技术领域 (Field)

本发明涉及人工智能领域的大语言模型 Agent 轨迹知识提取技术，具体涉及一种基于失败根因六分类与沉淀门（sedimentation gate）的 Agent 任务轨迹知识提取与沉淀方法。

所述方法面向电子设计自动化（EDA）场景下的代码生成 Agent：Agent 接收自然语言任务需求，调用 EDA 软件 API 编写 Python 代码并在远程沙箱执行，由隐藏测试用例判定通过/失败。一轮 benchmark 含 158 个任务，每个任务留下完整对话轨迹（搜索记录、API 调用、错误日志、成败信号）。本方法从这些轨迹中提取可复用知识，但并非所有轨迹都值得提取——环境故障和生成失败不含 API 使用信号，若强行沉淀会用环境噪声冒充 API 教训，污染知识库。

本发明通过失败根因六分类对每个失败任务判定"为什么会失败"（而非仅"发生了什么"），并通过沉淀门筛选哪些失败任务进入知识提取流程、哪些跳过，从而保证沉淀知识的信号质量。

本发明适用于一切"失败原因可分类、知识提取有信号质量要求"的 LLM Agent 轨迹挖掘场景。

2先前技术 (Related prior art)

2.1 Reflexion：对所有失败一视同仁反思

Reflexion（Shinn et al.）让 Agent 对所有失败任务做反思并写入记忆，不区分失败原因。其缺陷：环境超时、生成失败这类不含 API 使用信号的失败也被反思，产出"似是而非"的教训。论文 Table 3 证实：无可靠测试信号时反思反而有害（52% < 60% 基线），在噪声上做反思会产生"harmful edits"。问题：如何按失败根因筛选哪些失败值得反思、哪些应跳过。

2.2 AutoGPT / BabyAGI：无信号失败不收敛

AutoGPT / BabyAGI（2023 现象级开源 Agent）让 LLM 自主规划与执行，但循环里没有任何信号告诉它是否在进步——它会"plausible-sounding plans 跑几小时，最终产出一文件夹半成品"。这类无信号失败若被反思沉淀，产出的"教训"实质是环境噪声冒充 API 教训，污染知识库。问题：如何识别并过滤不含 API 使用信号的环境故障 / 生成失败。

2.3 OpenCode：失败无根因分类导致重试不收敛

OpenCode（22M+ 开发者使用的开源 Coding Agent）对失败仅由 LLM 自行重试，无根因分类——所有失败一视同仁按错误码（API 错、配置错、网络错）查 troubleshooting 文档。但错误码只描述"发生了什么"（what），不描述"为什么会发生"（why）：一个任务搜了很多 API 但最终报 TypeError，错误码是 TypeError，根因却是"用错了 API"而非"没搜到"。仅靠错误码会误归类，导致重试方向错误、不收敛。问题：如何把细粒度错误码多对一收敛为粗粒度失败根因，作为"要不要沉淀、沉淀成什么"的依据。

3发明目的与技术问题 (Motivation & challenge)

3.1 发明目的

提供一种从 Agent 任务轨迹中提取可复用知识的方法，使沉淀的知识具有高信号质量——只从"含 API 使用信号"的失败中提取教训，跳过环境噪声和生成失败，且对低信号失败采取保守策略，避免"似是而非"的知识系统性误导下游 Agent。

3.2 技术挑战

挑战 1：失败原因的粗粒度归类

错误码（TypeError/AttributeError/TimeoutError 等 15 类）只描述"发生了什么"（what），但"要不要沉淀、沉淀成什么"需要的是粗粒度"根因"（why）——是检索问题、API 用法问题还是逻辑问题。需要一个多对一收敛的根因分类器将 15 类错误码归入 6 类根因。关键约束：API 误用须先于检索缺失判定，否则"搜得多但用错"会被误判为检索问题，产出错误的"该多搜"教训。

挑战 2：无信号失败的过滤

环境故障（沙箱超时、session 初始化失败）和生成失败（没产出代码）不含 API 使用信号。若强行反思沉淀，产出的"教训"实质是环境噪声冒充 API 教训，污染知识库。需要一个沉淀门让无信号失败跳过 API 反思。

挑战 3：低信号失败的可靠性分层

即便过了沉淀门，失败信号的可靠性仍分层：属性错/类型错明确指向用错 API（信号最强）；断言错/未知错只说"结果不符"，说不清是 API 选错、参数错还是逻辑错（半可靠/纯猜测）。对低信号失败激进反思会沉淀噪声。此外通过的任务在尝试过程中也报过错（后来修好了），这些错误不是失败信号。需要按信号可靠性分层采取不同策略，并锚定最终成败而非中间错误。

4技术方案 (Technical solution)

本发明提供一种基于失败根因分类与沉淀门的 Agent 轨迹知识提取方法，包括 双层失败标注模块、六分类根因判定模块、沉淀门筛选模块、信号可靠性分层反思模块、规则引擎与 LLM 双路径职责划分模块 五部分。

4.1 双层失败标注与六分类根因判定

每个失败任务有两层标注：错误码（what，15 类，从错误日志异常类型提取）与失败根因（why，6 类，由根因分类函数在所有富集完成后统一计算）。两层多对一收敛——例如 TypeError/AttributeError/ImportError 都归入"③ API 误用"，各种 Timeout 归入"① 环境故障"。

根因分类函数（classify_failure_root）按优先级递减顺序判定，返回 6 类之一：

优先级根因判定条件含义是否沉淀
0SUCCESSexecution_success == True通过沉淀正面经验
1ENV_FAILURE错误码 ∈ {SANDBOX_TIMEOUT, SESSION_INIT_ERROR, ...}环境故障跳过沉淀
2GEN_FAILUREgen_status == "fail" 或 (codes==0 且 apis==0 且无错误)生成失败跳过沉淀
3API_MISUSE错误码 ∈ {TYPE_ERROR, ATTRIBUTE_ERROR, IMPORT_ERROR}API 误用沉淀
4SEARCH_MISS(codes==0 且 apis>0) 或 (searches>5 且 apis≤2)检索缺失沉淀
5LOGIC_ERRORASSERTION_ERROR 或 (codes>0 且 apis>0 且无非 UNKNOWN 错误)逻辑错沉淀
6UNKNOWN兜底未知兜底
关键设计：API 误用先于检索缺失判定。一个任务可能搜了很多 API（看起来像检索缺失），但若最终报参数类型错/属性错/导入错，根因是"用错了"而非"没搜到"。先判 API 误用避免把"搜得多但用错"误判为检索问题。

4.2 沉淀门筛选模块

沉淀门：环境故障和生成故障不含 API 使用信号，沉淀进来只会用环境噪声冒充 API 教训，故跳过 API 反思。其余 4 类（API 误用/检索缺失/逻辑错/未知）进入反思。

failure_root = classify_failure_root(artifact)
if failure_root in ("ENV_FAILURE", "GEN_FAILURE"):
    跳过 API 反思（环境故障类仍允许"决策反思"——若存在重复搜索等退化行为）
else:
    进入四类反思
技术效果：过滤无信号失败，保证沉淀知识的信号质量。实测环境故障类失败若被反思，产出的"教训"指向沙箱缺资源等环境问题，对下游 API 选择毫无指导价值。

4.3 信号可靠性分层反思（含成败锚定）

进入反思的失败任务，按失败信号的可靠性分层采取不同策略：

信号可靠性对应根因/错误码反思策略
最强API 误用（属性错/类型错/导入错）明确指向用错 API 或参数，正常反思
半可靠逻辑错（断言错）代码能跑但结果不对，不知 API 选错还是逻辑写错，保守判断
纯猜测未知错保守判断，有疑虑返回"无"

低信号保守判断：对断言错、未知错、执行错这三类低信号失败，场景反思注入不确定性提示与保守指引，要求 LLM 保守——只有 API 明确相关才产"待验证"条目，有疑虑返回"无"（→ 不写"待验证"条目，回退到坑点反思）。

4.4 知识可信度保障（双路径职责 / 状态强制 / 精准归因 / 不沉淀推断）

为保证沉淀出来的知识可信，本方法在反思产出后施加四项保障：

  • 规则引擎不越权：规则版场景提取是两态——成功产"已验证"，失败返回 None（不产条目），不产"待验证"。因为向量检索出的 API"看起来总是相关的"（词重叠近乎必然命中），规则无法区分"似是而非"，"待验证"专属 LLM 的语义判断。
  • 状态前缀系统强制：无论 LLM 输出什么前缀，系统都剥掉再用 ground-truth 成败重写（authoritative_status = "verified" if success else "unverified"），保证状态标签 100% 可信。
  • 错误 API 精准归因：从错误日志文本按 5 种模式（SWIG TypeError / AttributeError / ImportError / wrong kwarg / 缺参多参）提取真正报错的 API 名，用于反例计数——"已验证"条目被多个失败任务的真正报错 API 命中时加⚠️警告。反例只算 API_MISUSE（逻辑错/环境错不归因到 API）。
  • 治本：不沉淀 Agent 推断：反思规则改为"只陈述 Agent 代码真实调用的 API（used_apis 事实），不推断'正确 wrapper pattern'/'正确参数名'/'用属性 X 还是 setter Y'"。L1 只沉淀 used_apis 事实 + ground-truth 验证的用法，不沉淀 Agent 的"测试发现/参数名修正"类推断。
093 铁证（治本动因）：治本前一条标"已验证"的条目声称参数名 isReplaceMismatched（一个 s）是错的、正确的是 isReplaceMissmatched（两个 s）。Agent 采信后把对的位置参数改成 kwarg → fail。实际 API 根本不接受任何 isReplace* kwarg。这条"测试发现"是 Agent 自测时的误判，被标"已验证"后系统性误导下游。

5有益效果 (Advantageous effects)

5.1 根因分类准确驱动下游治理
沉淀门跳过环境故障/生成失败（不含 API 信号），API 误用先判确保"搜得多但用错"不被误判为检索缺失。实测 V5+evo 23 个失败中 API 误用 5 个（22%）、逻辑错 14 个（61%）、环境/资源 2 个（9%）、超时 1 个（4%），分类准确驱动了针对性的下游治理。
5.2 治本使 L1 注入从净负转净正
低信号保守判断 + 锚定最终成败 + 规则不越权 + 状态强制 + 不沉淀 Agent 推断，共同保证沉淀知识可信。治本前 L1 注入净负（093 铁证：含 Agent 推断的错误参数名"已验证"条目系统性误导，净 -5 题）；治本后 L1 注入净 +17 题（74.7% → 85.4%），真代码问题降 54%，AssertionError 降 36%。在 challenge split 上，自进化经 1-2 轮沉淀即在 test 上追平人类 V5.4 baseline（80.8%），R2 方差收敛到与人类一致（±3.82%）——根因分类 + 沉淀门 + 信号分层 + 治本是这一效果的前提。

6具体实施方式 (Detailed embodiments)

实施例 1：六分类根因判定函数

_ENV_ERROR_CODES = frozenset({"SANDBOX_TIMEOUT", "SESSION_INIT_ERROR",
                               "CONNECTION_ERROR", "FILE_NOT_FOUND"})
_API_MISUSE_CODES = frozenset({"TYPE_ERROR", "ATTRIBUTE_ERROR", "IMPORT_ERROR"})

def classify_failure_root(artifact: dict) -> str:
    if artifact.get("execution_success", False):
        return "SUCCESS"
    error_codes = {e.get("error_code", "") for e in artifact.get("errors", [])}
    searches = artifact.get("searches", [])
    apis = artifact.get("apis_fetched", [])
    codes = artifact.get("codes_executed", 0)
    gen_status = artifact.get("gen_status", "")

    # 1. ENV_FAILURE（优先级最高）
    if error_codes & _ENV_ERROR_CODES:
        return "ENV_FAILURE"
    # 2. GEN_FAILURE
    if gen_status == "fail":
        return "GEN_FAILURE"
    if codes == 0 and len(apis) == 0 and not error_codes:
        return "GEN_FAILURE"
    # 3. API_MISUSE（先于 SEARCH_MISS！）
    if error_codes & _API_MISUSE_CODES:
        return "API_MISUSE"
    # 4. SEARCH_MISS
    if codes == 0 and len(apis) > 0:
        return "SEARCH_MISS"
    if len(searches) > 5 and len(apis) <= 2:
        return "SEARCH_MISS"
    # 5. LOGIC_ERROR
    if "ASSERTION_ERROR" in error_codes:
        return "LOGIC_ERROR"
    if codes > 0 and len(apis) > 0 and not (error_codes - {"UNKNOWN_ERROR"}):
        return "LOGIC_ERROR"
    # 6. 兜底
    return "UNKNOWN"
