📖 阅读前：这个系统在干什么

读懂下文前，先建立几个基本概念：

  • EDA：电子设计自动化（Electronic Design Automation），用于做电路版图/芯片设计。
  • API：这里指 EDA 软件 pyAether（华大九天 Empyrean 平台）暴露的 Python 编程接口。这些 API 数量庞大（8000+），分三套等价命名前缀：过程式 db*（database 前缀，如 dbCrtInst）、面向对象 emy*（Empyrean 前缀，如 emyDesign.create）、底层 ae*（aether 前缀），三套常指同一个操作、可互相替换。另有 goa*（GOA = Geometric Operation Analysis，几何运算族）一族互相关联。详见 §3.5。
  • 谁在用：AI 编程 agent（如 Cline/Claude）。agent 拿到自然语言需求后，要写出调用这些 API 的代码——但它不可能记住 8000 个 API，所以需要检索：按自然语言描述找到正确的 API。
  • MCP：Model Context Protocol（模型上下文协议）。MCP Server 是挂载在 agent 旁的工具服务端，agent 通过它调用检索工具。本报告讲的"检索 API"就是 MCP Server 暴露给 agent 的工具。
  • 向量库（ChromaDB）：一个向量数据库，把每个 API 名字转成向量嵌入存起来，检索时按语义相似度找。本系统的一个关键约束：向量库只嵌入了 API 名称（不含描述全文），这决定了后续为何要补 BM25、要做缩写展开。
  • BM25：经典文本检索算法，按词频打分。本系统用它补充向量检索（BM25 索引了 API 描述全文，能命中向量漏掉的）。

一句话概括：agent 用自然语言搜 EDA API，本系统提供三个检索工具（语义向量 / 关键词 / 精确）协同找到正确 API，并用缩写映射、BM25 补充、零结果警告等机制弥补向量检索的盲区。

1系统总览：三工具协作架构

EDA FastMCP 提供三个检索工具，覆盖 语义 关键词 精确 三种搜索模式：

主路 search_apis

检索模式：向量语义 + BM25 始终补充

适用场景：自然语言描述（如 "get current design"）

返回格式：{api_name, description, similarity, source?}

核心特性：查询双向缩写展开 → 向量检索 → BM25 补充最多 3 条 → 零结果警告

补路 search_apis_by_keyword

检索模式：名称 Token Overlap + BM25 描述匹配

适用场景：缩写查找（CV/DM）、API 名片段（dbCrtInst）

返回格式：{api_name, description, similarity, source, note}

核心特性：query 分类路由 → keyword search → 软重定向/精确匹配 → 零结果警告

精确 get_api_details

检索模式：精确匹配 + 多级模糊容错

适用场景：已知 API 名（来自搜索结果或任务描述），获取完整文档

返回格式：{api_name, api_type, description, properties, inheritance_relations}

核心特性：精确匹配 → 唯一前缀匹配 → 大小写不敏感 → 候选提示

2search_apis：语义向量 + BM25 始终补充

2.1 执行流程

1

双向缩写展开：对 query 同时做缩写→全称（expand_query）和全称→缩写（expand_query_reverse），合并去重后生成 enriched_query

2

向量检索：HTTP POST 到远程 ChromaDB 服务，用 enriched_query 做 cosine similarity 搜索

3

BM25 始终补充：无条件执行，从 keyword_search 获取结果，去重后追加在向量结果后面

4

零结果警告：向量+BM25 都无结果时，返回 NO_RESULTS + search_warning

2.2 双向缩写展开

设计动机：向量库只嵌入 API 名称（不含描述），"create instance" 的 embedding 无法关联到 dbCrtInst（Crt=Create）。需要两个方向同时展开：
方向 1 缩写 → 全称

"DM file object"
→ "DM Design Manager file object"

让向量 embedding 能关联到全称语义

实际触发率仅 4% Agent 几乎从不输入缩写

方向 2 全称 → 缩写

"create instance"
→ "create instance crt inst"

让向量 embedding 能关联到 API 名中的缩写 token

核心方向 这才是解决命名鸿沟的关键

2.3 BM25 始终补充

设计动机：向量库仅嵌入 API 名，自然语言 query "polygon boolean operation" 搜不到 emyPointArrayAnd（名字里没有 "polygon"）。BM25 索引了描述全文，能命中向量遗漏的 API。
参数值说明
BM25_SUPPLEMENT_K3最多追加 3 条 BM25 结果
补充策略去重追加BM25 结果去重后追加在向量结果后面，不截断向量结果
source 标注bm25_fallback通过 source 字段区分向量结果和 BM25 补充
分数字段统一score → similarity字段名统一，但两者分数不可比（0-1 vs 0-30+）
分数不可比：向量 similarity 范围 0-1，BM25 score 范围 0-30+。统一到 similarity 字段仅是为了输出格式一致，不代表分数可比。必须用 source 字段区分来源。

2.4 查询示例

query = "polygon boolean operation"
# Step 1: 双向展开
expand_query:       "polygon boolean operation" → 无缩写可展开 → 不变
expand_query_reverse: "polygon boolean operation" → 无全称→缩写命中 → 不变

# Step 2: 向量检索
→ emyPointArrayAnd (sim=0.43)    # 名字含 "PointArray" 不含 "polygon"，向量弱命中
→ emyPointArrayOr  (sim=0.41)
→ dbSingleLayerGOA (sim=0.38)

# Step 3: BM25 补充（描述含 "polygon boolean"）
→ dbLayerOr        (sim=12.5, source=bm25_fallback)  ← 描述含 "polygon boolean"
→ dbPointArrayOr   (sim=9.8,  source=bm25_fallback)  ← 描述含 "point array or"
→ goaLayerOr       (sim=8.2,  source=bm25_fallback)  ← 描述含 "geometric or"  (goa* 见 §3.5，几何运算族)

3search_apis_by_keyword：关键词补路

3.1 Query 分类路由

设计动机：Agent 的 query 模式多样——纯缩写（CV）、API 名片段（dbCrtInst）、自然语言（create net）。不同模式需要不同的检索策略，不能一刀切。

3.2 Soft Redirect（自然语言软重定向）

设计动机

Agent 误用 keyword 工具搜自然语言（V2.0 中 23% 的 keyword query 是自然语言）。不是拒绝，而是自动补充语义搜索结果，让 agent 既看到关键词匹配也看到语义匹配。

# query = "create symbol" (natural_language)
# 1. keyword search → 找到 dbCrtSymbolRect (source=name_overlap)
# 2. soft redirect → api_recall("create symbol", threshold=0.3)  # api_recall 即向量检索函数
# 3. 补充语义结果，标注 source="vector_redirect"

3.3 Exact Match（精确匹配检测）

设计动机

V2.0 中 52% 的 keyword 调用是"工具选择偏移"——agent 用 keyword 做 API 名验证，该用 get_api_details。精确匹配检测直接告诉 agent："这就是你要的 API，别搜了，去查详情"。

# query = "dbCrtInst" (api_name_fragment)
# 1. keyword search → 找到 dbCrtInst (source=name_overlap, score≈0.8)
# 2. exact_match: "dbCrtInst" in data → True!  (data 即内存 API 全量字典，见 §4)
# 3. 移除已有的同名结果，插入:
#    {api_name: "dbCrtInst", similarity: 1.0,
#     source: "exact_match",
#     note: "exact API name match — use get_api_details instead"}

3.4 keyword_search 内部：Token Overlap + BM25 三层排序

读图提示：左半图是两个并行处理分支（A 名称重叠 / B BM25）各自产候选；右半图是排序层 1/2/3——把所有候选按"名称重叠度 NO"高低分到三层再排序。左边的"分支 A/B"和右边的"排序层 1/2/3"是两套不同分类，不是一一对应：分支 A 的高分结果进排序层 1、低分进排序层 2；分支 B（BM25）的结果若同时有名称重叠则进排序层 2 并升权，纯 BM25（无名称重叠）才进排序层 3。

3.5 Synonym Redirect（跨命令族等价提示）

设计动机

EDA API 存在三套等价接口：过程式 db*（database 前缀）、面向对象 emy*.create（Empyrean 前缀）、底层 ae*（aether 前缀），三套常指同一个操作。另有 goa*（GOA = Geometric Operation Analysis，几何运算族）一族互相关联。Agent 搜到 dbCrtRect 后，可能不知道还有 emyRect.create / aeCreateRect。Synonym redirect 自动追加等价 API，扩展 agent 的选择空间。

映射方向示例
db* → emy*.createdbCrtRect → emyRect.create
GOA 族互关联dbLayerAnd → goaLayerAnd、dbSingleLayerGOA（同族几何运算）
ae* → db*/emy*aeCreateRect → dbCrtRect、emyRect.create
不占 top_k 名额：Synonym 追加在 top_k 核心结果之后。即使 top_k=5 已返回 5 条核心结果，synonym 仍会追加。Score = 原结果 × 0.8，体现"推荐"而非"精确命中"。

4get_api_details：精确查询 + 模糊容错

1

精确匹配：api_name in data（data 是加载到内存的 API 全量字典，键为 API 名）— 直接命中返回完整文档

2

唯一前缀匹配：若输入恰是某个 API 名的唯一前缀（即只有这一个 API 以它开头），直接返回该 API。例如输入 "dbCrtSymbol" 若只有 dbCrtSymbolRect 一个 API 以它开头，则直接返回 dbCrtSymbolRect。

3

大小写不敏感："dbcrtinst" 匹配 "dbCrtInst"（仅当唯一匹配时）

4

候选提示：前缀有多个匹配时，返回相似候选列表

设计动机：Agent 拼写 API 名可能有小错（大小写、前缀截断）。四级 fallback 确保大多数拼写偏差都能被容错，而不是直接返回空。

5缩写系统：双向映射 + 驼峰拆分

5.1 缩写映射表设计

大小写区分语义

同一缩写的不同大小写形式映射到不同全称：

缩写全称出现位置
CPCompressemyPointArrayIsRectangleNoCP 中独立全大写 token
CpCheckpointgetCpID 中驼峰内嵌 token

精确匹配优先：query 中的 Cp 一定展开为 Checkpoint，CP 一定展开为 Compress。大小写不敏感的兜底匹配仅在大小写信息已丢失时使用。

5.2 Token 索引构建管线

5.3 _split_expansion：为什么 "CellView" 要拆成 ["Cell", "View"]

索引-查询对称性：如果索引中 "CellView" 作为单个 token "cellview" 存储，那么 query "cell view"（拆成两个 token）永远匹配不到。拆分后索引存 {"cell", "view"}，query 也有 {"cell", "view"}，匹配成功。

5.4 tokenize_query：完整查询 token 变换管线

1

双重分词：本管线对查询和 API 名同样适用。以 API 名 dbOpenCellView 为例——先驼峰拆分（split_camel）把 dbOpenCellView 剥离 db 前缀、拆成 ["Open","Cell","View"] 再转小写；同时整串小写化为 dbopencellview（这是 tokenize_text，只做整串小写）。两路 token 合并去重，得到该 API 名的完整 token 集（tokenize_query 是对用户查询做同样拆词的完整管线）。

2

首字母缩写反查：把多词短语的首字母组合反查缩写，如 "design manager" → "dm"（这样查 "design manager" 也能匹配到名字含 dm 的 API）。

3

⭐ 相邻 token compact 合并："cell" + "view" = "cellview" → 反查 _compact_reverse["cellview"] = "cv"

4

逐词处理：每个 token 检查缩写映射，命中则追加展开词

5

去重：最终 tokens = ["open", "cell", "view", "cv", "dbopencellview"]（最后一个是整串小写 token，用于精确匹配；驼峰拆词和缩写展开是另两路）。前述各示例为简洁有时省略整串 token，实际它在集合里。

相邻 token compact 合并解决了 camelCase 拆分把全称拆散的问题：dbOpenCellView → ["Open", "Cell", "View"]，"Cell"+"View" 重新合并为 "cellview" → 反查到缩写 "cv"，使 query 能匹配 API 名中的 "CV" token。

6评分与排序：F2 + 三层分层 + 异构不混排

6.1 F2 评分（替代 F1）

为什么选 F2 而不是 F1？

F1 对 precision 和 recall 等权。F2 让 recall 权重 = 4× precision。在 EDA API 检索场景中，query 中的噪音词不应压过名字 token 的匹配——F2 偏重 recall，让"名字命中占 name tokens 多数"的好匹配不被 query 里的噪音词拉低。

F2 = 5 × P × R / (4P + R)    # beta=2, recall 权重 4x

# 示例：query="emyDesign open view polygon" vs API=emyDesign
# query tokens（查询拆词）: {emydesign, open, view, polygon}  ← 3 个噪音词
# name tokens（API 名拆词，见 §5 tokenize 管线）: {emy, emydesign, design}
# intersection（交集）: {emydesign}
# P = 1/4 = 0.25（命中1个 / query 共4个 token，被噪音词拉低）
# R = 1/3 = 0.333（命中1个 / name 共3个 token）
# F1 = 2×0.25×0.333 / (0.25+0.333) = 0.286 ← P 低拖累整体
# F2 = 5×0.25×0.333 / (4×0.25+0.333) = 0.312 ← 偏重 R，比 F1 高 ✅

# 关键：R > P 时 F2 > F1（噪音多但名字命中占 name 多数时，F2 给更高分）；
# MIN_SCORE 从 0.3 降到 0.2，配合 F2 让更多合理匹配进入候选

6.2 三层分层排序（替代归一化混排）

为什么不用归一化混排？ Token Overlap 分数范围 0-1，BM25 分数范围 0-30+。两者量级不可比，归一化后固定权重混排本质是 overfit——不同 query 下分数分布不同，一套权重不可能普适。
层级条件排序键含义
排序层 1 name_overlap ≥ 0.5 NO score 降序 高置信名称匹配，BM25 不参与
排序层 2 name_overlap 0.2~0.5 (has_bm25_dual_hit, no_score) 降序 弱名称匹配；BM25 双命中时升权（名字+描述都相关）
排序层 3 纯 BM25（无 name overlap） BM25 score 降序 描述匹配兜底，排在所有名称匹配之后
排序层 2 中 BM25 仅作"升权信号"：不是把 BM25 分数混入排序，而是用布尔值 has_bm25_dual_hit 决定排序层 2 内部的排序。一条 API 如果 name_overlap 和 BM25 都命中，说明名字和描述都相关，应排在纯 NO 结果前面。

6.3 BM25 质量过滤

参数值设计动机
BM25_MIN_SCORE1.0低于 1.0 的 BM25 分数通常是单词弱匹配，统计噪音
BM25_MIN_DESC_LEN10描述为 "Hint"（4字符）等无信息短描述的 API 即使匹配也无助 agent 决策
Name 权重x1（原 x2）名称 token x2 导致同族 API（如 dbCrt* 一批）分数虚高，压跨族相关结果

7边界处理与安全网

关于"规则（Rules）"：本节会提到"常驻规则 Rules"。Rules 不是检索系统的功能，而是挂在 agent 侧的常驻硬约束（Markdown 文件，agent 每次启动都加载）——例如"搜索满 5 次还找不到就停止搜索、直接写保底代码"。检索系统只负责返回结果，"何时该放弃搜索"这类纪律由 Rules 管，二者配合构成安全网。

7.1 零结果警告

双向 fallback

两个搜索工具的零结果警告互相指向对方，形成双向 fallback：

  • search_apis 零结果 → 返回提示"请换用 search_apis_by_keyword"
  • search_apis_by_keyword 零结果 → 返回提示"请换用 search_apis"

仅"零结果"时触发：注意区分两种情况——① 向量无结果（一条都没召回）才触发 fallback 提示；② 向量有结果但结果不相关（agent 拿到的 API 不是它要的）则不触发，因为服务端无法判断结果"对不对"，这种情况靠另一层的常驻规则（Rules）约束 agent："搜索满 5 次还找不到就停止搜索、直接写保底代码"，这是规则层的纪律而非检索层的机制。

7.2 向量 0 结果 + BM25 有结果

BM25 补充结果正常追加。零结果警告不触发（因为 formatted 非空）。这是 BM25 始终补充的设计目标——向量搜不到时 BM25 补上。

# query = "SDL bind individual instance"
# 向量: 0 条（名字和描述都不含 "SDL"）
# BM25: aeCphSetInstPhysicalBinding (source=bm25_fallback)
# 结果: 仅 BM25 补充，无零结果警告
7.3 vector_redirect 排除

search_apis() 做 BM25 补充时，跳过 source="vector_redirect" 的结果。这是防止循环标注：keyword 工具的 soft redirect 产生的语义结果，不应被 search_apis 重新标记为 bm25_fallback。

7.4 Synonym 截断恢复

top_k 截断可能丢弃 BM25 命中的 synonym API。这些 API 在 seen 集中但不在最终结果中。synonym 逻辑会检查被截断的 API 是否是核心结果的 synonym，如果是则从 seen 中移除，以便 synonym redirect 重新拾起并标记为 synonym_redirect。

7.5 Prefix Stripping
为什么剥离 db/ae/pyAether. 前缀？

db/ae 是命令族前缀（database / aether），pyAether. 是模块名前缀（API 以 pyAether.xxx 形式引用时）——三者都是命名空间标记、不是语义内容。如果 dbOpenCV 拆分保留 ["db", "Open", "CV"]，"db" 会匹配所有 db* API（数百个），产生巨大噪音。剥离后 ["Open", "CV"] 才是语义有意义的 token。（emy* 前缀不在此列，因为它经驼峰拆分后本身就是有效语义 token，如 emyDesign → ["emy","design"]，无需剥离。）

保护条件：name[len(prefix)].isupper() 确保只在真正的前缀边界处剥离。aeAndesPMFloorplan 剥离为 AndesPMFloorplan，但假想的 aether 不会剥离。

9典型查询全程追踪

Example 1: query = "CV"（纯缩写） 
=== search_apis("CV") ===
  Step 1: expand_query("CV") → "CV CellView"  (CV→CellView 方向)
          expand_query_reverse("CV") → "CV"    (CellView不在query中，无需反向)
          enriched = "CV CellView"
  Step 2: api_recall("CV CellView") → 向量检索
  Step 3: BM25补充 → dbOpenCV等（描述含"CellView"）

=== search_apis_by_keyword("CV") ===
  classify_query("CV") → "abbreviation" (≤4字符+全大写)
  keyword_search("CV"):
    tokenize_query("CV") → ["cv", "cell", "view"]
    name_overlap: dbOpenCV→F2=0.83, emyCellView→F2=0.75 → 排序层 1
    BM25: dbOpenCVByType等 → 排序层 3
    synonym: 无
  → 返回 name_overlap + bm25 结果
Example 2: query = "dbCrtInst"（API 名片段） 
=== search_apis("dbCrtInst") ===
  Step 1: expand_query → 补 "Create" "instance"（Crt→Create、Inst→Instance 展开）
          expand_query_reverse → 补 "crt inst"（create→crt、instance→inst）
          enriched = "dbCrtInst Create instance crt inst"（原词 + 两向展开词）
  Step 2: 向量检索（enriched query）
  Step 3: BM25补充

=== search_apis_by_keyword("dbCrtInst") ===
  classify_query("dbCrtInst") → "api_name_fragment" (CamelCase)
  keyword_search → name_overlap: dbCrtInst→F2≈0.8
  exact_match: "dbCrtInst" in data → ✅!  (data 即内存 API 全量字典)
  → 插入 {similarity:1.0, source:"exact_match",
           note:"use get_api_details for complete documentation"}
Example 3: query = "create net"（自然语言） 
=== search_apis("create net") ===
  Step 1: expand_query → "create net" (无缩写可展开)
          expand_query_reverse → "create net crt" (create→crt)
          enriched = "create net crt"
  Step 2: 向量检索（enriched query）
  Step 3: BM25补充 → dbCrtNet等

=== search_apis_by_keyword("create net") ===
  classify_query("create net") → "natural_language" (≥2词)
  keyword_search("create net"):
    tokenize_query → ["create", "net", "crt"]
    name_overlap: dbCrtNet→F2≈0.7 → 排序层 1
  soft redirect: api_recall("create net", threshold=0.3)
    → 补充语义结果，标注 source="vector_redirect"
Example 4: query = "compress"（全称反查缩写） 
=== tokenize_query("compress") ===
  raw_tokens = ["compress"]
  Direction 2: _compact_reverse["compress"] → "cp" (CP→Compress)
  最终: ["compress", "cp"]

=== 匹配效果 ===
  emyPointArrayIsRectangleNoCP 的 name_index = {"point", "array", "rectangle", "no", "cp", "compress"}
  （"compress" 是建索引时把名里的 CP 展开为 Compress 后加入的，见 §5 tokenize 管线）
  query {"compress", "cp"} vs name_index → 交集 {"cp", "compress"}
  P=2/2=1.0, R=2/6=0.333, F2=5×1.0×0.333/(4×1.0+0.333)=0.385 → 排序层 2 ✅
