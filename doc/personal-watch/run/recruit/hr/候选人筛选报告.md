## 二、采集到的数据结构

每位候选人包含：
`姓名` · `年龄` · `性别` · `应聘岗位` · `关系类型` · `会话标签` · `最近时间` ·
**`最后一条消息内容`** · `最后消息发送方(我/候选人)` · `uid` · `encryptUid` · **`securityId`**（拉简历用）

> 其中 **818 人最后一条消息是候选人发的**，即正等着你回复。

### 关键技术点
- 页面加载会 `POST /wapi/zppassport/set/zpToken` 生成 `__zp_stoken__`，**纯 Cookie 直接调接口必失败**，必须在页面上下文内 `fetch`
- 主接口：
  - `POST /wapi/zprelation/friend/filterByLabel` → 全部候选人 ID
  - `POST /wapi/zprelation/friend/getBossFriendListV2.json`（body `friendIds=id1,id2,...`）→ 候选人详情 + `securityId`
  - `POST /wapi/zpchat/boss/userLastMsg`（body `src=0&friendIds=...`）→ 最后一条消息
- `getBossFriendListV2` 的 `degree` / `lastWorkExpr` / `expectSalary` **均为 null**，学历与经历必须看简历或问本人

## 七、风险提示

1. **Cookie 会被风控清除**：短时间多次访问页面 → 跳 `web/user/?ka=bticket` 人机验证 → 登录失效
2. **登录态在 MCP 默认 context 里，不在新建的独立 context 里**（已实测纠正）：
   默认 context 持有 `bst` / `wt2` / `zp_at` / `wbg` 登录 Cookie，可正常打开 `web/chat/index`；
   而 `browser.newContext()` 新建的独立 context **只有匿名 Cookie**（`__a`/`__c`/`__g`/`__l`），
   访问聊天页会被重定向到 `web/user/?ka=bticket`。**发消息/采集一律用默认 context。**
3. **简历接口 `/wapi/zpgeek/resume/...` 返回 `code 7`**：Boss 对简历访问有**独立风控 + 配额消耗**，不要程序化批量拉
4. **批量发消息风险最高**：Boss 反骚扰风控极严，群发可能导致账号限流/封禁
