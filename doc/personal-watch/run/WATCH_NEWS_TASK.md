> **用户的判断（原话）**：**"三层链的『串联』结构本身就是风险 —— 把三个高不确定性假设串起来，整链成功率是乘法衰减的。"
> → **冻结 L3；L2 降级为探索性并明确标注「非因果」；集中火力把 L1 和 N1 语料做扎实。**

### 为什么要解耦：**乘法衰减**

若三层各自的成功率是 `p1 · p2 · p3`（每层都只是"有点希望"），**串联成功 ≈ p1×p2×p3 → 趋近于 0**。
→ **所以不串**：**三层各自独立评估、各自可以单独有价值**；**不要求 L2 基于 L1 的信号**，避免**"上游没做好 → 下游全废"**。

| 层 | 解耦后的定位 | 优先级 | 措辞红线 |
|:--|:--|:--|:--|
| **L1 政治信号预警** | **核心**：**独立有用**（"知道会发生什么"本身即有信息价值）；**不以"能赚钱"为目标** | **P0（唯一焦点）** | 允许「**倾向 / 概率 / 时间窗**」 |
| **L2 与股价的关联** | **探索性研究**：可做，但 🚫 **不声称因果** | **P2**（低优先，可并行） | 🚫 禁用「**影响 / 导致 / 利好 / 利空**」；只用「**相关 / 同期 / 滞后**」 |
| **L3 算法交易** | ❄️ **冻结**（L1 扎实前不碰） | **不做** | 🚫 不许讨论策略 / 仓位 / 择时 |

### 三条推论

1. **L1 的验收标准 = 信息质量**（覆盖 / 准确率 / **提前期** / 可比基线），**不是收益率**。
2. **L2 允许产出"没找到稳定关联"** —— 那**同样是有效结果**。
3. **解耦意味着可并行**：L2 可用**简单事件标签**（不必等 L1 的预警模型），但**必须标"探索性、非因果"**。

**三层共用红线**（细则见各节）：不许编造数据 · 防**前视/幸存者/数据窥探** · **必须给基线 + 置信区间** · **政治中立、不预测敏感事件** · **未获授权禁接真实交易接口** · 产出是**研究性观察，非投资建议**。

## 0.1 什么是「新闻」（入账判据 · **硬性**）

> ⚠️ 本线**只收"新闻"**。**不符合下面 4 条的一律不算新闻** —— 它们可能仍有价值，但必须**移入文末「非新闻」区**并打类型标签，**不得混进"新闻"条目里**。

**新闻 = 对「刚发生的、可核验的具体事件」的时效性报道。4 条必须同时成立：**

| # | 判据 | 说明 |
|:--|:--|:--|
| 1 | **时效** | 事件发生于最近：**日报口径 ≤ 72 小时**（周报 ≤ 7 天）。**过期长文不算。** |
| 2 | **事件性** | 报道一个**具体发生的事**：发布 / 决定 / 事故 / 数据 / 人事 / 诉讼 / 收购 / 政策落地…。**泛论、专栏、教程、心得不算。** |
| 3 | **报道体** | 来源是**新闻机构**或**官方公告**（在报道他人）；**不是**作者第一人称观点、公司软文、Show HN 自述、论坛讨论。 |
| 4 | **可核验** | 有具体事实点：**谁 / 何时 / 什么数字或决定**。 |

**典型反例（一律不进"新闻"）**：
- 特稿 / 长读（feature / long-read）、观点 / 专栏（opinion / op-ed）；
- 个人博客 / Substack / Medium 分析；
- 论文 / preprint（**例外**：当"某机构发布了某论文"本身是**事件**时，按**发布事件**报并注明"论文发布"）；
- 论坛帖（Ask HN）、Show HN 自述；
- 工具 / 仓库上线（**例外**：有官方**发布公告**时按公告报）；
- 软文 / 赞助内容。

**非新闻怎么处理？** **单列**到文末「**附录 · 非新闻（分析/观点/论文/工具/讨论）**」区，并打**类型标签**：
`🏷 类型：news | analysis | opinion | feature | paper | tool | discussion`
（只有 `news` 进各大类的"新闻"条目。）

**每条新闻必带字段**：`标题` + `来源` + `发布日期` + `🔗 链接` + `🏷 类型：news`。

## 2. 每轮采集 SOP（**每次唤醒照此执行**）

1. **读现状**：`MEMORY_NEWS.md` 顶部快照 + `news/SEEN.md`（已收录，避免重复）+ `news/<今天>.md`（已写部分）。
2. **定窗口**：确认**上次采集时间**（见 `MEMORY_NEWS.md` 流水）→ 本轮优先覆盖**上次之后**的新增。
3. **逐类搜索**：对 §1 每类跑 1~3 条查询（**优先用 `search_news`**；中文补充用 `web_search`），拿到候选列表。
4. **筛与去重**：
   - 与 `SEEN.md` 比对**链接**（主键）与**标题**（近似）→ 命中即跳过；
   - 只保留**与关注清单相关**且**有明确来源**的条目；
   - 目标量：**每轮 8~20 条**（宁精勿多，**不凑数**）。
5. **落盘**：把新条目**追加**到 `news/<YYYY-MM-DD>.md`（格式见 §3），并把其链接/标题写入 `news/SEEN.md`。
6. **更新索引**：更新 `news/INDEX.md` 的当日计数。
7. **回写状态**：更新 `MEMORY_NEWS.md` 顶部快照 + `WAITING`；当日流水追加 `daily-memories-news/<date>.md`。
8. **提交**：`git add` **只加本线文件**（`MEMORY_NEWS.md` `news/` `daily-memories-news/`）→ `commit -m "news <date> <n> 条"` → `push`。

> ⏱ **不要 sleep / 不要等待**：一轮做完就更新记忆并退出（loop 会按 `WAITING` 决定何时唤醒下一轮）。

## 3. 输出格式

### `news/<YYYY-MM-DD>.md`（当日摘要，同轮多轮则追加）

```markdown
# 新闻摘要 · <YYYY-MM-DD>

> 采集窗口：<上次时间> ~ <本次时间> ｜ 本轮新增：<n> 条 ｜ 来源：<...>

## 1. 前沿模型与能力
- **[标题]**（<来源>，<YYYY-MM-DD>）
  摘要：<2~3 句，忠实原文>
  🔗 <URL>
  🏷 关联：<可选，本书章节/主题，如"第32章 制度新生">

## 2. AI 安全与对齐
- ...（无新增则写：_本类无新增_）
```

**字段硬要求**：`标题` + `来源` + `发布日期` + `🔗 URL` **缺一不可**。
可选 `🏷 关联`（与本书的连接）**属判断**，若写必须措辞为**我们的观察**，不得冒充原文。

### `news/SEEN.md`（去重台账）

```markdown
# SEEN — 已收录条目去重台账

| 首次收录 | 标题 | 来源 | 链接 |
|:--|:--|:--|:--|
| 2026-10-03 | <标题> | <来源> | <URL> |
```

> **主键 = 链接**；标题近似亦视为重复。每轮落盘后**同步追加**。

## 4. 铁律（红线，**违反即失败**）

1. 🚫 **不许编造**：**必带**链接 + 发布日期 + 来源；**无来源不收录**。搜不到就写"未找到"。
2. 🚫 **不许把推测写成事实**：摘要区分「原文说了什么」与「我们的判断（须显式标注为观察）」。
3. 🚫 **不采集需登录/付费墙的正文**：只引用公开可见的标题/摘要 + 链接。
4. 🚫 **不整篇转载**：只做摘要 + 链接（版权）。
5. 🚫 **不 `git add -A`**：只加本线文件（共享工作副本，会卷入他人在途文件）。
6. 🚫 **不在正文/快照/流水写以 `WAITING:` 开头的行**（会误触发 loop 长睡）。
7. ⚠️ **控制频率**：单轮查询数受限（§2.3），避免对同一站点高频抓取；尊重 robots。
8. ⚠️ **不占 GPU、不登录训练机**：本线只做网络采集与文本整理。
9. 📒 **台账诚信（2026-10-05 新增，红线）**：**台账/日志类产物**（`STABILITY_LOG.md` · `EVENTS.csv` · `SEEN.md` · 各类 `*LOG*`）**只允许记录「真实发生过的事」**。
   - 🚫 **禁止补造 / 回填 / 用"模拟运行""重放""估算值"充数**；
   - ✅ **允许并鼓励**：**如实标注条目类型**（如 `record-only(补记/自检)`）—— 现行做法正确，继续保持；
   - ✅ **跨天重复运行只算 1 天**：🚫 **别为了凑"连续 N 天"而在同一天刷行**。
10. 📉 **指标未达标要如实写**：任何"是否达标"的判定（G2′④ 连续天数 / 覆盖率 / 准确率等），**未达标就写「未达标 + 当前实际值」**；
    🚫 **禁止**为"看起来达标"而**改口径 / 挑样本 / 刷台账 / 改时间戳**。→ 与 §0.0.2「**负面结果可接受**」一致。
11. 📦 **体积红线（2026-10-05 新增，红线 · 用户明令）**：**任何单个文件 ≥ 5 MB，一律不得用 GitHub 传输**（不 `git add`、不 commit、不 push）。
    - ✅ **正确做法**：**走百度云盘**（首选 `bypy`；备选 `BaiduPCS-Go`），把**网盘路径 / 提取码 / 文件名**登记进 `INDEX_FILES.md`；
    - ✅ **落实手段**：对应目录**必须先有 `.gitignore` 规则**（如 `news/archive/*.jsonl.gz`、`news/**/*.gz`、`*.zip`、`*.pdf`、`*.mp4`、`*.wav`、`*.docx` …）；
      **`git add` 前自查**：`git check-ignore -v <file>` 应命中；**未命中就先补 `.gitignore`**；
    - ⚠️ **元数据仍要入 git**：`INDEX_FILES.md` 必须记 **路径 / 行数 / 字节数 / sha256 / 存放位置（`git` 或 `网盘:<路径>`）** ——
      **数据本体不进 git，但「账」必须在 git**（否则等于丢数据）；
    - 🚫 **禁止规避**：`git add -f` 强推、先压成 `.zip` 再进、把大 `.gz` 塞进别的容器 —— **一律按"原始单文件实际字节数"判**（`ls -l` / `du -b`，**不看"压缩后估计"**）；
    - 🚫 **若网盘也不可用**：**宁可不传**（本地保留 + 清单登记 + 在 `PROGRESS.md` 如实写「未上云」），**也绝不许塞进 git**；
    - 📌 **存量说明**：截至 2026-10-05，`news/archive/chinanews-2016~2025.jsonl.gz`（**10 个分片 ≈ 94 MB**，单个 5.4–12.3 MB）
      **已按旧规则（单年 >20MB）入库** —— **那是旧口径的遗留**；**存量迁移由 ops 指令统一处置**，
      **本轮起 agent 不得再 `git add` 任何 ≥5MB 文件**（含新抓的 2026 分片、`chinanews-2016.jsonl.gz` 等）。

## 5. 记忆维护（**硬性**）

> 理由：`MEMORY_NEWS.md` **每次唤醒都被 agent 全文读取** → 越大越烧 token。

- **上限（两者相同）**：`MEMORY_NEWS.md` **与本线任务书 `WATCH_NEWS_TASK.md`（全文=prompt）** 均 **≤ 32KB**（红线 40KB）；一旦超限即执行滚动。
- **任务书自己滚（2026-10-06 用户裁定）**：任务书的归档**由本线 agent 自己做**（与 MEMORY 同机制），**不再依赖 supervisor** —— 只把「已闭合」的历史轮次 / 已执行完的运维块**【原文】搬入** `run/WATCH_NEWS_TASK_ARCHIVE.md`（**留 1 行指针**；**不新增/不改写任何指令**，本区作者仍是 supervisor）。
- **滚动**：把**较早的流水条目**（保留最近 ~20 条）**追加**到 `daily-memories-news/<条目日期>.md`（原文不改），再从 MEMORY 删除。
- **顶部必须保留**：① `WAITING:` 行（**仍只出现一次**）② 状态头 /「进度快照」③ 「运维问答」④ 最近 ~20 条。
- **纪律**：归档**不改变任何结论**；`WAITING:` 纪律不变。
