1Don't Stop Long-Context Continual Pre-Training Too Early: An Empirical Scaling Law

中文一句话
该文把长上下文继续预训练（LCCP）的收益写成「模型规模 + 短上下文预训练预算 + LCCP token 预算」的经验加性幂律：在 5 个模型规模、100+ 组 短/长上下文预算配置上拟合，能复现观测趋势并外推到留出的模型规模；提出 Constant-Last4（恒定学习率下对最近 4 个连续 checkpoint 取平均）让单条可延长训练轨迹的监控稳定，同一律形式可准确预测 1.22B 模型约 100B LCCP token 的性能轨迹；沿轨迹下游长上下文能力持续提升、无明显饱和，且在 128K 上下文扩展 + SFT 之后收益仍在，并外溢到长上下文理解与 agentic 任务。

推荐理由（借鉴 · BaiZe 长上下文阶段）
  1. 可直接套用的预算—收益曲线：BaiZe 若走「短上下文预训练 → 长上下文继续预训练」两段式，这条律给出「给定模型规模与短上下文 token 预算，LCCP 加到多少 token 能到多少分」的估计，用来决定 LCCP 何时停、要不要继续加预算，而不是凭经验拍一个固定 token 数。这正是我们下一步要回答的「阈值」问题。
  2. 观测协议可搬：Constant-Last4（恒定 LR 轨迹上平均最近 4 个 checkpoint）本质是降噪的 eval 节奏；我们长上下文阶段的 checkpoint 抖动同样会误导早停判断，这套平均口径可以直接进我们的评测流程。
  3. 「收益没被后训练吃掉」这条对我们最有用：128K 扩展 + SFT 之后 LCCP 收益仍在，说明长上下文预算不该为了省后训练成本而被砍；也提示 LCCP 与 SFT 的预算应分开核算。
  4. 边界（我们判断）：幂律形式与系数绑定其数据/模型族与训练配方，迁移到 BaiZe 必须重拟合；未覆盖 >100B LCCP token 区间（正是「不要过早停」的主张所依赖的外推区）；数字为作者自报，本线未复现；未精读，图 18 张的具体消融未核。

2TrainBridge: Agentic NPU Training Optimization Guided by GPU Compilation Evidence

中文一句话
在 Ascend NPU 上，框架级编译优化（如算子融合）只被部分应用，留下碎片化计算与可避免开销；TrainBridge 把成熟 GPU 编译栈产生的高度优化执行当作任务特定参照 —— 先抽取 GPU 执行里的优化意图，指导 NPU 程序重写，再用迭代 profiling 精化；4 个负载（LLM 预训练、图像分类、视觉语言训练）平均 1.7×，27 个 Modded-NanoGPT speedrun 记录（本身已是高度优化的 GPU 实现）上平均接近 2.0×。

推荐理由（借鉴 · 训练效率 / 非 NVIDIA 栈）
  1. 对准我们的现实约束：若 BaiZe 的训练要在国产/非 NVIDIA 加速器上跑，「框架级编译只应用了一部分优化」是典型痛点。这篇的做法不是手写 kernel，而是把 GPU 上已经验证过的执行形态当作「任务特定参照」，让 agent 去改 NPU 程序——工程上比从零调优更可控。
  2. 闭环可映射到 ZhuLong：「抽取优化意图 → 重写 → profiling 迭代」正好是 generate–execute–refine 的一个实例，其中 profiler 是工具、编译日志是证据；我们判断这套「以证据驱动重写」的骨架可以脱离 NPU 场景复用。
  3. 1.7× / ~2.0× 的量级要正确解读：收益来自补上缺失的融合与调度（即把已有的优化意图补齐），不是算法突破；因此它是「可得但需要工程化」的收益，且很可能依赖起点有多差。
  4. 边界（我们判断）：只在 Ascend NPU + 特定框架/编译栈上验证；依赖可获得且可对照的 GPU 参照执行（拿不到 GPU trace 就不成立）；摘要未给逐负载方差与失败案例（4 个负载的 1.7× 是否被单个负载拉动，未知）；数字作者自报、本线未复现；未精读。

3PAUSE: Search-Free Steering of Coding Agents Before Their First Source-Code Edit

中文一句话
作者观察到 coding agent 的首次源码编辑发生在轨迹中位约 60% 处；PAUSE 就在这条编辑请求执行前拦截，让独立 Planner 读任务 + 编辑前 transcript 写一份修复计划，再由同一个 Executor agent 带着计划继续（保留上下文与工作区）——无需学习型 monitor、不搜索 checkpoint、不额外调用执行 agent（search-free）。在 SWE-bench Verified / Multilingual 上（2 Executor × 3 harness）：OpenHands Verified +16.8%、SWE-agent Multilingual +14.7%；离线可恢复 35.4% 失败任务、从记录前缀续跑省 33–41% Executor token。

推荐理由（借鉴 · ZhuLong agent harness）
  1. 改动极小、可插拔：只在「首次向源码写入前」加一次规划调用，不改模型、不改工具集、不改奖励。对 ZhuLong 这种 execution-grounded EDA coding agent 来说，这是 harness 层最容易 A/B 的一个开关。
  2. 把「何时干预」量化了：中位 60% 处首次编辑 —— 比周期性复审便宜（只在必要时打断一次），也比异常检测触发更早（没有异常行为不等于方向对）。这条观察本身对我们设计 EDA 任务的干预点有独立价值。
  3. Planner / Executor 解耦 = 成本杠杆：强模型只做一次规划，Executor 用便宜模型跑长轨迹；论文给的「Planner 成本约为 SICA 的 11–15%」说明与周期性 overseer 效果相当但贵得少，对成本敏感的批量实验很关键。
  4. 边界（我们判断）：依赖一个更强的 Planner 模型（是额外模型调用，不是零成本）；对「首次编辑」这一时点敏感——探索型/多文件重构任务里首次编辑可能过早或过晚；论文不含 EDA 仓库，跨域迁移未验证；指标作者自报、本线未复现；未精读。

4BrickWright: Agentic Creation of Physically Feasible Brick Builds

中文一句话
让前沿 coding agent 用写代码的方式搭乐高：作者给出 Python 工具包 BrickLayer（面向积木的拼装 API + 物理可行性校验器），agent 写拼装程序、校验器回传「悬空 / 穿模 / 不连通 / 非真实零件」，agent 据此改代码；在 512 条文本或图片提示上，基线 agent 的物理可行率只有 9%（GPT-6 Luna）到 69%（GPT-6 Astra），BrickWright 引导下达到 100%，同时提升轻量模型的提示遵循度、对强模型保持不降，并在文本→积木任务上超过专用模型。

5LLM Multi-Agent Systems Are Vulnerable to Herding and Runaway Cascades

中文一句话
把经典「Music Lab」从众实验搬到 LLM 群体：让大规模 LLM 智能体给不熟悉的新歌打分，一组能看到别人的累计推荐数、一组看不到；结果可见他人选择会触发失控级联，让集体推荐变得极端、不可预测、越来越偏离歌曲本身的质量；与人类相比，LLM 群体对从众更敏感，且级联发生后更难自我纠偏——作者指出这会影响推荐系统、自动评测、复杂问题求解，甚至「未授权的合谋」。
