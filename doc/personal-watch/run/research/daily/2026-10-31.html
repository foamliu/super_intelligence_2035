1Nemotron 3.5 Super and Lightning: Open, Efficient Mixture-of-Experts Hybrid Mamba-Transformer Models for Agentic AI

中文一句话
NVIDIA 开源两个 MoE + 混合 Mamba–Transformer 模型：Nemotron 3.5 Super（120B 总参 / 12B 激活，多模态）与 Lightning（30B / 3B 激活，文本），走「大规模蒸馏（各 1 万亿 token）+ 长上下文训练 + 原生 MTP 投机解码 + NVFP4 量化」的组合，把 agent 负载的能力与推理效率一起优化。后训练 Super 在 SWE-bench Pro 51.78%，作者称超过 Nemotron 3 Ultra，而激活参数约少 4.6×；MTP boosting 把投机解码接受长度 4.287 → 4.718（最高 +21.8%）；NVFP4 相对 BF16 中位精度恢复 99.62%、交互式 agent 负载吞吐 2.43×。

推荐理由（借鉴 · 与 BaiZe / ZhuLong 的关系）
  1. 与 BaiZe 的架构路线同构：同样属于「MoE + Mamba/attention 混合」这一族。这篇把每个训练阶段的先后与预算写得很细 —— 蒸馏 1T tokens（Lightning 取教师 top-128 logits，损失 0.9 KL + 0.1 CE、LR 从 1e-5 用 200B tokens 缓升到 1e-4 再线性退回）→ 长上下文 → agentic 软件工程 mid-training → SFT + RLVR/RLHF。我们可在 2B 规模上按比例缩配这张「阶段配方表」，尤其是「蒸馏与 mid-training 谁先谁后」。
  2. 投机解码的坑给了现成修法：递归共享 MTP 头在两段递归训练下会出现训练–推理条件分布错配（推理时草稿头看到的是主干隐状态与合成隐状态的混合），作者用隐状态混合（hidden-state mixing）并冻结主干、只用 100B tokens 预热 MTP 头，接受长度最高 +21.8%。若 ZhuLong 侧要上投机解码，这条是可直接对照的实现细节，而不只是「加了 MTP」。
  3. 量化的「精度恢复」口径值得抄：NVFP4 报告的是相对 BF16 的中位精度恢复 99.62% + 分场景吞吐（交互式 agent 负载 2.43×、GB200 上 4,856 output tokens/s/GPU 且每用户 ≥50 tokens/s）—— 「精度掉多少 + 吞吐换多少」成对报告，正是我们做量化评估时该有的表结构。
  4. 边界（必须写清）：① 这是 NVIDIA 厂商技术报告（79 页、559 位署名），所有数字自报，对比基线（Nemotron 3 Ultra、Qwen3.5 122B-A10B、Qwen3.8 Flash-Next）多为自家或闭源配置；② SWE-bench Pro 51.78% 是「整套后训练流水线」的结果，不能归因到某一个技术点；③ 120B-A12B / 30B-A3B 是大模型经验，2B 规模是否同样成立未被验证；④ 本线未复现。

2Rimuru: Unified Memory Management for Modern LLM Serving via Elastic Expert Offloading

中文一句话
LLM 服务里「模型权重」和「注意力状态（KV）」一直被划成两块固定内存，重负载时 KV 不够、轻负载时另一半闲置。Rimuru 把它们并成一个共享页池：不同张量类型用各自的页大小 + 页表（memory views）解释同一段内存，配大页对齐 + 多级页分配器（可切分/合并）做跨类型复用，再加页表感知的融合 MoE kernel（直接读非连续专家权重、省掉拷贝）与负载感知调节器（运行时重新分配页）⇒ 在 vLLM 上的弹性专家卸载。作者自报：相对卸载类基线吞吐 1.39×–19.03×、TTFT 平均降低 98.1%。

推荐理由（借鉴 · 与 BaiZe / ZhuLong 的关系）
  1. 命中「存储/内存受限推理」这条线：它不是又一个调度器，而是把「权重池」与「KV 池」的边界打掉，用页表在同一段显存上做跨类型复用 —— 这正是我们关心「显存/带宽受限时怎么把并发撑起来」的问题形态；对 ZhuLong 这类要在有限资源上跑长上下文 agent 的场景尤其对口。
  2. 可迁移的具体机制（不是概念）：① memory views：每种张量用自己的页粒度与页表；② 多级分配器 split/merge 处理不同分配粒度；③ 页表感知的融合 MoE kernel 直接吃非连续专家权重（避免 gather/copy）；④ workload-aware adjuster 在预热/解码阶段动态调页。这四条可以逐条对照我们现有 serving 栈的可改点。
  3. 实验口径清楚：两套硬件（8×RTX 5090 32GB；2×RTX 4090D 24GB）、三个 Qwen MoE 模型（30B-A3B / 35B-A3B / 122B-A10B）、ShareGPT 负载、五个基线（vLLM / SGLang / KTransformers / Fate / llama.cpp），指标是吞吐 + TTFT + TPOT。
  4. 边界（必须写清）：① 19.03× 的前提是「4090D 上对走 AVX2 的 KTransformers」（该机 CPU 无 AMX，作者注明对方退化），不能当成通用加速比；对 SGLang / vLLM 是 1.1×–2.88×；② 只用消费级 GPU + Qwen MoE + 合成请求流，无生产 trace；③ vLLM 在其中一个配置因 Triton GDN kernel autotuning OOM 被移出该面板（作者如实写出）；④ 数字作者自报、本线未复现。

3Every Token Needs Its Own Teacher: Multi-teacher Adaptive On-policy Self-distillation

中文一句话
on-policy 自蒸馏（OPSD）通常给整条回答一个固定教师（或按回答调参考暴露比例）。作者用教师干预试验证明：同一条回答里，不同 token 偏好的教师并不一样 ⇒ 提出 MTA-OPSD：建 7 个教师配置（完整参考 / prefix-0.5 / prefix-0.75 / suffix-0.5 / suffix-0.75 / random-span-0.5 / random-span-0.75，每种都保留最终答案），用多数投票 + KL 选择为每个 token 挑教师，学生只对被选中的教师做 on-policy 蒸馏。Qwen3-1.7B / 4B / 8B 上数学推理平均分相对 base +5.9 / +1.5 / +2.8，三个规模均为最高平均分。

推荐理由（借鉴 · 与 BaiZe / ZhuLong 的关系）
  1. 给 BaiZe 的后训练提供一条「不需要奖励模型」的稠密监督路径：只要有参考解（数学题解、EDA 修 bug 的 gold patch），就能把参考答案当作 privileged information 做 on-policy 蒸馏，比 RL 更容易复现、比纯 SFT 更贴合学生自己的分布。
  2. 「token 级选教师」是低侵入的可加项：不改模型结构、不动数据，只在教师侧加一个池子 + 选择器（多数投票 + KL 过滤）。对 ZhuLong 这种「有编译器/仿真器真值」的场景，可把「参考暴露多少」编码成不同教师（例如只给报错行 / 只给 diff hunk / 给完整补丁），正好对上它的 generate–execute–refine 循环。
  3. 与本期第 1 篇形成对照：Nemotron 走的是工业级多点蒸馏（MOPD），本篇走学术级 token 级教师选择，两篇一起看能把「蒸馏在 2026 年的两条实践路线」摆在一张桌上。
  4. 边界（必须写清）：① 只做数学推理（DeepMath-103K 中等难度）+ 3 个基准（AMC23 / AIME24 / AIME25），不外推到代码/agent；② 只用 Qwen3 系学生、每方法仅 300 步；③ 对比是按步数对齐，而 7 个教师配置意味着更多教师前向 ⇒ 论文没有给等算力/等墙钟的对照（这点必须自己补实验才能判断性价比）；④ 数字作者自报、本线未复现。
建议动作：读原文（§3 教师偏好试验、§5 多教师池与选择机制、§6 主表与消融）+ 试跑（在 2B 上取 1–2k 条有 gold 的样本，做「单教师 OPSD vs 本方法」的等算力小规模 A/B，并显式记录教师前向成本）。
