原题AIChipBench: Benchmarking LLM Agents for Automated AI Accelerator Design

2 · ShellBench: What Matters More for AI Agents, Models, or Harness for Everyday Tasks

原题ShellBench: What Matters More for AI Agents, Models, or Harness for Everyday Tasks
中文一句话用 100 个来自 >1,000 万真实请求的日常任务（杂乱工作区、竞争数据源、正确性 + 安全性双评分），跑 12 模型 × 5 harness × 3 推理档 = 53,100 次 rollout：模型选择的影响大于 harness，但前三名模型只差 1.1 个百分点；五个 harness 的 pass@1 仅在 42.9–45.2 之间。
作者 / 机构Vincent Koc · Aditya Washikar · Rishab Naveen Venkataraman（等 22 位；摘要区未列机构）

分类 + 标签cs.AI ｜ 🏷 借鉴（harness 选型与评测）
链接arXiv:2611.32946
推荐理由直接回答我们 harness 线的核心问题——「换 harness 到底值不值」。结论对我们不利但重要：在本基准上 harness 对性能与安全都影响很小（pass@1 42.9 Claude Code → 45.2 OpenClaw），模型才是主要变量；而成本差异巨大，GPT-6.1 Sol 以约 1/6 的估计 token 成本拿到 61.4%，GPT-6 Astra 以 62.5% 领跑。可落地的验收规则：① 选 harness 先用固定模型做「harness-only」消融，别把模型升级的功劳记到 harness 上；② 报分必须同时报每次尝试 token 成本与安全分，否则 1.1 pp 的模型差距会被成本与安全淹没。⚠️ 100 题 / 53,100 次 rollout 为作者自报；公开释放仅占 20%。

4 · Latent Merger: Latent-Space Composition of Hypernetwork-Generated LoRAs

原题Latent Merger: Latent-Space Composition of Hypernetwork-Generated LoRAs
中文一句话超网络为每个文档一次性生成 LoRA，但逐文档存适配器在流式场景不可持续；作者发现这类 LoRA 的几何与直接微调的 LoRA 截然不同（谱更集中、跨文档更对齐、近正交），于是在中间潜空间合并再经冻结的 LoRA 生成头解码，在固定输出秩下稳定优于权重空间 / 因子空间合并。
作者 / 机构Yanlai Yang · Minki Kang · Divyam Madaan · Sung Ju Hwang · Mengye Ren（摘要区未列机构；Sung Ju Hwang 为 KAIST）
提交 / 更新2026-11-24（arXiv v1；published=2026-11-24T17:54:58Z；comment=Accepted at NeurIPS 2026）
分类 + 标签cs.LG ｜ 🏷 借鉴（pretrain 适配 / posttrain 多知识注入）
链接arXiv:2611.33048
推荐理由给我们「多份 LoRA / 适配器怎么合并」提供了可测的判据与更省的做法。值得照搬的是先量几何再选合并空间：直接微调（NTP / QA）的 LoRA 谱弥散、跨文档近正交；超网络生成的 LoRA 谱更集中、跨文档更对齐——正因为对齐，潜空间合并才可能有效。做法上不新增适配器：在中间潜变量层合并，再经冻结的生成头解码，保持单一固定秩。对我们多域数据注入的启示是：若我们用超网络/文档级适配器，应优先在潜空间合并并做「谱集中度 + 跨文档余弦」体检，而不是直接平均权重。⚠️ 具体增益幅度摘要未给数字，按作者结论转述；本线未复现。

5 · BriConstrain: Geometrically Constrained Decoding for Autoregressive Brick Assembly Generation

原题BriConstrain: Geometrically Constrained Decoding for Autoregressive Brick Assembly Generation
中文一句话自回归生成 LEGO 拼装常出现撞件或悬空，拒绝重采样既丢 token 又不保证合法；作者改为在采样前用几何预言机约束「怎么接」而不是「接哪块」，把碰撞自由率从 31%→91%（BrickNet）、15%→65%（ICLF），代价约为拒绝采样的 60%。
作者 / 机构Nadav Magar · Amir Hertz · Ariel Shamir · Or Patashnik（摘要区未列机构；Or Patashnik 为 Tel Aviv University）
提交 / 更新2026-11-24（arXiv v1；published=2026-11-24T18:54:38Z；comment=Project Page: https://nadmag.github.io/BriConstrain/）
分类 + 标签cs.CV ｜ 🏷 科普（兼借鉴）（designflow 结构化生成 / 约束解码）
链接arXiv:2611.33135
推荐理由「让语言模型拼乐高还不撞件」这件事本身大众就能懂，而方法对我们的结构化设计生成也成立：合法性依赖非预先确定的拼装状态，无法编译成固定文法，必须动态检查；合法放置空间组合爆炸、无法穷举，所以作者把约束从「选哪块」下移到「怎么接」，用预计算几何预言机展开连接空间、过滤碰撞后再偏置 next-token 分布。结果：BrickNet 31%→91%、ICLF 15%→65%，并优于拒绝采样且只花约 60% 解码成本。对我们 designflow 的启发是：把「局部合法」提升到「装配级合法」，用可预计算的几何/规则预言机做动态掩码，而不是事后拒绝。⚠️ 两个格式上的比例与成本比例均为作者自报。
