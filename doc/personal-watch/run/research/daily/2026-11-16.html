1Discovering Effective Agent Memory Designs through Program Evolution

中文一句话
把「agent 记忆系统」当成可进化的程序来搜：MAPE 从最小种子出发，用统一的生命周期接口 + 「诊断—提议」迭代循环演化整套记忆程序。在 LoCoMo 与 LongMemEval 上比人工设计基线最高 +12% 绝对准确率，而服务成本只有基线的 35%；两个反复出现的设计模式被消融验证：保留原始对话作为可检索证据（补回抽取式记忆丢掉的细节）、按查询意图组合检索到的证据（把组合模块移植进 5 个已有记忆系统，全部涨点）；把服务成本写进搜索目标后，计算从「建记忆时用 LLM」转向「查询时有选择地处理」。

推荐理由（借鉴 · harness 主目标；zhulong / data 次之）
  1. 它把「记忆设计」变成可复现的搜索对象：过去记忆系统靠人工经验（抽取什么、怎么组织、怎么检索），本文用「诊断—提议」循环把整套程序一起搜。动作：harness 线在自己的长任务场景里先固定一个最小记忆种子（只存原始轨迹 + 一个检索接口），把「加什么组件」作为可枚举变量，而不是一次性设计完整记忆系统。
  2. 「保留原始对话」这一条最可直接搬：抽取式记忆会丢掉后续推理需要的细节，把原文留作可检索证据能补回来。动作：harness 的记录格式里摘要与原文必须同时落盘（原文按段哈希分块，摘要只做索引），评测时允许 agent 回查原文。
  3. 「按查询意图组合证据」是低成本模块：移植到 5 个已有系统都涨点，说明它与具体记忆实现解耦。动作：把「组合」实现成独立一步（输入 = 检索到的证据 + 查询意图，输出 = 给回答模型的证据块），单独开关做 A/B。
  4. 成本口径值得抄：本文报「准确率 + 服务成本」双指标，成本含建记忆与查询两侧。动作：我们的 agent 记忆实验一律同时报「每解出任务成本」，🚫 不允许只报准确率。
建议动作：harness 在现有长任务集上做三联对照：① 无记忆 ② 摘要式记忆 ③ 摘要 + 原文可回查 + 意图组合；预注册判据：只有「准确率提升 ≥5 个百分点且每任务成本增幅 ≤20%」才纳入默认配置。

2Pretraining Data Statistics Shape the Phases of Learning Entity Comparison in Language Models

中文一句话
用 163M 参数小模型在「自然预训练语料 + 合成任务数据」的混合上训练，追踪「实体比较」类任务（如「法国和巴西哪个大」）的学习过程，识别出三个阶段：(1) 按词频选实体 → (2) 按提示内位置选（先提到 / 后提到的那个）→ (3) 选正确答案。三个阶段由训练数据的统计性质因果决定：少量合成数据只能到前两阶段（任务学不会），数据量足够大时模型直接从前两阶段跳到正确求解；把实体频率从自然界的 Zipf 分布改成均匀分布，会削弱词频阶段并加速任务学习；最后在开源 OLMo-2 32B 上复现出同样的三阶段。

推荐理由（借鉴 · data 主目标；pretrain 次之）
  1. 「先按词频、再按位置、最后才对」给出可观测的失败顺序：若我们的 2B 在事实比较类任务上「看起来会、换个体就错」，很可能停在第 1/2 阶段。动作：评测集按实体频率分桶（高频 / 中频 / 长尾）× 提示位置（先提 / 后提）交叉切分，单独报每一格准确率，而不是只报总分。
  2. 「少量合成数据有害」有可检验的预测：数据不足时模型只学会前两阶段且会卡住。动作：data 线对每类合成任务做三档数据量（如 1k / 10k / 100k）曲线，判据是「是否跳过启发式阶段」。
  3. 「频率分布本身是变量」：Zipf → 均匀会加速学习，说明配比不只看领域比例，还要看实体频率分布。动作：配比表新增一列「实体频率分布（Zipf / 均匀 / 混合）」，与领域标签并列。
  4. 小模型 → 大模型的迁移证据：163M 上的三阶段在 OLMo-2 32B 上同样出现。动作：把「163M 级可控实验」作为 2B 主跑之前的预注册探针，成本低、可先跑。
建议动作：data 线本周先跑「163M × 三档合成数据 × Zipf/均匀」的 6 格网格；预注册判据：若均匀分布在两档数据量上都加速收敛且不损其他任务，则把「实体频率均衡」纳入下一版配比实验。

3LazyWeights: Decode-on-Demand Edge LLMs

中文一句话
端侧跑大模型卡在内存容量（4 GB Jetson Nano）与带宽（8 GB Jetson Orin Nano Super）。现有量化格式（GPTQ / AWQ / llama.cpp 的 K-、I-quant）对矩阵里每个整数码分配等长比特，但码的分布远非均匀。LazyWeights 不改格式：调整 GPTQ 让码本身可压缩 → 用 Huffman 无损编码写进交织 lane → 在 DRAM 与 L2 之间放一个按需解码的小单元，GPU kernel 不用改，DRAM 只搬编码后的字节。1% / 3.5% 困惑度预算下，Phi-3-mini / Mistral-7B / SmolLM-1.7B 比最好的 llama.cpp 格式小 5.7–31.4%；0.21 mm² / 1 GHz / 7 nm 的位精确 ASIC 解码器把 Orin 每 token 延迟与能耗最多降 36% / 38%（叠加 prompt-lookup 推测后 54% / 44%）；Nano 上比 CPU llama.cpp 省 58–64% 时间、53–57% 能耗，流式 Mistral-7B 在 3.89 bit/weight 下快 6.6×。

LazyWeights: Decode-on-Demand Edge LLMs

推荐理由（借鉴 · zhulong 主目标（成本口径）；与「存储 / 内存墙」方向直接相关）
  1. 它把「带宽」而非「算力」当瓶颈：端侧与推理集群的第一限制都是 DRAM 搬运量。作者不改 kernel、只改DRAM 搬多少。动作：zhulong 的成本表把「每 token 从 DRAM 读出的字节数」单列一列，与 token/s 一起报；这比单纯报 ppl 更能解释部署差异。
  2. 「码分布不均匀」是可验证的观察：等长比特浪费在低频码上，Huffman 在交织 lane 内无损压缩；作者还实测 Huffman 在码率与面积上优于 rANS（同吞吐）。动作：量化实验里记录「码熵 / 平均码长」，作为是否值得上熵编码的判据。
  3. 数字口径必须按预算读：5.7–31.4% 的体积缩减绑定在 1% 与 3.5% 困惑度预算，不是「无损」；延迟 / 能耗数字绑定在特定 Orin / Nano 平台 + 特定 ASIC。动作：引用时一律带预算与平台两句话，🚫 不写成「端侧推理普遍加速 36%」。
  4. 「格式不变」降低了落地门槛：仍是 GPTQ/AWQ/llama.cpp 格式，只是编码层不同。动作：若要做原型，先在不改推理框架的前提下加一层「读入即解码」的胶水，验证 DRAM 流量假设再谈硬件。
建议动作：zhulong 在 2B 模型的量化对照里补两个指标——「每 token DRAM 字节数」与「3.5% ppl 预算下的体积」；预注册判据：若在目标平台上 DRAM 流量下降 <15%，则不引入熵编码层（复杂度不划算）。
