1AnalogLayoutWorld: An Open Benchmark for Agentic Analog Layout Design

中文一句话
给「agent 做模拟电路版图」搭了一个开源基准：40 个专家复核任务（输入固定晶体管级网表，输出端到端 GDS），配集成设计环境 + 独立物理验证 + 后仿电学验证 + 客观版图质量指标。在 13 个 model–harness 配置上，91.1% 的尝试能产出 GDS，但只有 23.0% 通过验收；作者内部系统 Novara 综合分最高，并把差距归因于固定预算下的 test-time scaling（推理效率 + 有效利用验证反馈）。

推荐理由（借鉴 · designflow / zhulong / harness 三线直接对口）
  1. 「能产出」与「能过验收」被拆成两个数：91.1% vs 23.0%。这正是造题时最容易自欺的地方 —— 只看「有没有输出文件」，agent 看起来很行；一旦加上独立物理验证 + 后仿电学验证，通过率掉到四分之一。designflow 的 L3–L5 可直接抄这个口径：产出率与验收率必须分开报。
  2. 验证器是独立组件，不是判分脚本的一部分：物理验证与电学验证分开跑，质量指标由版图专家共同设计。我们的 harness 最容易把「判分」写成「读 agent 自己的日志」；这里应把验证器做成 agent 不可写、不可读内部状态的独立进程。
  3. 差距归因落到「test-time scaling + 验证反馈利用」，而不是换更大模型 —— 与 zhulong 正在做的 subagent 消融同构：固定预算下比较的是每一步把预算花在哪。
建议动作：designflow 先在现有 L3 题里抽 5 题，补两列 artifact_produced（是否产出终态文件）与 acceptance_passed（独立验证器通过）；预注册判据：若两列差距 >3×，则后续只报验收率、产出率降为诊断项。

2CADET: Construction of PCB Routing Instances with Executable Demonstrations

中文一句话
指出公开 PCB 布线数据只有终态、没有 EDA 引擎动作的可执行演示，于是联合生成合成板与演示：RouteDemos 给出 100,000 块零 DRV 合成板及逐步演示，17 项统计量分布贴近 142 块真实参考板；在其上先行为克隆再 RL 微调，真实测试板的「完全无 DRV 布线率」从 RL-only 基线 38.0% → 67.2%，与开源自动布线器 FreeRouting 相当、优于其余基线（含 GPT-6 Astra）。

推荐理由（借鉴 · data / designflow / zhulong 直接对口）
  1. 它解决的是「数据里没有动作」的问题，不是「数据不够多」：真实布线数据的终态板学不到「第 3 步为什么这样走」。我们 zhulong 的 trace 也一样 —— 只有最终网表/日志的样本，无法训练过程策略。CADET 的做法是用引擎本身生成演示（不是人工标注），这条路线可以照搬到「综合脚本调优 / 时序修复」的演示合成。
  2. 合成数据的验收标准写得很克制：17 项统计量 vs 142 块真实板。这是一个可复用、可预注册的「合成数据保真度」检查清单，而不是笼统说「分布接近」。data 线能给每条合成数据产出一条这样的对照表。
  3. 38.0% → 67.2% 的增益来自「先 BC 再 RL」，而非纯 RL。这对 zhulong 的 RL 排期是直接证据：在有可执行演示时，先把演示学会再加 RL 比直接 RL 更省样本；但摘要未给两臂的样本量与训练步数，不能据此下定论。
建议动作：data 线先对现有 trace 数据做一次「17 项统计量 vs 真实参照集」的分布对照（选 3 个最关键统计量起），预注册判据：任一关键统计量偏离 >2 个标准差 ⇒ 该批合成数据不进 SFT 训练集。

3EvoX: Rethinking the Agent Harness as a Runtime Policy

中文一句话
把 harness 当成与模型语义策略互补的运行策略（Operational Policy）：用 Action Realization（动作落地）、Execution Continuity（流程不中断）、Outcome Grounding（完成声明必须有证据）三个确定性机制，解决「模型决策看起来对、执行却失败」（工具调用失配 / 流程中断 / 无根据的完成声明）；并提出 Contrast 评测框架（公平约束 + provider 侧请求核验 + 证据裁定）。在 5 个基准 / 6 个基座 / 6 个 harness、691 个共同 task–model 对上成功率 56.2% 最高，比其余 5 个 harness 均值高约 3.0 个百分点（GLM-5.3 +10.7、Kimi K3 +7.9）。
原题
EvoX: Rethinking the Agent Harness as a Runtime Policy
作者 / 机构
Haoyang Zhang · Qumeng Sun · Xiao Zhang · Xiang Liu · Zhidong Fan · Junjie Wang（共 6 位；机构未从 PDF 核验）

分类 / 标签

链接

推荐理由（借鉴 · harness / zhulong 直接对口）
  1. 「Outcome Grounding」正是我们评分表缺的那一条：agent 说「已修复」但网表没变、DRC 没跑 —— 这类失败在我们 TB-2.1 / zhulong 的失败集里占比不低。可落地做法：凡是「完成」类声明，必须绑定一个可复算的证据文件（时间戳 + 命令 + 退出码 + 产物哈希），否则该步记 unverified_claim，不进成功计数。
  2. 「Execution Continuity」把中断当一等公民：我们的工具链（综合 / 仿真）经常超时或被 OOM 杀掉，当前口径容易把「基础设施故障」计入模型能力。EvoX 的做法是把「恢复」写成运行时策略，与模型解耦 ⇒ 可直接对齐 harness 的额度失败 vs 能力失败归因纪律。
  3. Contrast 的「provider 侧请求核验 + 证据裁定」值得抄成评测协议：它防的是「harness 偷偷替模型补 prompt / 重试 / 改判分」。我们的 7 路对比里，各 harness 的隐式重试策略还没被固定下来。
建议动作：harness 在 TB-2.1 rerun 的合并脚本里加一列 claim_verified（成功声明是否绑定产物证据），并单独统计 unverified_claim 数量；预注册判据：若该列导致通过率变化 >5 个百分点，则历史 7 路结果需标注「口径不同、不可直接比较」。
