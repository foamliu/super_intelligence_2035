1Multi-View MoE: Letting Every Router Shape Expert Computation

中文一句话
传统 MoE 只用一个路由头做 top-k 选专家。作者先做稠密评估（把每个专家都跑一遍再算「专家效用」），发现单路由的排序与真实效用排序在中层/深层明显不一致。于是提出 Multi-View MoE：① Multi-Router —— 多个独立初始化的 sigmoid 路由头，各自给分后求和再选 top-k；② Multi-View —— 用每个被选专家在各路由上的相对分数去混合多个学到的 latent view，作为该专家的输入（每个被选专家仍只做一次前向）。在 24 层 10B-A1B（top-8 路由 + 1 个常驻共享专家）、708B tokens 上：九任务均值 33.07 → 34.25（+1.18 个百分点），只加 Multi-Router 为 33.69（+0.6）；相对 Multi-Router，GPQA +2.74、MMLU-Redux +2.03、CMMLU +1.43、MMLU +1.17。

  1. 几乎「零成本」的架构改法，适合在 BaiZe 的 MoE 路线上做小规模验证：参数只增 ≈0.19%（两个路由头 +0.06%，每层一个 view 投影 +0.13%），且作者明确激活专家数、专家 FLOPs、all-to-all 通信量都不变 ⇒ 我们现有的显存/带宽/并行切分假设不用重算，这是「能不能上」的第一道门槛，本篇直接给了答案。
  2. 给了可复用的「路由器质量」诊断指标：先用稠密评估得到专家效用排序，再比 router 排序（论文实测两个路由头的 top-8 Jaccard 仅 0.145、top-1 一致率 11.2%）。我们平时只看 loss/下游分数，这套诊断能把「路由没学好」与「专家没学好」分开，值得直接搬进 BaiZe 的分析脚本。
  3. 「路由偏好二次利用」是个便宜的可加项：选专家用一遍分数，再用同一批分数去混合输入视图 —— 不额外做一次专家前向，也不额外通信。对 ZhuLong 这类要在固定延迟预算下提升能力的场景，「不增加每 token 计算量」比绝对涨点更重要。
  4. 边界（必须写清）：① 只验证 10B-A1B 单一体量（24 层、708B tokens），2B 规模是否同样成立未验证；② 九任务均值绝对值只有 33 左右（含 CMMLU/MMLU-Pro/GPQA/BBH/SimpleQA 等混合），+1.18 点不等于「能力跃迁」；③ 只报训练期 loss 与离线评测，没有端到端 serving 实测（通信量不变是设计论证，不是集群实测）；④ 数字作者自报、本线未复现。

2Raincheck: Deferred Multimodal Prefill for Efficient Multi-Turn MLLM Inference

中文一句话
多轮多模态对话（同一张图/同一段视频反复追问）里，长视觉输入把 TTFT（首 token 延迟）拉高；按当前问题做硬剪枝能少算 prefill，但被剪掉的 token 永久丢失，后面几轮可能正好要用。作者提出 Raincheck：把「先算哪些」和「以后还能不能用」解耦 —— 先用现有剪枝方法选 30% 做初始 prefill，没被选中的 token 保留下来，在解码阶段的闲置算力里按源顺序渐进补 prefill，答案返回后仍可继续补；靠 attention 可见性控制 + 仿射状态映射，让 full-attention 与 hybrid 循环（GDN）模型在「已经开始生成」之后还能更新上下文；prefill–decode 融合减少重复权重读取。结果：在 Qwen3-VL-8B / Qwen3.5-9B、4 种剪枝方法上，分别找回硬剪枝所丢质量的 77.7% / 60.4%（MultiVerse / ConvBench）；MultiVerse 首轮 TTFT 相对全量 prefill 降低 24.1% / 17.9%，平均 TPOT 只增 0.13% / 0.47%。

推荐理由（借鉴 · 与 BaiZe / ZhuLong 的关系）
  1. 直接命中 ZhuLong「长上下文 agent」的成本结构：agent 多轮调用同一份长上下文（日志、代码库、报错栈）时，「先看到全部」很贵，「只看一部分」会误判。Raincheck 的思路是把「暂时不看」变成「稍后补看」，用解码阶段的闲置算力（小 batch 下 decode 是 memory-bound，算力有余）去补 prefill —— 这是「时间换信息完整性」的显式调度，与我们「多轮里怎么复用上下文」是同一问题。
  2. 机制可对照到我们 serving 栈的具体位置：① attention 可见性控制：补进来的 token 何时对后续解码可见；② 仿射状态映射：full-attention 与 GDN 循环态在「生成已开始」后如何增量更新（这对混合 Mamba/attention 模型尤其关键，正好对上 BaiZe 的混合架构）；③ prefill–decode 融合减少重复权重读取。三条都是可以拿我们自己的 kernel/torch 实现去比对的点。
  3. 指标口径干净：同时报质量找回比例（相对硬剪枝的损失）与延迟（TTFT、TPOT、E2E），并给了「静默丢信息」的量化 —— 初始选择会漏掉第二轮所需 token 的 19.34%（Qwen3-VL）/ 17.32%（Qwen3.5），这是「为什么要补」的直接证据。
  4. 边界（必须写清）：① 系统实验是单卡 H20-3e、TP=1、batch=1（一次只跑一个请求），作者在结论里明确写「并发与批处理下的状态映射仍是开放问题」⇒ 不能直接套到我们的高并发生产 serving；② 24.1% 的 TTFT 降幅是相对「全量 prefill」，而相对硬剪枝的 TTFT 差值置信区间包含 0（作者如实给出）；③ 个别轮次会回退（如 Qwen3-VL 的 T1/T2 略低于硬剪枝）；④ 数字作者自报、本线未复现。

3A Case Study of a Multi-Agent Kernel-Optimization Loop That Learns a New AI Accelerator

中文一句话
前沿 LLM 写 CUDA kernel 已经不错，但换到没见过、文档稀疏的加速器上正确率会塌（作者引用的对照：Ascend C 上 GPT-5.2 的 pass@4 从 CUDA 的 92% 掉到 14%）。本篇是一份单案例研究：在 FuriosaAI RNGD NPU（较新的 Rust DSL，文档少）上，用 LLM agent 循环在共享且稀缺的设备上、12 天（283 h）优化 3 个 Gemma-4-12B 解码 kernel。循环自己建目标知识（写并自检 DSL 文档摘要、用微基准测芯片、记录编译器派生的合法性规则，工具链变了就回查重测），用基于角色的 Design Tree 搜索探索整 kernel 设计并累积被接受的小改动；因为设备时间稀缺、读数有噪声 ⇒ 先用廉价检查筛掉候选再上设备，后期要求与当前最优在设备上反复对比才接受。最终相对官方基线 几何平均 9.293×，每个 kernel 的周期数都在「仅搬运权重所需周期」的 1.25× 以内。

4Spokes, not a Ring: Revisiting the Weekday Manifold in Language Models

中文一句话
已有工作发现「星期几」在语言模型激活空间里排成一个圆环，并据此认为沿圆环移动等于日期/时间的连续变化。本文检验这个「连续流形假设」：① 以恒定角速度沿拟合圆环做 steering（层 2 注入、层 28 读出），行为与残差的变化在星期附近极慢、在相邻星期之间的弧段很快，呈台阶状（越靠近输出层 steering 越平滑 ⇒ 「晚期层看起来平滑」不能反推表征连续）；② 用 Jacobian 的 Frobenius 范数画极坐标敏感度图，得到七个以星期为中心的低敏感「辐条」，且向外径向延伸（说明不是「只沿切向走」造成的假象）；③ 「一天中的时刻」几乎不在环上：时刻修饰词在环平面内造成的角位移 ≤6.30°，远小于相邻星期质心的 44.33°–59.81°，且与「very rainy」这类非时间修饰词同量级；沿环 steering 对预测小时的改变 <0.02h，而沿「late–early」平面外方向同范数 steering 改变 −1.8h / +1.1h；④ 「不确定性」不填充两星期之间的弧段，而是让表示沿两根星期辐条向内收缩；⑤ FineWeb 的 49,678 条（574,217 篇文档）以星期结尾的 16-token 片段显示：上下文主要整体平移七个星期表示（减去每段均值后，段内 RMS 半径从 0.65 降到 0.23 个环半径），而不是把它们旋转到中间区。
