1MuonGS: Pretraining LLMs with Relaxed Weight-Norm Control

中文一句话
把 Muon 系优化器里的「权重范数控制」换成一个可分析的量 —— 累积有效学习率 C_T = Σ_{t<T} η_t / ‖W_t‖_F：作者证明 vanilla Muon 在训练全程只能按对数累积（Θ(log T)）（越到后期「每步实际挪动」越小，可能是它经验上进步偏慢的原因之一），而 MuonW / MuonH 在给定条件下能保证至少线性累积；再进一步指出「范数增长得足够慢」本身就足以比对数最坏情况更快，于是提出 MuonGS：用 Gram–Schmidt 投影去掉每次 Muon 更新的径向分量，但不固定权重范数。在恒定名义学习率 + 有界更新方向下，证明范数 至多按 √t 增长、C_T = Ω(√T)（后期仍在累积），并对光滑尺度不变目标给出 O(T^{−1/2}) 的平稳性保证。预训练实验：160M / 400M 稠密 GPT 式模型（100B-token FineWeb 子集，BF16）+ 135M active / 1B total 的 MoE（Ultra-FineWeb，10.8B / 21.6B tokens）；长训练 horizon 下验证困惑度低于 MuonH，稠密模型在等验证 loss 下估计 token 等效加速最高约 15%（正文口径为「长训练 horizon 约 7–15%」）。

推荐理由（借鉴 · 与 BaiZe / ZhuLong 的关系）
  1. 直接落在 BaiZe 的「训练优化器」这一步：MuonGS 不改模型结构、不改数据配比，只在每次 Muon 更新后做一次 Gram–Schmidt 径向投影（把更新里「让权重整体变大」的那一维减掉）⇒ 若 BaiZe 的预训练已用 Muon / MuonW / MuonH 一类优化器，这是低改造成本的候选替换。
  2. 它回答的是「为什么该控范数」，不只是「调个超参」：把 C_T 当诊断量，可以直接在我们自己的训练日志里估（每步 η_t/‖W_t‖_F 累加）—— 先用它判断「我们的优化器后期是否也在对数停滞」，再决定要不要换；这比直接换优化器更便宜、更适合先做「读原文 + 加一个监控指标」。
  3. 「不需调 weight decay」这一点对我们有利：作者明确把 MuonGS 与 MuonH 并列为无需调 weight-decay 系数的一类（对比 MuonW 要调 λ），少一个随规模漂移的超参，对 2B 级长期训练更省调参预算。
  4. 边界（必须写清）：规模只到 160M / 400M 稠密（3–25B / 8–63B tokens，约 1–8× Chinchilla）+ 1B total / 135M active 的 MoE（10.8B / 21.6B tokens，属「初步结果」），没有 2B 级验证；15% 是拟合 MuonH loss 曲线反推的 token 等效加速估计，不是实测墙钟加速；结论依赖「有界更新方向 / 尺度不变目标」等假设；数字作者自报、本线未复现。
建议动作：读原文（重点 §3 的 C_T 定义与 Thm 条件、§5.2 的 token-equivalent speedup 拟合方法、§5.3 MoE 的「初步」口径）+ 试跑（小规模对照：同数据/同 token 预算下 MuonH vs MuonGS，先看 C_T 曲线与验证 ppl；不改主训练）。

2EnvSched: Environment-Aware Scheduling for Rollout-Efficient Agent Reinforcement Learning

中文一句话
Agentic RL 的瓶颈常常不是「训练步数」而是「rollout 太贵」：每个任务都要拉起工具有状态有验证器的可执行环境、跑完还要验。本文把调度的粒度从「题」换成「环境–任务对」：把环境–任务对建成双关系图（同环境内连边抓任务语义与共享的工具/状态/验证器结构；跨环境连边抓抽象的执行与奖励拓扑），沿两类边传播历史 rollout 统计量、预测「任务内奖励方差」，再按两个互补目标排批 —— exploitation（优先能给到「有信息量的奖励差」的任务）+ coverage（把每批摊到欠观察的环境与交互模式上），并用环境配额与相似度惩罚防集中与冗余，不需要额外的 pilot rollout。实验：在 EnvScaler 池（2,550 个任务实例 / 51 个可执行环境）上对 Qwen3-Thinking 1.7B / 4B / 8B / 30B-A3B 做 GRPO（每批 B=64 对、每对 K=8 条 rollout = 512 条轨迹，200 步，覆盖比例 ρ=1/2）；Qwen3-8B 在 BFCL-v3 / τ-Bench / ACEBench-Agent 上 40 步平均 48.81，已超过随机选题 120 步的最高分；200 步时各规模三基准一致优于随机（4B：+3.05 / +3.23 / +2.00；8B：+4.00 / +3.03 / +3.34）；仅按「prompt 信息量」调度的 DPS / LEEPS 整体打不过它，个别维度还不如随机。

  1. 正对 ZhuLong 的「generate–execute–refine」成本结构：EDA coding agent 的每条轨迹都要真跑（编译 / 仿真 / 检查），rollout 是主要开支；本文给的正是「同预算下怎么选题」—— 把「环境」当一等对象（同一 EDA 工具链 = 一个环境），按预测奖励方差 + 欠观察覆盖排批，可直接映射到我们的 RL 数据采样器。

3Context Is a Pipeline, Not a Window: Information Attrition in LLM Agent Harnesses

中文一句话
大家评估 agent 只看两个数 —— 上下文窗口多大、最终答案对不对；本文指出还有第三个被忽略的数：工具输出在「模型看到之前」丢了多少。作者把自己那个「读 Linux 内核 trace 定位注入故障」的 tool-using agent 当显微镜，提出五阶段上下文流水线：S1 产生→投递、S2 投递→行动、S3 行动→保留、S4 保留→交接、S5 交接→跨运行持久（S5 是为保持运行独立而故意关掉的设计选择，不是测出的失败）。实测 720 次运行：最大的一次 prompt 只用了 400k 窗口的 5.75%（≈23k tokens），但 11,189 条工具结果里有 3,827 条（≈1/3）在到达模型前被按 JSON 文本固定长度前缀截断，且每条被截的都成了坏 JSON；同一个 payload 里一个列表只有 4.7% 的调用到达模型（742 次），紧挨着的另一个列表 99.3% 到达。证据恰好藏在哪一边，取决于故障进程是「trace 中途新起」还是「早已在跑」⇒ 诊断准确率沿同一条线分裂（40–55/60 vs 0–24/60）。受控实验（864 条真实工具结果回放）：截断的代价先表现为「多干活」，而不是「答错」 —— 工具调用 +43%（53→76）、计算量翻倍（18→36）、yield 从 0.61 掉到 0.31（findings 始终 11 个）；作者明确说「截断是否真的导致准确率下降」仍是开放问题。另抽 7 个 agent 框架：2 个同样按位置截断（langchain-core 保留前 500 字符；smolagents 删掉超 20k 字符观察的中间），3 个完全不截断（只是把损失推到上下文窗口），1 个只截自己的 tracing 数据，1 个按整行截断（结构感知的安全做法存在，但不是默认）。

4Learning to Read Braille: Benchmarking and Improving Braille Recognition Capabilities of VLMs

中文一句话
会转写文档的 AI，几乎读不了盲文。作者做了 BrailleBench（259 张人工校验的真实盲文照片：215 张一级（Grade-1）+ 44 张二级（Grade-2），覆盖书本插图、标牌、印刷点、低分辨率等多种材质与拍摄条件），把「闭源 VLM / 开源模型 / OCR 专用 / 工具辅助 agent」四类系统拉到同一张卷子上：单次推理的通用 VLM 普遍不及格 —— 一级上除 GPT Sol 系以外全部低于 3% 完全匹配，最强的 GPT-6.1 Sol 也只有 53.95%（CER 0.374）、GPT-5.6 Sol High 11.16%；二级更难（GPT-6.1 Sol 11.36%、GPT-5.6 Sol High 4.55%）。「工具辅助」的 agent harness 强得多但很贵：Claude Code（Opus 5.5 High）一级 88.37%（CER 0.019）、二级 40.91%；Codex 一级 62.79%、二级 0%；代价约 180 秒/图、$0.51–0.58/图。作者另造合成盲文生成管线（276k 样本，含版式与图像扰动），用它完整微调 Qwen3.5-2B，一次模型调用即在真实基准上达 一级 86.98% / 二级 61.36%（二级比 Claude Code 高 20.45 个百分点）。最扎心的是负结果：用先前工作的合成数据（WMT-Train）训练时，同一个 2B 模型在合成验证集 96.00%，到真实照片一级只剩 3.26%、二级 0%（Llama-3.2-11B 为 55.00% → 0.47%）；把合成语料扩到 500k 长文本，真实一级反而从 82.63% 掉到 72.97%（合成验证集却从 41.70% 升到 63.10%）⇒ 「合成集高分」几乎不预测真实照片表现。
