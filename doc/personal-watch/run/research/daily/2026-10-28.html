1EvoRouter: Cost-Efficient Multi-Agent Routing via Insight-Guided On-Policy Distillation

中文一句话
大规模多智能体系统（MAS）服务要同时决定：用哪几个 LLM、什么协作模式（IO / CoT / Reflection / Chain / FullConnected / Debate）、几个 agent、几轮交互、挂哪些技能 —— 配置空间是组合爆炸，而执行只回传「成功/失败 + 成本」这种稀疏结果奖励，对互相耦合的规划决策几乎没有细粒度监督。本文提出 EvoRouter：① 一个 LLM 专家周期性把跨任务的「配置—结果—成本」轨迹综合成带适用条件的洞察（任务相关的能力瓶颈、扩资源的边际收益、配置项之间的相互依赖）；② 用「带洞察条件」的 on-policy 蒸馏（OPD）（MiniLLM 式 reverse KL、只作用于 <analysis> / <plan> 段、教师带特权信息且 stop-gradient）把洞察变成 token 级稠密监督；③ 用成本感知 RL，奖励 R(τ)=Rperf−λC·Rcost、Rcost=log2(1+C(τ)/B(q)) 按任务预算归一，并把成本罚分上限压在 cmax<1 以保证成功轨迹奖励仍为正；④ 更新后的策略再产生新轨迹，形成「执行 → 洞察 → 内化」自演化闭环。实验为 21 个数据集 / 7 个领域（19 个域内：数学 / 常识 / 知识 / 检索 / 多模态；2 个域外：LiveCodeBench 代码 / BBH-LD 逻辑），LLM 池 = Qwen3.5-35B-A3B / 122B-A10B / 397B-A17B + DeepSeek-V4-Flash + GLM-5。EvoRouter-4B 域内平均 68.69%（比最强基线 RCR-Router 的 61.46% 高 7.23 个百分点），同时平均 MAS 成本降 50.95%（15,280.79 相对 FLOPs 单位）；把 router 自身开销计入后总成本 18.94k 单位，仍比 MasRouter 低 76.5%、比 RCR-Router 低 39.2%。域外平均 74.67% / 76.80% / 78.93%（4B / 8B / LLaMA-8B），比最强基线高 7.74–12.00 个百分点。

推荐理由（借鉴 · 与 BaiZe 推理服务 / ZhuLong agent 编排的关系）
  1. 把「多模型 + 多协作模式」的选择变成一个可训练对象：我们若在 BaiZe 服务侧同时挂着不同规模/不同家族的模型（评测、数据合成、线上兜底），现在多是人写规则或按显存硬切；本文说明「router 是一个 4B/8B 的小模型 + 两路训练信号（稠密蒸馏 + 稀疏成本感知 RL）」就能拿到 +7.23 pp 准确率同时 −50.95% 计算，而且是端到端含 router 开销的成本（18.94k vs 39.2% 更低）—— 这个「把 router 自身算进去」的口径值得照搬。
  2. 成本项的设计有可直接复用的细节：Rcost=log2(1+C/B) 用任务自己的预算 B(q) 归一化，使不同难度任务的成本可比；并把成本罚分上限压在 cmax<1，保证成功轨迹永远拿正奖励。这是「成本惩罚把成功样本也压成负奖励 → 训练崩」的常见坑的直接补丁，我们的 RL 配方可以直接借用这一条。
  3. 消融证明「只加 RL 不够」：4B 上仅 SFT 53.23 → 去 RL+OPD 59.77 → 去 OPD 63.23 → 完整 68.69（去 insights 则 64.54）。也就是说 OPD 稠密监督贡献 +5.46、洞察本身贡献 +4.15，两者都不是装饰。若我们只上 RL、不上「跨轨迹洞察 → token 监督」，按本文数据会明显打折。
  4. 洞察是「离线周期生成」的，不是在线 critic：专家 LLM 定期批量总结，训练时无需额外在线模型 —— 对算力紧张、又想让策略自我改进的场景，这比 online critic / MCTS 便宜得多（对照同批 FOCUS 需要 critic 精化 GPU）。
  5. 边界（引用时必须带上）：定位云侧 MAS（作者自述下一步才做云–边协同）；成本用相对 FLOPs 代理，不是墙钟 / 能耗 / 显存；router 只到 4B/8B；21 个数据集中 19 个为域内；作者自报、本线未复现、未精读附录。

2FOCUS: Active Critic Learning for Long-Horizon Language Model Agents

中文一句话
长程 agent（几十到上百次工具调用）用「可验证奖励 RL」训练时，一条轨迹只给一个 0/1 终局奖励，早期动作拿不到信用；学一个 critic 给中间状态估值是常见解法，但 critic 本身不准，而在轨迹中间反复续采样来估值又很贵。本文把「用续采样改进 critic」当成主动学习问题：FOCUS 把每个 episode 当作搜索树，用上下文压缩（compaction）产生的段边界作为候选状态，用 critic 的预测 + 已采样续接的证据估计「再采一条能把估值误差降多少」，把有限 rollout 预算分配给最可能降误差的状态；细化后的状态价值用 TD(λ) 给相邻状态之间的「段」打 advantage，采样得到的证据同时作为 critic 的训练目标 —— 于是「本轮信用分配」与「下轮 critic 更准」耦合起来。context management 与 rollout 分配解耦，可替换压缩算子 / harness / 信用估计器。实验：Qwen3.5-9B，DeonticBench（法律推理）、BrowseComp-Plus（深度检索）、LocBench（代码定位），与 GRPO、VinePPO 在匹配的每步生成预算下各训 1 epoch、每次 rollout 都压缩：FOCUS 三个基准都第一 —— DeonticBench 总体 56.5（GRPO 52.4 / VinePPO 49.4）；BrowseComp-Plus 55.4（48.2 / 46.6，+7.2 个百分点）；LocBench File@1/@5 72.4 / 81.6（70.1 / 80.5、67.8 / 79.3）。Qwen3.5-27B（LoRA）DeonticBench 76.3（74.3 / 74.9），增益变小 —— 作者称可能因未训练的 27B 起点已达 73.4。诊断：critic MSE 随细化预算下降、Spearman 相关上升；GRPO 训练后期出现「工具调用塌缩」（压缩完就交卷，即使法规/代码还没读完），FOCUS 保持更长程探索。

3Shared Context, Separate Engines: Streaming Vision--Language Inference on Edge SoCs

中文一句话
边缘 SoC 上通常同时有 CPU / GPU / NPU，但 VLM 运行时往往只把语言生成放在一个引擎上，其余闲置；流式 VLM 又天然有并行机会（新帧在到达、旧查询还在作答）。难点是各引擎算力与访存特性不同、同跑互相干扰（实测 RK3588 上共跑让 CPU 与 Mali GPU 解码分别慢 26% / 11%；QCS6490 上三引擎共享约 16 GB/s 读带宽，三引擎同跑时聚合解码带宽从 40–45 升到约 60 GB/s），且每个后端把历史放在自己的 KV 布局里，别的引擎接不上。本文提出 CrossInfer：把「流的历史」抽象为带版本号的已发布上下文，与各引擎私有的 KV 状态解耦 —— 任何引擎都能通过复用 / 导入 / 重建该版本继续这条流（跨引擎 KV 导入比重新计算前缀让首 token 早 4.6×）；两种执行模式：Stateful Streaming Generation（一个引擎摄取新帧、另一个按已发布版本作答，答案与串行参考一致）与 Concurrent Sequence Generation（CPU/GPU 并行服务不同就绪请求），再加按「预计完成时间」派发的调度器。三块板实测（Apple M4 Max / Rockchip RK3588 / Qualcomm QCS6490）：RK3588 双路视频流下吞吐比「单引擎 + 上下文复用」高 19.6%、比「双引擎但无共享状态」高 27.2%，首 token 时间降 34.9%；M4 Max 上 SSG 吞吐是串行的 2.48×（RK3588 +56.7%）；FastVLM-1.5B 上视觉与语言重叠使吞吐最高 +23%、平均 TTFT −22%；Qwen3.5 0.8B–9B 四个模型上相对「串行 + 上下文复用」吞吐最高 +72.4%；Qwen2.5-VL-3B 单请求能耗比 llama.cpp 低 23.6%；状态感知派发把完成时间最多降 72.7%。

推荐理由（借鉴 · 与存储/芯片视角 + BaiZe 高效推理的关系）
  1. 把 KV 状态当成「可发布、可导入、可重建」的一等对象：这是我们最该抄的一条设计 —— 不是「共享内存就能共享 KV」，而是显式定义版本化上下文 + 引擎私有状态的转换接口。本文实测这种状态搬运把首 token 提前 4.6×（对比重新算前缀），说明状态迁移的成本模型（导入 vs 重算的临界点）本身就是性能杠杆，和我们在意的 KV cache 分层 / prefill–decode 分离是同一类问题。
  2. 给出了「多引擎共用带宽」的实测口径：QCS6490 三引擎共享约 16 GB/s 读带宽且分配不均；三引擎同跑把聚合解码带宽从 40–45 抬到约 60 GB/s，但同时共跑会让 RK3588 的 CPU/Mali 解码慢 26% / 11%。这类「加引擎 ≠ 线性加速」的量化，比只看单引擎 TOPS 更接近真实部署。
  3. 调度目标很朴素但有效：按「预计完成时间」派发，而不是「哪里空闲放哪里」—— 在 9 组 RK3588 历史/积压设置里都选中更快的引擎，完成时间最多降 72.7%。这是可以被我们直接借用的调度原则（含状态所在位置与共跑干扰的代价项）。
  4. 端侧多模态的能效点：单个 Qwen2.5-VL-3B 请求比 llama.cpp 少 23.6% 能耗 —— 对「端侧/近存计算」叙事是可引用的第三方实测（但只有单点，未给全负载曲线）。
  5. 边界（引用时必须带上）：只测 3 块边缘板、模型 0.5B–9B、无数据中心 GPU 场景；收益强依赖具体 SoC 的引擎速度与干扰特性（作者自己强调「没有一种放置通吃」）；能耗只报单点；作者自报、本线未复现、未精读附录。
