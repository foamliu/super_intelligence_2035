1Safe Reinforcement Learning for Multi-Turn Clinical Agents: When Dense Rewards Beat Outcome Rewards

中文一句话
在多轮临床 agent（该问什么、何时停止收集证据、采取哪个动作）上做受控实验：只用最终结果奖励的 GRPO 常把平均分刷上去，却同时制造过早承诺、只问一个问题就收手、在罕见高危病例上崩掉；给「能降低不确定性的提问」加稠密过程奖励（λ=0.2）后，在 3 个训练种子上留出集价值 +0.285→+0.313、高危价值 +0.098→+0.157、高危支持率 0.33→0.50、中等病例支持率 0.38→0.67，且不再出现 outcome-only 的高危种子崩坏；但过程奖励的强度是任务相关的（滴定任务里 λ=0.1 才把提问数从 1.24 拉回 2.67，λ=0.2 则过度提问、价值掉到 −0.091），且 RL 修不好有偏 SFT 留下的稀有行为缺口。

推荐理由（借鉴 · 与 vision 的 v6 奖励重设直接对口 / 与 zhulong 的「分数 + 成本」口径侧向相关）
  1. vision 的根因就是「奖励离散、组内全同」：v5 诊断显示 78.7% 的组 advantage 标准差为 0、全 0 组 0%、全同档组无信号。本文的对照组正是outcome-only GRPO，并把它拆成三类失败模式（过早承诺 / 只问一次 / 高危崩坏），与「离散档位把过程压扁」是同一类病。它给的解法不是调温度，而是把过程信号显式写进奖励，且用 λ 做强度旋钮 —— 这正好对应 v6 要做的「奖励连续化」。
  2. 有可用的量化对照与安全护栏：3 个种子、留出集、support@k（不是只看均值）——高危支持率 0.33±0.29 → 0.50±0.00，中等 0.38±0.18 → 0.67±0.10，同时提问数只从 1.82 增到 2.08。说明「加过程奖励」不是无代价地鼓励多动作，而是把「有效动作」与「凑动作」区分开。v6 若只看总分，会把「多测几次波形」误判为变好。
  3. 负结果同样值钱：分离探索/利用能把高危支持推到 1.00，但提问数升到 4.4、良性支持从 0.48 掉到 0.04，且末次 ckpt 回落到 0.50 —— 「选点乐观」会把一次性收益当成稳定收益。这对 vision「CPU 小样本、几次就下结论」是直接警告。
  4. 边界：① 临床多轮决策，不是波形，数值不可移植，只有奖励结构/报告口径可移植；② 高危子群只有 2 个病例（support 只能取 0/0.5/1），统计力极弱；③ 主实验 3 seeds，滴定/解耦实验是单种子；④ 作者自报、本线未复现。

2WorkflowArena: Benchmarking Executable Workflow Orchestration in LLM-Based Multi-Agent Systems

中文一句话
把「多 agent 怎么组织」当成一项可测能力：造 145 个长程任务 / 8 个专业域 / 17 种任务形态，每个任务给初始工作区 + 一个由隐藏 verifier 判分的整合交付物；agent 自己决定要不要委派、怎么委派，所有委派必须走统一的 Workflow 工具（最多 16 个并发 worker、原生 sub-agent 被禁用），委派次数、worker 规模、主/子 agent 的 token 与成本全部记账，且共享同一时间预算。25 个「模型 × effort」配置里没有任何一个通吃所有域：最强 Opus max 平均解出 36.95%，MATH 最高 95.83%、SWE 最高 29.41%、LAW 从未超过 9.09%、FIN 从未超过 18.75%；连续得分与 resolved 率的 Spearman 只有 0.90，但域内差得离谱（SWE 平均差 66.16 分：Opus high 的 SWE 得分 96.98 却只 resolved 17.65%）。组织策略也分家：Claude Code 系少委派、大编组（Opus 0.86 次/任务、5.55 worker/次），Codex 系多委派、小编组（Astra 2.09 次、1.72 worker）；把执行模型固定后，Opus 写的 workflow 能提升所有弱执行者（Kimi 35.75→46.61、DeepSeek 18.37→25.24）。

3Will AI mess my RTL? A snapshot-based approach to verifying AI-written RTL

中文一句话
提出 SVApshot：让 LLM 为一个已有 RTL 模块自动生成 SystemVerilog 断言（SVA），再用形式验证工具反复给出反例（CEX）→ LLM 修断言，直到得到一组「对参考 RTL 证明通过」的断言快照；快照就是该模块功能的回归测试集，之后无论人还是 AI 改代码，只要跑这组断言就能发现「功能被改坏」。在 16 个 RTL 模块（24–419 行，含带子模块的层次化设计）上测 3 个模型：覆盖率不再是 0/1（如 branch_unit 14.4%→42.0%、score_board_scalar 55.7%→86.0%、ptw 47.9%→52.8%、tlb 23.7%→39.3%；alu 初始即 100%）；人工在 scoreboard 里埋一个「64 位乘法写错 inst_d[2] 而非 inst_d[1]」的真 bug，生成的断言成功检出。成本约 0.5 €/模块快照，但时间主要花在「修断言」（55 分钟，占 77.4%；FPV 工具占 69.4%），作者建议调小修复次数上限。

推荐理由（借鉴 · 与 designflow 的「判分可验证性 + L1–L5 保真度」直接对口 / 与 zhulong 的 EDA 代码评测侧向相关）
  1. designflow 正在把「检查」做成 k_check≥16 的断言闸门，但仍以「全过 = PASS」为主。SVApshot 的做法补上了三件缺的东西：① 快照（对参考实现证明通过的性质集，作为未来改动的回归基线）；② 覆盖率/通过断言数作为分级分数（不是二值）；③ 埋 bug 哨兵（参考实现里故意埋一个错，检查器必须报错）——这正好对应 designflow 已有的 bad_p7 切边 rect 哨兵思路，可把「哨兵必须失败」写成通用验收项。
  2. 它把「部分完成」变成可解释的数字：同一模块不同模型/不同初始断言集，最终覆盖率 1.76%–100% 连续分布（mul_unit：GPT 92.6→98.9，Llama 3.3 70b 仅 0.7→1.76）。这比只看 pass/fail 更能区分「勉强过」与「真的覆盖了边界」。
  3. 成本口径可直接进设计：0.5 €/快照，77.4% 时间在修断言，FPV 占 69.4% —— 说明判分器本身的时间/成本要单列；designflow 若加形式/断言类检查，应按「每 case 分钟数 + 工具费」入账，而不是只算造题成本。
  4. 边界：① 全程依赖 SystemVerilog + JasperGold，designflow 的 Python/GDS/DRC/SPICE 任务不能直接跑，只能移植协议；② 只测 16 个 24–419 行的小模块，未测 SoC 级；③ 断言快照假设「参考 RTL 是对的」，参考错则快照错；④ 作者自报、本线未复现。
