推荐理由（借鉴 · 直接对口 data 线的「中文 token 预算」）
  1. 它问的是我们每天在付的钱：UTF-8 是变长编码，同一个汉字占 3 字节、同一个拉丁字母占 1 字节 ⇒ 在固定 token 预算下，不同语言的「信息量/token」并不相等。摘要的结论（中文、韩文受益于压缩式编码）正是「为什么中文语料要按字符数而不是按字节数计量」的实验依据。
  2. 结论有明确边界，不能直接搬：实验对象是 byte-level LM（无 tokenizer）；我们用的是 BPE/分词器 ⇒ 🚫 不能直接读成「中文模型更省 token」。可搬的是方法：把「编码/分词」当作一个可消融的变量，并按文字系统分组报告。
  3. 可落地的一件事：data 线在语料统计脚本里加三项「每字符 token 数」——中文 / 英文 / 代码，再算「每 1k token 覆盖的文档页数」；这张表能直接解释「为什么同样 2T token，中英配比一改评测就抖」。
  4. 边界与风险：① 只在 4 种语言上验证；② byte-level 与 BPE 不可直接类比；③ 作者自报、无大规模下游任务验证；④ 「压缩式编码更好」不等于「分词越细越好」，需自行复现。

5Are Dense Rewards Worth Their Tokens in GRPO?

中文一句话
给「稠密过程奖励」算了一笔算力账：提出等算力协议（按生成 token 与训练 GPU 小时对齐预算）+ 预注册实验，指出逐步蒙特卡洛奖励的续写本身就占 91% 的生成 token。在 Qwen2.5-1.5B 上，该奖励「每次更新」看着领先 GRPO，但等 token 结束时低 14.3 个百分点、等训练时间低 7.8 个百分点；四个稠密奖励变体在同等训练时间下均未超过 GRPO。反向发现：按「预测成功率最接近 1/2」挑 prompt 在等算力下提升 1.7（Qwen3-0.6B）/ 0.8（Qwen2.5-1.5B）个百分点。据摘要：1,668 次运行、6 个模型。

推荐理由（借鉴 · 直接对口 zhulong 的 RL 消融口径与 data 的难度采样）
  1. 「稠密奖励免费」是错觉：过程奖励要为中间步骤采样续写，而续写吃掉 91% 的生成 token ⇒ 只看「每次更新的分数」会系统性高估它。这个偏差量级（14.3pp / 7.8pp）大到足以改变技术选型，我们的 RL 消融如果按 update 对齐，很可能正在犯同一个错。
  2. 方法可原样借用：matched-compute protocol（生成 token + GPU 小时双口径）+ 预注册 + 控制副作用。这正好是我们 zhulong 消融表缺的「算力口径」一列，也与我们已写的「等计算预算对比」原则一致。
  3. 一个更便宜的正向发现：不改奖励，只改挑哪些 prompt（预测成功率≈1/2），在等算力下也能涨 1.7 / 0.8 个点 ⇒ 数据侧的「难度采样」是比「设计更复杂的奖励」更省的杠杆，可直接进 data 线的课程学习方案。
  4. 边界与风险：① 模型规模 0.6B–1.5B、以数学/推理类 RLVR 为主，EDA 任务未验证；② 「梯度测试高估 1–2 个点」说明单 batch 诊断不可靠；③ 收益出现在训练早期，且 2× 学习率的 GRPO 只差 0.5 个点 ⇒ 别把增益全归给方法；④ 作者自报、本线未复现。
