1SLIC: Reinforcement Fine-Tuning Small LMs for Multi-Turn Analog Circuit Optimization

中文一句话
把模拟集成电路设计当成多轮、依赖仿真器的工程任务：用强化微调训练 4B 本地模型做闭环电路优化（结构化电路表示 + 离散「相对更新」动作 + 按域/成功门控的多目标奖励 + 把每步仿真反馈用于策略与 rollout 的 RGRS），并开源 41 个放大器拓扑的基准（分布内 / 留出拓扑 / 跨工艺节点三种协议）。摘要称：仅用开源 65nm CMOS PTM 训练，SLIC-Random 在 8 轮内分布内四指标 Pass@1 87.1%（比 763B 的 DeepSeek-V4.1-Flash Think 高 48.5 个百分点）；SLIC-Softmax 留出拓扑 72.6%；跨 5 个未见工艺节点零微调迁移；商用 TSMC 65nm PDK 留出拓扑 49.9%；测试时仿真交互增到 32 轮可到 83.2%。

推荐理由（借鉴 · 与 designflow / zhulong / pretrain 的「小模型 + 多轮工具」直接对口）
  1. 它是「小模型 + 仿真器闭环」的完整样板，不是又一个 benchmark：动作 = 离散化的相对更新（不是自由文本），奖励 = 按域与成功门控的多目标，再叠加 RGRS 把逐步仿真反馈同时用于策略学习与在线 rollout 构造。我们的 ZhuLong 也是「模型出动作 → 工具跑 → 看指标」的闭环，差别只在工具（波形/版图仿真 vs 电路仿真）。可直接对照的三处：动作怎么离散、奖励怎么门控、失败 rollout 怎么复用。
  2. 「4B 打过 763B」是任务结构带来的，不是模型更强：+48.5pp 的对照是通用大模型直接做同一任务，而非同数据同预算的 763B 微调 ⇒ 🚫 不能读成「小模型普遍更强」。真正可迁移的是：把领域动作空间与奖励写死，比把通用模型堆大更省。这正好支持我们 pretrain/SLM 侧的「域内 2B + 结构化接口」路线。
  3. 三种泛化协议可原样借：分布内（同拓扑族）/ 留出拓扑（未见结构）/ 跨工艺节点（未见 PDK）。对应 designflow 的 L1–L5 保真度：每一级都要单独报，并且报告「测试时预算」（8 轮 vs 32 轮），否则「多给几轮就能刷上去」会被误读成模型能力。
  4. 边界：① 模拟电路是连续参数 + 小动作空间 + 可仿真，EDA 数字流程是离散、长流程、工具昂贵，🚫 不可直接搬；② 87.1% / 72.6% / 49.9% / 83.2% 均为作者自报，基准自建、任务自选；③ 商用 PDK 上的 49.9% 是「本地推理、不传数据」的部署论证，不等于生产可用；④ 论文摘要未给训练成本与失败案例。

4When does text encoding matter for language modeling?

中文一句话
把「文本编码」当变量而不是默认：在 byte-level 语言模型上系统比较 UTF-8、其它 Unicode 方案、语种专用编码与自定义编码，并提出「按文字系统编码 + UTF-8 回退」的混合方案 Aether（在 4 种拼写差异大的语言上建模）。摘要称：信息密度高的字符语言（中文、韩文）显著受益于压缩式编码，而单字符信息量低的文字（格鲁吉亚文、泰米尔文）对编码选择基本不敏感 ⇒ 作者主张「编码应作为语种相关的设计选择，而非通用默认」。

推荐理由（借鉴 · 直接对口 data 线的「中文 token 预算」）
  1. 它问的是我们每天在付的钱：UTF-8 是变长编码，同一个汉字占 3 字节、同一个拉丁字母占 1 字节 ⇒ 在固定 token 预算下，不同语言的「信息量/token」并不相等。摘要的结论（中文、韩文受益于压缩式编码）正是「为什么中文语料要按字符数而不是按字节数计量」的实验依据。
  2. 结论有明确边界，不能直接搬：实验对象是 byte-level LM（无 tokenizer）；我们用的是 BPE/分词器 ⇒ 🚫 不能直接读成「中文模型更省 token」。可搬的是方法：把「编码/分词」当作一个可消融的变量，并按文字系统分组报告。
  3. 可落地的一件事：data 线在语料统计脚本里加三项「每字符 token 数」——中文 / 英文 / 代码，再算「每 1k token 覆盖的文档页数」；这张表能直接解释「为什么同样 2T token，中英配比一改评测就抖」。
  4. 边界与风险：① 只在 4 种语言上验证；② byte-level 与 BPE 不可直接类比；③ 作者自报、无大规模下游任务验证；④ 「压缩式编码更好」不等于「分词越细越好」，需自行复现。
建议动作：data 线在下一版配比报告里加一节「编码与 token 计量口径」：给出中/英/代码的 chars-per-token 与 bytes-per-token 两个数，并在固定 token 预算下做「按字符均衡 vs 按 token 均衡」两臂对照（判据：留出中文评测上按字符均衡臂不低于按 token 均衡臂，且英文侧下降 ≤1 个绝对点）。

5Are Dense Rewards Worth Their Tokens in GRPO?

中文一句话
给「稠密过程奖励」算了一笔算力账：提出等算力协议（按生成 token 与训练 GPU 小时对齐预算）+ 预注册实验，指出逐步蒙特卡洛奖励的续写本身就占 91% 的生成 token。在 Qwen2.5-1.5B 上，该奖励「每次更新」看着领先 GRPO，但等 token 结束时低 14.3 个百分点、等训练时间低 7.8 个百分点；四个稠密奖励变体在同等训练时间下均未超过 GRPO。反向发现：按「预测成功率最接近 1/2」挑 prompt 在等算力下提升 1.7（Qwen3-0.6B）/ 0.8（Qwen2.5-1.5B）个百分点。据摘要：1,668 次运行、6 个模型。

Are Dense Rewards Worth Their Tokens in GRPO?

推荐理由（借鉴 · 直接对口 zhulong 的 RL 消融口径与 data 的难度采样）
  1. 「稠密奖励免费」是错觉：过程奖励要为中间步骤采样续写，而续写吃掉 91% 的生成 token ⇒ 只看「每次更新的分数」会系统性高估它。这个偏差量级（14.3pp / 7.8pp）大到足以改变技术选型，我们的 RL 消融如果按 update 对齐，很可能正在犯同一个错。
  2. 方法可原样借用：matched-compute protocol（生成 token + GPU 小时双口径）+ 预注册 + 控制副作用。这正好是我们 zhulong 消融表缺的「算力口径」一列，也与我们已写的「等计算预算对比」原则一致。
  3. 一个更便宜的正向发现：不改奖励，只改挑哪些 prompt（预测成功率≈1/2），在等算力下也能涨 1.7 / 0.8 个点 ⇒ 数据侧的「难度采样」是比「设计更复杂的奖励」更省的杠杆，可直接进 data 线的课程学习方案。
  4. 边界与风险：① 模型规模 0.6B–1.5B、以数学/推理类 RLVR 为主，EDA 任务未验证；② 「梯度测试高估 1–2 个点」说明单 batch 诊断不可靠；③ 收益出现在训练早期，且 2× 学习率的 GRPO 只差 0.5 个点 ⇒ 别把增益全归给方法；④ 作者自报、本线未复现。
建议动作：zhulong 线把现有 RL 消融重跑为等 token 预算（固定 gen_tokens，报告 Δ 准确率与总生成 token）；判据：若某「稠密奖励」在等 token 下增益 <1 个绝对点，则从默认配方中移除，并把省下的生成预算转投「难度采样」臂。
