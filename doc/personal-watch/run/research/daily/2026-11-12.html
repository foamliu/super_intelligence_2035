1SLIC: Reinforcement Fine-Tuning Small LMs for Multi-Turn Analog Circuit Optimization

中文一句话
把模拟集成电路设计当成多轮、依赖仿真器的工程任务：用强化微调训练 4B 本地模型做闭环电路优化（结构化电路表示 + 离散「相对更新」动作 + 按域/成功门控的多目标奖励 + 把每步仿真反馈用于策略与 rollout 的 RGRS），并开源 41 个放大器拓扑的基准（分布内 / 留出拓扑 / 跨工艺节点三种协议）。摘要称：仅用开源 65nm CMOS PTM 训练，SLIC-Random 在 8 轮内分布内四指标 Pass@1 87.1%（比 763B 的 DeepSeek-V4.1-Flash Think 高 48.5 个百分点）；SLIC-Softmax 留出拓扑 72.6%；跨 5 个未见工艺节点零微调迁移；商用 TSMC 65nm PDK 留出拓扑 49.9%；测试时仿真交互增到 32 轮可到 83.2%。

推荐理由（借鉴 · 与 designflow / zhulong / pretrain 的「小模型 + 多轮工具」直接对口）
  1. 它是「小模型 + 仿真器闭环」的完整样板，不是又一个 benchmark：动作 = 离散化的相对更新（不是自由文本），奖励 = 按域与成功门控的多目标，再叠加 RGRS 把逐步仿真反馈同时用于策略学习与在线 rollout 构造。我们的 ZhuLong 也是「模型出动作 → 工具跑 → 看指标」的闭环，差别只在工具（波形/版图仿真 vs 电路仿真）。可直接对照的三处：动作怎么离散、奖励怎么门控、失败 rollout 怎么复用。
  2. 「4B 打过 763B」是任务结构带来的，不是模型更强：+48.5pp 的对照是通用大模型直接做同一任务，而非同数据同预算的 763B 微调 ⇒ 🚫 不能读成「小模型普遍更强」。真正可迁移的是：把领域动作空间与奖励写死，比把通用模型堆大更省。这正好支持我们 pretrain/SLM 侧的「域内 2B + 结构化接口」路线。
  3. 三种泛化协议可原样借：分布内（同拓扑族）/ 留出拓扑（未见结构）/ 跨工艺节点（未见 PDK）。对应 designflow 的 L1–L5 保真度：每一级都要单独报，并且报告「测试时预算」（8 轮 vs 32 轮），否则「多给几轮就能刷上去」会被误读成模型能力。
  4. 边界：① 模拟电路是连续参数 + 小动作空间 + 可仿真，EDA 数字流程是离散、长流程、工具昂贵，🚫 不可直接搬；② 87.1% / 72.6% / 49.9% / 83.2% 均为作者自报，基准自建、任务自选；③ 商用 PDK 上的 49.9% 是「本地推理、不传数据」的部署论证，不等于生产可用；④ 论文摘要未给训练成本与失败案例。
建议动作：designflow 线按它的三协议改写评测表（新增「留出拓扑/留出节点」两列 + test_time_budget 列）；zhulong 线评估「相对更新动作 + 门控多目标奖励」是否可映射到工具调用序列。

2Plumbline: When the Loss Lies, Validating LLM Training Correctly

中文一句话
一个训练正确性验证系统（摘要自述在 Amazon 生产使用）：沿训练生命周期逐段检查——从训练数据到服务模型、再到每个模型新增的层与整轮 run；诊断复用这些检查回溯根因。支持两个 agentic 用例：新模型 Day-0 onboarding（团队依赖前先验证训练）与训练故障根因定位。摘要称：跨 3 个框架、5 个模型发现 61 个问题，其中 32 个是静默故障；42 个已修复或上报上游、8 个由作者首次提出；61 个归纳为 7 类失败模式。

Plumbline: When the Loss Lies, Validating LLM Training Correctly

Ruochen Wen · Hongyang Wang · Siwei Li · et al（arXiv 作者列表；摘要自述「used in production at Amazon」，作者所属机构未逐人核验）

链接

推荐理由（借鉴 · 与 pretrain 的「loss 不可信」/ harness 的「判分可信」直接对口）
  1. 「loss 下降 ≠ 训练正确」是可复用的故障模型：论文的立论是有些故障很响（崩）、有些很静（只在最终评测掉分），我们的训练看板上「loss 正常」并不能排除数据管线错位、层实现错、框架默认值变化。它把检查拆到数据 / 单层 / 整轮 / 服务四段，正好对应我们 pretrain 现有脚本的四个可插入点。
  2. 61 / 32 / 42 / 8 这组数字的价值在「静默占一半」：32/61 ≈ 52% 的问题不会自己报错 ⇒ 只靠「跑通 + loss 正常」验收一定漏。可迁移动作是给每类故障写一个最小可复现探针（如单 batch 过拟合、标签打乱后 loss 应≈ln(V)、固定种子重放哈希一致），而不是买一个系统。
  3. 7 类失败模式可直接当检查表：摘要只给数量、未在摘要列出七类明细 ⇒ 必须读正文表格才能抄；在读到之前，我们只把它当「需要系统化检查」的证据，不编造类别名。
  4. 边界：① 生产环境是 Amazon 内部栈，我们的框架/硬件不同；② 61 个问题是**作者在 3 框架 5 模型上的发现**，不是普遍故障率；③ 摘要未给误报率与检查开销；④ 作者自报，本线未复现。
建议动作：pretrain 线在下一轮训练前加 3 个 Day-0 探针（① 单 batch 过拟合到 loss<0.05；② 标签打乱后 loss≈ln(V)±5%；③ 固定种子两次前向/反向的梯度哈希一致），任一失败即停训并记入 run log。

3Do They Do as They Are Told? Investigating Coding Agents' Adherence to Explicit Instructions in Context Files

中文一句话
检验 agent context files（ACF，如 AGENTS.md）的核心假设：写进去的指令是否真的被执行。方法：取真实 ACF 快照及其关联的 agent 生成 commit，把显式可执行指令操作化成可运行测量脚本，再逐条评估合规。摘要称：多数可观察指令能被操作化；agent 多数情况下会遵循，但遵循度呈尖锐两极——一部分始终被遵守、一部分从未被遵守，且不同指令类别与不同 coding agent 之间存在差异。

https://arxiv.org/abs/2611.13709（PDF 见附录 C）
推荐理由（借鉴 · 与 harness 的「任务书是否被执行」直接对口）
  1. 我们的 6 线任务书就是 ACF，而且从未验证过执行率：research / pretrain / vision / harness / data / zhulong / designflow 各自的任务书都写着「每轮必做」「🚫 不许」等显式指令，但没有任何机制检查 agent 是否真的执行。本文给出的方法（把指令改写成可执行检查脚本，再在 agent 产出上逐条判定）可以直接复用。
  2. 「两极分化」比「平均遵循率」更有用：如果某些指令从未被遵守，继续加更多同类指令只会让任务书更长、token 更贵。可迁移动作是定期审计：把「从未遵守」的指令挑出来，要么改写成可验证的形式，要么删掉。
  3. 摘要没给具体合规率（只给定性结论）⇒ 日报不编数字；要落地必须读正文的指令分类表与脚本。我们本轮只引用其方法与结论方向。
  4. 边界：① 研究对象是真实开源项目的 AGENTS.md 与 commit，不是我们的任务书；② 「合规」由脚本代理判定，存在测量误差；③ 未覆盖多 agent 协作与长流程任务；④ 作者自报，本线未复现。
建议动作：harness 线做一次 任务书合规审计：从 6 份任务书各抽 10 条显式指令（共 60 条），逐条写成可判定的检查（文件是否存在 / 字段是否齐全 / 命令是否执行），在下一轮产出上跑一遍；输出「始终遵守 / 从未遵守 / 无法判定」三列，从未遵守的进入改写清单。
