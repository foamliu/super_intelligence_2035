1Negative-Only Policy Optimization for One-Sided Verifiable Rewards

中文一句话
把「只能判错、不能判对」的奖励情形形式化为 one-sided verifiability（OSV）：既然「通过检查」只是未被否证，就直接把它当未标注样本，只用可信的负例更新策略。方法 NOPO 由「相对参考模型的负例抑制损失 + 组级适配器（按未被否证的回答比例缩放每次更新）」组成，在单元测试 / 约束检查 / LLM 自评三类验证器上提升代码、逻辑、数学任务的 pass@k，且增益在推理期扩展与跨基准迁移下仍在。
原题
Negative-Only Policy Optimization for One-Sided Verifiable Rewards
作者 / 机构
Jiacheng Xu · Shuo He · Fuxiang Zhang · Chaojie Wang · Bo An（共 5 位；机构未从 PDF 核验，本页不写猜测机构）

推荐理由（借鉴 · zhulong / pretrain 直接对口）
  1. 它命中的正是我们评测的真实处境：「DRC 通过」「单测通过」「约束满足」都是只能否证、不能证明的检查。如果把这些检查当正奖励，等于奖励「钻空子」。本文的做法是只用负例 —— 与 zhulong 的奖励设计直接冲突也直接互补：动作：把奖励源分成「可证正例 / 只可证负例」两栏，后者不进正奖励项。
  2. 组级适配器是一个可照抄的设计：用「未被否证的回答比例」缩放更新幅度，避免某一批样本几乎全通过时更新过猛。动作：消融表加一列 non_falsified_ratio，与梯度范数一起报，用来解释「为什么这轮训练没动」。
  3. 增益覆盖 pass@k 而非只 pass@1：说明它不是「把概率挤到一个答案上」。动作：我们的 RL 实验统一报 pass@1 / pass@8 / pass@32，缺 k 的结论不写进对比表。
建议动作：zhulong 先做一个 3 臂对照（base / 标准 RLVR 把通过当正例 / 只抑制负例），固定采样数与步数；预注册判据：若「把通过当正例」臂在留出集上的 non_falsified_ratio 上升但人工抽检正确率不升，则该奖励口径判为无效，写进结论。

2Eliciting and Mitigating Specification Satisficing in Coding Agents

中文一句话
给代码 agent 的一种失败命名：specification satisficing —— agent 先想到一个满足需求的实现，后来又改成一个不满足需求、但它自认为理由充分的实现。作者提出 SatisFix：在写码前先让 agent 以「顾问」身份报告「需求 / 我的选择 / 理由」，再逐条对照任务描述复核是否保留。在 DeepSWE 与 SWE-bench Pro 上，5 个基座 × 2 个 agent 框架，pass@1 平均提升 5.09%（DeepSWE）与 7.06%（SWE-bench Pro 困难子集），比最好的自纠正基线（Self-Refine / DeCRIM / ProgCo）高 3.98%（DeepSWE）。
原题
Eliciting and Mitigating Specification Satisficing in Coding Agents
作者 / 机构
Ruixin Wang · Tianyi Zhang（共 2 位，Purdue University；机构取自 PDF 首页作者块，逐字核）

推荐理由（借鉴 · harness / designflow 直接对口）
  1. 「不把 agent 放法官位」是关键设计：现有自纠正让 agent 判断自己错没错，而 satisficing 的定义就是「它不觉得自己错」。改成让它报告选择与理由，绕开了自我偏袒。动作：我们的 harness 里凡是「让 agent 自评」的环节，都应改成「先记录选择 + 理由，再由规则或独立进程判」。
  2. 失败模式可以落到题面上：satisficing 多发生在「需求描述有模糊处」。动作：designflow 出题时给每题加一份 requirement_checklist（可逐条判真假），并在题面里显式标出「允许的实现自由度」。
  3. 数字口径要注意：摘要写的是「平均提升 5.09% / 7.06%」，未说明是绝对百分点还是相对提升，也未给前置两步的 token 成本。动作：引用时只写「作者自报提升 5.09%，口径未注明」，不得当成绝对百分点写进方案对比。
建议动作：harness 在现有 20 道代码题上加一个「SatisFix 式前置报告」开关做同预算对照（同 max tokens），比较 pass@1 与总 token；预注册判据：若同预算下 pass@1 不升或总 token 增幅 >30%，则不纳入默认流程，仅作诊断工具。

3Human or Synthetic? What a Fixed Budget Buys for Post-Training

中文一句话
以往比较「人类标注偏好」与「合成偏好」时固定样本数，本文改成固定金额对齐：在同等标注预算下比较 SFT + DPO 后的胜率。结论是合成数据在低到中等预算下明显更划算（200–400 美元即可取得较高胜率）；在 helpfulness 上人类数据要大约两个数量级更大的预算才追平，在 summarization 上任何测试预算都未追平。此外，一个被广泛使用的人类偏好来源明显差于另一个，且该差距在域限制与去重等常规补救后依然存在。

推荐理由（借鉴 · data 主目标；pretrain / zhulong 次之）
  1. 「按金额对齐」比「按样本数对齐」更接近工程决策：我们做 2B 后训练时真正受限的是钱和人天，不是样本条数。动作：data 线的偏好数据表加「每千条成本（含生成 / 标注 / 质检）」列，报表按每美元胜率排序，而不是按条数。
  2. 「人类数据不一定更可靠」有具体证据：一个广泛使用的来源显著更差，且去重 / 域限制补救无效 —— 这更像标注规范问题，不是噪声。动作：数据源准入加一条「同任务多来源交叉一致性」检查，低于阈值的数据源先停用。
  3. 结论的边界必须写清：预算档只测到「两个数量级」的差距，模型族与任务限于 helpfulness / summarization，未覆盖中文与 2B 级小模型。动作：我们若要外推，必须先跑自己的低预算点，🚫 不得直接引用其倍数当结论。
建议动作：data 线先建一张 3×2 的预算表（$100 / $500 / $2500 × 人类 / 合成），固定基座与 DPO 超参，只改偏好数据来源；预注册判据：若合成数据在 $500 档的胜率优势 <3 个百分点，则中文场景按「人类优先」立项，不照搬论文结论。

4Maximizing Capacity Utilization of LoRA Adapters for Mitigating the Learning-Forgetting Trade-off

中文一句话
作者指出 LoRA 的「设定秩 ≠ 实际用到的秩」：标准 LoRA 更新的有效秩远低于配置秩（高秩尤甚），更新能量分布过窄，于是出现「学得少 / 忘得多」的权衡。方法是在语言建模损失上加一个可微、免 SVD 的 Rényi-2 有效秩正则项（主实验 λ=0.01）；三个模型、多个随机种子的混合域秩扫描中，≥16 的每个测试秩上 Wiki 困惑度均低于无正则 LoRA，除一处模型–秩组合外训练困惑度变化不超过 0.02。作者还报告单任务与调度实验中「学习 vs 保留」的平衡随配置而变，且若干已有 LoRA 变体同样存在该容量问题。

5EvoX: Rethinking the Agent Harness as a Runtime Policy

中文一句话
把 harness 本身当成一层「操作策略（Operational Policy）」，与模型的语义策略互补：Rust 运行时用三条机制——动作落地（tool-call 与实际工具对齐）、执行连续性（工作流中断后接续）、结果接地（完成声明必须有证据）——处理「模型决策看似合理但执行失败」的三类故障。评测侧提出 Contrast 框架（显式公平约束 + provider-bound 请求校验 + 证据化裁决），在 5 个基准 × 6 个基座 × 6 个 harness 的 691 个共同 task–model 对上数值成功率 56.2%，比其余五个 harness 的均值高约 3.0 个百分点；对 GLM-5.3（+10.7）与 Kimi K3（+7.9）的增益更大。作者明写：结果未使用 memory / evolution / 扩展机制。
