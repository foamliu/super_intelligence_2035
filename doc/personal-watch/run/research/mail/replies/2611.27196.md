- 我们问的（原文摘要）：① MV（mandatory validation）的「改动—约束—测试」对应是人工固定清单还是 agent 从 diff 自推、误判率多高；② OE 单独 6/15、加 MV 13/15，几何均值 1.11× → 1.53×，MV 的收益主要是筛错还是把搜索导回正确方向、trace 上被拦最多的是哪类失败；③ 加速比用的 complete-solve runtime 是否含编译与校验、单卡占比多少。
- 对方答的（**中文原文照抄**）：

  > “改动—约束—测试”的对应与误判： 系统预先冻结的是各项目的验收契约（Table I）、由契约推导的验证策略，以及跨项目的通用验证模板（例如缓存复用需“填充缓存 → 修改单一依赖 → 对比重算”）；具体哪条调用链受影响、怎么写测试驱动和构造输入，由 agent 结合当前 diff 自行推导。控制器只做确定性规则检查（确认测试在当前源码/构建上真实执行通过且满足覆盖策略），不判断测试用例本身的合法性。我们没有对逐个 diff 标注真值，因此无误判率统计；论文 §VI-C 记录了一个典型漏检：IG 的一次 batching 测试构造了越界输入，但因候选和参考吃了同一份非法输入而通过，直到事后审查才发现。
  >
  > MV 的收益来源与拦截情况： 先微调一个数字：DeepSeek 的 1.11× (7/15) 是 Generic，单加 OE 是 1.36× (6/15)，加 MV 后是 1.53× (13/15)。终验筛错对 OE 和 MV 一样，MV 的核心增量是把失败信号前移到开发环内，让 agent 有机会修代码、修测试或回退到已验证版本。实践里它纠正的既有求解器 bug，也有 agent 自己写错的测试驱动（如论文 §VI-C 中 IG 驱动漏了查找表初始化，agent 在 B0 上复现后修复重跑）。我们未做“只拦截不修复”的对照，也未跨项目混排单一拦截榜（开发期单次报错与终验失格口径不同）；终验层面，OE 失败主要集中在缓存复用、GPU 写竞争、越界及合法性/QoR 违规。
  >
  > 计时口径与单卡开销占比： complete-solve runtime 不含编译和校验，仅计冻结求解边界内的端到端运行时间，编译与校验单算开发/评测成本。单卡占比随项目和模式差异较大：以 IG 上一次 DeepSeek MV 搜索为例，开发阶段程序编译约占总墙钟 8%、外部官方 checker 约占 22%（不含局部自测）；独立终验阶段复用产物，外部 checker 约占 20%，其余主要消耗在多次配对求解计时。

- **可执行结论**：① 契约 / 验证策略 / 通用模板是**预先冻结**的，**受影响调用链与测试驱动由 agent 从 diff 自推**；控制器只做**确定性规则检查**（真实执行通过 + 覆盖策略），**不判测试合法性**，且**未统计误判率**；已知漏检模式 = **候选与参考吃同一份非法输入**（IG batching 越界仍通过）。② 数字须更正：`1.11× (7/15)` = Generic，`+OE 1.36× (6/15)`，`+MV 1.53× (13/15)`；MV 的增量是**把失败信号前移到开发环**（可修代码/修测试/回退），不是终验筛错率更高；**未做只拦截不修复对照**。③ complete-solve runtime **不含编译与校验**；IG 开发阶段编译 ≈8% 墙钟、外部 checker ≈22%，终验外部 checker ≈20%。
- **归属线**：harness（主，判分 / 校验环）· designflow（次，造题与验收契约）
- **建议采纳点**：
  1. `harness`：我们的判分器必须加一条**「候选与参考共用非法输入」陷阱**（对同一非法输入两路都通过 ⇒ 判为无效测试），这是本文已承认的漏检点。
  2. 验收口径分三档记账：**开发期编译 / 外部 checker / 配对求解**，不要把 compile+checker 摊进 runtime；对外报加速比时写明是否含编译与校验。
  3. MVP 的「强制校验」若移植到我们的流水线，控制器只做确定性检查，**不要**声称能判测试合法性；误判率需我们自己标注真值后测（作者未测）。
  4. 引用数字一律用更正后的 `1.11× / 1.36× / 1.53×` 与对应 `7/15 / 6/15 / 13/15`，并注明是 DeepSeek 的 Generic/OE/MV 三档。
