Abstract—Memory decides which LLMs an edge device runs,
and how fast: capacity on a 4 GB Jetson Nano, bandwidth on
an 8 GB Jetson Orin Nano Super. Deployed formats (GPTQ,
AWQ, llama.cpp’s K- and I-quants) spend equal bits on every
integer code of a matrix, although the codes are far from uniform.
LazyWeights keeps these formats but tunes GPTQ so the codes
compress, Huffman-codes them losslessly in interleaved lanes, and
decodes them on demand in a small unit between DRAM and L2,
so GPU kernels run unchanged and DRAM moves only coded
bytes. At 1% and 3.5% perplexity budgets, coded Phi-3-mini,
Mistral-7B and SmolLM-1.7B are 5.7–31.4% smaller than the
best llama.cpp format. A bit-exact 0.21 mm2 ASIC decoder
unit (1 GHz, 7 nm) cuts Orin latency and energy per token
by up to 36% and 38% (54% and 44% with prompt-lookup
speculation). On the Nano, LazyWeights needs 58–64% less
time and 53–57% less energy per token than CPU llama.cpp,
and runs a streamed Mistral-7B 6.6× faster at 3.89 bits per
weight. A Huffman decoder beats an rANS decoder in rate and
area at equal throughput; the ASIC decoder unit runs bit-exact
on a Zynq UltraScale+ FPGA (AMD ZCU102).1

I. Introduction
Generating a token reads every weight of a large language
model (LLM) once, so on an edge device the weight footprint
decides whether a model fits and how fast it runs: a 7B model
needs 14 GB in 16-bit floats, more than most edge modules
have, and even at 4 bits each token moves gigabytes through a
phone-class memory system. llama.cpp [1] has made posttraining quantization the default, with GGUF files offering
fixed-width integer formats with per-block scales from 8 down
to about 3 bits per weight.
These formats and the quantizers that target them
(GPTQ [2], AWQ [3], the llama.cpp K- and I-quants) share
an unstated commitment: every code of a matrix costs the
same number of bits. This wastes bits twice. Weights are
bell-shaped, so a 4-bit alphabet’s inner codes dominate and
its entropy sits well below 4 bits [4], [5]; and many code
assignments reach the same quality, so a quantizer that knows
its codes will be entropy-coded can pick ones that compress.
Lossless weight coding, from Deep Compression [6] to
recent work on 16-bit LLM weights [7]–[10] or a quantizer’s
integers [11], [12], takes the quantizer as given and mostly
decodes in software. A coded 4-bit model is worth having
only if it beats the next-smaller fixed-width format at equal
quality, a comparison rarely made, and only if its codes can
be expanded at DRAM rate every token: software decoders
fall 15–20× short of that on an Orin Nano Super, making a
token 2.5–3.2× slower than the same codes at fixed width.
LazyWeights removes the commitment end to end
(Fig. 1). It shapes the codes inside the deployed format, codes
them with a Huffman layout built for parallel decoding, and
decodes them in a small unit between DRAM and L2, where
bytes are counted. The GPU still reads fixed-width codes, so its
kernels are untouched, the decoded weights are bit-identical to
a valid GGUF file, and quality is the quantizer’s alone. On the
bandwidth-bound Orin, fewer bytes then mean faster, cheaper
tokens; on the instruction- and capacity-bound Nano, the unit

in and which are our baseline. AQLM [13], QuIP# [14] and
QTIP [15] reach lower rates at equal quality with vector and
trellis codebooks but need their own formats and kernels; we
keep the deployed scalar format and code its integers.

Where we sit. LazyWeights is, to our knowledge, the
first design to code the deployed integer format rather than
merely store it: it shapes the codes inside llama.cpp’s
formats, keeps files valid GGUF, decodes in hardware where
DRAM traffic is counted, and compares against the best fixedwidth format at equal perplexity, the comparison that decides
whether coding is worth its decoder. Any quantizer that emits
integer codes in a fixed format can feed the bundle and the
unit.

C. A lossless Huffman bundle built for parallel decoding
Huffman decoding is sequential: a code’s start is known only
once the previous code is decoded. The bundle (Fig. 3a) breaks
this. Each matrix has one canonical code, length-limited to 11
bits so an 11-bit window always resolves a code. Each 64×256
tile is 32 lane streams of two rows, decoded in parallel without
waiting for each other. The lanes’ 32-bit words are interleaved,
so the words needed next are adjacent and a GPU warp or the
unit’s read port fetches them in wide, aligned reads; per-tile
lane offsets let any tile start independently. In 4-bit formats
two codes form one 8-bit pair symbol, two weights per decode
step.

E. Runtime

Decoding in the GPU kernels spends instructions on bit
manipulation, costing more time than the bytes save; expanding weights back into DRAM saves storage, not bandwidth.
LazyWeights decodes between the memory controller and
L2 (Fig. 3b): DRAM holds and moves only coded weights,
L2 receives fixed-width codes, and the kernel is unchanged,
so the first term of (1) follows the coded size.
Lane. A request side feeds the lane’s stream through a 4entry prefetch FIFO into a 64-bit bit buffer. The next 11 bits are
compared against 11 per-length limits at once; the thermometer
result gives the length, the symbol is the code plus a per-length
offset, and the buffer shifts. A lane emits one pair symbol (two
weights) per cycle; the per-matrix limit and offset tables are
broadcast by the engine.
Engine. 32 lanes share an 8-word read port through a
masked round-robin arbiter, decoding 31.9 symbols per cycle
(0.2% stall), i.e. 60–64 weights per cycle for pair-coded

Nano kernels. The instruction-bound Nano needs few instructions per weight. A 32-bit fetch yields four (5/6-bit) or
eight (4-bit) fixed-width codes; Q5 K/Q6 K codes are rebuilt
from their nibble and high-bit planes by byte permutes, one

by one subtraction) and table lookup (the 16 IQ4 XS grid
values, biased to unsigned bytes); the multiply-add order is
unchanged. The ordered reduction replaces Maxwell’s slow
global atomics.

VI. Results
A. Memory at equal quality
Every coded model is 5.7–31.4% smaller than the best
llama.cpp format within its budget, most for Mistral-7B
≤1% (Table III, Fig. 4). Huffman coding alone gives 6.2–
20.7% (coded vs twin); the quantizer gives the rest, letting a
coded file in a wider format undercut a narrower llama.cpp
format at equal quality. HellaSwag, ARC-easy and PIQA are
at most 1.5 points below the baseline, GSM8K at most 3.2
(Mistral ≤3.5%).
B. Latency and energy on the Orin Nano Super
With the unit, every greedy point beats the budget baseline
by 10–36% in time (up to 44% bandwidth-bound) and 9–38%
in energy (Table III); the decoder costs 3–13 mJ per token
against 5–61 mJ of DRAM energy saved, and with always-on
engines at 2× power energy still drops 6–36% greedy and 17–
42% with speculation. Without the unit, coding would slow the
Orin down (§I, Fig. 5b).
Speculation composes with the unit: it cuts passes per
token, the unit cuts bytes per pass. Against llama.cpp
with speculation, every point is 29–54% faster (up to 57%
bandwidth-bound) at 21–44% less energy. One change at a
time (Fig. 5a), speculation is the largest step on the Orin (1.3–
2.0×), the format gives 1.3–1.4× where it changes the file, and
the drafter is within 5%: ours accepts more tokens per pass
(1.96 vs 1.63 on Mistral), but larger passes cost more.

C. The Jetson Nano
For resident models (Table IV), LazyWeights with the
unit takes 58–64% less time and 53–57% less energy per
token than llama.cpp on the CPU, greedy, and 70–76%
less time and 69–76% less energy with speculation in both.
Most of this comes from the GPU kernels (Fig. 5a, bottom),
as Table I predicts, but the unit matters: software decoding
is 2.2–3.2× slower than the twin and beats the CPU only
on Phi-3 and SmolLM ≤3.5% (by 9–20%), not on SmolLM
≤1%, whose 5/6-bit codes decode singly. With the Nano’s
low DRAM energy per byte, energy with the unit is within
±0.03 J of the measured twin energy. Speculation helps our

GPU runtime (SmolLM ≤3.5% twin −25%; Phi-3 only −7 to
−9%, as an 8-token pass costs 3.6× a 1-token pass) and hurts
llama.cpp on the instruction-bound CPU by 28–32%.
Mistral-7B, streamed. Here the coded size decides: at
≤1%, LazyWeights is 6.6× faster than llama.cpp at
4.5× less energy, even decoding in software. At ≤3.5%,
llama.cpp wins greedy time narrowly at more energy and LazyWeights wins with speculation, because
llama.cpp’s memory-mapped IQ3 M file (3.28 GB) stays
in the reclaimable page cache, which does not count against
our floor. A slightly larger file gets almost no hits, since
every token scans the weights in the same order: our IQ4 XS
GGUF (3.91 GB) takes 15.1 s. Our bundle (3.18 GB) is smaller
still, but the cache cannot hold its streamed matrices beside
our pinned resident weights and the kernel’s 464 MB CMA
reservation, hence O DIRECT. A pass costs about 1.0 s of
compute plus the streamed bytes, and about the same for 1 or
8 tokens, so accepted tokens per pass set speculation’s gain;
a USB 3 stick (317 MB/s) instead of the SD card (70 MB/s)
cuts our software-decoding token time 2.1–2.7×.
D. Decoder cost, and Huffman versus rANS
A small unit clears the software wall (Fig. 5b; Table V).
Huffman outperforms rANS on both axes. Rate: rANS
is never smaller (0.0 to +1.0% more bits): Huffman is already
within 1.2–2.1% of entropy, and rANS pays 32 bits of state
plus padding per lane stream. Hardware: at equal throughput
(2 G weights/s), rANS needs 4.0× the area with pair symbols
(270 MHz) or 1.15× with single codes (645 MHz), as its onecycle recurrence holds a symbol search, a table select and
a 13×20-bit multiply against Huffman’s compare and shift.

E. FPGA prototype
On the ZCU102, four engines close timing at 112.5 MHz
(WNS +0.06 ns; the decode-to-arbiter loop caps the design
near 115 MHz) using 183.0k LUTs (67%), 37.2k flip-flops,
464 BRAM36 (51%, mostly payload copies) and no DSPs: 46k
LUTs and 116 BRAM36 per engine. All 29 matrices (2,723
chunks, 484M weights) decode bit-exact, with cycle, stall and
word counts equal to the C model on every chunk. Each engine
sustains 31.8 weights per cycle, 14.3 G weights/s for four; the
fabric (VCCINT) draws 0.88 W idle plus 3.7 W at full rate,
0.26 nJ per weight.
VII. Ablations
Quantizer (Table VI). Shared sub-block steps carry most of
the saving: with γ = 0 (llama.cpp’s fit), ∆PPL is lower but
every point costs 9–12% more bits. GPTQ feedback rescues
the coarse points, which reach up to +12.1% with RTN at the
same bits, but not the fine ones, where RTN is better. The step
scale is non-monotone in quality (Mistral ×1.25 +2.57%, ×1.5
+1.46%, ×1.75 +15.5%), hence the per-model search. λ > 0

saves at most 1.2% of the bits and usually raises perplexity;
int8 vs fp32 activations move perplexity by −0.07 to +0.18%.
Decoder. Comparator vs table lookup: Fig. 5b. An 8-word
read port with cross-stream prefetch reaches 31.9 symbols per
cycle; pair symbols cost −0.2 to +0.8% in size but double
an engine’s rate; 99% of the rate needs latency/4 FIFO words
per lane (SRAM: +0.014 mm2 per engine); wider engines (64
lanes: arbiter 6.4×, misses 1 GHz; Table V) only rescale the
engine count.
Run-to-run variance. Five more repeats of every measured
Orin row of Table III, clocks pinned, vary by at most 0.6% in
time and energy per token (median 0.1%), and every ∆t and
∆E stays within 1.7 points of the table.
VIII. Limitations and Conclusion
The unit’s latency and energy are projections from measured
device numbers and pre-layout synthesis, not a fabricated
SoC; the FPGA shows bit- and cycle-exact decoding, but at
FPGA clocks, not 1 GHz. For streamed Mistral-7B the twin
is no proxy for the unit: it streams the fixed-width bytes
(1.05 GB per token at a 2560 MB budget vs 0.68/0.26 GB
coded at ≤1%/≤3.5%), leaves less than our memory floor free,
and at a 2048 MB budget from the SD card was 1.2–1.8×
slower than software decoding. We therefore do not report
the unit’s streaming time; reading its coded bytes alone takes
2.2/0.8 s per token from USB. We did not evaluate Llama-3
or Qwen3, which quantize worse [23], or long contexts, where
the uncoded fp16 KV cache dilutes the saving (Mistral-7B at
4K tokens: 0.54 GB per pass vs 3.5 GB of weights).
The fixed width of edge LLM formats is a commitment,
not a necessity: the codes are far from uniform, the quantizer can make them less so at no quality cost, and an
entropy coder removes the difference if the decoder sits
where bytes are counted. Shaped and Huffman-coded, models
in llama.cpp’s formats are 5.7–31.4% smaller at equal
perplexity; a 0.2 mm2 unit between DRAM and L2 turns this
into faster, cheaper tokens on a bandwidth-bound Orin Nano
Super, with or without speculation, and lets a capacity-bound
Nano run a 7B model that otherwise does not fit. Coding the
KV cache, newer model families, and a layout next to a real
memory controller are independent next steps.
