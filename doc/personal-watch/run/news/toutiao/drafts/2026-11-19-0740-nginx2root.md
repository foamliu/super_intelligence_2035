先把结论摆出来：这次被公开的不是一个漏洞，而是一条链。
11 月 18 日，安全研究团队 Xint Security Research 披露了一条叫 NGINX2Root 的攻击链，里面包含 5 个 Nginx 远程代码执行漏洞，外加 1 个 Linux 内核 SCTP 子系统的权限提升漏洞。
最关键的一句是「无需身份认证」。攻击者在特定配置下不需要账号、不需要口令，就能让 Nginx 执行任意命令。
这 5 个漏洞分散在不同模块：HTTP/2、HTTP/3、反向代理和邮件代理。不是每个都要凑齐，按配置不同，能利用的入口也不同。
影响面最广的是 CVE-2026-123007。问题出在 HTTP/2 的流量控制里，一个整数溢出会导致堆内存越界写入。只要监听端口开了 HTTP/2，就可能落在影响范围里。
另外四个编号分别是 CVE-2026-123634、CVE-2026-123633、CVE-2026-121810 和 CVE-2026-113425，分别对应特定的反向代理配置、HTTP/2 上游连接、HTTP/3 上游请求以及邮件代理功能。利用成功后的权限，是处理请求的那个 Nginx Worker 进程的权限。
链子的后半段才是有意思的地方。研究人员先利用 Nginx 漏洞在容器内部以 Worker 权限执行命令，再用内核 SCTP 子系统里的另一处问题提权，最后突破容器隔离，拿到宿主机的 root。测试覆盖了 AWS、谷歌云和微软 Azure 的环境。
也就是说，一个跑在容器里的 Web 服务出问题，代价可能不是「这个容器被攻破」，而是「这台机器归别人了」。这层边界过去被当成安全垫，现在被证明只是一道有条件成立的墙。
时间线上有一点值得注意。欧盟网络安全机构 CERT-EU 同日发了公告，说 F5 已经公开处理这 5 个漏洞，但截至公告发布时，还没有发现它们在野外被实际利用的报告。
这既是个好消息，也是个提醒。好消息是还没有人拿它去打真实的站；提醒是「还没被利用」通常只说明现在还来得及。漏洞公开之后，从 PoC 到扫描器跟进，常常以天为单位。
修复路径写得很明确：升级到 Nginx 1.31.9。Sophos 的公告确认 Nginx Open Source 1.30.7 和 1.31.9 已包含修复，Nginx Plus 也发了对应版本。
暂时升不了级的管理员有一个折中办法：关掉 HTTP/2，可以缓解 CVE-2026-123007 和 CVE-2026-123633 这两个。但这一招盖不住剩下三个。
CERT-EU 的建议很朴素：优先检查那些直接对互联网开放的 Nginx 服务。翻成日常话说就是，先看门口那几台，别从最里面开始盘。
对普通用户来说，这类新闻通常看一眼就划过去，因为动不了手。但它其实说明了一件小事：你每天打开的那些页面，背后有一层叫反向代理的东西，它平时不出声，出事的时候动静最大。
对做运维的人来说，这一轮的现实问题是排期。一个要停机窗口的升级，排在周五下午还是下周一早上，风险完全不同。
还有个更隐蔽的问题：很多团队并不知道自己有多少台机器开着 HTTP/2。默认配置、镜像继承、历史遗留，都会让「清单」和「实际」对不上。漏洞公告最怕的就是这个。
所以真正该问的可能不是「我们有没有中招」，而是「我们能不能在两小时内说出哪些机器会中招」。
你所在的团队，遇到这种需要紧急升级的漏洞，通常是当天就动手，还是等下一个维护窗口？说说你们的排法。
