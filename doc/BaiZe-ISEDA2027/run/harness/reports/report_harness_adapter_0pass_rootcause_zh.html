3. 逐 harness 根因 + 证据

3.1 hermes —— 双根因，agent 两种意义上都没跑通

根因 A(36/50)：CLI 不在 PATH。 install() 用 pip install hermes-agent，约一半镜像 pip 不在 PATH，且 install从不校验 which hermes，静默装好 -> run 阶段 hermes command not found。

证据：jobs_hermes/.../dna-assembly__.../result.json -> agent_result.metadata
STDOUT: bash: line 20: hermes: command not found
EXIT_CODE: 127（全量扫描 exit 127 共 36 trial）

根因 B(51/50)：no_proxy 覆盖丢网关域名 -> HTTP 503。 hermes run() 给 _env_for_harness(extra=...) 显式塞 no_proxy: 127.0.0.1,localhost,10.239.*,172.19.*，而 _base._env_for_harness() 已正确把网关主机 agi-gateway.cxmt.com 加进 no_proxy——env.update(extra) 在后执行，把网关域名覆盖掉。于是对网关请求被走 MITM 代理 -> 503。

证据：jobs_hermes 全量扫描 stdout 首行签名
51 x API call failed after 3 retries: HTTP 503 -- ERROR: The requested URL could not be retrieve...（exit 0）
证据：源码对照 _base.py vs hermes.py(修复前)
_base._env_for_harness(): no_proxy_val = ...,{gateway_host}  # 含 agi-gateway.cxmt.com OK
hermes.run() extra:       no_proxy: 127.0.0.1,localhost,10.239.*,172.19.*   # 覆盖掉网关域名 FAIL

旁证：cline 走同一直连网关路线却 55% 通过——因 cline 用 _env_for_harness 默认 no_proxy(含网关域名)，没被 extra 覆盖。反向印证 503 是 no_proxy 覆盖所致，非网关不可用。

3.2 deepseek-harness —— SDK 装不上 + runner 吞异常

根因 A(36/50)：裸 pip 装不上 SDK。 install() 跑 pip install deepseek-harness-sdk，约 36 镜像 pip 不在 PATH(python3 在但 pip 不在)，且 install 不检查返回码，静默通过 -> run 阶段 import 失败 -> NonZeroAgentExitCodeError。

证据：jobs_deepseek-harness/.../path-tracing-reverse__jRF8V9v/trial.log
Running: pip install --break-system-packages deepseek-harness-sdk 2>&1 | tail -5
Trial failed: Command failed (exit 127): pip install ...
stdout: bash: line 1: pip: command not found

根因 B(52/50，最隐蔽)：runner 吞掉所有异常，静默空输出。 SDK 装上时 runner 的 harness.run() 可能因 dsh 运行时初始化失败/模型返回空拿到空 final_response，老 runner 只 print(... or "") -> 打印空串 -> exit 0 且无任何报错，verifier 自然 0 分。

证据：全量扫描 88 个 result.json stdout 首行签名
88 x <empty>；exit_code=0 共 52(跑完但啥也没产出)，exit_code=None 共 36(install/run 异常)。

R494 smoke 定性（2026-10-25 13:14）：根因 B 确切机理已确认 —— SDK 原生 dsh 运行时初始化失败，从未发起模型 API 调用。证据：① dsh proxy(9091) 请求日志在 smoke 时段(13:14+)无任何请求（仅 13:11 的手动 curl 测试）；② SDK 返回 RunResult(final_response='', finish_reason='error')，events 仅含 agent/inbox/spliced（指令已加载），无 model-call 事件；③ runner 修复后 stdout 打出 === DSH WARNING: empty final_response === + 完整 result repr。结论：deepseek-harness SDK 的原生 dsh 运行时在 TB 容器内无法初始化（疑似缺原生二进制/架构/权限/profile 配置），非适配器层可修。适配器修复（SystemExit 捕获 + diagnostic 打印）已生效，使错误从「静默空输出」变为「可见报错」，但 0 pass 根因仍在 SDK 内部。

旁证：手动 curl 测试 dsh proxy(9091) 可正常返回 kimi-k2.6-cloud 响应（200 OK），但模型将输出放在 reasoning_content 字段而非 content（content 为空串）——即便 SDK 发起调用，也可能因解析 content 为空而判错。双重故障：① SDK 不发请求 ② 即便发请求 content 也为空。

3.3 claude-code —— 模型在干活，但交付物落不了盘

根因 A(13/34 exit-0)：非 root 用户写不进 root 属主 /app/。 适配器为绕过 claude root 下禁用 --dangerously-skip-permissions 而以 agent 用户运行，却只 chown 了 task workdir(cwd)，没动 /app/。许多 TB 任务要求写到 /app/<file>，/app/ 仍 root 属主 -> agent EACCES -> 模型算对也交不出文件。

证据：jobs_claude-code/.../count-dataset-tokens__.../result.json -> metadata.stdout
The total number of DeepSeek tokens ... is: **79586**
However, I was unable to write this to /app/answer.txt because the directory
is owned by root and I do not have permission to write there (no sudo/su access).
-> 模型确实调通了(有推理有数值)，死在写文件这一步。同类 stdout：permission issue writing to /app；/app directory exists but is owned by root。

根因 B(18/34)：撞 max-turns=50。 Error: Reached max turns (50) -> exit 1 -> 无 patch -> 0 分。

证据：全量扫描 stdout 首行签名
18 x Error: Reached max turns (50)（exit 1）

claude-code 是七路里最慢的(~1.7 trial/h)，慢+撞轮数上限叠加 -> 34/87 且 0 pass。
