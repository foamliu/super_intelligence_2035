0. 概况与术语体系

OpenCode（opencode-ai，TypeScript + bun@1.3.14，Effect 效应系统 DI）是一个开源 AI 编码 agent。

它为自己的上下文模型建立了一套严谨、带「避讳词」的术语表（CONTEXT.md:7-52）——这本身就是一条「上下文生命周期」设计主张：区分「持久的历史」与「投影出来的运行时上下文」。核心术语：

术语（原文定义位置）含义
System Context（CONTEXT.md:7）呈现给模型的结构化上下文事实（初始指令 + 时序更新）。Avoid：System prompt
Session History（CONTEXT.md:11）「投影后的、按时间排序的对话」——在应用活动 compaction 与 Context Epoch 截断之后选出。
Context Source（CONTEXT.md:15）一个独立观察到的类型化值：稳定 key + JSON codec + 无错 loader + 纯 baseline/update renderer + 可选 removal renderer。
Context Epoch（CONTEXT.md:26）一段跨度：初始渲染的 System Context 保持为不可变 provider-cache 基线，结束于已完成 compaction / Session 移动 / 不兼容上下文切换。
Context Snapshot（CONTEXT.md:33）可覆盖的、对模型隐藏的 JSON 状态，用于把每个 Context Source 与「上次进入 provider turn 的值」做比较。
Provider Turn（CONTEXT.md:48）一次对 provider 的请求 + 该请求的投影响应。

这条术语表的关键洞察：Session History 是「投影」而非「原始存储」——与 cline 的「无损投影（原始消息从不被修改）」是同一哲学，但 opencode 用「Epoch + seq 截断」而非 cline 的「EditType/ContextUpdate map」来实现。

2. 线1 — 上下文注入与「投影」管线（Compaction 的上游）

① 它解决什么问题

把「发什么给模型」从「存了什么」里解耦：历史是追加式持久的，但每轮 provider turn 只发一个投影视图——这个投影同时叠加三件事：① compaction 之后的摘要、② Context Epoch 截断（只保留 compaction 之后的消息 + baseline 之后的 system 消息）、③ 指令文件注入（AGENTS.md/CLAUDE.md 向上遍历附加）。

② 怎么实现（原文）

投影的核心 SQL——packages/core/src/session/history.ts:30-52 messageRows() 决定哪些消息进入 Session History：

.where(and(
  eq(SessionMessageTable.session_id, sessionID),
  compaction
    ? or(
        gte(SessionMessageTable.seq, compaction.seq),                 // 压缩之后的消息全保留
        baselineSeq === undefined ? undefined
          : and(eq(SessionMessageTable.type, "system"), gt(SessionMessageTable.seq, baselineSeq)),
      )
    : undefined,                                                      // 压缩前 system 消息只留 baseline 之后
  baselineSeq === undefined ? undefined
    : or(ne(SessionMessageTable.type, "system"), gt(SessionMessageTable.seq, baselineSeq)),
)).orderBy(asc(SessionMessageTable.seq))

这是「无损投影」的 opencode 版：原始消息行从不被删除或改写，投影在读取时用 seq >= compaction.seq 与 seq > baselineSeq 两个阈值实时算出。压缩后的「摘要」是带 summary 字段的普通 assistant message，靠 seq 门槛自然成为投影「头部」。

指令文件注入——packages/opencode/src/session/instruction.ts:64-68 定义注入源，:193-218 向上遍历附加（每 message 只一次）：

③ 数据流图


原始持久历史（SessionMessageTable，全部消息行，含 compaction/summary 标记）
        │  读时投影（history.ts messageRows）
        ├── seq >= compaction.seq ─────────────▶ 压缩后的「尾」
        ├── (system 消息 且 seq > baselineSeq) ▶ Epoch 基线后的 system 事实
        └── 其余（压缩前旧对话）────────────────▶ 丢弃（不进投影）

        ＋ 已压缩 tool 输出（time.compacted）→ output/attachments 置空
                ▼
        buildPrompt → System Context + projected Session History → provider turn

④ 代价与边界

  • 代价：投影逻辑分散在 SQL 层（history.ts）、消息层（message-v2.ts）、prompt 层（prompt.ts）三处，读代码需跨层还原「一条消息最终长什么样」。CONTEXT.md 术语表的存在本身就是对「概念太多」的补救。
  • 边界：part.state.time.compacted 是不可逆标记删减——一旦 prune 抹掉 tool 输出，原始内容从常规投影失去，只能靠 PRUNE_PROTECTED_TOOLS=["skill"]（compaction.ts:31）保护少数工具。
  • 失败模式：指令 globUp 失败时 Effect.catch(() => Effect.succeed([] as string[]))（instruction.ts:84）——指令文件缺失会静默降级为无注入，模型可能少看到关键规则。

⑤ 我的判断

opencode 的「投影」比 cline 的「EditType/ContextUpdate map」更结构化：把「哪些内容进上下文」提炼成两个单调递增 seq 阈值（compaction.seq、baselineSeq），投影就是一条 SQL where，可复现、可审计、无重写。代价是灵活性：cline 的 map 能做任意粒度逐块编辑（剥离某段文件内容），opencode 的 seq 阈值只有「整段前后截断 + 逐 part compacted 标记」两档。这是「结构化简单性」换「编辑自由度」。

3. 线2 — Context Epoch / 检查点与回滚（Compaction 的可回退路径）

① 它解决什么问题

cline 的检查点是「非破坏性编辑 + 时间戳截断」（对话级回滚）。opencode 把它拆成两个正交机制：

  • Context Epoch（context 级）：记录 System Context 的「不可变 baseline」，compaction 完成后开启新 epoch，靠 baselineSeq 截断旧的 system 事实。
  • git-worktree Snapshot（workspace 级）：revert.ts 用 git 快照回滚文件改动，不是回滚对话。

两者都解决「压缩/操作之后还能精确回到之前状态」，但一个管「模型看到的上下文」，一个管「磁盘上的文件」。

② 怎么实现（原文）

Context Epoch 的表结构——packages/core/src/session/context-epoch.ts:18-21 与 :122-139（持久化 baseline + snapshot + baseline_seq）：

interface Prepared { readonly baseline: string; readonly baselineSeq: number }   // :18-21
const insert = Effect.fnUntraced(function* (db, sessionID, generation) {
  const baselineSeq = yield* EventV2.latestSequence(db, sessionID)
  yield* db.insert(SessionContextEpochTable).values({
    session_id, baseline: generation.baseline, snapshot: generation.snapshot, baseline_seq: baselineSeq,
  }).run()
  return baselineSeq
})

关键：compaction 结束一个 epoch——context-epoch.ts:59-70（compaction 的 seq 超过旧 baseline_seq 时，触发 SystemContext.replace 换新基线）：

const replacementSeq = compaction !== undefined && compaction.seq > stored.baseline_seq ? compaction.seq : undefined
const result = replacementSeq
  ? yield* SystemContext.replace(value, snapshot)   // compaction 后：整体替换
  : yield* SystemContext.reconcile(value, snapshot) // 正常：增量 reconcile
if (result._tag === "Unchanged" || result._tag === "ReplacementBlocked") {
  return { baseline: stored.baseline, baselineSeq: stored.baseline_seq }
}
if (result._tag === "ReplacementReady") {
  const baselineSeq = replacementSeq ?? (yield* EventV2.latestSequence(db, sessionID))
  yield* replace(db, sessionID, baselineSeq, result.generation)
  return { baseline: result.generation.baseline, baselineSeq }
}

「compaction 找最新 compaction 消息 seq」的证据在 packages/core/src/session/history.ts:13-22 latestCompaction()。

git-worktree 快照回滚——packages/opencode/src/session/revert.ts:70-73（先 track() 再 restore() 旧快照、revert(patches) 撤文件）：

rev.snapshot = session.revert?.snapshot ?? (yield* snap.track())
if (session.revert?.snapshot) yield* snap.restore(session.revert.snapshot)
yield* snap.revert(patches)
if (rev.snapshot) rev.diff = yield* snap.diff(rev.snapshot)

快照底层是 git——packages/opencode/src/snapshot/index.ts:382-399（restore = git read-tree）、:408-441（revert = checkout/delete）：

const result = yield* git([...core, ...args(["read-tree", snapshot])], { cwd: state.worktree })  // :386 restore
// revert: file existed in snapshot → checkout；not existed → delete            // :408-441

关键差异：opencode 的「检查点」持久化的是文件改动 diff（revert.ts:76-77 用 summary.computeDiff 算出并写 session_diff；:79-87 setRevert 记录 revert 点），不是 cline 那种对话编辑的 timestamp 截断。

③ 数据流图


              Context Epoch（DB: SessionContextEpochTable）
                 baseline / snapshot / baseline_seq
                        │
  buildPrompt ──▶ context-epoch.prepare：
        │           无存储 → initialize（insert baseline）
        │           有存储 + compaction.seq > baseline_seq → replace（新 epoch）
        │           有存储 + 无新 compaction → reconcile（publish ContextUpdated + advance snapshot）
        ▼
  provider turn（投影用 baselineSeq 截断 system 消息 —— history.ts）
  ============ workspace 侧（正交）============
  tool 改文件 → Snapshot.track()（git commit 快照）
  revert()  → snap.restore(旧快照) + snap.revert(patches) → 文件回到之前状态
               session.revert 持久化 revert 点（messageID/partID/snapshot）→ unrevert() 可撤销回滚

④ 代价与边界

  • 代价：两套机制（context 侧 epoch + workspace 侧 git 快照）带来概念成本——「回滚」在 opencode 里是两个不同动词：epoch 的 replace/reconcile 管上下文，snapshot 的 restore/revert 管文件。
  • 边界：git 快照依赖底层 git（snapshot/index.ts:71 用 Global.Path.data/snapshot/<project>/<worktree hash> 作独立 gitdir）；大仓库会拖慢 track()（:277-294 有 large 大仓库过滤）。
  • 失败模式：restore/revert 大量 Effect.logError("failed to restore snapshot")（:392/:399/:435）——git 快照失败时只记日志、不抛异常，回滚可能半途而废而不被上层感知。

⑤ 我的判断

cline 用「非破坏性编辑 + 时间戳截断」把对话与压缩做成一体的可回退历史；opencode 把「上下文状态」（epoch）和「文件状态」（git snapshot）分层。后者更贴合「agent 真正要回滚的是磁盘副作用」这一事实，且 git 快照天然复用成熟的 diff/checkout——但要说明：opencode 没有 cline 那种「精确回退到摘要生成前」的对话级时间戳截断；它对「压缩」的回退通过「epoch 换基线」而非「截断时间戳」实现。线2

4. 线3 — 插件与 Hook 系统（把调控能力开放给外部）

① 它解决什么问题

和 cline 的 Hook 系统同源：把内置的上下文/tool/权限调控能力，以受控方式开放给插件。但 opencode 的插件面更细——不是 cline 的粗粒度 beforeRun/afterRun/beforeTool，而是一张字符串键控的细粒度 Hook 表。

② 怎么实现（原文）

Hook 接口全清单——packages/plugin/src/index.ts:222-334（Hooks interface），关键项（贴要点非全文）：

插件形态：Plugin = (input, options) => Promise<Hooks>（:74）——插件是一次函数调用，返回 Hook 集合，与 cline 的「manifest.capabilities 声明 + hooks 对象」同一思想、不同封装。加载应用见 packages/opencode/src/plugin/index.ts:114 applyPlugin(load, input, hooks[])。

⭐ 核心问题：Compaction 能否插件化？——证据矛盾，如实拆解：

  • ✅ 有 Hook 接入压缩生命周期：experimental.session.compacting（:305-306）压缩时触发；experimental.compaction.autocontinue（:316-318）控制压缩后自动续跑。
  • ❌ 压缩算法本身硬编码在核心：真正的压缩逻辑在 packages/opencode/src/session/compaction.ts 的 SessionCompaction Service（prune + processCompaction），插件无法替换。
  • 📌 官方自承边界——CONTEXT.md:223-225 明确：experimental.chat.system.transform 能改 baseline system prompt，但「V2 插件尚未暴露等价 Hook」，是否移植另行决定：
- Legacy experimental.chat.system.transform can mutate the assembled baseline system prompt arbitrarily, but V2 plugins do not yet expose an equivalent hook. Decide separately whether to port it, replace dynamic uses with plugin-defined Context Sources, or narrow its semantics.

④ 代价与边界

  • 代价：字符串键 Hook 表让插件 API 表面扁平，但 experimental.* 前缀 Hook 是临时契约——compaction.ts:537-539 注释明确 compaction_continue 标记「not a stable plugin contract and may change or disappear」，依赖它的插件有漂移风险。
  • 边界：扩展边界画在「观测与包裹」而非「替换核心」——与 cline 结论一致：Compaction 这类上下文调控核心硬编码，Hook 能挂时长、能改 system prompt，但换不掉压缩算法。

⑤ 我的判断

opencode 的 Hook 面比 cline 更细、更贴近请求生命周期（细分到 chat.params/chat.headers/tool.execute.before/after），反映它把「provider 请求」当一等抽象。但两者在「上下文调控核心是否可替换」上给出相同的保守答案：压缩算法硬编码，Hook 只开放「观测 + 外围改写」。真正开放给生态的，是 cline 的「工具/权限/生命周期包裹」与 opencode 的「provider 接入 + system prompt transform + 压缩时机」——压缩策略本身都在核心，留给生态的是它的『四周』。线3

5. 线4 — Todo 任务状态跨压缩存活（长期目标解耦）

① 它解决什么问题

cline 的 Focus Chain 命题：「压缩的是『对话说了什么』，但『接下来要做什么』通过 todo list 单独维护」。opencode 的实现更直白：Todo 存在一张独立 SQL 表里，与消息表（会被压缩投影）彻底分开——压缩天然碰不到它。

② 怎么实现（原文）

Todo 用独立表 TodoTable 持久化（非消息、非投影）——packages/opencode/src/session/todo.ts:29-51：

const update = Effect.fn("Todo.update")(function* (input: { sessionID; todos }) {
  yield* db.transaction((tx) =>
    Effect.gen(function* () {
      yield* tx.delete(TodoTable).where(eq(TodoTable.session_id, input.sessionID)).run()   // 先清空
      if (input.todos.length === 0) return
      yield* tx.insert(TodoTable).values(
        input.todos.map((todo, position) => ({          // 重插，position 显式编码顺序
          session_id, content: todo.content, status: todo.status, priority: todo.priority, position,
        })),
      ).run()
    }),
  ).pipe(Effect.orDie)
  yield* events.publish(Event.Updated, input)
})

读取按 position 升序——todo.ts:54-60 orderBy(asc(TodoTable.position))。position（:38-43）让「顺序」成为显式持久化事实，不依赖消息时间。

③ 数据流图


  短期记忆（会话）：SessionMessageTable ──▶ 会被 compaction 摘要 / seq 截断（投影里消失）
  长期目标（Todo）：TodoTable（session_id/content/status/priority/position）
                    └── 独立表，从不进入 compaction 的 prune/process 对象
                    └── 每次 update 是「delete+insert」整体覆盖，position 定义顺序
        → 压缩发生后：todo 原样保留，agent 靠 todo 而非对话历史记住「接下来做什么」

④ 代价与边界

  • 代价：update 是全量 delete+insert（:33-46），无增量 diff——todo 每更新都重写整表，todo 多时有 O(n) 写放大。
  • 边界：todo 内容如何进 system prompt 属于「注入」（走 experimental.chat.system.transform 之类外围 Hook），不是 compression 本体职责。

⑤ 我的判断

opencode 的「长期目标 vs 短期对话」解耦最朴素也最彻底：换一张表。cline 的 Focus Chain 是「todo 作独立消息流/文件」的显式机制（目前甚至还是 stub），opencode 直接用数据库表物理隔离。「跨压缩存活」这一性质由 schema 保证、无需额外代码，但代价是灵活性低（全量覆盖、无历史版本）。线4

6. 线5 — 模型适配与 token 计数策略

① 它解决什么问题

cline 用「3 字符/token」保守估算 effectiveMaxInputTokens，并有 Issue #7772（local 模型上下文窗口无法自动检测）。opencode 有同样两件事：token 估算 + 压缩条件启用，但参数取值不同。

② 怎么实现（原文）

token 估算——packages/core/src/util/token.ts:3-5（4 字符/token）：

const CHARS_PER_TOKEN = 4
export const estimate = (input: string) => Math.max(0, Math.round(input.length / CHARS_PER_TOKEN))
对照：cline 用 3 字符/token（更保守 → 高估 token，压缩来得早）；opencode 用 4 字符/token（更乐观 → 低估 token，压缩来得晚）。直接影响「何时触发压缩」。

压缩预算常量——packages/opencode/src/session/compaction.ts:28-33：

export const PRUNE_MINIMUM = 20_000
export const PRUNE_PROTECT = 40_000
const TOOL_OUTPUT_MAX_CHARS = 2_000
const PRUNE_PROTECTED_TOOLS = ["skill"]
const MIN_PRESERVE_RECENT_TOKENS = 2_000
const MAX_PRESERVE_RECENT_TOKENS = 15_000

保留近端预算——compaction.ts:115-119（默认保留可用窗口 25%，夹在 2k~15k）：

return input.cfg.compaction?.preserve_recent_tokens ??
  Math.min(MAX_PRESERVE_RECENT_TOKENS, Math.max(MIN_PRESERVE_RECENT_TOKENS, Math.floor(usable(input) * 0.25)))

条件启用开关——packages/opencode/src/config/config.ts:594-597：

if (Flag.OPENCODE_DISABLE_AUTOCOMPACT) { result.compaction = { ...result.compaction, auto: false } }    // :593-595
if (Flag.OPENCODE_DISABLE_PRUNE)     { result.compaction = { ...result.compaction, prune: false } }   // :596-598

注：这是环境变量 flag 开关（OPENCODE_DISABLE_AUTOCOMPACT / OPENCODE_DISABLE_PRUNE），不是 per-provider 白名单。自动压缩运行时判定见 processor.ts:622（compaction?.auto === false && !ctx.assistantMessage.summary）与 :693（if (ctx.needsCompaction) return "compact"）。

③ 数据流图


  消息文本 → Token.estimate（len / CHARS_PER_TOKEN=4）→ 各层估算 token
        │
        ├─ isOverflow(token, model)？→ 超 provider 限额 → compaction.create(auto:true)
        ├─ needsCompaction（processor 累积超预算）→ return "compact"
        ├─ prune：保留 2k~15k（默认 25% 窗口）近端，向前抹旧 tool 输出（PRUNE_PROTECT=40k 门槛）
        └─ 受 config.compaction.auto/prune + preserve_recent_tokens 调制（多模型 provider 走 Provider 抽象）

④ 代价与边界

  • 代价：4 字符/token 是乐观估算，对 token 密集文本（代码、表格）会低估，压缩触发偏晚，可能撞 provider 真实硬上限。
  • 边界：开关系（auto/prune）与预算常量是全局/配置级，非 per-provider 白名单——cline 有 provider 特殊待遇清单（Claude 4/GPT-5 等才启 Auto Compact），opencode 的适配靠 Provider 抽象（usable(input) 取 model 可用窗口）而非硬编码白名单。
  • 失败模式：prune 只保护 skill（PRUNE_PROTECTED_TOOLS=["skill"]），其他工具（read/bash 等）大输出可能被抹掉，模型丢失关键中间结果。

⑤ 我的判断

两条线都承认「token 估算是启发式」，但取值方向相反：cline 偏保守（宁早压缩不留溢出），opencode 偏乐观（宁晚不浪费上下文）。折射两类产品哲学：cline 面向「多 provider 兼容 + 本地模型兜底」，opencode 面向「头部云模型 + 高效利用上下文」。适配上，cline 做显式白名单，opencode 做 provider 抽象 + 配置开关——前者硬编码在 utils，后者参数化在 config。线5
