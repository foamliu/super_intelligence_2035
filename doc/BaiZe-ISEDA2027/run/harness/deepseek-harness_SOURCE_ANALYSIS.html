0. 概况与术语体系

DeepSeek Harness（dsh，@deepseek-ai/dsh-*）由 DeepSeek AI 开源，构建在 Cordis 框架之上，采用「everything-is-a-plugin」架构（README.md:5-7）：连 模型适配器、工具注册表、会话日志、agent loop 本身都是插件，每一环都可从配置替换。

它给自己建立的术语体系，本质是一条「上下文生命周期」设计主张 —— 把「持久的事件日志」与「投影出来的模型可见视图」严格分离。核心术语：

术语含义证据
Session Log（事件日志）append-only 事件流，是「唯一事实源」（the source of truth）。任何到达模型请求的东西都必须能从日志重建。surface.ts:3-4；docs/architecture.md「Model-visible means logged」
Surface（表面）日志之上「能产生 LLM 消息」的事件的有序投影视图，只有 3 类事件可上表面：user/message / assistant/message / tool/result。surface.ts:22-26
deriveMessages()把日志「投影」成模型可见历史的逐节点折叠规则。surface.ts:81；index.ts:790
surfaceOp: append/replace每个上表面事件携带一个表面操作标记；replace 即「影子替换」—— 新摘要节点覆盖一段旧范围，但原事件永不删除。surface.ts:42-75
log-only 事件带 surfaceOp 之外、不进表面的记录（compaction/*、hook/*、goal/change、todo/write）。types.ts:26 等多处

⚠️ 任务书 5 条线用的是 cline 旧 vscode 架构名（ContextPipelinePrepareTurn / EditType·ContextUpdate / 时间戳截断 / Focus Chain / context-window-utils.ts）。deepseek-harness 的内核同构但形态迁移：预处理 = agent/pre-step waterfall + surface 投影；无损编辑 = append-only log + surfaceOp 影子替换；Focus Chain = goal/todo 包。本报告逐线给「旧→新」对照。

1. 上下文生命周期全景图（总图）


                          ┌─────────────────────────────────────────────────────────┐
                          │               Session Log（append-only，唯一事实源）        │

                          │  compaction/* · hook/* · goal/change · todo/write（log-only）│

        │  {surfaceOp:{op:'replace'}}) 影子替换      │         └─ 线1 surface 投影（3 类消息）
        │  + session-checkpoint-policy flush 落盘    │              └─ 线3 拦截点：agent/pre-step（waterfall）
        └───────────────────────┬──────────────┘                       ▼
                                │                          agent-loop 组装 canonicalHeader + request
            user 输入 → inbox → │ ─（线3 Hook 桥：PreToolUse/Stop/… 外部进程）─→  llm/stream

                                │                                              ▼
                     tool/execute（线2 再 flush）  ←──  assistant 工具调用 ── 模型回复

一句话主线：五条线都挂在「append-only 日志 → surface 投影」这条脊椎上。线1 管「投影怎么算」（哪些事件、按什么规则进模型视野）；线2 管「压缩如何不破坏原日志地收掉一段历史」（影子替换 + 落盘检查点）；线3 管「历史之外的拦截点开放给谁」（外部 Hook 进程 vs 进程内插件）；线4 管「任务目标为何不在被压缩的对话里」；线5 管「压缩/截断的阈值与预算从哪来、怎么按模型适配」。

2. 线1 — 上下文注入与「投影」管线

线1 ① 解决什么问题：模型看到什么、看不到什么，必须是一条可回放、可审计的确定性规则，而不是「散落在各处的拼装字符串」。deepseek 的答案是：模型可见 = 已落日志。

② 怎么实现（贴原文）

投影层定义 —— packages/core/session/src/surface.ts:1-9：

/** Surface layer on top of the session event log: an ordered view of events
 * that produce LLM messages. The append-only log remains the source of truth. */

只有 3 类事件能上表面 —— surface.ts:22-26：

const SURFACE_EVENT_TYPES = new Set<string>([
  'user/message',
  'assistant/message',
  'tool/result',
])

逐节点投影规则（「无损投影」的核心） —— surface.ts:81-90：

/** THE per-node projection rule: `Session.deriveMessages` folds it over the
 * live surface, external reconstructors and pure projections fold the same
 * function over a log prefix's surface to rebuild the exact messages any
 * request was built from. */

请求前拦截点（对应 cline 的 ContextPipelinePrepareTurn）—— agent/pre-step 是 waterfall，可改写/拒绝要进入模型的 claimed messages（docs/architecture.md）：

`agent/pre-step` decides what the model sees. Listeners may rewrite the claimed
messages or reject them outright; a rejected or empty first claim still closes a
durable turn that spent no step.

请求组装（投影的终点） —— packages/core/agent-loop/src/agent.ts:535-542：把 boundaryMessages（surface 投影结果）deepFreeze 后封成 request：

messages: boundaryMessages,
...header.system !== undefined ? { system: header.system } : {},
...header.tools !== undefined ? { tools: header.tools } : {},

③ 数据流图


  Session Log（append-only）
       │  foldSurface / deriveEventMessage（逐节点 → Message | null）
       ▼
  Surface 视图（仅 user/message · assistant/message · tool/result）
       │  agent/pre-step waterfall：可改写 / 拒绝 / startsRequestSeries
       ▼
  boundaryMessages ─┐
  system（system-prompt 装配）  ├─ deepFreeze ─→ canonicalHeader ─→ llm/stream
  tools（tool schema）         ┘

④ 代价与边界

  • 代价：所有「模型可见」都要先变成日志事件（docs/architecture.md「This is why a new model-visible input requires a new session event」）—— 加一种新输入就得扩 SessionEventMap 并写 render。
  • 代价：投影是运行时重放；SurfaceManager 做增量 _processDelta（surface.ts:460-475）减轻。
  • 边界：SurfaceManager「replacement history is not retained」（surface.ts:415）——「原始 vs 投影」对照靠 isAppendSurfaceEvent，而非 cline 的持久化编辑 map。

⑤ 我的判断

deepseek 用比 cline「更纯粹」的事件溯源答同一条线：cline 是「原始消息 + 编辑 map，读取时应用」；deepseek 是「原始事件流 + 表面 fold，读取时重放」。前者把「怎么改」持久化，后者把「完整事实」持久化 —— 后者回放更完备，但每步付 fold 成本。线1

3. 线2 — 检查点与「影子替换」式回滚

线2 ① 解决什么问题：压缩绝不能破坏已发生的对话（用户已看到的），压缩动作本身要可靠持久化（否则重启后重复压缩 / 阈值错乱）。

② 怎么实现（贴原文）

压缩 = 一串 log-only 事件 + 一次影子替换。压缩事件本身不进表面；真正的替代是紧跟着的一条 user/message（packages/compaction/compaction/src/types.ts:34-40）：

'compaction/summary': {
  summary: ContentBlock[]
  shadowedRange: { start: SessionSeq; end: SessionSeq }
  shadowedSeqs: SessionSeq[]
  shadowedTokenCount: number
}

影子替换的落点 —— packages/compaction/compaction-basic/src/region.ts:472-475：摘要以 user/message 追加，携带 surfaceOp:{op:'replace',start,end} —— 原事件不删，只是被「遮蔽」：

session.append('user/message', checkpointMessage, {
  surfaceOp: { op: 'replace', start, end },
  sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
})

检查点 provenance 标记 —— packages/compaction/compaction/src/checkpoint.ts:19-51（每条压缩 checkpoint 带稳定 compactionId，供持久化后识别）：

export function isCompactCheckpointSource(source: MessageSource): boolean {
  return source.kind === 'plugin' && source.plugin === COMPACT_CHECKPOINT_MARKER.plugin
}

落盘检查点策略（fail-closed） —— packages/session/session-checkpoint-policy/src/index.ts:29-37 / 63-82：模型请求、工具副作用前必须 flush，否则「不派发下游」：

async function* afterCheckpoint(...) {
  await ctx.sessions.flush(session)
  yield* next()
}
// Checkpoint failures are fail-closed at the model and tool side-effect boundaries

③ 数据流图


  token-meter 判定需要压缩
       ├─ append compaction/start（log-only，持锁）
       ├─ 异步 summarize（复用 provider KV-cache 前缀，region.ts:498-523）
       ├─ append compaction/summary（log-only，记 shadowedRange + shadowedTokenCount）
       ├─ append user/message { surfaceOp:{op:'replace'} }  ← 影子替换，遮蔽旧范围
       ├─ append compaction/end（log-only，放锁）
       └─ flush（session-checkpoint-policy 在下一请求/工具前强制）
  折回 surface：被遮蔽的旧事件仍存在，只是不在模型可见视图（人类转录走 isAppendSurfaceEvent）

④ 代价与边界

  • 代价：事件日志只增不减，磁盘随压缩持续增长（被遮蔽事件仍在日志里）。
  • 边界（诚实声明）：我未找到 cline 那种「按时间戳截断 ContextUpdate 精确回退到压缩前」的显式 rollback API。deepseek 的回滚是隐式、靠事件溯源的：foldSurface（surface.ts:397）对任意日志前缀重放即可重建「压缩前」视图 —— 影子替换只是投影层一个 replace 节点，取消它即「回到压缩前」。「重放即回滚」，非「截断即回滚」。
  • 代价：影子「价格」靠 shadowedTokenCount（启发式，types.ts:82-89）事后扣减 —— 是事后定价而非逐节点存价。

⑤ 我的判断

deepseek 把 cline 的两件事拆清楚了：cline 的「compaction sidecar 持久化（PR #12747 修的点）」在 deepseek 是第一公民的 session-checkpoint-policy（flush fail-closed）；cline 的「非破坏性编辑」在 deepseek 是事件溯源 + surfaceOp 影子。可靠持久化不是事后补丁，而是从「模型可见=已落日志」这条不变量里长出来的。线2

4. 线3 — 全插件架构与 Hook 桥（扩展边界）

线3 ① 解决什么问题：把调控能力开放给外部时，deepseek 走了两极：进程内全插件（Cordis，连 kernel 都可换）与外部 Hook 桥（兼容 Claude Code / Codex 的 wire protocol）。

② 怎么实现（贴原文）

没有特权核心 —— docs/architecture.md：

There is no privileged core to patch: you extend dsh by mounting a plugin beside
the others. Every part of the product is a plugin, including the model adapter,
the tool registry, the session log, and the agent loop itself.

Hook 桥的方言中立词表 —— packages/hooks/hook-protocol/src/types.ts:8-48：

/** ... shared by the Claude Code and Codex hook bridges ... `point`
 * the hook point (`PreToolUse`, `Stop`, …) ...*/
export type HookDialect = 'claude-code' | 'codex'

只有 command 型 hook 进 runner —— types.ts:50-61（CC 的 prompt/agent/http 被 parse-and-skip）：

export interface CommandHook { command: string; timeoutSec?: number }

Hook 输出（被解析但不全被采用的字段） —— types.ts:89-137：

decision?: 'approve' | 'allow' | 'block' | 'deny' | 'ask'
additionalContext?: string   // CC additionalContext，注入下次请求
updatedInput?: ...           // parsed but NOT honored（input rewrite 已 deferred）
systemMessage?: string       // CC systemMessage

Hook 只写 log-only 事件 —— packages/hooks/hook-protocol/src/events.ts:75-104（hook/invoked 与 hook/result 成对）：

session.append('hook/result', {
  decision: output.decision ?? (output.continue === false ? 'stop' : 'pass'),
  ...stderrSummary !== undefined ? { stderrSummary } : {},  durationMs })

进程内插件拦截点 ≠ 桥 —— types.ts:43-46：

A native plugin at the interception points is not a bridge
and writes no `hook/*` invocation/result records

③ 数据流图


  拦截点（agent/pre-step · PreToolUse · Stop · SessionStart · UserPromptSubmit …）
        ├─ 进程内：Cordis 插件直接挂 listener（waterfall/serial/emit）→ 不写 hook/*
        └─ 外部：Hook 桥（claude-code / codex dumb）→ 起子进程跑 command
                → 解析 exit code + stdout JSON + stderr → decision
                → append hook/invoked + hook/result（log-only）

④ 代价与边界

  • 代价：两条扩展路径语义不同源 —— 进程内插件幂等、有类型、可 veto（waterfall）；外部 hook 是带超时的子进程 + 字符串协议，需 dialect 归一。
  • 边界：updatedInput（工具输入改写）被解析但未采用（deferred）—— 兼容是「faithful-but-degraded」（types.ts:84-87）。
  • 核心问题结论：Auto Compact（等价物）可以用插件实现 —— compaction-basic 本身就是 dsh-compaction 这个 Service Definition 的一个 Provider，挂 agent/pre-step + agent/request-error listener。Hook 桥拦不到 agent/pre-step 这种底层管线节点 —— hook 是外部进程制的「观察/审批」旁路，不是进程内「改写管线」。所以 deepseek 的扩展边界是：「核心能力 = 可替换的 Cordis Service/Plugin；外部生态 = 审批与观察的 hook 桥」。

⑤ 我的判断

三者对比：cline 是「插件 manifest + 有限 hook 点」；opencode 是「细粒度字符串键 hook」。deepseek 最激进 —— 连 agent loop、模型 adapter、会话日志本身都非核心，唯一不可替换的是 Cordis 的「插件树 + 类型化事件 + 可逆 effect」元架构。hook 桥退化为「兼容别人 wire protocol 的进程隔离旁路」。线3

5. 线4 — Goal/Todo 任务状态跨压缩存活

线4 ① 解决什么问题：压缩掉的是「对话说了什么」；「接下来要做什么」不能跟着被压缩。deepseek 用两个独立 log-only 事件域（goal 与 todo）把它从对话 surface 解耦出来。

② 怎么实现（贴原文）

Goal：全快照 + 墓碑的可持久变化 —— packages/goal/goal/src/domain.ts:14-22 / 61-68：

export type GoalOperation =
  | 'create' | 'edit' | 'pause' | 'resume' | 'complete' | 'block' | 'clear'
// 声明进 SessionEventMap：
'goal/change': GoalChangeMeta   // 全快照变更或 clear 墓碑

Goal 是可重放的纯 fold —— domain.ts:70-82（FoldedGoal 由 goal/change 序列重放，含 roundsStarted）：

export interface FoldedGoal {
  goal?: GoalSnapshot;  roundsStarted: number
  createdAt?: number;   updatedAt?: number;  lastRef?: GoalRef
}

Todo：整表快照、last-write-wins、永不进历史 —— packages/todo/tool-todo/src/types.ts:21-33：

export interface TodoItem {
  content: string
  status: 'pending' | 'in_progress' | 'completed'
}
'todo/write': { todos: TodoItem[] }   // Whole-list snapshot; latest write wins on replay.
// Log-only UI state; never derived history.

③ 数据流图


  模型调用 todo/write 或 goal 工具
       │  append log-only 事件（goal/change、todo/write）—— 不进 surface
       ▼
  SessionProjectionStateMap（独立投影键：todos / goal 由 fold 重放）
       │  压缩只 shadow surface 节点，碰不到 log-only 域
       ▼
  下一次 pre-step 从投影键读取「当前待办 / 当前目标」，与对话长度无关

④ 代价与边界

  • 代价：任务状态与对话分属不同投影域，一致性靠「都从同一 append-only 日志重放」保证。goal 用「全快照 + 墓碑」、todo 用「整表 last-write-wins」，牺牲细粒度增量换「重放简单」。
  • 边界：todo/write 明确「never derived history」（types.ts:30）—— 是「Log-only UI state」，本身不进模型对话；模型通过 tool 读写，而非靠对话历史记住进度。
  • 与 cline Focus Chain 差异：cline 的 Focus Chain 当前多为 stub；deepseek 的 goal 是完整领域模型（带 roundsStarted/maxRounds 的续会话目标生命周期），todo 是独立工具。二者都靠「独立于 surface 的持久域」实现跨压缩存活。

⑤ 我的判断

这是「短期记忆（对话）与长期目标（任务列表）解耦」的事件溯源版本：两者都写同一日志，但只有对话进 surface（可压缩），goal/todo 走独立投影键（压缩不碰）。干净之处在于「能/不能被压缩」由事件类型是否 surface-eligible 一刀切决定，而非代码特判混杂。线4

6. 线5 — 模型适配与 token 计数策略

线5 ① 解决什么问题：压缩/截断的阈值与预算必须按每个 provider/model 的真实容量算出，同时 token 估算在「无需精确分词」时要有统一启发式。

② 怎么实现（贴原文）

固定密度启发式 —— packages/llm/token-meter/src/estimate.ts:12-19：

/** Fixed text-density estimate used until exact tokenization is needed. */
const CHARS_PER_TOKEN = 4
/** Per-block structural overhead for JSON framing and type tags. */
const BLOCK_OVERHEAD = 4
/** Role-field framing overhead added to every priced message. */
export const ROLE_OVERHEAD = 4

模型级策略（数据驱动，非硬编码白名单） —— packages/compaction/compaction-basic/src/config.ts:18-22：

/** Default request-pressure fraction for every routed model. */
const DEFAULT_THRESHOLD_RATIO = 0.8
/** Default verbatim-tail fraction for every routed model. */
const DEFAULT_RETAIN_RATIO = 0.16

按真实 capacity 缩放预算 —— config.ts（resolveCompactSpec）：

/**
 * Scale one routed policy into concrete token budgets for its model capacity.
 * @param contextWindow - positive adapter-owned capacity for that target. */

两条触发路径 —— packages/compaction/compaction-basic/src/index.ts:148-166 / 180-195（agent/pre-step 的「pressure」，与 agent/request-error 的「context-overflow」）：

ctx.on('agent/pre-step', ... this.compactIfNeeded(agent, 'pressure', signal) ...)
ctx.on('agent/request-error', ...
  if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE || signal.aborted) return next()
  ... this.compactIfNeeded(agent, 'context-overflow', signal) ...)

provider 抽象下的 adapter 职责 —— packages/llm/llm/src/types.ts:1-5：

/** Canonical provider-neutral message and streaming vocabulary for the loop,
 * session log, and plugins. Adapters alone translate provider wire messages; */

③ 数据流图


  token-meter.measure(session)  ── CHARS_PER_TOKEN=4 固定启发式
        │ totalTokens
        ├─ pressure：resolveCompactSpec(policy, contextWindow) → threshold/retain 预算
        │     若 total ≥ threshold → model-free prune → 再 summarize
        └─ context-overflow：CONTEXT_WINDOW_EXCEEDED → prune → 重选范围 → compact
  modelPolicies（provider/model 精确覆盖）→ 覆盖默认 0.8 / 0.16 / maxTokens=8192

④ 代价与边界

  • 代价：4 字符/token 是乐观估算（同 opencode），对 token 密集文本（代码/表格）会低估，压缩触发偏晚，靠 context-overflow 事后兜底。
  • 代价：contextWindow 是 adapter 提供的「authoritative capacity」，若某 adapter 不报 capacity 则甩 TargetPressureConfigError（index.ts:297-303）—— 即「适配模型必须显式声明容量」，否则压力压缩直接失败。
  • 边界：不是硬编码白名单，而是 modelPolicies 数据表（provider+model → 覆盖项）。cline 的「只对 Claude 4/GPT-5/Gemini/Grok 启 Auto Compact」是核心硬编码；deepseek 是配置数据。
  • 诚实声明：未发现 cline Issue #7772 那种「本地 llama-server 上下文无法自动检测、默认按 128K 处理」的对应问题 —— 因为 deepseek 把 capacity 交给 adapter 显式声明，缺省即报 TargetPressureConfigError（不放行、不猜 128K），这是更保守的 fail-closed。

⑤ 我的判断

token 估算方向三者一致（启发式），但适配哲学不同：cline 硬编码白名单（pro/con 各半）；opencode 走 Provider 抽象 + 全局开关；deepseek 走「per-provider/model 配置数据表 + adapter 显式声明容量 + 缺失即报错」。三者的适配「妥协」本质是同一件事 —— 把「模型真实上下文窗口」这个 runtime 事实，替换成「代码里写死的假设」。deepseek 用「fail-closed 报错」暴露假设，而非静默降级。线5
