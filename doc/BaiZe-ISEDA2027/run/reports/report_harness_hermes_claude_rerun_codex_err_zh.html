5.4 归因（三选一，逐条带证据）

(a) 适配器 bug —— 部分成立（设计差异，非崩溃性 bug）
codex.py:156-162 命令 codex exec --cd <cwd> --model kimi-k2.6-cloud --sandbox danger-full-access --skip-git-repo-check --json <instruction> 无 max-turns / 迭代上限参数。codex-cli 0.94.0 exec --help 确认无 --max-turns； 源码 grep max_iterations|turn_limit|max_turns|iteration_limit 0 命中 → exec 模式无内置回合上限。 后果：codex 在难题上持续跑到外层 1800s 被杀，记为 exception，放大 exception 计数、压低 eval-trial 计数（41/87）， 但不直接压低条件通过率。对照 cline 完成率 92% → cline 在 1800s 内更常自行结束。

(b) 容量 / 上下文 —— 为辅（25/59=42.4%）
15 AgentTimeoutError + 10 RuntimeError(无 429) 是纯 1800s 预算超时：codex 跑满预算的多为重编译/构建类 （build-pov-ray、compile-compcert、build-pmars…，与 cline 也超时的难题重叠，但 cline 超时仅 ~19 题）。 codex 0.94.0 走 wire_api="responses" 经 gw_proxy 翻译 /v1/responses→/v1/chat/completions，单轮开销较高 → 难题 1800s 跑不完。 这不是「模型不行」：codex 完成的 41 题里通过 20 题（48.8%）。

(c) 上游服务 —— 成立（为主，34/59=57.6%） 【R510 修正：推翻 R499「不成立」】
R510 复查 result.json stdout 发现 34 个 RuntimeError 的真正触发链是网关 429 限流： exceeded retry limit, last status: 429 Too Many Requests → turn.failed → codex CLI 卡住 → 撞 1800s 超时。 429 是 codex 独有：7 路横向对照（严格标记），只有 codex 命中 34 次，其余 6 路全为 0 （cline stdout 的 60 次「429」是 ISO 时间戳 .429Z 误匹配，0 次 turn.failed）。 ⇒ codex 0.94.0 responses 代理路径调用频次/突发高于其余 6 路 → 触发网关 429；且 codex 重试无有效退避 → 429 致命化。 gw_proxy 9090/9091 本身在线、20 pass 通路正常，但在 codex 的调用模式下确实返回了 429。

5.5 修法判断：codex 可改善（R510 修正 · 推翻「非适配器可修 / 改命令不会提分」）

R499 判「非适配器可修」是基于「没有 429」的错误前提。R510 证实 34/59 异常是 429 限流所致 → codex 有真实提升空间： 1. 降并发复跑 codex（单独跑或 2-3 路，降低网关 429 触发率）—— 最直接； 2. 给 codex 配 429 退避/重试上限（config.toml 或 -c 覆盖），让 429 后干净重试而非 turn.failed 卡死； 3. 排查 wire_api="responses" 代理翻译路径是否放大请求频次。 预期：消解 34 个 429 异常后，完成率可从 47.1% 上行 → resolve rate 有真实提升空间。

结论：codex 高 err（59/87=67.8% exception，resolve 20/87=23.0%）根因 = (c) 上游 429 为主（34/59=57.6%，codex 调用模式独有）+ (b) 容量/超时为辅（25/59=42.4%）+ (a) 适配器无回合上限/无 429 退避放大了前两者。 非「非适配器可修」：降并发复跑或加 429 退避可改善。条件通过率 48.8% 表明 codex 能力与存活线同档，短板是「429 致命化 + 固定预算内完成题数少」。

codex 全量补跑待办：建议先「降并发（如单独跑）+ 加 429 退避」smoke 5 题（至少 2 题是旧 429 题）验证 429 是否消解，再报机时 + load 评估；铁律仍守四 survivor 源码不硬改。
