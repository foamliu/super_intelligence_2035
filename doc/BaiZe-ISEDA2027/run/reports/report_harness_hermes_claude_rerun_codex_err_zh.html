5.4 归因（三选一，逐条带证据）

(a) 适配器 bug —— 部分成立（设计差异，非崩溃性 bug）
codex.py:156-162 命令 codex exec --cd <cwd> --model kimi-k2.6-cloud --sandbox danger-full-access --skip-git-repo-check --json <instruction> 无 max-turns / 迭代上限参数。codex-cli 0.94.0 exec --help 确认无 --max-turns； 源码 grep max_iterations|turn_limit|max_turns|iteration_limit 0 命中 → exec 模式无内置回合上限。 后果：codex 在难题上持续跑到外层 1800s 被杀，记为 exception，放大 exception 计数、压低 eval-trial 计数（41/87）， 但不直接压低条件通过率。对照 cline 完成率 92% → cline 在 1800s 内更常自行结束。

(b) 容量 / 上下文 —— 主要成立
codex 完成率 47.1% ≪ cline/opencode/pi 的 86–92%。codex 跑满 1800s 的 59 题多为重编译/构建类 （build-pov-ray、compile-compcert、build-pmars、make-doom-for-mips…，与 cline 也超时的难题高度重叠，但 cline 超时仅 ~19 题）。 codex 0.94.0 走 wire_api="responses" 经 gw_proxy 翻译 /v1/responses→/v1/chat/completions， 单轮开销较高 → 难题 1800s 跑不完。这不是「模型不行」：codex 完成的 41 题里通过 20 题（48.8%）。

(c) 上游服务 —— 不成立
gw_proxy 9090/9091 在线；日志仅见 benign 的 ConnectionResetError 与 LiteLLM model-cost fetch Errno 101（loop 剥代理所致）。 codex 20 pass 的题证明模型调用通路正常，无 429 / 网关 403 / API 截断。

5.5 修法判断：非适配器可修（不硬改）

codex 0.94.0 exec 模式无内置回合上限 → 无法通过 -c key=value 让它干净退出。 唯一可调旋钮 = TB_AGENT_TIMEOUT（默认 1800s）：调小→codex 更快失败但不提分；调大→更费机时、边际收益不明。 改 codex.py 命令/超时处理不会提升通过率（codex 已在它完成的题上拿到 48.8%）；只会把 59 个超时 exception 转成更早的干净失败。 铁律遵守：四 survivor 源码（含 codex.py）本轮不改动。

结论：codex 高 err（59/87=67.8% exception，resolve 20/87=23.0%）根因 = (b) 容量为主 + (a) 适配器设计为辅： codex 0.94.0 exec 无内置回合上限 + 单轮开销较高，导致 59/87 题在 1800s 预算内跑不完被超时杀掉； 非上游服务问题，亦非可经适配器层修复的崩溃性 bug。条件通过率 48.8% 表明 codex 能力与其它存活线同档， 短板是「在固定预算内完成题数少」。

codex 全量补跑待办：需先报「预计机时 + 与 SWE-bench 下载/复跑共存的 load」评估，避免三线挤爆。
