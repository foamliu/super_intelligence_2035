一、实验设计

此前 #788 的 seq=8192 验收是单机 8 卡（296,543 tok/s），16 卡吞吐靠「2× 外推 ≈ 593K」估计，非实测。本节用 .12（vision 闲置，WAITING=1/0MiB）+ .29 双节点 16 卡把 16K/32K 换成真实测量。集群 SSH 探测仅 .12+.29 双向免密可用（其余 10 节点全拒 key），.12 闲置是唯一可行路径——借用闲置 GPU ≠ 抢（vision R9 收敛待派，未在跑）。

脚本 baize_dualnode_seq16k32k_16gpu.sh 含安全闸：preflight 查 .12 非空闲即 abort（vision 起训自动跳过）；每配置 postflight 验两节点 GPU 回 0 MiB 才进下一格。三格同口径：FP8 tensorwise、--use-distributed-optimizer、overlap-grad-reduce/param-gather、真数据 16 片 p5b_l3_train_s{0..15}、graph OFF（rev3 修复）、ITERS=40、稳态取 log-interval=10 的 Step Time 中位（剔除首段 warmup）。拓扑：CP 对节点内（NVLink），DP=8 跨两节点（IB/RoCE）。

三、关键分析

3.1　8→16 卡扩展效率（把外推换成实测）

配置8 卡 tok/s（#791）16 卡 tok/s（本节）扩展倍数8卡 per-GPU16卡 per-GPUper-GPU 变化
16K CP=1300,133613,9922.045×37,51638,374+2.3%（轻微超线性）
32K CP=2183,394351,5261.917×22,92421,970−4.2%（跨节点 DP 开销）

16K CP=1 轻微超线性：DP16 把 distributed-optimizer 分片摊到 16 卡、param-gather/grad-reduce overlap 更充分 → per-GPU 不降反升 2.3%。32K CP=2 接近线性但 4.2% 损耗来自跨节点 IB 的 DP allreduce（CP 部分在节点内 NVLink，无跨节点开销）。外推 → 实测的修正：16K 由 593,086（2×296,543）→ 613,992（+3.5%）；32K 由 366,788（2×183,394）→ 351,526（−4.2%）。

3.2　为什么 16K 上 CP=2 反而更慢

E2（16K CP2, 281,970）= E1（16K CP1, 613,992）的 0.459×。CP=2 把每卡激活显存砍半（75.2→49.7 GB）但吞吐掉 54%。

机制：CP=2 在 forward/backup 两阶段都要对 attention 的 KV 块做 ring send/recv（P2P），16K 这个序列长度下计算/通信比偏低，P2P 开销 > 省下的显存收益。且 16K CP=1 已只占 75.2GB（<80GB），本就不需要 CP 减压。结论：16K 应关 CP（CP=1 DP16）。

3.3　为什么 32K 达不到 600K（结构性受限）

E3（32K CP2）= 351,526 tok/s = 600K 的 58.6%。三因素叠加：

  1. CP P2P KV 交换（主因，≈42.7%）：E3 与 E1 每卡 token 数相同（tok/mb/gpu=16384），唯一差 = CP=2 的 ring-attention KV 交换。per-GPU 38,374→21,970 = 0.573× → CP 开销 42.7%。
  2. 跨节点 DP（≈4.2%）：8 卡同口径 22,924→16 卡 21,970 = 0.958×。
  3. CP=2 是 32K 的强制项：32K CP=1 OOM @ 81,049 MiB（#787 实测，32K 无 CP 不入 80GB 卡）→ 非「可选优化」。

即便 8→16 卡完美线性（183,394×2 = 366,788）也只到 600K 的 61%。趋近 600K 的路径（后续，非本节）：① CP 通信/计算 overlap（当前 ring-attention KV 交换未必 fully overlapped）；② zigzag / unified CP 降低 KV 交换量；③ 更大 DP 摊薄（已 16 卡封顶，需更多节点）。

3.4　附带里程碑：#787 的 CP=2 阻断已解除

§五·6（#787）曾报告 flash-attn-3 的 window_size 元组签名与 Megatron CP 不兼容（Unknown keyword argument 'window_size'），32K CP=2 在首个 attention 层即崩、峰值仅 23,639 MiB。本节应用 FA3 CP patch（window_size→window_size_left/window_size_right，共享 NFS /nas_train 两节点透明可见）后 E2/E3 均 status=OK、rc=0、0 NaN、跑完 40 iter（峰值 49.7/76.0 GB）。这是首批真实 CP=2 吞吐数据。

五、建议

  1. 16K 训练用 CP=1 DP16、graph-OFF：613,992 tok/s 达 600K 目标，峰值 75.2GB 安全，per-GPU 38,374。不要再开 CP（CP=2 在 16K 上掉 54% 吞吐，纯亏）。
  2. 32K 训练接受 ≈351K tok/s：CP=2 是 80GB 卡上 32K 的强制项，600K 在当前拓扑/CP 算法下不可达。若需提升，按 §3.3 路径：CP comm/comp overlap → zigzag/unified CP → 扩节点。
  3. FA3 CP patch 已稳定，32K CP=2 可放心进入正式训练（本节证 0 NaN、健康 loss/gnorm、跑满 40 iter）。
  4. 16K 选择不影响 e18 8K 主线：16K step 6.83s ≈ 8K 6.81s，吞吐持平，且支持更长上下文。可按需切换。

六、口径与局限（caveat）

  • 三格均 40 iter、从零随机初始化：loss≈7.94 为 40 步预热态，非收敛值，仅证训练健康（0 NaN、gnorm 1.3–1.4 正常）。
  • 稳态 Step Time 取 log-interval=10 的中位：E1=6.76/6.83/6.87→6.83s；E2=7.44/7.48→7.46s；E3=12.09/11.91/11.93→11.93s。首段 warmup（E1 10.45 / E2 11.37 / E3 18.58s）已剔除。
  • 峰值显存取两节点 nvidia-smi max；.12/.29 几乎一致（差 <0.2GB）。
  • .12（vision）借用窗口 12:23–12:47，全程 vision 闲置；pretrain（.29）R2 训练未受影响（本测与 pretrain loop 分时；postflight .29 已回 4 MiB）。
  • 「双节点 16 卡」受 SSH 免密限制——集群仅 .12+.29 可用，无第三机；如未来 .10/.11 等开放，可补 8K/长序列多对验证。
