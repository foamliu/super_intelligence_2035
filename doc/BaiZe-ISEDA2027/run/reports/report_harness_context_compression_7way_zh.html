七大 Harness 上下文压缩（Compaction）机制横向对比

claude-code · cline · codex · deepseek-harness · hermes-agent · opencode · pi

生成日期：2026-10-23 | 每条结论均附 file:line 源码证据

摘要

本文对 7 个主流 AI Coding Harness 的上下文压缩（context compaction）机制进行源码级横向对比。每条结论均标注 file:line 证据，基于各 harness 实际仓库源码（非文档推断）。

核心发现：7 个 harness 的压缩策略可归为三大范式——

  • 单层 LLM 摘要（opencode、pi、cline-agentic、codex-local）：在阈值触发后调用模型生成结构化摘要，替换历史消息。
  • 多层级联（claude-code、hermes-agent）：先做模型无关的剪裁/微压缩（micro-compact），再视情况做全量 LLM 摘要，并带断路器防止抖动。
  • 插件化 + 模型无关优先（deepseek-harness、cline-basic）：先用确定性规则裁剪工具结果，仅在不足以降到阈值时才触发 LLM 摘要。

证据来源路径统一前缀：harness/<name>/，下文仅写相对路径。

2. 压缩策略详解（逐 harness）

2.1 claude-code —— 多层级联压缩

策略概述：claude-code 采用四层级联压缩，按代价从低到高逐级触发：

  1. 微压缩（MicroCompact）：清理旧工具结果与思考块，无需 LLM 调用。基于时间间隙触发（microCompact.ts:438-441），并在 API 层通过 clear_tool_uses_20250919 / clear_thinking_20251015 参数实现（apiMicrocompact.ts:16）。
  2. 自动压缩（AutoCompact）：LLM 摘要。阈值 = 有效上下文窗口 − 13,000 buffer（autoCompact.ts:62,72-76），有效窗口 = contextWindow − summary预留（autoCompact.ts:30,33-48）。
  3. 全量压缩（Compact）：摘要后保留 POST_COMPACT_TOKEN_BUDGET=50,000 tokens，最多恢复5个文件（5K/文件）+ 技能恢复（25K预算）（compact.ts:122-130）。摘要使用 <analysis> 草稿 + <summary> 结构。
  4. 反应式压缩（Reactive）：捕获 prompt-too-long 错误后触发（autoCompact.ts 反应式路径）。

防护：连续自动压缩失败 ≥ 3 次触发熔断（autoCompact.ts:67-70,260-264）；session memory / marble_origami 查询源跳过自动压缩以防死锁。

2.2 cline —— 双策略切换

策略概述：cline 提供两种内置压缩策略，通过 mode 字段切换：

  • basic 策略：纯确定性裁剪，不调用 LLM。工具结果截断至 2,000 字符（compaction-shared.ts:21），保留最近 20,000 tokens（compaction-shared.ts:19）。
  • agentic 策略：调用 LLM 生成对话摘要。目标压缩比 0.7（compaction-shared.ts:18），长对话降至 0.5（compaction.ts:89）。

触发逻辑：requestInputTokens >= maxInputTokens × 0.9（compaction.ts:318,323；compaction-shared.ts:17）。maxInputTokens 优先取模型 info，否则 contextWindow × 0.9（compaction-shared.ts:15,51-69）。

防护：overflowRecovery 强制使用 basic 策略（确定性优先），自定义压缩器失败时回退到 basic（compaction.ts:435-460）。

2.3 codex —— 多实现引擎 + 作用域控制

策略概述：codex（Rust 实现）提供三种压缩引擎，由 feature flag 与 provider 能力决定选用：

  • local（compact.rs）：LLM 摘要。摘要用户消息上限 20,000 tokens（compact.rs:61）。支持手动 / 自动 / turn 中三种触发场景。
  • token-budget（compact_token_budget.rs）：跳过模型摘要，直接安装全新上下文窗口（compact_token_budget.rs:22-25,47-51）。仍走完整 compaction 生命周期（hook + ContextCompaction 事件）。
  • remote v2（compact_remote_v2.rs）：服务端摘要，将压缩卸载到 API 侧。

触发逻辑：token_limit_reached = scope_tokens >= buffered_limit OR full_window_reached（context_window.rs:107-109）。作用域可选 Total（全量）或 BodyAfterPrefix（仅前缀之后的增量）（context_window.rs:61-80），通过 model_auto_compact_token_limit 配置（config/mod.rs:629）。

初始上下文重注入：turn 中压缩使用 BeforeLastUserMessage 模式，将初始上下文注入到最后一条用户消息之前（compact.rs:69-76,98-107）；turn 前/手动压缩使用 DoNotInject，下一轮自然重注入（compact.rs:63-67,166）。

摘要提示词：使用 SUMMARIZATION_PROMPT / SUMMARY_PREFIX（compact.rs:59-60,128,357），模板见 prompts/templates/compact/prompt.md（"CONTEXT CHECKPOINT COMPACTION" 交接格式）。

2.4 deepseek-harness —— 插件化 + 模型无关优先

策略概述：compaction-basic 作为可插拔包，采用"先剪裁后摘要"两阶段：

  1. 模型无关剪裁（toolResultPruner）：先执行确定性工具结果裁剪，无需 LLM。溢出场景与压力场景均先跑此步（index.ts:282-291,309-312）。
  2. LLM 摘要（compactRegion）：若剪裁后仍超阈值，选择可压缩区间并调用摘要模型。支持按 target model 配置独立的 summarizationProvider/Model（config.ts:161-162）。

触发逻辑：压力触发阈值 thresholdTokens = contextWindow × thresholdRatio，默认 thresholdRatio=0.8（config.ts:20,144；index.ts:305）。溢出触发绕过阈值直接压缩（index.ts:284-292）。

保留策略：保留区 retainTokens = contextWindow × retainRatio，默认 retainRatio=0.16（config.ts:23,145-147）。摘要 maxTokens 默认 8,192（config.ts:91）。

防护：重试循环最多 compactionRetries + 1 次，仍超阈值则抛异常（index.ts:316-332；config.ts:92）；溢出重试通过 WeakMap 追踪，idle/assistant 消息后重置（index.ts:168-178）。

2.5 hermes-agent —— 最复杂的多层级联

策略概述：hermes-agent（Python）集成了三层压缩，由多个 Mixin 组合实现：

  1. 微压缩（MicroCompactionMixin）：滚动单轮微摘要。每个 turn 结束时吸收一个完整 assistant+tool 交换到 rolling summary，按 cadence 门控（每 N 轮一次）（micro_compaction.py:39,205-222）。用户消息永不吸收（micro_compaction.py:70）。支持从 transcript marker 恢复 rolling summary（micro_compaction.py:50-62）。
  2. 主动剪裁（proactive prune）：模型无关的工具结果裁剪，在全量压缩前先跑。
  3. 全量压缩（compressor）：保护头部+尾部，LLM 摘要中间。头部 = system prompt + protect_first_n（首次压缩后衰减，防早期用户轮次固化）（context_compressor.py:4671-4678），尾部 = protect_last_n=20（context_compressor.py:2804）。摘要目标比 0.20（context_compressor.py:2805）。

触发逻辑：threshold_tokens = (context_length − max_tokens) × threshold_percent，下限 64,000（MINIMUM_CONTEXT_LENGTH），小窗口（<512K）时 threshold_percent 从 0.50 提升至 0.75（context_compressor.py:1150-1151,2755-2758,2769-2801）。

防护：反抖动断路器 _ANTI_THRASH_RECOVERY_SECONDS=300（context_compressor.py:2726）；结构性 no-op 退避 300s（context_compressor.py:2729）；仅 provider 确认的"无效压缩"才触发断路器（context_compressor.py:3020）；断路器到期后允许一次"probation probe"试探（context_compressor.py:3061,3082）。

2.6 opencode —— 单层结构化摘要

策略概述：opencode 采用单层 LLM 摘要策略，使用结构化 Markdown 模板生成摘要，并支持增量更新（将前次摘要与新对话合并）。

触发逻辑：estimate(request) > context − max(output, buffer)，默认 buffer=20,000（compaction.ts:12,237-241）。也支持 compactAfterOverflow 在 provider 错误后触发。auto 模式默认开启（compaction.ts:133）。

保留策略：select() 将对话分为头部（被摘要）+ 最近部分（原样保留），保留预算 DEFAULT_KEEP_TOKENS=8,000（compaction.ts:13,137-158）。工具输出截断 TOOL_OUTPUT_MAX_CHARS=2,000（compaction.ts:14）。摘要输出上限 SUMMARY_OUTPUT_TOKENS=4,096（compaction.ts:15）。

摘要模板：五段式 Markdown（Objective / Important Details / Work State / Next Move / Relevant Files）。另有 context-epoch 系统跨压缩快照/协调系统上下文（context-epoch.ts:46-77）。

2.7 pi —— 结构化 checkpoint + split-turn

策略概述：pi 采用单层 LLM 摘要，生成结构化 checkpoint。独特之处在于支持 split-turn 模式（将一轮对话拆分为 turn-prefix 摘要 + 历史摘要两部分）。

触发逻辑：shouldCompact = contextTokens > contextWindow − reserveTokens，默认 reserveTokens=16,384（compaction.ts:126-129,267-269）。也支持溢出触发 _runAutoCompaction("overflow")（agent-session.ts:3111-3113）。

保留策略：最近 keepRecentTokens=20,000 tokens 原样保留（compaction.ts:129）。摘要 maxTokens = min(0.8 × reserveTokens, model.maxTokens)（compaction.ts:712-714）。

三套提示词：

  • SUMMARIZATION_PROMPT — 首次结构化 checkpoint（compaction.ts:507）
  • UPDATE_SUMMARIZATION_PROMPT — 增量合并到已有摘要（compaction.ts:577）
  • TURN_PREFIX_SUMMARIZATION_PROMPT — split-turn 前缀摘要（compaction.ts:942）

防护：estimateProjectedContextTokens 处理 context_edit/compaction 后的 token 估算失效（compaction.ts:227-262）；跳过 aborted/error 消息的 usage 数据（compaction.ts:148-160）。

关键差异：

  • 固定 buffer vs 比例阈值：claude-code（13K）、opencode（20K）、pi（16K）用绝对 buffer；cline（90%）、deepseek-harness（80%）用比例。比例随窗口缩放，但小窗口下可能不足。
  • codex 独特性：唯一将阈值完全交给用户配置（config/mod.rs:629），且 token-budget 模式跳过 LLM 摘要（compact_token_budget.rs:47-52）。
  • hermes 自适应：小窗口（<512K）时 threshold_percent 从 0.50 提升到 0.75（context_compressor.py:1150-1151），避免频繁触发。

4. 保留 / 保护策略对比

4.1 claude-code —— 富信息恢复

压缩后保留 POST_COMPACT_TOKEN_BUDGET=50,000 tokens（compact.ts:124）。最多恢复 5 个文件（每文件 5K）+ 技能恢复预算 25K（compact.ts:122-130）。微压缩阶段清理旧工具结果与思考块（microCompact.ts:438-441）。

特点：最丰富的压缩后恢复——不仅保留摘要，还主动重注入最近编辑的文件内容和技能定义。

4.2 cline —— 双策略保留

basic 模式：工具结果截断至 TOOL_RESULT_CHAR_LIMIT=2,000（compaction-shared.ts:21），文件内容同样 2,000（compaction-shared.ts:22）。

agentic 模式：LLM 摘要替换历史，保留摘要 + 最近消息（agentic-compaction.ts:159-172）。

永不摘要最新用户输入（compaction-shared.ts:345）。

4.3 codex —— 三实现保留

local：LLM 摘要，CompactionStrategy::Memento（compact.rs:474）。

token-budget：跳过模型摘要，直接安装新窗口（compact_token_budget.rs:47-52）。可配 auto_compact_fallback_prompt（config_tests.rs:724）。

remote：服务端摘要（compact_remote.rs:53）。token-budget 是唯一"零 LLM 调用"压缩。

4.4 deepseek-harness —— 插件化剪裁优先

保留区 retainTokens = contextWindow × retainRatio，默认 retainRatio=0.16（config.ts:23,145-147）。摘要 maxTokens 默认 8,192（config.ts:91）。

独立的 compaction-tool-result-pruner 插件先做模型无关裁剪（compaction-tool-result-pruner/src/index.ts:4），剪裁不足才触发 LLM 摘要。

特点：确定性剪裁与 LLM 摘要解耦为独立插件。

4.5 hermes-agent —— 头尾保护 + 衰减

头部 = system prompt + protect_first_n（首次压缩后衰减，context_compressor.py:4671-4678）。尾部 = protect_last_n=20（context_compressor.py:2804）。摘要目标比 0.20（context_compressor.py:2805）。

首次压缩后 protect_first_n 衰减——防止早期消息永远不被摘要。

4.6 opencode —— 尾部保留 + turn 分割

DEFAULT_KEEP_TOKENS=8,000（compaction.ts:13）。工具输出截断 TOOL_OUTPUT_MAX_CHARS=2,000（compaction.ts:14）。摘要 SUMMARY_OUTPUT_TOKENS=4,096（compaction.ts:15）。

splitTurn 在 turn 内部找截断点，保持 turn 完整性（compaction.ts:140-158）。

4.7 pi —— 大保留窗口 + 增量摘要

keepRecentTokens=20,000 原样保留（compaction.ts:129）。摘要 maxTokens = min(0.8 × reserveTokens, model.maxTokens)（compaction.ts:712-714）。

保留窗口（20K）大于 opencode（8K），支持增量更新。

5. 摘要提示词模板对比

5.1 claude-code —— analysis + summary 双段

摘要提示词要求先在 <analysis> 标签做草稿分析，再在 <summary> 标签输出最终摘要（prompt.ts:24）。analysis 段是草稿区，formatCompactSummary 会剥离（prompt.ts:306-314）。禁止工具调用（prompt.ts:20-23）。

5.2 cline —— 可配 summarizer

agentic 模式下，摘要由可配置 summarizer 模型生成（agentic-compaction.ts:57,135-140）。summary 预算受 summarizer 输入限制约束（agentic-compaction.ts:159-172）。basic 模式不使用 LLM，无摘要提示词。

5.3 codex —— 可配 fallback prompt

local 模式使用内建摘要提示词（compact.rs:474 Memento 策略）。token-budget 模式支持用户配置 auto_compact_fallback_prompt（config_tests.rs:724），有长度校验（config_tests.rs:759）。

5.4 deepseek-harness —— checkpoint + compacted-summary

摘要包装在 <compacted-summary> 标签中（summarizer.ts:21-22）。规则要求保留精确文件路径、命令、错误字符串（summarizer.ts:61）。CHECKPOINT_PREAMBLE 指示后续模型将摘要视为已建立背景（summarizer.ts:69-71）。支持增量合并（summarizer.ts:65）。

5.5 hermes-agent —— 动态组装摘要提示词

摘要提示词运行时动态组装，支持首次摘要和增量更新（context_compressor.py:4051）。焦点引导放最后以确保优先级。

5.6 opencode —— PR 风格摘要

摘要提示词为纯文本文件 prompt/summary.txt："Summarize what was done... Write like a pull request description."（agent.ts:15,263）。限制 2-3 句，第一人称，不提及测试过程。

另有 context-epoch 系统跨压缩快照协调（context-epoch.ts:46-77）。

5.7 pi —— 结构化 checkpoint（最详细模板）

三套提示词：

  • SUMMARIZATION_PROMPT（compaction.ts:507）：六段式——Goal / Constraints / Progress (Done/In Progress/Blocked) / Key Decisions / Next Steps / Critical Context。
  • UPDATE_SUMMARIZATION_PROMPT（compaction.ts:577）：增量合并规则。
  • TURN_PREFIX_SUMMARIZATION_PROMPT（compaction.ts:942）：split-turn 前缀摘要。

要求保留精确文件路径、函数名和错误消息（compaction.ts:538）。

6. 已知缺陷与防护机制

6.1 claude-code

缺陷：1,279 个会话出现 50+ 次连续自动压缩失败（最高 3,272 次），全球每日浪费 ~250K API 调用（autoCompact.ts:66-67 注释）。压缩请求本身可能触发 prompt-too-long（compact.ts:462 CC-1180）。

防护：连续失败 ≥ 3 次熔断（autoCompact.ts:67-70）；prompt-too-long 时截断压缩请求（compact.ts:462）。

6.2 cline

缺陷：agentic 模式的 LLM 摘要调用可能超时（本项目 Terminal-Bench 评测中多次遇到 3600s 超时）。summarizer 无已知输入限制时使用保守预算可能导致摘要空间不足（agentic-compaction.ts:150）。

防护：溢出时强制降级为 basic 模式（确定性裁剪，无 LLM）；永不摘要最新用户输入（compaction-shared.ts:345）。

6.3 codex

缺陷：local 模式依赖模型可用性；remote 模式依赖服务端。

防护：token-budget 模式作为零 LLM fallback（compact_token_budget.rs:47-52）；compact_model_fallback.rs 提供 ContextLimit 降级（compact_model_fallback.rs:32）；fallback_buffer_tokens 可配（config_tests.rs:725）。

6.4 deepseek-harness

缺陷：重试循环可能耗尽预算。

防护：重试上限 compactionRetries + 1 次，仍超则抛异常（index.ts:316-332）；溢出重试通过 WeakMap 追踪（index.ts:168-178）；validateRatioRetention 确保保留比 < 阈值比（config.ts:181-188）。

6.5 hermes-agent

缺陷：不可压缩会话可能导致压缩循环（每 1-2 轮触发但无法降低体积）。

防护：反抖动断路器 _ANTI_THRASH_RECOVERY_SECONDS=300（context_compressor.py:2726）；结构性 no-op 退避 300s（context_compressor.py:2729）；仅 provider 确认的"无效压缩"才触发断路器（context_compressor.py:3020）；断路器到期后允许一次 probation probe（context_compressor.py:3061,3082）。

6.6 opencode

缺陷：摘要提示词本身可能溢出。

防护：摘要输出上限 SUMMARY_OUTPUT_TOKENS=4,096（compaction.ts:15）；compactAfterOverflow 在 provider 错误后触发（compaction.ts:133）。

6.7 pi

缺陷：context_edit/compaction 后 token 估算可能失效。

防护：estimateProjectedContextTokens 处理压缩后估算失效（compaction.ts:227-262）；跳过 aborted/error 消息的 usage 数据（compaction.ts:148-160）；split-turn 模式减少单次摘要压力。

7. 结合本项目教训与总结建议

7.1 本项目教训：cline Auto-compacting 超时问题

在 BaiZe 项目的 Terminal-Bench 2.0 横评中，我们使用 cline 作为 harness 之一（cline-patched）。实际评测中多次遇到 Auto-compacting 超时：当对话接近 maxInputTokens × 0.9 阈值（compaction-shared.ts:17）时，agentic 模式触发 LLM 摘要调用，但该调用在 3600s 会话限制内未完成，导致整个 trial 超时失败。

根因分析：cline 的 agentic 压缩需要一次完整的 LLM API 调用生成摘要（agentic-compaction.ts:57 policyIntent: "agentic_summary"）。在 Terminal-Bench 长任务中（多轮工具调用 + 大量代码上下文），待摘要历史很长，摘要调用本身输入 token 量巨大，导致 API 响应缓慢甚至超时。cline 没有 claude-code 的微压缩前置层（先清理工具结果再决定是否需要 LLM），也没有 hermes-agent 的反抖动断路器。

对比其他 harness：

  • claude-code：微压缩先清理工具结果和思考块（microCompact.ts:438-441），可能无需 LLM 就降到阈值以下。且有 3 次失败熔断（autoCompact.ts:67-70）。
  • codex：token-budget 模式完全跳过 LLM 摘要（compact_token_budget.rs:47-52），直接安装新窗口。API 受限时最稳健。
  • deepseek-harness：先跑模型无关的 tool-result-pruner（compaction-tool-result-pruner/src/index.ts:4），剪裁不足才触发 LLM 摘要。
  • hermes-agent：微压缩每 N 轮滚动吸收一个 assistant+tool 交换（micro_compaction.py:39），分散压缩压力。

改进建议：① 在 Terminal-Bench 评测配置中，将 cline 压缩模式设为 basic（确定性裁剪，无 LLM 调用），避免摘要超时；② 或增加 cline 摘要调用 timeout 配置；③ 长期看，cline 应借鉴 claude-code 的微压缩前置层和 hermes-agent 的反抖动断路器。

7.2 总结

三大范式回顾：

  • 单层 LLM 摘要（opencode、pi）：实现简单，但每次压缩都需要一次完整 LLM 调用，长任务下可能成为瓶颈。pi 的 split-turn 模式和增量更新是有效缓解措施。
  • 多层级联（claude-code、hermes-agent）：先做低成本操作（微压缩/剪裁），再视情况做 LLM 摘要。claude-code 的微压缩 + 富信息恢复 + 熔断器最完善；hermes-agent 的滚动微压缩 + 反抖动断路器最精细。
  • 模型无关优先（deepseek-harness、cline-basic、codex-token-budget）：先用确定性规则裁剪，仅在不够时才调用 LLM。codex token-budget 模式完全跳过 LLM，是 API 受限场景的最稳健选择。

选型建议：

  • 长任务自动化评测（如 Terminal-Bench）：优先选 basic/token-budget 模式（cline-basic、codex-token-budget、deepseek-harness tool-result-pruner），避免 LLM 摘要超时。
  • 交互式编码：claude-code 的微压缩 + 富信息恢复体验最佳；hermes-agent 的滚动微压缩对长会话最平滑。
  • API 受限 / 离线场景：codex token-budget 模式（零 LLM 调用）或 cline basic 模式（纯确定性裁剪）。
  • 结构化摘要需求：pi 的六段式 checkpoint 模板最详细，适合需要精确恢复任务状态的场景。
