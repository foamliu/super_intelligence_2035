三、ETA 测算

3.1　测算口径与基准

吞吐基准：613,992 tok/s（#792 实测，commit 594c9cb1b，报告 report_pretrain_seq16k32k_throughput_zh.html §5 · E1）。该实测档 = 16K / CP1 / DP16 / 关 graph / FP8 tensorwise / 真实数据 / tok-step=4,194,304 / step-time 6,831.2 ms / peak 75.2 GB / 0 NaN，恰好等同 S2 与 Decay 的 4M tok/step 配置。

两口径：①「纯训练」= 总 token ÷ 613,992；②「含故障/checkpoint 预留」= 纯训练 × (1 + 预留率)。预留率取 10% / 15% / 20% 三档（覆盖 checkpoint 写盘、偶发故障重启、中间 eval 暂停、跨节点 IB 抖动等）。

⚠️ 2026-10-26 运维令 22:0x 勘误：S1 的 ETA 不再用 613,992 那一档。#792 的 613,992 tok/s 是在 gbs256（4M tok/step）档实测的，恰为 S2/Decay 配置；S1 当前档 = gbs128（2M tok/step），21:40 实测稳态仅 ≈400–510K tok/s（中位 ~480K）。归因（双点求解）：固定每步开销 F ≈ 2.57 s（optimizer step + grad-allreduce barrier + dataloader/prefetch 落定 + kernel-launch 尾），纯计算吞吐 C ≈ 984K tok/s；gbs128 下 F 占步时 55% ⇒ 446K，gbs256 下 F 占 38% ⇒ 614K —— 差额主要落在「固定每步开销摊薄」，非计算/通信/数据效率问题。

四、商榷点与建议

4.1　S1 2M tok/step 吞吐：已实测 ~480K（2026-10-26 22:0x 运维令，归因已给出）

实测：S1 gbs128（2,097,152 tok/step）21:40 稳态 step time 4.09 / 4.87 / 5.20 s ⇒ ≈400–510K tok/s（中位 ~480K），仅为 #792 gbs256 基线 613,992 的 65–83%。

归因（双点求解，无需 nsys）：以 gbs256→613,992 tok/s（6.831 s/step）与 gbs128→~446K（~4.7 s/step）两点解 t = F + tok/C ⇒ 固定每步开销 F ≈ 2.57 s（optimizer step + grad-allreduce barrier + dataloader/prefetch 落定 + kernel-launch 尾），纯计算吞吐 C ≈ 984K tok/s。gbs128 下 F 占步时 55%（⇒446K），gbs256 下 F 占 38%（⇒614K）。613K→480K 的差额主要落在「固定每步开销摊薄」，非计算效率/通信扩展/数据瓶颈。GPU 实测 per-step 分解（nsys / Megatron timers step 50–200）待 data 线恢复 l1_en_hq 后补，用于确认 F 内部各子项占比。

方案三选一（已预置，待运维裁定 + smoke 验证）：

  • A（推荐，已预置）：S1 gbs 128→256（=4,194,304 tok/step，与 #792 E1 同档），步数 700k→350k，总 token 1.468T 不变 ⇒ 预期 ~614K / 27.7 天。落地：GBS=256 ITERS=350000 bash code/baize-llm/scripts/train.sh s1（configs/s1.env 的 GBS/ITERS 已改为 ${VAR:-default} 可 env 覆盖）。「放弃 S1 小 batch 阶段」的取舍 = warmup 已处理早期稳定性，accum16 对 2.2B AdamW 在稳定区间，无 loss-descent 硬理由保留 gbs128 —— 由运维否决权裁定。
  • B：保持 gbs128，压固定开销（--overlap-grad-reduce/--overlap-param-gather/--use-distributed-optimizer 已在 recipe 开；dataloader workers/prefetch、NCCL env 逐项调）—— F≈2.57s 中通信/barrier 占比待 nsys 确认后逐项压。
  • C：gbs=192（3,145,728 tok/step）测一档，连 2.1M/3.1M/4.2M 三点画 tok/s 曲线。

验收：稳态（step 50–200 中位）≥ 600K tok/s（≥0.98×613,992）。达不到 ⇒ 沿用 ~480K / 35.4 天（§3 已同步）。红线：不开 CUDA Graph（16K 下崩到 ~110K）；tok/mb/GPU ≤16,384；FP8 tensorwise 不改；不许用「更多 token/step」冒充提速（验收看 tok/s）。

4.2　LR 与优化器：已定案（2026-10-26 用户直令，不再商榷）

三项定案：① 优化器 = AdamW（--optimizer adam）；② WSD 的 D 段 = exponential 指数衰减；③ 监控 = TensorBoard 监听 .29:6006。落地代码见 code/baize-llm/（§五）。

WSD 释义：① 2000 步线性 warmup 到 1e-3 → ② 保持 1e-3 跨 S1+S2 稳定段 → ③ Decay 段 20,000 步按指数降到 1e-4。

D 段公式（唯一口径）：令 p = (iter − 1,050,000) / 20,000 ∈ [0,1]，则

lr(p) = peak × (min_lr / peak) ^ p = 1e-3 × (0.1) ^ p

验收：python code/baize-llm/scripts/lr_schedule.py --peak 1e-3 --min 1e-4 --decay-iters 20000 --total-iters 1070000 的输出必须与 TensorBoard 的 learning-rate 逐点吻合（相对误差 ≤0.1%）。

实现前提：launcher 需支持 --lr-decay-shape exponential；若 --help 里没有，按 code/baize-llm/docs/LAUNCHER_PATCH_EXP_DECAY.md 打补丁（新增一个参数 + 一个分支，默认 linear 不影响历史实验）。

其余注意点：① 1e-3 在 2.2B / AdamW 下属偏激进的上界（本项目 decay 参考实验 1113.sh 用 muon + decoupled-lr 1e-2），开跑后前 2,000 步须盯 loss/gnorm，异常则降到 5e-4；② 2000 步 warmup = 4.0B token，对 2.2B 偏短但可接受，若早期不稳可加到 5000 步；③ min_lr 固定 0.1×peak = 1e-4（与 1113.sh 的 1.04e-4 同量级）。

4.3　数据配比 epochs<1 的采样语义

S1/S2 多个数据集 epochs<1（Math-L3=0.72、Code-L3=0.87、en_v1_4=0.81、Math-L1=0.85）。语义：在 2.8T 全程内，该集每个文档平均被采样 < 1 次 ⇒ 有 14%–28% 的数据从未被模型见过。

权衡：

  • 对海量主体数据（en_v1_4 0.81）epochs<1 是合理的——数据足够多，单遍即足。
  • 对稀缺高价值数据（Math-L3 仅 0.72、占比 0.02）epochs<1 = 部分难题从未训练到，可能浪费稀缺资源。建议对 Math-L3 / Code-L3 这类高难度集适当提升 epochs（如 ≥1.0），或在小 prop 下用「过采样 + 重复去重标识」确保全覆盖。
  • prop 与 epochs 是耦合的（epochs ≈ prop × 总token / 集大小）；若想提升某集 epochs，要么提 prop（挤占他集）要么接受更长总 token。建议在 §2.2 表基础上做一次「目标 epochs → 反推 prop」的配平。

4.4　Decay 阶段 SFT/Agent 占比 0.72 的合理性

Decay 段 80B token 中 SFT(0.60)+Agent(0.12)=0.72，预训练态数据仅 0.28。这是「以指令数据退火（instruction annealing）」策略，与 Phi 系列「末段注入教科书/SFT 数据」思路一致，能显著提升下游指令跟随与 Agent 能力。

风险与建议：

  • 退火窗口短：Decay 仅 2.78% 总 token，72% 的 SFT 影响被压缩在末段——若 SFT 数据质量不均或分布偏移大，可能在 LR 衰减中引入能力骤降（参考本项目 v2 decay 训坏先例）。
  • 建议分段：把 Decay 20k 步再切为「前半 0.4 SFT 比例 + 后半 0.85 SFT 比例」，让 base 能力先稳后退火，降低一次性倾斜风险。
  • 保留 base 评测基线：Decay 前（S2 末）存 ckpt 并跑 CS8/CX6 eval，与 Decay 后对比，量化「退火收益 vs base 损失」。
  • SFT-2605 / Agent-2609 去重与质量：0.60+0.12 的体量需确认两集已去重、无 prompt 泄漏、无安全/风控问题（本项目禁令：不绕过验证/风控）。

4.5　总计耗时与 GPU 预算

核心约束：纯训练 54.3 天、含预留 ~65 天，16×H100 连续占用 ~2 个月、~2.5 万 GPU·h。

  • 连续性风险：2 个月级单集群连续占用，故障/重启几乎不可避免 ⇒ 必须有可靠的断点续训（ckpt 频率建议 S1/S2 每 5000 步一存 ≈ 8.6 GB/次、Decay 每 1000 步），并验证 resume loss 无跳变（本项目 P-8 resume 闭环已验证可用）。
  • 分阶段决策点：S1（26 天 / 1.4T）跑完是一个天然评估闸门——建议 S1 末存 ckpt + 全量 eval（CS8/CX6/scaling-law 外推），评估达标再启 S2，避免一次性 commit 2 个月预算。
  • 资源争用：本集群与 vision/data/harness 共用 NFS 与部分节点；长任务期间需与各线协调 GPU/IO 时段（吞吐实测已要求无争用干净测量，长训练同理需避免 IO 抖动）。
  • 预算对照：本项目 2B 超参搜索阶段单次 ~44B token（P-8）；本计划 2.88T 是其 ~65 倍，是真正的「正式预训练」量级，资源量级需运维/用户拍板。

5.6　Checkpoint 策略（用户补令：每 2,000 步一个）

三阶段 --save-interval 统一改为 2,000 步：S1 350 个、S2 175 个、Decay 10 个。按实测体积（torch_dist 模型态 ≈4.4GB/个；含 Adam 状态 ≈30GB/个）全量保留分别需 1.54TB / 10.5TB（S1），会挤压数据迁移与后续训练的空间。

配套保留策略（code/baize-llm/scripts/prune_ckpts.sh，默认 dry-run）：保留最近 3 个 + 每 25,000 步一个里程碑 + latest_checkpointed_iteration.txt 指向的那个（永远保护）。S1 收敛到 ≈31 个（4.4GB 口径 ≈136GB / 30GB 口径 ≈930GB）。

执行节奏：每 20k 步跑一次 dry-run，每 50k 步执行一次 --apply；红线 = /nas_train 可用低于 15TB 时立即清理并上报。

5.7　RoPE / 1M 位置（用户补令 2026-10-26）

要求：56 层中 4 层全注意力（其余 24 Mamba2 + 28 MLP）的 RoPE max embedding position = 1M。落地口径 = rope_theta = 1e6（ABF）+ max_position_embeddings = 1,048,576（2^20）。

为什么不能只改 max_pos：本项目 2026-10-06 的 B1 实验实测——只把 max_position_embeddings 从 4096 抬到 131072、rope_theta 仍为 1e4 ⇒ cos/sin 高频分量溢出 ⇒ 全 NaN（连 4K 都 NaN）。同一实验里 ABF_1e6（max_pos=1048576 + theta=1e6）可用：4K / 128K / 1M 的 PPL = 83.24 / 54.66 / 55.42。故本次两个参数必须同改。

实现落点：训练期真正生效的是 --rotary-base 1000000（Megatron 逐位置算 RoPE）；max_position_embeddings 只在导出 HF/SGLang 的 config.json 生效。因此「训练能跑」≠「配置达标」，必须走导出后校验。

验收：① train.sh --dry-run 命令里出现 --rotary-base 1000000（launcher 不支持该参数时脚本拒绝开跑，不许静默退回 1e4）；② 导出后用 python scripts/check_rope.py --hf-dir <dir> 校验 56 层 / attention=4 / max_pos=1048576 / theta=1e6 / rope_scaling=None；③ 前 500 步 loss 与 baseline 对照抬升 ≤5%、0 NaN。

已知代价：既有实测的 +10.5%（4K PPL 83.24 vs 75.36）是「在 4K 训练的 ckpt 上事后换 theta」的税；本计划从头训练、theta 初始即 1e6，不背这笔税，但仍需盯早期 loss。

5.8　长上下文：ABF 与「为此做好准备」（用户补令 2026-10-26）

口径：产品目标 = 1M（用户 2026-10-26 明确：「产品目标自然是长上下文 1M，要不为啥预训练就用 16K 这么长」）。训练从 16K 起步，使 16K→1M 的外推倍数只有 64×（4K→1M 是 256×）；路径 = 16K 主训练 → 阶梯 32K/64K/128K(/256K) → ABF 外推 1M。现实约束：16 卡最多训到 256K（CP16/DP1），1M 原生训练需 ≥64 卡（CP64）。

为什么 ABF 而不是裸抬 max_pos / 纯 PI：B1 实测三组对照——baseline（θ=1e4）只能 4K；maxpos_only 全 NaN；ABF（θ=1e6）在 32K/128K/256K/512K/1M 的 PPL = 58.55 / 53.34 / 52.99 / 55.81 / 55.42，全程无退化。ABF 的代价是训练长度上的轻微退化（4K +10.5%），而本计划从零训练、θ 初始即 1e6，不背这笔税。

已备好的三件工具：① scripts/abf_plan.py —— θ_ABF 公式 + 16 卡可行性（CP/DP/gbs）表；② scripts/check_longctx_data.py —— 按 EOD(129280) 切分统计「≥32K / ≥128K 文档覆盖的 token 占比」，防止「长序列其实是跨文档拼接」；③ scripts/longctx_ladder.sh —— 32K→64K→128K 阶梯扩展，逐级 0 NaN / 吞吐门禁、累计 iters 续跑。
