一句话结论：方案 F（同 run 热切换 blend 权重）在 stock Megatron 中不可行——BlendedDataset 无权重更新 API（blended_dataset.py:65-97），索引在构造时一次性预计算并缓存。若以「checkpoint resume + 新 blend」实现同 run 切换，重叠特性与 D+E 完全等价（非零重叠）。因此 D+E 仍为首选，F 降为 fallback；D+E 的 ~12% 重叠属未量化假设（无实测），剩余风险 = 需 S2 启动后抽样验证。

§0 零重叠方案（含新增方案 F + §0.1 修正）

0.1 修正：v3 §0.1 表述的限定条件

v3 原文：「S2 如果使用与 S1 相同的 7 个数据源且不修改随机种子，则 S2 将以 ~83-100% 的概率重复采样 S1 已看过的文档」
修正：该结论仅在「重开 run（新训练进程 + 新 blend 构建）」前提下成立。同一 run 内若不重建 dataloader、游标沿 shuffle_index[K:] 继续前移，则本身零重叠——但此时无法改变 blend 权重（比例不变）。
根因：改变比例 ⇒ 必须重建 BlendedDataset ⇒ 新 dataset_index（blended_dataset.py:97）⇒ 游标归零 ⇒ 可能重叠。「想换比例」与「想零重叠」存在根本矛盾——不重建则不能换比例；重建则游标归零。v3 未区分这两种情形，导致 §0.1 表述被误读为普适结论。

0.2 方案 F 核查：同 run 内切换配比

F = 前 350k 用 S1 blend，之后在同一 run 内切到 S2 blend。

核查 1 — GPTDataset 能否热更新 blend 权重？
→ 不能。BlendedDataset.__init__（blended_dataset.py:65）在构造时调用 self._build_indices()（blended_dataset.py:97）一次性预计算 dataset_index 与 dataset_sample_index。权重 self.weights（blended_dataset.py:82）被烘焙进 unique_description_hash（blended_dataset.py:95，MD5 of JSON 含 weights），决定 .npy 缓存文件路径。类中无 setter、无 update 方法——改权重 = 新 hash = 新索引文件 = 必须构造新对象。__getitem__（blended_dataset.py:112）只读预计算数组，不接受运行时权重变更。

核查 2 — 重启 dataloader 时能否保留 shuffle_index / sample_idx 游标？
→ 不能（对不同 blend）。MegatronPretrainingRandomSampler（samplers.py:222）用 consumed_samples（samplers.py:235）计算 epoch = consumed_samples // active_total_samples（samplers.py:263）和偏移 current_epoch_samples = consumed_samples % active_total_samples（samplers.py:264）。
• 若 blend 变了：total_samples 变（samplers.py:232）→ epoch 计算错位 → 游标无法对应到新 blend 的正确位置。
• 若 consumed_train_samples 不重置（loaders.py:185 传给 sampler）：sampler 在新 blend 索引空间跳过旧消耗量 → 浪费 S2 数据且不防重叠。
• 若重置为 0：从新 blend 排列起点开始 → 共享源同种子 → 83-100% 重叠（与「重开 run」无异）。
• GPTDataset._build_document_sample_shuffle_indices（gpt_dataset.py:381）生成的 shuffle_index 是静态预计算排列，缓存于 .npy；不同 num_samples（因 weight 变）→ 不同 hash → 不同排列 → 游标无法跨 blend 映射。

核查 3 — 结论
→ 热更新不可行（核查 1：BlendedDataset 无 API）；重启保留游标不可行（核查 2：total_samples 变 → epoch 错位）。
→ 唯一零重叠路径 = 不改 blend（但比例不变，无法实现 S1→S2 课程）。
→ 若接受「checkpoint resume + 新 blend + 重置 consumed=0」：重叠 = D+E（新源 0% + 旧源换种子 ~30%），与 D+E 等价，无额外收益。
→ 若要真正零重叠 + 换比例：需自定义 Megatron 改造——在 BlendedDataset 中实现权重热更新 + 跨 blend 游标映射（保留共享源的 shuffle_index 游标，仅重建 dataset_index）。非 stock 功能，开发量 ~2-3 人日，本时间线不推荐。

0.4 D+E 重叠声明的诚实性标注

「~12% 可接受」属未量化假设：v3 给出 ~12% 总重叠但无任何实测证据。该数字来自理论估算（新源占比 ~28% × 0% + 旧源占比 ~72% × ~30% ≈ ~22%，再按实际 token 权重加权后约 12%）。实际重叠率取决于 shuffle 种子碰撞，需 S2 启动后抽样实测。但当前 Megatron 无跨 run 消费追踪（核查 2 已证）→ 实测需开发。结论：12% 是合理估计但非实测值，报告与论文中应标注「理论估算」。

§1 S1→S2 接力：LR / Optimizer / 是否重开 run

WSD 调度（optimizer_param_scheduler.py:259-266）：warmup 0-2k（线性 0→1e-3）→ stable（num_steps ≤ wsd_anneal_start_ 时 coeff=1.0，LR=max_lr 恒定）→ decay 末段（exponential）。S2（350k-700k）完全在 stable 阶段 → LR 恒定 1e-3，无需重新 warmup。

Optimizer state：Adam β1/β2 动量从 checkpoint 加载 → 延续不重置。num_steps 从 checkpoint 恢复 → LR scheduler 从 step 350k 继续。

两种 resume 方式：

  • 方式 ①（checkpoint resume + 新 blend）：在 350k ckpt 基础上改 data_paths/blend TSV → resume。optimizer + LR 连续，仅 dataloader 重建。论文可声称「单次 700k 连续训练」（权重/优化器/步数连续）。
  • 方式 ②（新 run from 350k ckpt）：独立训练进程 load 350k ckpt。需显式 --lr-warmup-iters 0（跳过 warmup）。同样连续但叙事弱于 ①。

推荐：方式 ①。改 blend TSV + 清 .npy 缓存 + 设 SEED=5678 → resume。LR/optimizer 连续性不受数据切换影响——这比数据重叠更能影响最终指标，v3 一字未提，v4 补全。
