🔴 L2 诊断结论（P0 · 2026-11-11 · 160k v3 结果）

GSM8K = 0.0%（strict + flexible）@ 160k（671B tok，15× P-8） — 判定：真能力问题，非配置错误。
维度证据指向
strict-match=0%模型从未产生 "The answer is X" 正确格式 → 格式生成能力缺失能力
训练量极低P-8 仅 44.4B tok（当前 160k=671B，15×）→ 早期 ckpt 生成能力必然弱能力(早期)
L1 正常同期 L1=48.01%(loglikelihood 正常) → 模型加载/权重/分词无误排除配置
stop tokenseval log: until:['Question:','</s>','<|im_end|>'] → 标准，无误排除配置
实际输出curl 直查 160k llama-server：模型输出 "The answer is 5 years old3335431111..." → 尝试答案格式但内容错误，随后退化为重复"1"×200+，finish_reason=length能力(数学)
数据配比P-5b/P-8 主体=Ultra-FineWeb-L3（网页文本），无显式数学/代码数据 → 数学推理能力必然弱数据配比
结论：GSM8K=0% 是真能力问题，根因是训练数据缺乏数学/代码内容。
① 模型有基本生成能力（产生 "The answer is..."）但数学内容完全错误；② 退化为重复"1"是小型模型在未见过的推理模式上的典型行为；③ L1(loglikelihood)正常说明模型权重/加载无误；④ stop tokens/few-shot 配置均标准。
建议（写进 MEMORY 待用户拍板）：① 后续训练阶段增加数学/代码数据配比（参考 MiniCPM/DeepSeek 的 code+math 占比 15-30%）；② 或在 post-train SFT 阶段补数学推理能力。

🔴 L3 可行性分析（2026-11-11 · P0 调研结论）

维度发现影响
基础设施TB 用 Harbor Docker 容器 + gw_proxy + 7 个 agent 适配器(cline/codex/hermes/...)。适配器硬编码 cloud API endpoint (http://agi-gateway.cxmt.com/v1) 和 model name (glm-5.3-flash)。改用本地模型需修改 _base.py 的 TB_BASE_URL/TB_MODEL/TB_API_KEY + 重建 Docker 镜像。中等工作量
服务化CPU llama-server 可服务但 agentic 多轮交互极慢(~30s/轮)。GPU vllm/sglang 需要 GPU 窗口(训练占满)。需 GPU 窗口
模型能力定性测试(160k llama-server)：发送 "Write a Python function to check if a number is prime" → 模型输出 "The following are the answers111111111..." → 退化为重复字符，无法生成连贯代码🔴 根本性障碍
与 L2 一致性GSM8K=0%(数学退化重复) + 代码生成退化 → 同一根因：训练数据缺 code+math。Agentic 任务需多轮工具调用+代码生成，2B base model 在当前训练阶段不可能完成。🔴 同 L2 根因
结论：L3 评测在当前阶段(base 2B @ 160k)不可行——不是基础设施问题，而是模型生成能力根本不足。模型在任何需要连贯多步生成的任务上都退化为重复输出。
建议：L3 延后至 ① post-train SFT 后(模型有基本指令跟随能力) 或 ② pretrain 增加 code+math 数据后。基础设施(GPU 服务化 + Docker 适配)可在模型能力达标后 1-2 天内完成。
