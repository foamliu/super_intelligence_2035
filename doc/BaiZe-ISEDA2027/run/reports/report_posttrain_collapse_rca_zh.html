一句话结论：run2/3/4「各仅 1 条 execution_result、Pass@1=0.0%」是评测管线的 bug，不是模型 degenerate collapse。核心根因：eda_fastmcp 抽取脚本 format_cline_cli_output.py 使用共享相对临时目录 ./pyAether-eval/temp/pyAether_code，并在每次调用开头 shutil.rmtree 清空它；当 36.15 上有多个 eval 并发时，互相踩踏导致本 run 已写到 code/<task>/pyAether_code/ 的真实 .py 被丢弃（run2 丢 43/44、run3 丢 36/37、run4 丢 43/43）。次因：posttrain 5-run 链脚本旧逻辑 ls -dt|head -1 抓陈旧 output_evaluation → run4 复用 run3 评分产物（sha256 字节相同）→ run4 INVALID。8 题回补验证 PASS：绕过共享 temp、把 8 个真实 .py 喂给 run_eval，assemble 出 8 脚本 → 沙盒产 8 条 execution_results（1/8 pass），满足「≥8 条」判据。

2. 四个异常的逐一解释（含证据）

异常 A：completed=158 行但 execution 只有 1 行 —— run_eval 的「有效生成」判定在哪？

run_eval.py 把一个 task 计为「有效生成（gen_success）」的判据是 completion 字段非空且不为 "pass"： 
run_eval.py:570   info.get("completion", "").strip() not in ("", "pass")   # 有效生成
run_eval.py:577   info.get("completion", "").strip() in ("", "pass")       # 无效（gen_fail）
run_eval 读的「generations 文件」是 completed_code_generation_<batch>.jsonl（经 patch_config() 写入 config.yaml 的 generations_file: 字段，见 run_eval.py:145-148）。该文件由 Step6 complete_code_generation.py 产出，恒 158 行（为 158 题逐行补全）。run2 该文件里 157 行 completion="pass"、仅 1 行是代码 → gen_success=1 → execution_results=1 行。158 行是「补全后的全量占位」，不是「158 个有效生成」。

异常 B：completion 多为 "pass" —— 谁写的？语义？和 run_eval 读的是同一个吗？

关键区分：存在两个名字相近、但完全不同的文件。

  if task_id in completion_tasks and status == "success":

所以 "pass" = 「Step5 没抽到这个 task 的代码」，不是「session 通过」。run1 的 attribution 副本 158 行全 "pass"（0 行代码），但 run1 gen_success=36 —— 因为 attribution 副本与 run_eval 实际读的 generations 文件不是同一份（run1 的真实 generations 文件 36 行有代码，已在 36.15 被清理；attribution 副本是错拷）。MEMORY 早期「run1 全 pass→0 行代码」的读法混淆了这两个文件。

异常 C：唯一被执行 task run2=003 / run3=107 / run4=107 —— 为什么恰好这 1 个？

这 1 个不是「模型只写出 1 个」，而是共享临时目录 race 下唯一幸存到 code_generation_<batch>.jsonl 的那 1 个 .py。实测（36.15）： 
run2 batch code/ 下 44 个真实 .py（全部 mtime ≤ 14:17:31）；
  但 code_generation_2026_1115_110506.jsonl（Step5产物，mtime 14:17:31）只有 1 行 = task 003。
run3 batch code/ 下 37 个真实 .py；code_generation_2026_1115_144001.jsonl 只有 1 行 = task 107。
run4 batch code/ 下 43 个真实 .py；code_generation_2026_1115_183438.jsonl = 0 字节（被踩更彻底，一个都没剩）。
extractor 读的目标路径是对的（code/<task>/pyAether_code，format_cline_cli_output.py:165）；44/37/43 个 .py 当时都在那。它们被丢是因为 extractor 先把 .py 拷进共享 temp 再从 temp 读 jsonl，而共享 temp 被并发进程清空了（见第 3 节）。

异常 D：codegen_rejection_stats.json run2/3/4 是 0 字节（run1 是 1573B）

codegen_rejection_stats.json 是 posttrain 链脚本侧从 cline session 日志聚合的 PreToolUse hook 拒绝统计（非 eda_fastmcp 产出；写入者：posttrain_attribution_trace_analysis.py / baize_posttrain_zhulong_baseline_5run_chain.sh 等）。run1 的 1573B 内容：rejected_total=1304（run_commands 1048 / read_files 103 / get_api_details 41 …），即 08:1x 令提到的「PreToolUse 禁 run_commands」的设计性拒绝。run2/3/4 为 0 字节 = 该聚合步骤对这几个 batch 没产出（链脚本 trace 分析未跑通 / session 日志未找到），是链脚本侧的次要缺陷，不是 0% 的原因（0% 的原因是异常 A/C 的共享 temp race）。底层拒绝数据仍存在于各 batch 的 cline session 日志中。

3. 根因：管线 bug，不是模型 collapse

3.1 主因 —— 共享临时目录 race（eda_fastmcp format_cline_cli_output.py）

# format_cline_cli_output.py:155-157  (process_cline_gene_files)
    temp_path = "./pyAether-eval/temp"
    pyAether_code = "./pyAether-eval/temp/pyAether_code"      # ← 共享、相对路径
    shutil.rmtree(pyAether_code, ignore_errors=True) or shutil.os.makedirs(pyAether_code)  # ← 每次先清空

# format_cline_cli_output.py:95  (format_cli_gene_code2jsonl)
    pyAether_code = "./pyAether-eval/temp/pyAether_code"      # ← 同一个共享路径
流水线 Step5 分两段：先把 code/<task>/pyAether_code/*.py 拷进共享 temp，再从共享 temp 读出写 jsonl。该 temp 是 项目级共享、相对 CWD（=eda_fastmcp 根）的固定路径，且 process_cline_gene_files 开头 shutil.rmtree 清空它。当 36.15 上同时有 ≥2 个 eval 在跑 Step5（posttrain 链 + zhulong 自身 eval / 其他用户 eval），后启动者的 rmtree 会清空前者的拷贝 → 前者从 temp 读到空/残缺 → jsonl 只剩 0~1 个文件。

证据链：

  • run2 batch code/ 下 44 个真实 .py，全部 mtime ≤ 14:17:31（format 运行时刻），format 理应全部抽到；但 code_generation_2026_1115_110506.jsonl 只有 1 行。（36.15 实测 find + stat）
  • extractor 读的是正确路径 code/<task>/pyAether_code（format_cline_cli_output.py:165），不是早先 MEMORY 猜的 ws/pyAether_code（实测仅 1 个 task 有 ws/ 子目录）。→ 推翻「ws vs no-ws」假说
  • 36.15 上有并发 run_cline_script.sh 实时运行（PID 3245417，-p 4 -n，5 个 run_cli.sh worker）；且 batch 2026_1115_110406 在 run2（110506）前 1 分钟启动 —— 并发是常态。
  • run1=18.99%（gen_success=36）恰恰是因为它跑得早/并发少，共享 temp 未被踩；run2/3/4 跑在并发窗口内 → 被踩 → 1 或 0。

3.2 次因 —— 链脚本陈旧拷贝（run4==run3）

posttrain 5-run 链脚本旧逻辑用 ls -dt ~/eda_code_eval/*/ | head -1 抓「最新」batch 目录配对 eval；当某 run 的 eval 未产生新 output_evaluation 时，会抓到上一个 run 的目录。run4 自身 codegen 抽取=0（共享 temp 被踩空），其 eval 又复用了 run3 的 generations 文件 completed_code_generation_2026_1115_144001.jsonl： 
sha256(run3/final_report.json)        = 74eacea2...3e1f93
sha256(run4/final_report.json)        = 74eacea2...3e1f93   ← 字节相同
sha256(run3/execution_results.jsonl)  = 374bf0ca...0422b
sha256(run4/execution_results.jsonl)  = 374bf0ca...0422b   ← 字节相同
→ run4 INVALID（无论看自身 codegen=0 还是看 eval=run3 复用，都不能作数）。

4. 修复

4.1 主因修复（eda_fastmcp 侧，需 zhulong 协调应用）：把共享 temp 改成按 batch 隔离的临时目录，消除 rmtree 互相踩踏。建议 diff（示意，不改 eda_fastmcp，交 zhulong）： 
# process_cline_gene_files(cli_output) 内
-    pyAether_code = "./pyAether-eval/temp/pyAether_code"
+    _bid = os.path.basename(cli_output.rstrip("/"))          # batch_id
+    pyAether_code = f"./pyAether-eval/temp/pyAether_code_{_bid}"   # 隔离
# format_cli_gene_code2jsonl 同步接收该 pyAether_code 路径作参数（不再写死相对路径）
# main() 把隔离路径同时传给两个函数
4.2 即时可用的回补 wrapper（已写好，不改 eda_fastmcp）：run/rca_recover_extract.py 在 run_cline_script.sh 跑完后，直接从 code/<task>/pyAether_code/（及 ws/pyAether_code/）重新抽取 .py 写回 generations jsonl，完全绕过共享 temp，再喂 run_eval。（注：本工具早先 docstring 写的「ws vs no-ws」机理已被本次取证推翻，但其「直接读 code/<task>/pyAether_code」的实际行为对当前共享-temp 丢码同样有效，作为 post-pipeline 回补成立；docstring 待更正。）
4.3 次因修复（已应用）：链脚本 baize_posttrain_zhulong_baseline_5run_chain.sh:86-117 已改为「按 final_report.json 的 generations_file 字段精确匹配 batch↔eval」，不再 ls -dt|head -1 抓陈旧目录；无匹配则标 INVALID-noeval 不拷陈旧。bash -n 通过。

6. 结论与纪律

根因定性：管线 bug（共享 temp race + 陈旧拷贝），不是模型 degenerate collapse。
• run2/3/4 的 0.0% 不可作为模型能力结论；模型在 run2/3/4 batch 实际产出了 44/37/43 个真实 .py（真实「生成」率 ≈ 28%~34%），被共享 temp 丢弃。
• 5-run mean 在 RCA 结论前不得引用；5run_zhulong_baseline_interim.json（n=4 mean=4.75%±8.22%）含 3 个被踩坏的 run，无效。
• run1=18.99%（30/158，gen_success=36）是当前唯一可信的单 run 数；但它是单 run，不是 5-run mean。
• 下一步：① 经 zhulong 应用 4.1 隔离 temp（或用 4.2 wrapper 回补）→ ② 用修好的链脚本（4.3 已改）重跑 5-run → ③ 与 run1 同表对比，得到可信 5-run mean。

取证均在 36.15（hfeg0tedaap02）经 3333 隧道实测；产物全部保留，未删任何 trace；未 kill 他线（vision/zhulong/pretrain）；本轮未起新 5-run。隧道/沙盒/端点在取证期间实测可达（sandbox 端口 8650-8654 返回 405=POST 可用）。
