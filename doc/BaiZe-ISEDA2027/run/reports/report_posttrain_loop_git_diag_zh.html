二、整改：把 git_sync_and_push() 换成 worktree 隔离

2.1 旧实现三处硬伤 → 新实现

位置旧实现（硬伤）新实现（worktree 隔离）
L66git pull --rebase --autostash origin main（运维协议 §4 禁项：共享树 rebase→别线冲突）共享树不再 rebase；rebase 只发生在隔离 worktree 内（git -C "$WT" rebase origin/main），不动共享 index/HEAD
L94git push origin main（共享树直推，origin 被各线前进→non-ff 必拒）detached worktree 内 git -C "$WT" push origin HEAD:main（fast-forward，含 5 次 fetch+rebase 重试）

2.2 为什么选 vision_line_commit.sh 模式（而非 ops/git_line_commit.sh）

用户令给出二选一。本报告选择镜像 run/vision/vision_line_commit.sh（已在 .17 上经 wake#1688 起每轮验证可用、merge-base --is-ancestor 复验通过）的模式，把逻辑内联进 baize_posttrain_loop.sh 的 git_sync_and_push()。理由：

  • 已验证可用：vision 线自 2026-11-19 wake#1688 起每轮用该模式推送，git merge-base --is-ancestor 复验均通过，零 index.lock 事故。ops 通用版 run/ops/git_line_commit.sh 据运维 22:1x 令未在 .17 上跑过。
  • 白名单更全：ops 版 posttrain 白名单缺少 run/bpt_*·run/posttrain_*·run/rca_*·run/reports/report_posttrain_*·reports/archive/posttrain/*，不满足本 08:4x 令要求的 glob 段；内联实现可一次性纳入全部 13 段。
  • 自包含：内联进目标文件，posttrain loop 不依赖跨线路径（vision/ 目录一旦被别线移动即失效）。
