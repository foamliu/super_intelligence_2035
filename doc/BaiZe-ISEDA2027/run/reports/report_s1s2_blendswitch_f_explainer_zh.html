方案 F 科普 · S1→S2 数据配比热切换（零重叠）

撰写：BaiZe Data Agent · 2026-11-22 · 面向不熟悉分布式训练的读者
代码证据：blend_switcher.py + CPU 验证 · base commit 14c215dc · v4/v5 报告保留不删

一页看懂（三句话）
① 为什么会重叠？ 换数据配比必须重建索引，索引一重建，"读到哪了"的书签就被扔掉、从头重读，于是把 S1 已经读过的旧数据又读了一遍——这就是"重叠"。
② 方案 F 解决什么？ 给每个数据源单独留一张书签，切换配比后，共享的旧源从书签处继续往后读、新源从头开始，做到零重叠 + 换比例两全。
③ 现在到哪一步？ 实测 CPU 验证 7/7 全通过：零重叠=0、比例偏差 0.0087%、关掉开关与原版逐字节一致。估算 对照组 D+E 的 ~12% 重叠尚未实测。真实训练尚未切换，预计切换点 ≈ 11-28。

§1 背景科普：先搞懂五个词

这份报告讲的是"训练到一半，怎么换数据配比又不重复读旧数据"。在看技术细节前，先用大白话把核心术语讲清楚——每个词首次出现都会带一个生活类比。

1.1 blend（配比混合）= 按比例混合几桶米

白话：训练语料不是一个巨大文件，而是好几个"数据源"（网页、代码、数学题…）按各自比例混在一起喂给模型。类比：就像煮饭时把白米、糙米、糯米按 74:19:7 混到一口锅里。这个"比例"就是 blend（配比）。改比例 = 换配方。

1.2 shard（分片）= 把一大桶米分成小袋

白话：每个数据源太大没法一个文件装下，所以被切成很多小份，每份叫一个 shard。类比：一桶 100 斤的米太重，分成 100 袋每袋 1 斤，一袋一袋取。

1.3 epoch（轮次）= 把一本书从头翻完一遍

白话：把所有数据从头到尾完整读一遍叫一个 epoch。BaiZe 的 S1+S2 加起来还不到一遍。类比：1000 页的书从头翻到尾 = 一个 epoch。只翻了前 350 页 = 还不到一个 epoch。

1.4 shuffle（打乱）= 把书页打乱顺序再读

白话：训练前会把数据顺序随机打乱，得到一串固定的"阅读顺序表"。只要种子一样，每次打乱结果完全相同——这正是重叠问题的根源。类比：把 1000 页书拆散重排成乱序版再读。同一把"种子"排出的顺序永远一样。

1.5 游标（cursor）= 书签，记录读到哪了

白话：游标是一个整数，告诉你"当前读到第几条数据了"。训练中断后恢复靠它。类比：夹在书里的书签——今天读到第 350 页，夹个书签，明天从 351 页继续。方案 F 的核心创新就是给每个数据源单独夹一张书签，而不是只有一张"总书签"。

1.6 S1→S2 课程学习：训练到一半换配方

BaiZe 的 70 万步预训练分两阶段，好比先打基础再提高难度：

  • S1（0→35万步）：网页为主、代码次之、数学较少。配比 Web 74% / Code 19% / Math 7%——先打"通用语言能力"基础。
  • S2（35万→70万步）：代码和数学占比大增，并引入全新数据源（stack-v3 代码、MegaMath 数学等）。配比 Web 40% / Code 40% / Math 20%——"加难"。

关键：这不是"训练完重启"，而是同一次训练中途换配方——模型权重、优化器、学习率都连续不断。难点就在：怎么在不停训练的情况下把配比从 74/19/7 换成 40/40/20，又不重复读旧数据？

§2 为什么难：换比例 ⇔ 游标归零 ⇔ 重读旧数据

问题的根源可以用一句话概括："想换比例"和"想零重叠"存在根本矛盾。"

矛盾链条（配 stock 真实行为）：
  1. 想换比例 → 必须重建 BlendedDataset 的索引。
    blended_dataset.py:86 调用 _build_indices()，:97 把权重烘焙进 dataset_index 数组——这个数组是一次性预计算好的"阅读计划表"。
  2. 重建索引 → 游标（书签）归零。新索引从头开始，consumed_samples 被重置为 0。
  3. 游标归零 → 从头重读。由于 shuffle（打乱）用的是同一个种子（seed=1234），新索引的打乱顺序和 S1 完全一样——所以 S2 从第 0 条开始读，读到的还是 S1 已经读过的那些文档。
  4. 结果：S2 把 S1 读过的旧文档又读了一遍 = 重叠。

用代码说话——stock 的 MegatronPretrainingRandomSampler（samplers.py:222-264）用全局游标算进度：

epoch = consumed_samples // active_total_samples　（samplers.py:263-264）

这句的意思是："总共读了多少条 ÷ 每轮多少条 = 读到第几轮了"。问题在于：重建索引后 consumed 归零，于是 epoch=0，模型从第一轮的第一条重新开始——而因为种子一样，第一轮的内容和 S1 完全相同。这就是 v4 报告认定的 "epoch 错位根因"。

图 3：stock 原版换配比时，S2 从第 0 条重新开始读（游标归零），因为打乱种子一样，读到的文档和 S1 完全相同，形成红色重叠区。

§4 方案 F 原理逐步图解（全文重点）

方案 F 的核心思想可以用一句话说清："给每个数据源单独夹一张书签，换配方时不扔书签。" 下面分三步讲清。

第 1 步：权重热更新——换配方但不扔阅读顺序表

stock 原版的 dataset_index（"阅读计划表"）是一次性算好、烘焙死的。方案 F 新增 update_weights() 方法：切换时用新配比重新算一张 dataset_index，但不重建每个源内部的 shuffle_index（打乱顺序表）。
gpt_dataset.py:381 的 shuffle_index 是一个静态排列（无重复的 0 到 N 的打乱），只要种子不变，S1 和 S2 用的是同一张打乱表——这正是"从断点继续"的前提。

第 2 步：per-source 游标映射——每个源一张书签（核心创新）

为什么按"源"记进度，而不是记"总进度"？
因为不同源的读取速度不同。比如 S1 配比下，网页源 en_v1_4 权重 0.65（占比最大），代码源 code_l2 权重 0.15——训练每走 100 步，en_v1_4 被读了约 65 次，code_l2 只读了约 15 次。如果只记一个"总共读了 50000 条"的全局游标，你根本不知道这 50000 条里 en_v1_4 读了多少、code_l2 读了多少——没法把全局进度映射回每个源的断点。

方案 F 的做法：维护一个数组 consumed_per_source[s]，记录每个源 s 各自读了多少条。切换时，对共享源令 new_cursor[s] = consumed_per_source[s]（在新配比的打乱表中从该位置继续前移），新源从 0 起。总游标不复位。

§8 常见问题（FAQ 5 条）

Q1：会重复读同一批数据吗？

不会（实测）。方案 F 给每个共享数据源单独夹了书签（per-source 游标），切换后从书签处继续往后读。CPU 验证 7 个共享源的 overlap_docs 全部 = 0。数学保证：shuffle_index 是无重复排列，[0, 已读) 和 [已读, 已读+S2量) 是不相交的两段。唯一例外：如果某源读超过一整轮（epoch），会回绕产生重叠——但 BaiZe 所有源的 S1+S2 消费量都不超过一轮，不会触发。

Q2：新数据从哪开始？

从第 0 条开始。S2 新增的数据源（stack-v3、MegaMath、Nemotron-CC-Math、finemath）在 S1 阶段完全不参与，没有"书签"，所以切换后从头读。这些新源的 S1 消费量 = 0，跟任何旧数据天然没有交集，重叠 = 0（实测，见验证第 4 项 new_source）。

Q3：关掉开关会怎样？

跟 stock 原版逐字节完全一致（实测，见验证第 3 项 flag_off_equivalence）。开关 --blend-hot-switch 默认就是关的。关掉后：①update_weights() 永不被调用 ②BlendHotSwitchRandomSampler 永不被实例化 ③checkpoint 不加任何新字段。训练行为、数据顺序、checkpoint 格式与不改代码的 stock Megatron 完全相同。这就是"安全开关"的意义——不想要新功能，关掉就回到了原版。

Q4：为什么不用"换种子（seed）"来避免重叠？

换种子确实能让 S2 的打乱顺序跟 S1 不同，看似不重叠。但问题在于：换种子后 S2 从第 0 条开始读，读到的是不同的随机文档——虽然不是"同一条"，但仍然是从 S1 已经读过的文档池里重新抽样。因为 S1 还不到一个 epoch（没读完所有文档），S2 从头读还是会碰到 S1 读过的文档，只是碰到的具体是哪几条不同了。换种子减小了重叠比例但无法做到零重叠。方案 F 的 per-source 游标映射才是唯一能做到严格零重叠的方法——它不是"换个随机起点"，而是"从 S1 停下的确切位置继续"。

Q5：怎么自己复跑验证？

第 1 步：进入目录 run/data/blendswitch/
