4.4 FLOPs交叉验证

  • 总FLOPs = 6 × N × T = 6 × 2.22e9 × 1.5e12 ≈ 2.0 × 10²²
  • 8×H100 bf16 dense peak = 8 × 989 TFLOPS = 7.912 × 10¹⁵ FLOPS
  • 249K tok/s反推 MFU = 6 × 2.22e9 × 249K / 7.912e15 ≈ 41.9%
  • FLOPs口径（6ND, 同MFU）→ 33.2天
  • ⚠️ 两个口径差2.1×：token口径含SSM scan/通信/优化器/packing，FLOPs的6ND只算dense matmul（Mamba2 scan/conv不计入）。结论以token吞吐口径（69.7天）为准。

6. 长上下文注入（ABF）

6.1 注入方案 = ABF（不是YaRN），分两层

推理侧（零训练）：

  • rope_theta 1e4 → 1e6
  • max_position_embeddings 4096 → 1,048,576（1M）
  • 沿用 baize_b1_longctx_extend.py 的 B1 写法
  • 既有实测：PPL 4K=83.24 → 128K=54.66 → 1M=55.42，全程53–56 无退化
  • 机制：56层里只有4层full_attention吃RoPE，Mamba2层无位置编码 ⇒ ABF只需适配4/56层 → hybrid相对dense的结构性优势

训练侧（真正注入）：

  • ABF免训练只保PPL，不产生needle/多跳检索能力（B1已证passkey 0%）
  • 1M能力必须在长上下文续训阶段用真实长文档训练，不能只靠配置外推

6.2 ABF vs YaRN 对比

方案代价收益结论
ABFPPL@4K +10.5%（75.36→83.24）免训练到1M；零依赖（改config）✅ v5采用
YaRN需rope_scaling参数对只4层attention的hybrid收益有限仅作对照/兜底
仓库既有结论：hybrid应沿用B1的ABF写法，dense才需YaRN/rope_scaling（ARCHIVE_OPERATOR_PRETRAIN.md）。

6.3 次序评估：decay → 1M → SFT/RL

段评估理由
decay在1M前✅ 合理先让Stable段收敛（LR从1e-3降下来），再进长上下文
1M在SFT/RL前✅ 合理对齐阶段样本要"装得进"上下文，长上下文能力必须先具备
长上下文 = 预训练的一部分⚠️ 要求用pretraining数据（长文档/代码库/多文件仓库），不是SFT数据

裁定：✅ 采纳 decay → 1M → SFT/RL

6.4 风险与对策

风险对策
1M吞吐崩塌（attention ~77%, 1M PPL单次172s）seq课程：32K→128K→256K→512K→1M阶梯；每档token预算；"ABF外推+只在128K训练、1M靠外推"降本方案
decay后LR已低，长上下文学不动长上下文阶段单独设LR（小幅回升，需用户批准，不得擅改）
SFT/RL前无能力门禁必须做needle/RULER/长文档QA门禁，不达标不进SFT

6.5 1M阶段独立ETA（单列，不与1.5T Stable混算）

  • seq课程预算 [假设]：32K(50B) + 128K(100B) + 256K(50B) + 512K(20B) + 1M(10B) = 230B tok
  • 吞吐估算：1M阶段attention占比高，吞吐预计降至 30–80K tok/s [假设]
  • 粗估时长：230B / 50K = 4,600,000s ≈ 53天 [假设，待实测修正]

附录：可行性问题正面回答

Q1: LR 1e-3 恒定是否会欠拟合？

  • 历史对照：P-8用3e-3（44B发散后换1e-3 AdamW重启）；decay run用1.67e-3→1e-5
  • 判断：1e-3介于P-8（3e-3）和decay min（1e-5）之间，合理但偏保守。1.5T token量大，恒定LR可能在S2后半段收敛放缓
  • 监控判据：每2000步记录loss；若S2后半段（步370K+）loss仍单调不降→建议在S2末端加短decay（需用户批准）

Q2: batch 从2M跳到4M怎么处理？

  • seq 4096 / MBS 2时：2M tok → GBS 488（grad accum 31）；4M tok → GBS 976（grad accum 61）
  • per-step时间：8.0s → 16.1s（@249K）
  • 切换记录：S1最后一个ckpt的loss vs S2第一个ckpt的loss（断点监控）

Q3: en_v1_4 数据量够吗？

  • 需500B tok，全量≈2.2T tok（6.75T bytes）。500B = 全量的23%
  • 当前：85/110 shard已下（≈4.1T bytes ≈ 1.3T tok），已下部分就够500B
  • 前置：续传25 shard（proxy .23→hf-mirror 200 ✅）+ 分词500B tok。分词吞吐未知→需实测补ETA

Q4: S2 混料供给够吗？

  • code 200B：UltraData-Code 411B ✅（余量2.06×）
  • math 10–20B：UltraData-Math 303B ✅（余量15–30×）
  • HQ 780–790B：ultraweb_en(1.12T) + l1_en_hq(152B) + zh(112B) + UltraX(31B) = 1.415T ✅（余量1.82×）
  • 瓶颈 = HQ预训练（余量最低1.82×，但充足）
