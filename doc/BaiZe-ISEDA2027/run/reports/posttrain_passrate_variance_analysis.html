1. 概述

本报告对 posttrain 基线 5 次运行（EDA-Eval-PyAether-158, 158 任务）的通过率剧变进行深度归因分析。五次运行的通过率从最低 4.43% 到最高 59.49%，跨越 13 倍。经分析，通过率剧变由 两个独立因素 共同导致：

  1. 代码提取格式 Bug（基础设施层）：format_cline_cli_output.py 脚本路径不匹配，导致 Run1-2 仅能提取约 25% 任务的代码进行评测，大量可正确通过的任务被"隐形跳过"。
  2. 代码生成质量波动（模型层）：同一模型、同一配置下，不同运行批次生成的代码质量差异巨大。Run2 批次出现大量语法错误和 API 幻觉，代码生成成功率仅 19.6%，而 Run3-5 批次接近 100%。
核心发现：Run2 是"双重异常值"——同时受格式 Bug 和代码生成质量崩塌两个因素影响。修复格式 Bug 后（Run3-5），通过率稳定在 56.96% ± 2.19%，方差仅 3.8 个百分点。

4. 通过率剧变原因分析

4.1 Run1 → Run2: 模型非确定性 (18.99% → 4.43%)

4.1.1 基本情况

4.1.2 原因分析

Run1 和 Run2 均使用旧版格式提取脚本，因此格式 Bug 不是两者差异的原因。两次运行的区别完全来自 模型代码生成质量的非确定性波动。

任务级对比（11 个重叠任务）：

结果任务数占比

Run1 通过 & Run2 失败981.8%
Run1 失败 & Run2 通过00%
两次均失败218.2%

在 11 个重叠任务中，Run1 通过的 9 个任务在 Run2 全部失败，而 Run2 没有任何一个任务能"翻盘"通过。这说明 Run2 的代码质量出现了 系统性退化，不是个别任务的随机波动。

错误类型对比：

  • Run1 的 6 个失败任务：5 个断言失败（代码能运行但逻辑错），1 个类型错误——属于"正常失败"。
  • Run2 的 36 个失败任务：9 个语法错误（SyntaxError）+ 12 个属性错误（AttributeError，模型幻觉了不存在的 pyAether API）——合计 21/36 = 58% 是"代码根本无法运行"的硬性错误。
结论：Run1 → Run2 的通过率下降（18.99% → 4.43%）是 纯模型非确定性 导致的。同一模型、同一配置下，Run2 批次生成的代码出现了大量语法错误和 API 幻觉，代码质量系统性退化。这与格式 Bug 无关——两次运行都受同一格式 Bug 影响，但 Run2 的代码本身就更差。

4.2 Run2 → Run3: 格式Bug修复 + 代码生成质量恢复 (4.43% → 59.49%)

4.2.1 两个独立变化

Run2 到 Run3 之间发生了 两个独立变化，共同导致了通过率的 13 倍跃升：

变化影响贡献估计

② 代码生成质量恢复生成成功 31/158 → 158/158约 +21 个新通过任务

4.2.2 格式提取 Bug 详解

Bug 描述：format_cline_cli_output.py 脚本在提取 cline agent 生成的代码时，查找路径为 code/<task>/ws/pyAether_code/*.py。但 zhulong agent 实际将代码写入 code/<task>/pyAether_code/*.py（无 ws/ 中间层）。

Bug 影响：当 cline agent 恰好在工作目录中创建了 ws/ 子目录时，代码能被找到；否则代码被"隐形跳过"，任务不会进入评测。

Run格式脚本评测任务数占 158 比例被跳过

Run2旧版4327.2%115
Run3修复版158100%0
Run4修复版15698.7%2
Run5修复版15799.4%1

修复方式：在 format_cline_cli_output.py 中添加 fallback 路径：当 ws/pyAether_code/ 不存在时，查找 pyAether_code/（无 ws/）。

被跳过任务的通过率：以 Run3 为参照，Run2 因 Bug 跳过的 115 个任务中有 68 个在 Run3 中通过（59.1%）。Bug 不仅减少了评测任务数，还 系统性低估 了模型的真实能力——被跳过的任务中有近六成是可以通过的。

7.3 Run2 异常根因推测

Run2 批次（2026_1117_143628, 生成于 11/17 14:36）的代码生成质量崩塌（19.6% 成功率, 9 个语法错误）可能由以下因素导致：

  • 模型服务状态波动：反向隧道 18096→.17:8096 在该时段可能不稳定，导致推理质量下降
  • 并发干扰：记忆记录显示该时段存在 posttrain agent 冲突（cline PID 1967844），可能影响了 cline agent 的工作环境
  • 磁盘空间压力：/home 分区当时已达 94%，可能影响 cline agent 写入临时文件
  • 纯模型非确定性：小模型（2B 参数）在特定 prompt 上的输出方差较大，可能在某些批次中出现系统性退化

由于缺乏该时段的模型服务日志和 cline agent 详细运行日志，无法确定具体根因。但 Run3-5 的稳定性（CV=3.8%）表明这是一个 偶发事件，而非持续性问题。

8. 建议

8.1 短期

  • 引用修复后基线：论文中使用 56.96% ± 2.19%（3-run）作为 posttrain baseline，不包含 Run1-2
  • 补充 Run6：再跑 1-2 次确认基线稳定性，使 std 更可信（3-run 的 std 统计效力较弱）
  • 记录模型服务日志：在后续运行中记录模型推理延迟、token 吞吐量等指标，以便检测类似 Run2 的异常
  • 增加代码生成质量检查：在 Step 5-6 之后增加语法检查（如 py_compile），及时检测语法错误率异常

8.2 中期

  • 分析 37 个翻转任务：这些任务是提升 Pass@1 的关键发力点。分析其失败模式（是 API 知识缺失、逻辑错误、还是边界条件处理不当？），针对性改进 SFT 数据
  • 分析 49 个稳定失败任务：这些是模型能力不足的硬骨头。按错误类型分类，评估哪些可通过更多训练数据解决，哪些需要更强的推理能力
  • 降低 API 幻觉率：Run3-5 中仍有 11-14 个属性错误（AttributeError），说明模型对 pyAether API 的知识不够准确。可在 SFT 数据中增加更多 pyAether API 使用示例

8.3 评测管道改进

  • 代码提取路径检查：在 format_cline_cli_output.py 中增加日志，记录每个任务的代码提取路径（ws/pyAether_code/ 或 pyAether_code/），便于审计
  • 评测覆盖率检查：在 Step 7 后增加检查：评测任务数 / 总任务数 应 ≥ 98%，否则报警
  • 语法错误率监控：如果某次运行的语法错误率 > 5%，标记为"异常运行"并触发排查
