▍ 结论（ROOT CAUSE · rev2）
吞吐 5.4× 骤降的根因是 tok/microbatch/GPU = mbs×seq ≥ 16384 导致单卡激活显存顶满 ~80GB HBM，进入 memory-bound；与序列长度无关、与批几何(gbs/accum)无关、与每步总 token 数无关。

一句话铁律：tok/mb = mbs × seq。≤ 12288 → 峰值显存 < 70GB、余量 ≥ 10GB → 维持基线 606,449 tok/s（84% MFU）；≥ 16384 → 峰值显存 81.1GB 顶格（reserved 74GB / max-alloc 69GB / 余量 ~6GB）→ MFU 崩到 13% → 每 token 耗时 5.4×。

决定性证据：11 格单变量阶梯（脚本 baize_seqlen_control_test.sh，结果表 pretrain_rc_ladder_20261026.tsv）。三组同 tok/mb=12288 的格（seq=4096/mbs3、seq=12288/mbs1、seq=6144/mbs2）全部 ~600K 快；七组同 tok/mb=16384 的格（seq 从 1024 到 16384、mbs 从 1 到 16）全部 ~108–121K 慢且峰值 81.1GB。序列长度在 1024↔16384 间扫遍，慢/快完全由 tok/mb 决定，与 seq 无关。

处置：seq=8192 用 mbs=1（tok/mb=8192）即可满速 605K tok/s = 1.00× 基线（「8K 满速配方」，已复测达标 ≥0.7× 门槛）。seq=16384 须上 context-parallel CP=2/4 把单卡有效 tok/mb 压回 ≤12288，或开 --recompute-activations 降激活显存（配方变更组，单列）。

一、问题与实验设计

原始 6 格 seq×tok/step 扫描（cfg1–6）观测到 seq≥8192 吞吐崩 5×，初步归因为「序列长度效应」。rev1 用 cfg0a（固定 seq=4096、复刻小批几何）复现 5.2× 跌幅后改归因为「批几何→GPU 饥饿（H4）」。但 rev1 仍是双变量混淆：cfg0a 同时改了 seq（保持 4096）和 mbs（3→4），即 tok/mb 从 12288 跳到 16384 —— 真正的变化量没被隔离。

rev2 的运维令（23:0x 通宵攻坚）要求单变量隔离：固定配方 DP16/TP1/PP1 + FP8 tensorwise + CUDA Graphs + 真数据（与双机 e18 基线字节级一致），唯一变量 = tok/mb = mbs × seq。设计 11 格阶梯覆盖 tok/mb ∈ {8192, 12288, 16384}，每个 tok/mb 用 2–4 个不同 (seq, mbs) 组合交叉验证，以排除 seq 与批几何的独立效应。

三、显存证据：为什么是 memory-bound

关键观测：所有慢格的峰值显存都精确顶在 81,08x MiB（≈80GB HBM 上限），所有快格的峰值显存都 < 70GB。这不是巧合——激活显存 ∝ tok/mb（每 microbatch 每卡的 token 数），因为全激活驻留（未开 --recompute-activations）。

E5a16,38469.4 GB74.1 GB81.1 GB

max-alloc 随 tok/mb 单调递增：42.8 → 56.0 → 69.4 GB。tok/mb=16384 时 reserved 74GB、距 80GB 上限仅 ~6GB 余量 → 顶格。

memory-bound 的机制链

  1. tok/mb ↑ → 每 microbatch 激活张量 ∝ tok/mb 驻留显存
  2. tok/mb=16384 → max-alloc 69GB + 碎片/临时 → reserved 顶 74GB
  3. allocator 接近上限 → 频繁 cache reclaim / sync / 可能触发隐式重算路径
  4. HBM 带宽被显存搬运/同步占用，有效计算带宽骤降 → MFU 84%→13%
  5. 每 token 耗时 = 1/0.13 ÷ 1/0.84 ≈ 5.4×

当前生效 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True；未开 --recompute-activations（全激活驻留 ⇒ 激活显存 ∝ tok/mb 是顶格直接来源）。

为何 81GB 是「顶格」而非巧合：H800 单卡 HBM = 80GB（可用 ~79GB 扣系统）。七组 tok/mb=16384 的格峰值全部 81,07x MiB（差异 < 8 MiB，仅 alloc 对齐），说明 PyTorch caching allocator 已把显存用到极限——任何进一步分配都触发 reclaim。而 tok/mb=12288 的格峰值 67–69GB，余量 ≥10GB，从不顶格。顶格与慢一一对应，是 memory-bound 的直接物证。

五、三版归因的演进与证伪

v1「seq/SSM 超线性」（#779/#781）

主张：seq≥8192 → attention/SSM 超线性变慢。

证伪：E5a(seq=2048 最小)仍慢 112,739；E3(seq=12288)却快 617,269。seq 在 1024↔16384 间扫遍，慢/快与 seq 无关。

证据：TSV E5a/E5b/E3 行。

v2「批几何→GPU 饥饿」（#782 / rev1）

主张：小批几何（小 gbs/accum）→ GPU 饥饿、低 MFU。

证伪：E2 用同样小批（gbs256/accum16，tok/step 仅 2.1M）却 605K @ 84% MFU 快。cfg2/cfg4(tok/step=4.19M≈基线)仍慢 ⇒ 「tok/step≥4M 回到 500-600K」预言破产。

证据：TSV E2/cfg2/cfg4 行。

v3「tok/mb ≥ 16384 → 显存顶格 memory-bound」（rev2 · 本报告）

主张：tok/mb = mbs×seq ≥ 16384 → 单卡激活显存顶 80GB HBM → memory-bound → MFU 84%→13% → 5.4×。

确认：11 格中 7 个 tok/mb=16384 格全慢全顶格 81.1GB；4 个 tok/mb≤12288 格全快全 <70GB。max-alloc 42.8→56.0→69.4 GB ∝ tok/mb 单调。无反例。

6.3 配方变更组（cfg5/cfg6 32K OOM 重试，单列）

  • --recompute-activations（selective recompute）：省 ~60% 激活显存，仅 ~5% 额外开销。可把 tok/mb=16384 的激活显存从 69GB 降到 ~28GB ⇒ 预期解除顶格。recompute 重测为本报告下一步。
  • --use-distributed-optimizer：把优化器状态分片到 DP 维，省显存换通信。对激活显存（主因）无直接帮助，属次要杠杆。

七、处置建议

  1. seq=8192 立即可用：用「8K 满速配方」（mbs=1/accum=16），已 1.00× 基线验证。无需任何额外配置。
  2. seq=16384：单卡 mbs=1 必慢（memory-bound）。二选一：① 上 CP=2（单卡有效 tok/mb=8192，预期满速，smoke 待跑）；② 开 --recompute-activations（降激活显存，重测待跑）。
  3. seq=32768：单卡 OOM。须 CP≥4 或 --recompute-activations+CP 组合。
  4. 判据铁律（写入任务书）：tok/mb = mbs×seq ≤ 12288 安全；= 16384 顶格慢；> 16384 OOM。规划任何 seq 时先算 tok/mb。

八、方法论警示

双变量混淆是本次两版错误归因的共同根因。v1 在调 seq 时同步改了 gbs/accum；v1→rev1 的 cfg0a 在「固定 seq」时又同步改了 mbs（3→4），把 tok/mb 从 12288 偷偷推到 16384。真正隔离变量的做法 = 固定 tok/mb、扫 (seq, mbs) 组合——这正是 rev2 的 11 格阶梯所做的。今后凡涉及吞吐的扫描，必须先写明「单变量是什么」，并交叉验证（同一变量值用多个不同组合复现），否则任何观测到的「效应」都可能是混淆伪迹。这是比本次根因更重要的教训。
证据可复现性：所有 11 格由脚本 baize_seqlen_control_test.sh 串行跑出，结果表 pretrain_rc_ladder_20261026.tsv（逐格一行，LADDER COMPLETE @ 01:13:39）。每格原始日志 /tmp/baize_rc_ladder/<格>/{master,worker}.log + worker.peakmem。ms/step 直接取自 Megatron elapsed time per iteration (ms) 日志行。显存快照取自 Rank0 after 10 iter 的 torch.cuda.memory_summary 等价查询。
