# POSTTRAIN_ENV_ATTRIBUTION_SPEC.md — 「3.04% → 15.82%」≈5× 跳升归因 + prompt 迭代规格

> 下发：运维 2026-11-14 19:2x（用户直令）。**引用处**：`BAIZE_POSTTRAIN_TASK.md` 顶部令。
> **用户原话**：「请 posttrain 分析一下这 ≈5 倍跳升从何而来。既然 MCP 工具一样，难道差异仅仅来自于系统 PROMPT 的差异吗？如果系统 PROMPT 差异这么大，那么看看 trace，是否还能继续优化系统 PROMPT 来提分？」

---

## 0. 这条线在干什么（先对齐职责，2026-11-14 用户订正）

**posttrain 是「文本/脚本能力线」**：基模 `minicpm5-2b` → 在 **EDA-Eval-PyAether 158** 上测基线通过率（写 PyAether 脚本的能力）→ 走 **SFT / RL 域适配** → 通过率**显著提升**。

`designflow` 是**做 benchmark 的线**（造题/判分），**不**产模型能力结论；`vision` 是**多模态能力线**（agent + VQA MCP）。

**那为什么还要做这个归因？** 因为 posttrain 的结论是「SFT/RL 带来显著提升」，这句话只有**基线可复现**时才成立。现在同一基模（`minicpm5-2b-sft` / step105）在同一批 158 题上出现了 **3.04%（.17 测法）vs 15.82%（36.15 测法）** 的 5× 差异 —— 若测法不统一，后面任何「SFT 后 +X pp」都可能只是换了 harness。

**所以本任务的第一性目标 = 把评测口径钉死**，让「基线 → SFT → RL」三段可比；归因（prompt / 沙盒 / RAG）是达成这个目标的手段。

## 1. 先纠正一个前提：3.04% 与 15.82% 之间不是「只差一个 prompt」

`3.04%`（.17）与 `15.82%`（36.15 run1）之间**同时变了四件事**，因此现在**不能**把 5× 归给系统 prompt：

| 变量 | .17（3.04%） | 36.15（15.82%） |
|:--|:--|:--|
| **V1 系统提示** | `eval_sys_prompt_template_no_sandbox.md`（**明写「本场景无沙箱，内部推演是唯一逻辑校验」**） | sandbox 版（承认沙盒、要求自测） |
| **V2 RAG 后端** | 本地 MCP `:18888` 内置 search_apis | 原生 `pyAether_MCP_server:8090` |
| **V3 沙盒** | 实际可达（dual-nix-tunnel），但**提示词否认其存在** | `eda_flow:18891` 直连，提示词承认 |
| **V4 网络/延迟** | 模型本地（.17 GPU6:8096） | 模型经反向隧道 .17:8096 → 36.15:18096，**延迟更高** |

同模型（`minicpm5-2b-sft-v39-final`）、同 158 题、同协议（Pass@1 / 2500s / `-p 8 -n`）。

## 1. 已有证据（先读，别重查）

来自 `reports/report_posttrain_pyaether_rca_v2_zh.html`（旧环境 790 题-运行）：

- 工具调用：检索 **5,544** + 沙盒 `run_code` **507** + `submit_and_exit` **13,699（91.77% 报错）**。
- **只有 9.88%（72/729）的题-会话真正走过「检索→执行→修错」**。
- 头号失败 = **degenerate pass 479/790 = 60.63%**（空操作/无效实现却被判过）。
- **507 次 `run_code` 中 236 次（46.55%）**，其前一条 assistant 文本含「infer/reason/verify/assume/推测/推演/假设」⇒ 模型在「提示说别执行」与「环境能执行」之间**摇摆**。
- 报告原话结论：prompt 矛盾没有让模型完全放弃工具（确实调了 507 次），但**显著抑制了「执行」**。

**由此得到的待验假设**：5× 的主因可能是 **prompt 与环境的自相矛盾关闭了「执行→报错→修正」反馈回路**，而不是 prompt 措辞本身，也不是 RAG 后端。**必须用单变量实验判定，不许直接写结论。**

## 2. 任务 A — 单变量归因（先做，一天内可完成）

基线 = 36.15 现配置（15.82%）。子集 = **40 题**，按「旧环境 5-run 是否至少通过 1 次 × 失败类型」分层抽样，种子固定。

| 臂 | 只改这一项 | 其余 |
|:--|:--|:--|
| **A1** | 系统提示 → no_sandbox 版 | 与 36.15 逐字节一致 |
| **A2** | RAG → 本地 `:18888` | 同上 |
| **A3** | 沙盒关闭 + 提示同步改 no_sandbox（≈还原 .17 组合） | 同上 |
| **A0** | 不改（36.15 基线对照） | — |

每题-臂记录：pass、`search_apis`/`run_code`/`submit_and_exit` 次数、submit 报错率、degenerate pass 数、平均 turn、超时数。

**预注册判据**（写在跑之前，结果出来只做核对）：
- 若 **A3 ≈ 3%** 且 **A1 ≥ 12%**（相对 15.82% 降幅 <25%）⇒ 「**prompt 措辞不是主因，反馈回路才是**」。
- 若 **A1 ≤ 8%** ⇒ 「prompt 是主因」，需在报告里解释机制（为何措辞能造成 5×）。
- 若 A1、A2 都下降明显 ⇒ 按 **prompt × 沙盒交互** 解释，不许二选一糊弄。

预算：4 臂 × 40 题 ≈ 每臂 2h（`-p 8`），可并跑；确认阶段再上 158×5run。

## 3. 任务 B — trace 驱动的 prompt 迭代

数据：**用 36.15 这一轮的 trace**（`completed_code_generation.jsonl` + `execution_results.jsonl` + `codegen.log`），不要再用旧环境 trace。

1. 画像：每题 tool 调用序列、submit 次数与报错原文归类、degenerate pass 复核。
2. 分型：沿用 RCA v2 六类但**按 36.15 重算**（退化提交 / 检索到但未进代码 / API 误用 / 断言不足 / 超时 / 输出格式）。
3. 每型写 **一条最小 prompt 补丁**，并写明「预期影响哪类失败 + 预期幅度」。
4. **train/dev 分离**：79/79 按难度+域分层拆分；补丁在 **dev** 上选，**test 只最后验一次**（防止对着 158 题调 prompt）。
5. 门槛：dev 上 3 seed，**≥ +3pp 且 submit 报错率降 ≥10pp** 才进下一轮。
6. 终局：dev 选出的组合在 **test** 上 5-run，用 McNemar 对 15.82% 基线做检验。

**候选补丁（按 ROI 排，RCA 已给线索）**：

| ID | 补丁要点 | 针对失败 |
|:--|:--|:--|
| **P1** | 提交前必须回读验证：创建类用 get/query 反查数量并打印实际值；空实现 / 只 `return None` / 只 print 不建对象 ⇒ 禁止 submit | degenerate pass（60.63%） |
| **P2** | `submit_and_exit` 每任务 ≤2 次；提交前必须已 `run_code` 跑通或写明无法验证原因；连续 2 次被拒 ⇒ 停下重读报错原文再改，**禁止原样重提** | submit 风暴（13,699 次 / 91.77% 报错） |
| **P3** | `search_apis` 命中的 API 必须在最终代码出现并经 `get_api_details` 核过参数；`source=bm25_fallback` 结果不得直接当 API 名 | 检索未落地（333 API 仅 19 进代码 = 5.7%） |

🚫 **一次只加一条**，每条单独在 dev 上测——否则又回到「多变量同时变、无法归因」的老问题。

## 4. 纪律

- 单变量 · 预注册判据 · train/dev 分离 · 先 dev 后 test · 反作弊钩子常开并报 cheat。
- 🚫 不改 benchmark / 不改 `check.py` / 不改题面 / 不挑题 / 不删失败样本。
- 🚫 不引用未完成的 run（36.15 目前只有 run1 的 `final_report`）。
- 每步落 `EXPERIMENTS_POSTTRAIN.md`；报告用中文 HTML；commit 前缀 `posttrain attribution:`。
- **最终必须能用一句话回答**：5× 里 prompt 占多少、沙盒反馈回路占多少、RAG 占多少。
