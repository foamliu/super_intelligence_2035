## 13:40 本轮（S3 巡检 + 关键诊断：S1「6.7342 平台」实为 LR 坍缩伪影）

- S3 进度（train.log 权威口径）：**openvision2 ✅ done（10k 步，loss 4.4540，steady 2139 img/s）**、**deepencoder_v2 ✅ done（5k 步，loss 4.4662，steady 1458 img/s）**、**mambaeye 🔄 step~2100/5000（loss 4.64 下降中，~800 img/s）**、**moevie ⏳ 排队**。剩余 ETA ≈40–50min（mambaeye 约 13min + moevie ~36min）。
- 🔑 **关键诊断（对比 S1 vs S3 日志）**：S1 的「四架构 loss 全 6.7342 平台」是 **cosine LR 坍缩伪影，不是架构等价**。S1 用 `--steps 1000 + warmup 100 + cosine`，cosine 在仅 1000 步内把 LR 从 1e-3 衰减到 ~2.6e-4@700 步 → ~1e-5@1000 步，LR 过早塌到 min_lr，loss 卡死在 6.7342（step700→1000 纹丝不动）。S3 用 `--steps 10000`，cosine 跨 10000 步，step700 时 LR 仍 ~9.9e-4，故 loss 继续降：6.85@500 → 5.92@1000 → 4.45@5000-10000。
  - 证据：S1 openvision2 step100=7.6147 与 S3 step100=7.6082 几乎一致（同 seed 同代码同数据），step600 S1=6.8541 / S3=6.6448 开始分叉，S1 step700+ 卡 6.7342、S3 继续 6.50→6.26→…。
  - train.py/data.py 在 S1(11:42 commit)→S3(12:10 commit) 间**无 diff**（已核 git），故差异唯一来源 = `--steps` 对 cosine 调度的影响。
- 结论修正：EXPERIMENTS 里「1000 步内四架构 loss 收敛同一平台、差异仅在吞吐」的表述要改。S3 干净轨迹显示：**loss 排名 OpenVision2(4.454) ≈ DeepEncoderV2(4.466) < MambaEye(~5.95@1k，仍在降)**，架构 loss 差异很小（<0.012 @5k），但**吞吐/延迟差异巨大且确定**（2139 vs 1458 vs 800 img/s；推理 6.5 vs 17.8 vs 卡死 ms）。
- 影响：S6/S7/S8 消融若仍用 `--steps 1000` 会落入同一 LR 坍缩区间 → 最终 loss 区分度低。已考虑：S6/S7/S8 保持单变量 1000 步（吞吐为主信号 + loss 二次），或视预算把关键消融提到 2000-3000 步。S5 检索 R@K 才是真实质量区分信号（loss 近乎并列时）。
- 验证：`analyze_s3.py` 已跑通（解析 S3 日志 → 对比表 + /tmp/s3_loss_<tower>.csv），产出 checkpoint 对比表（500/1000/5000/10000）。
