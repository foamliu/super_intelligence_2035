**① 归因实测（~10 分钟，先做，不写论文）**
- 采样：训练同跑 `nvidia-smi dmon -s u -c 60`（或 `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 1`），记 **GPU util + 显存峰值**。
- 扫描：**bs 64 / 128 / 256** 各跑 **≥200 步**（同塔同数据），记 `ms/iter`、`image/s`、显存峰值。
- **判据**：
  - util **≲70%** 或 **`ms/iter` 基本不随 MBS 变** ⇒ **数据/IO 受限** ⇒ **别靠加 MBS**，改数据管线（②）；
  - util **≈100% 且 img/s 随 MBS 上升** ⇒ **算力受限** ⇒ 加 MBS 有效（③）。
- 把**原始输出**（dmon + 三档 `[step]` 行）贴进 `MEMORY_VISION.md` / `EXPERIMENTS_VISION_ROUND11.md`（铁律：命令 + 原始输出 + 路径）。

**② 若数据受限（运维判断可能性更大，且**不改 recipe** —— 最安全）**
- 提 `--num-workers`（6 → 12/16/rank）；把 CC12M/Amshaker 的 tar **预热到本地 NVMe / page cache**；**避免与 data 线大下载争 NFS**；降 `--probe-every` 频率；评估更快解码（`torchvision.io` / `decord` 替 PIL）。

**③ 若确为算力受限（才动 MBS）**
- 显存允许时可把 `--batch-size` 提到 **128（必要时 192/256）**（先测梯度稳定性 + 显存峰值）。
- ⚠️ **MBS↑ = global batch 变大（512→1024/2048）= InfoNCE 负样本数变了 ⇒ recipe 变了**：必须**显式标注**「global batch 与 R11-G 不同、**不并入同一条 scaling 曲线**」，或用**梯度累积把 global 拉回 512** 再谈可比。
- 其它不改 recipe 的提速：`torch.compile` / `channels_last` / TF32（大 N 时收益更明显再采用）。

> ✅ 结论先行：**显存没满 ⇒ MBS「能加」；但「能加」≠「会更快」**——请用上面的归因实测给出你线上的确切答案。

#### R11-G —— AIMv2-style 长跑 → **重拟合 scaling 并外推**

**目的**：⑥-A 只给了 **30k 步（N≤15.36M）的 3 个点且非单调**（11.39→11.14→12.08%）→ **无法拟合/外推**。本项把它拉到 **与 R9 阶段二同口径的 108k 步**，回答「**翻盘后的渐近是多少？**」

| # | 项 | 值 |
|:--|:--|:--|
| 1 | 目标函数 | **与 ⑥-A 完全同款**：`InfoNCE + 1.0 × masked-patch-MSE`（`--loss aimv2 --mask-ratio 0.6 --patch-loss-weight 1.0`）|
| 2 | 其它全部固定 | 塔 w512 · 冻结 CLIP-768 · 数据 CC12M+Amshaker(~18.5M) · AdamW 3e-3 / warmup 20 / seed 1234 / bf16 / bs64×8=512 |
| 3 | **唯一变化** | **步数 30k → 108k**（= 55.3M 样本，对齐 R9 阶段二）|
| 4 | 采点 | `--save-interval` 对齐 **R9 阶段二**（见 `run/vision/r9_run_stage2.sh`）；**对照点至少** step{10k,20k,30k,60k,100k}+final（N = 5.12/10.24/15.36/30.72/51.2/55.3M）|
| 5 | 评测 | `r8_eval_in1k.py` 对每个采点跑 **IN-1k frozen-trunk lp**（同 R8–R11 口径）|
| 6 | 成本 | 108k × ~80ms ≈ **2.4h**（⑥-A steady 5971 img/s）+ ≥5 点 lp eval ≈ 1.1h → **≈3.5h** |

**🔒 预注册判据（先定后测，🚫 不许事后改）**
- 对 (lp, N) 做**与 R9 相同**的两种拟合（幂律 `a − b·N^−c` + 对数线性），报 **R² + 渐近 a**，并与 InfoNCE 的 **a=25.1%** 并列对照。
- 裁定：**R² ≥ 0.90 且 渐近 a 显著 > 25.1%** → 「**换目标函数可抬高渐近上限**」（正面结论，可进论文）；**R² < 0.90 或轨迹非单调** → 如实写「**非简单幂律，需更多点/更长跑**」，**🚫 不得强行拟合或外推**。
- 基线参照（同法拟合）：InfoNCE `acc=0.251−0.864·N^−0.090`（R²≈0.94）。

#### R11-H —— 臂 **⑥-B：纯 AR（去对比项）** 30k 步

> 别名 = `ROUND11 §14.0(3)` 与 `§14.3` 里的 **⑥-B**；官方 AIMv2 = **vision AR + text AR、无对比项**，而 ⑥-A **保留了 InfoNCE**（为控变量）。

|:--|:--|:--|
| 1 | **唯一变化** | 在 ⑥-A 基础上 **去掉 InfoNCE 对比项**（`total = 1.0 × masked-patch-MSE`；文本塔不再参与梯度）|

| 3 | 评测 | 同 ⑥-A：IN-1k frozen-trunk lp @ step{10k,20k,30k}+final |
| 4 | 成本 | ≈**1.2h** + eval ≈0.2h → **≈1.4h** |

**🔒 预注册判据（以 ⑥-A 为对照：11.39 / 11.14 / 12.08%；基线 3.43 / 5.45 / 6.08%）**

| 结果 | 裁定 |
|:--|:--|
| 两点（@5.12M/@10.24M）**仍 ≥ 基线 +1.5** 且 ≥ ⑥-A −1.5 | 「**不依赖对比项即可翻盘**」→ 稠密 patch 监督本身是主因（更接近官方 AIMv2 路线）|

### 🆕 运维指令 · 2026-10-11（📄 **外部反馈 → 审视 + 简单合入论文**：Muon 坍缩的「**梯度谱**」解释）· 用户直令 · 高优先

> **用户原话（2026-10-11 晚）**：「关于 **vision 报告的 Muon 的问题**，下面是**朋友的意见（支持 vision 的实验）**。请 vision **审视一下**，把**实验简单合入论文**。」

**① 对方的核心主张（**原文要点，待你核**）**
1. 我们的坍缩**不是调参失败**，而是 **Muon 核心机制（均匀谱白化 = Newton–Schulz 把动量矩阵奇异值全拉到 ≈1）在特定梯度几何下的结构性不兼容**；
2. 外部证据（称 2026 年论文 **“Pion: high-pass replacement for Muon”**）：均匀谱白化在**全秩/高 SNR 的预训练梯度上是优势**，但在**低秩（VLA 动作头）或低 SNR（RLVR rollout）**梯度上变**失效模式**（把尾部纯噪声方向也放大到 ≈1）；
3. **平行证据**：Muon 在**纯 CE 的 LLM 预训练**表现好，却在 **VLA 微调 / RLVR** 里「坍缩到零准确率」——与我们的「**pretrain 成功 / vision InfoNCE 联合目标失败**」同构；
4. 机制补充：① **InfoNCE 本身偏好低秩**（正对含不变/变化分量时，把变化分量压到低秩子空间可降 loss）；② **AdamW 逐参自适应缩放对梯度谱结构不敏感**，Muon 是矩阵级全局谱约束 ⇒ 作用维度不同；
5. 对「**降 LR 只延缓不阻止**」的解释：纯 GD 下 InfoNCE 坍缩由 lr 控制（0.01 不坍缩 / 1 强坍缩），但 **Muon 改的是更新的「方向结构」而非缩放** ⇒ lr 只改变**到达时间**，不改轨迹几何；
6. **建议改写的结论**：**Muon 的适用边界由「梯度谱形状」决定，而非由损失函数类型决定**；
7. **建议的验证**：坍缩前记录**各层动量矩阵的奇异值分布**，与 AdamW 对比 —— 若 Muon 谱**明显更平坦（尾部抬高）**即证实该诊断。

### 🆕 运维指令 · 2026-10-10（🧪 **变体实验：① 优化器 AdamW→Muon → ② 全量数据 GPIC+CC12M+Amshaker；③ 分辨率暂缓**）· 用户直令 · **最高优先**【已归档 2026-10-12】

**① Baseline（已存在，🚫 不重跑）**
- `E1fair` = OV2 **w512**/d30 · **224/p16** · from scratch · **187,101 步** · `lr=5e-4` / `warmup=2000` / **cosine** / `min_lr=5e-5` · 冻结快照 `total_shards=10787`。

**② 执行次序与变体（用户 2026-10-10 晚调整）** —— **先 `1`（Muon）→ 再 `2`（全量数据）；`3`（分辨率）暂缓**。各 1 臂；除被检验的单一变量外，与 baseline 逐字节相同。

1. **V1 · 优化器：AdamW → Muon**【**本轮第一优先** · 原 V2】
   - 🔎 **框架事实（运维已核实 · 用户 2026-10-10 追问）**：`r9_train.py` = **纯 PyTorch DDP**（`dist.init_process_group('nccl')` + `torch.nn.parallel.DistributedDataParallel` + `torch.optim.AdamW`；`python -m torch.distributed.run --nproc_per_node=8`）—— **不是 Megatron-LM / NeMo** ⇒ **没有现成的 `dist_muon` 开关**（`dist_muon` 是 **Megatron-Core** 的 layer-wise distributed 优化器，vision 栈里不存在）。
   - ✅ **但 Muon 无需自行实现**：**直接用上游 `emerging_optimizers`**（`pip install emerging_optimizers`；**Megatron-Core 的 `core/optimizer/muon.py` 就是它的 shim**）接入 `r9_train.py`（torch.optim 风格 API）。**参考 pretrain 最近的 dist_muon 实验**：`run/EXPERIMENTS_PRETRAIN_2B_ROUND2.md`「**dist_muon 实测验证（三路对比）**」节 · `doc/BaiZe-ISEDA2027/report_pretrain_muon_vs_adamw.html §8`。
