## 0. 一句话摘要

在**正确评测环境**（36.15 起评、RAG + 沙盒 MCP 齐备、模型经反向隧道取自 .17）下，先测出 MiniCPM5-2B 的**真实基线**；
再基于真实基线做**失败归因 → 分档干预（数据 / 工具 / 提示 / 训练）**，用**同一评测协议**验证提升是否显著。

## 1. 结论先行：当前基线数字不能直接采信

### 1.1 已测得的数字

| 来源 | 数字 | 环境 |
|:--|:--|:--|
| posttrain RCA（2026-11-14） | **3.04% ± 0.83%**（5-run 通过数 6/3/4/5/6） | ckpt `minicpm5-2b-sft-v39-final`(step105)，vLLM GPU6 `:8096`，**在 .17 启动** |
| zhulong full_v3（历史锚点） | **82.1% ± 3.0%**（5/5） | **36.15 启动**，主基座 `deepseek-v4-pro-cloud` |

### 1.2 为什么 3.04% 不能直接当作"模型上限"

- RCA 报告的评测协议写的是「cline harness + pyAether MCP 工具 + **沙盒经 dual-nix-tunnel**」，
  **说明它确实调用了 MCP 与沙盒** —— 这一点与我们最初的怀疑不同，必须如实记录。
- 但**启动位置不同**：posttrain 在 **.17** 起评；zhulong 在 **36.15** 起评。
  两机关键差异：**.17 无法直连 EDA 环境（防火墙），只能靠隧道间接访问**；36.15 在内网，可直连 `.75` 沙盒。
- ⇒ **待验证的核心问题**：`.17 → 隧道 → 36.15 → .75` 与 `36.15 → .75` 直连，
  在 **RAG 召回质量、沙盒延迟、工具可用性** 上是否等价。
- ⇒ **验证之前，3.04% 只能标注为「.17 口径基线」**，不能当作能力结论。
  同理 82.1% 是 `deepseek-v4-pro-cloud`（大模型）的成绩，**不能与 2B 模型比较**。

## 4. 执行计划（四阶段）

### 阶段 A · 打通并复现（目标：拿到可信基线）

| # | 动作 | 负责 | 验收 |
|:--|:--|:--|:--|
| A1 | .17 确认 vLLM serve `minicpm5-2b-sft-v39-final` 在 `:8096` 健康（`curl /v1/models`=200） | posttrain | 返回 model 名 |
| A2 | .17 起反向隧道 `ssh -p3333 -fN -R 18096:localhost:8096` | posttrain | 36.15 `curl localhost:18096/v1/models`=200 |
| A3 | 36.15 确认 RAG `:9006`、MCP `:18891`、沙盒端口可用；`PROXY_PORTS` 按 `.env` 口径 | zhulong | 三端口实测 |
| A4 | **单题冒烟**：36.15 用 `run_cline_script.sh` 跑 **1 题**，模型指向 `localhost:18096/v1` | posttrain+zhulong | 有 tool_call、有 code、无 403/超时 |
| A5 | **单题双跑对照**：同 1 题，分别在 .17 本地起评 vs 36.15 起评，比对 trace | posttrain | 差异可解释 |

> **A5 是本方案的核心实验**：它直接回答「.17 口径与 36.15 口径是否等价」，
> 从而判定 3.04% 是否作废、要不要全量重测。

### 阶段 B · 全量基线重测（目标：可信的 Pass@1）

| # | 动作 | 验收 |
|:--|:--|:--|
| B1 | 36.15 起评全 **158 题**，`-p 8 -n`，2500s/题，N-run（见 Q3） | N 次全跑完 |
| B2 | 打分以 **log 里 `pass (xx.x%)`** 为口径（🚫 不用 `run_eval.py`，会超时） | 与 N-run 一致 |
| B3 | 输出 **Pass@1 mean ± std**，与 3.04% **并列同表** | 差异写明 |
| B4 | 逐题结果落盘（158 行），供阶段 C 归因 | 可复算 |

### 阶段 C · 失败归因（目标：找出真因，不预设分类）

- 基于 B4 逐题 trace **自行提炼分类**（不套用任何预设表）；
- 每类给：题数、占比、**trace 原文摘引 + 路径**；
- 关键对照：**同样 158 题，`deepseek-v4-pro-cloud` 能过而 2B 不能过的，差在哪一步**
  （检索不到 API？写错 API？跑不通沙盒？定位不了错误？）；
- 产出：中文 HTML 报告（饼图 + 表格 + 逐类 fix 方案）。

### 阶段 D · 分档干预与验证（目标：显著提升）

按阶段 C 结论分档，**每档独立验证**，不混合归因：

| 档 | 干预手段 | 预期适用 |
|:--|:--|:--|
| D1 | **数据侧**：针对失败类型造 SFT 语料（API 用法/约束/常见错误） | 模型"不知道该调什么" |
| D2 | **工具/提示侧**：system prompt、工具 schema 收紧、检索策略、上下文管理 | 模型"会但用不出来" |
| D3 | **训练侧**：SFT 续训 / RL（GRPO，已有 loop 与 sft-v39 经验） | 需改变行为分布 |
| D4 | **环境侧**：超时预算、沙盒稳定性 | infra 造成的假失败 |

**验证纪律**：
- 每档与阶段 B 基线**同协议、同题目、同判据**；
- **≥3 run**，给 `mean ± std`；
- 显著性用**配对检验**（McNemar / bootstrap CI）；
