1. 背景

运维 2026-10-06 提速令：P-9.12 已证 NCCL 非瓶颈（NV18 full-mesh NVSwitch，100% P2P/CUMEM）→ 转向运行时/并行/IO 提速候选清单（Step 2）。每条给实测 tok/s + 判据 + 可否迁移 8 卡 + 时间盒。 优先「不改 recipe、只改运行时/并行/IO」的项。

recipe 审查结论：overlap_grad_reduce=True / overlap_param_gather=True / use_distributed_optimizer=True / num_workers=8 —— 均已开启，无优化空间。 launcher 仅暴露 23 个 CLI flag，无 recompute / cuda_graph / attention_backend / loss_fusion 入口。 可变项 = env 变量（CUDA_DEVICE_MAX_CONNECTIONS）+ MBS/GBS（CLI 已支持）。

2. 实验设计

  • 硬件：GPU0-1 only（GPU2-7 = data agent BO 并发，不占 GPU0-1）
  • 口径：TP1 / DP2 / seq=4096 / GBS=256 / bf16 / seed=1234 / 60 步短测
  • 可比性：GBS=256/DP2/MBS2 = 64 micro-batches/GPU = P-9.7 (GBS=1024/DP8/MBS2) per-GPU load → 2-card tok/s 可直接与 P-9.7 249K × 2/8 = 62.25K 对照
  • token/step = 256 × 4096 = 1,048,576 = 1.05M · 每次只改一个变量

5. 关键观察与判据

  1. 2-card baseline = 63853 tok/s = P-9.7 249K × 2/8 = 62.25K 的 103% （微超线性：2-card allreduce 比 8-card 更轻 → comm 开销更小）。→ per-GPU 效率已接近上限。
  2. MAX_CONN=1 vs default +0.8%，MAX_CONN=4 vs default +0.0%：两者均 在噪声内（Δ < 1%）。 → ✅ CUDA_DEVICE_MAX_CONNECTIONS 对 bf16 无显著影响。 机制：MAX_CONN 主要影响 FP8 TE kernel 的 CUDA stream 并发数；bf16 下 compute kernel 串行度已足够。
  3. MBS=4 OOM（79847 MiB → 逼近 80GB 上限）→ 与 P-9.1 一致：TP1 下 MBS 上限 = 2。 P-9.1 已证明 MBS=4 在 8-card 下吞吐不优于 MBS=2（218K vs 218K），P-9.2 证明 TP2·MBS4 = 200K < TP1·MBS2 218K → MBS=4 即使落地也不提速。
  4. peak 64GB vs P-9.7 54.7GB：use_distributed_optimizer=True 在 DP2 下每 GPU 持有 4× optimizer state（vs DP8）→ 显存更高但仍 <80GB。
  5. loss 曲线健康：所有成功候选 11.06→7.44，0 NaN/skip → 配置变更无训练稳定性影响。
  6. ckpt 清理：framework 在 train_end 自动存 ckpt（非 --save-interval 99999 意图）； 候选①②（8.4GB）+ 候选③（4.2GB）已清理，候选④ OOM 无 ckpt。总计释放 12.6GB。
