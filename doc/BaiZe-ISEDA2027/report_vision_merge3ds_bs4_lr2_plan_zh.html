1. HERO + TL;DR

核心问题：在 24 小时墙钟预算（10.239.2.12 H100×8 独占）内，将 GBS/MBS ×4、LR ×2 后，能跑几个 epoch？ProtB 预期多少？

  • 数据：GPIC（7437 tar）+ CC12M（1100 tar）+ Amshaker（2250 tar）= 10787 shards ≈ 95.8M 图文对（与 ④-4ep 基线完全相同的冻结快照 data_snapshot_20261009.txt）
  • 超参变动：MBS 64→256/GPU（×4），GBS 512→2048（×4，负样本 512→2048），LR 5e-4→1e-3（×2），warmup 2000→4000（×2 同比），cosine min_lr 5e-5→1e-4（=10%×lr）
  • 时间估算：基线 steady 2818 img/s；×4 batch 后吞吐估计 2818–4227 img/s（NFS I/O 可能是瓶颈）→ 1 epoch ≈ 6.3–9.4h → 24h 可跑 2.5–3.8 epoch（中位估计 ~3 epoch）
  • ProtB 预估（外推·待验）：3 epoch ×4-GBS/×2-LR 预计 ~64–66%（乐观~67%，悲观~63%）；vs ④-4ep 基线 67.05% 可能持平或略低，原因是每 epoch 梯度更新数减少 4×（46,777 vs 187,101 步/epoch）且 LR 未按线性缩放规则充分放大
  • 关键风险：① MBS=256 显存可能 OOM（需校核）② LR ×2 对 ×4 batch 为欠缩放（线性规则需 ×4）→ 收敛可能偏慢 ③ NFS I/O 瓶颈可能限制吞吐增益 ④ r9_train.py 无 grad-accum 参数 → 若 MBS=256 OOM 需改代码

3.2 LR 缩放规则分析

缩放规则建议 LR本方案 LR偏差影响
线性缩放（LR ∝ GBS）5e-4 × 4 = 2e-31e-30.5× （欠缩放）收敛可能偏慢；每 epoch 梯度更新少 + LR 不足 → 需更多 epoch 才能达到同等特征质量
平方根缩放（LR ∝ √GBS）5e-4 × 2 = 1e-31e-31.0× （匹配）本方案 = 平方根缩放；适合对比学习经验

本方案 LR=1e-3 恰好匹配平方根缩放规则（√4=2，×2 LR），但低于线性缩放规则（×4 LR）。在大 batch 对比学习中，负样本池扩大（512→2048）本身提供了更强的对比信号，可能部分补偿 LR 欠缩放。结论：×2 LR 合理但偏保守，收敛速度可能慢于线性缩放方案。

5.2 ×4-GBS / ×2-LR 对 ProtB 的影响分析

因素方向量级估计机制
负样本池 ×4（512→2048）↑ 正面+0.5–1.5 ppInfoNCE 对比学习：更多负样本 = 更硬的负例 = 更好的表征。文献 (CLIP) 显示 batch 512→2048 可提升 ~1–2pp。
每 epoch 梯度更新 ÷4（187k→47k 步）↓ 负面−1–3 pp每 epoch 参数更新次数减少 4× → 收敛步数减少 → 同 epoch 下特征质量可能偏低。
LR ×2（欠缩放）↓ 偏负面−0.5–1.5 pp线性规则需 ×4 LR；×2 = 0.5× 欠缩放 → 每 step 学习率相对不足 → 收敛偏慢。
warmup ×2（2000→4000）中性~0 pp保持 warmup/LR 比例稳定，减少大 batch 初期不稳定。
数据不变（同快照）中性~0 pp同一 95.8M 快照，数据质量/数量无变化。

净效应估计：负面（更新数↓ + LR 欠缩放）vs 正面（负样本↑）大致相抵，但负面略占优 → 同 epoch 数下 ProtB 可能略低于基线。

6. 风险评估

#风险概率影响缓解措施
R1MBS=256 显存 OOM中高（需改代码）先 smoke test MBS=256 单步前向+反向；若 OOM → 方案 B：保持 MBS=64 + 新增 --grad-accum 4（~20 行代码改动）
R2NFS I/O 瓶颈导致吞吐不提升高中（仅跑 2.5 epoch）增加 --num-workers 8；与 data 线下载错峰；监控 nvidia-smi GPU 利用率
R3LR 欠缩放导致收敛偏慢中中（ProtB 偏低 1–2pp）记录 loss 曲线；若前 10k 步 loss 不降 → 回退 LR=2e-3（线性缩放）；warmup 后监控 C1 坍缩指标
R4大 batch + 高 LR 训练不稳定（C1 坍缩）低高（实验作废）r9_train.py 有 C1/C2 坍缩检测；PROBE every 300 步监控；若 C1>0.95 → 自动 fuse + 停止
R524h 预算不足（吞吐低于预期）中低（少跑 0.5–1 epoch）每 10k 步存 checkpoint；即使 24h 到期也有中间结果可评测
R6与外部编码器评测 GPU 冲突低中外部评测 AIMv2/RICE 仍在跑（GPU 2,4）；新训练用 GPU 0–7 → 需等外部评测完成或分卡。建议等外部评测 5/5 完成后再启动
R7对比学习大 batch 效应不确定中中文献效应 (CLIP batch 512→2048 ≈ +1–2pp) 基于大规模数据；我们 95.8M 对可能不重现

8. 诚实条款

  1. 本文件是计划，不是结果：所有 ProtB 数字（§5.3 表）均为基于基线曲线 + 理论分析的外推估计，标注 外推·待验。实测前不得引用为结论。
  2. 不编造数字：基线数字（62.34% / 65.37% / 67.05% / 2818 img/s / 10787 shards 等）全部来自 EXPERIMENTS_VISION.md / MEMORY_VISION.md 实测记录，可溯源。
  3. 时间估算有不确定度：24h 可跑 epoch 区间 2.5–3.8，取决于 NFS I/O 瓶颈程度。中位估计 3 epoch ≠ 保证值。
  4. ×2 LR 是保守选择：运维指令指定 ×2，非线性缩放规则建议的 ×4。若结果不佳，不排除是 LR 不足而非 batch size 问题。
  5. 数据口径：运维指令标 ≈59M 对，实际配置 95.8M 对（10787 shards）。差异可能来自 unique vs total pairs 的口径差。本计划以实际配置为准。
  6. 未启动训练：本计划严格遵守「只出计划不启动」纪律，不占 GPU，不打断在飞的外部编码器评测。
  7. 预注册判据（建议）：① ProtB ≥ 67%（= ④-4ep 基线）→ 大 batch 至少持平 → 可继续探索；② 64% ≤ ProtB < 67% → 大 batch 略差 → LR 欠缩放可能为主因；③ ProtB < 64% → 大 batch 显著不利 → 回退基线配置。判据须运维确认后定稿。
