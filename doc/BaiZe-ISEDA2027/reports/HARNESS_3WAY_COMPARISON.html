TL;DR

  1. cline-patched and Pi achieve identical 60.0% (18/30) — and solved the exact same 18 instances. Hermes scored 53.3% (16/30), a strict subset. This suggests the model (kimi-k2.6-cloud) is the bottleneck, not the harness, for these 30 instances.
  2. Pi is 1.7× faster than cline-patched (mean 275s vs 479s) and 2.0× faster than Hermes (553s), despite identical resolve rate — lightweight TypeScript/Bun print-mode architecture minimizes overhead.
  3. Hermes's 2 unique failures (django-10924, django-11422) are both "broke existing tests" (p2p_fail) — its verbose execution-discipline prompt may cause over-editing. cline's YOLO prompt ("run test suite to confirm") may prevent this.
  4. 12/30 instances unsolved by all three — these are genuinely hard for kimi-k2.6-cloud, not harness-dependent. The harness ceiling for this model+subset is ~60%.
  5. Tool count inversely correlates with speed: Pi (7 tools) > cline (9 tools) > Hermes (20+ tools). More tools = more prompt tokens = slower per turn, but does not improve resolve rate.

2. System Prompt Comparison

The system prompt is the single most impactful harness design choice — it shapes how the model approaches the task. All three prompts were read from source:

cline-patched — YOLO_CLINE_SYSTEM_PROMPT

Source: cline/sdk/packages/shared/src/prompt/system.ts:38-68

Key directives:

  • "You are Cline, a careful and helpful coding agent that works in the background" — emphasizes autonomous operation
  • "Your goal is to utilize the tools at your disposal to investigate and answer the question" — investigation-first
  • "When the user describes a bug... your primary goal is to produce a correct fix" — fix-focused
  • ⭐ "After applying your fix, you must run the relevant test suite to confirm your changes actually resolve the problem. If tests fail, analyze the failures, revise your fix, and re-run until tests pass." — explicit test-verification loop
  • ⭐ "You should only end the task when all the requirements are met by calling the 'submit_and_exit' tool" — structured termination
  • "Always show your planning process" — plan-then-execute pattern
  • "You can call multiple tools in a single response" — encourages parallel tool calls

Pi — buildDefaultSystemPrompt()

Source: dist/core/system-prompt.js:70-100

Key directives:

  • "You are an expert coding assistant operating inside pi, a coding agent harness" — identity is the harness, not a persona
  • "You help users by reading files, executing commands, editing code, and writing new files" — tool-oriented, no bug-fixing framing
  • Tool list is injected inline (formatAvailableTools()) — model sees exact tool names + descriptions
  • Orchestration section (conditional on subagent tool): "You are the primary agent and final decision-maker. Use subagents as isolated workers" — multi-agent delegation
  • State compression (conditional): "Consider compress_context at concrete checkpoints" — explicit context management guidance
  • Guidelines are tool-aware: "Prefer grep/find/ls tools over bash for file exploration (faster, respects .gitignore)"
  • No test-verification directive — Pi does not explicitly tell the model to run tests after fixing

Hermes Agent — DEFAULT_AGENT_IDENTITY + OPENAI_MODEL_EXECUTION_GUIDANCE

Source: agent/prompt_builder.py:160-169 (identity) + :442-506 (execution guidance)

Key directives:

  • "You are Hermes Agent, built by Nous Research. Be direct: match the length of your reply to the weight of the ask" — conciseness-focused, anti-filler
  • "No filler, no restating the request back, no re-summarizing what you already said" — token economy
  • Execution discipline (7 sections):
    • <tool_persistence>: "Keep calling tools until: (1) the task is complete, AND (2) you have verified the result"
    • <mandatory_tool_use>: "NEVER answer these from memory — ALWAYS use a tool" (arithmetic, hashes, time, file contents, git history)
    • <act_dont_ask>: "When a question has an obvious default interpretation, act on it immediately"
    • <prerequisite_checks>: "Do not skip prerequisite steps"
    • <verification>: "done means every named acceptance criterion is verified"
    • <external_state_verification>: "verify the effect by reading back the exact target before claiming success"
    • <literal_preservation>: "Preserve identifiers, commands, and values exactly as given"
  • Very verbose — the execution guidance alone is ~700 words, vs cline's ~200 and Pi's ~150

Key insight: cline's prompt has the most SWE-bench-specific guidance (test-verification loop + submit_and_exit). Pi's prompt is the most minimal (tool list + guidelines, no bug-fixing framing). Hermes's prompt is the most verbose (7 execution-discipline sections), which may increase prompt tokens but not improve task-specific behavior.

Hermes's sophisticated turn pipeline

Source: agent/conversation_loop.py:1-62 — the turn is decomposed into 15+ phases:

begin_turn → prepare_iteration → announce_api_call → build_api_request
  → assemble_api_request → perform_api_call → check_api_response
  → normalize_model_response → run_tool_round → finalize_turn
  → handle_api_error → handle_api_interrupt → finish_text_response

Each phase is a separate module (turn_api_call.py, turn_tool_round.py, etc.), making Hermes the most architecturally complex of the three.

Pi's lightweight print-mode flow

Source: dist/modes/print-mode.js:29-80

runPrintMode(runtimeHost, options)
  → session.sendUserMessage(initialMessage)
  → session.waitForIdle()
  → writeFinalTextOutput(lastMessage)  // extracts text from assistant message
  → disposeRuntime()  // cleanup + exit

Pi's print mode is radically simple: send prompt, wait for idle, extract text, exit. No retry loops, no compression triggers, no repetition guards — the simplicity directly contributes to its 1.7× speed advantage.

6. Resolve Overlap Analysis

The most striking finding: cline-patched and Pi solved exactly the same 18 instances — zero divergence. Hermes's 16 solves are a strict subset of both. This means:

  • The model (kimi-k2.6-cloud) determines which instances are solvable, not the harness — for these 30 instances, the harness only affects whether a solvable instance is actually solved, not which instances are solvable.
  • Hermes lost 2 instances that cline/Pi both solved: django__django-10924 and django__django-11422. Both are "broke existing tests" failures (p2p_fail).
  • 12 instances were unsolved by all three — these are the model's genuine capability ceiling for this subset.

Pi is the fastest harness by a wide margin (mean 275s vs cline's 479s vs Hermes's 553s). This is because:

  • Pi's print mode (dist/modes/print-mode.js) is a minimal send-wait-extract loop with no retry, no compression, no repetition guard

  • 7 tools = smaller tool-definition payload in each API request = fewer prompt tokens

Hermes's 2 unique failures (evidence)

① django__django-10924 — Hermes produced a 5412-byte patch that fixed the target test (f2p=1/1) but broke an existing test (p2p=0/1):

== harness=hermes rc=0 timed_out=False wall=567.5s ==
[run_single] model_patch: 5412 bytes
eval: f2p_pass=1/1, p2p_pass=0/1  ← broke existing test!

cline-patched and Pi both resolved this instance (p2p=1/1). cline's YOLO prompt says "run the relevant test suite to confirm... If tests fail, analyze the failures, revise your fix" — this test-verification loop likely caught the regression before submission.

② django__django-11422 — Hermes produced a tiny 977-byte patch (vs cline/Pi's larger patches), suggesting under-editing:

== harness=hermes rc=0 timed_out=False wall=335.5s ==
[run_single] model_patch: 977 bytes  ← suspiciously small
eval: f2p_pass=0/1, p2p_pass=46/46  ← didn't fix the bug, but didn't break anything

Hermes's conciseness-focused prompt ("match the length of your reply to the weight of the ask") may have caused the model to produce a minimal patch that didn't fully address the issue.

Root cause hypothesis: cline's submit_and_exit + test-verification prompt creates a self-checking loop that catches regressions before submission. Hermes's verbose execution-discipline prompt focuses on process (tool persistence, mandatory tool use) rather than outcome verification (run tests, check regressions). Pi achieves the same rate as cline without explicit test-verification guidance — suggesting kimi-k2.6-cloud may natively run tests when fixing bugs, but the prompt can still prevent regressions (as Hermes's failures show).

The paradox: Hermes has the most sophisticated architecture (concurrent tools, 4 compression strategies, repetition guard, API retry ladder, run-budget notices) yet achieves the lowest resolve rate and slowest wall time. This suggests that for SWE-bench tasks with a capable model (kimi-k2.6-cloud), harness simplicity is an advantage: less prompt overhead, faster tool dispatch, fewer retry loops. The harness's job is to get out of the model's way.

11. Implications for BaiZe

If BaiZe 2.2B is to serve as a backbone for SWE-bench-style tasks, this analysis suggests:

Capability neededWhy (evidence)Priority
Test-verification behaviorcline's prompt explicitly tells the model to "run the relevant test suite to confirm" — this prevented 2 p2p regressions that Hermes suffered. A 2.2B model may need stronger prompt reinforcement for this.⭐ Critical
Concise tool usePi's 7-tool setup achieved the same rate as cline's 9 tools. Fewer tools = less prompt token overhead. For a 2.2B model with limited context, a minimal tool set is essential.⭐ Critical
Structured terminationcline's submit_and_exit prevents both premature termination (model stops too early) and endless loops (model keeps exploring). A 2.2B model is more prone to both failure modes.⭐ High
Bug-understanding capability12/30 instances were unsolved by all three harnesses — these are model capability gaps, not harness gaps. The model must understand the bug, locate the relevant code, and produce a correct fix.⭐ Critical (model-level)
Patch completenessHermes's 977-byte patch on django-11422 (under-editing) vs cline/Pi's larger patches — a 2.2B model may tend toward minimal patches that don't fully fix the issue.⭐ High
Regression awarenessHermes broke existing tests on 2 instances — the model must understand that a fix should not break other tests. This requires either prompt guidance or training data with test-suite feedback.⭐ Medium

Recommended harness design for BaiZe 2.2B:

  1. Minimal tool set (≤7 tools): read, bash, edit, write, grep, find, submit_and_exit — no browser, no memory, no skills, no subagents
  2. Test-verification prompt: explicitly instruct "run tests after fixing, check for regressions, revise if any test fails"
  3. Structured termination: provide a submit_and_exit tool that signals task completion
  4. Short system prompt (≤200 words): focus on bug-fixing discipline, not general execution philosophy
  5. No retry loops: fail-fast is faster and doesn't improve outcomes — let the model handle errors by seeing the error output
  6. No context compression for 30-instance runs: none of the instances hit the context limit with kimi-k2.6-cloud's 128K context

12. Limitations

  1. 30 instances only — the identical cline/Pi solve set could be coincidental with this small sample. A 100+ instance run would be needed to confirm.
  2. Single model (kimi-k2.6-cloud) — the "model is the bottleneck" finding may not generalize to weaker or stronger models. A 2.2B model might show more harness-dependent variation.
  3. cline-patched is modified — it's not vanilla cline; the "patched" version may include SWE-bench-specific optimizations not in the upstream.
  4. Pi and Hermes versions are early — Pi v0.2.15 and Hermes @0e219331 are both pre-1.0; later versions may have different behavior.
  5. No token consumption data — the eval didn't capture per-turn token counts, so cost analysis is limited to wall time.
  6. Non-Docker sandbox (unshare R1) — may differ from official Docker-based SWE-bench evaluation.
  7. Single seed — no variance estimation; different random seeds might produce different resolve patterns.
