4. 失败归因（本轮取证结论 · 按估计影响大小排序）

取证方式：只读（读训练脚本 / HF 建模代码 / 训练日志首尾 / 数据 .bin 字节数与分词 .json / ckpt 权重）。未重训、未改配方、未跑任何训练。

4.1 🔴 双移位 bug（double-shift）—— 候选最大单项根因（代码级已确认）

  • 训练脚本 baize_xmodel25_decay_v2.py 预先移位：input_ids = full[:, :-1]、labels = full[:, 1:]（py:547-548）。
  • HF forward 内部再次移位：shift_logits = logits[:, :-1]、shift_labels = labels[:, 1:]（modeling_xmodel2.py:1209-1210）。
  • chunked CE 路径同样再移位（py:567-568），且代码注释明确承认："Data is already pre-shifted… so HF model double-shifts. Replicate here for numerical equivalence."
  • 后果：训练时模型学的是 2 步预测（位置 i → 预测 i+2），而评测是标准 1 步预测（i → i+1）→ train/eval 任务不匹配，14 集全部退化。官方 decay 不会预移位（标准做法仅在 forward 内移位一次）。
  • 该 bug 对 CX 类（gsm8k / mbpp / humaneval，需多步推理）打击最重，与 §3 中「CX6 崩得最狠」的现象一致。

4.2 🔴 peak LR 1.67e-3 过高 + warmup 100 步过短

  • WSD：warmup 100 步 → peak 1.67e-3 → exp(-5.0) decay → min 1e-5（.sh 实值 LR=1.67e-3 / WARMUP=100 / MIN_LR=1e-5）。
  • 从 1.41T 已收敛末点起步，decay 段应继续用 1e-5 ~ 3e-4 的温和 LR，而非重新 warmup 到 约 5~17× 典型 decay LR 的 1.67e-3。高 peak LR 在前几百步破坏预训练表征（相对新数据重学），warmup 100 步不足以在破坏前「软着陆」。

4.3 🟠 code 严重过采样 ≈26 epochs（计划标 23.7）

  • Code 可用仅 0.270B tokens（anneal_code num_tokens=90.3M + r3_ultradata_code 180.0M，取自分词 .json 元数据），以 9.8% 配比训练 6.98B → ≈26 epochs，属严重过采样/过拟合（计划书估算 23.7，实测更高）。
  • Math 可用 0.609B（anneal_math2 430.7M + r3_ultradata_math 178.4M）→ ≈4.6 epochs，正常（计划标 5.25）。

4.4 🟡 step 0 loss = 11.72（≈ 随机）—— loss 起点未「接住」stable 末点

  • 训练日志首步：step 0 loss=11.7244（lr=0，≈ ln(vocab 129280)=11.77 = 随机量级），step 10=6.49 → step 20=3.45 → step 100≈2.0。
  • 一个 1.41T 已训练模型加载后首步 loss 应在 ~2.0，而非随机量级 11.72——说明 loss 起点没有「接住」stable 末点。可能成因：①torch.compile 首步热身 ②双移位使首步目标变异 ③数据分布突变（web→SFT/code/math）。50~100 步内回落到 ~2.0 → 权重大概率仍正确、被短暂扰动后恢复。
  • 注：此项为现象记录，非独立根因；需配合 §4.5 基线实验才能判定是「加载/起点」问题还是「decay 配方」问题。

4.5 ⏸ 关键判定实验缺失：起点 step_532000 的 14 集基线（待用户批准）

  • 这是判定失败环节的唯一关键实验：起点 xmodel25_history/step_532000（Xmodel-2.5 stable 末点盘上就绪，pytorch_model.bin 2.70GB + HF 全套）在本地尚未用同一 baize_xmodel_eval.sh 跑过 14 集。
  • 判定逻辑：
    • 若 step_532000 基线 ≈ 官方 65.40%（已收敛的 1.41T 模型）→ 评测/加载链路正常，decay 段把模型练坏了（坐实 §4 前三项）。
    • 若 step_532000 基线也仅 ~45% → 问题在起点/加载（如权重映射、tokenizer、eval 链路），而非 decay 配方。
  • 历史参照（同脚本同口径 CS8 zero-shot）：step_2000=46.12% / step_4000=49.11% / Xmodel-2.5 final=65.40%。我方 decay v2 final（44.97%）甚至比仅训练 4B 的 step_4000（49.11%）还低 4.14pp，强烈提示 decay 段在退化。
  • ⏸ 待用户批准后在 .29 跑（~1h，8×H100 已空闲）：bash run/baize_xmodel_eval.sh <step_532000路径> <out> step532000_baseline 0,1,2,3,4,5,6,7。

5. P-8 旁注（架构/参数量不同，不作归因依据）

P-8 不可作为对照基准：P-8 是 2.22B Mamba2-hybrid（56 层 Nemotron-H 式混合），与 decay v2 final 的 1.3B Dense Transformer 架构、参数量均有本质差异，且 P-8 是「从头预训练 44.4B」而非「decay 现成 1.41T 模型」。P-8（CS8 49.21% / CX6 6.81%）与 decay v2（44.97% / 6.21%）之间的 -4.24pp / -0.60pp 差异是多种因素（架构/参数量/训练曲线/起点）混合，不能据以判断 decay 配方好坏。本报告仅在第一版中误将 P-8 作主对照，现已更正；P-8 数字仅为完整起见列出，不再作为任何结论的支撑。

7. 小结

  • 本版已更正对照口径：主对照 = Xmodel-2.5 final（同起点 step_532000 / 同 71.2B decay / 相近配比），弃用 P-8 / step_6000 作主对照。
  • 结果：decay v2 final CS8 = 44.97%、CX6 = 6.21%；对比 Xmodel-2.5 final（65.40% / 32.90%）差 -20.43pp / -26.69pp，14 集全面大幅落后 → 「decay 段没练出来」。
  • 归因（按影响排序）：①双移位 bug（train 2-step / eval 1-step，代码级确认）②peak LR 1.67e-3 过高 + warmup 100 步过短 ③code ≈26 epochs 严重过采样 ④step 0 loss=11.72 起点异常 ⑤step_532000 基线缺失（关键判定实验）。
  • 修正 #648 笔误：code 实测 0.270B / ≈26 epochs（非 0.17B / 41）；架构为 1.3B Dense（非 2.22B Mamba2-hybrid）。
  • 待办：⏸ 用户批准后在 .29 补跑 step_532000 基线 eval，即可终判「decay 训坏模型」还是「起点/加载问题」，届时据实补一个码块到 §4.5。
  • 所有数字可溯源至 eval_decay_v2_final/eval_summary.txt、scaling_report/scaling_data.json 及训练脚本/日志（见 §6）。
