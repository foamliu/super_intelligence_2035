4. 🔴 EOS 多令牌处理风险（新发现）

发现：MiniCPM5-2B 有 两个 EOS：eos_token_id: [1, 130073]

  • Token 1 = </s>（标准 EOS）
  • Token 130073 = <|im_end|>（ChatML 结束）

风险：SGLang/verl 可能只认第一个 EOS → 生成在 <|im_end|> 处不停 → 输出超长 / 多轮混乱。

缓解（11/9 smoke test 必查）：检查生成是否在 130073 处停止；若不停止加 --stop-token-ids 130073。

6. ✅ GQA KV Cache 重新计算（R11 修正）

R11 原估计：13.8GB（用了 16 个 Q heads）→ R17 修正：4.1GB（GQA 只存 2 个 KV heads）

KV per token = 42 × 2 × 128 × 2 × 2 = 42 KB
Per sequence (8192 tokens):  42 KB × 8192 = 344 MB
Total for 12 sequences:     344 MB × 12   = 4.1 GB

影响：实际 KV cache 仅 4.1GB（R11 估偏高 3.4×）。gpu_memory_utilization=0.50 (24GB) 中模型 4.7GB + KV 4.1GB = 8.8GB，余量 15GB。可安全将 max_num_seqs 提到 16-24。

8. 残余风险

  1. SGLang 0.5.6.post3 + tokenizer 兼容：架构无碍，tokenizer 映射可能有版本差异
  2. multi-eos 在 verl 多轮：若只检测 </s> 不检测 <|im_end|>，多轮可能卡住
  3. 工具定义双重注入：chat_template + verl need_tools_kwargs 可能重复注入
  4. thinking 消耗预算：思考内容消耗 4096 token，可能导致工具调用空间不足

对 post-train 三步的侧重建议：

  • SFT：数据格式已验证 ✅。关注 chat_template 与 need_tools_kwargs 交互。
  • RL：EOS 多令牌是 P0 风险。KV cache 预算充裕（4.1GB），可增大 batch。
  • 评测：SGLang serve 架构无碍，需验证 EOS 行为确保生成正确终止。
