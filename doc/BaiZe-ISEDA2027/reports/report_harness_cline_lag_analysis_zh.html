cline 落后 opencode / hermes 根因分析

评测：SWE-bench Verified 500 题 · 7 路横评　|　基座：glm-5.3-flash　|　口径：Pass% = resolved/500

核心对比：cline 303/500 = 60.6% · opencode 415/500 = 83.0% · hermes 444/500 = 88.8%

数据源：run/harness/swebench_verified_full/reports/eval_glm53_*.json（最终 resolved/failed/empty_patch）＋ progress_glm53_*.json（逐题 wall_s / returncode / stdout·stderr tail / quota / timeout）＋ predictions_glm53/*.json（model_patch）

一、结论（TL;DR）

cline 落后的第一根因不是「不会写代码」，而是「93 个空 patch」。

cline 在 500 题里有 93 题（18.6%）交的是空 patch（model_patch 为空），而 opencode 只有 1 题、hermes 只有 4 题。这 92~89 题的空 patch 差异，解释了 cline 对 opencode 差距的 约 82%、对 hermes 差距的 约 63%。

而这 93 个空 patch 里，超过六成是基础设施故障（Token 额度 429 消耗尽、超时、上游 5xx、鉴权），并非模型「能力差」。真正的「写出 patch 但测试不过」的能力差距只占次要地位。

结论：93 个空 patch 中 约 62.5%（58 个）是 infra 故障（38 额度 + 13 超时 + 5 上游 5xx + 2 鉴权），按项目红线「429/5xx/timeout/adapter = infra，非能力」应当**重跑**，而不是记作能力失败。

4.1 额度耗尽的直接证据

多个空 patch 实例的 stderr 尾含网关原文，例如：

django__django-15315 → {"type":"error","message":"本次Token额度已用完，请等待19分钟后重试"} → model_patch: 0 bytes
django__django-15368 → {"type":"error","message":"本次Token额度已用完，请等待11分钟后重试"} → model_patch: 0 bytes

这些是 glm-5.3-flash 网关的瞬时额度限制撞上了 cline 的较慢节奏（见 §五），直接导致 patch 为空 —— 与模型解题能力无关。

4.2 「干净退出但无 diff」的 35 题

这 35 题 stderr 为空、returncode=0、stdout 尾只有 harness 脚手架的 cleanup: git reset --hard <hash>，即 cline 会话跑完但没有产出可提取的 diff。wall time 分布很宽：有 19s 秒退（django-13112，几乎没做事）、也有 1800s（顶满 30 分钟超时）。由于 progress 尾只保留了脚手架日志、未保留 cline 会话正文，这 35 题需要 transcript 级复查才能判定是「模型自认无需修改」还是「diff 提取失败」——本报告如实标注为「待定」，不臆断。

cline 平均每题慢 20~50%，且 p90 已经压到 1800s 的 30 分钟上限。更慢 → 同样时间段内更容易踩中网关的瞬时 Token 额度窗口、更容易超时 → 空 patch 更多，形成一个自我强化的恶性循环。此外 cline 的 no_patch（progress 口径）= 108，是 opencode（47）的 2.3 倍、hermes（32）的 3.4 倍，进一步印证「产出率」才是首要瓶颈。

即便排除空 patch，cline 的「一修就对」比例仍比 opencode 低 ~9pp、比 hermes 低 ~15pp。这是**真实存在、但次等量级**的能力/端到端差距（生成的 patch 质量或自测不充分）。但它只解释差距的 18%（vs opencode），远小于空 patch 的 82% 贡献。

七、结论与建议

结论（按贡献排序）

  1. 主因：cline 空 patch 93 题（18.6%），其中 ~62% 是 infra（额度/超时/5xx/鉴权），~38% 待 transcript 复查 —— 这一项解释了它对 opencode 差距的 ~82%。
  2. 次因：cline 竞速最慢（均值 620s、p90 顶格 1800s），更容易撞额度/超时，放大第 1 条。
  3. 第三：给 patch 后的条件成功率 74.4%，低于 opencode 83.2% / hermes 89.5% 的真实（但次要）差距。

建议动作

  1. 把 58 个 infra 空 patch 立即重跑：额度（38）+ 超时（13）+ 5xx（5）+ 鉴权（2），用重试机制补齐，预计至少回收其中相当一部分（额度/超时是瞬时态，重跑大概率能出 patch）。这是性价比最高的一步。
  2. 修口径：empty patch 若由 429/超时/5xx/鉴权导致，应回填进 infra_or_quota 桶，不要并进「能力失败」；否则 cline 的 60.6% 是被 infra 拖低的假象。
  3. 给 cline 降并发 + 加额度退避：cline 慢，就别跟 opencode/hermes 同并发抢同一把 glm-5.3-flash 额度的网关；单独额度 key 或错峰，配合 429 自动退避重试。
  4. 保留 cline 会话 transcript：当前 predict 只留脚手架 stdout/stderr tail，缺 cline 会话正文 → 35 个「干净退出无 diff」无法判定根因。后续 predict 落盘 cline transcript，归因才有据可依。

反直觉但必须说清：这张表如果拿给只看数字的人，会得出「cline 比 opencode 差 22pp」的结论；但把 infra 空 patch 拆出来后，cline 的「真实编码能力」与 opencode 的差距其实缩小到 ~9pp（74.4% vs 83.2% 条件修复率）这一量级 —— 剩余差距是 infra 管理差距，不是模型智商差距。
