Research Report 1: How to Fairly Compare Hybrid vs Dense Inference Speed & Cost

BaiZe Mamba2-Hybrid 2.220B (4/56 attn) vs Dense Llama 2.512B (42/42 attn)

sglang 0.5.9 | H100 80GB | ctx 4K–1M | Generated: 2026-10-07

Evidence grading: 【实测·本项目】 【一手文献·URL】 【二手·未核】 【推测·未验】

1. TL;DR

Our two benchmark runs produced opposite conclusions — P-9.11 (mem-frac=0.85, bf16 SSM) showed hybrid 2.18× faster prefill at 64K; P-9.11-E (mem-frac=0.3, float32 SSM) showed dense 3.3× faster at 128K. This is not a contradiction — it reveals five confounders that must be controlled for any fair comparison.

  1. Five confounders flipped our results 【实测·本项目】: (1) --mem-fraction-static (0.85 vs 0.3) determines KV pool size and hence which ctx levels are even servable; (2) --mamba-ssm-dtype (float32 vs bf16) doubles SSM state memory and slows hybrid ~2× 【一手文献·URL】; (3) prompt construction (char-count vs tokenizer-precise) caused spurious 128K failures; (4) batch size (bs=1 vs bs=8) changes prefill throughput by 280×; (5) parameter count mismatch (hybrid 2.22B vs dense 2.51B).
  2. VRAM "constancy" is a preallocation artifact 【实测·本项目】: sglang's --mem-fraction-static pre-allocates (weights + KV pool) at startup. At 0.3 on 80GB H100, this = ~24GB regardless of ctx. Dense KV pool caps at 455K tokens → dense OOMs at 512K. The true VRAM advantage of hybrid (measured without preallocation) is 0.22–0.44× at 128K (P-9.10③ direct measurement).
  3. Hybrid's real advantage is capacity, not speed 【实测·本项目】: Hybrid serves 1M ctx in ~26GB; dense cannot serve 512K+. At 128K–256K (both valid), dense's flashinfer attention is 1.7–3.3× faster in prefill and 2.2–2.6× faster in decode. This is expected: hybrid has only 4/56 attention layers, but those 4 layers become the bottleneck at ≥512K (~77% of prefill time at 1M, B1 measured).
  4. External evidence confirms the pattern 【一手文献·URL】: NVIDIA's 8B Mamba-2-Hybrid (43% Mamba-2 + 7% attention + 50% MLP) reports up to 8× faster token generation (Waleffe et al. 2024, arXiv 2406.07887). Nemotron-H (8% attention, arXiv 2504.03624) reports up to 3× faster inference. AI21 Jamba (1:7 attn:Mamba) fits 256K in 4GB KV cache vs Mixtral's ~32GB (8× reduction). All emphasize decode speed and memory, not prefill.
  5. Recommended protocol 【推测·未验】: Control all 5 confounders simultaneously: equal mem-fraction, same SSM dtype (bf16), tokenizer-precise prompts, match parameter count or report per-parameter, sweep bs∈{1,4,8,32}, measure both prefill and decode separately, and report capacity ceiling (max servable ctx) alongside speed.

3. External Evidence (First-Hand Sources)

3.1 Waleffe et al. 2024 — 8B Mamba-2-Hybrid vs Transformer 【一手文献·URL】

Paper: "An Empirical Study of Mamba-based Language Models" — Waleffe et al. (NVIDIA), arXiv 2406.07887, June 2024

URL: https://arxiv.org/abs/2406.07887

Key claims:

  • 8B Mamba-2-Hybrid (43% Mamba-2 + 7% self-attention + 50% MLP) exceeds 8B Transformer on all 12 standard tasks (+2.65 avg)
  • Predicted up to 8× faster token generation at inference time
  • Hybrid extended to 128K can perform Phonebook lookup perfectly even at >150K tokens — no position-encoding bottleneck (global attention without explicit PE)
  • Pure SSMs lag on tasks requiring "strong copying or in-context learning abilities (5-shot MMLU, Phonebook Lookup)"

Relevance: Our hybrid has 4/56 = 7.1% attention — very close to their 7% design. Their 8× speedup is at 8B scale with 3.5T tokens; our 2.2B with 20B tokens is much smaller, so absolute speedups will be smaller.

3.2 Nemotron-H — NVIDIA Production Hybrid (2025) 【一手文献·URL】

Paper: "Nemotron-H: A Family of Accurate and Efficient Hybrid Mamba-Transformer Models" — NVIDIA, arXiv 2504.03624, April 2025 (v4 Sep 2025)

URL: https://arxiv.org/abs/2504.03624

Key claims:

  • 8B model: 52 layers, 4 attention (8%), 24 Mamba-2, 24 MLP — same 4-attn design as our BaiZe
  • Up to 3× faster inference vs same-size Transformers (Qwen-2.5-7B, Llama-3.1-8B)
  • 56B model: 118 layers, 10 attention — MiniPuzzle distillation to 47B = 20% faster
  • FP8 training recipe achieves on-par with BF16
  • Replaces "majority of self-attention layers with Mamba layers that perform constant computation and require constant memory per generated token"

3.3 AI21 Jamba — Production Hybrid 【一手文献·URL】

Architecture: 1:7 attention-to-Mamba ratio, 52B total (12B active MoE), 256K context

URL: https://arxiv.org/abs/2404.01808 (Lieber et al., "Jamba: A Hybrid Transformer-Mamba Language Model", March 2024)

Key claim: 256K tokens in 4GB KV cache vs Mixtral's ~32GB — 8× memory reduction. 3× throughput at long context. Model fits on a single GPU.

Source for KV cache number: Multiple secondary sources cite this; original Jamba technical report. 【二手·未核】 for exact 4GB vs 32GB figure (not independently verified from primary source).

3.4 SGLang Documentation — mem-fraction-static 【一手文献·URL】

URL: https://docs.sglang.io/advanced_features/hyperparameter_tuning.html (accessed 2026-10-07)

Key mechanism (direct quote):

mem_fraction_static = (model weights + KV cache pool) / GPU memory capacity
Total memory usage = model weights + KV cache pool + CUDA graph buffers + activations

Implication: --mem-fraction-static determines the KV cache pool size at startup. The pool is pre-allocated. nvidia-smi reads this preallocation regardless of actual per-request usage. This is exactly why our VRAM appears "constant" at ~26GB across 128K–1M in P-9.11-E — it's the 0.3 × 80GB = 24GB preallocation, not actual per-request memory.

Log field to verify: max_total_num_tokens in startup log = pool capacity in tokens. Dense at 0.3: pool = 455K tokens (matches our observation). Hybrid uses dual pools (state + KV), so its effective token capacity is higher.

3.5 SGLang Skills — mamba-ssm-dtype Effect 【一手文献·URL】

URL: https://skillsmp.com/zh/creators/sgl-project/sglang/claude-skills-compute-mamba-ratio (accessed 2026-10-07)

Direct quote on fp32 vs bf16 SSM:

fp32 ssm vs bf16 ssm → ×≈2: only the SSM tensor doubles, conv stays fixed,
so the exact factor is (2·SSM + conv)/(SSM + conv) — just under 2.
conv is usually small relative to SSM, so estimate ≈2

Implication: Our --mamba-ssm-dtype float32 in P-9.11-E doubles the SSM state memory and likely ~2× slows the SSM computation compared to bf16. This is the single biggest confounder between P-9.11 (bf16) and P-9.11-E (float32). float32 was used for numerical stability, not production speed.

3.6 Mamba-2 Core Layer Speed (Dao & Gu 2024) 【一手文献·URL】

Paper: "Transformers are SSMs: Generalized Models and Efficient Algorithms Through Structured State Space Duality" — Dao & Gu, arXiv 2405.21060, May 2024

URL: https://arxiv.org/abs/2405.21060

Key claim: Mamba-2's core layer is 2-8× faster than Mamba-1, leveraging Tensor Cores via matrix multiplication formulation. This is training-time parallel scan speed, not necessarily decode-time recurrent speed.

4. Candidate List — Confounders to Control

C1. Equalize --mem-fraction-static P0 · Critical

① Motivation: P-9.11 used 0.85 (KV pool ~4.3M tokens), P-9.11-E used 0.3 (pool 455K tokens). Changes (a) which ctx levels are servable, (b) nvidia-smi VRAM reading (preallocation mask), (c) KV cache hit/eviction behavior under batch.
② Expected benefit: Eliminates the "VRAM looks constant" artifact and makes capacity ceiling comparable. Dense at 0.85 can serve up to ~4M tokens (vs 455K at 0.3).
③ Cost/risk: Low. Just set the same flag. Risk: at 0.85 with long ctx, may OOM during decode if activations spike.
④ Testable criteria: Run both models at mem-frac ∈ {0.3, 0.6, 0.85} at same ctx. Verify: (a) VRAM reading scales with mem-frac (not ctx), (b) dense capacity ceiling moves with mem-frac, (c) speed ratios stable across mem-frac within servable range.
⑤ Priority: P0 — without this, any VRAM or capacity comparison is meaningless.

C2. Use bf16 SSM dtype (not float32) P0 · Critical

① Motivation: --mamba-ssm-dtype float32 doubles SSM state memory and ~2× slows SSM computation 【一手文献·URL】 (SGLang skills, §3.5). This penalizes hybrid but not dense, flipping the speed ratio. P-9.11 (bf16) → hybrid 2.18× faster; P-9.11-E (float32) → dense 3.3× faster.
② Expected benefit: Recovers hybrid's true speed. Expected: hybrid prefill crossover ~50K (as in P-9.11), decode advantage at long ctx.
③ Cost/risk: Low for speed benchmarking. Risk: bf16 SSM may have numerical issues at very long ctx (>512K) — but for speed comparison at ≤128K (target range), bf16 is production-correct.
④ Testable criteria: Run hybrid at --mamba-ssm-dtype bf16 vs float32 at same ctx/bs. Measure: prefill tok/s, decode tok/s, VRAM. Expect: bf16 ~2× faster decode, ~2× less SSM state memory.
⑤ Priority: P0 — this single flag flipped our conclusion from "hybrid wins" to "dense wins."

C3. Tokenizer-precise prompt construction P1 · Important

① Motivation: P-9.11 used character-count to size prompts → 128K request had 146131 actual tokens > 131072 ctx limit → spurious "failed = max_pos limit" conclusion. P-9.11-E fixed this with AutoTokenizer.encode() precise counting.
② Expected benefit: Eliminates false failures. P-9.11's 128K failure was a prompt construction bug, not an architecture limitation (confirmed in B1 step 1).
③ Cost/risk: Trivial. Already fixed in P-9.11-E.
④ Testable criteria: All prompts: len(tokenizer.encode(prompt)) ≤ ctx - gen_len. Log actual token count in results JSON.
⑤ Priority: P1 — already solved, but must be standard in all future runs.

C4. Batch size sweep (bs ∈ {1, 4, 8, 32}) P1 · Important

① Motivation: P-9.11-E hybrid at 128K: bs1 prefill=1591 tok/s, bs8 prefill=447797 tok/s — 281× difference. Single-bs comparison is misleading for production cost analysis. Dense benefits more from batching (parallel attention matmul), hybrid benefits from parallel scan amortization.
② Expected benefit: Reveals throughput-vs-latency tradeoff. At high bs, hybrid's O(1) state per token may dominate dense's O(n) KV cache growth.
③ Cost/risk: Medium. Needs more GPU time (4× runs per ctx). Risk: at high bs × long ctx, may OOM for dense (KV pool exhausted).
④ Testable criteria: For each ctx ∈ {4K, 16K, 64K, 128K}, run bs ∈ {1, 4, 8, 32}. Report: aggregate tok/s, per-request TTFT, VRAM. Identify crossover bs where hybrid overtakes dense in aggregate throughput.
⑤ Priority: P1 — needed for production cost analysis, but not for architecture-level speed comparison.

C5. Parameter count normalization P1 · Important

① Motivation: Hybrid = 2.220B, Dense = 2.512B (13% more params). Dense has 42 attention layers vs hybrid's 4. Comparing raw tok/s favors the larger model in matmul-bound regimes.
② Expected benefit: Per-parameter normalization reveals architecture efficiency independent of model size.
③ Cost/risk: Low (just reporting). Risk: non-standard, may confuse readers.
④ Testable criteria: Report both raw tok/s and tok/s per billion parameters.
⑤ Priority: P1 — important for paper, not for engineering decisions.

C6. Separate prefill vs decode reporting (always) P0 · Critical

① Motivation: Prefill (compute-bound, parallel) and decode (memory-bound, sequential) have fundamentally different scaling. Hybrid's SSM advantage is primarily in decode. Dense's advantage is in prefill. Reporting only TTFT or e2e conflates both.
② Expected benefit: Clear attribution instead of a single ambiguous number.
③ Cost/risk: Low. Already measured separately in our experiments.
④ Testable criteria: Always report: TTFT, prefill tok/s, decode tok/s, e2e latency — as separate columns.
⑤ Priority: P0 — our data already does this; must remain standard.

C7. Report capacity ceiling alongside speed P0 · Critical

① Motivation: Dense OOMs at 512K (KV pool 455K < 504K prompt). Hybrid serves 1M. A speed comparison covering only ctx where both can serve misses hybrid's decisive advantage: it can serve contexts dense cannot.
② Expected benefit: Prevents "dense is faster" from being misleading. Dense is faster only where it can run.
③ Cost/risk: Low (just report max servable ctx for each model/config).
④ Testable criteria: For each (model, mem-frac) pair, report: max servable ctx at bs1, at bs8, OOM type (hard crash vs soft reject).
⑤ Priority: P0 — this is the headline advantage of hybrid architecture.

C8. Warmup + multiple runs for stability P1 · Important

① Motivation: P-9.11 bs8 at 4K: hybrid decode=31.1 tok/s (CUDA graph compilation overhead). Subsequent batches normal. Single-shot can be 10–50× off.
② Expected benefit: Eliminates warmup artifacts. Stable medians.
③ Cost/risk: Low. 3–5 runs per cell, discard first.
④ Testable criteria: 5 runs per cell, report median + IQR. First run discarded. Verify CUDA graph compiled before measurement.
⑤ Priority: P1 — important for publication-quality data.

5. Recommended Protocol + Time Box

Do these 3 things first (1 GPU, ~2h total):

Step 1: Controlled re-benchmark (C1+C2+C3+C6+C7) — ~1.5h, 1 GPU

Run the same matrix with all confounders controlled:

# Fixed config for BOTH models:
--mem-fraction-static 0.85      # C1: equal pool
--attention-backend flashinfer  # same backend
SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1

# Hybrid ONLY:
--mamba-ssm-dtype bf16          # C2: production dtype, not float32

# Matrix: ctx ∈ {4K, 16K, 64K, 128K, 256K, 512K} × bs ∈ {1, 8}
# gen_len=64, temp=0, 3 runs (discard first), tokenizer-precise prompts
# Report per cell: TTFT, prefill tok/s, decode tok/s, VRAM, max_servable_ctx, OOM type

Expected outcome: Hybrid prefill crossover ~50K (as P-9.11), decode advantage at ≥64K. Dense OOMs at 512K. VRAM will still look constant (0.85 preallocation) — supplement with B1-style direct measurement.

This is the single most important experiment — it reconciles our contradictory results and produces publication-quality data.

Step 2: Direct VRAM measurement (C7 supplement) — ~0.5h, 1 GPU

Use the B1 method (transformers chunked PPL, torch.cuda.max_memory_allocated()) to measure actual per-request VRAM without sglang preallocation. Already done for 4K–1M (B1, §2.4). No new work needed — just cite B1 data alongside sglang results.

Step 3: Batch sweep at target ctx (C4) — ~1h, 1 GPU, optional

At ctx ∈ {32K, 128K} (target range for agentic EDA), sweep bs ∈ {1, 4, 8, 32}. This answers: "at what concurrency does hybrid overtake dense in aggregate throughput?"

What NOT to do

  • Do not compare speed at ctx where only one model can serve (e.g., 512K: dense OOMs → "hybrid wins by default" is a capacity statement, not a speed comparison)
  • Do not report only TTFT or e2e — they conflate prefill and decode
  • Do not use float32 SSM for speed benchmarks — it's a stability hack, not production config
  • Do not use char-count prompt sizing — always tokenizer-precise
  • Do not compare 2.22B hybrid vs 2.51B dense without noting the parameter difference
