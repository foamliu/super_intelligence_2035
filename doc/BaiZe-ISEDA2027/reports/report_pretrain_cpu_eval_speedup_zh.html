BaiZe 2B CPU 评测提速报告

生成时间：2026-11-07 16:33

一、背景与问题

用户提问：「pretrain 全量 eval 需要时间这么久吗？已经使用 llama.cpp 了吗？线程并发多一点有帮助吗」

现状：iter_112000 的 8 集全量评测（21,465 题 / 73,106 次 loglikelihood 请求） 在 HF float32 单进程 16 线程下预估需要 22.5 天。

核心发现：
1. 线程已饱和：Mamba2-hybrid 的 SSM 顺序扫描不可并行，16 线程已达瓶颈
2. llama.cpp 后端可用：_fixed_ GGUF 转换器精度回归通过（Δacc ≤ 0.02）
3. 任务级并行：8 个任务拆成多进程，零技术风险
4. 综合提速：llama.cpp + 多服务器 → 预估 22.5 天 → ~5-20 小时

四、提速方案

方案 A：llama.cpp 后端

llama-server 加载 f16 GGUF，HTTP /completion 提供 loglikelihood 打分。

  • 转换：323 tensors, 4.2GB f16 GGUF
  • 服务：llama-server --parallel 8 -t 64 --cache-prompt
  • 吞吐：~1 it/s（8 并发 slot, 64 线程）
  • 预估全量：73,106 / 1.0 ≈ 20 小时

方案 B：HF 任务级多进程并行（零风险备选）

8 任务拆成 11 进程（hellaswag 4 片 + 7 任务），每进程 16 线程 = 176 核。

预估总耗时：木桶效应 → hellaswag 最慢 ≈ 2.1 天

方案 C：llama.cpp 多服务器实例（推荐）

多个 llama-server 实例（不同端口），每个处理不同任务子集。

七、结论

回答用户三个问题：

1.「需要时间这么久吗？」
不需要。通过 llama.cpp + 多服务器并行，22.5 天 → 5-20 小时。

2.「已经使用 llama.cpp 了吗？」
已切回。GGUF 转换成功，精度回归通过（Δacc ≤ 0.02），llama-server 已运行。

3.「线程并发多一点有帮助吗？」
单进程内加线程没有帮助（16 线程已饱和，SSM 不可并行）。 但多进程/多服务器并行有帮助——每个独立进程有自己的 SSM 扫描序列。
