一、背景与问题

用户提问：「pretrain 全量 eval 需要时间这么久吗？已经使用 llama.cpp 了吗？线程并发多一点有帮助吗」

现状：iter_112000 的 8 集全量评测（73,110 次 loglikelihood 请求） 在 HF float32 单进程 16 线程下，实测速率 26.7 s/req → 预估需要 542.2 小时（≈22.6 天）。

核心发现：
1. 线程已饱和：Mamba2-hybrid 的 SSM 顺序扫描不可并行，16 线程已达瓶颈
2. llama.cpp 后端可用：_fixed_ GGUF 转换器精度回归通过（Δacc ≤ 0.02）
3. 任务级并行：8 个任务各独占 1 个 llama-server（16 线程），零技术风险
4. 综合提速：llama.cpp + 8 服务器并行 → 详见第五节实测对照

四、提速方案（8 服务器 × 16 线程，推荐）

8 个 llama-server 实例（端口 8080–8087），每个 16 线程 8 并发 slot， 8 个任务各独占 1 个 server → 无资源争用。总线程 128（224 核机器安全），内存 ~40GB（2TB 充裕）。

配置服务器数每服务器线程总并发 slot总线程
旧 HF 串行1（进程内）16—16
GGUF 8 服务器（采用）81664128
为何 16 线程而非 56：第二节探测矩阵证明 16 线程饱和。56 线程会让单 server 因 SSM 顺序扫描的调度开销变慢。 8 服务器各 16 线程 = 任务级并行（每个 server 独立 SSM 扫描序列）+ 单任务内 16 线程饱和点，两者叠加最优。

八、结论

回答用户三个问题：

1.「需要时间这么久吗？」
不需要。通过 llama.cpp + 8 服务器并行，542.2 小时（22.6 天）→ 2.5 小时。

2.「已经使用 llama.cpp 了吗？」
已切回。GGUF 转换成功（4.2GB f16, 323 tensors），iter_10000 精度回归通过（HF vs GGUF Δacc ≤ 0.02）。 全量 GGUF eval 已完成：8 个 llama-server 实例（各 16 线程）+ 8 任务并行。

3.「线程并发多一点有帮助吗？」
单进程内加线程没有帮助（16 线程已饱和，SSM 不可并行）。 但多服务器并行有帮助——每个独立 server 有自己的 SSM 扫描序列。 当前方案 = 8 服务器 × 16 线程 = 128 核，叠加 llama.cpp 本身的推理加速。
