生成时间：2026-11-08 02:26｜检查点：iter_112000

一、背景与问题

用户提问：「pretrain 全量 eval 需要时间这么久吗？已经使用 llama.cpp 了吗？线程并发多一点有帮助吗」

现状：iter_112000 的 8 集全量评测（73,110 次 loglikelihood 请求） 在 HF float32 单进程 16 线程下，实测速率 26.7 s/req → 预估需要 542.2 小时（≈22.6 天）。

核心发现：
1. 线程已饱和：Mamba2-hybrid 的 SSM 顺序扫描不可并行，16 线程已达瓶颈
2. llama.cpp 后端可用：_fixed_ GGUF 转换器精度回归通过（Δacc ≤ 0.02）
3. 任务级并行：8 个任务各独占 1 个 llama-server（16 线程），零技术风险
4. 综合提速：llama.cpp + 4 NUMA-pinned 服务器并行 → 详见第五节实测对照

三d、NUMA-pinned 分阶段并行优化（2026-11-07 21:1x）

8 服务器同时跑 = 内存带宽争用 → hellaswag 13.6 s/it（76h/shard）！

8 服务器同时启动后实测发现：Mamba2-hybrid SSM 是内存带宽受限（非计算受限）， 8 个 server 共享 4 个 NUMA 节点的内存带宽 → hellaswag 退化为 13.6 s/it。 但同一 server 在独占 NUMA 带宽时可达 2-7 s/it → 带宽是瓶颈，不是线程。

优化方案：4 NUMA-pinned 分阶段并行（最终采用）
核心思想：每 NUMA 节点 1 个 server（独享带宽）→ 4 server × 16 线程 + 阶段重叠
N0(8080, cores 0-55): arc_easy→arc_challenge→openbookqa→hellaswag_chunk1b
N1(8081, cores 56-111): piqa_part1→hellaswag_chunk0b
N2(8082, cores 112-167): piqa_part2→hellaswag_chunk1a
N3(8083, cores 168-223): hellaswag_chunk0a（最大任务先启）
boolq/sciq/winogrande 在早期阶段已完成
配置并发 server每 server 独享hellaswag s/ithellaswag ETA
8 server 同时（旧）81/4 NUMA 带宽13.676 h/shard
4 server NUMA-pinned（采用）4全 NUMA 带宽2-7~6-9 h/shard
关键洞察：Mamba2 SSM 顺序扫描 = 内存带宽受限 → 并发 server 数增加会线性分摊带宽。 最优策略 = 每 NUMA 节点 1 个 server（独享带宽），阶段重叠消除串行等待。 taskset -c 绑定核心到 NUMA 节点确保内存访问局部性。

4 个 NUMA 节点各 1 个 llama-server（taskset -c 绑核），每 server 16 线程 8 并发 slot。 阶段重叠：arc 链完成后 → N0 切 hellaswag_chunk1b；piqa 两半完成后 → N1/N2 切 hellaswag_chunk0b/1a。

八、结论

回答用户三个问题：

1.「需要时间这么久吗？」
不需要。通过 llama.cpp + 4 NUMA-pinned 服务器并行，542.2 小时（22.6 天）→ 预估 ~14 小时（eval 进行中，详见第五节）。

2.「已经使用 llama.cpp 了吗？」
已切回。GGUF 转换成功（4.2GB f16, 323 tensors），iter_10000 精度回归通过（HF vs GGUF Δacc ≤ 0.02）。 全量 GGUF eval 运行中：4 个 NUMA-pinned llama-server 实例（各 16 线程）+ 任务级并行（hellaswag 分 4 片并行），日志在各任务子目录 *.log。

3.「线程并发多一点有帮助吗？」
单进程内加线程没有帮助（16 线程已饱和，SSM 不可并行）。 多 server 并行有帮助但有上限——Mamba2 SSM 是内存带宽受限，8 server 争用带宽反而退化。 最优策略 = 每 NUMA 节点 1 server + taskset 绑核 + 阶段重叠，独享带宽 + 消除串行等待。
