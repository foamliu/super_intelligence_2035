BaiZe pretrain 事故复盘：2026-10-20 凌晨 NCCL 崩溃与 6.4 小时损失

生成时间：2026-10-20 · 范围：Xmodel-2.5 80B decay v2 @ .29 · 性质：事故复盘 + 改进方案（本文为分析文档，不改变任何训练配置）

一句话结论：本次损失 6.4 小时 的主因不是硬件、不是模型，而是三个工程配置缺陷叠加——checkpoint 间隔过长（2000 步≈7.4h）、训练脚本未设置任何 NCCL 容错参数、崩溃后无人自动恢复（靠巡检发现，白等 75 分钟）。调大 NCCL timeout 是错误的解法，反而会让故障暴露更晚、损失更大。

2. 根因分析：三个独立缺陷叠加

缺陷 ①（直接原因）checkpoint 间隔 2000 步 ≈ 7.4 小时

SAVE_INTERVAL = 2000 步 × 12s/step ≈ 26,800s ≈ 7.4 小时才有一次保存
崩溃在 step 19,920，最近 ckpt 在 step 18,000 ⇒ 回退 1,920 步 ⇒ 6.4 小时白跑

这是纯工程配置问题，与硬件/模型无关。已修复：脚本现值 SAVE_INTERVAL=500（≈1.7h 一次，下次最多损失约 100 分钟）。

缺陷 ②（放大因素）训练脚本未设置任何 NCCL 容错参数

经代码核查（baize_xmodel25_decay_v2.py / .sh）：

检查项现状影响
dist.init_process_group(backend='nccl')无 timeout 参数使用 PyTorch 默认 10min，未显式化
NCCL_* 环境变量全脚本 0 处未启用异步错误处理
TORCH_NCCL_*0 处超时无现场 dump，事后无法定位
后果：崩溃只留下「rank6 collective timeout」一行，无法定位是哪张物理卡、卡在哪个 collective。这正是本次无法判断「是否硬件隐患」的原因。

缺陷 ③（时间放大器）无自动恢复，靠人工巡检发现

崩溃发生在 02:45，下一次巡检是 04:00 —— 75 分钟 GPU 全空。若巡检间隔更长，损失会进一步放大。

3. 关于「是不是某张卡坏了」——现有证据的边界

判断依据实测说明
resume 后 8 卡利用率96–100%若某卡永久损伤，不可能重新满载
resume 后步速~12s/step与崩溃前 11.9–12.1s 完全一致（无降频迹象）
error 计数0resume 后 1,400+ 步无任何错误
Xid / ECC / Remapped 硬件错误未采集这是判断「永久 vs 瞬时」的唯一硬证据，目前缺失
诚实结论：「训练已恢复正常」有充分证据；「该卡无硬件隐患」尚未证实。需补一次只读硬件检查（见 §5 P2）。

4. 为什么「调大 NCCL timeout」是错误解法

核心逻辑：NCCL timeout 是故障检测阈值（fail-fast 保护），不是故障预防机制。
把 10min 调到 30min，意味着崩溃时 8 张卡要多空转 20 分钟才报错退出 ⇒ 损失不是变小，而是变大。
做法效果说明
调大 NCCL timeout❌ 有害延迟发现故障，GPU 空转更久；不解决任何根因
加密 checkpoint✅ 直接减损损失 = 崩溃点到最后 ckpt 的距离，与 timeout 无关
自动重启 watchdog✅ 直接减损把 75 分钟无人处理压到 ≤5 分钟
开启超时 dump✅ 提升可诊断性超时时记录 rank/卡/collective 现场，下次能定位根因

5. 改进方案（按性价比排序）

P0 —— 立即实施（零风险，不碰运行中进程）

① 崩溃自动重启 watchdog

每 5 分钟检查 pgrep -f xmodel25_decay_v2；
若进程消失 且 最近 step < ITERS 且 24h 内崩溃 < 3 次
⇒ 自动 RESUME_DIR=<最新完好 ckpt> setsid bash baize_xmodel25_decay_v2.sh
判活须用 strings <log> | grep '^\[step'（该 log 为 sparse file，tail 不可靠）

收益：无人处理时间 75min → ≤5min。必须防死循环：加崩溃计数器，24h 内 ≥3 次则停止并告警（避免"崩-重启-再崩"烧掉更多时间）。

② 开启 NCCL 超时现场 dump

export TORCH_NCCL_DUMP_ON_TIMEOUT=1
export TORCH_NCCL_ASYNC_ERROR_HANDLING=1
export NCCL_ASYNC_ERROR_HANDLING=1

收益：下次若再超时，可精确定位 rank / GPU / collective，而不是只知道「rank6 timeout」。注意：这些是「更快发现问题」，不是「放宽超时」。

P1 —— 下次启动前（需先验证 NFS 带宽）

项现状建议
ckpt 间隔500 步（≈1.7h）250 步（≈50min）或改按时间触发（每 45min）
保存方式同步阻塞异步保存（torch.distributed.checkpoint）或「先写本地 + 异步同步 NFS」
ckpt 内容含 optimizer state（2.7GB）分档：仅权重（体积约减半）用于高频，全量用于低频
风险提示：ckpt 写 NFS，频率翻倍会使 NFS I/O 压力翻倍，可能反而引入新的超时。必须先实测 NFS 写带宽，或改用「本地写 + 异步同步」。

P2 —— 训练收尾后（回答硬件问题）

nvidia-smi -q | grep -iE 'Xid|ECC|Remapped|Retired'
nvidia-smi --query-gpu=index,temperature.gpu,clocks_throttle_reasons.active --format=csv
dmesg -T | grep -iE 'xid|nvrm|fallen off'

判据：无 Xid 且可纠正 ECC 错误为 0 ⇒ 确认为瞬时软件/网络抖动；有 Xid 或 ECC 增长 ⇒ 该卡有隐患，需专项巡检。

6. 对下一阶段（v5 Stable 1.5T）的强制要求

关键换算：本次 65.3 小时出现 1 次 NCCL 瞬时故障。
v5 Stable 计划纯训练 69.7 天 ⇒ 线性外推约 25 次同类故障。
若仍按 2000 步/ckpt + 无自动恢复，总损失 ≈ 25 × 6.4h ≈ 160 小时（6.7 天），且每次都要人工介入。这是不可接受的。

建议把以下内容作为 PLAN_V5_STABLE_1.5T.md 的启动前置条件（硬性）：

#要求验收标准
1崩溃自动恢复 watchdog进程消失 <5min 自动 resume；24h 内 >3 次崩溃则停止并告警（防死循环）
2checkpoint 策略损失窗口 ≤ 1 小时（按时间或 ≤300 步）；含完整性校验（逐文件大小 / 可加载性）
3NCCL 可诊断性TORCH_NCCL_DUMP_ON_TIMEOUT=1 + 显式 timeout 参数；故障后能定位到 rank/卡
4硬件基线启动前采集 Xid/ECC 基线；运行期每日采集一次，异常增长即告警
5断点续训演练正式开跑前做一次主动 kill + 自动恢复演练，验证 RTO（恢复时间目标）
