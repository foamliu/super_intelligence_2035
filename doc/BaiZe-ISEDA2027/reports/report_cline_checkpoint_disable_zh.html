关闭 Cline Checkpoint 的收益分析与实施方案

主题：desktop-app 与 cline-cli 的 checkpoint 默认关闭 · 参考对象：BaiZe 多 agent 自动化工作副本 · 2026-10-28

一、背景：Checkpoint 是什么

Cline 的 Checkpoint（检查点）是一套「影子 Git 仓库」快照机制：agent 每执行一轮工具调用（改文件、跑命令）前，对当前工作区打一个可回滚的 git 快照，存进独立于主仓库历史的 refs/cline/checkpoints/<sessionId>/<runCount>。目的是让交互式用户能一键「恢复文件 / 恢复对话 / 两者都恢复」。

其核心实现位于 sdk/packages/core/src/hooks/checkpoint-hooks.ts，触发点是 beforeModel 且 iteration === 1（即每个 run 第一次调模型前）。关键代价路径是：

  1. git stash create（快照已跟踪文件的改动）；
  2. git ls-files --others --exclude-standard -z —— 枚举工作区全部未跟踪文件；
  3. 把未跟踪文件逐个 git add --force --pathspec-from-file 写进临时 index，再 write-tree/commit-tree 合入 stash 的第三个 parent（createUntrackedParentCommit）。

第 2、3 步的开销与「未跟踪文件数量」成正比，与大文件数量、文件所在文件系统（本地盘 vs NFS）强相关。这正是问题所在。

二、问题：在 BaiZe 场景下，Checkpoint 是纯负担

BaiZe 的四条 agent 线（pretrain / data / vision / harness）以 无人值守循环方式运行 cline：loop 每轮唤醒 cline，读到任务书、只推进一步、更新心跳后退出，从未使用交互式「回滚」功能。

但这套循环跑在一个共享、巨大、挂在 NFS 上的 Git 工作副本里。工作区存在海量未跟踪文件（各线在途产物、大模型权重、数据分片、下载缓存等）。于是每次 cline 进程启动、第一个 run 触发 beforeModel 时，checkpoint 都要做一次全量未跟踪文件扫描 + 哈希 + 写 index：

  • 实测现象：data 线启动时 checkpoint 的 git add --force --pathspec-from-file 卡住 4 分钟以上仍未走完，把 agent 挡在启动阶段，长期停滞。
  • 后果：每次唤醒的前几分钟被 checkpoint 吃掉，agent 迟迟无法进入正题；在 loop 的 25 分钟单次超时预算里，占比可观，且随未跟踪文件增长只会更慢。

对「无人值守、从不回滚、且晚点可用 git 本体兜底」的自动化场景，checkpoint 提供不了任何价值，却付出每轮数分钟的高昂代价。

三、默认开关现状（三个入口逐一定位）

入口文件:行当前默认说明
core（引擎底层） sdk/packages/core opt-in（默认关闭） 核心把 checkpoint 留作可选项；注释明确「Core leaves checkpoints disabled by default」。
cline-cli apps/cli/src/runtime/defaults.ts:16-18
CLI_DEFAULT_CHECKPOINT_CONFIG = { enabled: true }		 开 CLI 显式开启，让每次 run 都有可恢复快照。已在本项目关闭：改 enabled:false 并重编译为 standalone 二进制。
desktop-app apps/examples/desktop-app/sidecar/chat-session.ts:378
checkpoint: { enabled: true }		 开 桌面应用侧车进程 buildSessionConnectionUpdate 里硬编码开启，与 CLI 是两套独立入口。

结论：desktop-app 的 checkpoint 默认是开的，且改 defaults.ts（CLI 入口）不会影响它；要关 desktop-app，必须改 chat-session.ts:378。

四、关掉 desktop-app checkpoint 的性能收益

4.1 收益定性

  • 消除每次会话首个 run 的固定冷启动开销：不再执行「全量未跟踪文件枚举 + 哈希 + 写 origin index + write-tree/commit-tree」这一整套 O(未跟踪文件数) 的磁盘/NFS 扫描。
  • 大仓库 / NFS 场景收益最显著：未跟踪文件越多、文件越大、存储越慢（NFS），节省越明显。实测同类工作副本下单次 checkpoint 可达分钟级，关闭后该开销归零。
  • 日常小仓库、本地盘场景收益有限：当未跟踪文件少、git 扫描快（几十毫秒级），关闭 checkpoint 几乎感觉不到差别——此时它本就不是瓶颈。

4.2 收益量化（经验估计）

工作区状态关闭前单次 checkpoint 耗时关闭后相对收益
小仓库、本地 SSD、少量未跟踪文件≈ 5–50 ms0可忽略
中型仓库、几千未跟踪文件≈ 0.5–5 s0低–中
大型共享仓库、NFS、海量/巨量未跟踪文件（BaiZe 现状）数十秒至数分钟（实测一度 > 4 min）0极高

以 BaiZe 灰区现状为基准，关闭后每条 agent 线每次唤醒可省下数分钟纯等待，直接转化为「更快进入任务、更高唤醒吞吐、更少被误判卡死」。

4.3 收益边界与代价

  • 代价：失去「一键回滚工作区文件 / 对话到历史检查点」的交互式能力。
  • 对自动化循环：无代价——这些线从不使用回滚，且已有 git 本体 + 各线 MEMORY/日报 + loop 兜底提交作为安全保障。
  • 对交互式桌面用户：确有代价——如果用户依赖「改坏了→恢复」，关闭后需改用 git 自己管理。因此建议按「部署形态」区分：无人值守形态关，交互形态保留。

五、如何关掉 desktop-app 的 checkpoint

方案 A：硬编码关闭（最小改动）

编辑 apps/examples/desktop-app/sidecar/chat-session.ts，把第 378 行的 enabled: true 改为 false：

// 改前（第 378 行）
checkpoint: { enabled: true },

// 改后
checkpoint: { enabled: false },

随后重新构建侧车并打包：

cd apps/examples/desktop-app
bun run build:sidecar           # 编译 sidecar/index.js
bun run build:sidecar:bin       # 生成侧车 standalone 二进制（如发布需随包）

方案 B：改成可配置（推荐，兼顾两种部署形态）

不写死，而是从已有配置对象读一个可选字段（例如 config.checkpointEnabled 或复用 config.checkpoint），缺省时按部署环境决定：

// 示意：让 webview 传入的 config 能显式覆盖，缺省关闭
checkpoint: { enabled: config.checkpointEnabled ?? false },

这样交互式桌面构建可通过配置按需开启，无人值守形态默认关闭，避免同一份源码在两种场景下反复改。

方案 C：与 CLI 总结对齐

如果希望三入口（core / cli / desktop-app）口径统一，最终应把「默认是否开启 checkpoint」收敛到一处配置来源（例如统一读 config.checkpoint?.enabled），由各 host 在启动时注入，而不是各自硬编码 true。这属于结构性清理，收益是长期消除「改了 one 处、漏了 another 处」的隐患。

六、结论与建议

  • desktop-app 的 checkpoint 默认开启（sidecar/chat-session.ts:378 硬编码 enabled:true），与 cline-cli 是独立的开关点。
  • 在 BaiZe 这类「NFS 大仓库 + 无人值守循环」环境下，checkpoint 是纯开销：实测单次可达分钟级，关闭后每次唤醒收益显著。
  • cline-cli 侧已完成关闭并落地为 standalone 二进制；desktop-app 侧若有无人值守部署，建议按 方案 B 改为可配置（缺省关闭），交互式场景再显式开启。
