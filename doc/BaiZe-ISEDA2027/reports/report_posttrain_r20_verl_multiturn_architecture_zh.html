R20: verl 多轮 Tool-Calling Rollout 执行架构深度分析

日期：2026-11-07 · 阶段：零 GPU 深入调研 · 目的：11/9 GPU 到位前填补 verl 多轮执行流程知识缺口

摘要：R1-R19 覆盖了 verl+SGLang 集成的架构选型、工具 schema、数据格式、SGLang 调参和 GRPO 超参，但端到端执行流程从未深入分析。R20 发现两条独立的多轮架构路径、delta tokenization 的 token 一致性风险、以及配置中6 项问题（含 2 项 P0）。已修复 4 项，新增 6 项 11/9 验证清单（V9-V14）。

2. 端到端执行流程

PPOTrainer.sample_batch → AgentLoopManager.generate_sequences
  → wake_up(servers) → sync_weights(FSDP→SGLang)
  → split → AgentLoopWorker → ToolAgentLoop.run()
    → LLMServerClient.generate(prompt_ids) → response_ids
    → ToolParser.extract_tool_calls → BaseTool.execute → repeat
    → AgentLoopOutput(prompt_ids, response_ids, response_mask)
  → sleep(servers) → custom_reward_function → train_step

关键设计：① token 级 generate 接口（非 Chat API）；② sticky session（KV cache 复用）；③ weight sync（rollout 前 FSDP→SGLang，后休眠释放显存）。

3. 状态机与 Delta Tokenization

状态转移：PENDING→RUNNING→(TOOL_CALLING→RUNNING)*→COMPLETED，循环上限=max_assistant_turns。

Delta 分词：对每个 assistant 消息计算 tokenize(template(messages[:i+1])) 与 tokenize(template(messages[:i])) 的差值 → LLM token (mask=1)。Tool 响应 mask=0。

Token 一致性风险：ToolParser 剥离标签后 re-encode ≠ 原始 token_ids → 轨迹偏离 policy 分布 → PPO 不收敛。缓解：tokenization_sanity_check_mode: strict ✅
