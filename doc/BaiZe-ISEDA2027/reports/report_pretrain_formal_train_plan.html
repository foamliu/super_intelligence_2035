§2 密度差异归因

2.1 为什么 tok/comp-byte 跨源差异巨大 (0.0636–0.4977)？

核心结论：v3 报告中 0.0636–0.4977 的密度范围是 tok/compressed-byte（用 du -sb 压缩后的 parquet/jsonl 字节做分母），它混合了两个独立因素：
① 压缩率：parquet/jsonl 的压缩比因数据类型而异（英文网页 3-5x，中文 1.5-2x，代码 2-3x，数学 1.5-2x）
② 分词密度：同一原始文本，不同 tokenizer 产生不同 token 数
正确做法：用 .bin 字节 / 4 计算 token（v4 §1.1），或用未压缩原始 UTF-8 字节计算 tok/raw-byte（需解压，本次未做）。

2.2 密度差异的物理机制

英文网页 (tok/comp-byte ≈ 0.07)：英文文本压缩率最高（~4-5x），因为英文单词高度冗余、重复模式多。du -sb 后字节大幅缩小，使得分母极小 → tok/comp-byte 极低。但实际 tok/raw-byte ≈ 0.32-0.39，是所有源中最低的——英文 BPE 分词效率高，每个 token 平均覆盖 ~2.6-3.1 个原始字节。

中文网页 (tok/comp-byte ≈ 0.35)：中文压缩率低（~1.5-2x），因为汉字信息密度高、重复少。同时，DeepSeek tokenizer 对中文的覆盖率不如英文——每个汉字常需 2-3 个 token。tok/raw-byte ≈ 0.52-0.69，约为英文的 2 倍。

代码 (tok/comp-byte ≈ 0.45)：代码的符号密集、短标识符多，BPE 分词后每字节产生更多 token。压缩率中等（~1.5-2x）。tok/raw-byte ≈ 0.68-0.90，是所有源中最高的。

数学 (tok/comp-byte ≈ 0.50)：LaTeX 公式和数学符号的 BPE 分词效率最低——大量特殊字符（\, _, ^, {, }）各占独立 token。压缩率也低。tok/raw-byte ≈ 0.75。

SFT (tok/comp-byte ≈ 0.07)：JSONL 格式含大量重复的 "role": "user", "role": "assistant" 等模板 → 压缩率极高（~4-5x）。但tok/raw-byte ≈ 0.26-0.33，因为对话文本以英文为主。

2.3 对跨源 Token 估算的影响

关键教训：v3 报告使用 tok/comp-byte 对 en_v1_4 估算 ~217B。这个估算恰好合理（因为 0.0777 的密度乘以压缩字节给出了正确量级），但方法论是错的——它假设压缩率与 base en 相同。如果 en_v1_4 的压缩率不同（很可能，因为它是不同版本的过滤），估算可能偏差 ±30%。

v4 正确做法：对未分词的源，应使用同类型已分词源的 tok/raw-byte（而非 tok/comp-byte）进行估算，或直接等待全量分词完成。

SFT 过采样风险：当 D ≥ 226B 时，SFT 源 (29B) 的 epoch > 1.0，开始重复采样。在 D=2,232B (全量) 时，SFT 被采样 9.9 次。这会导致：
① 模型对 SFT 数据过拟合，泛化能力下降
② 需要考虑增加 SFT 数据量 或 降低 decay 段 SFT 占比
③ 或在 D > 500B 时启用 SFT 数据增强（回译、改写等）

建议：D ≤ 200B 时 SFT epoch ≤ 0.88，安全；D = 400B 时 epoch = 1.76，需监控；D ≥ 800B 时 epoch ≥ 3.52，必须增加 SFT 数据或调整配比。
