§2 背景与目标

2.1 已有实测结果

本线已完成 Xmodel-2.5 final 的 14 集 lm-eval 评测（2026-10-15，baize_xmodel_eval.sh，trust_remote_code=True）：

  • Xmodel-2.5 final（decay+LCR 后）：CS8 Avg = 65.40% / Complex6 Avg = 32.90% （MEMORY_PRETRAIN_2B.md #451，lm-eval harness 0.4.x）
  • Xmodel-2.5 stable 段（step_2000/4000/6000）：CS8 显著低于 final（stable 段尚未退火）
  • Xmodel-2 final：CS8 = 64.82% （同上）
  • BaiZe P-8（44.4B，Mamba2-hybrid 2.22B）：CS8 = 49.21% / CX = 6.81% （不同架构/规模，不作直接基准）

2.2 实验目标

核心命题：用 BaiZe 自己配比的 80B 数据（MiniCPM5 数据源 + P-8 decay 配方）， 对 Xmodel-2.5 stable 末 ckpt 做 WSD decay，争取 14 集超越 Xmodel-2.5 官方 final。 若超越 → 证明「BaiZe decay 数据配比/annealing 策略」优于 Xmodel 官方（至少在同等模型上）。

公平性：我们给 80B 预算 > Xmodel 官方 71.2B，数据量不落下风； 若 80B 内 14 集超 Xmodel-2.5 final，即证明 BaiZe 的 decay 数据配比/annealing 策略更优。 超出 80B 仍不超 → 需分析是数据配比问题还是 annealing 策略问题。

2.3 Xmodel-2.5 训练全景（出处：method.tex L35-44）

Xmodel-2.5 采用五段 WSD 调度，总 560k 步 / 1.4T tokens：

  • Warmup (W)：2k 步，LR 线性升至 1.67×10⁻³（hidden）/ 0.01（embedding）
  • Stable S1：270k 步，batch = 3712×480 ≈ 1.78M tok/步 → ~480.6B tok
  • Stable S2：260k 步，batch = 3712×960 ≈ 3.56M tok/步 → ~925.6B tok
  • Decay (D)：20k 步，指数退火，batch ≈ 3.56M tok/步，66.9% SFT，AdamW→Muon → 71.2B tok
  • LCR：10k 步，同 66.9% SFT，batch = 16384×240 ≈ 3.93M tok/步，ctx 16k → 39.3B tok

出处：Xmodel-2.5/ACL2026/method.tex §Three-Phase WSD（L35-44）；result.tex §Training Loss（L36-37）

§5 Decay 数据配比（BaiZe 80B）

5.1 P-8 Decay 配方（沿用）

沿用 BaiZe P-8 实测 decay 配方：SFT 64% : L3 24% : code 8% : math 4% （baize_p8_decay.sh L7-10；DATA_MIX_RECIPE.md §3）

SFT 64% 的依据：Xmodel-2 超过 400 次试验 → SFT 最优 60-69%，取 64% （xmodel-2.tex L141-146, 154）。 Xmodel-2.5 取 66.9%，我们的 64% 在区间内，差异 2.9pp 可接受。

Token 计数口径：.bin 字节 ÷ 4（int32 dtype，v4 §1.1 口径）。 Code = anneal_code 90.34M + r3_ultradata_code 180.04M = 270.38M； Math = anneal_math2 430.71M + r3_ultradata_math 178.40M = 609.11M。 出处：v4 report §1 逐源精确计数

🔴 Code/Math 分词数据严重不足：80B decay 需 code 6.4B + math 3.2B = 9.6B token， 但已分词的 code+math 仅 879M token（epoch 5-24x）。原因：P-8 decay 仅 4.8B token（12% = 577M）， 现有分词量为其 1.5 倍已足够；但 80B decay 放大 17x，缺口巨大。

5.3 解决方案（三选一，推荐方案 A）

方案 A：重分词 UltraData-Code/Math（推荐）

原始 parquet 已下满（UltraData-Code 1121 pq / UltraData-Math 1823 pq）， 用 Xmodel-2.5 tokenizer（129280 vocab）重新分词 → 可获得 ~100B+ token 的 code/math 数据。 预估分词耗时：~2-4 GPU·h（CPU 分词，不占 GPU）。

推荐理由：① 数据量充足（epoch < 1）；② 使用 Xmodel-2.5 原生 tokenizer 消除兼容性风险； ③ 原始数据已就位（DATA_RESEARCH.md Q1(1) 确认 1121/1823 parquet 全在）。

方案 B：调整配比降低 code/math 占比

将配比调整为 SFT 67% : L3 27% : code 3% : math 3%（code/math 各降 5pp）， code 需 2.4B（epoch 8.9x）、math 需 2.4B（epoch 3.9x）。 仍过采样但幅度可控；配比偏离 P-8 实测配方，但接近 Xmodel-2.5 的 66.9% SFT。

方案 C：接受高 epoch（不推荐）

直接使用现有分词数据，code epoch 23.7x、math epoch 5.25x。 decay 段质量优先，高 epoch 不一定有害，但 code epoch 23.7x 极端，模型可能过拟合。

5.4 SFT 过采样分析

SFT 合计 29B token，80B decay 中占 64% = 51.2B → epoch 1.76。 v4 report §3 已分析此风险。 Xmodel-2 原文（L152）提到 SFT 数据经 SimHash 去重后重复使用（+1.7% gain）， 说明 decay 段适度重复采样 SFT 是可接受甚至有益的。 epoch 1.76 在安全范围内。

6.2 Muon 优化器说明

为什么用 Muon（用户直令 + Xmodel 官方同构）：
  • Xmodel-2.5 method.tex L46-49：decay 段 AdamW → Muon 单变量切换 → +4.58pp 绝对提升
  • 此处的训练对象是 Xmodel 模型（其 stable 末 ckpt），不是 BaiZe 原生模型
  • BaiZe P-8 的 dist_muon 发散是 BaiZe Mamba2-hybrid 架构的问题，不适用于 Xmodel（Dense Llama 式）
  • Xmodel 官方自己也是「stable 段全用 Muon 会发散 → 只在 decay 段用 Muon」

出处：method.tex L46-49（Optimizer ablation）；任务书运维指令 2026-10-16 L19（用户直令）； EXPERIMENTS_PRETRAIN_2B.md P-8 dist_muon 发散记录

6.3 seq=3712 vs BaiZe 4096 的差异处理

Xmodel-2.5 原生 seq = 3712，BaiZe 固定口径 seq = 4096（用户直令 2026-10-14）。 本实验训练的是 Xmodel 模型，须用 Xmodel 原生 seq 3712（非 BaiZe 4096）。 已分词的 BaiZe 数据按 seq 4096 切片，需重新按 3712 切片。 若重分词（方案 A），则直接按 3712 分词+切片，无此问题。

§9 风险与可行边界

9.1 🔴 Tokenizer 不兼容（最高风险）

问题：BaiZe tokenizer_eod vocab = 128,000； Xmodel-2.5 tokenizer vocab = 129,280（DeepSeek-v3）。 两者均基于 DeepSeek tokenizer，但 vocab_size 不同 → token ID 映射可能不一致。 若直接使用 BaiZe 分词数据训练 Xmodel-2.5 模型，轻则性能下降，重则训练崩溃。

验证方案（训练前必做，~10 min）：

# 对比两 tokenizer 对相同文本的编码结果
python3 -c "
from transformers import AutoTokenizer
bz = AutoTokenizer.from_pretrained('data/tokenizer_eod')
xm = AutoTokenizer.from_pretrained('xmodel25_snapshot_dir')
test = ['Hello world', '你好世界', 'def foo(): pass', '2+2=4']
for t in test:
    b_ids = bz.encode(t)
    x_ids = xm.encode(t)
    print(f'{t[:30]:30s} BZ={len(b_ids):3d} XM={len(x_ids):3d} match={b_ids==x_ids}')
"

若不兼容（预期大概率不兼容，因 vocab 差 1280）→ 必须用 Xmodel-2.5 tokenizer 重分词所有数据源。 重分词工作量：SFT 29B + L3 20.56B + code/math → 原始 parquet 已就位， CPU 分词 ~4-8h（不占 GPU），产出的 .bin 量 ~100-120 GB（磁盘需确认余量）。

9.2 🟠 Checkpoint 格式转换

Xmodel-2.5 ckpt = HF 格式（pytorch_model.bin + modeling_xmodel2.py）。 BaiZe 训练框架 = Megatron-Core（pretrain_launcher.py）。两条路线：

  • 路线 A（推荐）：用 HF Trainer 训练（直接加载 XmodelForCausalLM），无需格式转换。 已有 eval 脚本 baize_xmodel_eval.sh 证明 HF 路线可用。 缺点：HF Trainer 可能比 Megatron-Core 慢 10-20%。
  • 路线 B：转换 HF ckpt → Megatron-Core 格式，用 pretrain_launcher.py 训练。 需编写转换脚本，且 Muon 优化器需在 Megatron-Core 中适配 Xmodel 架构。更复杂但吞吐更高。

建议：先用路线 A 冒烟验证（100 步），确认 Muon + Xmodel 架构稳定后决定是否切路线 B。

9.3 🟡 Muon + Xmodel 架构兼容性

Muon 优化器对权重矩阵做 Newton-Schulz 正交化。 Xmodel-2.5 = Dense Llama 式（标准 Linear 层），与 Muon 兼容性预期良好（Xmodel 官方已验证 +4.58pp）。 但 BaiZe 的 Megatron-Core Muon 实现是为 Mamba2-hybrid 调试的，需确认对标准 Transformer 层的兼容性。

验证：100 步冒烟训练 → 检查 loss 下降 + grad_norm 稳定 + 无 NaN。 若 dist_muon 不兼容，可回退 AdamW（但失去 +4.58pp 理论增益）。

9.4 🟡 SFT 过采样（epoch 1.76）

SFT 29B / 51.2B 需求 = epoch 1.76。Xmodel-2 原文（L152）表明 SFT 数据去重后重复使用是可接受的。 但 1.76 epoch 意味着 ~44% 的 SFT 数据被看 2 遍 → 可能对特定 SFT 样本过拟合。 缓解：① decay 段侧重质量而非多样性，适度重复可接受；② 可在第二 epoch 加入数据增强； ③ 若最终性能不理想，可降低 SFT 占比至 36%（29B/80B，epoch 1.0）。

9.5 🟢 seq=3712 vs 4096

非问题但需注意：Xmodel 原生 seq 3712 < BaiZe 口径 4096。 本实验训练 Xmodel 模型 → 用 3712（不违反 BaiZe seq=4096 口径，因该口径仅约束 BaiZe 原生训练）。

9.6 🟢 无 LCR 段的影响

Xmodel-2.5 官方在 decay 后有 10k 步 LCR（ctx 16k），13-task avg 从 52.36 → 52.49（+0.13pp）。 本方案不含 LCR → 长上下文能力可能略弱。但 14 集评测中无长上下文任务 → 对本实验结论无影响。

10.5 诚实条款（不确定度声明）

  1. 吞吐估算不确定度 ±15%：350-400K tok/s 为基于参数量比例的外推， 实际吞吐取决于 Muon 开销 + HF Trainer 效率 + 数据加载瓶颈，需 100 步冒烟实测校准。
  2. Tokenizer 兼容性未验证：128K vs 129K vocab 大概率不兼容 → 重分词可能为必做项， 额外增加 ~4-8h 前置时间 + ~100GB 磁盘占用。
  3. Muon + Xmodel 兼容性：Xmodel 官方已验证 +4.58pp，但我们的 Muon 实现（Megatron-Core muon.py） 是为 Mamba2-hybrid 调试的，对标准 Transformer 的兼容性需冒烟验证。
  4. SFT 来源差异：BaiZe 用 MiniCPM5 的 UltraData-SFT（公开），Xmodel 用内部 SFT-Mixed（未公开）。 SFT 质量差异是核心对比变量，但也意味着「超越/未超越」可能归因于 SFT 数据质量而非配比策略。
  5. 80B vs 71.2B 的公平性：我们多给 8.8B token（12.4%），若仅微超 final， 不能完全排除「多给数据」的贡献。建议同时跑 71.2B 对照组（同配比同超参，仅 decay token 不同）。
  6. 跨架构结论迁移边界：本实验训练的是 Xmodel Dense 架构， 结论可迁移到「Dense LLM 的 decay 策略」，但不可直接迁移到 BaiZe Mamba2-hybrid 架构 （P-8 dist_muon 发散已证明架构敏感性）。
