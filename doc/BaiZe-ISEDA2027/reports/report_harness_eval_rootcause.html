1. HERO + TL;DR

Bottom line: Module/env install failures account for 21.5% (451/2100) of all entries -- 14.8% (311) have explicit infra_failure_reason (missing_module 272 + OOM 28 + no_tests 11), plus 6.7% (140) unmarked patch-apply failures (mainly sphinx base_commit mismatch, 92 entries). True "wrong-fix" is only 48.0% (1007/2100), not the previously reported 83%. 5 repos (65 unique instances x 7 harnesses = 455 entries) are systematically suppressed by eval infra failures (matplotlib/pytest/sphinx/astropy/flask). Fixing eval infrastructure (P0) can recover ~23 additional resolved/harness (65 instances x 34.8% eval-OK rate), raising cline's resolve rate from 28.7% to ~36.3% (eval-OK caliber). Score vs external: 28.7% is comparable to Aider (26.3%) but below top agents (SWE-agent+Claude4=56.7%); eval-OK caliber 34.8% is mid-tier -- suppressed ~6pp by infra failures.
TL;DR:
  • "83% wrong-fix" was a miscalculation: old report (7x30, django+sympy only) got 83% in the eval-OK subset; full 2100 shows true-wrong-fix = 48.0%.
  • Infra failures concentrated in 5 repos: matplotlib (freetype download), pytest (version conflict), astropy (OOM), sphinx (base_commit mismatch), flask (no tests collected).
  • Patch tolerance is already 4-level (git apply -> --3way -> --reject -> patch --fuzz=5), NOT single-level as task spec claims -- that info came from outdated SWEBENCH_OFFICIAL_CRITERIA_VERIFICATION.md.
  • Root cause is NOT "missing deps" but pip install -e . compiling C extensions in unshare sandbox -> needs external downloads -> blocked by sandbox network policy.
  • Kimi K2 official 65.8% is SWE-bench Verified (500 tasks), not comparable to SWE-bench Lite (300 tasks).

3. Root Cause Chain

Core finding: Our r1_eval.py uses unshare sandbox (not Docker), with one shared rootfs template per repo (run_serial_kimi.py:24-37). The template has a conda env (/opt/miniconda3/envs/testbed), but pip install -e . in eval.sh tries to recompile C extensions, requiring external source downloads (e.g. freetype) -> sandbox network blocked -> build fails -> ImportError -> tests not collected -> f2p_total=0 -> classified as pbf.

3.5 "83% wrong-fix" Recheck

Old report claimed "Dominant failure mode is wrong fix (83% of all failures)". Recheck: that number was based on 7x30=210 entries (django+sympy only), valid within the eval-OK subset (83% = 85/103 pbf). But in the full 2100:
  • true-wrong-fix = 1007/2100 = 48.0% (not 83%)
  • env-or-patch-fail = 451/2100 = 21.5% (old report ignored this category entirely)
  • resolved = 574/2100 = 27.3%
Conclusion: the 83% was a caliber bias (subset vs full), not a data error, but severely misled the "main failure is model ability" narrative. Actually 21.5% of failures are infrastructure problems that can be fixed to significantly boost scores.

4.3 Patch tolerance -- already implemented (task spec correction)

4-level patch tolerance is already implemented. Task spec says "only single-level git apply" -- this came from outdated SWEBENCH_OFFICIAL_CRITERIA_VERIFICATION.md:103 (written 2026-10-06). Actual r1_eval.py:63-68 has 4 levels: 
GIT_APPLY_CMDS = [
    "git apply --verbose",          # 1. strict
    "git apply --verbose --3way",   # 2. three-way merge
    "git apply --verbose --reject", # 3. partial match
    "patch --batch --forward --fuzz=5 -p1 -i",  # 4. fuzzy
]
One more level than official (3-level). The 451 patch-not-applied entries failed all 4 levels (not a tolerance issue) -- root cause is rootfs state (see section 3).
Summary: how many resolved can be recovered?
  • All P0: matplotlib(~8) + pytest(~7) + sphinx(~4) + scikit-learn(~3) = ~22 additional resolved/harness
  • cline: 86 -> ~108 (of 300), resolve rate 28.7% -> ~36.0%
  • eval-OK caliber (235 instances): 86/235 = 36.6% (P0 fix should approach this)
  • P0+P1: + astropy(~2) + blocked fix(~3) = ~27 additional resolved/harness, rate -> ~37.7%

5.2 Analysis

Our 28.7% vs leaderboard 18-32%:
  • Within reasonable range. On SWE-bench Lite leaderboard, GPT-4o-class models + agent harnesses score 18-32%. Our 28.7% with kimi-k2.6-cloud + cline is in the upper-middle of this range.
  • The 3.3pp gap vs Agentless + GPT-4o (32.0%) can be partially attributed to infra failures -- eval-OK caliber 36.6% already exceeds Agentless.
  • But not directly equivalent: (1) we use unshare sandbox not official Docker; (2) kimi-k2.6-cloud is a different model from GPT-4o; (3) our 300-task sample may have selection bias.
Our 28.7% vs Kimi K2 official 65.8%:
  • Not directly comparable -- 65.8% is SWE-bench Verified (500 tasks, human-verified), ours is SWE-bench Lite (300 tasks, different subset).
  • SWE-bench Lite and Verified are different benchmarks: Lite is the easier file-localized subset, Verified is the human-verified solvable subset. Different task sets, different difficulty.
  • Kimi K2 official uses their own agent harness + official Docker eval; we use cline harness + unshare eval.
  • kimi-k2.6-cloud may not be the same model as open-source Kimi K2 (1T MoE) -- cloud version may have additional optimization or distillation. Not verified.

6. Honesty Clause

  1. Sample size: 300 SWE-bench Lite instances x 7 harnesses = 2100 entries. Single backbone (kimi-k2.6-cloud), no multi-run variance estimation.
  2. Eval environment: unshare sandbox (not official Docker), one shared rootfs template per repo. Fundamentally different from official SWE-bench per-instance Docker -- our scores are internal caliber, not directly comparable to leaderboard.
  3. Infra failure impact: 5 repos (65/300 instances) systematically suppressed to near-0 by eval infra failures. The eval-OK caliber (235 instances) 36.6% is an upper-bound estimate assuming infra is fixed, not a measured value.
  4. Web timeliness: leaderboard data from llmrun.dev (2026-10-10 search), ACM SE paper (2025), Moonshot blog (2025-07). Kimi K2 official score is SWE-bench Verified (not Lite), not directly comparable. Relationship between kimi-k2.6-cloud and open-source Kimi K2 not verified.
  5. Patch tolerance: Task spec cited SWEBENCH_OFFICIAL_CRITERIA_VERIFICATION.md claiming "single-level git apply", but actual r1_eval.py:63-68 already has 4-level tolerance. That document (2026-10-06) was written before 4-level was added or was not updated.
  6. Reproducibility: all statistics directly computable from kimi_pilot_results.json. Eval logs at /nas_train/app.e0031982/harness_work/logs_eval/. Generation script: gen_report_eval_rootcause.py.
