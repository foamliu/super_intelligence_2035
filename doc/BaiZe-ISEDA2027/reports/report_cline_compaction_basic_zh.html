Compaction 默认策略改为 basic 的收益分析与实施方案

主题：cline 上下文压缩默认策略 agentic → basic · 含 basic 机制详解与「切了会不会变笨」顾虑缓解 · 2026-10-28 修订

一、背景：Compaction 是什么，为什么会有它

会话上下文是有上限的。当对话历史（系统提示 + 全部消息 + 工具定义）逐渐逼近模型输入窗口时，必须对旧历史做「压缩」，腾出空间让 agent 继续往下走，否则请求会被模型直接拒绝（超窗）。Cline 的这套机制叫 Compaction（上下文压缩），实现在 sdk/packages/core/src/extensions/context/ 下。

按默认参数：当会话已吃掉可用输入预算的 90%（COMPACTION_TRIGGER_RATIO = 0.9）时触发一次压缩，压缩后压低到约 70%（DEFAULT_TARGET_RATIO = 0.7）。一句话：它只在你真的快用满上下文时才动手，平时完全不介入。

Compaction 支持两种策略（CoreCompactionStrategy = "basic" | "agentic"，types/config.ts）：

策略原理调 LLM结果形态
basic确定性规则：按「保留原则」裁剪历史，把被丢掉的工具活动提炼成结构化摘要。否原文保留 + 结构化足迹摘要
agentic额外调一次 LLM，把历史总结成一段自然语言「continuation note」。是LLM 生成的语义摘要

二、basic 的原理与机制（详解，源码为证）

以下全部来自 sdk/packages/core/src/extensions/context/basic-compaction.ts 与 compaction-shared.ts 的逐条实现。理解这些，就能判断「切到 basic 会不会变笨」——答案是：不会，因为它不是简单截断，而是有明确保留优先级的结构化裁剪。

2.1 四条硬保留原则（runBasicCompaction 的核心注释原文）

设计目标

「Typed user prompts always survive. The latest typed turn keeps its newest messages verbatim within the token target. Older turns keep their concluding assistant answer when it fits. Everything else is dropped and re-surfaced as dropped-work summaries.」

翻译成白话，压缩后一定还在的东西是：

  1. 你打过的每一句用户指令（typed user prompt）都会原样保留——sanitizedTypedByIndex 强制把所有 isTurnStartMessage（真正的用户输入，非工具回执）计入预算且永不删除。也就是说「目标、约束、要求」这些最关键的东西一条都不丢。
  2. 最新一轮对话的最近消息整体 verbatim 保留——keptExtraIndices 从尾部向前收录，直到撞到 token 预算才停。当前正在做的事，上下文是完整的。
  3. 历史每一轮都保留它的「结论性 assistant 答复」——olderFinalByIndex 从新到老为每个旧 turn 挑出那轮的最终回答（不含 tool_use 的纯文本答复）保留，「成果」不丢。
  4. 被丢弃的部分不是凭空消失，而是提炼成结构化摘要——buildDroppedWorkSummaryBlock 生成 <SYSTEM_NOTICE> 块，明确告知模型「这里压缩过了，你做过这些事」。

2.2 丢弃中间过程时，保留的是「结构化足迹」，不是空白

被压缩掉的大头是工具调用的中间过程（每个 read/edit 返回的长文本、每条命令输出）。basic 用 summarizeToolActivity 把这些中间过程萃取成三类足迹（ToolActivitySummary）：

足迹类型内容实现
Files read读过哪些文件（含 read_files 输入里的行长区间 path:start-end）formatReadFileEntry
Files edited改过哪些文件（从 editor/apply_patch 结果的带号 diff 里反解出 path:start-end）extractDiffLineRange + tool_use_id 关联
Commands ran跑过哪些命令（每条截断到 100 字符）truncateCommandForSummary + COMMAND_SUMMARY_CHAR_LIMIT

最终拼成一段高度浓缩的追述，贴在幸存的下一条用户消息上：

<SYSTEM_NOTICE>
Earlier context was compacted. Summary of your actions after the request above:
Files read:
  src/a.ts:12-40
Files edited:
  src/b.ts:100-180
Commands ran:
  npm run build
Your recent responses:
  ...（最近几条 assistant 回复原文）...
</SYSTEM_NOTICE>

关键洞察：agent 续作真正需要的，从来不是「曾经 read 返回的每一行原文」，而是「我碰过哪些文件、改到哪几行、跑过什么命令」——basic 恰好把后者原样保住了。

2.3 三个「防变笨」的工程细节

  • 保留最近 3 条 assistant 回复原文：PRESERVED_ASSISTANT_TEXT_COUNT = 3，跨轮衔接的「最近回答」会 verbatim 进入摘要块，模型不会断片。
  • 裁切边界落在安全位置，绝不拆散 tool_use/tool_result 对：isSafeCutBoundary 只允许在 assistant 消息或用户 turn 起点裁切；把保留尾向前「吸」到 assistant 消息（keep suffix starts at an assistant message），确保不会留下一个没有对应结果的孤儿 tool_result（那会被 provider 直接拒绝）。
  • 旧答复剥离 thinking 块：sanitizeOlderAssistantFinal 在保留历史结论时丢掉 thinking/redacted_thinking（历史思考过程对续作无价值，还占 token）。

2.4 反复压缩不会越压越烂（防退化）

  • 已压缩产出被「冻结」：markPreservedByCompaction 给被压缩存活的消息打 compaction: "preserved" 标记，下一次压缩 isPreservedByCompaction 跳过它们，绝不二次折叠——不会出现「摘要上叠摘要」的退化。
  • 用量指标跨轮累计正确：aggregateUsageMetrics 把即将被剥离的 per-message 指标（input/output/cache/cost tokens）聚合到压缩消息的 metadata 上，成本与用量统计不丢。
  • 估算漂移有安全阀：token 估算是约数，projectionTargetTokens = min(max(target, keptTokens), triggerTokens) 兜住「目标已低于必须保留内容」的极端情况，绝不为了追数字去砍掉用户指令。

三、顾虑缓解：切到 basic 到底会不会「智能下降」？

3.1 直答：对自动化 agent 场景，不会

「智能」在 agent 长任务里的承载物就三样：目标/约束、当前进展、历史结论。basic 的保留优先级正是对着这三样设计的——指令原文全留、最新一轮 verbatim、历史每轮的最终答复保留。它丢掉的只是「中间过程的细节」，而细节已经被提炼成文件级/行号级/命令级足迹。

反而 agentic 的语义摘要存在一个 basic 没有的风险：LLM 压缩有损还可能幻觉——总结者把「改了 A」记成「改了 B」，或把细节讲偏。basic 是确定性萃取文件名与行号，不会曲解事实。

3.2 两者对比：丢信息的「位置」不同，而非「多 vs 少」

维度agentic（LLM 摘要）basic（确定性裁剪）
用户指令是否保留原文被总结进 prose，原文可能改写原文全部保留
当前轮上下文部分进入摘要verbatim 保留
历史结论融合成一段话每轮最终答复原文保留
中间工具足迹可能被总结遗漏或改述文件/行号/命令结构化保留
事实准确性有幻觉/曲解风险确定性，无曲解
隐含的纯文本推理论证可能被语义摘要保留得更好可能被机械裁剪（见 3.3）

3.3 诚实的边界：何时 basic 略逊、何时无所谓

  • 可能略逊：一段「大量纯文本设计讨论、几乎没有工具调用」的超长对话里，agentic 的语义摘要可能比机械裁剪更好地保留中间推演脉络。
  • 对本项目基本无关：四条 agent 线都是「工具调用密集、结论导向」——读任务书、跑命令、改文件、写心跳。这类会话压缩时，basic 丢弃的恰好是最没信息量的工具输出长文本，保留的恰好是续作所需。
  • 更大概率不触发：loop 每轮唤醒往往只推进一步就退出，会话短，根本到不了 90% 触发线；即使 harness 跑超长单题触发压缩，也主要发生在「工具循环很长」的情形——正是 basic 最稳的情形。

结论：对交互式重度纯文本长会话，保留 agentic 作为可选覆盖；对无人值守自动化场景，basic 是「同等可靠、更便宜、无幻觉」的默认。

四、默认值现状（三处口径）

位置文件:行内容
CLI 默认常量apps/cli/src/utils/compaction-mode.ts:11-14DEFAULT_CLI_COMPACTION_MODE = "agentic"

CLI 暴露 --compaction <mode>（agentic|basic|off，默认 agentic），但 loop 未显式传参，走的就是默认 agentic。

五、收益分析（把默认改为 basic）

5.1 消除压缩时的额外 LLM 调用

agentic 在压缩时会额外发起一次模型请求（generateSummary → handler.createMessage("Summarize the provided coding session ...")）：

  • 多一次完整往返延迟（首 token + 流式生成摘要）；
  • 双向 token 支出（喂入历史 + 生成摘要输出）；
  • 外部失败点：summarizer 有输入预算上限，超限直接「budget exhausted」跳过；模型不可用/超时抛错。

basic 是纯内存裁剪，零额外交互、零附加成本、无外部失败点。

5.2 量化对比

维度agentic（现状）basic（建议）收益
压缩时额外 LLM 往返1 次/触发0 次消除
压缩附加 token 成本输入历史 + 输出摘要0归零
压缩延迟数百 ms ~ 数 s≈ 0大幅降低
外部失败点有（超限/超时/模型错）无消除
事实准确性有幻觉风险确定可复现提高

补充：overflowRecovery（模型端主动拒超窗时强制压缩）本就固定走 basic 确定性路径（「recovery must not depend on another successful LLM request」）——安全性不因本改动而有任何下降。

六、实施方案

6.1 配置层（零构建，立即可用，先做）

各 agent 线 <data-dir>/settings/global-settings.json 把 compactionStrategy 改为 basic：

{
  "compactionStrategy": "basic",    // 原 "agentic"
  "compactionEnabled": true         // 保留启用，仅换策略
}

6.2 源码层（固化默认，治本）

① CLI 默认常量 —— apps/cli/src/utils/compaction-mode.ts：

export const DEFAULT_CLI_COMPACTION_MODE = "basic";  // 原 "agentic"

② engine 兜底 —— sdk/packages/core/src/extensions/context/compaction.ts:285：

const strategy = userCompaction?.strategy ?? "basic";  // 原 "agentic"

③ help 文案同步 —— apps/cli/src/utils/compaction-mode.ts：

CLI_COMPACTION_MODE_OPTION_DESCRIPTION = "Context compaction mode: agentic|basic|off (default: basic)";

6.3 重新构建与验证

cd <cline-repo>
bun run build:sdk
bun -F @cline/cli build
# 需要 standalone 二进制时：
cd apps/cli && bun build --compile ./src/index.ts --outfile <out>

验证：不传 --compaction 跑一个能触发压缩的长会话，观察日志——basic 打印 Performed basic compaction（含 tokensBefore/After、messagesRemoved、budget Actions），agentic 则打印 Generated compaction summary / Agentic compaction summarizer diagnostics。确认无后者即可。

七、结论

  • basic 不是「粗鲁截断」，而是保留用户指令原文 + 最新轮 verbatim + 历史各轮结论 + 工具足迹结构化摘要的确定性裁剪，并有三层防退化机制（安全裁切边界、压缩产物冻结、指标聚合）。
  • 对自动化 agent 场景，「切到 basic 会导致智能下降」的顾虑不成立：它保留的恰是续作所需信息，丢掉的恰是最无信息量的工具输出长文本，且无 agentic 的幻觉风险。
  • 把默认从 agentic 改为 basic：消除压缩时的额外 LLM 调用、token 成本与失败点，换来更快、更便宜、更可复现的压缩；交互式重纯文本长会话可显式 --compaction agentic 覆盖。
  • 落地顺序：先配置层（compactionStrategy=basic，零构建），再源码层固化默认。
