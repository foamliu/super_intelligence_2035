Compaction 默认策略改为 basic 的收益分析与实施方案

主题：cline-cli 上下文压缩默认策略 agentic → basic · 参考对象：BaiZe 多 agent 自动化循环 · 2026-10-28

一、背景：Compaction 的两种策略

当会话上下文接近模型输入上限时，Cline 会触发 Compaction（上下文压缩），压掉较早的历史内容，为后续对话腾出空间。核心实现位于 sdk/packages/core/src/extensions/context/compaction.ts，支持两种策略（CoreCompactionStrategy = "basic" | "agentic"，见 types/config.ts:156）：

策略原理是否调用 LLM特点
basic
（确定性裁剪）		 纯确定性算法：按规则截断、保留最近 N tokens、压缩工具活动摘要，不生成新文本。 否 快、零额外交互、结果可预测、无外部失败点。
agentic
（LLM 摘要）		 调 LLM（generateSummary，见 agentic-compaction.ts:62）把历史总结成「continuation note」。需要额外的 summarizer 模型/输入预算。 是 摘要语义质量更高、可能保留更多隐含上下文；但多一次模型往返、有延迟/成本/失败风险。

另外还有一个 off（彻底关压缩），不在本报告讨论范围。

二、默认值是 agentic（三处口径）

当前压缩默认策略是 agentic，分散在多个入口：

位置文件:行内容
CLI 默认常量apps/cli/src/utils/compaction-mode.ts:11-14DEFAULT_CLI_COMPACTION_MODE = "agentic"
engine 兜底sdk/packages/core/src/extensions/context/compaction.ts:285strategy = userCompaction?.strategy ?? "agentic"
运行时全局设置settings/global-settings.json"compactionStrategy": "agentic"（各 agent 线均有）

CLI 暴露了 --compaction <mode> 命令行参数（agentic|basic|off，默认 agentic），但 loop 脚本没有显式传参，因此实际走的就是默认 agentic。

三、建议：默认改为 basic（纯确定性裁剪，不调 LLM）

把三处默认从 agentic 统一切到 basic，让「不传参」的默认行为变成纯确定性裁剪。核心考量：在无人值守、由 loop 反复唤醒的自动化场景下，agentic 带来的语义增益几乎用不上，却要付出实打实的 LLM 成本与延迟。

四、收益分析

4.1 消除额外 LLM 调用（成本 & 延迟）

agentic 策略在压缩时会额外发起一次模型请求（generateSummary 走 handler.createMessage("Summarize the provided coding session ...")）。这意味着：

  • 每单位压缩少量延迟：多一次完整的模型往返（首 token 延迟 + 生成摘要文本的流式时间）。
  • 每单位压缩少量 token 支出：要把历史内容作为输入喂给 summarizer，再生成 summary 输出，双向都有 token 账单。
  • 失败风险：summarizer 有输入预算上限（summarizerInputLimit），超限会「budget exhausted」直接跳过；模型不可用/超时会抛错。basic 无此类外部依赖。

4.2 收益量化（经验估计）

维度agentic（现状默认）basic（建议默认）收益
压缩时额外 LLM 往返1 次/触发0 次消除
压缩附加 token 成本输入历史 + 生成摘要0归零
压缩延迟数百 ms ~ 数 s≈ 0（纯内存裁剪）大幅降低
外部失败点有（超限/超时/模型错）无消除
结果确定性非确定确定可复现提高

4.3 收益边界（诚实说明）

  • 损失：agentic 的语义摘要可能比「机械截断」保留更多隐含上下文，极端长对话下 reduced 后的续写质量可能略低。对自动化循环（每轮只读任务书、推进一步、写心跳即退出）影响极小——它本就不依赖跨压缩的精细长程记忆。
  • 适用前提：本建议针对「无人值守 / 高频唤醒 / 成本敏感」场景。交互式重度长会话若依赖高质量摘要，可显式 --compaction agentic 覆盖。
  • 注意：overflowRecovery（模型端拒绝超上下文时强制压缩）本就固定走 basic 确定性路径（见 compaction.ts 注释「recovery must not depend on another successful LLM request」），不受此改动影响——安全性不降。

五、实施方案

5.1 改代码默认值（源码层，治本）

① CLI 默认常量 —— apps/cli/src/utils/compaction-mode.ts：

export const DEFAULT_CLI_COMPACTION_MODE: Extract<
	CliCompactionMode,
	"agentic" | "basic"
> = "basic";  // 原为 "agentic"

② engine 兜底 —— sdk/packages/core/src/extensions/context/compaction.ts:285：

const strategy = userCompaction?.strategy ?? "basic";  // 原为 "agentic"

③ CLI help 文案同步 —— apps/cli/src/utils/compaction-mode.ts：

export const CLI_COMPACTION_MODE_OPTION_DESCRIPTION =
	"Context compaction mode: agentic|basic|off (default: basic)";

5.2 改运行时全局设置（配置层，立即可用，不改源码）

各 agent 线的 <data-dir>/settings/global-settings.json 里把 compactionStrategy 改为 basic：

{
  "compactionStrategy": "basic",   // 原 "agentic"
  "compactionEnabled": true        // 保留启用，仅换策略
}

5.3 重新构建与验证

cd /nas_train/app.e0031982/harness/cline
bun run build:sdk
bun -F @cline/cli build
# CLI standalone 二进制（如需随包发布）
cd apps/cli && bun build --compile ./src/index.ts --outfile <out>

验证：不传 --compaction 启动一个长会话，观察压缩时是否仍产生 summarizer LLM 调用（agentic 会在日志打印 Generated compaction summary / Agentic compaction summarizer diagnostics，basic 则无）。

六、结论与建议

  • cline 压缩双策略中，默认是 agentic（调 LLM），basic（确定性裁剪）明明更省却被默认避开。
  • 将默认改为 basic：消除压缩时的额外 LLM 往返、token 支出与外部失败点，换来更快的压缩与可复现行为；仅在依赖「语义摘要保长程记忆」的交互式场景才有负面影响。
  • 建议分两步落地：先改 5.2 配置层（零构建成本、立即生效），再合并 5.1 源码层（固化默认，避免未来配置漂移）。
