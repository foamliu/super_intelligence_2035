TL;DR

cline 326/500 = 65.2% 排第 3，落后 opencode 401/500 = 80.2%（−15pp）。 75 题差距归因为两大类、三小类：

  • ① 适配器可靠性（55 题未产出 patch，损失 ≈39 题）——这是主因。
    • ①-A 静默退出（35 题，~2s/rc=0）：cline 启动后立即退出、不改任何文件。opencode 同类为 0 题。 根因 = cline 在 API 网关错误（429/503/Forbidden）时仍退出 0（run_harness.py:151-159 已记载）， 且 cline 的 stdout 被 run_single.py 吞掉 → predict_one 的错误检测失灵。 opencode 走 gw_proxy（127.0.0.1:9090）有重试，cline 直连 agi-gateway 无重试。 35 题中 opencode 解决 27 题 → 纯适配器 bug 导致 27 题白丢。
    • ①-B 超时卡死（18 题，~1800s/rc=1）：cline 跑满 30 分钟超时仍未产出 patch。opencode 同类仅 2 题。 18 题中 opencode 解决 12 题 → cline 陷入工具调用死循环 / 上下文耗尽。
  • ② 补丁质量（116 题产 patch 但测试失败，净损 34 题）——次要因素。 在 441 题共同评估集上，opencode 解决 44 题 cline 未解决，cline 仅解决 10 题 opencode 未解决 （McNemar n01=10, n10=44, discordant=54，极显著）。cline 倾向于产出更大但不够精准的补丁。

结论：cline 的 15pp 落后主要不是模型能力问题，而是适配器层 bug（静默退出 35 题 = 7% 的题直接白丢）。 若修复适配器（路由 gw_proxy + 检测 stdout + 加重试），预计可回收 ≈39 题 → resolve 率 ≈73.0%，缩小与 opencode 的差距至 ≈7.2pp。

三、失败归因（cline 的 174 题「未 resolve」拆解）

3.1 适配器静默退出（35 题，≈2s / rc=0 / 0 字节 patch）——最大可修复项

现象：cline CLI 启动后 ~1.5–2.7s 即退出，returncode=0，未修改任何文件，stderr 为空。 stdout 仅有 running cline (patched) ... → rc=0 timed_out=False wall=1.5s → model_patch: 0 bytes。

分布特征：35 题散布在 run order pos=26~478（非聚集 → 排除瞬时 API 断网）， 覆盖 astropy/django/matplotlib/xarray/pytest/sklearn/sphinx/sympy 全部 8 个仓库（非仓库特有）， problem_statement 平均长度 2292 字符（与成功题 1640 无显著差异 → 排除超长 prompt）。

根因（三层证据链）：

  1. cline 在 API 错误时仍退出 0——run_harness.py:151-159 ClineDriver 文档明确记载： "the gateway answered Forbidden on the first model call, while cline still exited 0"。 cline CLI 不把 API 错误传播为非零退出码 → r.returncode == 0 为真 → git_patch(workdir) 返回空 diff。
  2. cline stdout 被 run_single.py 吞掉——run_single.py:79-82 只打印 res.stderr[-400:]， 不打印 res.stdout（含 cline 的 --json 错误信息）→ run_verified_full.py:185 的 blocked = ("forbidden" in out ...) 检测的是 run_single.py stdout，不含 cline 自身 stdout → 错误检测失灵。
  3. cline 直连 agi-gateway，opencode 走 gw_proxy——ClineDriver（run_harness.py:170-178）base URL 来自 ~/.cline/data/globalState.json（openai@http://agi-gateway.cxmt.com/v1），直连网关无重试。 OpencodeDriver（run_harness.py:238-249）用 gw/ 模型经 gw_proxy（127.0.0.1:9090）中转， gw_proxy 内部有重试 → opencode 同类静默退出 = 0 题。

影响：35 题中 opencode 解决 27 题、失败 8 题。 即 cline 因适配器 bug 白丢了 ≈27 个本可解决的题（占 500 题的 5.4%）。

五、可改进点清单（按优先级 / 风险排序）

#改进点类别预计回收风险实现方式
1cline 路由 gw_proxy（像 opencode 一样经 127.0.0.1:9090 中转）适配器 / 低风险≈27 题 (+5.4pp)低改 ClineDriver base URL → gw_proxy；或设 OPENAI_BASE_URL=http://127.0.0.1:9090/v1
2run_single.py 透传 cline stdout适配器 / 低风险检测修复低run_single.py:79-82 加 if res.stdout: print("[stdout tail] ..." + res.stdout[-400:])；predict_one 的 blocked 检测即可生效
3cline API 错误加重试适配器 / 低风险≈27 题低在 predict_one 层加 retry（rc=0 且 patch_len=0 且 wall<10s → 重跑 1 次）；或在 gw_proxy 层加重试
4减少超时卡死上下文管理 / 中风险≈12 题 (+2.4pp)中① 降低 timeout 1800s→900s（快失败快重试）；② 上下文窗口到 80% 时强制收敛；③ 参考 CLINE_IMPROVEMENT_OPPORTUNITIES.md O3
5提高补丁精准度模型/架构 / 高风险≈34 题 (+6.8pp)高参考 CLINE_IMPROVEMENT_OPPORTUNITIES.md O1-O5（memoized 投影 / 检查点原子化 / 压缩 Hook / 任务记忆持久层 / token 计量优化）

合计预计回收：改进点 1+3（修复静默退出）≈ 27 题 + 改进点 4（减少超时）≈ 12 题 + 改进点 5（补丁质量）≈ 34 题 = ≈73 题 → resolve 率 ≈79.8%，与 opencode（80.2%）的差距缩小至 ≈0.4pp。

注：改进点 1 和 3 效果重叠（都修静默退出），取 max；改进点 4 和 5 独立可叠加。 实际回收取决于题集重叠度，上界约为各项之和。
