BaiZe-2B（Mamba2-hybrid）seq 长度 × tok/step 吞吐网格报告

⚠️ 根因更正（2026-10-25，cfg0a 对照实验确认）—— 本报告的「seq 效应」归因已被推翻

本网格在「seq 翻倍」时同步缩小了 gbs/accum（为适配显存），构成双变量混淆：观测到的 4096→8192 悬崖无法区分「序列长度效应」与「批几何效应」。

决定性对照 cfg0a（固定 seq=4096、仅复刻 cfg1 的小批几何 gbs512/accum8/mbs4）= 稳态 116,898 tok/s @ 14.2% MFU —— 用 seq=4096 复现了 5.2× 跌幅（基线 606K→117K），与 cfg1(seq8192)=108K 几乎一致。若 seq 是主因，cfg0a 应≈606K；实测 117K ⇒ seq 非成因。

真因（rev3 复测，2026-10-26 #786 终定）= CUDA Graph 在 HBM 顶格（~81GB）时的 replay 病态停滞，非显存带宽 memory-bound。cfg0a 每步只做基线一半 token(2.10M vs 4.13M)却花 2.64× 墙钟(17.9s vs 6.8s)、MFU 73.6%→14%——该低 MFU 是 graph 停滞的症状非成因。决定性复测：同一 tok/mb=16384 配方关掉 --enable-cuda-graph后恢复 561,126 tok/s = 0.93× 8K 满速，峰值显存 81GB→75.5GB（一个 flag 修复，无需 CP、无需 recompute）。CUDA graph 两侧均 built 112 成功 → 非「图回退」，而是「图 replay 在显存顶格时病态停滞」。

本报告的网格测量数据（cfg1–4 的 tok/s、显存、step time）仍然有效，但其「seq→吞吐悬崖 / SSM 超线性」的因果解释 hereby 作废。归因演进：rev1「GPU 饥饿」→ rev2「memory-bound（显存顶格）」→ rev3 终定「CUDA Graph 顶格停滞」（显存顶格是必要条件非成因；rev2 hereby 修正）。H1–H9 中 H4(低 MFU)为症状、H2(CUDA-graph)以「顶格停滞」形式确认（非回退），H1/H5/H6/H8/H9 全证伪。

处置（rev3 终版，2026-10-26 #786）：本段原先预测「保持 tok/step ≥ 4M 即可回到 ~500–600K」—— 该预测已被 cfg2/cfg4 证伪（tok/step=4.19M≈基线却仍 111,897/121,495 慢档）。驱动变量 = tok/microbatch/GPU = mbs×seq（与 seq/批几何无关，11 格 ladder 证实）：tok/mb ≤ 12288 → graph 可开、满速（如 seq8192/mbs1=605,012 tok/s）；tok/mb = 16384 → 关 --enable-cuda-graph 即满速 561K/75.5GB（无需 CP、无需 recompute；recompute 对 Mamba2-hybrid 非降显存杠杆，已证伪）；tok/mb > 16384 → 须 Context Parallel（32K CP=1 OOM@81GB，CP=2 待 patch flash-attn-3 API）。故 seq≥8192 可用。原「不建议用 seq≥8192」结论 hereby 撤销；「tok/step≥4M 回到 500-600K」预测 hereby 作废；rev2「memory-bound」归因 hereby 修正为「CUDA Graph 顶格停滞」。

用户原话：「在每步训练数据量不变（2M/4M，对应 S1 和 S2）的情况下，看看增大 seq 对训练吞吐的影响。」
nodes2 节点 × 8×H100 80GB SXM5（.12 master + .29 worker），DP=16 / TP=1 / PP=1
modelBaiZe-2B Mamba2-hybrid（56 层 = 24 Mamba2(SSM) + 4 Attention + 28 MLP-only，hidden=2048，heads=16，参数量 2.220B；hybrid_override_pattern=M-M-M--M-M*-M-M-M-M--M*-M-M-M-M-M*--M-M-M-M-M*-M--M-M-M-，attention 位于第 10/22/33/45 层；TP=1/PP=1，sequence_parallel=false、context_parallel=1）
data16 片 p5b_l3_train_s{0..15} 1:1 blend，真实数据（mock=false）；同组 3 个 seq 共用同一批 packed shard，仅运行时 --seq-length 切块长度不同 → 严格单变量
recipeFP8 tensorwise(hybrid) + CUDA Graphs（即 e18 配方），与双机基线字节级一致；Mamba2 SSM dtype 由 mamba2_hybrid_2b.recipe 内部管理（launcher 无 --mamba-ssm-dtype flag，与 606K 基线同口径）
ncclNCCL_IB_GID_INDEX=3 / MTU=4096 / TC=106 / TIMEOUT=22（主从两侧照抄），RoCE 多通道
measureITERS=80，前 20 步 warmup 不计，median 取 step 30–80（6 数据点）；tok/s = tok_per_step ÷ median_step_秒
frameworkMegatron-Bridge (NeMo 2.0) + TransformerEngine 2.12.0 / PyTorch 2.8.0+cu128 / CUDA 12.8 / mamba-ssm 2.2.6
grid_purpose每步 token 数固定（2M=S1 / 4M=S2）下，测增大 seq（8192→16384→32768）对 16 卡训练吞吐的影响
单变量保证：同组（S1 或 S2）3 个 seq 共用同一批 16 个 p5b_l3 packed shard，仅运行时 --seq-length 切块长度不同；配方（DP16/TP1/PP1 + FP8 tensorwise + CUDA Graphs + 真数据）与双机 e18 基线字节级一致，除 seq 与随之变化的 MBS / 累积外一律不改。
OOM 处置策略（运维令规定）：当某格因显存不足 OOM 时，只许两种回退，且必须标为「配方变更组」单列、不混进主表同口径对比：
(a) MBS 降到 1、用累积补回 tok/step；
(b) 加 --recompute-activations 或 --use-distributed-optimizer。
仍 OOM 就把该格写「OOM（峰值显存 xx GB，卡 x）」+ 已试过的回退，不许留空、不许编造。本网格 cfg5/cfg6（seq=32768）MBS 已为 1，故回退 (a) 不适用，只能用 (b) 加 recompute/distributed-optimizer。

5. 机制解释（带实测支撑）

BaiZe-2B 是 Mamba2-hybrid：56 层 = 28 SSM + 28 Attention + 28 MLP-only（只有 28/56 层带 KV cache / Attention 计算），注意力成本结构性低于纯 Transformer。seq 增大主要影响：(1) SSM 层的 state 扫描成本随 seq 超线性增长；(2) Attention 层 KV 与 attention 计算随 seq 增长（但仅 28/56 层）；(3) 激活显存增大 → MBS 被迫从 2 降到 1 → 每步累积步数增多 → launch/通信开销占比上升。
实测支撑①：基线 seq4096 per-GPU=37,903 tok/s → cfg1 seq8192 per-GPU=6,768 tok/s，seq 翻倍（4096→8192）per-GPU 吞吐 %.1f%%（崩塌 %.1f 个百分点）。tok/step 同期 4.13M→2.10M（S1 组），说明 Mamba2 SSM 扫描成本随 seq 增长远超线性，是吞吐崩塌主因 —— 已用本网格数据印证。
实测支撑②：S1 组内 seq 8192→16384，tok/s 108,291→112,094（%+.1f%%）。seq 翻倍但 tok/step 不变（均为 2M）、MBS 2→1、累积 8→8；吞吐略升，说明在 2M tok/step 下 seq 8192→16384 的 SSM 成本增长被「MBS 减半减少 launch 次数 / 单步批更大」部分抵消 —— 已用本网格数据印证。
关于「注意力成本结构性低于纯 Transformer」：本网格仅含 Mamba2-hybrid 一种架构，未在同口径下跑纯 Dense Transformer 对照，故该结构优势本网格未直接验证，标注为「推测·未验证」（需另起 Dense 对照实验方可证实）。

6. 结论：S1 / S2 该选多大 seq

基线 seq4096/4.13M=606,449 tok/s 是当前最高吞吐点；任何 seq≥8192 配置的 per-GPU 吞吐均显著低于基线（cfg1 已 %.1f%%）。

S1 组（2M tok/step）：seq8192→16384 吞吐变化 %+.1f%%；S2 组（4M tok/step）：seq8192→16384 吞吐变化 %+.1f%%。

可执行建议：若 seq 增大导致吞吐降幅 > 10%（vs 同组 seq=8192 或 vs 基线），明确建议维持 seq=4096 / 8192。鉴于 cfg1（seq8192）per-GPU 已较基线崩塌 ~82%，且 seq32768 大概率 OOM，全量预训练应维持 e18 配方 seq=4096（与任务书「305K 已定档、勿再扫吞吐」一致）；仅在需要长上下文建模能力时才考虑 seq=8192，并接受 ~5× 的吞吐代价。
