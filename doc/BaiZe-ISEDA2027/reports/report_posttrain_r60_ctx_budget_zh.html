3. KV Cache 显存预算（4×A40 46GB）

MiniCPM5-2B 架构：42 层 × 2 KV-heads × 128 head-dim × bf16。 权重 3.73GB（4 卡分片 ≈ 0.93GB/卡）。

KV_cache = 2 × n_layers × n_kv_heads × head_dim × ctx_len × batch × 2 bytes (bf16) = 2 × 42 × 2 × 128 × ctx_len × batch × 2 = 43,008 × ctx_len × batch bytes ≈ 0.0000400 GB × ctx_len × batch

4. 截断策略设计

4.1 为什么不能简单截断尾部？

EDA 多轮交互的典型模式：search_apis → get_api_details → run_code → 修正 → run_code → 断言。 截断尾部 = 丢失执行结果和断言判定 → 奖励信号失真。 截断头部 = 丢失系统提示和任务描述 → 模型不知道要做什么。

4.2 推荐截断策略：滑动窗口 + 工具结果摘要

策略保留压缩/丢弃奖励影响适用
A. 保留首尾系统提示+任务+最后N轮中间轮次丢弃高：丢失API查询上下文紧急回退
B. 工具结果摘要 ⭐系统提示+任务+所有assistant轮+工具参数工具返回大JSON压缩为摘要低：保留决策链推荐默认
C. 分段重置每K轮重置，保留摘要+最近状态历史完整丢弃中：依赖摘要质量超长任务(>32K)

4.3 工具结果摘要模板（策略 B）

# 原始工具返回（可能数 KB JSON） {"cells": [...500 items...], "status": "ok", "count": 500} # 摘要后（~50 tokens） [tool_result: run_pyAether_code → status=ok, type=list, len=500] # 原始错误日志（可能数 KB） Traceback (most recent call last): ... 50 lines ... # 摘要后（~30 tokens） [tool_result: run_pyAether_code → status=error, error_type=AttributeError, msg="obj has no attr 'X'"]

估算：策略 B 可将 user 角色 token 减少 60-80%（从 60.7% 降至 ~15-20%），总轨迹 token 减半， 使 16384 上下文的容纳率从 18.4% 提升至约 50-60%。

5. 对 RL 训练的具体影响

5.1 假阴性奖励问题

量化估算：在 8192 上下文中，98.1% 的任务被截断。 假设截断任务中 30% 是「模型做对了但结果被截断」→ 约 29.4% 的 rollout 会收到错误的 0 奖励。 这在 GRPO 中会产生负向优势，直接对抗正确行为的学习——与 vision 线 std=0=78.7% 的失败模式类似（R57）。

5.2 对 4 臂奖励的影响

奖励臂截断影响缓解措施
R1 二值最严重：截断=断言未执行=0分必须配合 ctx≥32768
R2 分档中等：执行成功可得分但断言未跑部分分缓冲截断影响
R3 R2+惩罚中等：工具调用可计但最终判定缺失工具频次可从完整轨迹提取
R4 R3+API合法最轻：API合法性可从已完成轮次判定仅尾部API调用受影响

这进一步支持从 R2 起步的决策（R57/R58 结论）：R2 的分档机制对截断更鲁棒。

5.3 对 SFT 阶段的影响

当前 SFT 脚本 baize_posttrain_sft.sh 默认 CONTEXT_LEN=8192。 DeepSeek 轨迹中位 23,906 tokens → 98% 的 agentic 轨迹在 SFT 时会被截断。 建议：SFT context_len 至少 16384，RL context_len 至少 32768。

6. 对 11/9 发射的具体建议

  1. RL 脚本补丁：在 baize_posttrain_rl_grpo.sh 中添加 CONTEXT_LEN=32768 参数， 传入 SGLang --context-length 32768 和 verl rollout 配置。 当前脚本缺失上下文长度配置（grep 确认），这是 P3 预备脚本的缺陷。
  2. SGLang 启动参数：--context-length 32768 --max-num-seqs 8 --mem-fraction-static 0.50 （与 R11 内存校准一致）。
  3. SFT 脚本：默认 CONTEXT_LEN 从 8192 升级到 16384（agentic 轨迹最低需求）。
  4. 截断策略 B（工具结果摘要）：在 baize_posttrain_eda_tool.py 中实现工具返回压缩， 将 >500 token 的工具返回摘要为 <50 token 的状态行。
  5. 基线评测：11/9 复测 36% 基线时使用 32768 上下文（与 RL 一致）， 避免因上下文不同导致的基线偏移。
  6. 监控指标：RL 训练中记录 truncation_rate（被截断的 rollout 比例）， 若 >5% 则需调大上下文或启用摘要策略。

8. 局限性与待 GPU 后验证

  • Token 估算基于 char→tok 比 3.8，实际 tokenizer（MiniCPM5 BPE）可能偏差 ±15%。GPU 到位后用真实 tokenizer 校准。
  • DeepSeek 轨迹代表强模型行为（更长的推理、更详细的 API 查询）。2B 模型的轨迹可能更短（更少轮次、更短输出），实际截断率可能低于本估计。
  • KV cache 估计未考虑 Flash Attention 2 的内存优化（实际可能更省）。
  • 策略 B（工具摘要）的摘要质量需 GPU 后用真实轨迹验证。
  • verl 的 multi-turn RL 框架对上下文管理的原生支持程度需 11/9 实测确认。
