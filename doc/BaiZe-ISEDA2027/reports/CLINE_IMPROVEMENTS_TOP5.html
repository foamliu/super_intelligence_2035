一句话总览：cline 的五份源码分析收敛到同一个命题——「状态 ≠ 文本」。最值得做的 5 件事里， P0 两条修「正确性/体验」硬伤（token 计量不吃服务端 usage、压缩后丢任务进度）， P1 一条低风险开压缩生命周期 Hook（回答「Auto Compact 能否插件化」）， P2 两条做性能/可观测性与长期架构收敛（投影归一化 + 检查点单事实源）。 其中 O5/O3/O1 可直接借鉴、O4 组合、O2 需架构改动。

优先级排序 + 一句话总览

优先级#主线一句话类别
P0O5线5 模型适配/tokentoken 计量改「服务端 usage 优先 + 保守兜底」，修本地模型踩 128K 假窗口（Issue #7772）可直接借鉴
P0O4线4 任务状态解耦补回 TodoWrite 等价物，让「接下来做什么」不随压缩丢（Focus Chain 已被移除）需架构改动
P1O3线3 Hook/扩展补 PreCompact/PostCompact 压缩生命周期 Hook，让 Auto Compact 可被观测/干预可直接借鉴
P2O1线1 注入/投影补单一 memoized 归一化终点 + 全链路 Telemetry，降低投影成本并补盲区可直接借鉴
P2O2线2 检查点/回滚把文件快照与压缩状态收进同一原子事务，消除 sidecar 漂移整类 bug需架构改动

优先级说明：P0 = 正确性/体验硬伤、低风险可直接起步；P1 = 低风险高生态价值；P2 = 性能/可观测性优化或需架构重构的长期项。

O5 · token 计量：服务端 usage 优先 + 保守兜底 P0 可直接借鉴

① 现状 / 问题（cline）

token 计量只用一个静态系数，预算解析在「模型不报窗口」时直接返回 undefined：

cline/sdk/packages/shared/src/llms/tokens.ts:8
export const CHARS_PER_TOKEN = 3;
cline/sdk/packages/core/src/extensions/context/compaction-shared.ts:13-15 → DEFAULT_MAX_INPUT_TOKENS = 128_000 / CONTEXT_WINDOW_INPUT_RATIO = 0.9
compaction-shared.ts:61-69 resolveEffectiveMaxInputTokens：maxInputTokens 空 → contextWindow * 0.9；contextWindow 也空 → undefined。

本地模型坑（任务书 §2.2 线5 Issue #7772）：llama-server 上下文窗口无法自动探测，Cline 默认按 128K 处理，131K 模型触发阈值计算错误。

② 其它 harness 怎么做

codex 把 token 计量做成「服务端 usage 观测优先、客户端估算兜底」，且「压缩」是模型降级的第一闸门：

codex-rs/core/src/state/auto_compact_window.rs:24-30
pub(crate) enum AutoCompactWindowPrefill { ServerObserved(i64), Estimated(i64) }
codex-rs/core/src/compact_model_fallback.rs:9-20 should_retry_with_current_model：遇 ContextWindowExceeded / UsageLimitReached / ServerOverloaded / InvalidRequest 先压缩+当前模型重试，再降级。

claude-code 同样「usage 回执 + 粗略估算」并用：

claude-code/src/utils/tokens.ts:226 tokenCountWithEstimation（优先取 api usage，回退 roughTokenCountEstimation，默认 4 字符/token，见 tokenEstimation.ts:203-208）。
③ 为什么值得做（收益 / 风险）

收益：阈值准确 → 少溢出、少过早压缩；本地模型不踩 128K 假窗口；多窗口模型可移植。
风险：低–中（①② 是增量改动；③ 迁 hardcode 白名单到 config，测试面变宽）。

④ 落地建议 + 工作量估计
  • ① token 计量改「服务端 usage 优先 + 3 字符/token 兜底」（对齐 codex / claude-code）。
  • ② resolveEffectiveMaxInputTokens 无窗口信息时给保守默认值而非 undefined，并对本地模型做显式窗口探测/可配置覆盖（修 #7772）。
  • ③ 「provider 白名单」参数化为 config 元数据（对齐 codex 的可参数化阈值）。

工作量估计：①② 约 1–2 人日（增量 + 覆盖测试）；③ 约 1 人周（迁 hardcode 白名单 + 回归）。（人工工程估计，非实测）

O4 · 补回任务目标持久层，解耦长期目标与可压缩对话 P0 需架构改动（组合）

① 现状 / 问题（cline）

cline 的 Focus Chain 已被移除 / stub 化，不再有「把『接下来做什么』与『可压缩对话』解耦」的持久层，压缩后「从停止处继续」只能重新依赖摘要文本：

cline/apps/vscode/src/sdk/task-proxy.ts:144
/** Focus chain checklist (stub — focus chain removed) */
currentFocusChainChecklist?: null
② 其它 harness 怎么做

claude-code 把「接下来要做什么」拆成独立于对话历史的持久状态 + 自动记忆抽取：

claude-code/src/tools/TodoWriteTool/TodoWriteTool.ts:65-94 —— call({ todos }) 写进 appState.todos（session 状态，不随压缩丢）；
claude-code/src/services/SessionMemory/sessionMemory.ts:1-6 ——「automatically maintains a markdown file … forked subagent」后台抽取会话要点；
claude-code/src/services/extractMemories/extractMemories.ts:1-10 ——「Extracts durable memories … runs once at the end of each complete query loop」。

codex 用 codex_state::ThreadGoal（goal）+ update_plan 把目标/计划脱离对话历史。

③ 为什么值得做（收益 / 风险）

收益：压缩后进度不丢；长期记忆跨会话复用，减少重复探索。
风险：①（补 TodoWrite 等价物）低；②（Session Memory / auto-memory）中——后台 subagent 抽取有成本/延迟，memory 文件污染需管控。

④ 落地建议 + 工作量估计
  • ① 补回 TodoWrite 等价物（任务清单存 session 状态，不随压缩丢）——低成本高价值。
  • ② 中长期补 Session Memory / auto-memory（后台 subagent 抽取要点落盘，跨 session 记忆）。

工作量估计：① 约 1 人日；② 约 1–2 人周（引入后台抽取流程 + 污染管控）。（人工工程估计，非实测）

O3 · 补 PreCompact/PostCompact 压缩生命周期 Hook P1 可直接借鉴

① 现状 / 问题（cline）

运行时 Hook 只有 7 个生命周期回调 + 1 个 prepareTurn，无压缩生命周期 Hook：

cline/sdk/packages/shared/src/agent.ts:374-402
export interface AgentRuntimeHooks { beforeRun?/ afterRun?/ beforeModel?/ afterModel?/ beforeTool?/ afterTool?/ onEvent?; }
agent.ts:485-490（prepareTurn）返回的消息「affect only the provider request … not persisted as session history」（agent.ts:481-483）。

压缩（createContextCompactionPrepareTurn）在 Hook 之内、自身不暴露 Hook：插件观察不到也无法干预「何时压缩、摘要是什么」。

② 其它 harness 怎么做

claude-code 的 Hook 事件面最全，且显式包含压缩生命周期：

claude-code/src/entrypoints/sdk/coreTypes.ts:25-53 —— HOOK_EVENTS 共 27 个，含 'PreCompact'、'PostCompact'；每个事件支持 command / prompt / http / agent 四种形态（schemas/hooks.ts:30-53）。
③ 为什么值得做（收益 / 风险）

收益：直接回答「Auto Compact 能否插件化」= 能观测/干预、不能替换核心压缩算法，扩展边界清晰；生态可做调优/审计/成本观测。
风险：低（新增回调，不改既有 7 个 Hook 语义；调用序需文档化）。

④ 落地建议 + 工作量估计
  • 给 AgentRuntimeHooks 增加 beforeCompaction / afterCompaction，让插件观察压缩触发、注入指令或拦截摘要。

工作量估计：约 0.5–1 人日（新增回调 + 调用序文档 + 单测）。（人工工程估计，非实测）

O1 · 补单一 memoized 归一化终点 + 全链路 Telemetry P2 可直接借鉴

① 现状 / 问题（cline）

投影是「每请求全量 walk + 逐实例缓存」的 MessageBuilder：

cline/sdk/packages/core/src/session/services/message-builder.ts:105-107
/** Builds an API-safe message copy without mutating original conversation history. */
export class MessageBuilder {

且自认存在投影旁路 / Telemetry 盲区：

cline/sdk/packages/core/src/extensions/context/compaction.ts:251-254
// Known gap: compactions performed via plugin registerMessageBuilder() or via the beforeModel
// runtime hook bypass this wrapper entirely, so they do not emit compaction telemetry. ...
② 其它 harness 怎么做

claude-code 把「系统/用户上下文」做 memoized 单例，并收口到单一归一化终点：

claude-code/src/context.ts:116 getSystemContext、:155 getUserContext（均 memoize）；投影终点 claude-code/src/utils/messages.ts:1989 normalizeMessagesForAPI。

codex 把「投影注入」抽象为可插拔 ContextContributor（开放给插件）。

③ 为什么值得做（收益 / 风险）

收益：投影成本从「每请求全量 walk」降到「增量/缓存」，延迟下降；Telemetry 补齐 → 压缩行为端到端可审计。
风险：低（不动投影语义，只做收口与埋点；需定义 memoize 失效时机）。

④ 落地建议 + 工作量估计
  • ① 加一个 memoized 归一化终点（等价 normalizeMessagesForAPI），把「系统提示 + 环境注入 + 文件剥离 + 过期内容改写」收口为一处。
  • ② 把 registerMessageBuilder() / beforeModel 两条旁路管线纳入 Telemetry（补 compaction.ts:251-254 自认的盲区）。

工作量估计：约 2–3 人日（收口 + memoize 失效时机设计 + 埋点）。（人工工程估计，非实测）

O2 · 检查点收敛为单一原子事务 P2 需架构改动

① 现状 / 问题（cline）

检查点是两套并存：文件级用 git stash/ref，对话/压缩级用独立 JSON sidecar，各自成单：

cline/sdk/packages/core/src/hooks/checkpoint-hooks.ts:16-26
export interface CheckpointEntry { ref: string; createdAt: number; runCount: number; kind?: "stash" | "commit"; }
压缩 sidecar schema/projection 见 cline/sdk/packages/core/src/session/models/session-compaction.ts:25-34/161-190；持久化守卫 .../runtime/host/local-runtime-host.ts:621/1297-1360。

sidecar 可靠性曾被专项修复（PR #12747「compaction sidecar」）——暴露了「两套状态各自落盘 → 会漂移」的固有缺陷；一旦 sidecar 落盘失败，重启后阈值错乱、可能重复压缩。

② 其它 harness 怎么做

deepseek 用事件溯源：检查点 = append-only 事件流 flush，「重放即回滚」，无第二份状态需对齐。
codex 把「摘要生成 / 新窗口 / WorldState 基线」三者原子落进同一条 Rollout，以 window_id 链提供审计与恢复锚：

codex-rs/core/src/state/auto_compact_window.rs / mod.rs:3752（sidecar = AutoCompactWindowIds(window_id 链)）。
③ 为什么值得做（收益 / 风险）

收益：消除 PR #12747 类「sidecar 与文件状态不一致」整个 bug 类；恢复从「多源对齐」简化为「单源截断」。
风险：高——涉及 git 检查点、事务存储、迁移兼容的核心重构。

④ 落地建议 + 工作量估计
  • 把「检查点」收敛为一个原子事务——文件快照 + 压缩摘要 + 阈值窗口同一条记录落盘（借鉴 codex 的 Rollout/window_id 链，或 deepseek 的 append-only 事件流）。

工作量估计：约 2–4 人周（git 检查点 + 事务存储 + 迁移兼容 + 回归）。（人工工程估计，非实测）
