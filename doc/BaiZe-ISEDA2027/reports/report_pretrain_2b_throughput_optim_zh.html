4. 瓶颈归因与下一步建议

瓶颈分析

基线:252K tok/s

最佳:FP8 TW+CG=297K tok/s(+17.9%)

  • 🔥 关键发现 — FP8 + CUDA Graphs 协同效应：FP8 tensorwise 单独使用反而慢10.0%（227KK），因为 FP8 量化引入大量小 kernel（amax/缩放/类型转换），launch 开销 > 计算节省。但叠加 CUDA Graphs 后，全部量化 kernel 被图捕获、launch 开销归零，FP8 的显存带宽节省得以释放 → 协同提速 +17.9%（297KK），远超两者单独效果之和（+2.7% 和 -10.0%）。这是 Mamba2-hybrid 架构特有瓶颈：SSM 层 GEMM 小而碎，kernel launch 是主要开销，CUDA Graphs 是解锁 FP8 收益的前提。
  • CUDA Graphs(e01)+2.7%：消除 kernel launch 开销，对 Mamba2 频繁小 kernel 有效
  • FP8 单独使用反而慢 ~10%：Mamba2 SSM 层 GEMM 占比低，量化 launch 开销 > 计算节省（详见上方协同效应分析）
  • FP8 blockwise 不可用：TE 要求 CUDA≥12.9，当前 12.8
  • overlap-param-gather 崩溃：框架 IndexError，与 Mamba2 自定义层不兼容
  • CE Loss Fusion(e06)无显著变化：loss 计算非瓶颈
  • 显存:基线 54.7GB→CG 65.3GB(+10.6GB)→FP8+CG 66.9GB，80GB 充足仍有余量
  • NaN 计数：grep 误匹配配置打印行，实际训练 0 NaN（iteration log 均显示"number of nan iterations: 0"）

下一步建议

  • 组合优化（当前最佳 e09 基础上叠加）：CUDA Graphs + FP8 TW + CE Fusion + 更大 MBS（当前 66.9GB/80GB，可试 MBS=3 甚至 4）
  • 升级 CUDA 12.9+：解锁 FP8 blockwise（更精细缩放，预计再 +3-5%）
  • 序列并行(SP)：--sequence-parallel 减 activation 显存，为更大 MBS 腾空间
  • 数据侧：num_workers / pin_memory / mmap 预取，消除 host 侧瓶颈
  • NCCL 调优：NCCL_ALGO / NCCL_PROTO + NVSwitch 拓扑感知
  • 更大 GBS：减 optimizer step 频率提升有效吞吐
  • torch.compile fullgraph：替代 CUDA Graphs，可能进一步融合跨层算子

6.4 第二轮关键发现

🎉 新纪录: e18 = 306K tok/s (+3.0% vs e09, +22.9% vs 249K)

  • MBS3+CG 是关键突破：R2 无 defrag 时 OOM(79.7GB)，加 expandable_segments:True 后峰值降至 72.7GB。GBS 改为 1008(=3×8×42) 修复 e11b 的不可整除问题。
  • MBS3 比 MBS2 快的原因：① CG 已消除 launch 开销 → MBS 增大不再受限；② MBS3 仅 42 microbatches(vs 64)→ fewer per-microbatch overhead；③ larger GEMM → better GPU utilization。
  • MBS4 全部 OOM：CG pools 30GB + MBS4 act 8GB > 80GB。
  • CE Fusion / NCCL Ring / GBS 无效：loss 非瓶颈；NVSwitch 已最优；GBS 不影响吞吐。
  • SP 需 TP>1 / Recompute 与 CG 不兼容。

吞吐上限分析：306K 接近 8×H100 上限 —— VRAM 限制(MBS4 全 OOM)、CG+FP8 已饱和、通信已最优。剩余空间: CUDA 12.9(+3-5% FP8 blockwise) 需环境评估。
