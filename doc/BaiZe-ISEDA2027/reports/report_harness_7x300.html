1. 评测设计

对象：7 个 coding agent harness —— cline（BaiZe 的 agent 骨架，EDA 开发基于它）、opencode、pi（gpt-eng）、codex、claude-code、deepseek-harness、hermes（SWE-bench 官方 harness）。

控制变量：统一 backbone kimi-k2.6-cloud · 同一沙箱 · 同一 eval 判据（SWE-bench test patch applied + FAIL_TO_PASS 全过 + PASS_TO_PASS 全过）。

任务集：SWE-bench Lite 300 实例（stratified 抽样：30 Round-1 + 70 比例填充；100-set 是 300-set 子集，可 --resume 复用）。7 路并行跑（R2），每 harness 内部串行。

分类：resolved（解出）/ patch-but-failed（PBF，补丁产出但测试未全过）/ blocked / quota-blocked。

定位：这是 harness 选型 + cline 改进 研究（软件工程基准，不是 EDA 基准）；BaiZe 的最终下游评测用 EDA-Eval-PyAether（158 任务）。本报告是 harness 线的 7×300 结果汇总，与「交互轨迹 vs cline 报告」互补。

3. 速度-精度权衡

左上角 = 更快 + 更准（优）。opencode（370s / 29.0%）与 pi（358s / 30.3%）落在 Pareto 前沿；cline（399s / 28.7%）略慢一点、精度接近。codex（572s）与 hermes（479s）明显更慢且精度落在下沿 —— 属 Pareto 劣势。deepseek 最慢且精度最低（473s / 23.7%）。

5. Instance 重叠分析（7 方都测过的 294 个实例）

在 300 个 all-7 实例上：182 个实例（61%）全体 harness 都解不出，30 个实例（10%）全员解出，88 个是「部分解出」。

解读：61% 的实例「全灭」说明 SWE-bench 本批任务的难度对这些 harness + 同 backbone 组合整体偏高；「部分解出」的 88 个才是 harness 间真正的分化空间 —— 样本量小，差异不具统计显著性。

8. eval 基础设施失效归因（root-cause 专章）

8.1 失效面全景

⚠️ 结论修正：原「只 3 个 eval-可用 repo」的说法不准确。准确表述是：5 个 repo 因 eval 基础设施失效（matplotlib/pytest/sphinx/astropy/flask，共 65 唯一实例）被系统性压到 near-0；而 psf/requests 是被误判的 —— 它 patch 全 apply、0 resolved 是能力/难度问题，不应算「受限」。其余 eval-OK repo 里，django/sklearn 也各有少量 missing_module（见上表），并非 100% 干净。

8.2 逐 repo root-cause（日志实证）

root-cause 结论：这 5 个 repo 的 patch_applied=False 不是模型/harness 能力不足，也不是统称的「依赖装不上」——而是 eval 基础设施失效（根因各 repo 不同）。同时，原报告把 psf/requests 归入「受限」也是错误的：requests 的 42 次 patch 全部成功应用，0 resolved 只是 FAIL_TO_PASS 测试没过（模型没做对），评测管线本身完全正常。

matplotlib —— 全部 missing_module（C 扩展编译需外网下载 freetype）

23 个唯一实例 / 161 entries，其中 130 次 patch 未应用、全部为 missing_module（130 次）。根因（eval 日志实证）：rootfs 构建时 pip install -e . 触发 C++ 扩展编译（running build_ext / g++），需从 sourceforge.net / savannah.gnu.org 下载 freetype-2.6.1.tar.gz；沙箱无法访问外部源码站 → _c_internal_utils 等 C 扩展缺失 → import matplotlib 直接 ImportError。此时 patch 本身早已 cleanly apply，swebench 将 import 失败标记为 infra_failure_reason=missing_module（一个歧义类别），并连带把 patch_successfully_applied 置 false。0 分（0 resolved）是基础设施假象，不代表任何 harness 的 matplotlib 能力。

pytest —— 110 missing_module（少量真实可评）

17 个唯一实例 / 119 entries，113 次 patch 未应用，其中 110 次 missing_module（rootfs 内 pytest 运行所需的模块缺失）。仅 5 次 patch 成功应用，其中 2 次 resolved —— 说明在 eval 正常的那一小撮上，模型/harness 是能解 pytest 的（有效 rate 2/5 = 40%），整体 1.7% 的惨淡 rate 主要被 113 次 eval 失效稀释。

sphinx —— 92 次纯 git apply 失败（无 infra 标记，非缺模块）

16 个唯一实例 / 112 entries，92 次 patch 未应用，但 全部没有 infra_failure_reason 标记 —— 即 纯 git apply 失败（base_commit 与 rootfs checkout 不一致 / diff 上下文冲突），与 matplotlib 的「缺模块」是两类不同的失效。19 次成功 apply 的也无 resolved，样本不足以判能力。

astropy —— 28 次 out_of_memory（沙箱内存不足）

6 个唯一实例 / 42 entries，28 次 patch 未应用，全部 out_of_memory（28 次）—— astropy 的 C 扩展编译/测试在受限内存沙箱里 OOM，属资源型失效。

flask —— 7 次 no_tests_collected（样本极小）

3 个唯一实例 / 21 entries，14 次 patch 未应用（其中 7 次 no_tests_collected，patch 应用了但 FAIL_TO_PASS 测试收集为空）。3 个唯一实例，样本太小，不构成统计结论。

psf/requests —— 误判修正（patch 全 apply，非失效）

6 个唯一实例 / 42 entries，0 次 patch 未应用（0 次 False），42 次 patch 全部成功 apply；0 resolved 是因为 FAIL_TO_PASS 测试全没过（模型未做对），评测管线完全正常。故 requests 应从「受限」移入「小样本 eval-OK」。

scikit-learn / django —— eval-OK，但有少量 missing_module

scikit-learn：34 次 patch 未应用（其中 28 次 missing_module），但 125 次 patch 成功应用 → 有效 rate 56.0%（70/125），是全部 repo 中最高的。django：25 次 patch 未应用（其中 7 次 missing_module），762 次 patch 成功应用、有效 rate 27.6%。两者主体 eval-OK，只有零星 missing_module，不影响结论方向。

8.3 影响量化

5 个 eval 失效 repo 合计 65 个唯一实例（占 300 实例的 22%）、455 次 entries（其中 377 次 patch 未应用）被基础设施失效压制到 near-0，系统性低估了所有 harness 的平均 rate。真正可公正比较的 repo 是 django/sympy/scikit-learn（214 唯一实例），另加 requests/xarray/pylint/seaborn（21 唯一实例）为「小样本 eval-OK」，仅方向性参考。

8.4 修复建议（优先级从高到低）

  • matplotlib 专项（收益最大，23 实例一夜回血）：把 freetype-2.6.1.tar.gz 及 build 依赖预下载进 rootfs（或用 manylinux wheel 绕过源码编译），使 pip install -e . 走本地；预构建 _c_internal_utils 的 .so 一并注入。
  • astropy 专项：加大沙箱内存限额，或对 astropy 用 prebuilt wheel（avoid 源码编译 OOM）。
  • pytest 专项：核对 rootfs 内 pytest 测试运行依赖清单，补齐缺失模块后再 --resume。
  • sphinx 专项：92 次 git apply 失败需核对 eval spec 的 base_commit 与 rootfs checkout 是否一致（不是依赖问题）。
  • 统一：给 eval 沙箱开放 pypi / sourceforge / savannah / files.pythonhosted 白名单（或预置 wheel cache + 源码 tarball 镜像），一次性根治「外网下载」类失效。

9. 口径与诚实条款

  • 快照未闭环：hermes 300/300（还差 0 个，均为 sympy），其 rate（27.0%）可能受未完成实例的选择偏差影响；全部跑完后应重跑本脚本刷新数字。
  • R1/R2 wall time 不完全可比：R2 为 7 路并行，wall 含资源争抢开销；且 hermes/codex 的 wall 偏长部分源于自身较重实现。
  • 样本量：resolve rate 的 binomial SE ≈ 3 pp（p≈0.28, n≈300），故 pi/cline/opencode 三者之差（≤1.6 pp）不具统计显著性，排名仅有方向性意义。
  • 实例重叠：all-7 的 294 实例中「部分解出」仅 88 个，head-to-head 独解计数多为个位数，不作显著性结论。
  • 轨迹数据缺失：仅 stdout_tail 最后 500 字符，无 per-turn 轨迹 —— 工具调用序列、token、压缩事件均不可得。
  • 数据可复算：所有数字由 gen_report_7x300_zh.py 从 kimi_pilot_results.json 现算，脚本入库。

10. 对 BaiZe 的启示

  • harness 选型：pi / opencode / cline 三者在同 backbone 下难分伯仲（30.3% / 29.0% / 28.7%），若考虑速度，opencode（wall 最短 460s）与 pi 更优；cline 的护城河在于 BaiZe 的 EDA agent 已基于它开发、且有可落地的改进点（§4 的 patch 未应用率、ai@7.0.49 transform error）。
  • 6.7 pp 的 harness 差带 vs 数十 pp 的模型差带：ZhuLong 侧 full harness（DeepSeek-V4-Pro）≈94% vs 裸 LLM ≈10.5%，说明主要矛盾仍是模型能力 / 观测保真度，而非 harness 细节 —— 与 BaiZe「harness 冻结、换 backbone」的主体研究一致。
  • 基线参照：本次 backbone 固定为 kimi-k2.6-cloud，7 harness 的 23.7%~30.3% 可作为该 backbone 在 SWE-bench 的上限参考；BaiZe-backbone 接入后可在同一管线复测。
