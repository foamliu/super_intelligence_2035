2.3 调用后是否有「有效结果」——检索到 ≠ 用对

检索到了，但基本没用上：get_api_details 在 5-run 中检索到 333 个去重 API 名（取最后一段，如 dbCreateLib/emyBitNet/dbOpenCV），但真正出现在后续 run_code 代码 token 里的只有 19 个（overlap = 5.71%）。示例重叠 API：dbCreateLib, dbOpenCV, emyDesign, emyTerm, dbCrtRect, MdePlatLocalJobPolicy 等。

证据摘引（trace 原文）：get_api_details 返回 {"api_name":"pyAether.emyBitNet","api_type":"class",...getOriginal()->emyBitNet...} 这类真实文档；但紧随其后的 run_code 里模型往往写的是自己猜的 API 名（如 pyScript.filterSignals(...)），结果 AttributeError: module 'pyAether' has no attribute 'filterSignals'。模型「查了文档但没按文档写」，检索与生成脱节。

三条最致命的「写得出≠跑得通」证据：
  • 把工具名当函数（task 027 连续 4 次）：模型在 run_code 里写 pyAether_MCP_server__get_api_details(...)，沙箱报 NameError: name 'pyAether_MCP_server__get_api_details' is not defined，随后触发 max consecutive mistakes reached (3) in yolo mode 被强杀。

2.5 重复调用 / 死循环重试迹象

submit_and_exit 死循环是头号症状：13,699 次 submit，12,572 次报错（91.77%）。run1/run3 的单题 max tool_use 达 5,749 / 6,772，几乎全是 submit→报错→再 submit 的循环。真正进入「检索→执行→修错」有效迭代的题极少：729 个题-会话里只有 72 个（9.88%）曾经调用过 run_code，中位数 run_code 调用 = 0；657 个题（90.12%）一次沙盒执行都没有。

另外 180 个题（24.69%）从不调用任何 MCP 工具（既不检索也不执行），直接提交空/degenerate 答案。

2.6 prompt 矛盾的影响（指令与环境自相矛盾）

.17 评测用的系统提示模板 eval_sys_prompt_template_no_sandbox.md 明写「本场景无沙箱可实际执行，内部推演唯一校验」，但 agent 仍调用了 run_code 507 次（沙盒经 dual-nix-tunnel 实际可达，wake327/328/330 实测 2+2=4 通过）——指令说没有沙箱，环境里却有。

trace 证据：在 507 次 run_code 调用中，236 次（46.55%）其前导 assistant 文本出现了「infer/reason/verify/assume/推测/推演/假设」等措辞——即模型一边说「我推演/假设一下」一边又调用了它「被告知不存在」的沙盒。这表明模型表现出不敢确信执行结果的犹豫：它在「按提示纯推演」与「按环境真执行」之间摇摆，既没有放心地用沙盒闭环校验，也没有真正退化为纯推理，而是反复低效试探。

结论：prompt 矛盾没有让模型完全放弃工具（它确实调了 507 次 run_code），但显著抑制了「执行→看结果→修错」的闭环——模型不敢信任执行结果，迭代次数极低（见 §3.4）。

头号失败模式：C5_degenerate_pass = 479/790 = 60.6%——模型最终提交的代码就是 Python 空操作 pass（completion 退化检测：gen_fail_subtype=degenerate_pass 共 479 条，has_code 仅 10 条）。即六成的尝试根本没写出有效代码就放弃了。这与 §2.5 的 submit_and_exit 死循环同源：模型早早放弃，spam 退出工具。

3.2 检索到 ≠ 用对

get_api_details 检索到 333 个去重 API，仅 19 个进入后续代码（5.71%）。大量证据显示模型查完文档仍用猜的 API 名（filterSignals 等），检索结果未转化为生成依据。该现象对应 §3.1 的 C3_code_runtime（122 条，15.4%）中的 AttributeError 子类。

3.3 写得出 ≠ 跑得通

真正调用 run_code 的题里，失败率约 66%（231/349 可识别）。失败结构：NameError 66 / SyntaxError 58 / non-ASCII 39 / AttributeError 24 / 其它 52。non-ASCII（39 次）是纯环境/习惯问题，完全可修；把 MCP 工具名当 Python 函数（NameError 含 4 次 pyAether_MCP_server__...）是工具协议理解错误。

3.4 跑得通 ≠ 判得过 + 迭代次数

即使 run_code 执行成功（The code execution was successful.），最终 check 仍多数判 fail——C3_code_assert（断言/逻辑失败）只有 14 条，说明绝大多数题根本走不到「代码跑通但断言失败」这一步，而是更早就断了（degenerate 放弃 / 语法错 / 运行期错 / 超时）。

迭代次数极低（D6）：通过题平均迭代 2.1 轮，失败题平均 2.0 轮——两者几乎相同且都很低，模型基本不利用执行反馈做「跑→看错→改」闭环。

「原地打转」证据：失败题平均耗时 534s，反而比通过题 237s 更长——多出的时间并没有用于有效迭代，而是消耗在 submit_and_exit 死循环 / yolo-mode 连错被杀上。run_commands 6,401 次（用户粗扫口径）里相当一部分是这种原地打转，而非有效迭代。

3.5 失败漏斗（检索→用对→跑通→判过）

漏斗口径（729 题-会话）：549 题用过 MCP 检索 → 仅 72 题真正执行过 run_code → 其中约 64% 即 ~46 题执行成功 → 最终仅 24 题-运行 check 判过。最大流失在「检索→执行」这一步（549→72，流失 87%）：模型查了文档却极少动手在沙盒里写代码验证。

3.6 通过题的特征（pass 是「碰运气」还是「真会」）

union pass = 22/158 = 13.92%（至少 1 个 run 通过的题），但 Pass@1 仅 3.04%。分布：20 个题只在 1 个 run 通过，2 个题在 2 个 run 通过，没有任何题在 ≥3 个 run 通过。这意味着通过本质上是随机/碰运气：模型偶尔对某些简单题（如 003/010/050/100/153）蒙对一次，但无法稳定复现。3.04% 不是「能力上限被工具锁死」，而是「模型对绝大多数题没有稳定解题能力」。

P0-1：消除 degenerate「pass」提交 + submit_and_exit 死循环（改 prompt + SFT）。
理由：60.6% 的题-运行根本没写出有效代码就放弃了。在模型「不动手写代码」的前提下，无论检索多准、沙盒多通、迭代多少轮都无济于事——因为连被评判的对象都不存在。先把这 60.6% 的「放弃」行为止住（prompt 强制必须产出可执行代码 + SFT 教「完整解题轨迹」），后续的检索→执行→迭代改进才有发挥作用的对象。这是 ROI 最高、且是其它所有改进的前置条件。

5.1 综合判断：3.04% 主要卡在哪一层？

主要卡在「生成意愿/协议」层，而非「检索」或「执行环境」层。

  • 环境是齐的（意见 A 成立，wake482 已裁决）：RAG 检索可用（search_apis 成功率 ~78%）、沙盒可用（run_code 64% 成功、2+2=4 实测通）、工具已注册（4 个 MCP + cline 内建，enable_tools=true）。
  • 工具确实用了上万次，但绝大部分调用是 submit_and_exit 死循环（13,699 次/91.77% 报错），真正「检索→执行→修错」的有效调用极少（仅 9.9% 的题执行过 run_code）。
  • 最大断层在「动手写代码」这一步：60.6% 退化提交 pass；检索到的 333 个 API 仅 19 个进代码；通过题迭代仅 2 轮且 22 个 union-pass 题中 20 个只蒙对 1 次。

一句话：3.04% 不是「工具/环境缺失」（那是意见 B，已被 trace 否决），而是「模型有了工具却不会、也不敢稳定地用它把题做完」——查了不照着写、写了跑不通、跑通了不复现、没跑通就 spam 退出。这是能力 + 协议问题，正是 SFT（教完整轨迹）+ prompt（强制产出 + 纯 ASCII + 信任沙盒）+ RL（教执行反馈闭环）要解决的。
