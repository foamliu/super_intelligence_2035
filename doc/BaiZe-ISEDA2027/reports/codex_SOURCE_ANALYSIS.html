0. 概况与术语体系

Codex CLI（OpenAI Codex 的命令行版本）是一个 **Rust workspace**，核心在 codex-rs/，约 **115 个 crate**（codex-rs/Cargo.toml 的 [workspace] members 清单），根 README.md:1 仅一行 # Codex CLI。架构范式属「**Rust 微内核 + 分层 crate**」：核心代理循环在 core/，协议与模型元数据在 protocol/，可插拔宿主扩展在 ext/（当中就包括 goal / memories / history-notes / skills 等）。

它给自己建立的术语体系，本质是「上下文生命周期」设计主张 —— 把「持久的状态快照」与「要注入模型的投影片段」严格分离。核心术语：

术语含义证据
WorldState「模型可见状态」集合，按稳定 &'static str section ID 键控；每个 section 既能 snapshot()（持久化）也能 render_diff()（相对上一快照的差，注入模型）。core/src/context/world_state/mod.rs:285-289；trait :228
ContextualUserFragment注入模型的消息片段统一接口：role()/content_kind()/markers()/body()，后续能按 marker 反向识别。context-fragments/src/fragment.rs:64-99
Compaction把历史「收」成摘要 + 重装初始上下文的生命周期；三种实现：local / remote（compact_remote*）/ token-budget。core/src/compact.rs；compact_token_budget.rs:21-25
CompactionSummary压缩后注入的一条 user 片段，content_kind="compaction.summary"。core/src/context/compaction_summary.rs:17-19
AutoCompactWindow / sidecar每次压缩开新「window」，带 {first/previous/window}_id（Uuid v7）边界标识，随检查点持久化。core/src/state/auto_compact_window.rs:4-9
Rolloutappend-only 持久化条目流（RolloutItem::{Compacted,WorldState,TurnContext,RetainedContext…}），是检查点/恢复的事实源。core/src/session/mod.rs:3812-3816
Goal / Plan「接下来要做什么」独立存 codex_state::ThreadGoal 与 update_plan 工具，与对话历史解耦。ext/goal/src/spec.rs:9-11；core/src/tools/handlers/plan.rs

相对 cline 的「编辑 map + 读取时投影」、deepseek 的「事件溯源 + surface 投影」，codex 走第三条路：「WorldState 快照 diff 投影 + Rollout 回放」 —— 每个投影 section 自带可序列化的 snapshot()，压缩时落盘，开新窗口时用 render_diff(上一快照) 只把「变了的部分」重新注入。

一句话主线：codex 把「上下文生命周期」切成三段可独立替换的部件 —— 线1（放）用 WorldState 快照求 diff 决定「这次往模型里多注入哪些投影片段」；线2（收）用摘要 + start_new_context_window 开新窗口，把「旧历史 → 摘要 + 新基线」这条变换持久化为可回放的 RolloutItem；线3在放/收两侧都埋了 Hook 拦截点、并允许扩展用 contribute_world_state 塞进自己的投影 section；线4把「目标」从「对话」里请出来存到独立 thread state；线5用后端下发的 per-model 元数据决定「什么时候该压、压到哪一档」。

2. 线1 — 上下文注入与「WorldState 投影」管线

线1 ① 解决什么问题：模型到底能看到什么，必须是一条可回放、可求差的规则，而不是散落的拼接字符串。codex 的答案是两层抽象：① 一批 ContextualUserFragment（一次性注入的「片段」，约 48 类，core/src/context/mod.rs:1 的 mod 清单）；② 一个 WorldState（跨轮、跨压缩持久的「投影」，每个 section 都有 snapshot 与 diff 两套形态）。

「无损投影」的核心 = 差量渲染 —— world_state/mod.rs:405-413（相对精确持久化快照求差）：

/// Renders each section against the exact persisted snapshot when available.
pub(crate) fn render_diff(&self, previous: &WorldStateSnapshot) -> Vec<Box<dyn ContextualUserFragment>> {
    self.render_with(|id, _| match previous.sections.get(id) {
        Some(previous) => PreviousSectionState::Known(previous),
        None => PreviousSectionState::Absent,
    })
}

④ 代价与边界

「快照 + diff」比「编辑 map」更强的地方：每个 section 自带可序列化 Snapshot 类型，rollout 里存的是完整的、可独立校验的状态值，恢复时不必重建历史。代价：① 每个 section 都要手写 snapshot()/render_diff()/matches_legacy_fragment() 三件套（样板代码多）；② diff 正确性依赖 PreviousSectionState::Known/Unknown/Absent 三态判据——Unknown（能从旧历史认出片段但无精确快照）是兼容老会话的妥协，属于隐藏复杂度。

⑤ 我的判断

这比 cline 的「EditType/ContextUpdate 记录编辑、读取时应用」更面向持久化与恢复：投影的产物直接就是可落盘的 snapshot，而非仅作用于内存视图。代价是把「投影」从「一处集中逻辑」摊到「每个 section 各写一份」。

3. 线2 — 检查点与压缩窗口 sidecar（回滚路径）

线2 ① 解决什么问题：压缩不是单向的——要能精确知道「压缩到第几窗、基线是哪一版」，重启后不丢、不回错。codex 的答案是把压缩变成**一个带持久化 sidecar 的检查点事务**：摘要 + 新窗口边界 + WorldState 基线一起落进 Rollout。

④ 代价与边界

关键取舍：codex 的「回滚」不是 cline 的「时间戳截断」也不是 deepseek 的「重放整条事件流」，而是「新窗口 + 直达新基线的替换历史」——它把被压缩的那段历史整体替换成「初始上下文 + 摘要 + 保留片段」，旧窗口边界只用 window_id 链（first/previous/window_id）留痕，用作审计与恢复的锚，而不是保留完整旧文本。代价：① 一旦替换历史写完，旧的逐轮细节在核心 history 里就不再逐条可查（如需取证要靠 guardian_history / retained_context 旁路）；② 跨窗口一致性依赖 Uuid::now_v7() 的单调性（时间有序 id，用于断点排序）。

⑤ 我的判断

与任务书里 cline 的「PR #12747 修 compaction sidecar」是同构问题：两者都担心「压缩状态没持久化好导致重启后重复压缩/阈值错乱」。codex 把 sidecar 直接做成 AutoCompactWindowIds + window_number 并随 CompactedItem 一起原子落盘，是同一风险的工程解法，只是用了 Rust + Rollout 的类型化表达。

4. 线3 — Hook/插件/扩展 API（扩展边界）

线3 ① 解决什么问题：核心循环里的「压缩前后、工具前后」这些关键时刻，如何让第三方安全地插一脚。codex 有三层扩展机制，粒度从粗到细：Hook（生命周期回调）→ Plugin manifest（声明式能力清单）→ Extension API（Rust trait，直接贡献世界状态）。

③ 核心问题的边界判断：Auto Compact 能不能做成插件？


                      ┌────────────── （收：压缩引擎）────────────────┐
   compaction 决策    compact.rs:731 / compact_remote.rs /            │  ← 硬编码在 core，
   与摘要生成         compact_token_budget.rs                          │    不可插件化
                      └───────────────────────────────────────────────┘
                      ┌────────────── （放：注入给模型看的内容）───────┐
   WorldState section  ContextContributor::contribute_world_state      │  ← 开放：扩展可
   + 一次性片段        + contribute_contextual_user/developer          │    新增投影 & 片段
                      └───────────────────────────────────────────────┘
                      ┌────────────── （任务状态）────────────────────┐
   Goal / Plan / TODO  ext/goal → codex_state::ThreadGoal；            │  ← 独立于对话，
                      update_plan 工具                                 │    跨压缩存活
                      └───────────────────────────────────────────────┘

结论：「收」（何时压缩、怎么摘要、怎么替换历史）是 core 内置，不可插件化（压缩引擎三种实现都写在 core/src/compact*.rs，没有 trait 边界）；「放」（模型能看到哪些 world-state / 片段）是开放的（ContextContributor）；「任务状态」是第三条独立出路（goal 扩展靠 codex_state::ThreadGoal 存在 thread 上，不靠对话历史）。

④ 代价与边界

Hook 的 Sync/Async 双模式意味着「同步钩子能阻塞核心循环」——这是一把双刃剑：强一致性（PreCompact 同步钩子能拒绝压缩）但也会引入第三方的延迟/死锁风险。Extension API 要求写 Rust 并链接进 workspace，比 Hook 的「外部命令/JSON 协议」门槛高得多。

⑤ 我的判断

相对 cline 的「箱内插件」和 opencode 的「WebSocket hook」，codex 的三层（Hook 进程级 / Plugin 声明级 / Extension Rust trait 级）覆盖了从「运维脚本」到「深度定制投影」的全谱系，且把「投影注入」这个我们最关心的面，明确定位成 Extension API 的开放点——这是回答任务书 H-B「能否把别家的压缩/投影做成 BaiZe 的插件」的直接教材。

5. 线4 — Goal/Plan 任务状态跨压缩存活

线4 ① 解决什么问题：压缩把对话历史「收」掉之后，「现在要做什么、做到哪了」不能丢。codex 把「任务状态」从「对话」里拆出来，给了两条独立出路：goal 扩展（持久化的 thread 目标，带预算/用时）与 plan 工具（任务清单/进度）。

「只为跨轮审计」的快照入账 —— runtime.rs:521-536 用 progress_snapshot(turn_id) 拿到 {expected_goal_id, time_delta_seconds, token_delta} 后调 current_goal_status_for_metrics，说明 goal 的「预算消耗/剩余」是会计级独立记账、与对话轮次解耦。

plan 工具 —— core/src/tools/handlers/plan.rs（update_plan），与 context/mod.rs 里的 plan 片段联动。

③ goal 为什么「跨压缩存活」很多人没答清的两层

① 持久层：goal 存在 codex_state::ThreadGoal（thread 作用域的键值侧表）里，不落在被压缩的对话 history 中，因此摘要替换历史动不到它。② 投影层：goal 在每轮通过 get_goal / 扩展开的 world-state 片段重新注入给模型，属于「每次重算当前状态」，而非「依赖历史前缀」。这与线1 的 WorldState 同构：状态 ≠ 文本，状态落侧表、文本才进 history。

④ 代价与边界

goal 的「blocked 审计」有严格语义（spec.rs：blocked 需「同一阻塞条件连续 ≥3 个 goal turn 复发」且「恢复后重置审计」）——这是把「任务停滞」也做成引擎级状态机，而非纯提示词。代价：goal 状态一旦与对话历史不同步（例如模型口头说完成但没调 update_goal），会出现「状态表与叙述脱节」的经典问题，codex 靠 get_goal 的 status/budgets/usage/remaining 输出强制对齐。

⑤ 我的判断

这是五条线里对「H-A SWE-bench 长任务」最有用的一条：codex 明确区分了「任务意图（goal，跨压缩持久）」与「执行产物（history，可压缩）」。cline 靠 taskId 元数据近似实现，deepseek 靠事件溯源里的 immutable 意图事件，codex 直接给了 ThreadGoal 独立存储——三家的「意图存续」解法可以横向对比成一张表（见 §7）。

6. 线5 — 模型能力适配与降级策略

线5 ① 解决什么问题：不同模型上下文窗口不同（200K / 1M…），「什么时候该压缩、压到剩多少」必须由模型能力驱动，而不是拍脑袋。codex 把阈值计算集中到 protocol/src/openai_models.rs 的 ModelInfo，再由 session/context_window.rs 消费。

② 怎么实现（贴原文）

三阶阈值：resolved → usable → auto_compact —— protocol/src/openai_models.rs:488-511：

pub fn resolved_context_window(&self) -> Option<i64> {
    self.context_window.or(self.max_context_window)          // 档位上限
}
pub fn usable_context_window(&self) -> Option<i64> {
    self.resolved_context_window()
        .map(|cw| cw.saturating_mul(self.effective_context_window_percent) / 100)  // 默认 ×95%
}
pub fn auto_compact_token_limit(&self) -> Option<i64> {
    if let Some(limit) = self.auto_compact_token_limit { return Some(limit); }
    self.resolved_context_window().map(|cw| (cw * 9) / 10)   // 兜底 clamp 到 90%
}

⑤ 代价与判断

代价：每模型都要在后端 model_info 里维护 context_window / max_context_window / auto_compact_token_limit / effective_context_window_percent 四个字段（:433-448），配置面更宽、更容易写错（所以才有 :1976 那个「三语义勿混」的守护测试）。判断：这是一套「以模型元数据为单一事实源」的自适应压缩，比硬编码阈值可移植；BaiZe 若要支持多个不同窗口的模型，这条「config 元数据 + 消费端三阶阈值 + 服务端观测优先」值得照抄。

三条最有迁移价值的判断

  1. 「状态 ≠ 文本」：要把「意图/目标」（goal）、「环境投影」（WorldState）长期存侧表，只让「对话文本」进可压缩的 history。这是 codex 对「压缩不丢任务」的最干净回答（§5③）。
  2. 「压缩 = 一个带 sidecar 的检查点事务」：摘要生成、新窗口、WorldState 基线三者必须原子落进同一 Rollout，window_id 链提供审计与恢复锚（§3④）。
  3. 「收（压缩引擎）关、放（投影注入）开」：想复用别家压缩算法，BaiZe 应把「压缩决策/摘要」与「投影注入」拆成两个接口，前者保留自家核心，后者开放给插件（§4③）。
