10. 结论：58 pp 里多少是“协议可回收”

初步判断（基于 DeepSeek 94% 侧实测 + 对 36% 侧的合理外推，待 36% 轨迹实测修正）：
58 pp 差距的主体（估 35–45 pp）是“协议可回收”部分——工具调用频次/合法率(D1/D2)、API 领域知识(D4 执行报错占 74%)、执行反馈迭代闭环(D6)。这三者分别对应 post-train 三步：
① SFT 注入工具轨迹 + PyAether API 语料 → 修 D1/D2/D4-执行报错（回收 ~20–30 pp，对应 M1→M2）；
② 领域退火补 API 知识 → 降 import/file 错（回收 ~5–10 pp）；
③ RL(GRPO) 打磨“查-写-改”闭环 → 提 Φ、降断言失败（回收 ~5–10 pp，对应 M3）。
剩余 ~10–15 pp 为“真实能力差距”（语义推理/复杂多 API 任务），逼近 DeepSeek 94%(M4) 需更大量 RL + 可能更大模型。
未闭合项：MiniCPM5-2B 36% 侧 D1/D2/D6 未实测（轨迹不在本节点）。上述比例是“基于强模型行为外推的假设”。补齐 36% 侧后，本结论将从“假设”升级为“实测对照”。需运维提供：~/eda_code_eval/<36%_run>/{final_report.json, trace/*/api_conversation_history.json}。

12.1 判读

  • D1 与 D3 跨运行稳定（相对差 <10%）：工具调用强度代理与超时比例是鲁棒指标，单次估计即可信。DeepSeek 在两次运行中均保持 0.63–0.67 的工具调用强度且零超时。
  • D2 / D4 / D6 跨运行波动 20–30%：工具频次（20.5 vs 14.3）、迭代轮数（7.1 vs 5.0）、错误构成（100% 执行报错 vs 74%/26%）在两次运行间显著变化。→ 单次运行的 D2/D4/D6 点估计不可靠，必须多运行取均值。这从诊断侧直接印证了评测协议“5-run mean±std”的必要性（总纲 §5.3 红线）。
  • 错误提取敏感性：run-A 平均仅 0.04 个错误/任务（几乎无错误被标记），run-B 为 0.85/任务。差异可能源于（a）run-A 确实更“干净”（更多任务一次通过），或（b）轨迹格式/提取器版本差异导致 run-A 的错误未被捕获。警示：诊断指标对轨迹解析管线版本敏感，正式 post-train 评测须用冻结的同一版 trace_reader。
  • 对 36% 侧诊断的启示：由于 D2/D4/D6 单次波动可达 30%，MiniCPM5-2B 36% 侧的 D1–D6 也需≥2 次运行才能给出可信对照。若仅有单次轨迹，D1/D3 可信、D2/D4/D6 须标注“单次估计，±30% 噪声”。
对核心结论的影响：跨运行验证不改变第 10 节的核心判断（58 pp 主体为协议可回收），但增加了置信区间——D1/D3 稳定支撑“工具协议/超时非瓶颈”的判断；D2/D6 的波动说明“频次/迭代”指标需多运行收敛，且 DeepSeek 侧的“高频用工具 + 多轮迭代”行为在两次运行中均成立（v1 更高：20.5 次 + 7 轮；v1_3：14.3 次 + 5 轮），方向一致，仅幅度有噪声。
