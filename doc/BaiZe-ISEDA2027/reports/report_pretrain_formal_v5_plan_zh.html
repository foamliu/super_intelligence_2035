§6 长上下文注入（ABF）

6.1 注入方案 = ABF（不是 YaRN），分两层

推理侧（零训练）

rope_theta: 1e4 → 1e6
max_position_embeddings: 4096 → 1,048,576（1M）
沿用 baize_b1_longctx_extend.py 的 B1 写法
既有实测：PPL 4K=83.24 → 128K=54.66 → 1M=55.42，全程 53–56 无退化。
机制解释：56 层里只有 4 层 full_attention 吃 RoPE，Mamba2 层无位置编码 ⇒ ABF 只需适配 4/56 层 → 这是 hybrid 相对 dense 的结构性优势。

训练侧（真正“注入”）

ABF 免训练只保 PPL，不产生 needle/多跳检索能力（B1 已证 passkey 0%，且明确“是模型能力问题不是 ctx 问题”）⇒ 1M 能力必须在长上下文续训阶段用真实长文档训练，不能只靠配置外推。

6.2 ABF vs YaRN 对比（含代价）

方案代价收益结论
ABFPPL@4K +10.5%（75.36→83.24）免训练到 1M；零依赖（改 config）✅ v5 采用
YaRN需 rope_scaling 参数（factor/original_max_pos/attn_factor）对只作用于 4 层的 hybrid 收益有限、且引入新的超参面仅作对照/兜底
仓库既有结论：hybrid 应沿用 B1 的 ABF 写法，dense 才需 YaRN/rope_scaling（ARCHIVE_OPERATOR_PRETRAIN.md）。

6.3 次序评估：decay → 1M → SFT/RL

段评估理由
decay 在 1M 前✅ 合理先让 Stable 段收敛（LR 从 1e-3 降下来），再进长上下文；否则恒定 1e-3 在 1M 长度上会破坏已学分布
1M 在 SFT/RL 前✅ 合理对齐阶段（SFT/RL）的样本要“装得进”上下文，长上下文能力必须先具备；顺序颠倒会逼 SFT 用短样本、再返工。但要求写成“长上下文阶段也是预训练的一部分”，用 pretraining 数据（长文档/代码库/多文件仓库），不是 SFT 数据
裁定：✅ 采纳 decay → 1M → SFT/RL。

附录：可行性问题正面回答

Q1: LR 1e-3 恒定是否会欠拟合？

历史对照：P-8 用 3e-3（44B, 发散后换 1e-3 AdamW 重启）；decay run 用 1.67e-3→1e-5。
判断：1e-3 介于 P-8（3e-3）和 decay min（1e-5）之间，合理但偏保守。1.5T token 量大，恒定 LR 可能在 S2 后半段收敛放缓。
监控判据：每 2000 步记录 loss；若 S2 后半段（步 370K+）loss 仍单调不降 → 建议在 S2 末端加短 decay（需用户批准，不得擅改）。

Q2: batch 从 2M 跳到 4M 怎么处理？

seq 4096 / MBS 2 时：2M tok → GBS 488（grad accum 31）；4M tok → GBS 976（grad accum 61）。
per-step 时间：8.0s → 16.1s（@249K）。
切换记录：S1 最后一个 ckpt 的 loss vs S2 第一个 ckpt 的 loss（断点监控）。

Q3: en_v1_4 数据量够吗？

需 500B tok，全量 ≈2.31T tok（实测 0.343 tok/parquetB × 6.75TB, PLAN_V5_DATA_PREREQ.md §3）。500B = 全量的 21.6%。
当前：86/110 shard 已下（≈4.08TB ≈ 1.40T tok），已下部分就够 500B（余量 2.80×）。
分词实测：端到端 375K tok/s/进程，16 并发 ≈ 1 天切完 500B（纯 CPU）。R3 已降级为 🟢。

Q4: S2 混料供给够吗？

code 200B：UltraData-Code 411B ✅（余量 2.06×）
math 10–20B：UltraData-Math 303B ✅（余量 15–30×）
HQ 780–790B：ultraweb_en(1.12T) + l1_en_hq(152B) + zh(112B) + UltraX(31B) = 1.415T ✅（余量 1.82×）
瓶颈 = HQ 预训练（余量最低 1.82×，但充足）。所有数字可追溯至 DATA_LEDGER.md。
