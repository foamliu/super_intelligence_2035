撰写：2026-10-28 · 运维令 11:5x · commit: pretrain 报告:

核心结论（直接回答用户疑问）：训练时不会「串行出不同源」。 每个 global batch 内的样本已经按权重均匀交错包含全部 7 个数据源—— 不是「先读完源 A 再读源 B」，而是「每个位置都从混合索引取样本」。 此前 308K tok/s 的「串行」只发生在 nw=0 时「数据准备 vs GPU 计算」这一层 （每步 ≈6.8s 数据准备 + 6.8s 计算串行），与「源 vs 源」无关。

1. 背景：什么是 Blend？

BaiZe-2B 预训练使用 7 个数据源按权重混合（blend）训练。配比见 blend_s1.tsv：

数据源权重 (prop)说明
en_v1_4 (Ultra-FineWeb EN)0.65英文网页主体
code_l2 (UltraData-Code-L2)0.15代码中等级
ufw_l1_en_hq0.05英文高质量
math_l10.05数学基础
ufw_zh0.04中文网页
code_l30.04代码高等级
math_l30.02数学高等级
合计1.00—

问题：Megatron-LM 如何在训练时按这些权重混合 7 个数据源？是串行读还是交错读？

2. Megatron Blend 的「索引层」逻辑

2.1 核心数据结构：两个索引数组

Megatron 的 BlendedDataset 在初始化时一次性构建两个数组并缓存为 .npy 文件：

数组含义长度
dataset_index每个采样位置取哪个数据集（0~6 对应 7 源）总样本数 N
dataset_sample_index在该数据集内取第几条样本总样本数 N

训练时 DataLoader 只需按序遍历这两个数组——O(1) 查表，无额外计算。

2.2 索引构建算法：Bresenham 式加权交错

底层由 C++ 函数 helpers.build_blending_indices 实现。算法本质：

对每个采样位置 i（0, 1, 2, ..., N-1）：
    对每个数据源 k：
        deficit[k] = weight[k] * (i+1) - sampled_count[k]
    选择 deficit 最大的数据源：chosen = argmax_k(deficit[k])
    dataset_index[i] = chosen
    dataset_sample_index[i] = sampled_count[chosen]++

这保证了每个数据源的实际采样比例最大误差 ≤ 1 个样本，且不同源的样本在序列中均匀交错而非成块聚集。

直观理解：想象 7 个水龙头，每个有不同的流速（=权重）。Bresenham 算法就像一个快速旋转的阀门，在每一滴水时选择「欠采样最严重」的那个水龙头放一滴。结果 = 7 股水流均匀交织成一股混合流。

3. 具体交错序列示例（权重 0.65 / 0.35）

为方便理解，以简化的 2 源为例（源 A 权重 0.65，源 B 权重 0.35），展示前 20 个采样位置的交错序列：

位置 i012345678910111213141516171819
数据源 AABA ABAA BAAA BAAB AAAB
累计 A:B 1:02:02:13:1 4:14:25:26:2 6:37:38:39:3 9:410:411:411:5 12:513:514:514:6

20 个位置中 A 出现 14 次（14/20 = 0.70 ≈ 0.65），B 出现 6 次（6/20 = 0.30 ≈ 0.35）。随着序列增长，比例收敛到精确 0.65/0.35。实际 7 源的交错逻辑完全相同，只是 argmax 在 7 维上操作。

4. 训练时数据流（索引 → 取样本 → 组 batch → compute）

训练时的数据流路径：

统一混合索引
(dataset_index +
dataset_sample_index) → DataLoader
按序取 N 个样本
(N = global_batch_size) → 组 batch
样本来自 7 源
已交错混合 → GPU compute
forward + backward
+ optimizer step
  1. 统一混合索引：训练启动时，BlendedDataset 从 .npy 缓存加载（或首次构建）两个索引数组。数组长度 = 所有数据源的总样本数。
  2. DataLoader 取样：每个 training step，DataLoader 从当前 epoch 的索引位置开始，取 global_batch_size（= 256）个样本。每个样本的「来源」由 dataset_index[pos] 决定，「该源内序号」由 dataset_sample_index[pos] 决定。
  3. 组 batch：256 个样本已天然混合 7 源（按权重交错）。不存在「这个 batch 全是 en_v1_4，下个 batch 全是 code_l2」的情况。
  4. GPU compute：batch 送入 GPU 做 forward/backward/optimizer step。模型看到的就是一个混合了多源数据的 batch。

5. Pre-blend 与 Blend 的关系（正交两层）

关键区分：pre-blend（物理合并 shard）与 blend（索引交错）是两个正交的层，互不影响。
Pre-blend（物理层）Blend（索引层）
做什么把 628 片小 shard 合并成 ~100 片大 shard按权重交错采样 7 个数据源
改什么文件数 / 索引大小（628→100）不改权重、不改交错
为什么减 shard 数 → 减 fork-COW 内存膨胀 → 可开 nw=8保证 7 源按 0.65/0.15/.../0.02 混合
对训练的影响吞吐恢复（308K → 613K）数据配比（不变）

pre-blend 不改任何权重、不改交错算法、不改数据内容——只是把同一数据源的多片小文件合并成少数大文件，减少 DataLoader 打开/索引的文件数量。

6. 为什么之前吞吐只有 308K？

根因：不是「源 vs 源串行」，而是 nw=0（num_workers=0）导致数据准备与 GPU 计算串行。

正常情况下（nw=8），DataLoader 的 8 个 worker 子进程在 GPU 计算当前 step 的同时，预先加载下一个 step 的数据（数据/计算 overlap）：

nw=8 (理想 overlap):
  Worker: [加载数据_0] [加载数据_1] [加载数据_2] ...
  GPU:                 [compute_0]  [compute_1]  [compute_2] ...
  总步时 = max(加载, 计算) ≈ 6.8s  → 613,992 tok/s

nw=0 (串行):
  主进程: [加载数据_0] [compute_0] [加载数据_1] [compute_1] ...
  总步时 = 加载 + 计算 ≈ 6.8s + 6.8s = 13.6s  → ~308K tok/s

此前 nw=8 会 OOM 的原因是：628 片小 shard 的 blend 索引在 fork 子进程时因 Copy-on-Write (COW) 机制导致内存膨胀 → swap 耗尽 → OOM-kill。pre-blend 把 shard 数从 628 减到 ~100 后，索引数组骤小，COW 可忽略，nw=8 可正常工作。

7. 总结

  • 训练时不会串行出不同源：每个 batch 内 7 源按权重交错混合（Bresenham 算法，误差 ≤1）。
  • Blend 索引一次性构建并缓存：训练时 O(1) 查表，无额外计算开销。
  • Pre-blend 与 Blend 正交：pre-blend 只减 shard 数（物理合并），不改权重、不改交错。
  • 308K → 613K 的吞吐差额：来自 nw=0 的数据/计算串行，与「源 vs 源」无关。pre-blend 后恢复 nw=8 即可。
