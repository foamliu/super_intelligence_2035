seq8192 掉速 5.5× 的决定性归因 · 运维令 2026-10-25 23:0x 通宵攻坚交付 · rev1 @ 2026-10-26 00:4x

🎯 一句话结论（收敛条件 #1）

驱动变量 = tok/microbatch/GPU（= mbs×seq），与 seq 长度无关、与批几何(gbs/accum)无关。当 tok/mb ≥ 16384 时，单卡峰值激活显存顶到 ~80GB HBM 上限（reserved 74GB / max-allocated 69GB，余量仅 ~6GB）；在此显存压力下 PyTorch caching allocator（expandable_segments:True）与 CUDA-graph replay 进入显存受限(memory-bound)执行，实测 GPU 达成算力从 ~830–960 TFLOP/s（~84% MFU）崩到 ~125 TFLOP/s（~13% MFU），每 token 耗时上升 5.4×。tok/mb ≤ 12288 时峰值 <70GB、余量 ≥10GB，维持基线 606,449 tok/s。

基线 tok/mb=12288 606,449 tok/s 悬崖 tok/mb=16384 ~110,000 tok/s 跌幅 5.5× 峰值显存 67.6GB → 81.1GB顶格 修复配方 seq8192/mbs1 605,012 tok/s ✓

⛔ 两版旧归因 hereby 作废（均被本轮阶梯实验证伪）

旧①「seq 长度效应 / SSM 超线性」（seqlen 网格报告 + #779/#781）：声称 seq≥8192 触发 SSM 超线性开销。证伪：E5a(seq=2048, mbs=8, tok/mb=16384) —— seq 仅 2K（最小）却仍 ~110K tok/s 慢档；而 E3(seq=12288, tok/mb=12288) seq 高达 12K 却 617K 快档。seq 从 2048 到 16384 都能快也都能慢，唯一判据是 tok/mb。

旧②「小批几何 → GPU 饥饿 / kernel-launch 间隙」（#782 根因报告「MFU 73.6%→14%」）：声称 cfg0a 的 gbs512/accum8 小批导致 GPU 空闲。证伪：E2(seq8192/mbs1/gbs256/accum16, tok/step=2.10M = 与 cfg0a 同量级小批) 却 84% MFU / 605K tok/s 快档。E2 与 cfg0a 批几何几乎相同（tok/step 均 2.1M、accum 均 ≤16），唯一差别 = tok/mb（8192 vs 16384）+ 峰值显存（55GB vs 81GB）。故 13% MFU 是「显存受限」的症状，而非「批太小 launch 间隙」的成因。

2. 显存对比（Rank 0，after 10 iterations）—— 显存假说确认

运维令「显存假说（首选）」要求取 torch 显存快照在两侧比对。Megatron 自带 [Rank 0] (after 10 iterations) memory (MB) 报告即取自 torch.cuda.memory_stats()，三档实测如下：

关键读数：

  • max-allocated 随 tok/mb 单调爬升：42.8GB → 56.0GB → 69.4GB（8192→12288→16384，近似线性 ∝ tok/mb，符合「激活显存 ∝ mbs×seq×hidden×layers」）。
  • reserved 同步：51.3GB → 64.3GB → 74.1GB。H100 80GB HBM 减去 reserved 仅余 ~6GB 工作区 → 顶格。
  • 达成算力 在 E2/E3 维持 830–960 TFLOP/s（~84% MFU），到 E5a 崩到 125 TFLOP/s（~13% MFU） —— 不是「GPU 空闲等 launch」（#782 说法），而是 GPU 在跑但每个 kernel 都被显存带宽/分配器拖慢（memory-bound）。
  • 当前生效 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True；未开 --recompute-activations（全激活驻留 ⇒ 激活显存 ∝ tok/mb 是顶格的直接来源）。
激活显存 ≈ (mbs × seq × hidden × layers × dtype_bytes) × recompute_factor
tok/mb = mbs × seq ⇒ 激活显存 ∝ tok/mb（与 seq 单独无关）
tok/mb 8192 → 12288 → 16384 ⇒ max-alloc 42.8 → 56.0 → 69.4 GB ⇒ reserved 51.3 → 64.3 → 74.1 GB ⇒ 触顶 ~80GB ⇒ memory-bound ⇒ MFU 84% → 13% ⇒ 5.5× 掉速

4. 修复配方与验收（收敛条件 #2）

✅ 「8K 满速配方」已实测达标（运维令要求 tok/s ≥ 0.7×606K = 424K）

seq=8192 / mbs=1 / gbs=256 / accum=16 → tok/mb=8192 → 605,012 tok/s = 1.00×基线（远超 0.7 门槛），峰值仅 55.4GB，loss 7.56 / gnorm 0.59 / nan 0 健康。这就是给用户的答案：8K 上下文满速只需 MBS=1。

16K 上下文（seq=16384）处置：必须上 Context Parallel (CP)

seq=16384 单卡 mbs=1 已是 tok/mb=16384 慢档（cfg3=112K）。要让 16K 满速，唯一出路 = CP 把序列切到多卡，把单卡有效 tok/mb 压回 ≤12288：

  • CP=2（seq16384 切 2 卡）→ 单卡有效 seq=8192 → tok/mb=8192 → 预期回到 ~600K（待 20 步 smoke 验证，本轮未跑）。
  • CP=4（seq16384 切 4 卡）→ 单卡有效 seq=4096 → 更稳，但占用更多卡做通信。
  • 或开 --recompute-activations 把激活显存降一档，可能把 16384 的峰值从 81GB 压到 ~70GB 以下（需实测，属「配方变更组」，运维令要求单列不混主表）。
未跑项（诚实标注）：CP=2/4 smoke 与 --recompute-activations 重测本轮未执行（优先把 11 格主表 + 根因锁死）；列为下一步最小实验（各 ≤30 分钟可跑）。E5b(seq=1024/mbs=16, tok/mb=16384) 在 E5a 后由脚本自动起跑，进一步印证「极小 seq 也慢」，出数后补入 TSV。
