6. 机制解释（为什么 99.4%？为什么 IB 调参无收益？）

核心问题：为什么双机扩展效率能到 99.4%？为什么 IB 调参全无收益？

  1. 梯度体积：模型 2,220,268,032 参数（2.220B），BF16 梯度 ≈ 4.44 GB（参数量×2 bytes）。
  2. 跨节点传输量：e18 开启 --use-distributed-optimizer，梯度按 16 rank 分片，跨节点 reduce-scatter 传输 ≈ 2.2 GB/节点（分片口径）；上界（不分片全 allreduce）≈ 4.4 GB。
  3. 通信耗时：RoCE busbw ≈ 46 GB/s → 传输耗时 ≈ 0.05s（分片）/ 0.1s（上界）。
  4. 占步时比例：步时 6.81s → allreduce 占 ≈ 0.7%（分片，实际部署口径）/ ≈ 1.4%（上界） → < 2%，噪声级。
  5. 结论：通信开销远小于 6.81s 计算 → 近线性扩展是物理预期。NCCL_IB_QPS_PER_CONNECTION / NCCL_MAX_NCHANNELS / NCCL_ALGO / NCCL_PROTO / NCCL_NET_GDR_LEVEL 等 IB 参数只能压缩"通信"这一已非瓶颈的环节， 故结构性无收益。GPUDirect RDMA + 12×RoCE 多通道已把跨机通信压到噪声级。

↳ 这解释了为何 qps4(+0.0%)、qps8(+0.2%)、maxnch64(+0.0%) 三项实测全部落在 run-to-run 噪声范围内（Δ≤0.2%）， 也预测了 §5 其余未测 IB 调参项（algo/proto/gdr/hca/cross_nic）同样无收益。本机制分析为推论，已由 3 项独立实测一致印证。

7. 与单机优化线的对照

单机（DP=8）已完成 10 项候选（e00–e09 等），9/10 完成，命中吞吐上限 305,098 tok/s（e18）。

  • 上限 5 条依据：
    • VRAM：MBS4 四变体（e10/e10b/e17/e19）全 OOM（73.8GB > 80GB 余量）
    • 计算：GPU 利用率 100%，compute-bound
    • 通信：NCCL 调参无收益（本报告 Task B 印证）
    • 软件栈：torch.compile fullgraph 崩溃（AssertionError）
    • FP8 blockwise：驱动级阻塞（需 CUDA 12.9）
  • #2 CUDA 12.9 驱动级 BLOCKED（驱动 570.195.03 < 575，无 sudo 无法升级）——软件栈侧无进一步空间。
  • 双机对照：单机 305,098 → 双机 606,449（+99.4%）⇒ 双机几乎无损地翻倍了吞吐。
结论：单机软件侧已撞天花板（305K），双机扩展近线性（99.4%）—— 要再提吞吐只能靠加节点做数据并行，软件侧单机/双机均已无优化空间。
