三句话：
① 长上下文越用越省：prefill 优势从 4K 的 3.7× 单调拉到 128K 的 23× —— 这是 SSM O(n) vs attention O(n²) 的结构性差异，不是调参出来的。
② 长上下文"能不能服务"由显存决定，而这条我们赢 2–4.5×：128K×bs1 只要 13 GB（稠密 61 GB）；稠密在 128K×bs8 直接 OOM。
③ 代价只有训练吞吐 −8%（不是论文早期写的 −24%，那是跨节点测量 artifact），且参数还少 11.6%。

4🔑 关键：我们现在测到的是"下界"（而非上限）

核准到的配置事实（来自入库的 HF 转换脚本与对照 config）：

我们（baize_p6_ckpt_to_hf.py → nemotron_h config）
    "max_position_embeddings": 4096
    （无 rope_theta / 无 rope_scaling）        ⇒ 走 transformers 默认 rope_theta = 1e4

对照 MiniCPM5-2B（MiniCPM5-2B.config.json）
    "max_position_embeddings": 131072
    "rope_theta": 5000000                     ⇒ 比我们高 500×
⇒ 基线是"天生为长上下文配的"，我们从没配过。 而且 P-9.11 的 128K 结果不是"质量崩"而是 被直接拒绝（e2e≈0.5s、total_completion_tokens=0、非 OOM / 非超时），而 4K / 16K / 64K 都成功。
这意味着：本报告里的 3.7×–23× 与 0.22×–0.44× 是在 "hybrid 完全没有为长上下文做任何准备" 的条件下测出来的。
⇒ hybrid 的长上下文能力尚未被真正测过；B1 只需改 config（max_pos→131072 + rope_theta→5e5/1e6 + 试 PI/NTK/YaRN）就能给出统一口径的真实曲线。
⇒ 也就是说：目前的数字是"最保守"的一版，对申请资源而言是安全的下界。

5为什么这对 agentic EDA 特别重要

  • agentic 轨迹天然长：代码文件 + 工具返回 + 多轮 generate–execute–refine 的中间结果，很容易超过 32K；一次端到端 refactor 的上下文常达 数十万 token ⇒ 这是本项目 README 风险表 #3 🔴 明确点出的问题（"4096 对 agentic 轨迹过短"）。
  • 在长上下文里，"能不能服务"优先于"跑得快"：稠密模型在 128K 下要么 OOM（bs8）、要么显存吃掉绝大部分卡容量；hybrid 用 1/4–1/5 的显存就能服务同样长度 ⇒ 直接决定单卡能放多长的上下文、能并发多少条轨迹。
  • prefill 是大头：agentic 每一轮都要把整段上下文重新 prefill 一次；prefill 加速 3.7×→23× 直接乘以"轮数 × 任务数"，是端到端吞吐与成本的主要杠杆。
  • 与 ZhuLong 的叙事衔接：harness 把观测保真度解决之后，backbone 侧的长上下文成本就是下一个瓶颈——而 hybrid 恰好在这一点上占结构性便宜。

At 128K context, the 2.22B Mamba2-hybrid serves with 0.22× the memory of the 2.51B dense baseline (13 GB vs 61 GB at bs=1), while the dense baseline OOMs at 128K×bs=8. Prefill speedup grows monotonically with context length—from 3.7× at 4K to 23× at 128K—reflecting SSM O(n) versus attention O(n²) scaling, at a cost of only −8% training throughput and with 11.6% fewer parameters.
