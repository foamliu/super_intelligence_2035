3.1 为什么共享 temp 会把真码丢成 1 行（根因机理）

format_cline_cli_output.py 分两步：① process_cline_gene_files()（L138-）把每个 task 的 code/<task>/pyAether_code/*.py 拷进共享相对临时目录 ./pyAether-eval/temp/pyAether_code；开头 L157 先 shutil.rmtree 清空它。② format_cli_gene_code2jsonl()（L88-，读 L95 同一共享 temp）再把这些 .py 写成 generations jsonl。

L155-157（拷前先 rmtree 清空共享 temp）： 
temp_path = "./pyAether-eval/temp"
pyAether_code = "./pyAether-eval/temp/pyAether_code"
shutil.rmtree(pyAether_code, ignore_errors=True) or shutil.os.makedirs(pyAether_code)
L165（拷贝源 = 正确路径，非 ws）：
folder_path = os.path.join(cli_output, folder_name, "pyAether_code")
L95（jsonl 读取 = 同一共享 temp）：
pyAether_code = "./pyAether-eval/temp/pyAether_code"

因 temp 是进程间共享的相对路径（非按 batch 隔离），36.15 上多个 eval 并发时（实测 run2 batch 110506 起跑时，PID3245417 zhulong eval 同跑、batch 110406 早 1 分钟起），后启动者的 L157 rmtree 把前者已拷进去的 .py 清空 → 前者的 format_cli_gene_code2jsonl 在 L100 os.listdir 时只看到 0~1 个文件 → generations jsonl 只剩 0~1 行。run1 跑得早、并发少未被踩，故 36 行真实。

推翻早先假说：23:xx 版曾据 run2 仅 1 个 task 带 ws/ 子目录，推断「L166 只读 ws/pyAether_code」。取证源码后 L165 实读 pyAether_code（无 ws），该假说作废；真因是共享 temp race。

4. 四个异常的逐一解释（A/B/C/D）

异常 A：completed 158 行 vs execution 仅 1 行；run_eval「有效生成」判定在哪？

判定位置：run_cline_script.sh(Step 7.1) 调用 run_eval.py -g completed_code_generation_<BATCH>.jsonl；该 jsonl 由 complete_code_generation.py 消费 format_cline_cli_output.py 的产出生成。completion 为真实代码的题才被 assemble_for_execution.py 拼装送沙盒 → 产生 execution_results。completion 为 "pass"（哨兵）= 该题无 .py 进入 generations jsonl。

complete_code_generation.py:69（无 .py 的题写哨兵）：
record = {"task_id": task_id, "completion": "pass", "status": status}
run_eval.py:570（有效生成判定）：
if completion not in ("", "pass"):   # 视为有效生成，送 assemble
→ run2/run3 generations jsonl 经共享 temp race 后只剩 1 行真码 → 仅 1 条 execution_result。run1 共享 temp 未被踩 → 36 行真码 → 36 条。

run4 的 1 行另有原因：run4 未产新 output_evaluation 目录，链脚本 ls -dt|head -1 拷了 run3 的 20261115_1834 → 与 run3 字节相同（见 §1 sha256）。

异常 B：completion/status 字段语义？谁写？和 run_eval 读的是同一个吗？

由 Step 6 complete_code_generation.py 写。completion=抽取到的代码原文（无代码时哨兵 "pass"）；status=success(有代码)/fail(无)/timeout。run_eval 正是读这个文件（-g 指定 → patch_config 写 config.yaml 的 generations_file → assemble 读取）。是同一个文件。run1 本机那份「全 pass」的 completed_code_generation.jsonl 是链脚本串文件拷错（从另一 degenerate batch 拷来），与其真实 final_report(generation_success=36) 不符——这是链脚本拷贝 bug 的另一处表现，非 run_eval 判定问题。

异常 C：唯一被执行 task vs failed task trace 对比

trace 在 ~/eda_code_eval/<batch>/cli_data/worker_*/data/sessions/*/*.messages.json。run2 batch 抽样：

task有代码?messages最后 assistant 摘录画像

另有约 52 题（run2）把代码写到 code/<task>/pyAether_code/（抽取器正确目标路径）→ trace 里确实写了文件、但被共享 temp race 在拼装阶段丢掉。「failed task」分两群：① 真没写代码（submit_and_exit/循环，约 106 题）；② 写了代码但被管线 temp race 丢（约 52 题）。后者是坍塌数字主因。

异常 D：codegen_rejection_stats.json 为 0 字节

该文件不是 codegen 阶段产出，是此前 RCA 手动统计的拒绝画像（run1 的 1509B 是手算的 1304 次拒绝）。eda_fastmcp 管线本身不产此文件 → run2 缺失 / run3·4 为 0B 属预期，不代表「codegen 没产码」。真实产码见 §3（code/ 实测 52/55 题）。

5. 根因定论：管线 vs 模型

层级性质证据影响
主因 共享 temp race管线format_cline_cli_output.py L95/L156-157 共享相对 temp ./pyAether-eval/temp/pyAether_code + L157 shutil.rmtree；36.15 并发 eval 互相踩空；run2=52.py→1行、run3=55.py→1行、run4=43.py→0字节generation_success 被压成 1；execution_results 被压成 1
次因 链脚本陈旧拷贝管线ls -dt|head -1；run4 无 fresh eval → 拷 run3 的 1834；final_report/execution_results sha256 字节相同run4 INVALID；completed/execution 串文件
次因 模型零代码模型~106/158 题无 .py；trace 见 submit_and_exit 风暴 / 903 msg 循环真实生成率 33–35%（非 0.6%，但也非健康）

结论：排除管线 bug 之前，不得将 run2/3/4 写成「模型 degenerate collapse」。坍塌数字（1/158）由管线共享 temp race 主导；模型真实生成率约 1/3，代码质量通过率需回补后重测定论（8 题验证 1/8=12.5% 通过）。

8. 结论与后续

  • 根因：管线共享 temp race（主）+ 链脚本陈旧拷贝 bug（次）。run4 = run3 陈旧拷贝，作废。
  • 模型：真实生成率约 33–35%，存在 submit_and_exit 风暴/长循环退化（约 2/3 题零代码），属真实但非「1/158 坍塌」级别，需修复管线后重测才能定通过率。
  • 5-run mean 在 RCA 结论前不得引用；run2/3/4 的 0.0% 是管线 bug 压制结果，不可作为模型能力结论。
  • 后续：① 经 zhulong 协调应用 6.1 共享 temp 按 batch 隔离（或沿用 6.3 wrapper 回补）；② 用 6.2 已修链脚本重跑 5-run；③ 重测后再与 run1(18.99%) 同表对比；④ 模型侧 submit_and_exit 退化缓解（强制写文件/工具校验/重试）另列。
