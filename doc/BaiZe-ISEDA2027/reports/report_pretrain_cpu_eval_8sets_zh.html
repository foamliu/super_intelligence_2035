/v1/completions logprobs 格式问题（2026-11-04 新发现）

llama-server 的 /v1/completions 端点返回新版 OpenAI 格式：logprobs.content[] 数组（每元素含 token/logprob/bytes），不包含 lm_eval local-completions 后端所期待的 token_logprobs 字段 → 直接对接报 KeyError: 'token_logprobs'。三选一解法：① --model gguf（lm_eval 内置 GGUF 后端，自解析新格式）；② 检查 llama-server 参数输出旧格式；③ 兜底写 shim 转换。但由于模型本身输出不正确（见下），格式问题暂为次要矛盾。

生成质量测试（2026-11-04 新发现）

结论：llama.cpp 路线 FAIL（保留 HF float32 路线）

  • 速度达标：f16 llh 打分 7.03× 加速；llama-bench 生成 21.3 tok/s、prompt 82 tok/s（8 线程），比 HF float32 ~3 tok/s 快约 7×。
  • 精度不达标：SciQ -18pp / PIQA -16pp，Avg Δacc = -17pp。f16 / f32 / newbin 三次结果完全一致 → 不是量化误差（精度无关的系统性偏差）。
  • 根因更正（2026-11-04 深度调查）：此前推断"Duplicated key 覆写元数据"不成立——GGUF 元数据经原始二进制解析验证完全正确：block_count=56、feed_forward_length 数组（28 MLP 层=8192、24 SSM 层=0、4 attn 层=0）、head_count_kv 数组（4 attn 层=4、其余=0）均正确。层分类逻辑（C++ is_recr = (n_head_kv==0 && n_ff==0)）正确。SSM/MLP/attn 权重值与 HF safetensors逐一比对一致（bf16→f16 精度仅）。
  • 真根因：llama.cpp C++ build_mamba2_layer（基类 llm_build_mamba_base）的 Mamba2 SSM 数值实现与 PyTorch transformers reference 存在系统性计算差异 → 56 层混合架构误差累积 → logit 偏移 → 准确率下降 + 生成垃圾。具体差异点（conv1d 维度 6144=d_inner+2*n_group*d_state、ssm_norm group 结构 8×512 等）需逐算子排查，非本轮可完成。
  • 处置：CPU 评测保留 HF transformers float32 路径（数值可信），llama.cpp 提速路线搁置，待 llama.cpp 上游修复 Nemotron-H Mamba2 SSM 计算后再试。
