四、codex 异常归因（59/87 exception）

codex 主跑 20/87 resolve，59 条异常。逐条归因：

子类异常类型数量归因
429_rate_limitRuntimeError34上游 API 429 限流（codex 独有，其余 6 路无 429）→ 适配器无退避重试（codex.py:171-187 单次 exec，return_code!=0 即 raise），放大为 RuntimeError。接入层缺陷，非模型能力
timeout_900sAgentTimeoutError15单题 900s 超时（build/compile 类重任务）
exit1_no_stdoutRuntimeError8codex CLI exit 1 无 stdout（疑似上游返回异常体）
cli_arg_parse—1CLI 参数解析失败
signal_exit_137—1SIGKILL（OOM 或资源争用）

结论：59 = 34（429）+ 15（超时）+ 8（exit1）+ 2（其他）。429 为 codex 独有（其余 6 路 exception_stats 无 429；grep -rl 429 jobs_codex/ 命中 50 文件，其他 0）。根因 = 上游 429 + 适配器无退避放大。非模型能力。修复方案：codex.py 加指数退避重试（2/4/8/16s，上限 4 次），待资源窗口复测。

六、与公开基线对照（差距归因）

运维 web search 基线：骨干 kimi-k2.6 在 Terminal-Bench 2.0 公开分数 ≈ 57.3%–66.7%（benchleader / evals.report / benchmarklist）。本报告最高 cline 43/89=48.3% → 低 9.0–18.4 个百分点。

差距来源说明影响
评测口径/包装公开多用模型厂商自带 harness；本报告统一 7 个第三方 harness 接入同一骨干，接入层翻译（gw_proxy responses→chat、dummy key）引入损耗，非「裸模型」分数主要
超时 1800s/题cline 主跑 AgentTimeoutError 19 条（占其错误主体），build/compile 重任务难完成较大
接入层 bug（3 路）hermes/claude-code/deepseek 主跑 0% 全因适配器缺陷；修复后 hermes 28.1%、claude-code 22.5% 仍偏低较大
codex 429 限流34 题无退避重试判异常，修复后保守 +10–15 题中
2 题缺镜像mteb-leaderboard/mteb-retrieve 缺 Docker 镜像，拉低 /89 分母小

结论：本报告测的是「7 个 harness × 接入层」端到端能力，不是裸 kimi-k2.6 模型分数。9–18 点差距主要由接入层损耗 + 超时 + 适配器 bug 构成。可提升点：补镜像、加退避重试、放宽超时、修 deepseek install。
