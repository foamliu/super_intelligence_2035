4. seq=32K CP=2：bug 阻断 → 修复 → 验证

4.1 阻断现象

seq=32768 / CP=1 / mbs=1 ⇒ OOM（峰值顶 81 GB，cfg5/cfg6 已证）。必须 CP=2（每卡 seq/2=16384，峰值回落 ~77 GB）。

但 CP=2 + FA3 一启动即崩：RuntimeError: Unknown keyword argument 'window_size' for operator 'flash_attn_3::_flash_attn_forward'。FA3 的原生 custom op（_flash_attn_forward/_flash_attn_backward）的参数 schema 与 FA2 不同，而 TE 的 CP 代码在 FA3 路径里仍按 FA2 的 API 传参。

4.2 根因：FA3 原生 op 与 FA2 的两组 API 差异

FA3 原生 op（flash_attn_3.flash_attn_interface._flash_attn_forward/_backward，非 Python 封装层）的 schema：

_flash_attn_forward(... float? softmax_scale=None, bool causal=False, SymInt window_size_left=-1, SymInt window_size_right=-1, ...)
_flash_attn_backward(... float? softmax_scale=None, bool is_causal=False, SymInt window_size_left=-1, SymInt window_size_right=-1, ...)
差异FA2（旧）FA3（原生 op）TE CP 代码的错误用法
窗口大小window_size=(-1,0) 元组window_size_left/window_size_right 标量FA3 路径仍塞 window_size 元组 → Unknown keyword
因果掩码（反向）causalis_causal（仅反向）反向调用仍传 causal= → Unknown keyword

注：FA3 前向用 causal（与 FA2 同名，故前向不崩）；仅反向改名 is_causal。前向先跑通、反向才崩，故第一轮报错是 window_size（前向），修完后第二轮报错是 causal（反向）——两 bug 串行暴露。

4.3 修复（11 处代码点，均在 context_parallel.py）

#行号(修后)位置修复
1929前向 diagonal/upperwindow_size元组 → window_size_left/right标量
21181反向 diagonal同上

41487前向 FA3 setup（崩溃主因）"window_size"=(-1,0) → 标量 left/right

93714反向 FA3 setupctx.window_size → 标量 left/right
101225反向调用 #1causal= → **({"is_causal":..} if fa3 else {"causal":..})

修复原则：FA3 路径（if use_flash_attn_3: 或 OR 进标量分支）一律用标量 window_size_left/right + is_causal；FA2 路径（elif fa_utils.v2_3_plus:）保留元组 window_size + causal，不影响旧后端。分支从「fa3 or (v2_3_plus and not v2_7_0_plus) → 元组」重排为「fa3 or v2_7_0_plus → 标量；elif v2_3_plus → 元组」，把 FA3 从元组分支移到标量分支。

4.4 验证结果（32K CP=2 首次跑通）

配置：seq=32768 / mbs=1 / gbs=8 / DP=4 / CP=2 / accum=2 / tok/mb/卡=16384，单机 .29，关 graph，FP8，40 iter。

结果：rc=0（无崩溃），中位步时 1429.4 ms，tok/s=183,394（8 卡），每卡 22,924，峰值 77,619 MiB（<81 GB ✓），loss 10.96→8.33→7.89→7.77 单调下降，gnorm 1.51→0.56，0 NaN 全程，837.9 TFLOP/s/GPU。

修复确认：前向（window_size 标量）+ 反向（is_causal）均通过；峰值从崩溃点 73 GB 继续升到 77.6 GB 完成完整 forward+backward+optimizer，loss 下降证明数值正确（非空跑）。

32K 吞吐分析：每微批 1429.4/2=715 ms，比 16K CP=1 的 436.7 ms 慢 64%。差额（~278 ms/微批）= CP=2 P2P 环形 KV 交换开销（每步在 2 个 CP rank 间传 K/V 分片）。这是 2× 上下文长度的固有代价（CP 用通信换显存），非 bug。

16 卡外推（32K）：DP=8 / gbs=16 / accum=2 / tok/step=524,288。每微批 ~715 ms + 跨节点 AllReduce ⇒ 步时 ~1630 ms ⇒ tok/s ≈ 322,000（每卡 ~20,100）。32K 因 CP 开销，16 卡 ~320–360K，低于 600K——这是 seq 翻倍 + CP 通信的物理上限，要进一步提升需 graph ON（CP 路径 graph 兼容性待验）或更大 accum 摊薄 AR。

✅ 已由 §5.3 双机 16 卡实测确认：实际 351,526 tok/s（accum=16 优于外推时假设的 accum=2，略超 320–360K 外推上界），32K 结构性低于 600K 的判断成立。

5.2 seq=16K CP=2 DP8（对照：CP 在 16K 的代价）

6. 结论与后续
