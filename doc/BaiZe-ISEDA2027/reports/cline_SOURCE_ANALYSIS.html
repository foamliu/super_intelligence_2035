线 1 · 上下文注入与预处理管线（Auto Compact 的上游）

① 任务书假设（旧形态）

任务书认为存在一个 ContextPipelinePrepareTurn 节点，在请求链路里做「拦截与改写」；并假设 Cline 用一张 Persistent Map（Map<messageIndex, [EditType, Map<blockIndex, ContextUpdate[]>]>）记录对消息的编辑， 「原始消息从不被修改，所有编辑在读取时应用」—— 即 无损投影。

② 当前真实实现（新形态）

名字变了，但「无损投影」内核完整保留。先看调用点和类型：

调用点：preannounce 每个模型请求前

在 agent-runtime.ts 里，一次请求的组装顺序是：构建 request → 注入 pending 消息 → prepareTurn → beforeModel hook → 发请求。

// agent-runtime.ts:965-977 —— 用 cloneMessages 从 state.messages 构建请求（原始消息只读）
let request: AgentModelRequest = {
    systemPrompt: this.config.systemPrompt,
    messages: cloneMessages(this.state.messages),     // <-- 投影自此开始
    tools: [...],
    ...
};
// agent-runtime.ts:996 —— Auto Compact 的落点（在 beforeModel hook 之前）
request = await this.prepareTurnForModelRequest(request, options);

prepareTurn 的语义在 shared/agent.ts:478-484 写得非常清楚 —— 这就是「无损投影」的当代定义：

// shared/agent.ts:478-484
/**
 * Optional host-owned request projection hook invoked before each model call.
 *
 * Returned messages affect only the provider request for the current call.
 * They do not replace the canonical runtime transcript, are not persisted as
 * session history, and are not reflected in AgentRunResult.messages.
 */
prepareTurn?: (context) => Promise<...> | ... | undefined;
关键判断：这句注释精确复述了旧架构「原始消息从不被修改、所有编辑在读取时应用」的内核 —— 压缩得到的摘要只出现在本次 provider 请求里，runtime 里的 canonical transcript 原样不动，也不落库。 这正是「投影出来的视图」而非「改写后的存储」。

投影的物理实现：MessageBuilder「不修改原对话的 API-safe 副本」

// message-builder.ts:1-10（文件头，直接声明了它在压缩与旧内容改写中的角色）
/**
 * API-safe message builder for provider payloads.
 * Walks the conversation to produce provider-ready messages, handling
 * tool-result truncation and outdated-file-content rewrite for compaction.
 * Per-instance caches make this host state.
 */
// message-builder.ts:105-107
/**
 * Builds an API-safe message copy without mutating original conversation history.
 */
export class MessageBuilder { ... }

旧架构里的三类「读取时改写」—— 剥离过期文件内容、截断超长工具结果、重复 tool-call 标记去重 —— 在新架构里由 MessageBuilder 以显式常量承接（message-builder.ts:28-49）：

export const DEFAULT_MAX_TOOL_RESULT_CHARS = 8_000;
export const DEFAULT_MAX_FILE_CONTENT_CHARS = 50_000;
export const DEFAULT_MAX_TOTAL_TEXT_BYTES = 6_000_000;   // 聚合预算，仅在溢出时兜底
export const DEFAULT_MIN_OUTDATED_REWRITE_BYTES = 65_536; // 批量省写，避免每次打断 provider 前缀缓存
const OUTDATED_FILE_CONTENT = "[outdated - see the latest file content]";
为什么这个「批量省写」阈值（65_536 字节）重要？ 见 message-builder.ts:31-39 注释：provider 的前缀缓存 （prefix cache）会被「转录中段改写」整个打断 —— 因为它只缓存前缀，一旦中间某条被改写，后面全部失效。 所以过期内容改写被设计成攒够 64KB 才一次性提交（"Batch stale-read rewrites to avoid breaking provider prefix caches on every re-read"）， 把「无损投影」的 CPU 代价和 provider 侧缓存失效代价都压到最低。这是旧架构 EditType/ContextUpdate 里没有显式化出来的成本项。

代价与边界：把「改写」放到读取期意味着每次请求都要在内存里重投影一份消息数组（cloneMessages 是 JSON.parse(JSON.stringify)）， 对极长会话有序列化成本；但换来「回滚零成本」（见线 2）和「任意 hook/插件可观察同一份原始态」。投影层的缓存 （message-builder.ts:129-131 "Sticky rewrite decisions ... revalidated/pruned per build"）是专门用来抵消这个代价的。

线 2 · 检查点与状态恢复（Auto Compact 的回滚路径）

① 任务书假设（旧形态）

任务书假设检查点的核心是「非破坏性编辑 + 时间戳截断」：Map<messageIndex,[EditType,Map<blockIndex,ContextUpdate[]>]> 被持久化为 JSON， 每个更新带时间戳，恢复时「截断指定时间之后的更新」；并假设「压缩产生的摘要本质也是一组 ContextUpdate，所以能精确回退到摘要生成前」。 还点名 PR #12747 修过 "compaction sidecar" 的可靠性。

② 当前真实实现（新形态）—— 两条独立、但共享同一内核的回滚通道

当前架构把「检查点」拆成了两类异构状态，分别有独立的回滚机制：

(a) 文件系统检查点：git stash / ref，而非 JSON 编辑图

// checkpoint-hooks.ts:10 —— 检查点是 git stash，靠固定消息前缀标识
const CHECKPOINT_STASH_MESSAGE_PREFIX = "cline checkpoint session=";
// checkpoint-hooks.ts:16-21 —— 检查点条目是 git ref 而非消息编辑
export interface CheckpointEntry {
    ref: string;            // git ref / stash sha
    createdAt: number;
    runCount: number;
    kind?: "stash" | "commit";
}

对比工作区差异用 git diff 与 git ls-files --others（checkpoint-diff.ts:76-90）， 读取历史文件内容用 git show <ref>:<path>（checkpoint-diff.ts:53-63）。

内核是否保留？「回滚到某个时间点」这个语义被外包给了 git 的不可变对象存储：git 的 blob/tree/commit 本身就是 从不原地改写的历史，天然支持「精确回到某次 run 之前」。旧架构自己造的「时间戳截断」JSON 图，在这个新架构里 被更成熟的 VCS 原语取代了。代价是只能回滚文件系统状态，回滚不了对话记忆—— 后者交给下面的 sidecar。

(b) 压缩状态回滚：Compaction Sidecar（PR #12747 的主角）

压缩概要对「对话」的回滚，靠的是 SessionCompactionState（sidecar）。它的 schema 关键字段不是「编辑列表」，而是 边界定位器 + 已压缩消息副本 + 系统提示词副本：

// session-compaction.ts:25-34 —— sidecar 的 schema（version + 边界哈希 + 消息 + system_prompt）
export const SessionCompactionStateSchema = z.object({
    version: z.literal(1),
    updated_at: z.string().datetime(),
    conversation_id: z.string().min(1).optional(),
    source_message_count: z.number().int().nonnegative(),   // 压缩覆盖了多少条源消息
    source_prefix_hash: z.string().min(1).optional(),       // 源消息前缀哈希（边界定位）
    source_last_message_key: z.string().min(1).optional(),  // 旧格式边界键（向后兼容）
    messages: z.array(MessageWithMetadataSchema),           // 压缩后的消息副本
    system_prompt: z.string().optional(),                   // 系统提示词单独存放（见线4）
});

「精确回退到摘要生成前」在新架构里如何实现 —— 关键看投影函数：

// session-compaction.ts:161-190 —— 重新投影 = 压缩消息副本 + 压缩点之后的尾部
export function projectSessionCompactionState(state, sourceMessages): ... {
    const hasEnoughSourceMessages = state.source_message_count <= sourceMessages.length;
    // 用哈希/边界键验证：源消息前缀自压缩以来没有被篡改，否则放弃投影
    const canProjectState = hasMatchingSourcePrefix || hasMatchingLegacyBoundary;
    if (!canProjectState) return undefined;   // 失效 sidecar 不强行拼接
    return [
        ...cloneMessages(state.messages),                          // 摘要（压缩结果）
        ...cloneMessages(sourceMessages.slice(state.source_message_count)), // 压缩点之后的新消息
    ];
}
这直接回答了任务书线 2 的核心问题：摘要本质上是不是「一组 ContextUpdate、所以能精确回退」？ —— 在当前代码里，根本不是靠「编辑图」实现的，而是靠 「非破坏性 + 边界哈希指针」： 压缩从不删改源消息（canonical 一直完整保存），sidecar 只存「压缩到第 source_message_count 条」这个指针， 加上压缩结果副本和源前缀哈希。要「回滚」就是丢弃 sidecar，下轮投影时源消息自动原样出现 —— 因为本来就没被毁掉。哈希（source_prefix_hash）的作用是防串扰：如果会话在压缩后又被并发追加/恢复改过前缀，sidecar 就不再套用， 避免「旧摘要 + 新前缀」拼出错误上下文。这正是 PR #12747 要修的可靠性问题。

(c) 持久化可靠性：写队列 + 陈旧写守卫（PR #12747 的修复点）

git log 确认 PR #12747 真实存在且标题正是「make compaction sidecar persistence reliable」：

$ git log --oneline --all --grep='12747'
6cb43f030 fix(core): make compaction sidecar persistence reliable (#12747)

落库点在 local-runtime-host.ts。注意 createCompactionStateAwarePrepareTurn 的注入形态 —— 它就是把 「压缩」和「sidecar 读写」缝在一起的那个函数，即使 auto-compact 被关掉（compact=undefined），它仍会投影已有 sidecar：

// local-runtime-host.ts:606-624 —— 组装 prepareTurn（compact + get/saveState 三件套）
const compact = createContextCompactionPrepareTurn(configWithProvider);
const prepareTurn = createCompactionStateAwarePrepareTurn({
    compact,
    getState: () => activeSessionRef?.compactionState,
    saveState: async (state, sourceMessages) => { ... persistActiveSessionCompactionState(...) },
});

两个关键保护，都是「陈旧写不覆盖新写」，对应 PR #12747 暴露的 bug：

// local-runtime-host.ts:1313-1343 —— 写队列串行化 + 陈旧守卫
return await this.enqueueCompactionStateWrite(session, async () => {
    const currentState = session.compactionState;
    // 可投影的 sidecar 按计数判陈旧；失效（不可投影）的退化为时间戳对比，不永久阻塞替换
    if (currentState && (currentStateStillProjects
            ? isIncomingCompactionStateStale(state, currentState)
            : Date.parse(state.updated_at) < Date.parse(currentState.updated_at))) {
        return { updated: false };
    }
    await this.invoke("persistSessionCompactionState", session.sessionId, state);
    session.compactionState = state;
});
// local-runtime-host.ts:1345-1360 —— 写队列：previous.catch(()=>undefined).then(action)
PR #12747 暴露了什么设计缺陷？ 写队列 (compactionStateWriteQueue) 串行化是为了防并发写乱序； 双重守卫（可投影时按 source_message_count 计数判陈旧，不可投影时按 updated_at 时间戳判陈旧） 是为了防「一个旧写回马枪覆盖新写」。注释（1313-1326 行）本身就描述了 bug：sidecar 若因「会话恢复时消息身份 churn、或哈希格式变更」变得不可投影， 不能让它永久阻塞新 sidecar 的落库 —— 否则重启后阈值永不更新，导致「重复压缩」或「该压缩却不压缩」。 这正是任务书说的「压缩状态没持久化好 → 重启丢失 → 重复压缩/阈值错乱」。

③ 数据流图（线 2）

压缩发生（prepareTurn 内 createCompactionStateAwarePrepareTurn）
        │ 计算 source_prefix_hash + source_message_count
        ▼
sidecar（SessionCompactionState）→ saveState → 写队列 → 持久化（invoke persistSessionCompactionState）
        ▲                                          │（陈旧写守卫）
        │ getState                                    └─ 会话文件
        ▼
下一轮准备："[摘要] + [源消息 source_message_count 之后的新增]"
        │ projectSessionCompactionState（先验证前缀哈希再拼接）
        ▼

代价与边界：文件检查点依赖本地 git（副作用是 workspace 必须可 git init，且 checkpoint 是整仓库粒度、无法只回滚「对话」）； sidecar 的哈希校验意味着「任何对源消息前缀的并发修改都会让 sidecar 失效」—— 换来的是绝不产生错误的拼接上下文， 这是「宁可不压缩、也不压缩错」的取舍。

① 任务书假设

③ ⭐ 核心问题：Auto Compact 能不能用插件实现？

答案：不能，至少在「拦截 prepareTurn 这个底层节点」的意义上不能。 证据是类型体系的「刻意分层」：

// 证据 2：插件只能拿到 AgentExtensionHooks = Partial<AgentRuntimeHooks>
// contribution-registry.ts:141 —— 而 AgentRuntimeHooks 里没有 prepareTurn

换句话说：Auto Compact 被实现为 prepareTurn，而 prepareTurn 是 AgentRuntimeConfig 的 host 级字段， 不在 AgentRuntimeHooks 里，所以走 AgentExtensionHooks 的插件根本触碰不到它。它被硬编码在 core 的 createContextCompactionPrepareTurn（compaction.ts:256）+ createCompactionStateAwarePrepareTurn（local-runtime-host.ts:621）里。

但插件并非完全不能做「压缩类」的事 —— 有两条旁路，代价是不能复用 Auto Compact 的预算/telemetry：
  1. registerMessageBuilder()（messageBuilders capability，contribution-registry.ts:128）：可在消息进入 provider 前做任意变换。
  2. beforeModel hook（agent-runtime.ts:999-1018）：可改写 messages / tools / options。
两者都在 prepareTurn 之后执行，能「再加工」请求，但官方注释明确它们绕过了这个 wrapper 的 telemetry 覆盖： 
// compaction.ts:251-254 —— 官方承认的 telemetry 盲区（旁路压缩不上报）
 * Known gap: compactions performed via plugin `registerMessageBuilder()` or
 * via the `beforeModel` runtime hook bypass this wrapper entirely, so they
 * do not emit compaction telemetry. If we want coverage there too, the
 * plugin/hook pipelines must be instrumented separately.

代价与边界：把 Auto Compact 锁死在 core 换来的是「预算、触发阈值、溢出恢复、sidecar 持久化」这四件事的一致性 —— 它们必须被保证在任何 provider 请求前都以同一套规则执行、并以同一套 telemetry 上报；若开放成插件，就会出现「两个压缩器打架 / telemetry 盲区」的问题（上面的 Known gap 就是活例子）。这是「核心机制收敛、外围变换开放」的典型取舍。

线 4 · 焦点链与任务状态跨压缩存活

① 任务书假设

任务书引用 Auto Compact 文档的说法：「待办事项列表在摘要之间持续存在」。核心论点：压缩的是「对话说了什么」， 而「接下来要做什么」通过 Focus Chain 的 todo list 单独维护 —— 这是「短期记忆（对话）与长期目标（任务列表）解耦」的体现， 解释了「为什么压缩后能精确地从停止的地方继续」。

事实 A：Focus Chain 在「当前」SDK 化的 vscode 里已被移除（stub）。 这直接修正任务书「Focus Chain 与 Auto Compact 协同」的表述前提。

线 5 · 模型能力适配与降级策略

① 任务书假设

任务书认为 Auto Compact 有「条件启用」：只对 Claude 4 / GPT-5 / Gemini 2.5 / Grok 4 生效，其他模型回退规则截断；这套逻辑在 context-window-utils.ts；并引用 Issue #7772（llama-server 上下文窗无法自动检测、默认按 128K、131K 模型阈值算错）。 底层还有「保守 3 字符/token」的估算比例。

② 当前真实实现 —— 三层结论

(a) 「条件启用（按模型家族门控）」在当前代码里不存在 —— 已被「策略枚举」取代

全库搜不到任何把压缩能力绑定到 Claude/GPT/Gemini/Grok 模型家族的判断；策略选择是配置项，默认 agentic：

// compaction.ts:285-287 —— 策略来自 config，默认 agentic，不按模型家族 gate
const strategy = userCompaction?.strategy ?? "agentic";
const runBuiltinStrategy = BUILTIN_COMPACTION_STRATEGIES[strategy];
const mode = options.mode ?? "auto";

真正的「降级」不是按模型家族，而是按运行时失败：agentic（需一次 LLM 摘要调用）失败或产出不合格时，运行时回退 basic（确定性规则截断，不调 LLM）：

// compaction.ts:502-521 —— agentic 抛错时回退 basic（除非是用户主动取消）
try {
    result = await runBuiltinStrategy(builtinOptions);
} catch (error) {
    if (strategy !== "agentic" || isCompactionCancellation(error, ...)) throw error;
    // "Agentic compaction failed; falling back to basic compaction"
    executedStrategy = "basic";
    result = await BUILTIN_COMPACTION_STRATEGIES.basic(builtinOptions);
}
// compaction.ts:472-498 —— 溢出恢复场景下，agentic/custom 摘要若「不够小/为空」也回退 basic
const acceptable = result.messages.length > 0
    && customMessageTokens < messageInputTokens
    && customMessageTokens <= messageTargetTokens;

(b) 模型上下文窗适配：旧的硬编码 switch 已删，换成「目录声明 + 比率」

context-window-utils.ts 确已在历史中被删除（commit 1f31738b3 "delete unused files"），其旧形态正是任务书描述的「各模型特殊对待」：

新架构（compaction-shared.ts:13-19 / 51-70）不再「按窗口大小查表减量」，而是尊重模型目录（models.dev）上报的能力：

// compaction-shared.ts:13-19 —— 预算常量
export const DEFAULT_MAX_INPUT_TOKENS = 128_000;
export const CONTEXT_WINDOW_INPUT_RATIO = 0.9;   // 只报 contextWindow 时取 90% 作可用输入
export const COMPACTION_TRIGGER_RATIO = 0.9;     // 占满 90% 预算就触发压缩
export const DEFAULT_TARGET_RATIO = 0.7;         // 压缩后目标：降到 70%
export const DEFAULT_PRESERVE_RECENT_TOKENS = 20_000; // 最近 20K token 不压缩

// compaction-shared.ts:51-70 —— 权威值优先，其次 window * 0.9
export function resolveEffectiveMaxInputTokens(input) {
    if (maxInputTokens !== undefined) {   // 目录报了 maxInputTokens
        return contextWindow === undefined ? maxInputTokens
             : Math.min(maxInputTokens, contextWindow);  // 但不得超过 window
    }
    return contextWindow === undefined ? undefined
         : contextWindow * CONTEXT_WINDOW_INPUT_RATIO;   // 只报窗口 → 乘 0.9
}

(c) token 估算：3 字符/token（保守），且全局一致

// tokens.ts:8-11 —— 保守字符/token 估算
export const CHARS_PER_TOKEN = 3;
export function estimateTokens(chars) { return Math.max(1, Math.ceil(chars / CHARS_PER_TOKEN)); }

注意 compaction-shared.ts:8 把 CHARS_PER_TOKEN/estimateTokens 再导出，保证「压缩预算、触发阈值、溢出判定」三处用同一个估算器（避免单位不一致导致阈值错乱 —— 这正是 Issue #7772 类 bug 的根因）。

③ Issue #7772 的核实与「128K 兜底」的代价

任务书引用的 Issue #7772 在仓库历史里未直接搜到编号 7772，但它的症状与修复链完全可复现：

$ git log --oneline --all --grep='128k' | head
83f9991c9 Fix LM Studio context window stuck at 128k (#13457)
e47e90cc6 fix(lmstudio): resolve real context window from LM Studio's REST API

根因密钥是同一类：本地推理服务（llama-server / LM Studio / ollama）不在 models.dev 目录、又不主动上报 maxInputTokens， 于是走 resolveEffectiveMaxInputTokens → undefined → DEFAULT_MAX_INPUT_TOKENS = 128_000 兜底；若真实窗口是 131K， 把 128K 当上限看似「偏小」，但若模型目录把窗口报了 131072、而 90% 触发阈值又乘错单位，就会在「还没到真上限」时提前触发压缩（或反之溢出）。 修复方向一致：让 provider 主动上报真实窗口（LM Studio 从 REST API 解析），而不是依赖默认值。

总结 · 设计取舍与扩展边界

五个「内核保留、形态迁移」的判断

主线内核（不变）形态迁移（变）
线1 无损投影原始消息永不改写，编辑在读取期应用EditType/ContextUpdate → prepareTurn 投影 + MessageBuilder API-safe 副本
线2 检查点回滚非破坏式，回滚零成本时间戳截断 JSON 图 → git stash/ref（文件）+ 边界哈希 sidecar（对话）
线3 扩展性核心调控收敛、外围变换开放prepareTurn 锁死在 core（非 hook）；插件走 7 个 hook + capability
线4 长期目标解耦长期目标不随对话压缩Focus Chain md 文件（已移除）→ sidecar 单独存 system_prompt
线5 模型适配宁早压缩、不溢出switch 查表减量 → 目录 + 比率 + 溢出恢复硬回退

最值得记住的三条「设计取舍」

  • 投影而非改写（线1+线2 的共同根）：把「改写」推迟到读取期，一次性换来「可回滚、可观察、可并发」三种能力；代价是每次请求的内存重投影 + provider 前缀缓存失效风险（用 64KB 批量省写对冲）。
  • 核心机制锁死、外围能力开放（线3）：Auto Compact 的预算/触发/溢出/持久化必须全局一致，所以不放进 hook；插件只能做「压缩后」的再加工（beforeModel / messageBuilder），且官方明示这会绕过压缩 telemetry。
  • 安全优先的预算哲学（线5）：3 字符/token 高估 + 90% 触发 + 溢出回退重试，是「宁可更早压缩、也不冒溢出风险」的一整套保守设计；代价是本地无目录模型掉进 128K 兜底（Issue #7772 类）。
