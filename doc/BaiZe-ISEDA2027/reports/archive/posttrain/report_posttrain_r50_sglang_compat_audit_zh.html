结论: ✅ GO — 30/30 检查通过，Phase 1 可直接启动；Phase 2 修复 BUG-W1 后可用

1. 背景与触发

R47 发现 verl 0.4.0 与 SGLang 集成的 5 个 CRITICAL bug，创建了 v2 config 和 monkey-patch wrapper（baize_posttrain_verl_wrapper.py）。但 wrapper 中的 monkey-patch 代码从未被验证。11/9 GPU 到位后若 SGLang 无法正确服务 MiniCPM5-2B 或工具调用解析失败，整个 RL 管线阻塞。本轮对 SGLang 源码、MiniCPM5-2B 模型文件、tokenizer 词汇表进行源码级审计。

2. 模型架构 ✅

MiniCPM5-2B config.json: architectures: ["LlamaForCausalLM"], model_type: "llama"。
SGLang 有原生 llama.py 模型实现 → 无需 minicpm5.py，模型可直接作为 Llama 加载。模型参数：42 层、hidden_size=2048、vocab_size=130560、bfloat16。

3. Chat 模板 ✅

模型自带 chat_template.jinja（ChatML 格式 + thinking 标记 + XML 工具调用格式）。SGLang 从模型目录加载 chat_template，无需注册 minicpm5 conversation template。SGLang conversation.py 仅有 minicpmv/minicpmo，但 MiniCPM5 使用 Llama 架构 + 自带模板，不依赖 conversation.py。

5. BUG-W1（CRITICAL · 已修复）

问题: SGLang ToolCallItem（Pydantic BaseModel）字段是 parameters（function_call_parser.py line 32），但 wrapper line 72 使用 arguments=json.dumps(params)，导致 Pydantic ValidationError。

修复: arguments= 改为 parameters=（已修改 baize_posttrain_verl_wrapper.py line 75）。影响: 仅 Phase 2（多轮工具调用）。Phase 1 不受影响。

6. 抽象方法合规性 ✅

BaseFormatDetector 要求 3 个抽象方法: detect_and_parse, has_tool_call, structure_info。wrapper 全部实现。structure_info 返回 lambda name: StructureInfo(...)，与 Qwen25Detector 等内置实现模式一致。

7. ToolCallParserEnum 注册 ✅

FunctionCallParser.ToolCallParserEnum 是类级 dict。wrapper 注册 minicpm5 合法。验证后 enum_keys = ['llama3', 'qwen25', 'mistral', 'deepseekv3', 'minicpm5']。

8. Phase 1 安全性 ✅

v2 config multi_turn.enable=False → get_tool_call_parser_type() 不被调用 → Phase 1 R0 skeleton（单轮、无工具）完全不受 monkey-patch 影响，可安全启动。

9. Phase 2 注意事项

  • BUG-W4（低风险）: parse_streaming_increment 未覆盖，基类用 JSON 解析。verl 批量生成用 detect_and_parse（非流式），影响低。
  • Ray 分布式: monkey-patch 在驱动进程执行，需确保 Ray worker 进程也应用补丁。
