3.1 Xmodel-2.5 Decay「训坏 → 修复」全历程

设置

在 Xmodel-2.5 stable 末 ckpt（step_532000，~1.41T tokens 预训练后，CS8 起点 baseline = 61.03%）上做 WSD decay，目标超越官方 final（CS8=65.40% / CX6=32.90%）。数据配比 SFT 64% : Ultra-FineWeb-L3 24% : code 8% : math 4%。

过程

  1. decay v2（自写脚本 baize_xmodel25_decay_v2.py，训坏）：71.2B tokens，peak LR 1.67e-3，AdamW，无 μP。step0 loss=11.7244（≈随机）→ 训完 final CS8=44.97% / CX6=6.21%，远低于起点 61.03%（−16.06pp）与官方 65.40%（−20.43pp）。v2 eval：eval_decay_v2_final/eval_summary.txt（CS Avg=0.4497 / CX Avg=0.0621）
  2. 归因（4 因子叠加）：① 双移位 bug（baize_xmodel25_decay_v2.py:547-548 预移位 input_ids=full[:,:-1]/labels=full[:,1:] + :567-568 chunked CE 再移位，train 2-step / eval 1-step，全 14 集受影响）；② 缺 μP（自写脚本未用 use-mup，官方用 Muon + μP +4.58pp）；③ peak LR 1.67e-3 过高；④ code 26 epochs 过采样。归因见 daily-memories/2026-10-23.md:263 + 2026-10-20.md:881-891
  3. L1 排查（修双移位 + LR 5e-4 + 20B）：step0 loss=1.7510（vs v2 11.72，降 6.7× ⇒ 双移位修复确效）→ CS8=59.03%（≥55% 门槛，方向正确）。L1 eval：eval_L1_20b_cs8/eval_summary.txt@23:55
  4. decay-5000（官方 train_decay_fp8_1113.sh 落地，修复）：use-mup + Muon 0.2 + FP8 TE hybrid + 无 warmup + MBS=5 / seq=3776 / GBS=960 / lr=1.66667e-3 / WSD exponential / DP8+distributed-optimizer / tokenizer deepseekv3 / vocab=129280，train-iters 550000→5560（18.1B）→ CS8=58.97% / CX6=28.02%。ckpt out/decay_5000_fp8_mbs5/iter_0005000；eval nemo_experiments/eval_decay_5000_final/ + p8_eval_summary.json（0.5897/0.2802）；log /tmp/baize_decay_5000_mbs5.log

3.2 长上下文 Seq 扩展吞吐排查（tok/microbatch 悬崖根因）

设置

双机 16 卡（DP16）基线 = 606,449 tok/s（seq4096 / mbs3，tok/mb/GPU=12,288，扩展效率 99.4%）。扩 seq 到 8192/16384/32768 时吞吐骤降至 ~112K（5.4× 悬崖，峰值显存 81.08GB 顶到 HBM 上限）。运维令 23:0x 通宵攻坚查清根因并给可用档位。

过程（通宵攻坚 #780–#789）

  1. seq×tok/step 网格（cfg1–6）：cfg1(seq8192/mbs2)=108,291；cfg3/4(16K)=112,094/121,495；cfg5/6(32K) OOM。旧结论「seq≥8192 崩 5×」。
  2. cfg0a 对照（证伪 seq 假设）：seq4096/mbs4（tok/mb=16384，与基线同 seq 不同 tok/mb）= 113,514，同样慢 ⇒ 驱动变量 = tok/mb 而非 seq。
  3. E1–E5a 11 格实测：tok/mb≤12288 全快（~606K，<70GB，84%MFU）；tok/mb≥16384 全慢（~112K，81.1GB 顶格，13%MFU）。最小 seq=2048/mbs8（tok/mb=16384）仍慢 ⇒ seq 非成因终判。
  4. rev3 决定性复测（唯一变量 = --enable-cuda-graph）：cfg0a graph-ON = 121,032 / 81,087 MiB 顶格 ❌ vs cfg0ang graph-OFF = 561,126 tok/s = 0.93× 满速 / 75,517 MiB ✅（4.64× 提速，显存降 5.5GB）。recompute 56 层显存不变（75,517 MiB）⇒ recompute 对 Mamba2-hybrid 非降显存杠杆，证伪。
  5. seq=8192 验收复测（graph-OFF）：mbs2/DP8/accum16，中位 iter 20–60 = 7,072.0 ms，tok/s=296,543(DP8) / per-GPU=37,067 = 0.978× 基线(37,903) / vs cfg1(graph-ON 6,768) = 5.48× 恢复 / peak 77,265 MiB < 81,087 顶格 / loss 7.7489 / gnorm 0.8202 / nan 0 ⇒ §3 验收闭合。
  6. 32K CP 可行性 smoke：CP=1（seq32768/mbs1）OOM @ 81,049 MiB（须 CP）；CP=2（DP4×CP2）FAIL——RuntimeError: Unknown keyword argument 'window_size' for flash_attn_3::_flash_attn_forward，CP ring-attn 用旧 window_size=(l,r) 元组签名，flash-attn-3 已改 window_size_left/right 标量（site-packages，非 Mamba2 SSM 本身问题）。

结论

5.4× 吞吐骤降根因 = CUDA Graph 在 HBM 顶格（~81GB）时的 replay 病态停滞（非显存带宽 memory-bound——显存顶格是必要条件非成因；与 seq 无关）。驱动变量 = tok/mb = mbs×seq：≤12288 全快，≥16384 触发 graph 顶格停滞。修复 = 关掉 --enable-cuda-graph 一个 flag，无需 CP/recompute，已在 seq4096（0.93×）与 seq8192（0.978×）两点复测达标。16K = 当前实用满速上限（关 graph 561K / 75.5GB）；32K 当前不可跑（CP=1 OOM / CP=2 被 flash-attn-3 API 阻断，需代码 patch）。
