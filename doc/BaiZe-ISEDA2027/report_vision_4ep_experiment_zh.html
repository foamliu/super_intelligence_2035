2. 动机与预注册

背景：BaiZe 视觉编码器基线 E1fair（1 epoch）ProtB = 62.34%，外部评审质疑偏低。④-2ep（2 epoch）提升至 65.37%（+3.03pp）。运维侧预注册了 4ep 实验以判断 62.34% 是"预算不足"还是"特征质量天花板"。

预注册判据（2026-10-12 定稿，见 EXPERIMENTS_VISION.md §9.4）

ProtB 4ep 结果判据含义
> 70%VICTORYepoch 不足是主因，继续加 epoch
65~70%MODERATE / DIMINISHING增益递减，接近天花板，性价比下降
< 65%CEILING CONFIRMED特征质量天花板确认，停止加 epoch

预注册原文：「2ep first, 4ep if 2ep≥70%」——2ep=65.37% 未达 70% 胜利线，但运维侧仍批准 4ep 以获得完整递减曲线。④-4ep ProtB=67.05% 落入 65~70% MODERATE 区间。

4.1 训练健康度

全程无坍缩：C4 守卫在全部 PROBE 点均 OK。C1（对比对齐）从 2ep 的 0.5804 提升至 4ep 的 0.5932（+0.0128），C2_gap 从 +0.1844 微降至 +0.1791（稳定，无退化）。final_loss 从 0.1856 大幅降至 0.0805（−56.6%），表明重建分支持续收敛。

4.2 吞吐与 I/O

④-4ep 新增 374,202 步耗时 ~16.8h，steady_img/s ≈ 2,818。单步延迟 128–286ms（随 NFS 争用抖动），NFS 清闲时 ~95–105ms（≈5,100 img/s）。瓶颈为 NFS I/O 而非 GPU 算力——data 线并发下载拉低了有效吞吐。显存使用 ~16.5GB/卡 / 81.5GB（仅 20%）。

4.3 C1 轨迹

C1 增益递减：1→2ep +0.072，2→4ep +0.013（递减比 ≈ 0.18），与 ProtB 递减比 0.55 一致方向。

6. 结论

VERDICT: MODERATE, DIMINISHING

67.05% < 70% 胜利阈值。增益递减明确：1→2ep +3.03pp，2→4ep +1.68pp，递减比 ≈ 0.55。轨迹仍向上但接近天花板。

  • 增益真实：四指标一致 +1.7~2.9pp（2→4ep），seed 间 std ≤0.02pp
  • 递减确认：ProtB 增量从 +3.03pp 降至 +1.68pp（−44.6%）；C1 增量从 +0.072 降至 +0.013（−81.9%）
  • 未达胜利线：67.05% 落在预注册 MODERATE 区间（65~70%），不满足 >70% 继续加 epoch 的判据
  • 累计投入：~999 GPU·h（4ep 含前序），每 pp 增益的边际成本递增

决策建议：停止继续加 epoch（8ep/16ep 预期增益 ≤+1pp，ROI 极低）。转向其他方向（见 §8）。

7. 局限与诚实条款

  1. 单架构单数据：仅 OpenVision2 w512 + 部分 GPIC（94.9M）。结论不可外推至其他架构/数据组合。
  2. NFS I/O 瓶颈未隔离：④-4ep 训练期间 data 线并发下载，有效吞吐 2,818 img/s vs NFS 清闲时 5,100 img/s。若 I/O 充足，同样步数可能收敛更快（但 final loss 和 C1 不会因此改变）。
  3. Probe 可能未充分拟合：② probe sweep 已排除 90ep 欠拟合（×5ep 450ep = 62.15%，−0.18pp），但仅验证了 1ep 模型。4ep 模型特征维/分布不同，理论上可能存在不同的 probe 最优点。
  4. eval 数据量：ProtB 用全量 1.28M train + 50K val；ProtA / zero-shot / k-NN 仅 50K val 单次评测（无 seed 重复），std 不可计算。
  5. ProtB = BaiZe internal protocol：与外部 lp 数字不可直接比较。原因：(a) 预处理不同；(b) probe 超参不同；(c) 数据划分不同。
  6. 绝对数字口径：本报告所有数字与 MEMORY_VISION.md + EXPERIMENTS_VISION.md §9.5/§9.7 一字不差。吞吐/显存/iter 来自 daily-memories-vision/2026-10-13.md 实测。

8. 建议后续工作

8-a · MBS×4 / GBS×4 / LR×2 加速可行性分析

现状口径纠正

当前训练配置：MBS=64/卡 × 8 卡 = GBS=512（--batch-size 64 是每卡微批，非全局批）。显存使用 ~16.5GB/卡 / 81.5GB（仅 20%）。

三步分析

杠杆方案可行性风险/前提
MBS×4256/卡 → GBS=2048✅ 显存 ~60–80GB/卡，仍 fit H100 80GB需 100 步 smoke 验证不 OOM
LR×25e-4 → 1e-3⚠️ 方向正确（sqrt 缩放法则）本线稳定点 lr5e-4；lr3e-3 曾是 schedule 伪影。必须 smoke + C1/C2/C4 守卫
I/O 优化--num-workers 6→12–16 + tar 预铺本地 SSD✅ 真正瓶颈在 NFS I/O 而非算力需与 data 线下载错峰

关键发现：瓶颈是 I/O 不是显存

④-4ep 实测 iter 延迟 128–286ms（随 NFS 争用抖动），NFS 清时 ~95–105ms（≈5,100 img/s）。只加 batch 不加 dataloader 优化则加速有限——GPU 空等 NFS。杠杆优先级：

  1. --num-workers 6 → 12–16（脚本现传 6）
  2. tar 预铺本地 SSD/NVMe（消除 NFS 读取延迟）
  3. 与 data 线下载错峰（夜间跑 / 暂停下载）
  4. 然后才考虑 MBS×4 + LR×2

验证步骤：--batch-size 256 跑 100 步 smoke，测 img/s vs 现状（64/卡）。若 img/s 提升 ≥×3 → I/O 已修好，可推进 GBS=2048。若 img/s 不变 → 确认 NFS 瓶颈，先优化 I/O。

8-c · 三方向排序与 ISEDA 投稿建议

ISEDA 投稿截止 ~2027-02-01（剩余 ~3.5 个月）。按 ROI / 风险 / 投稿价值排序：

优先级方向预期收益GPU 成本风险投稿价值
1 (最高)Stage(iv) MLLM 对齐高（完整 story：编码器→MLLM）~50–100 GPU·h (SFT)中（框架复杂度）⭐⭐⭐ 核心 demo
2w384 更小塔中（R10-③ 暗示 w384 可能更优）~16 GPU·h (30k 步 smoke)低⭐⭐ scaling story 补全
3更多数据 N-epoch低（V3 full 118.1M @1ep=63.52% Null；④ 部分 94.9M @4ep=67.05%）~83–330 GPU·h/epoch高（NFS I/O 瓶颈未解决）⭐ 递减已确认

N-epoch 全量 vs V3 vs ④-4ep 关系

  • V3（full 118.1M @1ep）= 63.52% → Null verdict（vs E1fair 部分 94.9M @1ep = 62.34%，Δ=+1.18pp < 1.5pp 阈值）→ 更多 unique 数据 ≈ 更多 epoch 重复
  • ④-4ep（部分 94.9M @4ep）= 67.05% → epoch 重复有效（+4.71pp vs 1ep）
  • N-epoch 全量（full 118.1M @N-ep）= 未知，但 V3 Null + ④ 递减 → 预期 ≤ ④-4ep + V3 差值 ≈ 67.05 + 1.18 ≈ 68.2% @4ep → 仍不达 70%

结论：N-epoch 全量 ROI 极低——即使全量×4ep，预期 ~68%，仍在 MODERATE 区间，且需 ~330 GPU·h（保守）。优先将 GPU 预算投入 Stage(iv) MLLM 对齐。
