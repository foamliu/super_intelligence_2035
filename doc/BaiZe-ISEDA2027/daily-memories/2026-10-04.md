### 6) 🔬 根因定位与最终修复（RUN_ID 9 → 27，18 轮 ops 探查，全部留痕于 `run/ops/outbox.md`）

**四路 env 矩阵（RUN_ID 26）→ 收敛**：

| 组 | env | 结果 |
|:--|:--|:--|
| V0 | 原样 | ❌ Forbidden |
| V1 | 剥 `OPENAI_API_KEY+OPENAI_API_URL+API_TYPE` | ❌ |
| V2 | V1 + 剥所有 `*_proxy` | ❌ |
| **V3** | **V2 + 显式 `-k <secrets 里的有效 key>`** | ✅ **OK** |

⇒ **真凶 = `.29` 的 cline 必须显式 `-k`**；叠加故障 = loop 继承的 `OPENAI_API_KEY=01_549…`（**已吊销**）会**覆盖** secrets.json 的有效 key。

**最终修法（RUN_ID 27，已获批准）**：
```

# cline 调用行：
env -u <所有 *_proxy> -u OPENAI_API_KEY -u OPENAI_API_URL -u API_TYPE \
  cline -c "$CWD" --auto-approve true -m "$MODEL" -k "$CLINE_KEY" -t "$CLINE_TIMEOUT" "$prompt"
```
**校验通过**：前置 V3 复核 = OK；重启后 `error:.*Forbidden == 0`；两个 `bun cline` 均在正常推理；GPU 上 P-9 未受影响（80%+）。

### 7) ⚠️ 过程中我犯的错（已写入 `MEMORY.md §7`）

1. **`python3` 不在 relay 的非交互 PATH** → loop 里用 `python3 -c` 取 key 静默失败、退回 stale key（改用 `sed` 解决）。
2. **写 env 矩阵时漏剥 proxy** → 三组全红 → 误判"key 失效"，**白绕 3 轮**。
3. **在"修 driver"时把能跑的版本改坏**（去掉 `-u OPENAI_API_KEY`）→ 制造了一次回归。
4. `grep -c Forbidden` **会数到 agent 的散文** → 假阳性；精确探针应为 `grep -c 'error:.*Forbidden'`。
5. 脱敏 `sed` 写错 → **RUN_ID 11 把一把（已失效的）`OPENAI_API_KEY` 明文写进了 `outbox.md`**。

> 教训：**每次只改一个变量，并在同一块里验证该变量确实生效**；**别在没定位清楚前动生产进程**（其间两线本就在空转，等待成本为零）。
