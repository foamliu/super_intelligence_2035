1.2 机制解读（顺带给出了「坍缩的归因」）

  • 坍缩不是「稠密监督」的错，而是「caption 依赖」的错：arm④ CoCa（稠密 + 依赖 caption）坍缩到 0.47%；arm⑥ AIMv2（稠密 + 不依赖 caption）翻盘到 12.08%。
  • 合理机制：MAE 式 masked patch 重建提供逐 patch 的空间稠密监督，在数据受限（~15M 对）下显著优于 InfoNCE 的「每对 1 个全局标量」。
  • ⚠️ 诚实限定（C2）：本臂是 AIMv2-style 自研改编（InfoNCE + masked patch MSE，PatchPredictor 仅 +0.66M），非官方复现（官方是纯 AR、无对比项）；结论只对我们 recipe 成立。

10诚实条款：我这轮犯的错与更正

#我犯了什么后果 / 更正
1SSE 探针方法错：用 curl -w '%{http_code}' 探 /sseSSE 是长连接，该参数只在传输结束时打印 → 被 timeout 杀掉后空输出 → 我一度以为「服务不可用」。更正：只取响应头（curl -D - -o /dev/null）或抓首帧（curl -sN）。已入 MEMORY.md §7。
2用错 cline 子命令：cline mcp list不是有效子命令（报 Unknown command）。正解 = cline config mcp。已入 §7。
3smoke 用错 (model, base, key) 配对：拿 .cline_data/secrets.json 里 .12 那把 key 配 glm-5.2报 Forbidden，与 RUN_ID 56 是同一个坑。更正：一律复现 loop 的真实配对（llm_pick 选出的 model/key/base）。
4早前误判「cimi-search/cimi-fetch 在此环境从未可用」半对半错：MCP 服务一直在跑，缺的是客户端的 MCP 配置；而且其中一部分是我自己在 RUN_ID 55 重播 settings 时覆盖成空的。教训（新增纪律）：迁移/覆盖配置前先 diff 关键项（MCP、provider、secrets），别只看目标文件的字节数。
5编辑日志时误删了两行既有内容（MEMORY §6 的 cline 隔离目录行、MEMORY §7 的诊断教训行）已当轮发现并补回。教训：用 old_text 替换时，new_text 必须包含被保留的原句。
