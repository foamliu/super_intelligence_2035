1. 背景与动机

我们正在为 EDA Agent「烛龙」构建设计流评测集，按业务分数字 / 模拟 / 验证 / 测试等方向。 面向字节驻场人员的《设计流用例编写指南》已定义用例与框架之间的接口协议（prompt 任务目标（含文件/PDK 路径）+ entry_point 交付件 + test 交付件校验器）。 但真实设计流（如数字后端：load → syn → place → CTS → route → timing → export GDS）本质是 多步、有状态、长周期的 agent 任务：每一步消费上一步的产物（网表/DEF/报告）， agent 需要边跑边看输出、再决定下一步。这与框架当前的"单轮补全 + 一次沙盒调用 + 看末行标记判分"模型不匹配。

本文档评估现状、给出框架与 MCP 工具侧的改进设计，重点回答两个问题：

  • Q1：是否需要一个 run_commands 沙盒工具，以便在 EDA 服务器上执行命令？
  • Q2：是否需要 Session 概念，使一轮（Turn）交互中多次调用沙盒时保留之前保存的文件 / 进程状态？

结论先行：两者都需要。详见 §4–§7。

  • 一条 case = prompt(空函数体) + test(check(candidate)) + 执行入口。
  • 沙盒调用是单次 POST /v1/run_code，payload = {code, lang, host}，无 session_id。

3. 核心问题：单轮无状态 vs. 多步有状态

维度现状（单轮补全）设计流需要
任务形态补全一个函数驱动一整条 flow，N 个阶段
agent 行为产出 1 段代码即结束多轮：调工具→看输出→决策→再调
状态单次调用内闭环跨调用：阶段 N 产物被阶段 N+1 消费
沙盒调用1 次 run_code多次 run_commands/run_code
判分对象stdout 末行标记最终交付物（GDS/报告/指标）
耗时秒级分钟~十分钟级，占 license
隔离共享 daemon + clean_workdir每任务独立 workdir / 独立会话

这不是"加个字段"能解决的，需要一条新的会话化 agentic 评测通路，与现有单轮通路并存。

关键点：

  • Session 是一等公民：显式 open/run/read/close，状态不再"靠没清"。
  • 每任务独立 workdir（fresh），杜绝跨任务污染；session_id 贯穿一次 attempt。
  • pass@k = k 个独立 session（k 次 attempt），互不共享状态。
  • 单轮补全通路保持不变（向后兼容，字节同学已按此写 case）。

5.1 为什么需要（回答 Q1）

  • 跑 EDA 工具的批处理命令：innovus -batch -files run.tcl、innovus -files save.tcl。
  • 跑 shell 命令：cat timing.rpt、grep NFN def/*.def | wc -l、ls -la outputs/。

5.2 接口草案（MCP 工具 + 沙盒端点）

run_commands 有两层：eda_fastmcp 的 MCP 工具（agent 调用）和 eda_sandbox_lite 的 HTTP 端点（MCP 工具转发到此）。

MCP 工具（eda_fastmcp，agent 调用）

run_commands(
    commands: list[str],        # 必填：按序执行的 shell/EDA 命令
    workdir: str,               # 必填：NAS 上的会话工作目录(两机可见)
    cwd: str | None = None,     # 可选：相对 workdir 的子目录
    env: dict | None = None,    # 可选：追加环境变量
    timeout_per_cmd: int = 120, # 单命令超时(秒)
    return_files: list[str] | None = None,  # 执行后读回的文件(相对 workdir)
) -> dict:
    {
      "results": [               # 每条命令一项
        {"cmd": "...", "exit_code": 0, "stdout": "...", "stderr": "...",
         "duration_ms": 1234, "timed_out": false}
      ],
      "files": {                 # return_files 的内容(文本直返/二进制 base64)
        "timing.rpt": {"content": "...", "size": 1234, "is_text": true}
      },
      "workdir": "/nasdata/.../sessions/<id>",
      "error_log": ""            # 工具级错误
    }

HTTP 端点（eda_sandbox_lite，32.75 上）

POST /v1/run_commands
{
  "commands": ["innovus -batch -file run.tcl", "cat timing.rpt"],
  "workdir": "/nasdata/.../sessions/<id>",   # NAS 路径, 32.75 本地可见
  "timeout_per_cmd": 120,
  "return_files": ["timing.rpt"]

→ CodeResponse 兼容的四字段 + results/files 扩展
关键：workdir 是 32.75 侧的路径（EDA NAS 上的目录，如 /eda_nas/.../sessions/<id>/），36.15 看不到。 命令在 32.75 上执行，产物文件落 EDA NAS → 36.15 上的 agent 要看内容，只能通过 return_files 走 HTTP 取回（不能直读路径）。 DE 下发的文件（嵌入 prompt 的 EDA NAS 路径）同理：32.75 能读，36.15 不能。

5.4 Hook 重定向：cline 内置 run_commands → 32.75

cline 有内置 run_commands 工具，在 36.15 本机执行 shell 命令。当前为防泄题（agent 读 benchmark 数据集 / 读答案）已由 PreToolUse hook 完全禁用——hook 将 run_commands 调用 overrideInput 为 echo "ACCESS RESTRICTED" 的 no-op（见 scripts/cline_hooks/PreToolUse 第 127–128 行）。

6. 改进点 B：引入显式 Session 概念（回答 Q2）

6.1 为什么需要

设计流在一轮（Turn = 一次 attempt）中会有多次沙盒调用，它们必须共享：

  • 工作目录：阶段 N 写出的 DEF/报告，阶段 N+1 要读到。
  • EDA 进程 / 会话：loadDefFile 一次后，后续 dbGet 在同一 Innovus 会话里才有效。
  • env / license 上下文：工艺库、lib.defs、TECHLIB 挂接。

现状靠"daemon 长驻 + workdir 没清"隐式满足，但无隔离、无生命周期、无明确归属，是污染与不可复现的根源。需要显式 Session 抽象。

6.3 Session 与 Turn / pass@k 的关系

  • 1 Turn = 1 attempt = 1 session。一个 task 跑 pass@k 即开 k 个独立 session，各自 fresh workdir、互不污染。
  • session 内多次调用共享状态；session 间完全隔离。
  • session 超时 / 超预算 / agent 主动 declare_done 即关闭并判分。

6.4 Session 接口草案（MCP 工具侧）

# 评测驱动调 (HTTP 到 32.75):
open_session(task_id, host, eval_id, sample, budget) -> {"workdir"}   # 创建 workdir (§7.1)
# agent 调 (MCP 工具, eda_fastmcp):
run_commands(commands, workdir, ...)        # 见 §5.2, HTTP 到 32.75
run_code(code, lang, host, workdir=None)    # 现有 4 核心 MCP 之一, 加 workdir 参数
mcp__...__read_file(path)                   # 远程读 32.75 侧文件 (区别于内置 read_file)
mcp__...__list_files(dir, pattern)          # 远程列目录
declare_done()                              # agent 声明完成, 触发判分
# 评测驱动调 (HTTP 到 32.75):

实现注：open_session 不必新起 OS 进程——可复用 eda_fastmcp 现有 4 端口 daemon 池， 但绑定语义从"并发"改为"独占整个 session"（任务期间持有端口，结束才归还）。 池不够大时排队（与现状一致），但排队单位是"任务"而非"单次调用"。需要更大池子或 session 级 license 配额。

7. 改进点 C：EDA 服务器接入（eda_sandbox_lite 改造）

eda_sandbox_lite（32.75）当前只有 POST /v1/run_code（执行代码字符串），需新增 POST /v1/run_commands（执行 shell 命令序列）。无需 SSH——所有通信走 HTTP。

  • 新增 /v1/run_commands 端点：接收 {commands, workdir, timeout_per_cmd, return_files}，在 32.75 上按序执行 shell 命令（subprocess），cwd 设为 workdir，返回每命令 exit_code/stdout/stderr + 请求的文件内容。workdir 是 32.75 侧可见的路径（EDA NAS 或本地盘）。
  • session workdir 在 32.75 侧：EDA NAS 上的目录（如 /eda_nas/.../sessions/<id>/），36.15 看不到。EDA 环境的 DE 在其它服务器存文件到 EDA NAS，把路径嵌入 prompt → agent 调 run_commands（HTTP 到 32.75）→ 32.75 在 EDA NAS 上读写。open_session 时由 32.75 创建 workdir（或 DE 预先建好）；close 时由 32.75 归档+清理。
  • 文件读回必须走 HTTP：36.15 看不到 EDA NAS，agent 要看产物内容（报告、波形、日志）只能通过 run_commands 的 return_files 参数，由 32.75 读文件后通过 HTTP 返回。不能直读路径。
  • 新增 /v1/read_file 端点（推荐）：单独的文件读取端点，供 read_file MCP 工具调用——agent 不必每次为看一个文件发一条 cat 命令。参数 {path}（32.75 侧路径），返回文件内容（文本直返 / 二进制 base64）。
  • 无需 open/close_session 端点（简化）：session 的"状态"就是 32.75 侧 EDA NAS 上的 workdir 目录。run_commands 是无状态的（每次指定 workdir），状态全在 EDA NAS 文件里。
  • EDA 进程模型：run_commands 跑 innovus -batch -file <script.tcl> 等批处理命令——每次起新进程，设计/状态通过 EDA NAS 上的 DEF/LEF 文件传递（不靠 daemon 内存状态）。若需 daemon 常驻（避免冷启动），用 run_code 的 Innovus daemon 路径（已支持 workdir 参数）。
  • License / 资源：run_commands 并发 = 同时跑的 EDA 进程数 ≤ license 数。用信号量限并发（参照现有 TCL_MAX_CONCURRENCY 模式）。
  • 产物归档：close_session 时 32.75 把 EDA NAS workdir 的关键产物通过 HTTP 返回给评测驱动（36.15），由评测驱动存到 output_evaluation/<eval_id>/sessions/<task_id>/<sample>/（开发 NAS 上）。
关键约束：两个 NAS 不互通 → 文件跨机传递只能走 HTTP。return_files（run_commands）和 /v1/read_file 是 agent（36.15）获取 32.75 侧文件内容的唯一通道。 session workdir 在 32.75 侧 EDA NAS 上，36.15 无法直接访问。

7.1 工作目录的建立与冲突避免

每个设计流 attempt 需要一个独立的 workdir（避免跨任务/跨 sample 文件污染）。建立机制：

  • 谁创建：eda_sandbox_lite（32.75）在收到首次 run_commands（或专用 open_session 端点）时创建。36.15 看不到 EDA NAS，不能自己建。
  • 路径规则：<EDA_NAS_ROOT>/sessions/<eval_id>/<task_id>/<sample>/。 eval_id = 评测批次时间戳，sample = pass@k 的第几个样本（0~k-1）。四层目录保证不同批次/不同任务/不同样本绝不冲突。
  • workdir 路径传递：32.75 创建后返回 workdir 路径（绝对路径），评测驱动（36.15）记录下来，后续每次 run_commands / run_code 调用都带上这个路径。agent 也通过 system prompt 得知该路径。
  • 幂等创建：若目录已存在（续跑场景）则复用不报错；mkdir -p 语义。
  • 清理：评测结束后，评测驱动调 close_session（或 run_commands 带 rm -rf）清理 EDA NAS 上的 session 目录；关键产物先通过 HTTP 归档到 36.15 开发 NAS。
并发安全：pass@k 的 k 个 sample 可能并发跑，各自 workdir 路径含 sample 维度 → 天然隔离。 多批次并发（不同 eval_id）也由 eval_id 维度隔离。无需文件锁——路径唯一即不冲突。

9. 改进点 E：判分（test 交付件校验器）

设计流判分与现有 EDA 脚本评测同构——两态：assert 全过 → pass，任一抛错 → fail。区别只是判分对象从"函数返回值"换成"交付件"。

  • 判分时机：agent declare_done 或超预算，框架在同一 session内运行 test（即 check(entry_point, workdir)，通过 HTTP 在 32.75 上执行）。
  • 判分内容：由 case 作者在 test 里用断言自定义，交付件存在性也是其中一个 assert（如 unless(isFile(zip) error("deliverable missing"))）。常见模式：
    1. 交付件存在性：entry_point 指向的文件/对象是否已生成（如 zip 是否存在、5 个产物是否齐全）。
    2. 指标断言：从交付件/报告解析指标（如 timing WNS、DRC count），按真值断言。
    3. 结构/拓扑校验：复杂校验（如原理图拓扑、flow 完整性）由 test 脚本自行实现。
  • 判分结果：两态，与单轮一致——
    verdict条件类比单轮评测
    passcheck 不抛错（所有 assert 通过）代码跑通且 stdout 末行是 OK 标记
    failcheck 抛错（任一 assert 失败，含交付件不存在）代码执行报错/无输出，或 stdout 末行是 FAIL 标记
  • 判分输出：{verdict: "pass"|"fail", check_log: "..."}，写入评测结果 JSONL。
  • 与单轮判分的兼容：单轮仍用 stdout 末行标记；设计流用 test 交付件校验器（assert 抛错与否）。两套判分器并存，由 mode 路由，但判分语义同构（两态）。

10. 改进点 F：评测主驱动改造

现有 scripts/run_zhulong_batch.py 是单轮批处理驱动。新增设计流驱动 scripts/run_design_flow_batch.py：

for task in cases where mode == "design_flow":
  for sample in range(num_samples_per_task):          # pass@k
    workdir = open_session(task_id, host, eval_id, sample, budget)   # 32.75 创建 workdir
    try:
      run_agent(prompt, workdir, budget=task.budget,
                tools=[mcp__run_commands, run_code, search_apis, get_api_details,
                       mcp__read_file, mcp__list_files, declare_done])
      # 判分: 运行 test 校验器 (含交付件存在性 assert), 两态 pass/fail
      verdict = run_check(workdir, entry_point, test)
    finally:
      close_session(workdir)                           # 归档产物(HTTP回传) + 清理
    record(task_id, sample, verdict)
  • agent 侧仍用 cline + eda_fastmcp MCP，但工具集换成会话化版本（带 session_id）。
  • 并发度 = min(license 数, session 池大小)，远小于单轮的 8 worker。
  • 断点续传粒度从"任务"保持，但状态更重（需归档 session 产物以便续跑复盘）。

Innovus license 数有限，长驻 session 并发受限session 池大小=license 数；排队+超时熔断；重任务降级 per-session 子进程
per-session fresh workdir 带来 I/O 与空间压力close 后归档关键产物即清；设保留期；大设计用链接而非复制
agent 长程不可靠（跑飞 / 死循环 / 不 declare_done）budget 强制截断；超时即判分（多半 fail）；轨迹归档供分析
状态污染（daemon 全局变量残留）open_session 做 clean slate；close_session 彻底清理；每 session 独立 workdir
设计流 case 编写门槛高长鑫先出范例；指标真值与设计路径由长鑫统一提供
与单轮通路的兼容mode 字段分流，单轮完全不动；字节已写 case 不受影响

图 6 · 分阶段落地甘特图（P0 后端能力为关键路径）
  1. P0 · 确认后端能力（1 周）：与沙盒后端 owner 对齐 session/run_commands/read_file 端点现状与排期；明确 license/并发上限。
  2. P1 · 单 session 走通（1~2 周）：eda_fastmcp 实现 open/run_commands/read_file/close；EDA-Eval-Framework 出 1 个 设计流范例 case，端到端跑通 1 个 session（pass@1，单任务）。
  3. P2 · 判分与归档（1 周）：test 交付件校验器落地（check(deliverable, workdir) + 断言）；session 产物归档到评测结果目录。
  4. P3 · 批量与并发（1~2 周）：run_design_flow_batch.py + session 池 + 排队 + 断点续传；小规模验证集跑通 pass@k。
  5. P4 · 范例扩充与字节协同（持续）：长鑫出 3~5 个数字方向 设计流范例 → 字节参照扩写；模拟 / 验证 / 测试方向按需复用同一通路。
对 Q1 / Q2 的最终回答： Q1 需要 run_commands——设计流要跑 EDA 工具命令/shell/读产物，超出 run_code 的解释器语义，二者互补（§5）。 Q2 需要 Session——多轮调用必须显式共享 workdir/进程/产物，且需按任务隔离与生命周期管理，不能继续靠 daemon 残留（§6）。 两者共同构成"会话化 agentic 评测"通路，与现有单轮补全通路并存（§4）。
