② 六个问题的回答

Q1. 我们最薄弱的论证环节是哪个？

结论：grounding-depth 假设是「灵魂但未实证」，单骨干是「最显眼的枪眼」——前者更致命，后者更易被打。

① 单骨干（最显眼，审稿人第一枪）。论文在 sections/4_experiments.tex:22 原句：

"A multi-backbone sweep (GLM-5.2, Kimi-K2.6, DeepSeek-V4-Flash, Doubao-Seed-2.0-Pro) is configured but not yet run to completion, so this paper reports a single-backbone evaluation; RQ3 is therefore discussed as an open question"— sections/4_experiments.tex:22

而引言贡献第 2 条把 10.0% 称为「ceiling」（1_intro.tex:32「a 10.0% Pass@1 ceiling」）。用一个骨干定义 "ceiling" 在方法论上站不住——审稿人会问：换个骨干是不是就 15% 或 5%？论文自己在 §5 threats（5_analysis.tex:137）也承认 "Claims about 'the best' or about model scaling are therefore not supported by our own data"。这是论文已自认但未补救的最大弱点。

② grounding-depth 假设（更致命，因为是灵魂论断）。论文的核心解释变量 grounding depth 是手工标注而非测量，sections/5_analysis.tex:46 原句：

"Depth is not measured; it is an annotation we assign per domain (a design choice, stated as such)."— sections/5_analysis.tex:46

而图注（5_analysis.tex:65）进一步承认 "this figure does not by itself establish a causal or monotone relationship"。这意味着论文的核心解释变量 = 域标签，与因变量（per-domain Pass@1）共享同一个分组来源，存在循环论证风险：你按域标 depth，又按域报 Pass%，再说 depth 解释 Pass%——这不是独立证据。审稿人会指出：任何一个与域共变的隐藏变量（任务复杂度、断言数、资产可移植性）都能顶替 depth。

③ 附录 A 的 per-shard 硬编码是「会反复腐化」的脆弱点（v13 修订：r417 已补齐当前差额，但结构性隐患仍在）。附录 A 的 per-shard 分解是手写硬编码，每轮造题都要人工同步：appendix/A_benchmark_details.tex:53-54 当前原句（r417 同步后）：

站不住的部分（需补对照组）：

② characterization 19.2% 不稳健。仅 26 个 decided run、5 PASS。Wilson 95% CI 约 [8.5%, 36.7%]——区间宽度 28pp，几乎覆盖 spice_sim 到 pnr_signoff。论文把它列为「第二高领域」并写进引言（1_intro.tex:21「characterization 19.2%」），但这个数字一翻就变。补法很便宜：53 个 characterization case 只评了 28 个，把剩余 ~25 个评完，decided n 从 26 → ~50，CI 大幅收窄。建议验证。

③ spice_sim 拖低总体，且失败模式以「脚本崩溃」为主。spice_sim 是活集最大域（220 case，19.0%）也是评测第二大域（104 run）。Pass@1=8.4% 低于总体 10.0%——spice_sim 拉低了头条数字。失败分类（appendix/B:120）显示 spice_sim：NOSUB 8 · RT 26 · SEM 48 · UNK 12。RT（ASSERT_RUNTIME，候选脚本崩溃/非零退出）= 26，是 13 域里第二高（仅次于 schematic_netlist 26）。这反映 spice_sim 的真实难点：候选要解析二进制波形（.tr0）、写正确的 HSPICE .measure、处理工程后缀（583.3333m）——脚本能跑通本身已是高门槛，而非「语义对不对」。论文 §5（5_analysis.tex:33）把 spice_sim 归入「semantic failures dominate medium-grounding domains」，但实测 RT 占比 26/94=27.7% 说明运行时崩溃才是 spice_sim 的主因之一，论文的「semantic dominant」叙事对 spice_sim 不够精确。

④ 风险与反对意见（预判审稿人反驳 + 我们的答）

反驳 1：「单骨干，10.0% 不是 ceiling」

审稿人会问：你只用 DeepSeek-V4-Pro，凭什么称 ceiling？换 GLM-5.2 可能 15%。

论文现况：§4:22 已自认 single-backbone，RQ3 开放；但引言 §1:32 仍用 "ceiling" 一词。

我们的答：(1) 接受批评，把 "ceiling" 改为 "observed Pass@1 under a single frontier backbone"，删除「天花板」暗示。(2) 补 P1 的 100-case 多骨干析因，给出跨骨干区间。若区间窄（如 8–12%）→ 强化「task-type 主导」叙事；若区间宽（如 5–18%）→ 诚实报告「backbone 轴仍有显著效应」，RQ3 转为实证发现而非开放问题。两种结果都对论文有利（前者强结论，后者新发现），不补才是最大风险。

反驳 2：「grounding depth 是循环论证」

审稿人会问：depth 是你按域手工标的，Pass% 也按域报，两者共享分组——这不是独立证据。任务复杂度、断言数、资产可移植性哪个不能顶替 depth？

论文现况：§5:46 已声明 "a design choice, stated as such"；图注 §5:65 承认 "does not by itself establish a causal or monotone relationship"。诚实但未补救。

我们的答：(1) 接受「标注非测量」的定性，但补 P3 的实测化：从 50 case 日志数实际 live tool-call 次数，与 depth 标注做 Spearman 相关。若 ρ > 0.7，说明标注与实测一致，循环论证指控失效；若 ρ 低，说明标注需修订，但实测 depth 仍是更强的解释变量。(2) 补一个混杂变量检查：回归 Pass@1 ~ depth + 断言数 + 资产文件数，看 depth 系数是否稳健。建议验证。

反驳 3：「你的 spice_sim 任务不真实，资产是合成的」

审稿人会问：摘要说 "derived from real Cline traces"，但 spice_sim 的 PDK 是私有的，你的资产肯定是合成的——那这还是「真实轨迹」benchmark 吗？

论文现况：§9 reproducibility（9_reproducibility.tex:7,27）诚实承认 traces 与 PDK 不能发布，但未披露 per-domain 合成比例。

我们的答：(1) 精确区分「任务意图真实（prompt 源自真实工程师会话）」与「交付资产可移植化（私有 PDK → 合成 deck）」——前者是 benchmark 的认知来源，后者是可发布性的工程妥协。(2) 补 P2 的 trace_fidelity 披露表 + 配对比较：若 faithful 与 synthesized 的 Pass@1 无显著差异，则合成不系统性偏置难度，卖点的实质成立；若有差异，诚实报告并讨论方向。关键是不披露才是隐患，披露了反而是方法论透明度。

反驳 4：「70 ERROR 排除使分母偏乐观」

审稿人会问：你把 70 ERROR 排除出分母，其中 59 个是「资产缺失」——这到底是模型失败还是你 benchmark 没配齐？如果是后者，10.0% 是虚高。

论文现况：§4:66 脚注已给三分母（10.0/9.9/8.9%），但未单独拆「资产缺失」子类。

我们的答：(1) 59 个资产缺失是 benchmark 工程缺陷而非模型失败，排除出「模型能力分母」是正确的；但应单独列「benchmark 成熟度分母」。(2) 补 P3 的 ERROR 修复重跑：修齐 59 个 assets/ 后重跑，报告「X 个转 PASS / Y 个转 FAIL / Z 个仍 ERROR」。若修复后 10.0% 几乎不变，证明排除正当；若变动大，则更新头条数字。建议验证。

反驳 5：「domain 排序不稳健，7.1× 是点估计」

审稿人会问：pnr_signoff 20.8%（CI [9.2,40.5]）与 physical_verify 2.9%（CI [0.8,10.1]）区间重叠，7.1× 跨度可能是噪声。

论文现况：§4:77 已预判——"should be read as descriptive rather than established"，并明确 "What is robust is the ordering"。这是很好的预防性叙事。

我们的答：维持现有叙事，不再用 7.1× 作为强论断。补一个跨骨干的 ordering 一致性检验（P1 的副产品）：若 4 个骨干的 domain ranking 的 Kendall τ 都 > 0.7，则「ordering 稳健」从单骨干描述升级为跨骨干实证。已有的防御已足够，补 P1 后更强。

反驳 6：「可复现性不足，核心 trace 不发布」

审稿人会问：你说 trace 是 IP 不能发布，那外部研究者怎么复现？这不过是公司内 benchmark。

论文现况：§9 已有分层发布策略（harness 开源、sanitized 子集、mock-EDA、judge-only mode）+ 开源 EDA 路线图。

我们的答：分层发布是工业 benchmark 的标准做法（论文已引 rao2026sap, sulthanpete2026nyris）。强化三点：(1) mock-EDA 模式必须实际可用（不只是宣称），附一个外部人按文档跑通的截图；(2) sanitized 子集的规模应明确（当前未给数字——建议至少 100 case 跨 13 域）；(3) 开源 EDA 路线图给一个最小可跑 prototype（哪怕只映射 2 个域到 ngspice/OpenROAD），证明路线可行而非画饼。
