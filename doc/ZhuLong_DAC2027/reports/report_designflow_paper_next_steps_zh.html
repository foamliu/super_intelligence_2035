② 六个问题的回答

Q1. 我们最薄弱的论证环节是哪个？

最容易被 ICML 审稿人打穿的是中心解释构念「工具链接地深度（grounding depth）」，其次是单骨干未跑完 RQ3。具体到 section + 原句：

1接地深度是「人工按域标注」，与它要解释的域排序循环。§5.2 原句：

“We define grounding depth as the minimum number of live EDA tool calls needed to produce a correct deliverable. Depth is not measured; it is an annotation we assign per domain (a design choice, stated as such).” — sections/5_analysis.tex §5.2 Tool-Chain Grounding Depth

而图 fig:grounding-depth 的 caption 自己也承认：“the binning is a design choice, not a measured quantity … this figure does not by itself establish a causal or monotone relationship.” 一个手工按域贴的标签，恰好「解释」了按域统计的通过率排序——审稿人一句「circular / post-hoc」就能把 §4.2 与 §5.2 的核心叙事拆掉。这是全文最薄弱的一环。

2RQ3（模型扩展）整章无自己数据。§4.3 原句：

“the 10.0% vs. 76.5% gap is a cross-benchmark comparison, confounded by task type, and therefore cannot by itself show that model scaling is insufficient. We state this as a hypothesis to be tested by the multi-backbone sweep.” — sections/4_experiments.tex §4.3 Model Scaling (RQ3)

附录 B §per-model 进一步承认：“GLM-5.2, Kimi-K2.6, DeepSeek-V4-Flash and Doubao-Seed-2.0-Pro are configured in the same harness but their sweeps are still running, so we report no numbers for them.” —— 三个 RQ 里最关键的 RQ3 完全空缺，而摘要却把「单骨干 10.0%」当 headline。

3headline「7.1×」是点估计且 CI 重叠。摘要原句：“the highest-passing domain (pnr_signoff, 20.8%) exceeds the lowest (physical_verify and layout_aether, both 2.9%) by a factor of 7.1× (a descriptive point estimate; the two confidence intervals overlap)”。§4.2 给出 pnr_signoff CI [9.2,40.5] 与 physical_verify CI [0.8,10.1] 确实重叠，且 pnr_signoff 仅 24 个 decided run（翻一个 PASS 就 20.8%→24.0%）。摘要领先句用 7.1× 做卖点，正文却 downgrade，口径不自洽。

410% 批次是基础设施 ERROR，被排除在分母外。§5.1 原句：“predominantly a missing per-case asset directory (59/70)”。即 696 个 run 里 70 个 ERROR，其中 59 个是「单 case 资产目录缺失」这种框架侧可修 bug，不是模型能力问题。把它排除出分母在统计上可辩护，但审稿人会质疑「696-run 快照本身是否可信」。

5附录 A 任务示例是 [TODO]。附录 A §task-example 原文：“[TODO: show one complete task: prompt + assets + check.py + test_rationale. Suggested: a medium-difficulty schematic_netlist case …]”。基准细节附录未完成，直接影响「benchmark 论文」的可复现性印象。同一附录还有未解决的 TODO(T12)：摘要/引言写「268 位工程师、42 台工作站」，§2 写「698 台主机、224 位去重用户（mc≥30）」，三处口径未统一。

6逐 run 归因工具有 17.1% 类级 UNKNOWN。§5.1：“The tool's class-level UNKNOWN share is 119/696 = 17.1%”。失败分类法建立在一个自带 17% 未分类率的工具上，而 §5.1 的所有占比（21.0%/62.8%/0.3%）都依赖该工具的输出。

Q2. 10.0% 这个数字站得住吗？

站得住的方向：论文主动给了三个分母（10.0%/9.9%/8.9%），相差 ≤1.1pp 且 CI 重叠（§4.1 脚注），口径选择不影响结论；这点做得扎实。Wilson CI 已报，统计诚实在 ML benchmark 里属上乘。

站不住 / 需补对照组的方向（按必须性排序）：

  1. 单 backbone（最大软肋）。696 run 全部是 DeepSeek-V4-Pro。审稿人一句话：「10.0% 是 DeepSeek-V4-Pro@low 的属性，不是 task 的属性」。必须补多骨干扫描（附录 B 已配置 4 个，约 5 机器日，见行动项 E2）。
  2. 单 thinking level（thinking=low）。附录 C 原句：“We chose low over medium/high to control token cost … the trade-off is reduced reasoning depth. A thinking-budget ablation is planned for the camera-ready version.” 低思考档可能系统性压低深度接地域（physical_verify/layout_aether 需要多轮迭代推理），从而把 2.9% 压得更难看。这是一个与「接地深度」叙事强混杂的混淆量，必须在最低域上做 thinking=medium/high 消融。
  3. 70 个 ERROR 的处置。排除出分母可辩护，但 59/70 是可修的资产目录 bug。建议验证：修掉这 59 个资产目录问题并重跑，给出「ERROR-fixed 后的 Pass@1」；若仍 ≈10%，则数字稳；若明显变化，则现 10.0% 是被 infra 拉低/拉高的伪结果。
  4. 无 Pass@k（k>1）与无 seed 方差。§9 只报 Pass@1（单 trace/任务）。没有重复 seed，无法估计 10.0% 的随机方差。建议验证：在 100 任务分层子集上跑 5 seed 报 Pass@1±std 与 Pass@5。
  5. 620 decided 分母的域构成极不均。spice_sim 95 decided、schematic_netlist 113、physical_verify 68，而 pnr_signoff 仅 24、characterization 26。聚合 10.0% 被大域（spice_sim 8.4%、schematic_netlist 11.5%）主导。建议验证：报一个「域均衡子采样」后的 overall（每域抽等量 decided run 再平均），看 10.0% 是否被分布拉偏。

结论：10.0% 作为「单骨干单思考档下的点估计」站得住且诚实；作为「多步编排天花板」的论断站不住，需 E1–E3 三组对照才能升级为结论。

Q3. B 线视角的独特输入（spice_sim / characterization）

这两个域在论文里的表现，结合我造 case 的实测：

spice_sim：第二大域，但低于均值 — 信号在「语义失败」不在「工具调用失败」

附录 B 表：spice_sim 104 runs（8 PASS/87 FAIL/7 ERROR/2 ABSENT），Pass=8.4%，低于总体 10.0%。逐域失败矩阵（附录 B tab:failure-by-domain）：spice_sim F+E=94 = NOSUB 8 + RT 26 + SEM 48 + UNK 12。

  • SEM=48/94≈51% 占主导——agent 产出了能跑的 SPICE deck，但测量语义错（测了错误的量、错的节点、错的窗口）。这与 §5.1「semantic failures dominate the medium-grounding domains (spice_sim …)」一致。
  • RT=26：候选脚本崩溃/非零退出。这部分是判分器在 B 上真跑候选（§4.2 真跑候选）抓到的，说明 spice_sim 的 check.py「有牙」。
  • NOSUB=8：8 个 run 连 submit.zip 都没产出——在 spice 域 agent 卡在「该调哪个仿真器/怎么写 deck」的接地失败。

我造 case 的依据：本轮对 shard B 候选池的 mc-matrix 复算（src=designflow/summary_1105.tsv）显示 mc≥10 池 486、fresh 23；逐条 peek top 候选后，干净的 spice_sim/characterization design_flow 任务几乎已被采尽——剩余 fresh 多为 aether/GUI 连接（8hdj3/i6fn6）、咨询式（o5xjq「可以用哪些 cad tool」）、数字编译（wl9i4 xcelium）、或 EDA 工具自身开发（nsf5a 在改 ModelQA 的 C++/Perl）。这印证论文 §2「analog/mixed-signal 占主导」在造题供给侧也成立：spice 池在 mc≥30 已 98%+ ledgered，mc≥10 的增量多为假阳性。论文应正视「spice_sim 域样本量大但增量边际递减」。

characterization：小样本但第二高 — 它是「text-in script-out」的最佳样本

附录 B 表：characterization 28 runs（5 PASS/21 FAIL/2 ERROR），Pass=19.2%，第二高，仅次于 pnr_signoff 20.8%。失败矩阵 F+E=23 = NOSUB 5 + RT 7 + SEM 8 + UNK 3。§4.2 把它归入 depth 1–2（“largely text-in, script-out … produce from prior knowledge with only light tool interaction”）。

我的判断：characterization 高通过率 部分是样本量小（仅 26 decided，CI 必然宽），部分是真（脚本模板化、接地浅）。但这里有个判分口径隐患：我经手过 EDA-Eval-DesignFlow-Characterization-001，其 check.py 在 2026-11-02 的 rewrite_queue 里从 7 conds 重建成 14 conds（a–n）才过 k≥8 闸门——说明早期 characterization case 的断言强度是被「补」上来的。建议验证：抽查 characterization 域已跑的 28 个 run，确认其 check.py 都过了 k≥8 且含真跑候选（§4.2），否则 19.2% 可能偏高。

一个跨域的异常信号：anti-hardcode 断言在全批次 0 次命中

附录 B 逐域失败矩阵最右列 ANTI 全行 = 0（Total ANTI=0）。即所有 13 域、628 个 FAIL+ERROR 里，没有任何一个被 anti-hardcode 断言抓到。两种可能：(a) agent 确实不硬编码（好）；(b) anti-hardcode 断言太弱、或在 B 上没真跑（坏）。我造 case 时（见 rewrite_queue 里 Characterization-001 / SpiceSim StimLoopComplianceFix-001）都专门加了 cross-input guard（隐藏 B/B′ 反硬编码）。建议验证：抽 5 个含 ANTI 断言的 case，人工构造一个硬编码 A 的假提交，确认 check.py 在 B 上能 FAIL——若不能，则 ANTI=0 是判分器漏洞而非 agent 行为。

Q4. 下一步该补什么实验（按性价比排序，≥3 条）

E1 · 修 59/70 ERROR 的资产目录 bug 并重跑（table-stakes）

  • 目的：把 696-run 快照的 infra ERROR 清零，让 10.0% 的分母无可争议。
  • 方法：§5.1 已定位「59/70 = missing per-case asset directory」。用 eval_triage/05_batch_triage.py 列出 70 个 ERROR 的 asset 路径，逐个修 assets/<task_id>/ 目录与 hidden_manifest.json，重跑这 70 个（8 workers ≈ 2.5h）。
  • 数据：70 个 ERROR run 的 task_id 列表 + 修复后 status.jsonl。
  • 预计工作量：1–2 人日（修资产 + 重跑 + 重新出表）。
  • 预期能回答的质疑：「你的 696 快照 10% 是坏的，10.0% 不可信」→ 修后给出 ERROR-fixed Pass@1；若仍 ≈10% 则数字稳。

E2 · 100 任务分层子集上的 4-backbone 扫描（RQ3 方向性答案）

  • 目的：给 RQ3（模型扩展）一个方向性答案，回应全文最大软肋。
  • 方法：按 13 域 stratified 抽 100 任务（每域 ≈8，小域全取），对 GLM-5.2 / Kimi-K2.6 / DeepSeek-V4-Flash / Doubao-Seed-2.0-Pro 各跑一遍（同 Cline v3.0.51 / thinking=low / 2400s）。
  • 数据：4×100 = 400 run 的 status.jsonl，附 DeepSeek-V4-Pro 在同 100 任务上的对照（从 696 快照切出）。
  • 预计工作量：696/8 workers≈24h 全量 ⇒ 400 run ≈ 14h ≈ 2 机器日（含重试）。
  • 预期能回答的质疑：「单骨干 10.0% 是模型属性不是任务属性」→ 若 4 个 backbone 都在 8–15% 区间，则「编排天花板」叙事得到方向性支撑；若跨度大（如 5%–20%），则 RQ3 转为「模型选型重要」，论文叙事需改。全量 696×4 留 camera-ready。

E3 · 在 depth 7+ 两域做 thinking=low/medium/high 消融

  • 目的：解开「接地深度」与「推理预算」的混杂——2.9% 是因为接地难还是因为 low 思考档不够迭代？
  • 方法：physical_verify（73 runs）+ layout_aether（38 runs）共 111 任务，在 DeepSeek-V4-Pro 上各跑 thinking=medium 与 thinking=high（low 已有）。
  • 数据：2 域 × 2 新档 = 222 run。
  • 预计工作量：≈ 8 机器时（单骨干 222 run / 8 workers）≈ 1 机器日。
  • 预期能回答的质疑：「2.9% 是 low 思考档压出来的伪结果」→ 若 medium/high 后仍 ≈3%，则接地深度瓶颈坐实；若升到 ≥10%，则当前 2.9% 是推理预算伪影，论文需改口径。

E4 · 把「接地深度」从标注改成实测（救中心构念）

  • 目的：把 §5.2 自承的「annotation, not measured」改成测量量，破循环论证。
  • 方法：§5.3 已对 47 份 pilot 轨迹解析了每次工具调用。给每个 PASS run 算「实际 live EDA tool call 数」（eda_flow_*/pyAether_* 调用计数），与该 run 的域 pass 率做散点 + Spearman 相关。
  • 数据：47 run 的 (measured_depth, pass) 表 + 相关系数。
  • 预计工作量：解析器 trace_anatomy.py 已有，加一个 pass 标签 join ≈ 2 人日（难点：47 份 pilot 无判分，需先在对应 task_id 上跑 judge 补标签）。
  • 预期能回答的质疑：「接地深度是 post-hoc 标注」→ 若实测工具调用数与 pass 显著负相关，则构念从标注升级为测量；若不相关，则接地深度叙事需推倒。这是把全文最弱一环变最强一环的关键实验。

E5 · 100 任务 × 5 seed 的 Pass@1 方差与 Pass@5

  • 目的：给 10.0% 一个误差棒，回应「无方差」质疑。
  • 方法：与 E2 同一个 100 任务分层子集，DeepSeek-V4-Pro 跑 5 seed。
  • 预计工作量：400 run ≈ 1.5 机器日（可与 E2 调度复用子集）。
  • 预期能回答的质疑：「10.0% 没误差棒」→ 给出 Pass@1±std 与 Pass@5。

Q5. benchmark 本身该怎么演进

分布是否合理？—— 模拟偏科，数字偏少

评测快照的域分布（附录 B）：schematic_netlist 131、spice_sim 104、physical_verify 73、analog_context 55、digital 51、waveform 47、layout_virtuoso 40、layout_aether 38、verification 38、eda_other 38、pg_layout 28、characterization 28、pnr_signoff 25。§5.4 threats 已自承「top three domains hold 44.3% and digital-front domains 12.8%」。

  • spice_sim 过载且边际递减：104 runs(8.4%)，已是第二大域，再加 case 不会改变 8.4% 这个率。我侧实测 mc≥10 fresh 多为假阳性——建议给 spice_sim 设 cap（如 ≤120 eval runs），把造题产能转移到欠代表域。
  • 数字前端严重偏少：digital 51 + verification 38 + pnr_signoff 25 + eda_other 38 = 152/696 = 21.8%。这反映真实使用（数字工程师少用 cline，§2 已解释），但作为 benchmark 它削弱了「覆盖一次完整 tape-out 流」的宣称。建议：对数字前端采用 §附录 A 的放宽口径（mc≥15 + 扩展关键词），定向补 digital synthesis / SDC / UPF 任务。
  • pnr_signoff 仅 25 runs 但排第一（20.8%）：第一名的小样本使 7.1× 头条极不稳。建议：补 pnr_signoff case 到 ≥50 eval runs，稳住「榜首」的 CI。

要不要加新域？—— 建议加 2 个

  1. PDK QA / 模型文件校验：本轮我 scout 到的 nsf5a（rongjiez）正是 ModelQA（C++/Qt + openWave.pl 调 WaveView 读 .sw0 的 Id-Vd 扫描）——这类「 characterization 数据的 QA」任务有真实 trace 体量，但目前被散落到 eda_other 或未被采。它逻辑上介于 characterization 与 physical_verify 之间，且是真实高频工作流。建议：单列为第 14 域 pdk_qa，关键词加 modelqa/.sw0/idvd/itf/spectrum。
  2. AI 辅助 layout / 生成式布局：当前 layout_aether(2.9%)/layout_virtuoso(10.3%) 都是 GUI 驱动编辑，但产业界正在出现「LLM 生成 placement/tie-off 脚本」的新工作流，目前 13 域无对应。建议验证：在 698 机扫描里看是否有 genus/innovus place&route 脚本生成的高 mc session；若有，增设 ai_assisted_layout。

不建议加的：power/IR signoff（与 pg_layout 重叠度高，先归 pg_layout）；AMS 顶层验证（先归 verification，样本不足单列）。

13 域分类法本身的结构问题

当前按「设计阶段」切域，但 §5.2 的核心解释变量是「接地深度」。waveform（depth 6, 5.1%）其实是一个工具（WaveView）而非一个设计阶段，把它与 schematic_netlist 并列为「域」在分类学上不自洽。建议：在论文里补一个「按交付件类型」的二级切分（script / report / netlist / layout / measurement），它比 13 域更贴近 pass 率的驱动因素，且能解释为什么 characterization(script) 与 pnr_signoff(script) 都排前面。
