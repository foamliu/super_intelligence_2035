② 六个问题的回答

Q1. 我们最薄弱的论证环节是哪个？

结论：grounding-depth 假设是「灵魂但未实证」，单骨干是「最显眼的枪眼」——前者更致命，后者更易被打。

① 单骨干（最显眼，审稿人第一枪）。论文在 sections/4_experiments.tex:22 原句：

"A multi-backbone sweep (GLM-5.2, Kimi-K2.6, DeepSeek-V4-Flash, Doubao-Seed-2.0-Pro) is configured but not yet run to completion, so this paper reports a single-backbone evaluation; RQ3 is therefore discussed as an open question"— sections/4_experiments.tex:22

而引言贡献第 2 条把 10.0% 称为「ceiling」（1_intro.tex:32「a 10.0% Pass@1 ceiling」）。用一个骨干定义 "ceiling" 在方法论上站不住——审稿人会问：换个骨干是不是就 15% 或 5%？论文自己在 §5 threats（5_analysis.tex:137）也承认 "Claims about 'the best' or about model scaling are therefore not supported by our own data"。这是论文已自认但未补救的最大弱点。

② grounding-depth 假设（更致命，因为是灵魂论断）。论文的核心解释变量 grounding depth 是手工标注而非测量，sections/5_analysis.tex:46 原句：

"Depth is not measured; it is an annotation we assign per domain (a design choice, stated as such)."— sections/5_analysis.tex:46

而图注（5_analysis.tex:65）进一步承认 "this figure does not by itself establish a causal or monotone relationship"。这意味着论文的核心解释变量 = 域标签，与因变量（per-domain Pass@1）共享同一个分组来源，存在循环论证风险：你按域标 depth，又按域报 Pass%，再说 depth 解释 Pass%——这不是独立证据。审稿人会指出：任何一个与域共变的隐藏变量（任务复杂度、断言数、资产可移植性）都能顶替 depth。

③ 附录 A 的 per-shard 硬编码是「会反复腐化」的脆弱点（v13 修订：r417 已补齐当前差额，但结构性隐患仍在）。附录 A 的 per-shard 分解是手写硬编码，每轮造题都要人工同步：appendix/A_benchmark_details.tex:53-54 当前原句（r417 同步后）：

"As of 2026-11-12 the living build holds \Ntasks{} cases (A: 226, B: 273, C: 311, D: 347)"— appendix/A_benchmark_details.tex:53-54 (r417, 2026-11-12 09:37)

v12 写作时（09:37 前）这里还是 "A: 223, B: 270, C: 311, D: 341"=1145，而当时 \Ntasks=1155、jsonl 实际 A225/B273/C311/D346=1155，滞后 10 条。r417 刚把硬编码补到 226/273/311/347=1157 与 \Ntasks 对齐——但这恰恰证明了隐患：这是一个靠 4 个 shard agent 每轮手工同步、且历史上多次滞后 8–12 条的硬编码，下一次造题（A 或 D 再 +1）它又会立刻落后。审稿人若在两次造题之间读到论文，就会看到 \Ntasks 与附录加不上的不一致。修法不是「再补一次」，而是让附录 A 的 per-shard 数从 \Ntasks 自动派生（或干脆只写 \Ntasks 总数、把 per-shard 表移到会自动 regen 的日报/附录 B）。同时附录 A 仍有两处未完成的 TODO：appendix/A:11「[TODO: show one complete task]」（benchmark 论文没有完整 worked example 是硬伤），appendix/A:64「TODO(T12)：摘要/引言写 268 位工程师、42 台工作站，§2 写 698 台主机、224 位去重用户…三处口径需数据侧确认后统一」。这些是审稿人扫附录 5 分钟内必发现的扣分项。

（v14 live-validation）本节上述预言在本轮8 分钟内应验：v13 写作于 10:05:47，D shard commit 5d058949（10:14:06，CsvBackfillTableUpdate-001）把 D.jsonl 347→348 ⇒ committed 总和 1158，但 main.tex:43 的 \Ntasks 宏与 appendix/A_benchmark_details.tex:53-54 的硬编码（"D: 347"）至今仍是 1157/D347，无人同步。即论文若此刻被审稿人读到，\Ntasks=1157 与附录 "D: 347" 加不上 4 shard 实际的 1158——正是 v13 预言的「下一次造题又会立刻落后」。这把 Q1 ③ 的性质从「结构性隐患」升级为「已观测到的复现性 bug」：r417（09:37）刚补齐到 1157，r543（10:14）立刻又落后 1，两小时内两次腐化。据此 P2/P3 中「per-shard 硬编码改为从 \Ntasks 自动派生」的优先级应上调——这不是「锦上添花」而是「止血」，否则每轮造题都在制造新的不一致窗口。根治建议进一步细化为：\Ntasks 宏本身也应由 build 脚本从 4 shard jsonl 行数自动生成（wc -l → 写入 main.tex），而非由某个 shard agent 手工 bump。

Q2. 10.0% 这个数字站得住吗？

结论：作为「单骨干 · 单 thinking 档 · decided 分母」的描述性数字站得住；作为「编排天花板」的论断站不住，需补对照组。

站得住的部分：三分母稳健性做得不错——4_experiments.tex:66 脚注给出 10.0%/9.9%/8.9% 三个估计量，相差 ≤1.1pp，CI 重叠，且明确声明 "no conclusion below depends on the choice of denominator"。这是教科书式的稳健性辩护，审稿人很难从这里下手。

站不住的部分（需补对照组）：

  1. 单骨干（见 Q1）。10.0% 是 DeepSeek-V4-Pro 一个点的观测，不是天花板。补多骨干（哪怕只在 100-case 子集）能把「点观测」升级为「跨骨干区间」。建议验证而非「已验证」。
  2. 单 thinking 档。全文只用 thinking=low（4_experiments.tex:19），无任何 thinking-budget 消融。审稿人必问「你试过 medium/high 吗？也许 10% 是因为没给够推理预算」。这是零成本可补的对照（同一子集换 thinking 档重跑），不补会被判「实验设计不完整」。
  3. 70 个 ERROR 的处置。论文说 ERROR 是 "harness/tool infrastructure"（4_experiments.tex:34 表注），但 §5 失败分类（5_analysis.tex:13）细查后发现「59/70 ERROR 为单 case 资产目录缺失」——这是benchmark 构造缺陷（资产没配齐）而非模型失败。把 59 个资产缺失的 run 排除出分母可辩护（它们确实不评判模型能力），但审稿人会反问：10% 的 case 资产配不齐，benchmark 的工程成熟度是否足够发布？这需要一段「资产缺失已修复/已加资产完整性预检」的说明，而非单纯排除。
  4. UNKNOWN 比例。失败分类的工具级 UNKNOWN = 119/696 = 17.1%（5_analysis.tex:13），其中 FAIL-with-submit UNKNOWN = 49/696 = 7.0%。17% 的 run 无法被工具分类，对「systematic failure taxonomy」的宣称是个缺口。附录 B（appendix/B:87）说 Cohen's κ「deferred to camera-ready」——人机一致性也没报。审稿人会问：你的 taxonomy 连 17% 都分不出，怎么声称 systematic？

最小补救：100-case 分层子集上跑 thinking∈{low,medium} × backbone∈{DeepSeek-V4-Pro, GLM-5.2} 的 2×2，再把 ERROR 中「资产缺失」子类单独报一列「修复后重跑 N 个，M 个转 PASS」——这两件事用 ~2 机器日，能把 10.0% 从「单点」变成「区间 + 已知分母敏感性」。

Q3. B 线视角的独特输入（spice_sim / characterization）

结论：B 是 case 数最多的 shard 却在论文里被「拆成两个深度档」而无单独讨论；spice_sim 的 trace 保真度是论文「真实轨迹」卖点最薄弱的一环。

① B 域两领域内部异质，2.3 倍跨度。表 2 显示 spice_sim 8.4%（depth 5）与 characterization 19.2%（depth 1–2）落在同一个 shard。论文把 characterization 归入「standardized-flow / depth 1–2」（5_analysis.tex:52「pnr_signoff, characterization, eda_other: 19.4%… largely a script or tcl template」），但 characterization 是SPICE 域任务（SiliconSmart .lib 提取、corner sweep）——它的 19.2% 来自「脚本模板化」而非「非 SPICE」。这暴露 grounding-depth 分组的一个隐患：同一 area group（spice/char）跨 depth 1–2 与 5，说明 depth 标注与 area group 正交，论文按 area group 组织 shard 却按 depth 组织分析，两套分组互相切割，读者很难形成连贯心智模型。

② characterization 19.2% 不稳健。仅 26 个 decided run、5 PASS。Wilson 95% CI 约 [8.5%, 36.7%]——区间宽度 28pp，几乎覆盖 spice_sim 到 pnr_signoff。论文把它列为「第二高领域」并写进引言（1_intro.tex:21「characterization 19.2%」），但这个数字一翻就变。补法很便宜：53 个 characterization case 只评了 28 个，把剩余 ~25 个评完，decided n 从 26 → ~50，CI 大幅收窄。建议验证。

③ spice_sim 拖低总体，且失败模式以「脚本崩溃」为主。spice_sim 是活集最大域（220 case，19.0%）也是评测第二大域（104 run）。Pass@1=8.4% 低于总体 10.0%——spice_sim 拉低了头条数字。失败分类（appendix/B:120）显示 spice_sim：NOSUB 8 · RT 26 · SEM 48 · UNK 12。RT（ASSERT_RUNTIME，候选脚本崩溃/非零退出）= 26，是 13 域里第二高（仅次于 schematic_netlist 26）。这反映 spice_sim 的真实难点：候选要解析二进制波形（.tr0）、写正确的 HSPICE .measure、处理工程后缀（583.3333m）——脚本能跑通本身已是高门槛，而非「语义对不对」。论文 §5（5_analysis.tex:33）把 spice_sim 归入「semantic failures dominate medium-grounding domains」，但实测 RT 占比 26/94=27.7% 说明运行时崩溃才是 spice_sim 的主因之一，论文的「semantic dominant」叙事对 spice_sim 不够精确。

④ trace 保真度：spice_sim 是「真实轨迹」卖点最薄弱的一环（基于本人 273 条 B case 的造题经验）。论文摘要（0_abstract.tex:4）宣称 "each derived from real Cline coding-agent traces"，引言（1_intro.tex:13）"Each task is derived from an actual multi-turn session"。但spice_sim 的 A 档（trace-faithful，用真实 trace 原始资产）几乎都不可行：真实 trace 依赖私有 PDK（.inc /proj/.../model/）、二进制波形（.tr0）、私有项目树（/rundata/... Permission denied）。我的 273 条 B case 中，绝大多数是 B 档（synthesized）——用可移植的 level-1 NMOS HSPICE deck 替换真实 PDK，保持真实任务意图与断言结构，但资产是合成的。论文没有披露 A档/B档的逐域比例。审稿人若问「你的 spice_sim 任务到底有多『真实』」，论文目前无法回答。这不是错——保密约束使 A 档不可行——但不披露就是隐患。建议：给每条 case 打 trace_fidelity ∈ {faithful, synthesized} 标签，附录加一张「per-domain A档/B档 比例表」，并讨论合成是否系统性改变难度（合成 deck 更可移植 → 也许更容易？需验证）。

⑤ B 域供给瓶颈（影响「living benchmark」宣称）。本轮 mc-matrix 取证：mc10.fresh=0（1105 池，A 未换 1109）；rescan_1112 的 42 条 genuine unledgered 中无一满足 B 域过滤口径（spice 工具数 ≥10 ∧ 密度 ≥35%），最强候选 lvack 也只有 hspice:8（<10）。我过去 16 次 peek 仅 2 CLEAN（ikfrw / y9y0f，均来自唯一 spice-heavy 用户 joeyl），最近 10 peek 全 0 CLEAN。本轮对 42 条余量中 spice 关键词数最高的两条做了实测 peek（v9zug hspice:14、2gxuy hspice:20，是余量里仅有的 spice≥10 者）：v9zug 实为 .cline/apps/kanban/ 看板应用会话（根本不是 cline 编码会话，关键词命中来自看板卡片文本）；2gxuy 首条用户消息是「怎么在当前服务器中打开 vscode」，工具链全是 list_allowed_files / search_codebase / read_files，零仿真——即余量中 spice 关键词最多的候选是一个 how-to 咨询。这说明关键词计数系统性高估 spice 相关性：hspice:20 的会话可以和 SPICE 仿真毫无关系。spice_sim 的可移植 L2/L3 trace 供给已近枯竭，benchmark 在 spice_sim 上的增长已受 trace 可得性而非造题产能限制。论文 §2（2_benchmark.tex:77）称 "living benchmark currently holds \Ntasks curated cases" 并强调持续增长，但 spice_sim 这条增长曲线正在变平——这是「living」宣称的一个域特异性隐患，论文应明确哪些域仍在增长、哪些已收敛。

④ 风险与反对意见（预判审稿人反驳 + 我们的答）

反驳 1：「单骨干，10.0% 不是 ceiling」

审稿人会问：你只用 DeepSeek-V4-Pro，凭什么称 ceiling？换 GLM-5.2 可能 15%。

论文现况：§4:22 已自认 single-backbone，RQ3 开放；但引言 §1:32 仍用 "ceiling" 一词。

我们的答：(1) 接受批评，把 "ceiling" 改为 "observed Pass@1 under a single frontier backbone"，删除「天花板」暗示。(2) 补 P1 的 100-case 多骨干析因，给出跨骨干区间。若区间窄（如 8–12%）→ 强化「task-type 主导」叙事；若区间宽（如 5–18%）→ 诚实报告「backbone 轴仍有显著效应」，RQ3 转为实证发现而非开放问题。两种结果都对论文有利（前者强结论，后者新发现），不补才是最大风险。

反驳 2：「grounding depth 是循环论证」

审稿人会问：depth 是你按域手工标的，Pass% 也按域报，两者共享分组——这不是独立证据。任务复杂度、断言数、资产可移植性哪个不能顶替 depth？

论文现况：§5:46 已声明 "a design choice, stated as such"；图注 §5:65 承认 "does not by itself establish a causal or monotone relationship"。诚实但未补救。

我们的答：(1) 接受「标注非测量」的定性，但补 P3 的实测化：从 50 case 日志数实际 live tool-call 次数，与 depth 标注做 Spearman 相关。若 ρ > 0.7，说明标注与实测一致，循环论证指控失效；若 ρ 低，说明标注需修订，但实测 depth 仍是更强的解释变量。(2) 补一个混杂变量检查：回归 Pass@1 ~ depth + 断言数 + 资产文件数，看 depth 系数是否稳健。建议验证。

反驳 3：「你的 spice_sim 任务不真实，资产是合成的」

审稿人会问：摘要说 "derived from real Cline traces"，但 spice_sim 的 PDK 是私有的，你的资产肯定是合成的——那这还是「真实轨迹」benchmark 吗？

论文现况：§9 reproducibility（9_reproducibility.tex:7,27）诚实承认 traces 与 PDK 不能发布，但未披露 per-domain 合成比例。

我们的答：(1) 精确区分「任务意图真实（prompt 源自真实工程师会话）」与「交付资产可移植化（私有 PDK → 合成 deck）」——前者是 benchmark 的认知来源，后者是可发布性的工程妥协。(2) 补 P2 的 trace_fidelity 披露表 + 配对比较：若 faithful 与 synthesized 的 Pass@1 无显著差异，则合成不系统性偏置难度，卖点的实质成立；若有差异，诚实报告并讨论方向。关键是不披露才是隐患，披露了反而是方法论透明度。

反驳 4：「70 ERROR 排除使分母偏乐观」

审稿人会问：你把 70 ERROR 排除出分母，其中 59 个是「资产缺失」——这到底是模型失败还是你 benchmark 没配齐？如果是后者，10.0% 是虚高。

论文现况：§4:66 脚注已给三分母（10.0/9.9/8.9%），但未单独拆「资产缺失」子类。

我们的答：(1) 59 个资产缺失是 benchmark 工程缺陷而非模型失败，排除出「模型能力分母」是正确的；但应单独列「benchmark 成熟度分母」。(2) 补 P3 的 ERROR 修复重跑：修齐 59 个 assets/ 后重跑，报告「X 个转 PASS / Y 个转 FAIL / Z 个仍 ERROR」。若修复后 10.0% 几乎不变，证明排除正当；若变动大，则更新头条数字。建议验证。

反驳 5：「domain 排序不稳健，7.1× 是点估计」

审稿人会问：pnr_signoff 20.8%（CI [9.2,40.5]）与 physical_verify 2.9%（CI [0.8,10.1]）区间重叠，7.1× 跨度可能是噪声。

论文现况：§4:77 已预判——"should be read as descriptive rather than established"，并明确 "What is robust is the ordering"。这是很好的预防性叙事。

我们的答：维持现有叙事，不再用 7.1× 作为强论断。补一个跨骨干的 ordering 一致性检验（P1 的副产品）：若 4 个骨干的 domain ranking 的 Kendall τ 都 > 0.7，则「ordering 稳健」从单骨干描述升级为跨骨干实证。已有的防御已足够，补 P1 后更强。

反驳 6：「可复现性不足，核心 trace 不发布」

审稿人会问：你说 trace 是 IP 不能发布，那外部研究者怎么复现？这不过是公司内 benchmark。

论文现况：§9 已有分层发布策略（harness 开源、sanitized 子集、mock-EDA、judge-only mode）+ 开源 EDA 路线图。

我们的答：分层发布是工业 benchmark 的标准做法（论文已引 rao2026sap, sulthanpete2026nyris）。强化三点：(1) mock-EDA 模式必须实际可用（不只是宣称），附一个外部人按文档跑通的截图；(2) sanitized 子集的规模应明确（当前未给数字——建议至少 100 case 跨 13 域）；(3) 开源 EDA 路线图给一个最小可跑 prototype（哪怕只映射 2 个域到 ngspice/OpenROAD），证明路线可行而非画饼。
