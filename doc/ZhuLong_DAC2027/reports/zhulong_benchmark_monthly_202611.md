## 构建思路 · 与字节对比

> 大领导重视与字节的合作，此节说明长鑫与字节在 EDA Agent 评测上的路线差异与共建可能。

| | 路线 | 侧重点 |
|:--|:--|:--|
| **字节** | 强模型 + 单 Agent 端到端 | 少量极难 case 探 Spec2GDS 全链路上限 |
| **长鑫** | AI 是人的助手 | 大量短链 case 验工程可用性——"一个萝卜一个坑"，责任主体不消失，Agent 让每个坑里的人更快更稳 |

**两条路线非互斥，是不同抽象层级**——可共建分层 benchmark：

- **L1 短链原子**（岗位内助手）——对应本报告三层体系的 L1/L2，长鑫侧重
- **L2 中链组合**（跨坑协作，责任链可审计）——长鑫与字节共建区；除共建与依赖字节外，还可调研**开源评测 + 开源 EDA 软件**路线（如 Yosys/OpenROAD/Magic 等开源工具链 + 公开评测协议），降低对外部合作的单点依赖，提升评测体系的自主可控性与可复现性
- **L3 极难端到端**（能力上限探测）——对应本报告 L3，字节侧重；同样可探索开源 EDA 全链路（如 OpenROAD RTL-to-GDS）作为端到端能力探测的补充赛道

本月 EDA-Flow-Bench 的 500 任务集偏长鑫路线（大量真实工程短链 case，责任主体可审计）；与字节的合作空间在于：把长鑫的真实 Trace 与字节强模型端到端能力探上限结合，共建中链组合层（L2 共建区），形成既有工程可用性、又有能力上限探测的完整评测体系。同时，L2/L3 层可并行调研开源 EDA 软件路线作为补充，确保评测体系在合作之外有自主可控的备选路径。



## 本月主要进展

- **进展 1：评测框架搭建完成。** 跑通"题目 → agent 执行 → `check.py` 判分 → 报告"全链路；改进沙盒以支持 **Linux 命令执行 \+ session 概念 \+ 并发**，为多 Case 并行评测提供基础。500 任务主评测集已成形（4 shard 并行造题，覆盖 13 个 EDA domain），Full 集 2,186 个 case。

- **进展 2：真实 Trace 挖掘 Case。** 基于烛龙在长鑫 PDC / TYA 团队上线后的真实会话 Trace，挖掘并构建了一批 Case（Lite \+ Full）。针对烛龙 \+ 若干 LLM（doubao\-pro / lite / mini \+ deepseek\-v4\-pro）跑评测，**可跑出符合预期的结果**：deepseek\-v4\-pro 3\-run **20\.85±1\.03%**（r1=21\.78/r2=19\.75/r3=21\.02，3/3 clean）/ doubao\-pro 3\-run 10\.18±1\.18% / doubao\-lite 4\.68±0\.77% / doubao\-mini 2\.39±0\.19%；doubao\-pro 对齐用户基准 10\.5%，验证评测流程正确。**McNemar 配对检验**（deepseek vs doubao\-pro，majority\-vote 逐题对齐）：b=69, c=2, p≈0\.0000，**高度显著**，Δ=+10\.67pp（约 2\.0× gap）。

- **进展 3：人工核验启动。** Case 的人工核验正在进行，逐题审查任务形态、资产完备性、断言覆盖度。



## 当前问题

> 评测集仍处于初步构建阶段，以下三大问题需在后续迭代中解决：
> 
> 

- **问题 1：断言数量虽充足，但难度不足。** 当前每 Case 的 `check.py` 断言条数达标（≥8 条，多在 15\-16 条），但多数断言停留在"交付物存在 / 脚本能跑 / 格式正确"等表层检查，**对 agent 是否真正理解电路语义、是否正确处理边界条件的深度断言不足**。导致部分 Case 即使 agent 行为有缺陷也能蒙混过关，判分区分度不够。

- **问题 2：受权限限制，部分 Case 资产无法访问。** 真实 Trace 中的部分 Case 涉及内部工艺数据 / 受限设计资产，agent 沙盒无法访问原始资产目录。当前采取"导出可离线复跑样本"的折中方案，但**部分 Case 的资产完备性受损**，影响评测真实性。

- **问题 3：脚本类 Case 应从静态评估转向 EDA 服务器实跑。** 当前脚本类 Case 在开发服务器做静态评估（跑 `check.py` 看输出 JSON 字段对不对），但真实工程中脚本要在 **EDA 服务器上实跑**（调真实 pyAether / SKILL / Tcl 工具链）。静态评估能验证"脚本写对了"，但**验证不了"脚本在真实 EDA 环境里能跑通"**——后者才是评测本意。



## 风险与阻塞

- **风险 1：人工核验速度较慢。** 500 任务逐题人工核验工作量大，当前核验进度跟不上造题速度，Case 入库后积压等待核验。

- **风险 2：业务理解有限，断言质量存在风险。** 本人与几位实习生对电路设计各领域经验有限，**恐怕无法写出高质量的断言**——尤其是 analog / waveform / characterization 等深 domain 的语义级断言。这是问题 1 的根因，也是后续评测集质量的主要风险。
