三、为什么选 40 题子集 + 158 题全量双轨

40 题子集（复用 compaction_subset_40.txt）：长轨迹题，主 agent 探索多、可能受益于 subagent 拆分。用于主实验（每臂 3 轮，powered 检出 10pp）。
158 题全量（每臂 1 轮）：验证外部效度——简单题（API<5）subagent 是否反而有害（拆分开销 > 收益）。用于 §6 亚组分析。
预期：40 题子集（复杂题）subagent 可能有正效应；158 题全量（含简单题）subagent 可能有负效应或无差异。如果 158 题全量降了但 40 题升了，说明 subagent 只适合复杂任务。

六、Subagent 调用率风险与缓解

✅ P0 已验证：核心风险降级——原计划书标注"主 agent 可能不调用 subagent"为高概率风险。P0 smoke test 证实：在 task prompt 末尾加强提示「必须先调用 subagent_researcher」后，主 agent 确实调用了 subagent。风险从"高"降为"中"——强提示是否在 40 题批量场景下稳定生效仍需 P1 pilot 验证。
关键发现：configured agent 文件必须用 .yaml 扩展名（cline isYamlFile() 只认 .yml/.yaml）；tools 字段必须用完整 MCP 工具名 pyAether_MCP_server__search_apis（非 search_apis），否则 subagent 无工具可用。

6.1 缓解措施

措施适用臂方法风险
强制注入 system prompt 提示A1在主 agent system prompt 末尾加：「遇到 API 数 >5 的任务，必须先 spawn researcher subagent 查询 API 文档，再自己写代码」提示可能被忽略
configured agent 工具描述B1-B5/C1/C2researcher.md 的 description 写「必须在写代码前调用此 agent 查询 API」，cline 会把 description 放进工具列表主 agent 仍可能跳过
P1 pilot 验证全部P1 跑 8 题 × 4 臂，统计 subagent 调用率；如果 < 20%，升级到强制注入（改 system prompt 加硬性要求）—
最坏情况：强制 spawn全部如果 P1 调用率 < 20%，在 harness 层注入「任务开始时自动 spawn researcher，查完 API 后主 agent 才开始写代码」失去主 agent 自主性，变成"强制流水线"
P1 pilot 的 go/no-go 判据：subagent 调用率 ≥ 30% → 进 P2；20-30% → 升级提示后重跑 P1；< 20% → 改用强制 spawn harness（H1 变为"强制流水线 vs 单 agent"，而非"自主 spawn vs 单 agent"）。

九、预注册决策规则

在看到数据前，预先声明判据（避免 p-hacking）：
  1. H1：A0 vs A1/B1，McNemar discordant ≥ 6 vs 6（40 题），方向一致 → "subagent 有显著效应"；否则 → "无显著差异"。如果 A1（自主 spawn）调用率 < 30%，H1 结论改为 "主 agent 不会自主使用 subagent，需强制注入"。
  2. H2：B1 vs B2/B3/B4/B5 两两 McNemar，Δ ≥ 3pp 且 bootstrap CI 不跨 0 → "该弱基座有显著影响"；5 点梯度回归 R² > 0.7 → "基座能力与 Pass@1 呈剂量-反应"；梯度中最弱端（B5 lite）per pass token 降 ≥ 20% → "弱基座省成本"。如果 B3（doubao-pro）与 B1（同基座）无显著差异 → "subagent API 调研对基座能力不敏感，可用任意 pro 级模型"。
  3. H3：C1 vs C2，subagent 完成率差 ≥ 10pp → "maxIter=5 过紧"；C2 vs B2（maxIter=30 vs 15）无差异 → "maxIter=15 足够"。
  4. 实验无效判据：P1 pilot subagent 调用率 < 20% 且强制注入后仍 < 30% → "cline 3.0.51 subagent 机制不适用于 PyAether 单函数任务，需换多步骤任务集"。

十三、结论：为什么值得做

  1. 填补空白：前序 30 轮 + compaction 6 轮 trace 显示 subagent 从未被使用——这是 cline 能力栈里唯一未被验证的维度。
  2. 工程价值：如果 subagent 有正效应（尤其复杂题），意味着 EDA agent 应该用"主 agent 写代码 + subagent 查 API"的分工模式；如果无效应或负效应，说明单 agent 足够，省去 subagent 复杂度。
  3. 成本价值：H2（弱基座 subagent）如果成立，意味着 API 调研可以用 flash/mini/lite 级模型（省 80%+ token），只有写代码用 pro 级——这是生产部署的降本路径。doubao 三档（pro/mini/lite）提供跨厂家验证，避免"只有 deepseek flash 省钱"的单厂家结论。
  4. 方法学价值：subagent 的 SpawnAgentOutput.usage 可精确采集 token（不像 compaction 漏计），是首个能做"主/子 token 分拆"的实验。
  5. DAC 论文素材：subagent 消融 + compaction 消融 + thinking 消融 + 语言消融 = 4 轴完整消融矩阵，覆盖 cline 全部可调维度。
