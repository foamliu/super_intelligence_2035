1. 背景：两种压缩机制到底差在哪

来源：cline 源码 compaction.ts / basic-compaction.ts / agentic-compaction.ts 与 CLI --compaction（4.x）。本仓库已有 trace 分析：reports/report_zhulong_auto_compaction_analysis_zh.html。

维度basicagentic（当前默认）
触发每个模型请求前 prepareTurn 钩子：估算 token ≥ maxInputTokens × 0.9（COMPACTION_TRIGGER_RATIO）即触发；maxInputTokens 默认 128K（仅给 contextWindow 时按 90% 折算）。实测触发点约 100K token。
压缩目标目标 = 触发阈值 × 0.7（DEFAULT_TARGET_RATIO）；长会话（≥5 轮 user-assistant 且 maxTokens < 预算）目标为预算的 50%。另用上一轮 provider 实际输入 token 修正估算偏差（上限 4×）。
实现纯规则、零额外 LLM 调用；保留「最新 user prompt + 最近 3 条 assistant 回复」，其余折叠；完全确定性额外一次摘要 LLM 调用；保留 preserveRecentTokens 尾部 + 结构化摘要（目标 / 当前状态 / 关键决策 / 下一步）；非确定性
回退本身就是回退路径摘要调用失败或空 → 自动回退 basic
溢出恢复✅ 唯一保证路径❌ 不用于溢出恢复（溢出永远走 basic）
元数据kind=compaction + SYSTEM_NOTICEkind=compaction_summary + 结构化 details
遥测事件task.compaction_executed：strategy / mode / messagesBefore-After-Removed / tokensBefore-After-Saved / triggerTokens / maxInputTokens / durationMs；另有 task.compaction_skipped、task.compaction_budget_emergency
开关cline --compaction agentic|basic|off（默认 agentic）；配置项 compaction.enabled。⚠️ 训练机现用 cline 3.0.51，须先验证该 flag 是否存在（见 §5 P0）。

1.1 为什么这个对比值得做（既有证据）

  • 本仓库 6,162 个 session 中只有 745（12.1%）触发过压缩，压缩比中位数 13.98%，压缩主要发生在任务进度 ~88% 处，压缩后平均再工作 19 条消息。
  • 压缩过的 session TIMEOUT 率 11.1% vs 未压缩 0.04%（相差两个数量级）——压缩与「长任务失败」高度相关，但无法区分是「任务本来就长」还是「压缩丢了状态」。
  • 因此：压缩机制的价值只有在「触发压缩的长任务」上才能被看清；全量 158 题会被 88% 未压缩任务稀释 → 亚组分析是必需的，不是可选项。

2. 研究问题与假设（预注册，先写死再跑）

编号研究问题假设（方向性）判据
RQ1总体上，agentic 相对 basic 的 Pass@1 差多少？H1：agentic 更高，Δ ≥ +3pp（语义摘要保住目标/状态，减少「忘了做到哪」）3 轮均值；配对 McNemar 双侧 p<0.05 且 |Δ|≥3pp
RQ2优势是否集中在长会话/触发过压缩的任务？H2：交互项为正——轨迹越长，agentic 相对 basic 的优势越大亚组（是否压缩 × 轨迹长度四分位）Δ 与 95% CI；交互项方向一致
RQ3agentic 的额外摘要调用值得吗？H3：agentic 每题 token / 墙钟更高；每 +1pp 的边际成本低于团队可接受阈值（暂定：每 +1pp ≤ 3% 额外 token）tok/题、墙钟/题、batch 墙钟；增益/成本比表
RQ4两臂的失败模式是否不同？H4：basic 的 context-loss 型失败占比更高；agentic 的失败更多是能力型（题目本身难）失败分类表 + 5 个可测信号（见 §4.3）
RQ5压缩本身是否引入新风险？H5：agentic 摘要若质量差（缺 4 要素），其会话失败率不低于 basic摘要 4 要素覆盖率 × 通过率交叉表
预注册纪律（防 p-hacking）：
① 主终点唯一 = 3 轮 Pass@1 均值（全 158 题，ITT）；
② 亚组（压缩会话 / 长轨迹 / domain）只作次要终点，必须同时报效应量 + 95% CI + 样本量，不得用亚组结果替代主终点；
③ 所有轮次全部入表，不许剔除「异常轮」；确有 infra 故障须单列并说明，同时给「含/不含」两版；
④ 跑之前不改判据；要改必须在报告变更记录里写明「何时、为何、改前改后」。

3.3 样本量与功效

  • 主分析（ITT）：158 题配对。若 discordant 比例 ≈25%（basic 独过 12.5% / agentic 独过 12.5%），3 轮均值可检出 ~10pp 差异（McNemar 双侧 α=0.05、power≈0.8）。不足 3pp 的差异本设计不承诺可检出——报告须如实说明。
  • 亚组（触发压缩的会话）：按既有 12.1% 压缩率，单轮约 19 题/臂；3 轮合计约 57 对。若实际 <60 对，触发扩展预案：每臂加跑到 5 轮（+2 轮 ≈ +7.5h）。
  • 不做事后加样：扩展只在「亚组 n 不足」这一事先写明的条件下执行，并在报告中披露。

3.4 可选探索臂（非主结论）

压缩事件天然稀缺。若想提高压缩发生率，可在 exploratory 臂里把触发阈值下调（如 COMPACTION_TRIGGER_RATIO 可配则设 0.5），制造「提前压缩」压力测试；该臂结论单独标注 exploratory，不参与 RQ1 主判据。若该常量不可配，则不做，不得改源码强改（会破坏跨版本可比性）。

4.2 压缩事件怎么取（两路互证）

  • 落盘：每个 session 目录下 *.compaction.json（含 metadata.kind = compaction 或 compaction_summary、source_message_count、messages[]）；与 *.messages.json 并列。
  • 遥测：task.compaction_executed（strategy/mode/messagesBefore-After/tokensBefore-After-Saved/triggerTokens/maxInputTokens/durationMs）。若 CLI 不吐遥测，则以 compaction.json 为准，并在报告标注「遥测不可用」。
  • 注意：compaction.json 只保留最后一次快照（userRunSpan），多次压缩会低估次数；报告须写「观测下限」。

4.3 context-loss 失败信号（H4 的测量口径）

从 trace（messages.json 的 tool_use / tool_result）自动统计，命中任一项记 1 分，≥2 分判为「context-loss 型失败」；同时保留人工抽检 20 例做校准。

#信号检测规则（示例）
①重复读取同一文件且无新信息同路径 Read/read_files ≥3 次，且后续未基于其内容产生编辑
②重跑已成功的命令完全相同的 command 字符串出现 ≥2 次，且第一次 exit=0
③与已确认事实矛盾断言与之前 tool_result 中的输出相冲突（关键词/数值级比对）
④遗忘已写入的文件对已创建文件再次 create（非编辑），或声明「文件不存在」但此前已 write
⑤重复同一失败同一失败命令/断言连续 ≥3 次，中间无新信息

6. 分析计划（跑之前定好）

  1. 描述统计：每臂每轮 Pass@1、均值±std；逐题矩阵（158 × 6）落 TSV。
  2. 主检验：McNemar 精确检验（按轮配对后「题级多数票」；同时给「每轮各自配对」3 组结果，避免聚合口径争议）。
  3. 置信区间：按题 bootstrap 10,000 次，报 Δ 的 95% CI（配对重采样）；同时报 Wilson CI（单臂绝对通过率）。
  4. 交互/亚组：分层表（是否触发压缩 × 轨迹长度四分位 × domain）；如环境允许，拟合 pass ~ arm * log1p(tool_calls) + (1|task) 混合效应 logistic，报交互项。
  5. 失败分类：infra / timeout / context-loss / capability / format；两臂四格表 + 卡方或 Fisher。
  6. 成本：tok/题、墙钟/题、batch 墙钟；计算「每 +1pp 的边际 token 成本」。
  7. 多重比较：主终点单一不校正；次要终点 Holm；探索臂只报描述统计。
  8. 可复现：脚本 analyze_compaction_ablation.py + 原始 results/cost 一并入库；报告数字须能由脚本一键复算。
报告必须正面回答的三个问题：① agentic 是否带来 ≥3pp 的稳定增益？② 增益是否只存在于长会话？③ 综合 token/墙钟，默认策略应该选哪个？——三个问题都要给「是/否/证据不足」的明确结论，不许只列数字。

7. 风险与缓解

风险概率缓解
cline 3.0.51 无 --compaction中P0 用 --help 验证；不支持则升级到支持版本（记录版本），两臂同版本，并加做 10 题校准确认与历史基线不冲突
agentic 摘要额外调用触发额度 429中每轮前 quota probe；429 时等待恢复（不降并发）；摘要调用与主调用同基座，额度消耗计入成本表
压缩事件过少（12%）→ 亚组功效不足高预注册扩展预案（亚组 <60 对 → 每臂 5 轮）；主分析仍用 ITT；报告明确「压缩亚组为探索性」
非确定性（agentic 摘要每次不同）高3 轮取均值 + 报 std；结论只在「跨轮方向一致」时下；不做单轮结论
多次压缩不可见（只留最后快照）中以遥测累计为准；无遥测则报「观测下限」，不臆测次数
沙盒/端口被 designflow 占用中起跑前探测 8664/8665/8653/8669；与 designflow 串行，不并发
基座/上下文窗口混用中每轮记录 model id + maxInputTokens；两臂不一致则该轮作废重跑（并在报告说明）
与轴 A/B 实验互相干扰低串行执行；pgrep 有 run_cline_script 则不起跑
与 benchmark 污染低benchmark 文件 sha256 固定；不修改题库/评分器

10. 决策规则（跑完怎么用）

结果模式结论与动作
Δ ≥ +3pp 且 p<0.05，长会话亚组同向agentic 设为默认；论文/报告写「语义摘要保住任务状态，长会话收益最大」；保留 basic 作为溢出恢复路径
Δ 在 (−3,+3) 且 CI 跨 0证据不足；默认维持 agentic（成本可接受），报告写「未观测到显著增益」，不做宣传性表述
Δ ≤ −3pp查原因（摘要质量/额度抢占/非确定性）；建议 basic 默认，agentic 仅用于明确需要语义摘要的场景
亚组显著但总体不显著结论限定「长会话场景 agentic 更优」；给工程建议（按上下文占用率自适应切换），另开实验验证

11. v2 效率修订（覆盖 §3 / §5 / §9 的规模）

11.1 定量效率审计：v1 为什么不行

项v1（自然 128K，158 题 × 6 轮）v2（强制 32K，40 题 × 6 轮）说明
总 run 数948（158×6）240（40×6）题量 40/158 ≈ 25%
纯跑墙钟~22h~5.6h按 3.7h/158 题线性折算
预期压缩暴露~19 题/臂/轮（12.1%）≥28 题/臂/轮（≥70%，pilot 校准）暴露题 = 能回答机制问题的样本
若压题增益 +10pp 的 ITT Δ≈ +1.2pp（< 判据 3pp）≈ +7pp（≥70% 暴露）v1 被 88% 未压缩任务稀释
按 v1 判据的预计结论「证据不足」（即使机制有效）可判定这才是 v1 的真问题：不是慢，是系统性偏 null
结论：12% 触发率下，任何「全量 158 题 × 小轮数」的设计都在给 88% 无关任务付算力，且把机制效应稀释到判据以下。必须提高“事件率”而不是提高轮数。

11.2 v2 设计

项取值
Regime强制压缩：把该模型的 maxInputTokens 从 128,000 调到 32,000（pilot 可下调至 24K/16K），则触发点 = 0.9 × 32K ≈ 28.8K；两臂完全相同
任务集40 题“长轨迹倾向”子集：从 PyAether 158 的历史 trace（30 轮、6,162 session）按「上下文峰值 / tool_calls / 是否曾触发压缩」排序取 Top-40，按 domain 分层；固定清单入仓库（run/compaction_subset_40.txt），两臂同一清单
臂--compaction basic vs --compaction agentic（每臂 3 轮，ABBA 交替）
暴露目标每臂每轮 ≥70% 任务至少触发 1 次压缩；否则按 §11.4 调档
主终点该 regime 下 3 轮 Pass@1 均值（ITT；此时 ITT 已高暴露，不再被稀释）

11.3 可调旋钮（已在本机 cline 4.1.26 实证，不需改源码）

旋钮位置 / 用法作用
--compaction agentic|basic|offCLI 参数本实验自变量
compactionStrategy / compactionEnabled<data-dir>/settings/global-settings.json持久化默认值（可被 CLI flag 覆盖）
maxInputTokens / contextWindow<data-dir>/settings/models.json 的 providers[<provider>].models[<id>]提高压缩事件率的关键旋钮；生效预算 = min(maxInputTokens, contextWindow)
--data-dir <path>CLI 参数每臂独立配置目录（两臂只差 strategy，其余文件完全一致，便于审计）

11.4 Pilot 与自适应调档（P1）

观测（8 题 × 2 臂）动作
压缩率 < 60%下调 maxInputTokens：32K → 24K → 16K（每次只动这一个数），直到 ≥70%
压缩率 > 95% 且 Pass@1 < 20%说明压得太狠（任务不可解）→ 回调到 48K，目标压缩率 60–80%
两臂压缩率差 > 15pp检查是否 strategy 未生效（basic 的 kind 应为 compaction，agentic 为 compaction_summary）；未生效则先修配置再跑
pilot 全部通过锁档（把最终 maxInputTokens 写进轮级元数据），进入 P2

11.5 统计（v2）

  • 40 题 × 3 轮 = 120 配对观测；≥70% 暴露 ≈ 84 暴露对（v1 只有 ~57，且其中还混着“任务本来就更难”的选择偏倚）。
  • 主检验：McNemar（题级 3 轮多数票）；bootstrap 10k CI；报告每轮各自配对结果。
  • 次要：暴露题 subgroup（此时接近全体）、tool_calls 分位、domain、摘要 4 要素覆盖。
  • 功效声明：84 对、discordant ≈30% 时，可检出 ~10pp（α=0.05, power≈0.8）；不承诺检出 3pp。

11.7 外部效度验证（可选，+1h）

自然 128K regime 下取 20 题（同一 Top-40 清单的一半）× 2 臂 × 1 轮 ≈ 0.94h，只作描述性方向校验（不设判据）。用于回答「tight-context 的结论在默认配置下是否同向」；预期该臂压缩率仍 ~12%，不用于推断。

11.8 可选的零成本前置（P0.5，+0.5–1h）

用 cline 自带离线压缩工具（compact-session）对已有 session 分别跑 --strategy basic 与 --strategy agentic，比较摘要 4 要素覆盖率/token 压缩比/关键事实保留。若 agentic 摘要质量并不优于 basic，可直接判定「不值得跑昂贵评测」，先止损。注意：离线压缩只回答 H5（摘要质量），不能回答 Pass@1。

12. v3 补丁：P0d 实测推翻了「32K 强制压缩」的前提
