2.2 为什么必须发在 DAC 而不是软件工程会议

这是评审必问的定位问题。论据（推测，需在 intro 强化）：

  1. 问题领域是 EDA-specific：correctness 是 situated property（依赖 live layout/schematic/waveform 状态），不是通用代码生成的 functional correctness。SWE-bench 类 benchmark 的"测试通过"不捕获 EDA 的状态依赖。这是 DAC 而非 ICSE/SE 的核心理由。
  2. 统一接口覆盖 3 语言 4 商业运行时：PyAether/SKILL/Tcl-WaveView/Tcl-Innovus 是 EDA 工程师日常工具，软件工程会议受众不熟悉；DAC 受众这是核心痛点。
  3. 实证贡献是 cross-runtime benchmark + 受控消融：449 任务 + Ω/Φ 轴消融是 EDA 自动化的实证基准，不是 SE 的代码生成 benchmark（SWE-bench/HumanEval）。
  4. 部署场景是 EDA flow：在 leading memory design house 的量产 EDA flow 部署，是 EDA 产业链问题，不是通用 SWE。

风险：如果理论 overclaim 不修，审稿人可能说"这是 SE 论文披着 EDA 外衣"——所以 §4.2 必须降级为 framework/hypothesis（见 §⑦ P0）。

3.4 缺失的统计检验（评审 §B + 10-25 改稿令 I）

5 轮 + std 不足以 establish 显著性。需补：

  1. Wilson 95% CI for Pass@1（每臂 pooled + per-slice）：
    公式：CI = (p̂ + z²/2n ± z·√(p̂(1-p̂)/n + z²/4n²)) / (1 + z²/n)，z=1.96，n=任务数（per-slice 158/77/56，pooled 449）。
    数据已有，不用重跑。可用 reports/a1_significance.py（已存在）扩展。
  2. 配对 McNemar 检验（组件两两对比）：
    对每对臂（如 full vs wo_selfexp），用 5 轮 × 158 任务的 per-task pass/fail 矩阵建 2×2 列联表，算 McNemar χ²。
    关键：需 per-task 级别的 pass/fail（5 轮 × 449 任务 = 2245 个二元结果），数据应在 batch 目录的 regrade 结果里。
    判据：full vs wo_selfexp 在 PyAether 上 Δ=+4.1pp（81.4 vs 77.3），但 std=1.5/2.9 → 推测 McNemar 可能不显著（需实算）。
  3. 多重比较校正（C1 五臂两两比 = 10 对，S2 四臂 = 6 对）：
    用 Benjamini-Hochberg FDR 或 Bonferroni。不校正的话 10 对里至少 1 个假阳性概率 ≈ 40%（α=0.05）。
  4. 5 轮轮间方差 vs 任务间方差分离：
    当前 std 只反映轮间方差，任务间方差（难易分布）未报告。建议补 per-task 难度直方图 + bootstrap CI。
