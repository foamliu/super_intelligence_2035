一、摘要（三问结论）

NO-GOgo/no-go 决策

本实验旨在检验 cline 的 configured-agent（subagent）机制对 EDA 代码生成任务的影响，预注册了三个假设（H1 消融对比 / H2 基座梯度 / H3 迭代上限）。起跑前 P0 预检（17:20）通过三项：doubao key 连通、configured agent 工具注册可见、主 agent 调用了 subagent 工具。

P1 pilot 完成后对 trace 做深度审计，发现 P0 的三项验证均停留在「工具注册 + 被调用」层面，未验证 subagent 是否真正执行了 LLM（messages 非空 / usage>0 / finishReason=completed）。实际 trace 显示 subagent 100% 报错、0 token、session 0 消息——subagent 从未运行。

三问结论：
  • Q1 — subagent 机制在当前 harness 下是否可用？  否。cline 3.0.51 的 delegated-agent 消息流存在缺陷：相同 provider 配置下，主 agent 正常运行而 subagent 向网关发送空 messages 数组，被网关拒（messages must not be empty）。
  • Q2 — H1/H2/H3 是否可检验？  否。三个假设全部依赖 subagent 真正执行并消耗 token；0% 执行率下 P2（9 臂 × 40 题 × 3 轮 ≈16h）只会产出无意义数据，违反「不许包装成增益」「真实裁判=Pass@1」红线。
  • Q3 — 默认策略建议？  在 cline 3.0.51 下 不应启用 configured subagent（启用后仅增加 spawn 开销与报错噪声，无任何执行产出）。若要检验 H1/H2/H3，需先解除 harness 版本锁定（升级 cline 或修补源码），见 §8。

五、根因分析（含 cline 3.0.51 源码证据）

两类根因，均位于 cline 3.0.51 内部，非快速配置可修。

5.1 根因 A（dsv4 臂 B1/B2/C2）：messages must not be empty

现象：provider 解析成功（providerId: openai-compatible 是真 provider 类型，与主 agent 相同），但 subagent session 文件 agent_*.messages.json 全部 n_msgs=0——task 从未成为 user message 持久化。首次 LLM 调用 messages 数组为空 → OpenAI-compatible 网关拒绝。

源码定位：

// configured-agent-tool.ts:198
const result: AgentResult = await subAgent.run(input.prompt);  // input.prompt 非空（trace 已核实）

// session-runtime-orchestrator.ts:938-950  （executeRunInternal）
if (effectiveUserMessage !== undefined) {
  const content = await buildUserTurnContent(effectiveUserMessage, ...);
  this.conversation.appendMessage({ id, role: "user", content });   // ← 应注入 user 消息
}
// :1003-1005
const initialMessages = messagesToAgentMessages(this.conversation.getMessages());
// :1080
runResult = await runtime.run("");   // 空串：按注释，靠 initialMessages 作为种子

代码路径确实追加了 user 消息并以 initialMessages 种子化运行时，但网关仍收到空 messages。"messages must not be empty" 字符串在 cline 源码中不存在（全文检索确认）→ 该错误来自网关，证明 HTTP 请求体的 messages 数组确实为空。

关键证据（证明是代码 bug 而非配置问题）：将 B1 subagent 臂的 providers.json 与 compaction-basic（主 agent 正常工作、在本批同任务上完成评分）的 providers.json 逐字节比对——完全一致：

lastUsedProvider: openai-compatible
  profile=openai-compatible:
    provider   = openai-compatible
    model      = deepseek-v4-pro-cloud
    baseUrl    = http://agi-gateway.cxmt.com/cloud/v1
    apiKey     = 02_088EE9051AAE4BF0ABFC7130331BF697_e13f4f37...（同一把 key）

同一 provider、同一 key、同一 model、同一 baseUrl——主 agent 正常运行而 subagent 发空 messages。唯一差异是代码路径：主 agent 走 primary session runtime；subagent 走 createDelegatedAgent → new SessionRuntime(config) → run(prompt) 的 delegated-agent 消息流。定位为 cline 3.0.51 delegated-agent 消息初始化缺陷，非配置可修。

5.2 根因 B（doubao 臂 B3/B4/B5）：Unknown or disabled provider

现象：providers.json 中 doubao-lite 等是命名 profile（key=doubao-lite，其 settings.provider 实为 "openai-compatible"，同 baseURL/apiKey、仅 model 不同）。

源码定位：

// configured-agent-tool.ts:133-143  buildAgentRuntimeConfig
return {
  ...base,                                    // 继承父 runtime 的 apiKey/baseUrl
  providerId: agent.providerId ?? base.providerId,   // ← researcher.yaml 的 providerId 覆盖
  modelId:   agent.modelId   ?? base.modelId,
  maxIterations: agent.maxIterations ?? base.maxIterations,
};

researcher.yaml 写 providerId: doubao-lite（profile key），被 subagent 的 provider 解析当作 provider 类型查 → 注册表无此类型 → "Unknown or disabled provider"。主 agent 用 lastUsedProvider（profile-key 查找路径）能跑；subagent 走 buildAgentRuntimeConfig 覆盖 providerId 为命名 profile → 解析失败。

为何不可简单修复：即便把 researcher.yaml 改为 providerId: openai-compatible，buildAgentRuntimeConfig 只覆盖 providerId/modelId/maxIterations，不覆盖 apiKey/baseUrl——subagent 仍继承父 agent 的 dsv4-pro key，而 doubao 模型需各自独立 key。researcher.yaml 的 frontmatter schema（configured-agent-config.ts:8-16）不含 apiKey/baseUrl 字段，无法在 agent 级别指定连接凭证。需 cline 源码支持命名 profile 解析或 per-agent 凭证。

注：根因 B 在根因 A 修复前无实际意义——核心臂 B1/B2/C2（同基座 / dsv4-flash / 迭代上限）全部受根因 A 阻塞，即便 doubao 臂修好也无法检验 H1/H2/H3。

8.2 默认策略建议

  1. 生产配置：在 cline 3.0.51 下 不应启用 configured subagent。启用后仅增加 spawn 开销与报错噪声（B1/B3/B5 墙钟翻倍），无执行产出。当前 compaction=basic、thinking=medium、主基座 dsv4-pro-cloud 的单 agent 配置仍是该 harness 下的合理默认。
  2. P0 验证规范（修正）：今后凡验证「subagent / delegated-agent / teammate」类机制，P0 必须额外验证 subagent 真正执行：1 题 smoke 后检查 subagent session n_msgs>0 + usage>0 + finishReason=completed。「工具注册 + 被调用」不等于「机制可用」。
