关键发现：
  1. 每个 session 最多压缩 1 次（compaction.json 只保留最后一次快照，userRunSpan 全为 1）。即"一通会话触发几次压缩" = 0 次（87.9% sessions）或 1 次（12.1% sessions），平均 0.12 次/session。
  2. 每次压缩平均压到原来的 13.79%（中位数 13.98%，min 0.31% / max 35.29%）—— 即 100 条原始消息压缩成约 14 条（含 1 条结构化 summary + 压缩后继续的 ~13 条新对话）。

二、压缩机制说明

2.1 触发条件

cline 3.0.51 在每次 API 调用前检查 context window 使用率。当 context 接近满（实测阈值约 100K token，约 128K context window 的 80%）时自动触发压缩：

  1. 用 LLM 把前面的对话历史总结成结构化 summary（5 节：## Goal / ## State（Done/In Progress/Blocked）/ ## Highlights / ## Next / ## Files）
  2. 把 summary + 最近几条 message 作为新的 API 历史，替代完整历史
  3. 原始 messages.json 保留完整 UI 历史（不删），compaction.json 记录压缩后快照

2.2 典型案例：B_en_r2 / task-119

session: 1794197058573_y99fk（B_en_r2, task 119: create_inverter_schematic） source_message_count: 1352 条原始消息 compacted to: 13 条消息（1 条 summary 4362 字符 + 12 条压缩后新对话） tokensBefore: 103,045（被压缩源消息总 token 估算） 压缩比: 13 / 1352 = 0.96% compression.json 大小: 74,872 字符 session 持续: 4h48m（04:04 → 08:52） ## summary 结构（5 节）: ## Goal Implement and verify `create_inverter_schematic(design)` ... ## State - Done: Aether init ✓ / dbOpenCVByType ✓ / API 签名确认（dbNewCellView, dbCrtInst, dbCrtNet...） - In Progress: 确定 library/cellview 名 + 实现序列 - Blocked: run_commands/read_files 返回空 / 部分 get_api_details 响应被截断 ## Highlights - emyDesign.getTopBlock 返回 block 或 None - emyScalarInstCreate 是最干净的实例化方式 - 主要阻塞是 filesystem/tool output，非 API 知识 ## Next 1. 修复 filesystem/output 访问 2. 恢复 task spec（EDA-Eval-PyAether-119.md） 3. 探索 workspace 结构 4. 实现 create_inverter_schematic 5. 跑验证 ## Files - 读取尝试: /nasdata/.../full_tasks/EDA-Eval-PyAether-119.md（空） - 编辑: 无

五、压缩触发阈值

tokensBefore = 被压缩源消息的总 token 估算（cline 内部 tokenizer 粗估，非精确 context size）。不是单次 API 调用的 context size，而是被压缩的所有历史消息累计 token。

双峰分布：36% 在 100-110K（第一次压缩触发点），39.6% 在 200K+（疑似多次压缩累积）。真实压缩次数可能高于观测的 1 次——compaction.json 只保留最后一次快照，若 session 压缩过 2-3 次，前几次的快照被覆盖。但根据 userRunSpan=1（cline 内部字段），cline 的设计是 "只压缩一次，压缩后用 summary 持续替代"，双峰可能是 token 估算误差或单条超长 tool_result 导致。

5.2 触发阈值推断

实测触发阈值 ≈ 100K token（128K context window 的 ~80%）。第一次压缩的 268 个 session（36%）tokensBefore 落在 100-110K，集中度极高。cline 3.0.51 的默认配置是 autoCompactThreshold = 0.8 × contextWindow，即 128K × 0.8 ≈ 102K token。

  1. 因果方向 1（压缩→timeout）：压缩丢失关键上下文（API 签名、错误诊断历史），agent 压缩后效率下降，最终撑到 12h timeout

九、对评测结论的影响

压缩是 B 轴 pass 率偏低（76.2-81.2%）的一个混杂因素：
  1. B 轴压缩率 17.8% > A 轴 8.5%：B 轴更多 session 经历压缩，压缩丢失信息可能导致 pass 率下降
  2. 压缩 sessions 的 TIMEOUT 率 11.1%：压缩的 session 远更易 timeout，timeout 的 pass=0
  3. 压缩主要影响长难题：难题本身难（pass 率低）+ 难题触发压缩（context 撑满），两者叠加
  4. B_en_r1 重跑后：新 r1 用 dsv4-pro 基座（converged 更高、session 更长），压缩率可能从 8.2% 升至 ~17-18%（与 r2/r3 一致），需跑完后复验

9.1 对轴 A 倒 U 形结论的影响

轴 A 的 xhigh 档压缩率 16.5%（最高），而 xhigh 档 pass 率 82.3%（低于 medium 85.4%）。xhigh 档 pass 率下降可能部分因压缩导致——reasoning 太长撑满 context，压缩后丢失上下文。但这与"倒 U 形"结论方向一致（xhigh 边际递减），不改变定性结论，只是 因果归因需谨慎：xhigh 下降是"reasoning 过长导致压缩丢信息"还是"reasoning 过长本身干扰决策"？需进一步控制变量。

9.2 对轴 B 语言结论的影响

轴 B 5 语言压缩率相近（16.7-18.8%），压缩率差异不足以解释 5pp 的 pass 率差距（zh 81.2% vs fr 76.2%）。但压缩 sessions 的 TIMEOUT 率 11.1% 是真实信号——压缩可能放大了语言切换的负面效应（es/fr 部分切换混乱 → 更多试错 → 撑满 context → 压缩 → 丢失上下文 → 更多试错 → timeout）。当前 B 轴已因基座违规降级为描述性，压缩分析进一步支持"不作因果归因"的判断。

十、结论与建议

10.1 核心结论

  1. 自动压缩确实触发：6162 sessions 中 745（12.1%）触发过压缩，每 session 最多观测到 1 次（compaction.json 只留最后快照）
  2. 压缩比中位数 13.98%：100 条原始消息压缩成约 14 条（1 条 summary + 13 条最近消息）
  3. 触发阈值 ~100K token（128K context 的 80%），主要发生在任务后半段（88% 进度）
  4. 压缩后继续工作 19 条 message才完成任务（中位数）
  5. B 轴压缩率（17.8%）是 A 轴（8.5%）的 2.1 倍，因 B 轴 thinking=medium 恒定产生大量 reasoning
  6. xhigh 档压缩率最高（16.5%），与 xhigh 档 pass 率下降（82.3%）相关
  7. 压缩 sessions 的 TIMEOUT 率 11.1%（vs 未压缩 0.04%），压缩是"难任务"的信号

10.2 建议

  1. 报告口径：ZhuLong 消融报告应注明"压缩是混杂因素"，特别是 xhigh 档 pass 率下降 + B 轴 pass 率偏低的归因
  2. 压缩比作为难度信号：压缩比 < 5% 的 session 几乎都 timeout/fail，可在评测 pipeline 中加"压缩比预警"
  3. cline 配置优化：考虑提高 autoCompactThreshold（如 0.9 × context）或改用"分段保留"策略（保留最近 N 条 + summary），减少信息丢失
  4. 后续分析：对压缩 sessions 做"压缩前后的 pass 率对比"（如同一 task 在 A_medium 的 3 轮中，压缩轮 vs 未压缩轮的 pass 差异），可量化压缩的真实影响
