三大失败模式（占失败总量 60%+）：
  1. NO_SUBMIT（70 + 9 = 79 个，12.3%）：cline 整个 session 没产出。根因：budget 耗尽 / 陷入探索循环 / prompt 模糊导致 candidate 不知该交付什么。这是评测器该"放过"还是"扣分"的边界——如果 prompt 清晰，NO_SUBMIT 应算 0 分；如果 prompt 模糊，NO_SUBMIT 可能是合理的不确定。
  2. FileNotFoundError（63 + 4 = 67 个，10.5%）：candidate 声称产出了文件但 checker 找不到。根因：candidate 把文件写到了错的路径（如硬编码 A 的路径），或文件名拼错。这是 L1 边界守卫击穿 hardcode-A 的预期效果。
  3. assets dir missing（59 个，9.2%）：candidate 脚本在隐藏 B 上跑时找不到 assets。根因：candidate 假设了 A 的 assets 目录结构，未泛化读取。这同样是 L1 守卫的预期击穿。

4.2 失败模式与 case 质量的关系

失败模式 #2 和 #3（共 126 个，占失败 19.7%）是"泛化失败"—— candidate 在 A 上能跑，但硬编码了 A 的路径/assets，在隐藏 B 上崩溃。这恰恰是评测器设计的意图：通过隐藏 B/B2 跨输入守卫，击穿 hardcode-A 的 candidate。这部分失败是评测器有效的证据，而非 case 质量问题。

失败模式 #1（NO_SUBMIT 70 个）需深入排查：是 cline 自身能力不足（合理失败），还是 prompt/test 不清晰导致 candidate 无从下手（case 质量问题）？从 §2.3 的反直觉发现（PASS prompt 更长）推断，NO_SUBMIT case 的 prompt 可能过短/模糊。

七、结论与未来方向

7.1 核心结论

  1. 通过率 9.9% 偏低但区分度好：域间 2.6%-20.0% 跨度 7.7 倍，PASS/FAIL/ERROR 在行为（时长/压缩/产出率）上区分清晰。评测器能区分"做对"与"做错"，不是随机噪声。
  2. 失败结构健康：SEM 67.3% 为主（语义错，非崩溃），NO_SUBMIT 仅 12.3%（多数 candidate 至少尝试交付）。
  3. 三大失败模式占 60%+：NO_SUBMIT（79）、FileNotFoundError（67）、assets dir missing（59）—— 后两者是 L1 边界守卫击穿 hardcode-A 的预期效果，是评测器有效的证据。
  4. 反直觉：PASS 的 prompt 更长（1,619 vs 951 vs 765 chars）—— 长 prompt 提供清晰规格，短 prompt 模糊性高。prompt 长度与通过率正相关。
  5. PASS "做对就停"，FAIL "反复试错撑满 context"：PASS 时长 11.2min/压缩 18%，FAIL 15.8min/压缩 42.5%。
  6. 工具覆盖严重不均：hspice 占 64%，10 个工具从未被调用，calibre ERR 率 40%。

7.3 未来方向

短期（提升通过率 + 评测质量）：
  1. 补强短 prompt case：对 prompt < 1000 chars 的 case（多在 FAIL/ERROR）补充背景/示例/输入输出规格，减少模糊性。预计可提升 NO_SUBMIT case 的产出率。
  2. 排查 NO_SUBMIT 70 个 case：逐个看 cline_session.jsonl 末尾 —— 是 budget 耗尽、陷入探索循环，还是 prompt 误导？区分"candidate 能力不足"与"case 质量问题"。
  3. 修 judge 异常：top signature #5 "PASS" 误标 5 个，说明 judge 内部报告解析有 bug，需修。
  4. 统一元数据标注：14 种 track 值需归并（如 "B-synthesized" / "B (synthesized; ...)" → "synthesized"）；641 case 补 L_level。
中期（提升覆盖度 + 难度梯度）：
  1. 补充未覆盖工具的 case：为 asc/pvx/icc2/spyglass/star-rc/redhawk/totem/siliconsmart/smartspice/design_compiler 各增加 5-10 个 case，并在 prompt 中明确要求用该工具。
  2. 降低 physical_verify / layout_aether 难度（2.6-2.7%）：拆分复杂 case 为阶梯式子任务，或提供部分 skeleton code，让通过率提升到 10-15%，避免"天花板过低"打击 candidate。
  3. 增加难度梯度标注：每个 case 标注 expected_difficulty（easy/medium/hard），用于评估 candidate 在不同难度的表现曲线，而非单一通过率。
  4. 引入部分评分：当前是 binary PASS/FAIL，建议对多断言 case 报告"通过 N/M 条断言"，提供更细粒度的区分度。
长期（评测范式升级）：
  1. 从 binary 到 continuous：当前 9.9% 通过率的信息密度低。改为"断言通过率 + 工具调用效率 + 收敛速度"的多维评分，能更好区分 candidate 能力。
  2. faithful vs synthesized 平衡：当前 faithful 6% / synthesized 13.2%，差距 2.2 倍。faithful 复刻真实 trace 的模糊性是双刃剑 —— 更贴近真实场景，但 case 质量难控。建议：faithful case 增加"预期可行解"标注，确保 case 有解。
  3. 压缩与 timeout 的混杂因素：FAIL 压缩率 42.5%（撑满 context），可能丢失关键信息导致失败。建议：对压缩 case 单独报告"压缩前后的断言通过率差异"，量化压缩的真实影响（参考 ZhuLong 自动压缩分析报告的方法论）。
  4. 工具调用质量评分：tool_calls > 60 几乎都 FAIL（15% FAIL vs 3.3% PASS）。建议：将"tool_calls 效率"纳入评分（在 PASS 前提下，调用越少越好），引导 candidate 收敛而非试错。
  5. 跨批次稳定性：本批 9.9%，需对比其他批次（如 4 分片基准 A/B/C/D）的通过率，确认 9.9% 是 case 难度还是 candidate 模型/配置问题。建议固定 candidate 跑 3 批，看 case-level pass 率方差。
