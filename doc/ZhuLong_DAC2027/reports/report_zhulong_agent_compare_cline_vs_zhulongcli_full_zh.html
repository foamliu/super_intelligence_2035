cline 与 zhulong CLI 通过率差异：源码级归因（配置逐字节一致）

对象：ZhuLong EDA-Scripting-Bench（PyAether 切片，158 题）· glm-5.3-flash · READBACK=full · 各 5 轮
唯一设计变量：CLI agent（cline 3.0.51 vs zhulong CLI，fork 自 cline 3.0.29）
源码：zhulong = /nasdata/app.e0031982/code/eda_platform；cline = /nasdata/app.e0031982/code/cline
依据：zhulong_results.md、run/MEMORY_ZHULONG.md、run/daily-memories/ 与各轮 regrade 日志（出处见附录）
一句话结论：差距 ≈100% 来自"约 20% 的题目根本没生成出可执行的 .py"，不是模型 / 框架 / 代码质量。
定量看：cline 86.8 ± 1.6% vs zhulong 69.0 ± 2.3%（Δ = −17.8pp），其中几乎 100%（≈18pp）来自"未生成 / 未落盘"（生成失败）；
而"生成后答对率"两侧几乎无差（zhulong 88.6% vs cline 88.2%，差异 ≈ 0）。

源码级根因：zhulong CLI 是 cline 的早期 fork（@cline/core 0.0.51，约 2026-06-24），
缺少 cline 在 2026-08-01～08-04 引入、并随评估基线（3.0.51）一起发布生效的"空响应重试"（empty-response retry）机制。
在 glm-5.3-flash 这类会间歇性返回"空回复"的 backbone 下，一次空回复在 zhulong CLI 里是直接判死的硬失败（抛 Model returned empty response），
而在 cline CLI 里会被静默重试掉——这正是"生成失败 23–38/轮 vs 1–4/轮"的机制来源。

4. 源码级分析：为什么 zhulong CLI 的通过率更低

4.1 先给结论

围绕"生成失败 23–38 vs 1–4"这条最硬的观测，两个代码库在同一处关键逻辑上分叉：

能力zhulong CLI（core 0.0.51）cline 基线（core 0.0.71 / 3.0.51）
空响应重试中间件（LLM 层）❌ 无 retry-empty-response.ts✅ 有，且已在 ai-sdk.ts 全局挂载
agent 主循环对空回复的处理直接 throw "Model returned empty response"交由中间件重试
LLM 请求入口的 withEmptyResponseRetry❌ 无✅ 有

这条差异把"模型偶发返回一个空 turn"这件事，在 zhulong 里变成一票否决的任务失败，在 cline 里变成一次透明重试。

4.2 版本漂移量（先量化"两个仓库差多远"）

diff -rq eda_platform/sdk/packages/core/src cline/sdk/packages/core/src   # 仅 cline 独有 166 个文件；仅 eda_platform 独有 2 个
diff -rq eda_platform/sdk/packages/llms/src  cline/sdk/packages/llms/src   # 仅 cline 独有 67 个文件

zhulong 落后的不仅是版本号，而是数百个上游文件的新增 / 修改。其中对本次评测最致命的，是 4.3 这一处。

4.3 关键差异：空响应（empty turn）的重试

(a) cline 侧：retry-empty-response 中间件（LLM provider 层）

文件 sdk/packages/llms/src/providers/middleware/retry-empty-response.ts（cline 有，eda_platform 无）。 其设计注释直击本实验观测到的那类失败：

"providers intermittently return a response that finishes normally but carries no content at all … In Cline's runtime an empty assistant turn is a hard failure ("Model returned empty response"), so a single flaky generation kills the whole task."

  • 流式输出先缓冲，直到"首个有效 part（正文 / 工具调用 / 不支持输出 / 错误）"出现才判定本次请求成立并放行；被判定为"空 turn"的尝试整体丢弃。
  • 仅当一次 turn 真的一无所有（无正文、无推理、无工具调用）时才重试；纯工具调用 turn 算有内容，绝不重试。
  • 重试多花的 token 把各次 finish.usage 累加进最终 finish，计费诚实。

(b) cline 侧：在 ai-sdk.ts 全局挂载

文件 sdk/packages/llms/src/providers/ai-sdk.ts（评估基线 v3.0.51 版本已含该 import 与 withEmptyResponseRetry）：

import { createRetryEmptyResponseMiddleware } from "./middleware/retry-empty-response";
export function withEmptyResponseRetry(model, retryEmptyResponses) {
  if (retryEmptyResponses === false) return model;
  return wrapLanguageModel({ model,
    middleware: createRetryEmptyResponseMiddleware({ ...retryEmptyResponses }) });
}
// ... 在 vendor 模型构建出口处统一调用 withEmptyResponseRetry(...)

即 cline 的每一个 AI SDK vendor 模型默认套上这层空响应重试。

(c) zhulong 侧：agent 主循环直接判死

文件 eda_platform/sdk/packages/agents/src/agent-runtime.ts（约 602 行起）：

const { message, finishReason } = await this.generateAssistantMessage();
if (finishReason === "aborted") { throw this.normalizeAbortError(); }
if (message.content.length === 0) {
  throw new Error(
    finishReason === "error"
      ? (this.state.lastError ?? "Model stream failed")
      : "Model returned empty response",
  );
}
// ...
if (finishReason === "error" && toolCalls.length === 0) {
  throw new Error(this.state.lastError ?? "Model stream failed");
}

即：只要模型这一轮没有吐出任何内容，zhulong 立即把整个任务抛错终止，没有重试，也没有"纯工具活动 / 内容过滤 / 未知 finish"的细分。

(d) 时间线：为什么恰好是"cli 有、zhulong 无"

时间事件相对位置

即：zhulong 在空响应重试加入前约 6 周就已分叉，此后再未回灌该机制；而评估所用 cline 基线恰好包含它。

4.4 机制与观测现象的对账（不是猜，是对得上）

  1. 代码差异：eda_platform/.../agent-runtime.ts 第 602–606 行——if (message.content.length === 0) throw … "Model returned empty response"，即"这一轮模型没产出内容"就把整个任务判死（4.3c）。
  2. cline 的对应实现：同一处，cline 在 provider 层用 retry-empty-response 中间件把空 turn 吞掉并透明重试（4.3a/b），任务继续走到落下 .py。
  3. 结果差异的证据：配置逐字节一致的同一套 5-run 里，cline gen-fail ≈ 1–4/轮（~1–2%），zhulong gen-fail 23–38/轮（~20%）；5 轮 exec_err=0、timeout≤6、无 infra 故障。
  4. 归因结论：差距全部落在"生成落盘"这一端，与"空响应 → 判死 → 无 .py"完全吻合，而不是"生成错了"或配置 / 环境差异。

4.5 cline main 分支后续强化（方向性证据，注意版本边界）

作图时检出的 cline main（3.0.74 / core 0.2.0）还新增了以下韧性层，均晚于评估基线 3.0.51，故不直接参与本次计分，但进一步佐证方向：

  • fix(agents,llms): recover from max-tokens turns（#14378，2026-09-21）：finishReason === "max-tokens" && 无工具调用 时以简洁性 nudge 重试。
  • fix(llms): retry mid-stream network interruptions（#13052，2026-08-07）：输出前遭遇瞬态网络中断时重试。
  • agent-runtime.ts 的 generateAssistantMessageWithProviderRetry()：对 429 / 5xx / 网络抖动做指数退避重试。
  • 上下文窗口溢出的结构化恢复（ContextWindowOverflowError → 压缩对话后重试一次）。

这些在 eda_platform 中同样缺失。它们并非解释 −17.8pp 的必需项（空响应重试那一条已够），但说明 zhulong 想追平 cline，核心动作是回灌上游"可靠性层"，而非换模型 / 改提示词。

4.6 数值对齐：生成失败差距 ≈ 通过率差距

用 zhulong 实测 coverage（77.8% vs cline ≈98.4%）与条件通过率（88.6% vs 88.2%）回代（§3.2）：
仅"生成失败"一项就贡献 ≈18.2pp，几乎吃掉全部 −17.8pp；条件通过率几乎无差（zhulong 甚至略高 ≈0.4pp）。

结论：源码里一句 throw "Model returned empty response" vs 一层 retry-empty-response 中间件，在 Pass@1 口径下就是 ≈18pp，占 −17.8pp 的全部。

5. 结论与建议

  1. 差距定性：−17.8pp ≈ 100% 来自"生成失败 / 未落盘"，不是模型能力、EDA 框架或代码质量问题（exec_err=0；条件通过率 88.6% vs 88.2% 基本打平）。
  2. 差距根因（源码级）：zhulong CLI 是 cline 的早期 fork（core 0.0.51，≈2026-06-24），缺少 cline 在 2026-08-01～08-04 引入、随基线 3.0.51 一起生效的空响应重试（retry-empty-response 中间件 + withEmptyResponseRetry）。空回复在 zhulong 里被 throw "Model returned empty response" 一票否决。
  3. 建议（工程侧）：把 zhulong CLI 回灌到 cline 的 retry-empty-response 中间件（最小改动）；远景对齐 cline main 的可靠性层；重新打 5-run mean±std 确认 Pass@1 收敛到 cline 同量级。
