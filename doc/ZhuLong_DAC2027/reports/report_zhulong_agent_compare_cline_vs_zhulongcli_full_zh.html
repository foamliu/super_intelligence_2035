一句话结论：差距主要不是"模型/框架能力"造成的，而是"约 12% 的题目根本没生成代码"。
两轮同为 glm-5.3-flash、同为 full 回读、同为 158 题 PyAether 切片，唯一设计变量是 CLI agent （cline 3.0.51 vs zhulong CLI）。5-run 均值 86.8 ± 1.6% vs 75.6 ± 4.4%（−11.2pp）。 定量分解后：≈8.9pp（约 80%）来自"未生成代码（literal-pass）"，≈2.2pp（约 20%）来自"生成后的条件通过率略低"。 而条件通过率在 5 轮里有 3 轮（89.6% / 87.7% / 89.3%）已与 cline（≈88%）持平 —— 说明这批轨迹的"质量"并不差， 差的是"有没有跑完并落下 .py"。

4. 机制：什么是 literal-pass，为什么 zhulong CLI 会掉进去

4.1 直接证据：失败条目里写的是字符串 "pass"

zhulong 线 2026-10-23 02:24 的心跳对当时批次的 codegen 输出做了逐条核查：

completed_code_generation_2026_1023_002456.jsonl
status = {success: 142, fail: 16}
16 个 fail 条目的 completion 全 = 'pass'（comp_len = 4）   ← literal-pass 退化签名

即：这些题 agent 没有写代码，而是把 pass 当作"最终答案"交上去了。最终 5 轮的同类失败数为 r1=16、r2=16、r3=23、r4=12、r5=27（r5 心跳明确写"27 fail = literal-pass / 无 .py"）。

4.3 配置层面的可疑点（有记录，非推测）

  • MCP 超时只配到了 cline、没配到 zhulong：2026-10-23 10:4x 的记录写明 「~/.zhulong/settings/cline_mcp_settings.json 缺 timeout:600（会回退 60s → -32001 风暴）， 且 autoApprove 用的是旧工具名 run_pyAether_code_tool」→ 已补 600s 并改为新工具名。 修复前，run_code 这类长调用极易在 60s 被掐断或等待人工批准；
  • autoApprove 工具名不匹配的后果很直接：调 run_code 得不到自动放行 → 拿不到回读 → "看起来做完了" → 交 pass。与 literal-pass 形态高度一致；
  • maxTokens 不同：cline 线 8192，zhulong 线 providers.json 为 16384。它不直接解释"0 长度输出"， 但会改变长脚本的截断行为，补证时应一并核对。
时间线要读准：最终采用的 5 轮批次是 10:30 / 12:52 / 15:56 / 18:34 / 20:38，而 settings 修复在 10:4x。 因此 r1（10:30 起跑）很可能仍带旧设置，r2–r5 才是修复后。这与"条件通过率 r1 最低（76.8%）、r3–r5 追平 cline"的走势一致， 但目前只是时间相关，尚不能作为因果定论——需要逐题 trace 才能把"配置 → 工具失败 → 交 pass"这条链坐实。

7. 结论与行动项

  1. 不要把 −11.2pp 解读成"zhulong CLI 能力差"。按条件通过率算，两边只差 ≈2.2pp；差的主要是"没产出代码"。
  2. 优先修 literal-pass（预计回收 ≈9pp）：agent 侧加硬校验——提交前必须有非空 .py， 且**不得以字符串 pass 作为最终答案**；同时把 MCP timeout=600 与 autoApprove 工具名做启动自检（不一致直接拒跑）。
  3. 再谈质量（≈2pp）：r3–r5 的条件通过率已与 cline 持平，说明模型+框架没问题，不必急着换模型或改 prompt。
  4. 口径建议：以后同时报 pass/158 与 pass/gen_ok， 否则"生成失败"会伪装成"能力下降"，把结论带偏。
  5. 可复现性：若要写进论文，必须把 26.15 上两批 trace 归档进仓库（当前 git 里只有汇总数字）。
