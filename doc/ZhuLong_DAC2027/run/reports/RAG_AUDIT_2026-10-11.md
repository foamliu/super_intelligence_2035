## 结论（必答 4 问）

### 1. 9006 上到底有没有一个能召回的 RAG 服务？— **✅ 有**
`/health` http=200、executor_ready:true、collections 齐全（api_descriptions:4049…）。3 次真实 `POST /recall` 均 http=200，返回带 `api_name`+`description`+`similarity` 的语义正确排序结果（dbCreateLib@0.9283 等）。监听进程 = 本项目 venv 的 `eda_api_recall:app --port 9006`。

### 2. `full` 臂运行时 RAG 是否真的被调用并注入？— **✅ 是**
r5 log：`search_apis` 成功 1252 次、`get_api_details` 477 次（用 search 找到的 API 名查详情）。MCP app.log：full 运行日（10-09/10-11）`>>> Search APIs` 4258+6476 次，`<<< Found` 100% 成功，`recall error` = **0**。调用链 main.py→tools/search_apis.py→query_knowledge.py→`POST 9006/recall` 全通。recall 内容进了 prompt（模型据 search 结果调 get_api_details→run_code）。

### 3. RAG 从哪一轮开始失效？— **❌ full 全程未失效**
27036 条 recall error 全部是 09-24~10-04 的**死端口 9012**（legacy 时代）。full r1（10-09，URL=9010）= 0 error；full r2–r5（10-11，URL=9006）= 0 error。仅 10-07（rag 臂日）有 8 次 9006 瞬时抖动（数千调用中 8 次，不影响 rag=71.8%）。**不存在「r1 有效、r2 起失效」的情况**——每轮用的 URL（9010/9006）都指向活服务。

### 4. 对 C1 表格的影响 + 修法

**结论：`full` 与 `wo_retrieval` 的对比可解释、有效，无需重跑。** `full ≈ wo_retrieval` 是真实科学发现，不是 bug：

| 臂 | 检索 | run_code | Pass@1 | 增量解读 |
|:--|:--:|:--:|--:|:--|
| pure_llm | ✗ | ✗ | 10.5% | 基线（裸 LLM） |
| rag | ✓ | ✗ | 71.8% | **检索单独 +61.3pp**（证明 retrieval 有用！） |
| wo_retrieval | ✗ | ✓ | 81.0% | **run_code 单独 +70.5pp** |
| full | ✓ | ✓ | 81.2% | 两者叠加 ≈ run_code 单独（**retrieval 边际仅 +0.2pp**） |

- retrieval **确实有用**（rag 71.8% >> pure_llm 10.5%，+61.3pp）；
- 但 **run_code（执行反馈）主导**：有 run_code 后，模型可通过报错迭代发现正确 API，使前置检索 largely 冗余 → 叠加 retrieval 仅 +0.2pp；
- 这与「self-exploration/run_code 是主贡献者」的论文叙事**一致且可解释**。
- **论文建议**：在 `tab:main-ablation` 正文/脚注明确「retrieval 的增益在 run_code 在场时边际化」，把 full≈wo_retrieval 作为**发现**陈述，而非异常。

**修法（只写不执行，等 r5 收完 + 运维批准）**：
1. **无需重跑 full r2–r5**——retrieval 全程生效，数字有效。
2. （可选优化）裸名 `search_apis` 被拒 23 次：可在 MCP 侧给核心工具注册裸名别名，减少 1.8% 浪费；**非必须**（自纠正，不影响 Pass@1）。
3. （卫生）端口冗余清理：9012（死）仍在 .env 注释里；9001–9011 多实例混跑（含其它用户）。建议运维统一保留 9006 + 9010，注释掉死 URL，降低「端口漂移」风险。**本轮不动**（红线只读）。
4. （披露）写入结果报告「披露」节：full r1 用 9010、r2–r5 用 9006（RUN_ID 32 切换），两 URL 均活、同款服务，无口径偏差。
