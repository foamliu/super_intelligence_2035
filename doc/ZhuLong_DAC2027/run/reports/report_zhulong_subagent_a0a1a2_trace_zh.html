核心证据：三臂 gen-rate（pass/generated，即生成代码后的通过率）持平 ~87%，说明代码质量不变； 差异完全来自 cline_ok 率（成功生成代码的任务比例）。

结论：A2 的 −15.9pp 完全由吞吐崩溃导致，与 mcnemar_subagent_results.json 的 key_finding 一致： "primarily through reduced generation throughput (cline_ok 60% vs A1 72-90%), not code quality (gen-rate ~87% maintained)"。 验证型 spawn 增加了 写→spawn QA→读 verdict→修→提交 四段流程，使单任务负载翻倍， 在固定 -p 8 + 2500s timeout 下更多任务未能完成生成。

Q3. A1 为什么没增益（−2.5pp, p=0.68）？—— 调研成果传不回来，token 花两遍

用户 18:3x 诊断正确：「子 agent 做完调研，产出无法注入主 agent 的上下文，等于白跑一轮」。

证据：

  1. 子 agent 烧 46M token 做调研，但主 agent 仍需自己重做：
    cost_S_A1_r1.json: tokens_sub.total=46061840 (46M) | tokens_main.total=64097114 (64M) → 主+子合计 110M token，是 A0（~33M/轮）的 3.3× 子 agent tools_histogram: run_commands 704, search_codebase 158, read_files 281, fetch_web_content 71 → 子 agent 做了大量探索，但成果只在子 session 内，主 agent 看不到
  2. 主 agent 消息数翻倍但仍重做研究：A1 mean_n_msgs=68-77（A0=39-48），说明主 agent 在 spawn 返回后仍自己做了一遍研究（spawn 只返回一段文字摘要，不含完整 API 文档）。
  3. 子 agent 执行率 100% 但无 MCP 工具：A1 sub_exec=55/55, 59/64, 43/43（~97%），但 subagent_mcp_rejected=13-46 → 子 agent 同样无法调用 pyAether MCP 工具，只能用 search_codebase/read_files/fetch_web_content 做泛化搜索，非 API 级精准调研。
  4. ITT 不显著差异：A0 vs A1 per-round McNemar b=13, c=10, p=0.68 → 调研型 spawn 既不显著伤也不显著助，纯浪费 token。

结论：A1 的 −2.5pp 来自吞吐轻微下降（spawn 增加 1 轮往返开销，cline_ok 78% vs A0 ~100%）， 但代码质量持平（gen-rate 86%）。子 agent 46M token 调研对主 agent 不可见， 等于「花钱请人查资料但没把笔记带回来」——用户 18:3x 的结构性诊断完全正确。

A3 · 上下文预算臂（用户思路，优先评估）

字段内容
唯一变量主 agent + 子 agent 均设确定且较小的 token 预算（in/out 分别设上限），超限强制交付/交接
机制主 agent in_budget=X / out_budget=Y；超出 in_budget 时强制 spawn 子 agent 接力（子 agent 只收到前段摘要 + 结构化交接物）；子 agent 同样有预算上限。
同时弱化并重测基线：A0' = 同预算下无 spawn 的主 agent（预算打平时单 agent 会怎么退化的「预算基线」必须先测出）
预注册判据A3 ITT ≥ A0' ITT + 3pp（同预算下多 agent 优于单 agent）· McNemar b≥6,c≥6 方向一致
预期机制当所需上下文 > 预算窗口时，单 agent 被迫压缩 → 丢细节 → 质量降；多 agent 各自小窗口 + 结构化交接 → 保留更多细节 → 质量升
风险与失效① 预算太小 → 主 agent 连题目都读不完 → 全挂；② 交接物设计不好 → 子 agent 上下文断裂 → 质量更差；③ 40 题子集可能不够长 → 无法触发预算压力 → Δ≤0（此时需换超窗子集）
预估成本A0' + A3 各 3 轮 × 40 题 ≈ 6 × 40 = 240 任务 × ~20min = ~80h（串行）
为什么能超 A0只有当预算 < 所需上下文时，单 agent 压缩丢细节而多 agent 交接保细节 → A3 在超窗子集上可能赢。但若 40 题不超窗 → A3 ≤ A0。需先做可行性预检（§2 末）。

注入强度：需 wrapper 级——cline 的 maxTokens 控制 output，但 input 预算需 hook 或 wrapper 监控 inputTokens 并强制 spawn。当前 cline 3.0.51 无此机制 → 需改 wrapper 或用 H2 wrapper 扩展。

可行性预检：① 先测 A0' 预算基线（给主 agent 设 maxTokens=8192 看退化多少）；② 测 40 题中峰值上下文分布——若 >90% 任务 < 预算 → 判「本数据集无法检验 A3」→ 改用 158 全集 top-k trace 最长任务。

§3 为什么多 agent 可能赢——用户思路形式化

用户原话：「多 agent 的主要优势在独立上下文：当解决一个任务所需上下文 > 底模上下文窗口、且单 agent 压缩不足以保留足够细节时，多 agent 才可能优于单 agent。⇒ 给每个 agent（含主 agent）确定且较小的 token 预算。」

形式化假设 H_ctx

设 ctx_req(t) = 任务 t 所需的最小上下文（完整读完题 + 查全 API + 推理链不丢细节），W = 底模上下文窗口（deepseek-v4-pro ≈ 128K）。

H_ctx：在 ctx_req(t) > W 的子集 S_overflow 上，多 agent 的 Δ = ITT(multi) − ITT(single) 显著为正； 在 ctx_req(t) ≤ W 的子集 S_fit 上，Δ ≤ 0。 即 Δ 与 (ctx_req / W) 正相关，存在交叉点 ctx_req* ≈ W。

直觉：窗口够用时，单 agent 一口气做完最优（无交接损耗）；窗口不够时，单 agent 被迫压缩 → 丢细节 → 出错，而多 agent 各段小窗口 + 结构化交接保细节 → 赢。

分层口径

用 A0 的 per-task 指标做分层变量：

  • 分层变量：A0 per-task 峰值上下文（prompt_tokens）/ n_assistant_msgs / wall_sec
  • 分两层：S_overflow = 峰值上下文 > 阈值 T（例 T = 100K，接近 128K 窗口的 80%）；S_fit = ≤ T
  • 比较：在 S_overflow 和 S_fit 上分别算 A0 vs A1/A2 的 Δ 与 McNemar

当前数据：A0 per-task prompt_tokens 均值 2.0-2.5M（累计，非峰值窗口占用）；A1/A2 peak_ctx 均值 77-84K（峰值窗口占用）。40 题子集中绝大多数任务峰值 < 128K 窗口 → S_overflow 几乎为空 → 无法检验 H_ctx。

诚实说明

本 40 题子集无法检验 H_ctx。

原因：40 题子集是从 158 题中按 compaction 实验需求抽取的「中等难度」子集，峰值上下文 77-84K 远低于 128K 窗口。A1/A2 的 Δ≤0 恰好符合 H_ctx 在 S_fit 上的预测（窗口够用时多 agent ≤ 单 agent），但这是 H_ctx 的「弱支持」而非「否定」——因为缺少 S_overflow 的对照。

能检验 H_ctx 的任务构造方案：

  1. 取 158 全集中 A0 的 per-task trace 最长 top-k（n_assistant_msgs > 150 或 wall_sec > 2000s 的任务）——这些是最可能超窗的任务；
  2. 在 top-k 子集上重跑 A0 + A3/A4（小预算多 agent），看 Δ 是否在 top-k 上翻正；
  3. 若 top-k 的峰值上下文仍 < 128K → 说明 158 题本身不超窗 → 需构造更长任务（例：多文件联合修改、跨库 ref、长 API 链）才能检验 H_ctx。

🚫 不许用 40 题上的「无差异」去否定用户假设——40 题不超窗，本就不在 H_ctx 的作用域内。
