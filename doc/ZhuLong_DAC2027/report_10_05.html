2修复步骤（核心 · 复制粘贴即可）

§2-A 救 ops 中继（卡死 → 重启）

根因：昨晚运维把 git pull 写进了中继命令块 → git 的网络子进程继承了 stdout 管道，timeout 只杀 leader、子进程仍持有管道 → 中继读不到 EOF、.last_run_id 停摆（同 BaiZe §7 老坑）。

R=/nasdata/app.e0031982/code/super_intelligence_2035/doc/ZhuLong_DAC2027/run

# 1) 杀掉卡死的中继 + 残留的 git 子进程（关键：连 git 子进程一起清）
pkill -f zhulong_ops_relay.sh
pkill -f 'git .*pull'
pkill -f 'git fetch'
pkill -f 'git-remote-https'
sleep 3
ps -eo pid,ppid,args | grep -E 'zhulong_ops_relay|git .*pull|git fetch' | grep -v grep | cut -c1-160   # 期望：无输出

# 2) 在工作副本里（块外！）同步一次 —— 这一步绝不能放进 relay 块
cd $R && git pull --rebase --autostash

# 3) 重启中继
setsid bash $R/zhulong_ops_relay.sh > /tmp/zhulong_ops_relay.log 2>&1 < /dev/null &
sleep 3
pgrep -af zhulong_ops_relay.sh | cut -c1-160      # 期望：新的 bash zhulong_ops_relay.sh（ppid=1）
tail -n 8 /tmp/zhulong_ops_relay.log

4事故复盘（我该负的责 + 防复发）

直接原因RUN_ID 18 把 pkill legacy 与 git pull 放进同一个 relay 块 → git 网络子进程持有 stdout → 中继读不到 EOF 卡死；顺带把 legacy 的启停也一起失联。
为什么整夜没自愈36.15 的 GitHub 通道整夜无动作（对照 BaiZe 在 .12/.29 一直正常提交）—— 要么中继卡死，要么 36.15 出网断。
已固化到记忆MEMORY §7-17：relay 块内禁止任何 git 命令；接管/重启类块只做幂等动作；「停生产进程」与「动中继」绝不同块。
防复发清单① 块内无 git；② 每次只改一个变量；③ 改完立刻用一条无害探针验证通道；④ 停/启生产进程单独成块、幂等可重入；⑤ 变更前先确认在飞任务为空。
