DRC Connect QA 工具 —— 运行逻辑与检查方法

分析过的文件（仅阅读，未执行任何操作）：

  • connectivity/run.py 主脚本，537 行，python3.7，依赖 gdspy + calibre
  • connectivity/config 顶层配置模板（ruleType = LVS）
  • connectivity/ERC/config ERC 变体
  • connectivity/LVS/config LVS 变体
  • connectivity/LPE/config LPE 变体

1. 目的

针对真实 Calibre 规则文件（LVS / ERC / LPE）中 CONNECT 部分的 QA 校验工具。

该工具构建一个充满连接模式（patterns）的合成 GDS，这些模式的答案是已知的（KNOWN），然后用真实规则文件在其上运行两次 calibre，提取每个 marker 图形的网络 ID（net id），最后过滤结果，只保留错误的答案（WRONG answers）。

  • sameNet 单元：每个模式有两个 marker，它们必须落在同一条网络上。残留的结果 = 缺失的连接（OPEN，断路）。典型原因是某个 purpose 变体（CMP / SL / MATCH / CLOSE）没有被规则文件 CONNECT 进它所在的 layer net。
  • diffNet 单元：每个模式有两个 marker，它们必须保持在不同的网络上。残留的结果 = 多余的连接（SHORT，短路）。典型原因是 CONNECT 语句或 layer 定义过于宽泛。

处理后的 RDB 文件为空，表示该规则文件通过了本次 QA。

2. 调用方式与配置

python run.py <config_file>      # 恰好一个参数

配置文件是 Python 代码；run.py 会 exec() 它（第 451-456 行）。

rulePath       生成的 connect.drc 所 include 的真实规则文件
ruleType       LVS / ERC / ANT。仅在 ANT 特例中用于 are_layers_connected
               （使用距离 2 而不是 1）
topCell        生成的 GDS 的名称，也是输出 RDB 的后缀
connectivity   栈图（stack graph）。3 项：[lower, via, upper]；2 项：
               直接连接。方向很重要：边只会从 edge[0] 开始被跟随。
conn_layers    每个 layer 的 purpose 列表。第一项 = 主 drawing purpose，
               其余的是变体，各自获得一个 probe。
bottomLayer    路径枚举的起始节点，例如 [PG] 或 [PG, AT4]
connectOPC011  原样写入的 calibre 行，将 marker 层与真实导电层关联起来，
               例如 CONNECT OPC011 PGnet
precision      对 gdspy 和 RDB 头而言每微米的 dbu 数（4000）
markLayer      marker 所在的 GDS 层（10000，映射为 OPC011）

3. 阶段 1 —— 构建测试 GDS（connectivityCheck.gds）

find_all_paths（第 48 行）是对 connectivity 图做的一次递归 DFS，从每个 bottomLayer 条目出发（getPaths，第 77 行）。via 层会保留在路径中。死路（dead ends）会终止一条路径。LVS 配置示例：

PG -> PC2 -> M0C -> PCU -> M0U -> CT -> M1 -> V1 -> M2 -> ... -> M8 -> HSV -> HSP

会创建两个单元：sameNet（cell1）和 diffNet（cell2）。genTotal 为每个 path/layer/purpose 摆放一列模式；genPattern 绘制两列栈，并在 markLayer 10000 上放置 marker。marker 始终与栈的底层重叠，因此每个 marker 都会通过配置中的 CONNECT OPC011 行继承它所属栈的网络。

4. 阶段 2 —— 生成 connect.drc 并运行 calibre 两次

create_connect_file（第 415 行）写出 connect.drc：

#! tvf
tvf::VERBATIM {
    DRC RESULTS DATABASE  "AAAAA.drc.results"  ASCII
    LAYOUT PATH    "./<topCell>.gds"
    LAYOUT PRIMARY "diffNet"
    include "<rulePath>"
    LAYER OPC011 10000
    <connectOPC011 lines verbatim>
    drc select check test
    test{
        opcid = DFM PROPERTY OPC011 [netidnum = NETID(OPC011,1)]
        DFM RDB opcid "diffNet.rdb"
    }
}

NETID(OPC011,1) 会对每个 marker 图形报告：在应用 CONNECT 语句之后，该 marker 所属网络的 ID。

update_connect_file（第 365 行）原地修补 connect.drc：把 DFM RDB opcid 行改成目标 rdb 文件名；把 LAYOUT PRIMARY 行改成 sameNet 或 diffNet（被测单元）。

运行流程（第 526-529 行）：

update_connect_file("sameNet.rdb")  然后  calibre -drc -hier -turbo connect.drc
update_connect_file("diffNet.rdb")  然后  calibre -drc -hier -turbo connect.drc

风险：os.system 的返回码从未被检查，因此 calibre 二进制缺失或规则文件损坏时会静默失败。

5. 阶段 3 —— RDB 后处理（最终的判定）

main（第 388 行）+ process_net_file（第 198 行）重写原始的 calibre RDB。脚本统计每个 netidnum 值被多少个 group 携带，然后丢弃所有 netidnum 计数等于 target_count 的 group：

文件名包含 same -> target_count = 2  （丢弃正确的成对结果）
文件名包含 diff -> target_count = 1  （丢弃正确的单个结果）

最终存活下来的正是错误的答案：

sameNet_<topCell>.rdb ：marker 位于不同网络 -> OPEN（断路）嫌疑
diffNet_<topCell>.rdb ：marker 位于同一网络 -> SHORT（短路）嫌疑

清理（第 537 行）：rm -rf AAAAA* diffNet.rdb sameNet.rdb 会删除原始 RDB 和 AAAAA 结果/摘要；处理后的 RDB 和 GDS 会保留。

6. 输出以及如何判定它们

每个运行目录（已在 ERC/ 中确认）：

connectivityCheck.gds        生成的模式
connect.drc                  生成的规则文件，停留在 diffNet 状态
sameNet_<topCell>.rdb        OPEN 嫌疑；仅有表头 = 通过
diffNet_<topCell>.rdb        SHORT 嫌疑；仅有表头 = 通过
AAAAA.drc.results / summary  被清理步骤删除

历史上 ERC 的输出印证了该流程：两个处理后的 RDB 都只包含 5 行表头（calibre 曾报告 716 和 3634 个原始结果，全部被过滤掉），因此那次运行没有发现错误答案。一个空的 RDB 意味着“配置范围内通过”，而不是“CONNECT 部分是正确无误的”。

7. 怪癖与风险

  1. 对配置执行 exec()：配置是任意 Python 代码。
  2. calibre 失败是静默的（从未检查 os.system 的状态）。
  3. bad2 模式只生成一次，硬编码为路径索引 i == 1。
  4. 模式坐标单位是微米；precision 为 4000 意味着 GDS 中 dbu 为 0.25 nm，RDB 头中为每微米 4000 dbu。

8. 结论

该工具是对配置中声明的栈路径进行的一次针对性一致性采样。在其作用范围内，它能够可靠地捕获缺失的 purpose 连接和多余的跨层 CONNECT，而历史上的 ERC / LVS / LPE 运行都干净通过。但规则文件实际连接的内容远多于配置所声明的，因此一个空的 RDB 只意味着“配置范围内通过”，而不是“CONNECT 部分是正确无误的”。
