1. 背景与目的

我们正在为 EDA Agent「烛龙」构建设计流评测集——一组用于评测 Agent 在数字电路设计流（design flow）上能力的评测用例集合。 评测用例交给评测框架执行：框架启动 Agent、供给 EDA 环境、收 Agent 产出的交付件、运行校验器、给出 pass/fail。

要让写出的评测用例能被评测框架直接使用，二者之间必须先明确一个接口协议——用例里有哪些字段、各字段什么含义、框架如何消费它们。 本文档的目的就是规定这个协议，让大家照着写出来的 case 能迅速嵌入框架执行，无需框架侧额外改动。

按业务，设计流用例分为数字、模拟、验证、测试等方向；各方向协议同构，本文档适用所有方向，后续按需出方向专属补充说明。

2. 设计流 case 的核心契约

一条设计流用例驱动 Agent 在 EDA 工程里完成一项多步任务并交付产物。契约是一条链：

一句话契约： 你写 prompt（任务目标，含所需文件/PDK 在 EDA NAS 上的路径）+ entry_point（交付件路径）+ test（校验交付件的脚本）。 框架负责开 session、让 agent 工作、收交付件、跑校验器、判分。你不需要管 session、沙盒、调度，也不需要管文件怎么传到 EDA 环境。

2.1 与 scripting 口径的根本差异

维度代码补全口径设计流口径（本指南）
模型做什么补全一个函数体多步驱动一个 flow
判分对象函数返回值（stdout 末行标记）交付件（zip / cellview / 报告）
test 校验什么check(candidate) 调被补全的函数check(deliverable, workdir) 校验交付件
状态单次沙盒调用内闭环跨多次调用，session workdir 持久
输入文件无（题面自含）路径写在 prompt 里（EDA NAS 上的绝对路径，agent 通过 run_commands 访问）

3. 字段继承与演进（对照表）

从 scripting 的字段集出发，继承有用的、抛弃没必要的、新增缺的：

字段代码补全口径现状设计流口径演进
task_id全局唯一继承，前缀 EDA-Eval-DesignFlow-<方向>-NNN
mode（无，隐含 completion）新增，固定 "design_flow"
prompt代码补全题面（空函数体）重定义：自然语言任务目标（无函数体、无空签名）
entry_point待补全的函数名重定义：交付件路径（相对 workdir），test 的校验对象
testcheck(candidate) 校验函数重定义：check(deliverable, workdir) 交付件校验器
lang脚本语言 pyAether/skill/tcl抛弃：设计流不限定单一脚本语言，agent 混合用 SKILL/Tcl/shell
hostEDA 运行时（解释器宿主）抛弃：设计流一条 flow 可能跨多个 EDA 工具，让 case 填单个 host 不合理；所需 EDA 环境/license 由评测运行配置指定，不进 case
metadata可选统计继承，增加 domain（digital/analog/verification/test）
为什么丢 lang 和 host： 设计流 agent 不"用某一种语言补全一段代码"，而是用多种工具驱动整条 flow——lang 失去意义。 一条 flow 还可能跨多个 EDA 工具（如先 Virtuoso 画原理图、再 Spectre 仿真），让 case 填单个 host 不合理； 所需 EDA 环境 / license / 轮次 / 时长预算属于评测运行配置，由跑评测时指定，不进 case。 业务方向（数字/模拟/验证/测试）放 metadata.domain，仅用于分类统计。

4. 逐字段规范

4.1 task_id 继承

全局唯一。设计流统一前缀 EDA-Eval-DesignFlow-<方向>-NNN，方向取 Digital/Analog/Verification/Test，三位序号递增。

4.2 mode 新增

固定 "design_flow"。框架据此走 agentic 评测通路（开 session、多轮、交付件判分），与 scripting 的 completion 分流。

4.3 prompt 重定义

自然语言任务目标。把"要完成什么、交付什么、约束是什么、所需文件在哪里"讲清楚——这是 agent 唯一的任务说明。要点：

  • 写目标，不要写空函数体或代码签名（那是 scripting 的事）。
  • 明确交付什么（与 entry_point 对应：如"打包成 outputs/submit.zip，内含 5 个文件…"）。
  • 明确约束（在哪个库建 cell、用什么工艺、仿真精度、指标阈值）。
  • 所需文件 / PDK 路径直接写在 prompt 里（EDA NAS 上的绝对路径），如"测试激励模板在 /eda_nas/.../tb_inverter.scs""PDK 目录 /eda_nas/pdk/..."。agent 通过 run_commands 在 EDA 服务器上访问这些路径。不要用 attachments 字段（当前版本暂不支持）。
为什么路径写在 prompt 里：EDA 环境（32.75）与开发环境（36.15）的 NAS 不互通。所需文件必须放在 EDA NAS 上（DE 可在 EDA 环境的任意服务器上保存），agent 在 EDA 服务器上执行命令时才能访问。 可用路径由长鑫侧统一提供，不要硬编码未经确认的路径。

见 §5。

4.5 test 重定义 · 交付件校验器

见 §7。

4.6 所需文件 / PDK 路径写在 prompt 里

当前版本暂不支持 attachments 字段。任务所需的输入文件（电路网表、工艺库定义、testbench 模板、参考波形…）和 PDK 目录，一律把 EDA NAS 上的绝对路径写在 prompt 里，agent 通过 run_commands 在 EDA 服务器上访问。详见 §6。

5. 交付件 entry_point

这是设计流判分的锚点——agent 必须产出它，test 校验它。entry_point 路径必须与 prompt 里要求 agent 产出的路径严格一致，否则 test 里"交付件存在"的 assert 会直接失败。两种形态：

形态 A：文件路径（最常见，如 zip 包）

"entry_point": "outputs/submit.zip"

相对 session workdir 的路径。agent 把所有要求产物打包到这里；test 解包校验。适合"多个文件交付"（你的 5 文件 zip 就是这种）。

形态 B：结构化指针（指向 EDA 工程内对象）

"entry_point": {
  "library": "my_lib",
  "cell": "inverter",
  "views": ["schematic", "symbol"]
}

指向 agent 在 EDA 工程里创建的对象（如 Virtuoso cellview）。test 直接在工程里打开校验，不必导出文件。适合"产物就是工程内对象"的任务。

选哪种？ 交付"一组文件/报告"用 A（zip）；交付"工程里建好的 cell/设计"用 B（结构化）。两者 test 都能处理，check 第一个参数 deliverable 会拿到这个值。

6. 所需文件 / PDK 路径（写在 prompt 里）

任务除任务目标外还需要的输入文件（电路网表、工艺库定义、testbench 模板、参考波形…）和 PDK 目录，当前版本不通过 attachments 字段传递，而是直接把路径写在 prompt 里。

文件位置：EDA 环境（32.75）与开发环境（36.15）的 NAS 不互通。所需文件必须放在 EDA NAS 上（DE 可在 EDA 环境的任意服务器上保存），agent 通过 run_commands 在 EDA 服务器上执行命令时可直接访问。 可用路径由长鑫侧统一提供，不要硬编码未经确认的路径。

写法示例

在 prompt 里直接给出路径，例如:

"测试激励模板在 /eda_nas/designs/analog/tb_inverter.scs，请基于它搭建 testbench。
 PDK 目录: /eda_nas/pdk/skywater130/，工艺库定义: /eda_nas/designs/analog/lib.defs。
 参考网表(可选,供对照): /eda_nas/designs/analog/ref_netlist.cdl。"
要点说明
路径形态EDA NAS 上的绝对路径（如 /eda_nas/.../tb_inverter.scs）；不要用相对路径（agent 的工作目录由框架在 EDA 服务器上创建，你不必要知道）
可用路径由长鑫侧统一提供（刘杨），不要硬编码未经确认的路径
PDK 目录同样在 prompt 里给出绝对路径
可选文件参考网表、参考波形等供 agent 对照的文件，也写路径并标注"可选"

7. 交付件校验器 test 的约定

test 是一段内联代码（字符串），定义交付件校验器。语义与 scripting 的 check(candidate) 不同：

签名约定： 必须定义 check(deliverable, workdir)，两个参数：
  • deliverable = entry_point 的值（文件路径字符串，或结构化对象）。
  • workdir = session 工作目录绝对路径（附件、产物都在这里）。
在 check 内用断言校验交付件；不要自己打印 OK/FAIL 标记——框架会自动包一层执行入口，据 check 是否抛错打印判定标记。

校验器写法（按脚本语言）

设计流一条 flow 可能跨多个 EDA 工具，test 校验器用哪种脚本语言写，由你根据任务涉及的 EDA 工具决定（如交付件在 Virtuoso 工程里 → 用 SKILL；在 Innovus 工程里 → 用 Tcl）。框架据 test 代码语言选择解释器执行。

  • SKILL（Virtuoso）：用 unless(...) error("...") 断言；check 末尾返回 t。
  • Tcl（Innovus 等）：框架自动注入公共 assert 过程，直接用 assert {<expr>} "msg"（与 scripting Tcl 一致，不要重复定义 assert）。
  • 需要解 zip / 读报告 / 调外部工具时，用对应宿主的系统调用（SKILL system()、Tcl exec）。

框架自动生成的执行入口（你不用写，了解即可）

# 以 SKILL 为例, 框架拼在 test 之后:
if( errset(check("outputs/submit.zip" "<workdir>")) then
    println("DesignFlow-case-OK")
else
    println("DesignFlow-case-FAIL")
)
# Tcl 同构: catch {check $deliverable $workdir} ... puts Innovus-case-OK/FAIL
判分语义（两态，与 scripting 一致）：框架运行 check，据是否抛错判定：
  • check 不抛错（所有 assert 通过）⇒ pass
  • check 抛错（任一 assert 失败，含交付件不存在）⇒ fail
交付件存在性只是 check 里的一个 assert（如 unless(isFile(zip) error("deliverable missing"))），不需要框架单独处理。你只要做到"断言全过 ⇒ 不抛错"即可。

8. 完整示例：CMOS 反相器原理图 + 功能仿真

这是模拟方向的真实设计流任务：建原理图 → 建 symbol → 搭 testbench → 跑 Spectre → 验逻辑反相 → 打包交付。

7.1 拆开看各字段

prompt（任务目标，agent 看到的）

在指定 EDA 工程中创建一个 CMOS 反相器原理图，并完成初步功能仿真，验证输出与输入的逻辑反相关系。

所需文件 (EDA NAS 上的绝对路径):
- 测试激励模板: /eda_nas/designs/analog/tb_inverter.scs
- 工艺库定义:   /eda_nas/designs/analog/lib.defs
- PDK 目录:     /eda_nas/pdk/skywater130/

要求:
1. 在目标库 my_lib 下创建 cell inverter，schematic view：由一个 PMOS 与一个 NMOS
   构成标准 CMOS 反相器（源极分别接 VDD/GND，栅极共接为输入 Vin，漏极共接为输出 Vout）。
2. 生成 symbol view。
3. 搭建 testbench（基于上述 tb_inverter.scs 模板），对 Vin 施加 0→VDD 的扫描，运行 Spectre 仿真。
4. 将以下 5 个文件打包为 outputs/submit.zip 作为交付件:
   - schematic.cir   (原理图导出网表)
   - symbol.cir      (symbol 导出)
   - tb_inverter.scs (测试激励网表)
   - sim_inverter.log(仿真日志)
   - inverter_wave.raw(仿真波形/结果)

entry_point（交付件路径）

"outputs/submit.zip"

test（交付件校验器，SKILL）

procedure(check(deliverable workdir)
  let((zip tmp files vdd vout_hi vout_lo)
    ;; (0) 交付件存在
    zip = strcat(workdir "/" deliverable)
    unless(isFile(zip) error(strcat("deliverable missing: " zip)))

    ;; (1) 解包到临时目录
    tmp = strcat(workdir "/__check_tmp")
    system(strcat("rm -rf " tmp " ; mkdir -p " tmp " ; unzip -o -q " zip " -d " tmp))

    ;; (2) 5 个产物文件齐全
    files = list("schematic.cir" "symbol.cir" "tb_inverter.scs"
                 "sim_inverter.log" "inverter_wave.raw")
    foreach(f files
      unless(isFile(strcat(tmp "/" f))
        error(strcat("missing artifact in zip: " f)))
    )

    ;; (3) TODO(与长鑫对齐): 打开 schematic.cir / cellview, 校验 PMOS+NMOS 连接拓扑
    ;;     (栅极共 Vin / 漏极共 Vout / PMOS 源接 VDD / NMOS 源接 GND)

    ;; (4) TODO(与长鑫对齐): 解析 inverter_wave.raw / sim_inverter.log,
    ;;     断言逻辑反相:
    vdd = 1.2   ; 工艺电源电压, 按实际工艺填
    ;; vout_hi = parse_wave(tmp "/inverter_wave.raw" vin=0.0)
    ;; vout_lo = parse_wave(tmp "/inverter_wave.raw" vin=vdd)
    ;; unless(vout_hi > vdd*0.9) error("Vin=0 时 Vout 未拉高, 非反相")
    ;; unless(vout_lo < vdd*0.1) error("Vin=VDD 时 Vout 未拉低, 非反相")

    ;; 清理临时目录
    system(strcat("rm -rf " tmp))
    t
  )
)
关于 TODO：校验器里标注 TODO(与长鑫对齐) 的两段（原理图拓扑校验、波形解析断言）依赖具体 EDA 环境的 API 与工艺参数。 真值阈值、工艺电压、可用解析命令由长鑫侧统一提供，编写者先用占位骨架，最终校验逻辑由双方对齐后固化。

10. 交付与命名约定

  • 文件格式：JSONL，每行一道 case，行内紧凑 JSON。
  • task_id：EDA-Eval-DesignFlow-<方向>-NNN，方向 Digital/Analog/Verification/Test，全局唯一。
  • 所需文件/PDK 路径：写在 prompt 里（EDA NAS 上的绝对路径），不要用 attachments 字段（当前版本暂不支持）。可用路径由长鑫侧统一提供。
  • 提交方式：把 JSONL 交给长鑫侧入库，编写者不需要改框架/配置/沙盒，也不需要提交 assets 目录。
  • 真值与工艺参数：校验器里的真值阈值、工艺电压、可用设计/库路径，统一由长鑫提供后固化，避免硬编码失效。

11. 常见错误自查清单

症状原因修正
数据集加载即报错缺 mode，或 mode 非 design_flowmode="design_flow"
还带着 lang / host / budget 字段沿用 scripting 习惯或旧版设计流草案设计流不要这三个字段，删掉；EDA 环境/预算由评测运行配置指定
entry_point 写成函数名沿用 scripting 语义设计流里它是交付件路径，不是函数名
test 写成 check(candidate)沿用 scripting 签名改为 check(deliverable, workdir)，校验交付件
判分恒失败但产物看着对在 check 里自己 puts/println 了 OK/FAIL 标记，污染末行删掉自定义标记输出，只留断言
agent 找不到所需文件prompt 里没给文件/PDK 的 EDA NAS 路径，或路径未经长鑫确认所需文件路径写在 prompt 里（EDA NAS 绝对路径）；可用路径找刘杨确认
交付件路径 agent 产物对不上entry_point 与 prompt 里要求的产出路径不一致两者严格一致；路径相对 workdir
校验器跑飞 / 误判临时目录未清理、真值阈值写死错值结尾清理临时目录；阈值/工艺参数与长鑫对齐
Tcl 校验器 assert 报未定义重复定义了框架已注入的 assert直接用框架注入的 assert，不要重复定义
