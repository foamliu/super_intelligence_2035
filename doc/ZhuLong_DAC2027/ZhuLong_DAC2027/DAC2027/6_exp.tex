\subsubsection{Research Questions}

The framework of Section~\ref{sec:grounding-theory} makes three testable claims: that the grounding gap is bounded by observation fidelity rather than by the prior; that bridging it requires a runtime architecture supplying observation, belief update and execution; and that this follows from the domain's structure rather than from one toolchain. We ask one research question per claim.
% 第~\ref{sec:grounding-theory}节的框架给出三条可检验主张：落地鸿沟受观测保真度而非先验约束；
% 弥合它需要一个同时提供观测、信念更新与执行的运行时架构；这一点源于领域结构而非某个工具链。
% 我们针对每条主张提出一个研究问题。

\begin{itemize}
\item \textbf{RQ1 (Ceiling: observation or prior?).} Is the achievable accuracy bounded by the fidelity of the observation channel $\Omega$, or by the strength of the frozen prior $\mathcal{K}$? We answer from both sides: the observation-fidelity ladders (S1) vary $\Omega$ with the LLM fixed, and the prior-axis contrast (S3) varies $\mathcal{K}$ with the harness fixed.
\item \textbf{RQ2 (Which components are necessary, and are they interchangeable?).} Does bridging the gap require observation, execution through a causal interface, and continuous belief update---and can one of the three substitute for another? S2 varies the effector's presence and the belief-update budget.
\item \textbf{RQ3 (Domain class or toolchain?).} Does the same structure reproduce on a structurally different toolchain? The protocol of S1--S2 is re-run on the SKILL and Tcl slices of \textbf{EDA-Scripting-Bench}, so the comparison is made \emph{within} one benchmark rather than across separate artifacts.
\end{itemize}
% RQ1（天花板：观测还是先验？）可达准确率受观测通道$\Omega$的保真度约束，还是受冻结先验$\mathcal{K}$的强度约束？
% 我们从两侧回答：保真度阶梯（S1）固定LLM改变$\Omega$；先验轴对照（S3）固定框架改变$\mathcal{K}$。
% RQ2（哪些组件是必要的？它们可互换吗？）弥合鸿沟是否同时需要观测、经由因果接口的执行、以及持续的信念更新？
% 三者能否相互替代？S2改变执行器是否在场与信念更新预算。
% RQ3（领域类还是工具链？）同一结构能否在结构不同的工具链上复现？
% S1–S2的协议在EDA-Scripting-Bench的SKILL与Tcl切片上重跑，因此比较发生在同一评测集内部，而非跨不同工件。

RQ1 and RQ2 test the framework's structural claims; RQ3 tests whether they follow from the domain's structure rather than from one toolchain. Because RQ1's two arms sit in different studies, we read them against each other rather than in isolation.
% RQ1与RQ2检验框架的结构性主张；RQ3检验这些主张是否源于领域结构而非某个工具链。

\subsubsection{Benchmark and Evaluation Protocol}

We evaluate ZhuLong on \textbf{EDA-Eval-PyAether}, a benchmark of 158 real-world PyAether scripting tasks. Following the evaluation protocol defined in Section~\ref{sec:benchmark}, we adopt \textbf{Pass@1} (execution success rate) as the primary metric. Each task is evaluated in a single trace: the agent may iterate \emph{within} that trace through the belief update $\Phi$ (Section~\ref{sec:agent-workflow}), but a task is never restarted across traces; the timeout is set to 2500 seconds per execution. Every tool call is additionally mediated by a file-based \texttt{PreToolUse} hook---a JSON-in/JSON-out script dispatched by Cline's hook engine from the configured hooks directory---that enforces a tool whitelist, blocks shell and code-search tools, and confines all file access to a fresh, empty working directory; on each call it allows the call, rewrites it to a harmless no-op (\texttt{overrideInput}), or rejects it with an error message (\texttt{cancel}), with MCP tool calls passing through, so neither a task's own assertions nor any project copy of a solution is reachable from the workspace. The hook is identical in every configuration reported here and is thus part of the fixed protocol rather than a variable; it is also what makes the baselines interpretable. Traces terminated by the hook are identified separately so that they are not read as capability failures. To assess statistical reliability given the modest benchmark size (158 tasks), each configuration is evaluated over five independent runs with reshuffled task orderings and fresh agent contexts, and accuracy is reported as mean $\pm$ standard deviation over those runs. Quantities aggregated over traces rather than over runs---read-back counts, activation ratios and tool-call totals---are given as single aggregates over the pooled traces, without run-level dispersion; effect sizes ($\Delta$) are computed from the mean values in the same table. Generation-stage failures---tasks that produce no executable code, e.g.\ due to timeout or an exhausted message budget---are counted as not-passed and remain in the 158-task denominator; for the S2 low-budget arms this generation failure (gen-fail) is the direct consequence of the $\Phi$ execution budget being exhausted, not an infrastructure fault. Run validity is gated separately: a run that suffers an infrastructure fault (license exhaustion, sandbox port unreachable, or insufficient disk) is discarded and re-run, and is not counted toward the five runs; the anti-leak hook is held identical across all arms. To isolate infrastructure degradation from ablation effects, the full-system anchor is required to reach at least 75\% Pass@1 as a health floor---a run below it signals an infrastructure problem rather than a capability result and is re-run---while ablation arms have no such floor, so that their (sometimes low) scores reflect the true ablation effect. The dominant sandbox-execution effect ($+9.2$ pp) exceeds the spread by an order of magnitude, consistent with the theoretical account in Section~\ref{sec:grounding-theory}. All figures in this section are measured on the PyAether-only slice; the cross-language component ablation is reported in Section~\ref{sec:cross-language}, and the fidelity ($\Omega$) and belief-update ($\Phi$) axes are reported on PyAether only.

\textbf{Read-back axis.} The second axis is how much of the live state execution returns. Section~\ref{sec:bayesian} predicts that accuracy tracks this fidelity with the LLM held fixed; we therefore compare three closed-loop variants that differ only here: (N) \emph{no observation}---the agent predicts from the prior alone; (B) \emph{binary feedback}---\texttt{run\_code} reports only pass/fail; and (F) \emph{full observation}---stdout, exception traces, per-assertion outcomes, and queried state are returned (the default). The framework predicts a monotone gain from (N) to (F); the fresh 5-run measurement recovers the predicted ordering N$'$ $<$ B $<$ F; an earlier legacy probe had suggested the opposite, as analyzed below. We emphasize that the three rungs compress the \emph{same} executed state to different bandwidths: (F) returns the full \texttt{error\_log}/\texttt{print\_log}/\texttt{result}; (B) collapses this to a single bit---\texttt{PASS} means only that the sandbox raised \emph{no exception} (an empty \texttt{error\_log}), not that the task's assertions held; and (N$'$) returns only the literal token \texttt{executed}. A binary \texttt{PASS} is therefore a content-free confirmation that can endorse a wrong hypothesis, which is the mechanism the analysis below appeals to.

Beyond accuracy, the read-back rungs differ sharply in \emph{convergence cost}---how much execution the agent must spend to reach a submission. Table~\ref{tab:readback-cost} aggregates per-trace execution traces retained from the runs above: the mean number of \texttt{run\_code} calls per task, the wall-clock of the code-generation phase, and the count of tasks that hit the per-task time limit (a proxy for non-convergence). With the LLM and effector fixed, dropping the observation bandwidth from (F) to (B) substantially inflates the work the agent does per task: mean read-backs rise from 12.1 to 22.3 ($\sim$$1.8\times$), the code-generation wall-clock rises from 2.22~h to 3.73~h ($\sim$$1.7\times$), and the number of timed-out tasks rises from a mean of 3.4 to 7.6 ($\sim$$2.2\times$). The mechanism is visible in the traces: under (B) every execution returns \texttt{\{"response": "PASS"/"FAIL", "error\_log": "", "print\_log": ""\}}---the agent learns only that an exception was or was not raised, never which assertion failed or what the stack trace said, so it must hypothesize a correction blind and re-execute. One (B) trace issues 287 \texttt{run\_code} calls on a single task, cycling through \texttt{PASS}/\texttt{FAIL} verdicts with empty error logs. This is the cost-side counterpart of the accuracy result: poorer observation does not merely cap accuracy, it inflates the search effort needed to converge, and when the budget is fixed (per-task timeout) some tasks simply fail to converge in time---exactly the ``fidelity down $\to$ convergence cost up'' trade-off Principle~2 implies. We note that the fresh 5-run binary re-measurement reaches 78.1$\pm$1.3\% Pass@1 (replacing the legacy single-run probe's 66.2$\pm$16.1\% whose 43.0\% outlier had inflated the spread), and it restores the monotone N$'$\,$<$\,B\,$<$\,F ordering predicted by Principle~2. The convergence-cost figures reported here are aggregated from the retained execution traces of the fresh 5-run binary measurements (Mean \texttt{run\_code}, Wall, and Timeout are each 5-run means $\pm$ sample std). \subsubsection{S2: The closed loop (RQ2)}
\label{sec:closed-loop}

Principle 3 requires two things: that actions reach the design through a causal interface, and that the belief update $\Phi$ run continuously.

\textbf{Effector: does the action reach the live design?} Removing the sandbox from the full system drops Pass@1 from 81.4\% to 72.2\% ($-9.2$~pp; McNemar $p{<}10^{-8}$, paired bootstrap 95\% CI $[-13.1, -5.4]$~pp); adding it to the RAG baseline raises it from 72.2\% to 81.4\% ($+9.2$~pp, same significance). Without an effector no $a_t$ is executed against the design, so $b_t$ receives no evidence about the live state at all and the agent is reduced to a prior-only predictor. We attribute the gain to two mechanisms: execution returns concrete error messages that guide corrections, transforming one-shot generation into iterative search, and it lets the agent probe parameter combinations that documentation omits~\cite{kumar2026agentforge, jiang2024seed}.
% 执行器：动作是否抵达实时设计？从完整系统移除沙盒使Pass@1从81.4\%降至72.2\%（-9.2pp）；
% 把沙盒加入RAG基线使其从72.2\%升至81.4\%（+9.2pp）。没有执行器，$a_t$未被作用于设计，
% $b_t$得不到任何关于实时状态的证据，智能体退化为仅凭先验的预测器。

\textbf{Belief update: how much evidence may $\Phi$ accumulate?} ZhuLong is an ICL-type autonomous agent: once the task is issued it plans, queries the API knowledge base, and executes and debugs code on its own, and it is the agent---not the harness---that decides when the result is good enough to submit. We therefore do not shorten the loop or force an early submission; we bound how often the loop \emph{may execute}, which is what determines how much state evidence $b_t$ ever receives. Operationally the bound is the number of \texttt{run\_code} calls a trace is allowed: once the budget is spent, the call is denied at the tool boundary by a second, co-resident \texttt{PreToolUse} hook that counts \texttt{run\_code} calls per trace; its error carries a unique \texttt{{[PHI-BUDGET-EXHAUSTED]}} prefix because Cline's hook engine OR-merges cancellations and concatenates their reasons, which would otherwise make the anti-leak hook's denials indistinguishable from the budget hook's, and the agent keeps running under its own control until it chooses to submit. Because termination stays with the agent, we report the harness's own finish reason next to accuracy---\emph{completed} (the agent decided it was done) versus \emph{max iterations} or budget-denied---so that a tight budget cannot be mistaken for early convergence. In an agent with no explicit posterior, $\Phi$ is realized by what remains in the model's context, so Table~\ref{tab:phi-bound} additionally includes a lagged channel realized as a single-slot ($L{=}1$) buffer in the \texttt{run\_code} handler, whose read-back returns the state emitted by the previous execution---with a \texttt{reported\_call\_index} recorded so the one-step lag is auditable---leaving the agent permanently one action behind the design; the first read-back carries no state, and every other setting is unchanged. Both axes leave the LLM, the observation content and the effector untouched. Principle 3 predicts that accuracy rises with the execution budget but saturates once updates are fast enough for the design's own dynamics, since evidence obtained before the previous action is partly obsolete by the time the next action is chosen.

% 执行并调试代码，并由智能体（而非框架）决定结果何时足够好可以提交。

\subsubsection{L4: Situated truthfulness violations.}
% L4：情境真实性违反

The agent selects the correct API family and the generated code executes, but the result violates an undocumented contract that the C++-generated bindings enforce or the test oracle checks---hidden type expectations, internal state dependencies, or runtime-context preconditions that documentation does not reveal.

\textit{Case study: Task 010 (add\_instance\_to\_schematic).} The agent's code creates a schematic instance from a master cellview. Its own \texttt{run\_code} tests report ``ALL ASSERTIONS PASSED'' and the instance is created successfully (\texttt{ntn\_inst: db: 0x13f961a}). Yet the official harness fails with \texttt{AssertionError: target\_cv must be an opened cellview object.} The agent passed a cellview handle that was valid in its own execution context but did not satisfy the ``opened'' precondition the test oracle enforces---a property of the live design state (L4), not of the API signature (L3).

\textit{Case study: Task 063 (get\_cell\_file\_type).} The agent calls a function that returns an internal type name such as \texttt{"maskLayout"}, while the test harness uses a different getter that produces \texttt{"cellFileType"}. The API name is correct and the call succeeds, but the returned type depends on which internal representation the binding exposes---a situated property of the design database, not a documented return value. The agent cannot distinguish these without executing against the live design and reading back the actual type.

\textit{Case study: Task 146 (classify\_device\_types).} The agent's 133-line classifier passes all its own assertions, but the official harness raises \texttt{AttributeError: type object 'Param' has no attribute 'value'}. The internal \texttt{Param} type exposes attributes differently depending on the runtime context; the agent accessed \texttt{param.value} based on documentation that describes the logical property, but the binding object does not expose \texttt{.value} in the test's execution path. The attribute's availability is a situated property of the object's runtime state, not a documented API contract.

Other L4 instances follow analogous patterns: Task~074 attempted to create a \texttt{QStringList} via a self-invented wrapper that does not exist, because the C++ binding expects a specific type the documentation does not show how to construct from Python; Task~155 correctly implemented the \texttt{aeGetCommandPoint} call chain, but the function returns \texttt{False} in the headless sandbox rather than the \texttt{emyPointF} object the test expects---the return type depends on whether a GUI draw area is active, a runtime-context property the agent observed but could not resolve.
\subsubsection{L3: Semantic and logic errors.}

The agent selects individually valid APIs, and the generated code executes without runtime errors, but the composition logic---parameter propagation, post-processing, or control flow---fails the test oracle. These failures are harder to detect because each call appears correct in isolation.
% 智能体选择了各自有效的 API，生成的代码无运行时错误地执行，但组合逻辑——参数传递、后处理或控制流——未能通过测试预言。此类失败更难检测，因为每个调用单独看都是正确的。

\textit{Case study: Task 052 (check\_view\_list).} The specification required invoking \texttt{EmyNtlUtil.checkViewList} for netlist view validation. Instead, the agent implemented a custom validator using pure Python logic. The code printed ``All assertions passed'' in its own embedded tests, but the harness applied standard validation on a different configuration, where the heuristic returned an error message rather than \texttt{"VALID"}. The agent replaced the mandated library call with an approximation, violating the test assertion.
% 案例研究：任务 052（check_view_list）。规范要求调用 \texttt{EmyNtlUtil.checkViewList} 进行网表视图校验。智能体却实现了纯 Python 的自定义校验器。代码在自嵌入测试中打印“All assertions passed”，但测试夹具在另一配置上应用标准校验，此时自定义启发式规则返回了错误消息而非 \texttt{"VALID"}。智能体用近似逻辑替换了强制库调用，违反了测试断言。

\textit{Case study: Task 058 (batch\_oge\_job\_policies).} The agent used substring matching (\texttt{"high" in queue\_name}) instead of the equality check (\texttt{queue\_name == "priority"}) required by the specification, producing wrong \texttt{misc} parameter values. The API call itself was correct, but the logic governing which input maps to which parameter value was semantically wrong---a specification-comprehension failure (L3), not a type or context failure (L4).

The remaining L3 instances---Task~017 (instance-counting logic returns 0 instead of 2) and Task~144 (property set to \texttt{None} where a concrete value is expected)---follow the same pattern: valid API calls composed with incorrect logic.


% L3 案例：任务 052 用自定义校验器替代强制库调用；任务 058 用子串匹配替代相等性检查。其余 L3：任务 017（实例计数逻辑返回 0）、任务 144（属性设为 None）——有效 API 调用组合了错误逻辑。

\subsubsection{Generation-stage failures.}
% 生成阶段失败

The 17 generation-stage failures fall into three sub-categories (Table~\ref{tab:error-categories}). \emph{Timeout} (4 tasks): the agent exceeded the 2500\,s per-task limit on complex multi-step design-creation tasks requiring 24--41 APIs; traces show ongoing reasoning at termination, indicating computational-budget constraints rather than capability limits. \emph{Wrong save path} (10 tasks): the agent completed code generation and saved a valid \texttt{.py} file, but to the workspace root (\texttt{ws/}) instead of the expected \texttt{ws/pyAether\_code/} sub-directory, so the evaluation harness could not locate it. \emph{No code produced} (3 tasks): the agent's session was cancelled or ended without writing a code file, typically due to early termination on tasks with sparse documentation.

The wrong-save-path failures are notable because the generated code is likely correct---the agent solved the task but lost the point on a procedural error. This is an L1-level failure (instruction following) rather than an L4 failure (situated truthfulness), and it is amenable to harness-level mitigation (stricter output-path enforcement) rather than to improved API knowledge.
% 17 个生成阶段失败分为三类：超时（4个，24–41 API 复杂任务超 2500s）、错误保存路径（10个，存到 ws/ 而非 ws/pyAether_code/）、未产出代码（3个）。错误保存路径值得注意：代码可能正确但因程序性错误失分——L1 级失败而非 L4，可通过框架层面缓解。

\subsubsection{Implications.}
% 启示

The L1--L4 classification makes the grounding-gap framework concrete: 67\% of execution-stage failures are L4 (situated truthfulness violations), 33\% are L3 (semantic/logic), and 0\% are L1 or L2. No amount of offline knowledge---richer documentation, larger model, better retrieval---can prevent L4 failures, because the violated contracts are not visible until the agent acts on the live design and reads back the result. This is exactly why the execution loop is decisive (Section~\ref{sec:closed-loop}): the sandbox does not merely ``run the code,'' it is the only channel through which the agent can observe the hidden type contracts, internal selection states, and runtime-context dependencies that constitute two-thirds of the execution-stage failures. The generation-stage failures, by contrast, are mostly procedural (wrong save path) or budget-constrained (timeout), and are amenable to harness-level fixes rather than to knowledge improvements. These findings motivate type-aware API documentation and case-level knowledge distillation, where resolved L4 failures are stored as reusable experiences, forming the basis of agent self-evolution.
% L1–L4 分类使落地鸿沟框架具体化：执行阶段失败中 67% 为 L4，33% 为 L3，0% 为 L1 或 L2。无论多少离线知识都无法防止 L4 失败。这正是执行闭环决定性的原因：沙盒是观测隐藏类型契约、内部选中状态、运行时上下文依赖的唯一通道。生成阶段失败多为程序性或预算受限，可通过框架层面修复。这些发现推动了类型感知 API 文档和案例级知识蒸馏。
