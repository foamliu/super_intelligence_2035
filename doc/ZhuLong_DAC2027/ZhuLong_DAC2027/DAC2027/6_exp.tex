\subsection{Experimental Setup}
\label{sec:exp-setup}

\subsubsection{Research Questions}

The framework of Section~\ref{sec:grounding-theory} makes three testable claims: that the grounding gap is bounded by observation fidelity rather than by the prior; that bridging it requires a runtime architecture supplying observation, belief update and execution; and that this follows from the domain's structure rather than from one toolchain. We ask one research question per claim.
% 第~\ref{sec:grounding-theory}节的框架给出三条可检验主张：落地鸿沟受观测保真度而非先验约束；
% 弥合它需要一个同时提供观测、信念更新与执行的运行时架构；这一点源于领域结构而非某个工具链。
% 我们针对每条主张提出一个研究问题。

\begin{itemize}
\item \textbf{RQ1 (Ceiling: observation or prior?).} Is the achievable accuracy bounded by the fidelity of the observation channel $\Omega$, or by the strength of the frozen prior $\mathcal{K}$? We answer from both sides: the observation-fidelity ladders (S1) vary $\Omega$ with the LLM fixed, and the prior-axis contrast (S3) varies $\mathcal{K}$ with the harness fixed.
\item \textbf{RQ2 (Which components are necessary, and are they interchangeable?).} Does bridging the gap require observation, execution through a causal interface, and continuous belief update---and can one of the three substitute for another? S2 varies the effector's presence and the belief-update budget.
\item \textbf{RQ3 (Domain class or toolchain?).} Does the same structure reproduce on a different toolchain? S4 re-runs the protocol of S1--S2 on the SKILL and Tcl slices of \textbf{EDA-Scripting-Bench}, so the comparison is made \emph{within} one benchmark rather than across separate artifacts.
\end{itemize}
% RQ1（天花板：观测还是先验？）可达准确率受观测通道$\Omega$的保真度约束，还是受冻结先验$\mathcal{K}$的强度约束？
% 我们从两侧回答：保真度阶梯（S1）固定LLM改变$\Omega$；先验轴对照（S3）固定框架改变$\mathcal{K}$。
% RQ2（哪些组件是必要的？它们可互换吗？）弥合鸿沟是否同时需要观测、经由因果接口的执行、以及持续的信念更新？
% 三者能否相互替代？S2改变执行器是否在场与信念更新预算。
% RQ3（领域类还是工具链？）同一结构能否在结构不同的工具链上复现？
% S4在EDA-Scripting-Bench的SKILL与Tcl切片上重跑S1–S2的协议，因此比较发生在同一评测集内部，而非跨不同工件。

RQ1 and RQ2 test the framework's structural claims; RQ3 tests whether they follow from the domain's structure rather than from one toolchain. Because RQ1's two sides sit in different studies, we read them against each other rather than in isolation.
% RQ1与RQ2检验框架的结构性主张；RQ3检验这些主张是否源于领域结构而非某个工具链。
% 由于RQ1的两侧分布在不同研究中，我们将其相互对照而非单独解读。

\subsubsection{Benchmark and Evaluation Protocol}

We evaluate ZhuLong on \textbf{EDA-Scripting-Bench} (Section~\ref{sec:benchmark}), 449 real-world scripting tasks spanning PyAether, SKILL, and Tcl on four commercial runtimes, adopting \textbf{Pass@1} (execution success rate) as the primary metric. Each task is evaluated in a single trace---the agent may iterate \emph{within} it through the belief update $\Phi$ (Section~\ref{sec:agent-workflow}) but is never restarted across traces---with a 2500-second timeout per execution. Every tool call is mediated by a file-based \texttt{PreToolUse} hook that enforces a tool whitelist, blocks shell and code-search tools, and confines file access to a fresh working directory, so neither a task's assertions nor any reference solution is reachable; it is identical in every configuration and thus part of the fixed protocol rather than a variable. Hook-terminated traces are reported separately, not as capability failures.

Given the modest per-slice sizes (57--158 tasks), each configuration is evaluated over five independent runs (reshuffled task orderings, fresh agent contexts) and reported as mean $\pm$ s.d., per slice and pooled over all 449 tasks. Trace-level quantities (read-back counts, activation ratios, tool-call totals) are reported as single aggregates without run-level dispersion, and effect sizes ($\Delta$) are computed from the table means. The dominant sandbox-execution effect ($+13.2$ pp pooled) is several times the run-to-run spread; the smaller self-exploration effect ($+3.1$ pp) is treated as a complementary gain rather than a headline result, as predicted in Section~\ref{sec:grounding-theory}.
% 评测集与评估协议。我们在\textbf{EDA-Scripting-Bench}上评估ZhuLong，该评测集包含449个跨PyAether/SKILL/Tcl四商业运行时的真实脚本任务。
% 遵循第\ref{sec:benchmark}节定义的评估协议，我们采用\textbf{Pass@1}（执行成功率）作为主要指标。
% 每个任务只在单条trace上评测：智能体可在该trace内通过信念更新$\Phi$（第\ref{sec:agent-workflow}节）反复迭代，
% 但任务绝不跨trace重启；单次执行超时设为2500秒。此外，每次工具调用都经由基于文件的\texttt{PreToolUse} hook——
% 一个由 Cline hook 引擎自配置目录派发的 JSON-in/JSON-out 脚本——中介：它执行工具白名单、屏蔽 shell 与
% 代码搜索工具，并把文件读写限制在一个新建的空工作目录内；每次调用要么放行，要么改写为无害空操作
% （\texttt{overrideInput}），要么以错误信息拒绝（\texttt{cancel}），MCP 工具调用直接放行，
% 使任务的断言文件与任何项目内的参考解都不可达。

% 跨trace（而非跨运行）汇总的量——回读次数、激活比例、工具调用总量——按合并后的trace给出单一汇总值，

Two further properties support the comparisons' validity. Because the task cases derive from non-redistributable vendor documentation and customer designs (Section~\ref{sec:benchmark}), they are unlikely to appear verbatim in public pretraining corpora, limiting contamination. And because no third-party agent can execute these commercial runtimes without the MCP bridge under study, the baselines are tool-registration ablations of the same fixed harness rather than external systems---which is what makes single-variable attribution possible.

% 因此不太可能逐字出现在公开预训练语料中，这限制了基准污染。其二，任何第三方 agent 若无我们所研究的 MCP 桥接
% 便无法在这些商业运行时上执行，故基线以同一固定框架的工具注册消融而非外部系统实现；这一约束（而非疏漏）

\subsubsection{Baselines and ZhuLong Variants}

To isolate each component's contribution, we establish two baselines and three ZhuLong variants (Table~\ref{tab:configurations}), whose columns name the components a harness supplies: retrieval and documentation ($\Omega$, the observation channel), the sandbox (the effector through which an action reaches the live design), and self-exploration (offline enrichment of $\Omega$'s documentation). S1 probes the observation axes at their extreme endpoints, and S2 bounds the belief update $\Phi$, a component the table does not vary.
% 基线与ZhuLong变体。按第~\ref{sec:grounding-theory}节的框架解读，表中三列就是框架所提供的三个组件：
% 检索与文档是观测通道$\Omega$，沙盒是使动作抵达实时设计的执行器，自探索则是对$\Omega$可返回文档的离线增强。
% ZhuLong变体默认使用名称+描述索引进行向量检索；S1在两条观测轴的极端端点探针——文档轴上整体移除检索通道——S2则对信念更新$\Phi$加界，这是本表未涉及的组件。

Because every component is realized in the harness rather than inside the agent, each comparison isolates a single variable while the agent policy (model, prompt, decoding) is held fixed. Ablation acts only on tool registration---a disabled tool is unregistered and invisible to the agent, and every enabled tool runs the same implementation---so removing the sandbox unregisters \texttt{run\_code}, removing retrieval unregisters the three search tools, and the two self-exploration conditions differ only in the knowledge base served to retrieval. The anti-leak \texttt{PreToolUse} guard stays active throughout.
% 由于表中每个组件都在 harness 层实现、而非智能体内部，每次比较只分离单一操纵变量，而智能体策略（模型、提示词、解码）保持固定。
% 消融仅作用于工具注册：被禁用的工具从服务器注销、对智能体不可见；每个启用的工具在所有配置下执行同一实现。
% 移除沙盒即注销执行工具 run_code，移除检索即注销三个搜索工具；两个自探索条件只在检索所服务的知识库上不同，不涉及任何运行时工具。反泄露 PreToolUse 防护在所有配置中保持激活。

\subsubsection{S1: Observation fidelity (RQ1)}
\label{sec:omega-fidelity}

Principle 2 predicts that with the model fixed, accuracy is bounded by the fidelity of the observation channel $\Omega$. We vary $\Omega$ along the two axes through which it receives information, holding the LLM fixed in both.
% 原则2预测：固定模型时，准确率受观测通道Ω的保真度约束。我们沿Ω接收信息的两个轴改变Ω，两者均固定LLM。

\textbf{Documentation axis.} In Table~\ref{tab:main-ablation}, the agent loop, the effector and the LLM are held fixed while only how much of the environment's API facts the documentation channel exposes changes: nothing at all; retrieval removed entirely with the sandbox retained; a high-fidelity index adding descriptions, BM25 term matching, abbreviation expansion and synonym redirect; and that index enriched by offline self-exploration (Section~\ref{sec:selfdoc}). Removing retrieval costs 11.8~pp pooled, but the cost is highly toolchain-specific (Section~\ref{sec:cross-language}).
% 文档轴。表~\ref{tab:omega}(a)固定智能体循环、执行器与LLM，仅改变文档通道暴露多少环境API事实：
% 无暴露；整体移除检索（沙盒保留）；加入描述、BM25词项匹配、缩写展开与同义词重定向的高保真索引；
% 以及再经离线自探索增强的索引（第~\ref{sec:selfdoc}节）。PyAether 上移除检索仅损失 0.4pp（81.0 vs 81.4，在运行间噪声内），
% 但 SKILL 上损失 21.3pp（39.0 vs 60.3）、Tcl 上损失 14.1pp（73.1 vs 87.2），合并代价 11.8pp。

The PyAether result reflects the toolchain, and a trace-level analysis identifies the mechanism: with retrieval removed, 86.7\% of traces introspect via the sandbox, 56.5\% of \texttt{run\_code} calls are pure introspection, and 94.6\% of traces probe before implementing---against 49.0\%, 31.8\% and 34.1\% in the full system.\footnote{A trace is counted as introspective if any \texttt{run\_code} call invokes Python's runtime introspection facilities (e.g., \texttt{dir()}, \texttt{help()}, \texttt{inspect}, or reads \texttt{\_\_doc\_\_}). Counts are over 953 (full) and 886 (retrieval-removed) PyAether traces across five runs.} The agent enumerates the API namespace with \texttt{dir()}, recovers signatures with \texttt{inspect}/\texttt{\_\_doc\_\_}, and reads binding contracts off error messages; since PyAether docstrings are readable inside the sandbox, this reconstructs the same API knowledge retrieval would return. Retrieval is therefore one \emph{implementation} of $\Omega$, not the channel itself, and on PyAether the read-back channel substitutes for it; on SKILL and Tcl the Lisp-style and Tcl API surfaces cannot be recovered from execution alone, so removing retrieval removes the knowledge rather than relocating it.\todo{author: add SKILL/Tcl introspection stats (plan A)} The pooled 11.8~pp cost is thus a weighted average over slices where the two implementations are interchangeable and slices where they are not---the structure RQ3 asks about, not a defect of the ablation: what is substitutable is the \emph{implementation} of $\Omega$, not $\Omega$ itself, and the prior axis (Section~\ref{sec:k-axis}) shows no backbone substitutes for observation.
% PyAether 的结果不是反常，而是工具链属性，trace 级分析给出了机制。移除检索后，86.7% 的 trace 出现沙盒内省，
% 56.5% 的 run_code 调用为纯内省，94.6% 的 trace 先探测后实现——完整系统中分别为 49.0%、31.8%、34.1%。
% 脚注：一条 trace 若含任意一次调用 Python 运行时内省设施（如 dir()、help()、inspect、读 __doc__）的 run_code 调用，
% 即计为内省 trace；计数覆盖 953（完整）与 886（移除检索）条 PyAether trace（五次运行）。
% 智能体用 dir() 枚举 API 命名空间、用 inspect 与 __doc__ 恢复签名、从错误信息读取绑定契约；
% 在 PyAether 上 docstring 可直接在沙盒内读取，这实质上重建了检索本会返回的 API 知识。
% 因此检索只是观测通道 Ω 的一种\emph{实现}，而非通道本身，在该工具链上回读通道可以替代它。
% 在 SKILL 与 Tcl 上则不能：Lisp 风格与 Tcl 的 API 面无法仅凭执行恢复，因此移除检索是移除了知识本身，而非将其转移。
% 【待补数据】SKILL/Tcl 内省统计（方案 A）待 trace 分析后补入，正文暂按现有数据表述。
% 合并代价 11.8pp 因此是“可互换”与“不可互换”两类切片的加权平均——这正是 RQ3 所问的结构，而非消融的缺陷。
% 可替代的是 Ω 的实现（检索 vs 内省），而非 Ω 本身：S3 的先验轴表明没有任何主干能替代观测，
% 因为先验根本不是观测通道。

The intermediate rung corroborates this reading: the high-fidelity index without self-exploration scores 77.3 on PyAether, below both retrieval-removed (81.0) and full (81.4). The dip reflects the knowledge base served rather than the channel itself---this rung exposes the un-augmented V2 index, and its 4.1~pp gap to the self-exploration-enriched rung is exactly the self-exploration contribution measured next. Retrieval thus converges to the level introspection reaches alone only when its knowledge base is enriched: the two implementations meet at $\sim$81\% by different routes.
% 中间档与这一解读一致。无自探索的高保真索引（H）在 PyAether 上得 77.3，低于移除检索（81.0）与完整系统（81.4）。
% 这一凹陷反映的是所服务的知识库而非检索通道本身：(H) 暴露的是未增强的 V2 索引，
% 其与 (H+E) 之间 4.1pp 的差距恰为下一段测得的自探索贡献。
% 因此，检索路径只有在知识库被增强后才恢复到内省单独即可达到的水平——两种实现以不同路径收敛于约 81%。

\subsubsection{S2: The closed loop (RQ2)}
\label{sec:closed-loop}

Principle 3 requires two things: that actions reach the design through a causal interface, and that the belief update $\Phi$ run continuously.

\textbf{Effector: does the action reach the live design?} Removing the sandbox drops pooled Pass@1 from 75.7\% to 62.5\% ($-13.2$~pp; PyAether 81.4\% to 72.2\%), the retrieval-only baseline coinciding with this ablation by construction. Without an effector no action is executed against the design, so $b_t$ receives no evidence about the live state and the agent is a prior-only predictor. The gain comes from two mechanisms: execution returns concrete errors that guide correction (one-shot generation becoming iterative search), and it lets the agent probe parameter combinations documentation omits~\cite{kumar2026agentforge, jiang2024seed}.
% 执行器：动作是否抵达实时设计？从完整系统移除沙盒使合并 Pass@1 从75.7%降至62.5%（-13.2pp；PyAether 切片 81.4%→72.2%），
% 仅检索基线按定义与该消融合一。没有执行器，$a_t$未被作用于设计，$b_t$得不到任何关于实时状态的证据，智能体退化为仅凭先验的预测器。

\textbf{Belief update: how much evidence may $\Phi$ accumulate?} Because ZhuLong is an ICL-type autonomous agent (Section~\ref{sec:overall-architecture})---the agent, not the harness, decides when to submit---we do not shorten the loop or force early submission; we bound how often it \emph{may} execute, which determines how much state evidence $b_t$ ever receives. Operationally, the bound is the number of \texttt{run\_code} calls a trace may make: once spent, the call is denied at the tool boundary by a second, co-resident \texttt{PreToolUse} hook that counts calls per trace.\footnote{The denial carries a unique \texttt{{[PHI-BUDGET-EXHAUSTED]}} prefix because Cline's hook engine OR-merges cancellations and concatenates their reasons; without it, the anti-leak hook's denials would be indistinguishable from the budget hook's.} The agent keeps running under its own control, and we report the harness's finish reason next to accuracy---\emph{completed} versus \emph{max iterations}/budget-denied---so a tight budget cannot be mistaken for early convergence.

In an agent with no explicit posterior, $\Phi$ is realized by what remains in the context. Table~\ref{tab:phi-bound} therefore varies the evidence along two axes: the budget $k$, and a \emph{lagged} channel---a single-slot ($L{=}1$) buffer in the \texttt{run\_code} handler whose read-back returns the state emitted by the \emph{previous} execution (a \texttt{reported\_call\_index} makes the one-step lag auditable), leaving the agent permanently one action behind the design; the first read-back carries no state, and everything else is unchanged. Both axes leave the LLM, the observation content and the effector untouched. Principle 3 predicts accuracy rises with the execution budget but saturates once updates outpace the design's own dynamics, since evidence is partly obsolete by the time of the next decision.

% 因此我们不缩短循环、也不强制提前提交，而是给"循环可执行的次数"加界——

\textbf{API misuse}---the larger category---occurs when the agent selects the correct API family but violates contracts the C++-generated bindings enforce yet the documentation does not reveal: hidden type expectations, internal state dependencies, and context preconditions. In Task~098, passing a plain Python list to \texttt{aeSelectFigs} succeeded, but \texttt{aeDeleteObj} then failed because the internal C++ selection state was never populated; the runtime diagnostic carried no actionable signal, and five subsequent \texttt{run\_code} calls modified only the agent's own test harness rather than the type mismatch. \textbf{API composition and workflow errors} occur when individually valid calls are composed incorrectly---parameter propagation, post-processing, or control flow fails the oracle---or when a mandated library call is replaced by a plausible approximation (e.g., a substring match where equality is specified). Both categories share one signature: the violated constraint is invisible in documentation and only weakly exposed by execution---the L4 contract invisibility that Section~\ref{sec:grounding-theory} predicts situated correctness hinges on. These failures motivate two extensions: type-aware documentation surfacing binding-level contracts, and case-level knowledge distillation that stores resolved failures as reusable experience---the basis of agent self-evolution.
