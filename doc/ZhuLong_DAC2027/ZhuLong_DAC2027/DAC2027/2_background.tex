\section{Background and Motivation}
\label{sec:background}

We target three widely-used EDA scripting interfaces across four commercial runtimes: PyAether for Empyrean Aether \cite{empyrean_pyaether}, SKILL for Cadence Virtuoso \cite{cadence2024virtuoso}, and Tcl for Synopsys Custom WaveView and Cadence Innovus. Despite their prevalence, scripting for these environments poses challenges beyond what generic LLM code generators can address.
% 我们关注四种商业运行时上的三个广泛使用的EDA脚本接口：面向Empyrean Aether的PyAether、面向Cadence Virtuoso的SKILL、以及面向Synopsys Custom WaveView与Cadence Innovus的Tcl。尽管它们被广泛使用，但这些环境的脚本编写面临着通用LLM代码生成器无法解决的挑战。

\textbf{EDA scripting is fundamentally different.} Prior work on LLM code generation has succeeded in domains where correctness is verified by unit tests \cite{chen2021evaluating, austin2021program}. EDA scripting presents three distinct challenges: (i) APIs are long-tailed, tool-specific, and poorly documented; (ii) correctness depends on side effects in a live, stateful database, not return values; and (iii) the community lacks a standardized benchmark to evaluate whether generated scripts actually work. The first two are technical; the third is infrastructural.
% \textbf{EDA脚本根本不同。} 此前LLM代码生成的工作在可通过单元测试验证的领域取得了成功。EDA脚本编写面临三个不同挑战：(i) API长尾、工具特定、文档不完整；(ii) 正确性取决于实时有状态数据库的副作用，而非返回值；(iii) 社区缺乏标准化评测集来验证生成的脚本是否真正有效。前两个是技术性的，第三个是基础设施性的。

\textbf{Prior custom/analog scripting work stops short of execution.} Recent efforts like LayoutCopilot \cite{liu2025layoutcopilot}, ChaTCL \cite{rui2025chatcl}, and RAG-EDA \cite{pu2024rag} combine LLMs with static knowledge bases. Yet they all share a critical limitation: they do not execute generated code. Correctness is assessed by human judgment \cite{liu2025layoutcopilot, rui2025chatcl} or retrieval quality \cite{pu2024rag}, not by whether the script actually modifies a layout. Consequently, runtime errors remain undetected by construction, since no execution ever occurs, and the gap between "looks plausible" and "actually works" remains unbridged. Execution feedback is not itself new: in the digital flow, ChatEDA \cite{he2024chateda}, MCP4EDA \cite{wang2025mcp4eda}, AutoEDA \cite{lee2025autoeda}, and tool-feedback Verilog generation \cite{blocklove2024eda} close the loop against synthesis and place-and-route state. None of them, however, grounds against the live layout, schematic, or waveform database of custom/analog tools---the surface this paper targets.
% \textbf{已有定制/模拟脚本工作止步于执行。} LayoutCopilot、ChaTCL和RAG-EDA将LLM与静态知识库结合，但都存在关键局限：不执行生成的代码。正确性通过人工判断或检索质量评估，而非观察脚本是否真正修改了版图。因此，运行时错误在构造上就无法被发现——因为根本不发生执行——"看起来对"与"真正能用"之间的鸿沟始终未能弥合。执行反馈本身并非新事物：在数字流程中，ChatEDA、MCP4EDA、AutoEDA与工具反馈式Verilog生成已对综合与布局布线状态形成闭环，但都未触及定制/模拟工具的实时版图、原理图或波形数据库——这正是本文的目标面。

\textbf{The root problem: no benchmark, no progress.} Without a standardized benchmark, the community cannot systematically compare approaches or measure progress—each prior work uses task-specific tasks with different protocols. Recent concurrent benchmarks for Cadence Innovus Tcl flows \cite{xu2026iscript, li2026pdagent} confirm the growing recognition of this gap, yet they target specific flows within these toolchains and overlap only partially with the Tcl slice we study. A dedicated benchmark covering all four runtimes under a unified protocol remains absent.
% \textbf{根本问题：没有评测集，就没有进展。} 没有标准化的评测集，社区无法系统比较不同方法或衡量进展——每个已有工作使用任务特定的任务和不同协议。近期针对Cadence Innovus Tcl流程的同期评测集表明这一空白正被广泛认识，但它们针对的是这些工具链内的特定流程，与我们所研究的Tcl切片仅部分重叠。覆盖全部四个运行时、采用统一协议的专用评测基准仍然缺失。

\textbf{Our approach.} ZhuLong addresses the technical challenges through sandbox execution feedback—closing the loop from generation to execution to refinement—together with a \textbf{theoretical grounding} (Section~\ref{sec:grounding-theory}) that explains \emph{why} execution is necessary and an offline \textbf{API self-exploration mechanism} that enriches the prior as a complementary efficiency measure. It also supplies the missing infrastructure: \textbf{EDA-Scripting-Bench}, whose PyAether slice (\textbf{EDA-Eval-PyAether}) is the first standardized benchmark for PyAether scripting (Section~\ref{sec:benchmark}).
% \textbf{我们的方法。} ZhuLong通过沙盒执行反馈应对技术挑战——闭环从生成到执行到修正——辅以解释执行为何必要的理论基础（第~\ref{sec:grounding-theory}节）与作为互补效率措施的离线API自探索机制；同时补上缺失的基础设施：EDA-Scripting-Bench，其PyAether切片（EDA-Eval-PyAether）是首个标准化的PyAether评测集（第~\ref{sec:benchmark}节）。
