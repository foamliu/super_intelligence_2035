\section{System Design}
\label{sec:system}

\subsection{Overall Architecture}
\label{sec:overall-architecture}

ZhuLong is built on Cline-CLI \cite{cline2024cline}, an open-source framework for autonomous coding agents, extended with EDA-specific retrieval, documentation, and execution capabilities. Throughout, we call the resulting runtime an \textbf{ICL-type autonomous agent}: an agent that decides its own next action, keeps no explicit posterior, and maintains its belief state implicitly by in-context learning, as formalized in Section~\ref{sec:grounding-theory}. The choice is deliberate: our claims concern the harness---what the agent can observe and effect---rather than the agent policy, so the policy is kept commodity and unmodified, which is what makes any gain attributable to the interface; the runtime's permission and hook mechanisms also supply the enforcement points on which the fixed evaluation protocol relies (Section~\ref{sec:exp-setup}). As shown in Figure~\ref{fig:architecture}, the system comprises three components: the LLM-based agent runtime, the API knowledge base, and the EDA execution environment. The agent interacts with these components through four MCP tools, while an offline \textbf{API self-exploration mechanism} pre-augments the API knowledge base before runtime.
% ZhuLong基于Cline-CLI \cite{cline2024cline}构建，这是一个开源自主代码智能体框架，我们扩展了EDA特定的检索、文档查阅和执行能力。选择Cline-CLI是刻意为之：本文的主张关乎框架（智能体能观测什么、能执行什么）而非智能体策略，因此策略保持商品化且未作修改——任何增益才能归因于接口而非定制策略；该运行时的权限与hook机制同时提供了固定评测协议所依赖的执行点（第~\ref{sec:exp-setup}节）。如图~\ref{fig:architecture}所示，系统包括三个组件：基于LLM的智能体运行时、API知识库和EDA执行环境。智能体通过四个MCP工具与这些组件交互，离线\textbf{API自探索机制}在运行前预增强API知识库。

\subsection{Four MCP Tools}
\label{sec:mcp-tools}

The four tools jointly realize the observation channel $\Omega$ and the effector of Section~\ref{sec:grounding-theory}: \texttt{search\_apis}, \texttt{search\_apis\_\allowbreak by\_keyword}, and \texttt{get\_api\_details} return the environment's documented facts, while \texttt{run\_code} both acts on the design and reads back the result. ZhuLong implements them as MCP tools \cite{mcp2024protocol}, each accepting a unified \texttt{lang} and \texttt{host} parameter pair (\texttt{lang}: \texttt{pyAether}, \texttt{skill}, or \texttt{tcl}; \texttt{host}: \texttt{aether}, \texttt{virtuoso}, \texttt{waveview}, or \texttt{innovus}) that jointly selects the target runtime---\texttt{tcl} alone spans two hosts---so identical agent logic covers all four runtimes:
% 四个工具共同实现第~\ref{sec:grounding-theory}节的观测通道$\Omega$与执行器：search_apis、search_apis_by_keyword与get_api_details返回环境的已文档化事实，run_code既作用于设计、也读回结果。ZhuLong将它们实现为MCP工具 \cite{mcp2024protocol}，每个接受统一\texttt{lang}与\texttt{host}参数对（lang取pyAether/skill/tcl；host取aether/virtuoso/waveview/innovus），共同选定目标运行时——Tcl一个语言对应两个host——相同智能体逻辑覆盖全部四个运行时：

\begin{itemize}
    \item \texttt{search\_apis} retrieves relevant APIs by semantic similarity. We index APIs by name and description using BGE-M3 embeddings \cite{bge2024} with FAISS \cite{douze2024faiss} for efficient similarity search, returning the top-$K$ results above a similarity threshold ($K=5$, threshold $0.6$ by default) with scores and descriptions; keyword-based BM25 matches are merged in automatically as supplements when relevant.
    % \texttt{search\_apis}按语义相似度检索相关API。我们使用BGE-M3嵌入 \cite{bge2024}对API名称和描述建索引，FAISS \cite{faiss2017}支持高效相似度搜索，返回相似度阈值以上的top-$K$结果（默认$K=5$、阈值0.6），附带分数和描述；相关的BM25关键词匹配会自动并入作为补充。

    \item \texttt{search\_apis\_by\_keyword} retrieves APIs by explicit keyword matching (CamelCase token overlap plus BM25 description match), complementing semantic search when the agent already knows a name fragment or abbreviation (e.g., ``CV'' for \texttt{dbOpenCV}); each result is annotated with its match provenance.
    % \texttt{search\_apis\_by\_keyword}通过显式关键词匹配检索API（CamelCase词元重叠加BM25描述匹配），当智能体已知名称片段或缩写时（如用``CV''查\texttt{dbOpenCV}）补充语义检索；每个结果标注其匹配来源。
    
    \item \texttt{get\_api\_details} fetches comprehensive documentation for a list of APIs, including parameter types, return values, and examples. The returned documentation is augmented by the offline API self-exploration mechanism (Section~\ref{sec:selfdoc}) when available, enriching incomplete specifications with constraints and usage patterns discovered via sandbox exploration.
    % \texttt{get\_api\_details}获取一组指定API的完整文档，包括参数类型、返回值和示例。当可用时，返回的文档由离线API自探索机制（第~\ref{sec:selfdoc}节）增强，补充通过沙盒探索发现的约束和使用模式。
    
    \item \texttt{run\_code} executes generated code in an isolated, headless EDA sandbox and reads back a structured result---execution status, error log, captured stdout, and the code's return value---for iterative refinement. The sandbox dispatches on the \texttt{lang}--\texttt{host} pair: resident PythonE workers for PyAether/Aether, batch-mode \texttt{virtuoso -nograph} workers for SKILL/Virtuoso, one-shot \texttt{wv -ace\_no\_gui} processes for Tcl/WaveView, and a resident Innovus REPL for Tcl/Innovus, uniformly exposing execution feedback across all four runtimes. An optional \texttt{probe} flag pre-checks type and import errors before full execution.
    % \texttt{run\_code}在隔离的无头EDA沙盒中执行生成的代码，并回读结构化结果——执行状态、错误日志、捕获的标准输出与代码返回值——供迭代优化使用。沙盒按\texttt{lang}--\texttt{host}对分发：PyAether/Aether走常驻PythonE worker，SKILL/Virtuoso走批处理模式\texttt{virtuoso -nograph} worker，Tcl/WaveView走一次性\texttt{wv -ace\_no\_gui}进程，Tcl/Innovus走常驻Innovus REPL，在全部四个运行时上统一暴露执行反馈。可选\texttt{probe}标志在完整执行前预检类型与导入错误。
\end{itemize}

\subsection{Agent Workflow}
\label{sec:agent-workflow}

The agent iteratively refines its output through execution feedback \cite{cline2024cline}. A typical trajectory begins with reasoning over the user instruction, followed by API retrieval via \texttt{search\_apis} when needed. Candidate APIs are then inspected via \texttt{get\_\allowbreak api\_\allowbreak details}, and code is generated accordingly. The agent executes the code via \texttt{run\_code}, observes the result, and re-plans—revising the code, retrieving alternative APIs, or terminating. This loop continues until success or the agent determines further attempts are unlikely to succeed. The agent is not constrained to a fixed sequence; it may skip retrieval when it already knows the required API, or conduct multiple rounds of retrieval when initial results lack confidence.
% 智能体通过执行反馈迭代优化其输出 \cite{cline2024cline}。典型轨迹始于对用户指令的推理，需要时通过\texttt{search\_apis}检索API，然后通过\texttt{get\_api\_details}查阅候选API的文档，据此生成代码。智能体通过\texttt{run\_code}执行代码、观察结果并重规划——修改代码、检索替代API或终止。此循环持续至成功或智能体判断继续尝试不太可能成功。智能体不受固定序列约束——已知所需API时可跳过检索，初始结果置信度不足时可进行多轮检索。

\subsection{Offline API Self-Exploration (Complementary)}
\label{sec:selfdoc}

EDA API documentation is often incomplete, omitting parameter constraints, return structures, and error conditions. Prior work addresses these gaps through retrieval-based augmentation \cite{pu2024rag} or static knowledge graphs \cite{liu2025layoutcopilot}---both of which rely on what is already documented. As the theoretical framing of Section~\ref{sec:grounding-theory} makes precise, such mechanisms enrich only the L1--L3 facts the observation channel can return; they are therefore complementary to---and bounded by---the observation of L4 that requires acting on the live design. We accordingly position self-exploration as an efficiency and robustness mechanism, not as the primary accuracy driver.
% EDA工具的API文档往往不完整，省略参数约束、返回结构和错误条件。已有工作通过检索增强或静态知识图谱弥补文档缺口，但两者都依赖已有文档。
% 正如第~\ref{sec:grounding-theory}节的理论框架所指出的，这类机制只能丰富观测通道可返回的L1–L3事实；
% 因此它们相对"通过作用于实时设计来观测L4"是互补且有界的。我们将自探索定位为效率与鲁棒性机制，而非精度主驱动。

ZhuLong instead \textbf{proactively discovers} API behaviors through offline counterfactual experimentation in the sandbox. For each target API, the exploration agent reads available documentation, identifies gaps---e.g., unspecified parameter ranges, undocumented return fields, or ambiguous error semantics---and generates targeted test scripts to probe them. It executes these scripts via \texttt{run\_code}, observes outcomes, and iteratively refines a behavioral model of the API capturing parameter constraints, return structures, error conditions, and side effects. The exploration agent autonomously decides what to test next and when to stop, based on its current confidence. This offline process runs once per API; the enriched documentation is stored in the knowledge base and served at runtime via \texttt{get\_api\_details}, incurring no runtime overhead.
% ZhuLong转而通过沙盒中的离线反事实实验主动发现API行为。对每个目标API，探索智能体阅读现有文档、识别缺口、生成针对性测试脚本，通过run_code执行并观察结果，迭代细化API行为模型。探索智能体自主决定测试内容与停止时机。该离线过程每个API运行一次，增强文档存入知识库，运行时通过get_api_details提供，无额外开销。

\textbf{Implementation and cost.} The exploration agent targets the union of (i) APIs referenced by EDA-Eval-PyAether tasks and (ii) APIs whose official documentation omits at least one of parameter ranges, return types and structures, or error conditions. Each API is assigned a confidence score that accumulates the information gain of each probe; exploration terminates when the score exceeds threshold $\tau$, when two consecutive rounds contribute no new discriminated constraint, or when a per-API execution budget $M$ is exhausted. Generated test scripts are gated by EDA domain experts before execution to filter destructive operations, and discovered constraints are sanity-checked against vendor documentation where available. Exploration is thus a one-time offline cost per API that pays for itself at runtime: as Table~\ref{tab:cost} shows, removing the enriched documentation makes the agent both slower and more token-hungry per task.
% 实现与成本。探索以评测任务引用的API和官方文档缺失关键信息的API的并集为目标。每个API维护置信度分数，按每次探测的信息增益累积；当分数超过阈值、连续两轮无新增可判别约束、或单API执行预算耗尽时停止。生成的测试脚本在执行前经专家把关过滤破坏性操作。探索为每个API一次性的离线成本，且在运行时收回投资：如表~\ref{tab:cost}所示，移除增强文档后每任务的求解时长与token消耗均上升。
