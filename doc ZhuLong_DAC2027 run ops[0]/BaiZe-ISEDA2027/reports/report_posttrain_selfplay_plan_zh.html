0 首屏结论

表态：【部分同意】——方向对、优先级排序错。我支持把 L1（expert iteration / verifier 过滤回灌）与环境内多轮探索作为 pretrain ckpt（ETA 2026-12-25）之前的方法论预演主臂；反对把 L2/L3 self-play 与"2B 自进化"写成 ISEDA §5 的主结果；反对在生成器闸门 G0/G1/G2 未通过之前起任何 GRPO run（否则就是第三次"换个说法再跑一次"）。
三句话
① 这套方案里真正新的只有闸门①（canonical_solution 在沙盒真跑 PASS）。本地证据显示：现有 3,347 条合成 RL 题在 R128 静态审计中 V1–V6 全部 100% 通过、可解性分数全为 1.0，但它们从未被执行验证过（R128 的 "canonical validity" 只做 AST 解析）。"静态自洽但跑不通"的题正是 R2 训练 reward 里的纯噪声。这一条判"保留，且应作为零 GPU 成本的第一步先做"。
② 但方案 80% 的工作量押在"造更多题"，而本地证据指向的瓶颈不在题量。158 题的失败结构里 28.5%（45 题）是"静默不进入 agent 回路"、23.4%（37 题）是 protocol_fixable（r83 + 36.15 再归因）；这两块合成题解决不了，只有环境/ACI 修复能触及——而全项目目前唯一统计显著的正向结果（+3.80pp，McNemar p<0.001）恰好来自环境修复，不是来自任何权重更新。
③ R0/R2 的教训不是"GRPO 不行"，而是"奖励与评测未对齐 + 零方差"。若不先补上难度带闸门（p̂∈[0.18,0.82]）与奖励对齐审计（partial credit 与 full pass 的 Spearman ρ），这套方案会第三次落在同一处：训练 reward 涨、评测 Pass@1 跌。
K1 生成器可用性n=200 题，六闸全过率 ≥50%；其中 canonical 真跑可解率 ≥90%、4 个负例（含 near_miss）拒绝率 ≥95%、近重率 ≤10%。这是"能不能规模造题"的唯一判据。
K2 训练池可学带p̂∈[0.18, 0.82]（零方差步 ≤20%）。当前 158 实测反解 p̂=6.6%（由 R2 的 84/200 信号步反推），离可学带差 3 倍。
K3 主结果判据158 题 5-run，Δ≥+2.0pp 且 McNemar p<0.05。当前唯一显著正向仍是环境修复 +3.80pp（p<0.001）。

K3 的 +2.0pp 是算术推导（5-run 均值的 SE≈0.90/√5=0.40pp，配对设计下 Δ≈2pp 可达 ~80% power），不是实测；正式 MDES 必须由 python3 baize_posttrain_stat_power_analysis.py --n-tasks 158 --n-runs 5 --json 落盘，见 §9 TODO-4。

1 思路复述 + 逐条判断（A–G）

待评审方案（下文 A–G 为原文编号）：A 用 158 题当种子（只用 API 组合模式/场景×类目×难度轴/执行形态，不复制 prompt 文本与断言）让 LLM 生成大量新题；B 新题过四道闸门（canonical 真跑 PASS / 3 个 NEG 全 FAIL / 三重去重 / hidden-B 换参数双测）；C agent 在 EDA 环境内探索（RAG → 写码 → run_code → 读 check.py 逐条断言 → 修 → 重跑），过程信号用"Δ断言通过数"；D 三档 self-play（L1 expert iteration / L2 非对称自博弈 ASP / L3 对抗验证器）；E 按执行成本三档分层；F 先做 MV（生成 100 题，四闸全过率 ≥60% 才判定生成器可用）；G 已知坑（Alice 出退化题、过拟合合成分布、沙盒非确定性、reward hacking）。

条判断理由（依据必须可追）
A修改后保留保留：以真实题当"目标锚点"再生成同族新题，是当前唯一可能把 p 抬进可学带的路径，且有直接文献支持（GASP 明确指出无锚定的非对称自博弈"goal-agnostic"，必须用真实难题当 goalpost；SPICE 证明"语料/环境 grounding"是自博弈持续有效的关键）。
必须修改：①种子的字段要白名单化并落盘，只允许 scenario / category / num_apis 分箱 / loc 分箱 / API 名集合 / 目标 fail_mode，禁止 prompt 文本、test_code、模型在 158 上的逐题 pass/fail（后者一旦进训练就是"用评测标签训练"，红线①的实际破口）；②"不构成近重"必须给出数值而不是声明——落盘三项：8-gram 重叠率、embedding 余弦（要写模型名与阈值）、断言 AST 签名碰撞率；③生成前必须按 r83 的 fail_mode 配额定目标（none 59 / semantic 45 / infrastructure 22 / api_misuse 17 / timeout 12 / protocol 3），否则会生成一堆模型本来就会的题（见 §1.1 Q2）。
B保留 + 加两闸这是全方案最有价值的一条：闸门①（oracle 真跑）恰好补上现有 3,347 题从未做过的检查——R128 报告里 V2 "canonical validity" 只是 ast.parse 通过，不是沙盒执行通过（run/r128_quality_audit_report.json + baize_posttrain_r128_solvability_verifier.py 文件头 V2 描述）。
必须修改三点：
① oracle 闸门要去抖：已知沙盒非确定性（同代码 direct 2/79 vs rescue 0/79），单次 PASS 不足以判可解 ⇒ 连跑 3 次取多数，记录 per-task flaky 率，flaky 题直接不入库（否则把噪声直接注入 reward）；
② NEG 要加第 4 个、而且是最危险的那个："近似成功解"——复制 canonical 但删/改一个参数。R2 的教训是"能跑就给分"，因此最危险的负例是"几乎对"，而不是空壳/只 print；
③ 要新增两道闸门（原四闸全过 ≠ 能训练，R128 就是 100% 全过却训练失败的反例）：G5 难度带闸门（p̂∈[0.18,0.82]，见 §3.4）与 G6 分布对齐闸门（合成池与 158 在 scenario×category×num_apis 上的 JS 散度 ≤0.20，落盘数值）。
C否决一半否决"读 check.py 逐条断言"，理由三条：①与冻结评测协议分布失配——158 评测里 agent 看不到 test_code（check 由 harness 事后跑，且 designflow 的 PreToolUse hook 明确禁止按 case_id 反查源码），训练期可见、评测期不可见 = 训练一个评测时用不上的能力；②它本身就是捷径：等价于训练"看断言 → 反推返回值"，与红线②(anti-cheat) 精神冲突，也会让论文里"anti-cheat hook 常开"的说法被审稿人直接质疑；③会污染 L3 的结论（见 D 条）。
改法（blind verifier）：环境只回传 (pass/fail, 首个失败断言的序号, traceback 文本)，不返回断言源码；"断言可见"降级为消融臂 B1，若 B1 增益 >5pp 且无法迁移到 blind，则判定为 shortcut 并从主表剔除。
"Δ断言通过数"：保留但降级用途——只用于 L1 的过滤/回灌与课程排序，不作为 GRPO 的 advantage 来源（R2 的加权部分分已被证伪：proxy 涨、eval 跌）。若一定要进奖励，先过"奖励对齐审计"：在 dev 上算 (partial_credit, full_pass) 的 Spearman ρ，要求 ρ≥0.60 且 partial-credit 最优策略不能是"多写 assert 计数"。这个审计 R0/R2 都没做，是本方案最该补的一个实验。
DL1 保留 / L2 改判据 / L3 否决L1 保留（最高性价比）：STaR 式自举与 RFT 在稀疏正确率下有效，且 RFT 原文明确"能力更弱的模型从 RFT 获益更多"，正对本线 3–7% 的处境。
L2 保留但必须换 Alice 的奖励：原设计"Alice 奖励 = Bob 失败 ∧ 题可解"会稳定走向退化——2026 年两项工作直接给出这个失败证据：SGS 证明 Conjecturer 会 reward hack 成"人为复杂但对 Solver 无用"并导致学习平台期；ANCORA 证明"稀疏 verifier 反馈会让 Proposer 崩溃，即使奖励已对齐"，必须靠 manifold/SFT 投影 + curriculum DAG 等稳定器。因此 Alice 奖励改为合取式：Bob 失败 ∧ 可解（oracle 3 次多数）∧ 落在 158 目标 fail_mode 配额内 ∧ 与目标分布 JS≤0.2（即 PAIRED 的"regret vs goalpost"思路）。
L3 否决为训练臂，降级为 QA 工具：①改 verifier 是 designflow 的职责（AGENTS §7.1），posttrain 无权改判分口径；②verifier 与 policy 共同漂移会破坏"同一把尺子"红线，产出的数字不可比。L3 的产出只能是"发现的漏洞 → 交回 designflow → 修完的题重新入池"，该轮实验作废重跑。
E保留 + 加配额分层是对的（沙盒成本差 3 个数量级：默认 timeout 60s、评测单题上限 2500s）。但会产生"成本—难度"混杂：便宜题（query 类）天然更容易，按成本采样会让训练集偏向易题，p̂ 虚高、迁移不出去。要求：分层配额 + 层内分别报通过率，禁止只报总体 p̂。
⚠️ "query 类百 ms"目前无实测依据（本地只有 60s 默认 timeout 常量，没有分档延迟分布）⇒ 见 §9 TODO-1。
F判据要改"全过率 ≥60% 才可用 / <40% 退回 L1"这个门可以保留方向，但单指标定位不到瓶颈，且 n=100 时 60% 的 95%CI 约 ±9.6pp，判据噪声太大。改为四指标分别设阈（任一不过即退回）：可解率 ≥90%（硬门，过不了说明生成器写不出能跑的参考解）、3+1 负例拒绝率 ≥95%、近重率 ≤10%、p̂∈[0.18,0.82]；n 提到 200。另外MV 的第一枪应该打现有池而不是新池：见 §5 的 MV0。
G覆盖不足四个坑都点到了，但机制层面缺三样：①"沙盒非确定性"只写了"已知"，没写处理机制（→ 3 次多数 + flaky 率 + 剔除）；②"reward hacking"只靠 8-gram 查不到"硬编码返回值 / 按 case 反推 / 读断言"，必须加 hidden-B 参数化双测 + 返回值硬编码检测 + cheat_rate 每轮报；③缺"训练-评测分布偏移"的量化（G6）与难度漂移监控（每轮重估 p̂，若 p̂→0.9 说明题已太易、课程失效）。

1.1 直接回答四个必答问题

Q1 这套和已失败的 R0/R2 有本质区别吗？会不会又是"换说法再跑 GRPO"？
答：有三个潜在的本质区别，但一个都没自动成立，必须用闸门钉死。

  1. 奖励来源的"可瞄准性"变了：R0 是纯文本静态打分（proxy）、R2 是"执行成功=0.2"（proxy），本方案主信号是 check.py 全过（binary，verifier 与评测同族）。这是真正的区别——但只有在 C 条按我的修改执行（blind verifier、部分分不进 advantage）时才成立。
  2. 任务分布变了：R0/R2 训练池 p̂≈6.6%（反解，见 §2.2），约 58% 的 GRPO 步是零方差死步。本方案把 p̂ 推到 0.18–0.82 是直接对 R2 死因下药。若做不到（MV 判据不过），则没有区别，应直接取消。
  3. 单步内信息量变了：多轮 RAG+run_code+读 traceback 修正，把"一次生成定生死"变成"序列决策"，这是 ReTool / Search-R1 一族在有工具任务上成立的核心机制。但 158 评测里 agent 本来也是多轮的，所以这条只是"训练与评测形态对齐"，不是白送增益。

结论：设 Gate-0——上述第 1、2 条未以落盘数值证明之前，禁止起任何 GRPO run。此条预注册，不接受事后放宽。

Q2 在 158 只有 3–7% 通过率的现实下，合成题池能不能把 p 抬到 ≥0.2？
答：p_synth 抬到 ≥0.2 几乎必然（题是模型自己出的、难度可调），但这不是证据。必须分清三个 p。

量含义我的判断
p_158在 158 上的 Pass@1（唯一可报的数）3.04%（.17 口径）/ 6.84%（36.15 口径，含 run1 18.99% 锚点 outlier；剔除后 recovered 4-run = 3.80%±0.90%）。这是分母，动不了。
p_synth在合成池上的 Pass@1目标带 [0.18,0.82]。高 p_synth 不蕴含高 p_158——R2 已经演示过"训练侧涨、评测侧跌"。
p_transfer训练增益迁移到 158 的比例未知，且这是整个方案的生死线。历史先验不乐观：R2 = −2.56pp（负迁移）；vision 线 GRPO 相对 RFT2 = −3.3pp、McNemar p=1.0（不显著）。

我的量化判断：不靠合成题池、仅靠结构性修复（ACI / protocol / hook），p_158 的结构性可动上限约为 (45 静默 + 37 protocol_fixable) / 158 ≈ 52% 的失败样本；若修好其中一半，p_158 有望从 3–6.8% 到 10–15%。要到 ≥20% 必须叠加"多轮工具使用能力"的真实提升——那是 L1/L2 的目标，不是造题本身的目标。所以"造题"是手段，"进回路 + 会用工具"才是 p 上行的直接原因；计划必须以 ACI 臂为对照，否则无法归因。

Q3 出题器（Alice）用 2B 还是先用 DeepSeek？2B 出不了合格题，"小模型自进化"叙事是否就破了？
答：主实验必须用 DeepSeek（外部强教师）；2B-as-Alice 单独做一个小实验，并把结论写成"proposer 能力门槛"，而不是让叙事悬空。

  • 能力论证：出题比解题难——出题者要同时写出 prompt、可执行的 test_code、与之对齐的 canonical_solution，三者互相约束。当前 2B 解题通过率 3–7%，让它同时产出"能跑通的参考解 + 能判对的断言"，六闸全过率我预计 <20%（这是预测不是实测，见 §9 TODO-8）。
  • 决策规则（预注册）：2B-as-Alice 出 50 题（20 个种子上下文），若可解率 <40% 或 负例拒绝率 <80% ⇒ 判定"2B 不能承担 proposer"，主实验固化为 教师-学生（DeepSeek → 2B）设定。
  • 叙事不破，反而更强：论文可写"小模型自博弈的 proposer 能力门槛"——即"自进化是否需要 proposer 达到某能力阈值"的实证。这比含糊声称"2B 自进化"更站得住，也正面回答审稿人必问的"proposer 太弱会不会自己出废题"。若 2B 真能过闸，那也是正面结论。
  • 可行性警告：DeepSeek 走 agi-gateway.cxmt.com 云通道（deepseek-v4-pro-cloud）。本线历史上出现过 30 题 batch 里 19 个 error/timeout（EXPERIMENTS §L4.10）的 infra 故障 ⇒ 按"infra ≠ 能力"原则那批 0% 不能当能力证据，但也说明云通道必须先跑 20 题 smoke（可用率 ≥95%）才能当生成器；同表里 82.1%±3.0% 与 0%（30 题）两个数字口径冲突，见 §9 TODO-3。

Q4 在 pretrain ckpt ETA 2026-12-25 之前，这套的产出对 ISEDA §5 有什么用？主结果还是方法论预演？
答：如实说——是方法论预演 + 生成器可行性证据，不是主结果。

  • 不能是主结果：基座是 MiniCPM5-2B + SFT v39 step105，按 AGENTS §4.4 与 baize_posttrain_rl_grpo_loop.py 文件头红线，其结论必须标注"替身预演，收益不可迁移到 BaiZe"；论文 §5 主表必须是 BaiZe ckpt 上的 anneal/SFT/RL。
  • 能做的事很有价值：① 先把"有效后训练方法"的判据体系与工具链立起来（难度带反解、奖励对齐审计、blind verifier、cheat_rate、5-run 配对检验）；② 决定 ckpt 到达后跑哪两个臂（全臂上 GPU 时间不够，必须提前筛）；③ 题池与生成器不依赖基座，可跨模型复用 ⇒ 这 5 周的造题工作不会随 ckpt 到达而作废，这是它相对纯 GRPO 预演的最大优势。
  • 论文写法：放进 sec:posttrain-rl 作方法学小节（题池构建 + verifier 对齐 + 零方差控制），把"哪种后训练对 2B EDA 脚本有效"的结论留到 ckpt 之后。若 5 周内拿到"ACI 臂 vs 权重更新臂"的显著差异，本身就是可写发现。

2.2 三条必须直接面对的既有结论

(1) R2 不是"GRPO 不行"，是"奖励可被非目标方式满足"——而且可以算出来。

R2 的奖励定义（baize_posttrain_reward_functions.py L22/L313-322）：exec_success=0.2 打底，每过一条 assert 再加 0.2，全过 1.0。R2 实测 overall reward mean = 0.0901。若把总奖励拆开看，0.0901 / 0.2 ≈ 45% 的 rollout 拿到的是"恰好 0.2"——即代码跑起来了、但一条断言都没过。这解释了为什么训练 reward 能从 0.053 涨到 0.111（学会"写不抛异常的代码"）而评测 Pass@1 掉到 0.475%（"能跑"与"判对"无关）。⚠️ 该拆解是算术推算（分母 0.2 是代码里的常量），尚未对 metrics.jsonl 的 per-rollout 分布做核验 ⇒ §9 TODO-5。若核验不成立，结论"proxy 未对齐"仍由"train↑ eval↓"独立支撑。

(2) 零方差是可以从日志反解的，这就是我们要的难度尺。

GRPO 的 advantage 是组内标准化 A_i = (r_i − mean_g)/(std_g + eps)（rl_grpo_loop.py L385）。组内 8 条全零 ⇒ std_g=0 ⇒ 该组 8 条 advantage 全为 0，这一步等于白跑。

  • p=3.04% ⇒ (1−p)^8 = 78.1% 的步是死步；p=6.84% ⇒ 56.7%。R2 实测 58% ⇒ 反解 p̂ = 1 − 0.58^(1/8) = 6.6%，且与 84/200=42% 的有信号步一致。
  • 更糟的是活着的步也不干净：p=3.04% 时，"组内恰好 1 条成功"的概率 = 8×0.0304×0.9696⁷ ≈ 19.6%，占 21.9% 有信号步的 90%。此时该成功样本的 advantage = 0.875/0.3308 = +2.645，其余 7 条 −0.378。本质退化成"模仿一条幸运样本"，而 EDA 任务的"幸运通过"很可能是断言太弱。
  • 结论：p 在 3–7% 时 GRPO 的设计前提（组内有区分度）根本不成立。要它成立，p 必须进 [0.18,0.82]（p=0.18 ⇒ 死步降到 20.4%）。这不是调参能解决的，只能改任务分布或把 1 次生成改成多轮修正——这正是本方案 A/C 两条的价值，也是我唯一支持它们的理由。

(3) 静态闸门全过 ≠ 题能训练：R128 是现成的反例，也是现成的机会。

现有 3,347 条合成题在 R128 里 V1–V6 全 100% 通过、solvability 全 1.0，但它们从未被执行验证（V2 只查 AST 可解析）。R0 用这个池 + proxy 奖励 ⇒ 塌缩；R2 用这个池 + sandbox 奖励 ⇒ 负迁移。所以：

  • 对方案的启示一：把"全过率"当生成器判据是已经被证伪过一次的指标，必须加 G5（难度带）/G6（分布对齐）。
  • 对方案的启示二（机会）：MV 的第一步不必造新题——对现有 3,347 条抽样 100 条跑 canonical（3 次多数），零 GPU、数小时，就能回答"我们的合成题到底能不能跑通"。若可解率 <90%，说明生成器的问题早就存在，应先修生成器而不是扩大产量。这就是 §5 的 MV0，我建议作为第一个执行动作。
  • 启示三：API 覆盖已 70.11%（5,933/8,463）⇒ "造题"的边际价值不在覆盖 API，而在多 API 组合 / 真实工作形态 / 难度可控 / 可执行 verifier。方案的立论应改成这一点，别再说"补 API 覆盖"。
